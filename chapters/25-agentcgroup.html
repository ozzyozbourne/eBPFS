Chapter 25

AgentCgroup: understanding and controlling the OS resources of AI agents

A coding agent spends most of a task idling at about 185 MB while the model thinks. Then it runs pytest, and for one or two seconds the container needs gigabytes. If the container limit is set to the peak, most of that memory sits unused. If it is set lower, the OOM killer can wipe out ten minutes of LLM context. This chapter covers what the AgentCgroup study measured about such workloads, and how its prototype gives every tool call its own cgroup and pushes the priority decisions into the kernel with eBPF.

Why this matters

AI coding agents such as Claude Code, OpenHands and SWE-agent run a loop. The model reasons, emits a tool call, the framework runs it (often as bash -c "…" inside a sandbox container), and the output goes back to the model. Providers now run many such sandboxes side by side on shared machines. Each one is a Linux container, and Linux containers are governed by cgroups: the kernel mechanism that accounts for and limits the CPU, memory, I/O and process count of a group of tasks.

Cgroup limits were designed for workloads whose demand is roughly known: a web service with a steady footprint, a batch job that grows with its input, a serverless function that lives for a second. The AgentCgroup paper (Zheng et al., arXiv:2602.09345) asks whether agent sandboxes look like any of these. Its answer is no. Agent memory has a flat baseline with short, tall spikes caused by tool calls, and the size and timing of those spikes change from task to task and from run to run. Killing an agent is also unusually expensive: the in-process conversation state cannot be checkpointed, and a rerun takes a different path.

The repository (eunomia-bpf/agentcgroup) contains both halves of the paper: the raw traces and analysis scripts behind the characterization, and agentcg/, a proof-of-concept controller built from a bash wrapper, a Python daemon and three eBPF components.

Key idea

Make the cgroup tree follow the agent's structure. Each agent session is a cgroup, and each tool call becomes a short-lived child cgroup created by a wrapper that replaces /usr/bin/bash. Priority between sessions is enforced inside the kernel: a sched_ext scheduler (scx_flatcg) shares CPU by cgroup weight, and a memcg_bpf_ops struct_ops program (from an RFC kernel patch series) shields the high-priority session from reclaim and adds a throttle delay to low-priority sessions. The agent can also hint at what a command will need (AGENT_RESOURCE_HINT), and after an OOM kill it gets a plain-English explanation on stderr.

This chapter is about resources. Observing agents is the topic of chapter 23 (AgentSight), and AgentCgroup's process monitor comes from that code base. Enforcing information-flow policies is the topic of chapter 24 (ActPlane).

cgroup v2 for programmers

You only need a small part of cgroup v2 to follow this chapter. All of it is in the kernel's Control Group v2 document.

A tree of directories

cgroup v2 is a single hierarchy mounted at /sys/fs/cgroup. A cgroup is a directory. You create one with mkdir and remove an empty one with rmdir. You move a process into a cgroup by writing its PID to that cgroup's cgroup.procs file. Children forked afterwards start in the same cgroup. Everything else is a control file in the directory.

Controllers (cpu, memory, io, pids, …) are switched on per subtree. The kernel documentation says "No controller is enabled by default". A parent turns them on for its children by writing to cgroup.subtree_control:

# echo "+cpu +memory -io" > cgroup.subtree_control

One rule surprises most people. The no internal process constraint says a non-root cgroup can hand domain resources (such as memory) to its children only when it has no processes of its own. Processes live in the leaves, and the inner nodes only distribute. Keep that in mind when we read the wrapper's clean-up code later.

The four controllers that matter here

cpu

cpu.weight: proportional share among active siblings, range [1, 10000], default 100. cpu.max: a bandwidth cap, written as "$MAX $PERIOD", default "max 100000". The docs note that these files affect the fair class and "a BPF scheduler with the cgroup_set_weight callback".

memory

Two protections (memory.min hard, memory.low best effort) and two limits (memory.high throttle, memory.max hard). Observability: memory.current, memory.peak, memory.events, memory.pressure.

io

io.weight (default "default 100", per-device overrides keyed by MAJ:MIN) and io.max (BPS/IOPS caps). AgentCgroup does not use io.

pids

pids.max is a hard cap on the number of processes in the subtree. pids.current and pids.peak report usage. AgentCgroup does not use pids either. Its prototype manages CPU and memory.

memory.min, low, high, max

These four boundaries are the core of the memory story, so here they are in the kernel doc's own terms:

  • memory.min: "Hard memory protection". Memory within the effective min boundary "won't be reclaimed under any conditions".
  • memory.low: "Best-effort memory protection". Below it, the cgroup's memory is reclaimed only when no unprotected memory is left.
  • memory.high: "Memory usage throttle limit". Above it, "the processes of the cgroup are throttled and put under heavy reclaim pressure". Going over it "never invokes the OOM killer". The kernel adds a sleep (a penalty delay) on the way back to user space for tasks that allocate past it.
  • memory.max: "Memory usage hard limit". If usage reaches it and reclaim cannot help, "the OOM killer is invoked in the cgroup".

memory.peak is the high-water mark for the cgroup and its descendants since it was created, which is exactly what you want for a cgroup that lives as long as one command. memory.events counts how often each boundary was hit (for example high, max, oom_kill). memory.oom.group makes the OOM killer treat the cgroup as one unit. cgroup.freeze stops every process in a subtree, and cgroup.kill SIGKILLs every process in it.

PSI: measuring the pain

Pressure Stall Information (kernel doc) reports how much time tasks spent waiting for a resource. Each cgroup has cpu.pressure, memory.pressure and io.pressure with lines like

some avg10=0.00 avg60=0.00 avg300=0.00 total=0
full avg10=0.00 avg60=0.00 avg300=0.00 total=0

some is the share of time at least one task was stalled. full is the share of time all non-idle tasks were stalled at once. total is the cumulative stall in microseconds. User-space OOM daemons such as oomd and systemd-oomd watch these files and kill a cgroup when pressure stays high. AgentCgroup's fallback controller reads total too, as you will see.

Where eBPF comes in

Chapter 05 covered the classic cgroup BPF programs (cgroup/connect4, cgroup/dev, cgroup_skb, …). Those are allow/deny hooks. They cannot change how much CPU or memory a cgroup gets. AgentCgroup uses two newer mechanisms based on struct_ops instead, both also introduced in chapter 05:

  • sched_ext (kernel doc, LWN): the whole CPU scheduling policy is a BPF struct sched_ext_ops. If the BPF scheduler misbehaves, the kernel falls back to the default scheduler. It is in mainline since 6.12.
  • memcg_bpf_ops: a struct_ops for the memory controller, proposed by Hui Zhu in the RFC series "mm: memcontrol: Add BPF hooks for memory controller" (v3 on LWN, v6 on lore). It is not in mainline: when we checked on 2026-11-06, mm/bpf_memcontrol.c on torvalds/master had no memcg_bpf_ops. The repository ships the v6 series as agentcg/memcg/patches.mbox.

The characterization study

The first half of the paper is a measurement study. Everything in this section comes from the paper's v3 text (§3, §4) unless another path is given.

What was measured

The workload is Claude Code solving tasks from SWE-rebench (Badertdinov et al., 2025), a continuously collected, decontaminated set of real GitHub issues with ready-made Docker images. Each task ran in its own Podman container from the official image (2.9–17.3 GB) with no resource limits. Claude Code was bind-mounted from the host. Two model back ends were used: Claude Haiku 4.5 through the cloud API, and GLM-4.7-Flash on a local GPU. The paper counts 111 GLM tasks and 33 Haiku tasks; the Haiku tasks are a subset of the GLM ones, so cross-model comparisons use the overlap. The machine was an Intel Core Ultra 9 285K (24 cores, 128 GB DDR5) running Ubuntu 24.04 with Linux 6.15.11 and cgroup v2.

CPU and memory were sampled once per second, and each tool call's type and timestamps were recorded. In the repository the sampler is a thread in scripts/run_swebench.py that shells out to podman stats:

    def _get_sample(self) -> Optional[dict]:
        """Get a single resource sample."""
        try:
            result = subprocess.run(
                ["podman", "stats", "--no-stream", "--format",
                 "{{.MemUsage}}\t{{.MemPerc}}\t{{.CPUPerc}}", self.container_id],
                capture_output=True, text=True, timeout=5
            )
            if result.returncode == 0 and result.stdout.strip():
                parts = result.stdout.strip().split('\t')
                if len(parts) >= 3:
                    return {
                        "timestamp": datetime.now().isoformat(),
                        "epoch": time.time(),
                        "mem_usage": parts[0],
                        "mem_percent": parts[1],
                        "cpu_percent": parts[2]
                    }
        except Exception as e:
            pass  # Container may have stopped
        return None

Two consequences follow. The data is per container, not per tool call. And a burst shorter than a second can be missed or blurred. The repo's own Chinese-language summary (analysis/data_analysis_summary.md) points this out and suggests 100 ms sampling as future work. Each task directory under experiments/all_images_haiku/ and experiments/all_images_local/ holds trace.jsonl, resources.json, tool_calls.json, results.json and a plot (experiments/README.md).

Three mismatches

The paper compares these properties with serverless (Azure Functions, Shahrad et al., ATC '20), microservice/VM and batch workloads, and names three ways in which today's controls do not fit:

Granularity

Demand varies per tool call, but limits are set per container. Setting memory.max to the peak "wastes over 90% of allocated memory"; setting it near the average OOM-kills tool bursts. A single memory.high cannot tell git status (13.5 MB) from pytest (518 MB P95).

Responsiveness

Bursts last 1–2 s and arrive at unpredictable times. A PSI-driven daemon needs a signal, a wake-up, a decision and a control-file write; the paper puts that loop at "tens of milliseconds", by which time the burst may be over or the kernel has already intervened. PSI is also per cgroup, not per tool call.

Adaptability

History-based sizing (Borg, Autopilot, Kubernetes VPA) assumes repeatable demand. Agents vary 1.8× between runs of the same task, and killing and restarting one loses all its context and takes a different path. The paper argues for degrading gracefully (throttle, freeze) instead of killing.

The insight behind the design is that agents, unlike a web server, can read English. They can state their intent before a command and change strategy after a failure. The controller can use both.

Architecture

The paper's §5 maps the three mismatches to three mechanisms: fine-grained resource domains (a cgroup per tool call) for granularity, in-kernel eBPF enforcement for responsiveness, and intent-driven coordination (hints up, feedback down) for adaptability. The code in agentcg/ implements them with five parts:

Mapping tool calls to cgroups: the bash wrapper

How do you learn where one tool call starts and ends without modifying Claude Code? AgentCgroup's answer: almost every agent framework runs shell commands as bash -c "<command>". So rename the real bash to /usr/bin/real-bash and install a script as /usr/bin/bash. Every -c invocation is then a tool call. Interactive shells and scripts pass straight through. Note the shebang: the wrapper itself runs on real-bash, or it would recurse.

#!/usr/bin/real-bash
# AgentCgroup Bash Wrapper
/* ... */
REAL_BASH="/usr/bin/real-bash"
CGROUP_ROOT="${AGENTCG_ROOT:-/sys/fs/cgroup/agentcg/session_high}"
LOG_FILE="${AGENTCG_LOG:-/tmp/agentcg_tools.jsonl}"

# If disabled, pass through directly
if [ "${AGENTCG_DISABLE:-0}" = "1" ]; then
    exec "$REAL_BASH" "$@"
fi

# Non "-c" invocations pass through (interactive bash, source scripts, etc.)
if [ "$1" != "-c" ]; then
    exec "$REAL_BASH" "$@"
fi

# --- Per-tool-call cgroup creation ---

TOOL_CG="${CGROUP_ROOT}/tool_$$_$(date +%s%N 2>/dev/null || echo $$)"
IN_CG=0

# Parse resource hint (upward: Agent → System)
HINT="${AGENT_RESOURCE_HINT:-}"
MEM_HIGH="max"
case "$HINT" in
    memory:low)     MEM_HIGH=$((256 * 1024 * 1024)) ;;
    memory:medium)  MEM_HIGH=$((1024 * 1024 * 1024)) ;;
    memory:high)    MEM_HIGH="max" ;;
    memory:*[gG])
        NUM="${HINT#memory:}"
        NUM="${NUM%[gG]}"
        # Use shell arithmetic; fall back to max on error
        MEM_HIGH=$(( NUM * 1024 * 1024 * 1024 )) 2>/dev/null || MEM_HIGH="max"
        ;;
/* ... memory:*[mM] handled the same way ... */
esac

# Create ephemeral child cgroup
if mkdir -p "$TOOL_CG" 2>/dev/null; then
    # Apply memory.high if hint was provided
    if [ "$MEM_HIGH" != "max" ] && [ -f "$TOOL_CG/memory.high" ]; then
        echo "$MEM_HIGH" > "$TOOL_CG/memory.high" 2>/dev/null
    fi
    # Move self into child cgroup
    if echo $$ > "$TOOL_CG/cgroup.procs" 2>/dev/null; then
        IN_CG=1
    fi
fi

The design choices are visible here. The cgroup name is tool_<pid>_<nanoseconds>, so concurrent calls never collide. The hint only ever sets memory.high, the throttle boundary, never memory.max: a wrong guess slows the command down instead of killing it. A hint of memory:low means 256 MiB, memory:medium 1 GiB, and memory:high or no hint means no per-call limit. And every step fails open: if mkdir or the PID write fails, the command still runs, just untracked.

Then the wrapper runs the command, collects metrics and talks back:

# --- Execute the actual command ---
"$REAL_BASH" "$@"
EXIT_CODE=$?
/* ... */
if [ "$IN_CG" = "1" ]; then
    PEAK_MEM=$(cat "$TOOL_CG/memory.peak" 2>/dev/null || echo "")
    CURRENT_MEM=$(cat "$TOOL_CG/memory.current" 2>/dev/null || echo "")
fi

# --- Downward feedback: System → Agent ---
if [ $EXIT_CODE -eq 137 ] && [ "$IN_CG" = "1" ]; then
    PEAK_MB=""
    if [ -n "$PEAK_MEM" ]; then
        PEAK_MB=$((PEAK_MEM / 1024 / 1024))
    fi
    echo "[Resource] Command killed (OOM, exit 137). Peak memory: ${PEAK_MB:-unknown}MB." >&2
    echo "[Resource] The command exceeded the available memory budget." >&2
    echo "[Resource] Suggestions: run more targeted operations (e.g., specific test" >&2
    echo "  files instead of full test suite), reduce data size, or split into" >&2
    echo "  smaller steps. You can also request more memory by setting" >&2
    echo "  AGENT_RESOURCE_HINT=\"memory:<size>g\" before the command." >&2
fi
/* ... JSONL logging: ts, pid, cgroup, cmd (200 chars), exit, duration_ms, peak_mem ... */

# --- Cleanup: move back to parent cgroup, remove child ---
if [ "$IN_CG" = "1" ]; then
    echo $$ > "$CGROUP_ROOT/cgroup.procs" 2>/dev/null
    rmdir "$TOOL_CG" 2>/dev/null
fi

exit $EXIT_CODE

Exit code 137 is 128 + 9, a process killed by SIGKILL, which is what the OOM killer sends. The feedback is ordinary text on stderr, so it arrives in the tool result the model reads next. No agent-side change is needed. Because memory.peak is read from a cgroup that existed only for this command, the log gives exactly the per-tool-call attribution that the container-level characterization lacked.

Read the clean-up carefully

The clean-up moves the wrapper's PID back into session_high. But the daemon has enabled +memory +cpu in session_high/cgroup.subtree_control, and the no-internal-process rule forbids processes in such a non-root cgroup. By our reading, that write should fail, so the rmdir runs while the wrapper is still inside tool_…/ and also fails, leaving an empty directory behind when the wrapper exits. The repo's 14 wrapper tests run against simulated directories (bash_wrapper_local.sh uses a tmpdir and /proc), so they would not show this. We did not run the wrapper on a real cgroup v2 system, so treat this as unverified. If you deploy it, check for leftover tool_* directories, which the daemon's own scanner (_manage_tool_cgroups) would also see.

The daemon's process monitor is not involved in placing processes. The comment in handle_event says it plainly: "With bash wrapper, tool-call processes self-assign to child cgroups. Daemon only logs the event for observability."

The daemon: building the tree

agentcgroupd.py is small (351 lines). It must run as root. Its setup function is the whole cgroup policy of the prototype:

def setup_cgroup_hierarchy(root: str) -> bool:
    """Create the cgroup hierarchy with session_high and session_low.

    Enables subtree_control on session_high to allow per-tool-call
    child cgroups created by the bash wrapper.
    """
    high = os.path.join(root, "session_high")
    low = os.path.join(root, "session_low")

    if not cgroup_create(high) or not cgroup_create(low):
        return False

    # Enable controllers on root
    cgroup_write(root, "cgroup.subtree_control", "+memory +cpu")

    # Enable subtree_control on session_high for per-tool-call child cgroups
    cgroup_write(high, "cgroup.subtree_control", "+memory +cpu")

    # Set CPU weights (higher = more CPU time)
    cgroup_write(high, "cpu.weight", "150")
    cgroup_write(low, "cpu.weight", "50")

    log.info("Cgroup hierarchy ready at %s (per-tool-call subtree enabled)", root)
    return True

For cgroup_write(root, "cgroup.subtree_control", …) to work, the parent of agentcg/ (here the real root) must already delegate cpu and memory, which systemd hosts normally do. Then start() launches the components in order: scheduler/scx_flatcg -i 5 (print stats every 5 s), the memory controller, a one-second pause "for BPF programs to attach", and process/process -m 2 -c python,bash,pytest,node,npm, whose JSON lines on stdout drive the event loop. If the scheduler or memcg component fails to start, the daemon logs a warning and carries on without it. If the process monitor dies, the daemon exits.

Two memory back ends

memcg_controller.py hides the choice of memory mechanism behind one interface, because the BPF one needs a patched kernel:

def create_memcg_controller(script_dir: str) -> MemcgController:
    """Auto-detect: use BPF if binary exists, otherwise cgroup v2 fallback."""
    bpf_bin = os.path.join(script_dir, "memcg", "memcg_priority")
    if os.path.isfile(bpf_bin) and os.access(bpf_bin, os.X_OK):
        log.info("Using BPF memcg controller (%s)", bpf_bin)
        return BpfMemcgController(bpf_bin)
    log.info("BPF memcg binary not found, using cgroup v2 fallback")
    return CgroupMemcgController()

The BPF back end just runs memcg/memcg_priority --high … --low … --delay-ms 50 --threshold 1 --below-low (the defaults in MemcgConfig) and watches that it stays alive. The fallback, CgroupMemcgController, is a classic user-space controller and a useful contrast. On every loop iteration it checks three signals, in order: the high counter in memory.events of session_high grew; the PSI some … total= of the parent grew; or the parent's memory.current is at least 85% of its memory.max. Any one of these turns protection on for a one-second window:

    def _activate_protection(self) -> None:
        """Enter protection: shield HIGH from reclaim, throttle LOW."""
        if not self._config:
            return

        # Determine memory limits from parent cgroup
        parent = os.path.dirname(self._config.high_cgroup)
        total = self._read_memory_limit(parent)

        if total and total > 0:
            # Protect 80% for HIGH
            high_low = int(total * 0.8)
            # Restrict LOW to 50%
            low_high = int(total * 0.5)
        else:
            # Fallback: use a large value for protection, small for throttle
            high_low = 1 << 30  # 1 GiB
            low_high = 512 << 20  # 512 MiB

        _cgroup_write(self._config.high_cgroup, "memory.low", str(high_low))
        for low in self._config.low_cgroups:
            _cgroup_write(low, "memory.high", str(low_high))

This is exactly the pattern the paper calls too slow. The daemon learns about pressure only after it has built up, and only as fast as its loop runs. Since that loop also blocks on proc.stdout.readline() from the process monitor, the polling rate depends on how often process events arrive. The BPF back end moves the same decision ("is HIGH busy right now? then protect it and slow LOW down") into the kernel's reclaim and throttling paths.

The BPF value can only lengthen the built-in penalty, never shorten it, and it still passes the kernel's existing clamp on the maximum delay per return to user space. Two more properties matter for AgentCgroup. When a child memcg comes online, memcontrol_bpf_online() copies the parent's bpf_ops ("Inherit the BPF program from the parent cgroup"), so ops attached to session_high also cover every new tool_* child with no extra work. And the hook only acts when the cgroup is over memory.high: a LOW session with memory.high = max is never delayed by it.

The BPF program

agentcg/memcg/memcg_priority.bpf.c (209 lines) is close to the sample program in the patch series (samples/bpf/memcg.bpf.c). It has one tracepoint and two struct_ops maps. The tracepoint decides when the HIGH session is "active":

SEC("tp/memcg/count_memcg_events")
int handle_count_memcg_events(struct trace_event_raw_memcg_rstat_events *ctx)
{
	__u32 key = 0;
	struct AggregationData *data;
	__u64 current_ts;

	/* Only count page faults from HIGH priority cgroup */
	/* PGFAULT = 23 in the kernel enum */
	if (ctx->id != local_config.high_cgroup_id || ctx->item != 23)
		return 0;

	data = bpf_map_lookup_elem(&aggregation_map, &key);
	if (!data)
		return 0;

	current_ts = bpf_ktime_get_ns();

	/* Reset window if more than 1 second has passed */
	if (current_ts - data->window_start_ts < ONE_SECOND_NS) {
		data->sum += ctx->val;
	} else {
		data->window_start_ts = current_ts;
		data->sum = ctx->val;
	}

	/* If threshold exceeded, record trigger timestamp */
	if (data->sum > local_config.threshold) {
		bpf_map_update_elem(&trigger_ts_map, &key, &current_ts, BPF_ANY);
		data->sum = 0;
		data->window_start_ts = current_ts;
	}

	return 0;
}

Then every struct_ops callback asks one question, "did HIGH cross the page-fault threshold within the last second?":

static __always_inline bool need_protection(void)
{
	/* ... */
	trigger_ts = bpf_map_lookup_elem(&trigger_ts_map, &key);
	if (!trigger_ts || *trigger_ts == 0)
		return false;

	current_ts = bpf_ktime_get_ns();

	/* Protection window is 1 second */
	return (current_ts - *trigger_ts < ONE_SECOND_NS);
}
/* ... */
SEC("struct_ops/get_high_delay_ms")
unsigned int get_high_delay_ms_impl(struct mem_cgroup *memcg)
{
	/* ... stats counter ... */
	if (local_config.over_high_ms && need_protection()) {
		/* ... */
		return local_config.over_high_ms;
	}

	return 0;
}

SEC(".struct_ops.link")
struct memcg_bpf_ops high_mcg_ops = {
	.below_low = (void *)below_low_impl,
	.below_min = (void *)below_min_impl,
};

SEC(".struct_ops.link")
struct memcg_bpf_ops low_mcg_ops = {
	.get_high_delay_ms = (void *)get_high_delay_ms_impl,
};

Two maps of the same type are defined because each cgroup gets its own attachment. The HIGH session gets high_mcg_ops (reclaim protection). Each LOW session gets low_mcg_ops (extra delay). The whole policy is: when the important agent is actively faulting in memory, protect it and slow the others down, for one second at a time. Nothing waits for a user-space daemon.

static __u64 get_cgroup_id(const char *path)
{
	struct stat st;

	if (stat(path, &st) < 0) {
		fprintf(stderr, "Failed to stat %s: %s\n", path, strerror(errno));

	}

Two details are worth noticing when reading this program. The page-fault item number is hard-coded (ctx->item != 23, "PGFAULT = 23 in the kernel enum"), so it depends on the exact vm_event_item layout of the patched kernel. And the filter matches only session_high's own id. As far as we can tell from reading the code, faults charged to a tool_* child carry the child's id, so whether tool-call faults trigger protection when the wrapper is in use depends on how the tracepoint reports them. We did not test this. In the paper's evaluation the replayed workloads ran directly in the HIGH and LOW cgroups.

CPU: scx_flatcg under sched_ext

The CPU side reuses scx_flatcg, the "flattened cgroup hierarchy scheduler" that ships with the kernel in tools/sched_ext/ (upstream source). A diff against torvalds/master shows the copy in agentcg/scheduler/ is the same algorithm. The differences are compatibility changes (for example __COMPAT_scx_bpf_task_cgroup() and a one-argument scx_bpf_dsq_move_to_local()), a -d option to dump cgroups, and using online rather than possible CPUs for nr_cpus. Its header comment explains the idea:

/*
 * A demo sched_ext flattened cgroup hierarchy scheduler. It implements
 * hierarchical weight-based cgroup CPU control by flattening the cgroup
 * hierarchy into a single layer by compounding the active weight share at each
 * level. Consider the following hierarchy with weights in parentheses:
 *
 * R + A (100) + B (100)
 *   |         \ C (100)
 *   \ D (200)
 * ...
 * So, instead of hierarchically scheduling level-by-level, we can consider it
 * as B, C and D competing each other with respective share of 1/6, 1/6 and 2/3
 * and keep updating the eventual shares as the cgroups' runnable states change.
 */

Each cgroup gets its own dispatch queue (DSQ) whose id is the cgroup id, created in cgroup_init. Cgroups wait in a red-black tree ordered by cgroup virtual time. Each one is charged slice time divided by its compounded weight (hweight), so a cgroup with twice the share runs twice as often. Weight changes from cpu.weight arrive through the cgroup_set_weight callback:

void BPF_STRUCT_OPS(fcg_cgroup_set_weight, struct cgroup *cgrp, u32 weight)
{
	struct fcg_cgrp_ctx *cgc, *pcgc = NULL;

	cgc = find_cgrp_ctx(cgrp);
	if (!cgc)
		return;

	if (cgrp->level) {
		pcgc = find_ancestor_cgrp_ctx(cgrp, cgrp->level - 1);
		if (!pcgc)
			return;
	}

	bpf_spin_lock(&cgv_tree_lock);
	if (pcgc && cgc->nr_active)
		pcgc->child_weight_sum += (s64)weight - cgc->weight;
	cgc->weight = weight;
	bpf_spin_unlock(&cgv_tree_lock);
}
/* ... */
SCX_OPS_DEFINE(flatcg_ops,
	       .select_cpu		= (void *)fcg_select_cpu,
	       .enqueue			= (void *)fcg_enqueue,
	       .dispatch		= (void *)fcg_dispatch,
	       /* ... runnable, running, stopping, quiescent, init_task ... */
	       .cgroup_set_weight	= (void *)fcg_cgroup_set_weight,
	       .cgroup_init		= (void *)fcg_cgroup_init,

	       .cgroup_move		= (void *)fcg_cgroup_move,

With the daemon's weights, session_high (150) gets three times the CPU of session_low (50) when both are runnable. Tool cgroups start at the default weight of 100 and share session_high's portion among themselves. Note what this does not do. The paper's §5 says the CPU side maintains "per-workload and per-tool-call metadata in BPF maps, prioritizing latency-sensitive tool calls". In the code at 551ca168 there is no agent-specific logic in the scheduler. The priority comes entirely from cpu.weight, which is the cgroup interface a standard kernel's fair scheduler also honours. What sched_ext adds here is the flattened hierarchy (cheaper with deep trees) and a place where agent-aware logic could go later.

The process monitor

agentcg/process/process.bpf.c comes from the AgentSight lineage (chapter 23). It attaches to tp/sched/sched_process_exec, tp/sched/sched_process_exit, tp/syscalls/sys_enter_openat and sys_enter_open, plus a uretprobe on bash's readline (SEC("uretprobe//usr/bin/bash:readline")) that captures interactive command lines. Events go through a 256 KB ring buffer, and the user-space side filters by command name (-c) and mode (-m 2 is "filter": report only tracked processes and their descendants). In AgentCgroup it is observability only: the daemon logs EXEC and EXIT with durations.

One tool call, step by step

1. The model chooses a command

Claude Code decides to run the test suite and emits a Bash tool call. If the agent was told about the protocol (the live test in test_live_agent.sh puts it in the prompt), the command carries AGENT_RESOURCE_HINT="memory:high".

2. The framework forks bash

The framework runs bash -c "pytest tests/". /usr/bin/bash is the wrapper. It sees -c, computes tool_<pid>_<ns>, and maps the hint (memory:high means no per-call limit, memory:low would mean 256 MiB).

3. A new cgroup is born

mkdir under session_high/. The kernel brings the memcg online, and memcontrol_bpf_online() copies high_mcg_ops from the parent. sched_ext calls fcg_cgroup_init, which creates a DSQ for the new cgroup. The wrapper writes its PID to cgroup.procs; sched_ext sees cgroup_move.

4. pytest runs and allocates

All children of the wrapper inherit the cgroup. Page faults are charged to it, and the scheduler accounts its CPU time against session_high's 150 weight. If a LOW tenant is over its memory.high while HIGH is active, get_high_delay_ms returns the configured delay (50 ms by default from the daemon) and the LOW allocator sleeps.

5. Reclaim protects the agent

When memory runs short, reclaim walks the cgroups. For session_high and its children, below_low returns true during the protection window, so reclaim takes memory from elsewhere first.

6. The command ends

The wrapper reads memory.peak and memory.current. If the exit code is 137, it prints the [Resource] … lines to stderr. It appends one JSON line to $AGENTCG_LOG and tries to move back and remove the cgroup.

7. The model reads the result

The tool result includes the feedback text. The model might now run one test file instead of the whole suite, or retry with AGENT_RESOURCE_HINT="memory:2g". That is the "adaptability" mechanism: no history, just a conversation.

Benefits and limitations

What works well

  • Attribution for free. One cgroup per bash -c gives exact per-command memory.peak, with no agent changes and a few milliseconds of overhead. That alone is useful for measuring agents.
  • Kernel-speed priority. The memcg callbacks run inside reclaim and the over-high path. They answer from a map lookup and a timestamp comparison. There is no wake-up and no control-file write.
  • Degrade, do not kill. Hints set memory.high, not memory.max, and the BPF policy delays LOW tenants instead of OOM-killing them. That fits a workload whose death costs all its context.
  • Agents as participants. Hints and stderr feedback treat the agent as something that can cooperate, an idea no classic resource manager could use.
  • Safe fallbacks. sched_ext reverts to the default scheduler on error, the daemon runs without missing components, and the memory controller falls back to plain cgroup v2.

Limitations

  • Needs an unmerged kernel interface. memcg_bpf_ops and bpf_map__attach_struct_ops_opts() exist only in the RFC series. Their names and semantics may change, and on a stock kernel you get the user-space fallback.
  • Code is narrower than the paper. At 551ca168 we found no use of cgroup.freeze (the paper's "throttling … then freezing") and no per-tool-call logic in the scheduler. The CPU policy is two static weights.
  • Only two priority classes, hard-wired as session_high/session_low. Nothing assigns a real agent session to either; the daemon creates the directories and the wrapper uses session_high.
  • Interception is shallow. Only bash -c is wrapped. Tools that exec programs directly, long-lived language servers, or framework-internal work (a sub-agent, a web fetch) stay in whatever cgroup they started in. Replacing /usr/bin/bash also changes a system binary in the container.
  • Hints are advisory and unauthenticated. Any process can set AGENT_RESOURCE_HINT. Since a hint can only lower memory.high for its own call, a lying agent mostly hurts itself, but the scheme does not protect against a hostile one.
  • Fragile details found by reading: the hard-coded PGFAULT = 23, the HIGH-only id filter versus faults in tool children, and the move-back-then-rmdir sequence under the no-internal-process rule (all unverified on a live kernel).
  • Study scope. One agent framework (Claude Code), one benchmark, 1-second container-level sampling, and a parser bug under review (PR #11). The paper says so itself: "the characterization covers one agent framework and one benchmark".

Related work

  • User-space pressure controllers. oomd and systemd-oomd act on PSI from user space and kill whole cgroups. Meta's TMO (ASPLOS '22) uses PSI to drive proactive memory offloading. AgentCgroup's fallback controller is in this family; its BPF path is an attempt to move the decision into the kernel.
  • BPF for memory management. Roman Gushchin's "mm: BPF OOM" series adds a struct_ops for OOM handling, memcg kfuncs and PSI struct_ops. It also supplies the attach-struct_ops-to-cgroup support that memcg_bpf_ops builds on.
  • BPF schedulers. sched-ext/scx collects production sched_ext schedulers (scx_layered, scx_lavd, scx_rusty, …). scx_flatcg is one of the kernel's example schedulers. The org's LLM-for-scheduler work is in chapter 30.
  • Workload characterization. The paper positions itself against studies of serverless (Shahrad et al.), Azure VMs (Resource Central, SOSP '17) and Borg/Autopilot.
  • Agent systems. AgentSight observes agents with eBPF and is the code base the prototype extends. ActPlane enforces information-flow rules on the same kind of process tree. Chapter 26 and chapter 27 cover the org's other agent-safety tools.

Check your understanding

Q1. Why does the wrapper map a hint to memory.high instead of memory.max?

The kernel doc: memory.high is a "throttle limit" and going over it "never invokes the OOM killer". memory.max is the hard limit that triggers OOM. For an agent, an OOM kill loses context, so the soft boundary is the safer target.

Q2. Which eBPF mechanisms enforce AgentCgroup's priorities in the kernel?

Classic cgroup programs only allow or deny operations. AgentCgroup uses struct_ops-based interfaces: sched_ext_ops and the RFC memcg_bpf_ops.

Q3. In memcg_priority.bpf.c, when does get_high_delay_ms return a non-zero delay for a LOW cgroup?

The kernel calls the hook from the over-high path only. The program then returns over_high_ms only if need_protection() sees a trigger timestamp less than one second old, set by the count_memcg_events tracepoint.

Q4. A new tool_* cgroup is created under session_high, which has high_mcg_ops attached. What happens?

The RFC patch's online handler says "Inherit the BPF program from the parent cgroup". The paper relies on this: ops on the parent cover all tool children "requiring no BPF code changes".

Q5. According to the paper, which resource limits how many agent sandboxes fit on one machine?

§3.3: "Memory, not CPU, is the primary bottleneck for multi-tenant concurrency density." CPU stays below 36% of capacity at that density.

Q6. What does the agent see when a wrapped command is OOM-killed?

When EXIT_CODE is 137 and the call was in its cgroup, the wrapper reads memory.peak and prints the feedback to stderr, which becomes part of the tool result.
