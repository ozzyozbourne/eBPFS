Chapter 04

Maps, helpers and kfuncs

An eBPF program runs for a few microseconds per event and then its stack is gone. So where does it keep a counter, how does it hand a record to a process in user space, and how does it ask the kernel for the current PID or a reference to a task? This chapter covers the three answers: maps for state, helpers and kfuncs for calling the kernel, and BPF-to-BPF calls and tail calls for structuring programs.

Why this matters

Chapter 02 showed that an eBPF program is a function with eleven 64-bit registers and a small stack (512 bytes, or up to 2 KiB on JITs that support large stacks). Chapter 03 showed that the verifier proves the function terminates and touches only memory it is allowed to touch. Those two facts leave three problems.

  1. No memory between runs. The program is invoked once per packet, system call or function entry. When it returns, its registers and stack are discarded. A program that counts system calls per process needs storage that outlives a single invocation.
  2. No channel to user space. A tracing tool such as execsnoop needs to deliver thousands of variable-sized records per second to a process that prints or stores them. A firewall needs the reverse: a process writes a rule table that the program reads.
  3. No access to the rest of the kernel. The verifier forbids arbitrary calls and arbitrary pointer dereferences. Yet a program often needs to read the clock, find the current task, redirect a packet or take a reference on a kernel object.

The kernel answers the first two with maps: kernel-managed data structures that both programs and user space can reach. It answers the third with a fixed list of helper functions and, since Linux 5.13, with kfuncs: ordinary kernel functions that have been explicitly exposed to BPF and are type-checked through BTF. Finally, programs grew too large to be one function, so the kernel added BPF-to-BPF function calls (4.16) and tail calls (4.2).

Key idea

An eBPF program owns nothing except its registers and stack. Everything persistent lives in a map, which is a kernel object with a file descriptor. Everything the program does to the outside world goes through a call the verifier knows the signature of: a helper (stable ABI, numbered), a kfunc (unstable, described by BTF) or another BPF function.

Maps: kernel objects with a key/value interface

What a map is

A map is created with the BPF_MAP_CREATE command of the bpf(2) system call. The caller supplies a type, a key size, a value size, a maximum number of entries and some flags; the kernel returns a file descriptor. The kernel documentation shows the raw form (docs.kernel.org/bpf/maps.html):

int fd;
union bpf_attr attr = {
        .map_type = BPF_MAP_TYPE_ARRAY;  /* mandatory */
        .key_size = sizeof(__u32);       /* mandatory */
        .value_size = sizeof(__u32);     /* mandatory */
        .max_entries = 256;              /* mandatory */
        .map_flags = BPF_F_MMAPABLE;
        .map_name = "example_array";
};

fd = bpf(BPF_MAP_CREATE, &attr, sizeof(attr));

Inside the kernel each map type is a C implementation behind a table of function pointers (struct bpf_map_ops): kernel/bpf/hashtab.c for the hash family, arraymap.c for arrays, lpm_trie.c, ringbuf.c, stackmap.c, bpf_task_storage.c, arena.c and so on. When a program is loaded, the loader rewrites every reference to a map into a special 64-bit load instruction (BPF_LD_IMM64 with BPF_PSEUDO_MAP_FD). The verifier replaces the file descriptor with the kernel address of the struct bpf_map and takes a reference on the map, so the map lives at least as long as any program that uses it.

A map stays alive while anything holds a reference: an open file descriptor in some process, a loaded program that uses it, an outer map that contains it, or a pin in the BPF file system. When the last reference goes away, the map is freed. This reference counting is what lets a loader exit while its programs keep running and keep counting.

Declaring maps in C: the BTF-defined syntax

Nobody writes union bpf_attr by hand for a normal program. With libbpf, a map is a global variable of an anonymous struct type placed in the ELF section .maps. The struct carries no data; its type carries the map's parameters, and the compiler records that type in the object's BTF (BPF Type Format, see chapter 06). libbpf reads the BTF and calls BPF_MAP_CREATE for you. The trick lies in three macros from libbpf:

#define __uint(name, val) int (*name)[val]
#define __type(name, val) typeof(val) *name
#define __array(name, val) typeof(val) *name[]

__uint(max_entries, 256) declares a member max_entries that is a pointer to an array of 256 ints. The number 256 is encoded in the array dimension of the type, which BTF preserves; no memory is allocated. __type(key, u32) declares a pointer to u32, so libbpf learns both the key size and its BTF type. The BTF type of the value lets the kernel check special fields (spin locks, timers, kptrs) and lets bpftool map dump pretty-print values. The array map example from the kernel docs:

struct {
        __uint(type, BPF_MAP_TYPE_ARRAY);
        __type(key, u32);
        __type(value, long);
        __uint(max_entries, 256);
} my_map SEC(".maps");

Other members you will see are map_flags, pinning, numa_node, map_extra (used by bloom filters and arenas) and key_size/value_size for types whose key or value is not a C type (prog arrays, perf event arrays). Older code used a struct bpf_map_def in a "maps" section; libbpf 1.0 removed support for that legacy form.

In the program, the map variable is only ever used by address: &my_map is passed as the first argument of a map helper. The verifier knows the map's key and value sizes, so it checks that the key pointer points at enough readable bytes and that every access through the returned value pointer stays inside value_size.

Hash and array: the workhorses

The two oldest types behave differently in ways that matter. An array has exactly max_entries slots, all allocated and zeroed at creation. Lookups of an in-range index always succeed, there is no delete, and the verifier can inline a lookup into a bounds check plus an address calculation. A hash allocates elements on insert. By default it preallocates max_entries elements up front so that an insert from any context (including NMI) never calls the memory allocator. BPF_F_NO_PREALLOC trades that for memory savings. When a hash is full, bpf_map_update_elem() fails with -E2BIG; the update flags are BPF_ANY, BPF_NOEXIST and BPF_EXIST.

bpf_map_lookup_elem() returns a pointer into the map, not a copy. The verifier types the result as "pointer to map value or NULL" and refuses any dereference until the program has checked for NULL. Writes through that pointer are visible to everyone at once, so concurrent updates from several CPUs race. The fixes are atomic instructions (__sync_fetch_and_add compiles to a BPF atomic add), per-CPU maps or a spin lock, covered below.

Per-CPU variants

PERCPU_HASH and PERCPU_ARRAY keep one copy of every value per CPU. A program always sees the slot of the CPU it runs on, so increments need no atomics and cause no cache-line bouncing. Because BPF programs are not migrated to another CPU while they run, the slot is stable for the whole invocation. A per-CPU array with one element is also the classic "scratch heap" for building records larger than the stack allows. User space pays the price at read time: a lookup returns an array of value_size rounded up to 8 bytes times the number of possible CPUs (libbpf_num_possible_cpus()), and the reader sums or merges them. Since 5.19, bpf_map_lookup_percpu_elem() lets a program read another CPU's slot.

LRU hash

An LRU hash never fails an insert because it is full: it evicts an element that has not been used recently. That is what you want for a connection-tracking table that sees an unbounded set of flows. The kernel documentation's table summarises the two knobs: map type (LRU_HASH versus LRU_PERCPU_HASH) decides whether values are per CPU, and BPF_F_NO_COMMON_LRU decides whether there is one global LRU list or one per CPU. Per-CPU LRU lists scale better but evict more aggressively, because each CPU only sees its share of max_entries. Eviction is approximate; do not use an LRU map for data you cannot afford to lose.

LPM trie

The longest-prefix-match trie answers "which stored prefix is the most specific match for this address?", the question behind every routing table and CIDR allow-list. The key is a struct bpf_lpm_trie_key_u8 header with a 32-bit prefixlen, followed by the address bytes in network byte order. To look up an address, set prefixlen to the maximum (32 for IPv4, 128 for IPv6). The map must be created with BPF_F_NO_PREALLOC; prefix lengths are multiples of 8 from 8 to 2048.

Stack trace maps

Profilers need to record "where was the CPU" thousands of times per second. Storing full stacks in every sample would be expensive. A STACK_TRACE map deduplicates instead: bpf_get_stackid(ctx, &stacks, flags) walks the kernel or (with BPF_F_USER_STACK) user stack, hashes it, stores the array of instruction pointers and returns a small integer ID. The program counts IDs in a hash map, and user space resolves IDs to address arrays and then to symbols. bpf_get_stack() (4.18) is the variant that copies the stack into a buffer you own.

Maps of maps

ARRAY_OF_MAPS and HASH_OF_MAPS hold references to other maps. A program can only look up the outer map; the result is a map pointer it can pass to the normal helpers. User space can replace an inner map in one syscall, which gives an atomic swap of a whole rule table: build the new table off to the side, then update one slot. All inner maps must match the template map given at creation. The selftest shows both declaration styles, including static initialisation of the outer map with __array(values, ...):

Local storage: task, socket, inode, cgroup

A common pattern is "remember something about this task (or socket) until it goes away". With a hash keyed by PID you must delete entries yourself, typically by hooking process exit, and PIDs get reused. Local storage maps attach the value to the kernel object itself. The object keeps a small list of storage slots; looking one up is a short list walk, not a global hash lookup, and the kernel frees the value when the object dies. The four flavours are socket (5.2), inode (5.10), task (5.11) and cgroup (6.2, CGRP_STORAGE, which replaces the older cgroup-attached CGROUP_STORAGE). These maps must be created with BPF_F_NO_PREALLOC, and the "key" a program passes is the object pointer:

struct {
	__uint(type, BPF_MAP_TYPE_TASK_STORAGE);
	__uint(map_flags, BPF_F_NO_PREALLOC);
	__type(key, int);
	__type(value, long);
} enter_id SEC(".maps");

/* ... */

SEC("tp_btf/sys_enter")
int BPF_PROG(on_enter, struct pt_regs *regs, long id)
{
	struct task_struct *task;
	long *ptr;

	task = bpf_get_current_task_btf();

From user space, the key of a task storage map is a pidfd, and for a cgroup storage map it is a cgroup fd, as the kernel's map_cgrp_storage.rst describes.

Arena: a heap shared with user space

Maps are key/value stores. Linked lists, trees and graphs with pointers between nodes do not fit that model. BPF_MAP_TYPE_ARENA (6.9) is a sparse memory region of up to 4 GB that both the program and a user-space process map. In the patch cover letter (LWN) Alexei Starovoitov describes it as a "sparse shared memory region between the bpf program and user space". Pages are allocated on demand, by user-space page faults or by the sleepable kfunc bpf_arena_alloc_pages(). Pointers into the arena carry the __arena address-space tag. The compiler and JIT translate between the kernel and user addresses of the same page, so a pointer stored by the program is valid in the user process. The verifier treats arena memory as data only: a kernel pointer written into the arena cannot be used as a pointer after it is read back. The selftest declares an arena of 100 pages:

struct {
	__uint(type, BPF_MAP_TYPE_ARENA);
	__uint(map_flags, BPF_F_MMAPABLE);
	__uint(max_entries, 100); /* number of pages */
#ifdef __TARGET_ARCH_arm64
	__ulong(map_extra, 0x1ull << 32); /* start of mmap() region */
#else
	__ulong(map_extra, 0x1ull << 44); /* start of mmap() region */
#endif
} arena SEC(".maps");

#include "bpf_arena_alloc.h"
#include "bpf_arena_list.h"

struct elem {
	struct arena_list_node node;
	__u64 value;
};

struct arena_list_head __arena *list_head;

sched_ext schedulers are the heaviest users today. LWN's report from the 2025 LSFMM+BPF summit ("A look at what's possible with BPF arenas") describes how they keep the bulk of their data structures in the arena and only the kernel-object references in ordinary maps.

Pinning maps in bpffs

File descriptors are per-process. If a loader exits, the only things holding a map are the programs that use it, and no other process can find the map. The BPF file system (since 4.4), normally mounted at /sys/fs/bpf, fixes that. BPF_OBJ_PIN creates a file there that holds a reference to a map, program or link, and BPF_OBJ_GET turns the path back into a file descriptor. Pinned objects survive the exit of every process and disappear on unlink() or reboot.

libbpf can pin declaratively. With LIBBPF_PIN_BY_NAME, libbpf pins the map under the pin root (default /sys/fs/bpf) using the map's name. If a pin of that name already exists and is compatible, libbpf reuses the existing map instead of creating a new one. That is how two programs loaded at different times end up sharing state:

struct {
	__uint(type, BPF_MAP_TYPE_ARRAY);
	__uint(max_entries, 1);
	__type(key, __u32);
	__type(value, __u64);
	__uint(pinning, LIBBPF_PIN_BY_NAME);
} pinmap SEC(".maps");

struct {
	__uint(type, BPF_MAP_TYPE_HASH);
	__uint(max_entries, 1);
	__type(key, __u32);
	__type(value, __u64);
} nopinmap SEC(".maps");

Using maps from user space

User space reaches maps through the same bpf(2) system call. Every command takes a map fd plus pointers to user buffers. Unlike the in-kernel helper, a user-space lookup copies the value out:

  • BPF_MAP_LOOKUP_ELEM, BPF_MAP_UPDATE_ELEM, BPF_MAP_DELETE_ELEM: one element. libbpf wraps them as bpf_map_lookup_elem(fd, key, value), bpf_map_update_elem(fd, key, value, flags) and bpf_map_delete_elem(fd, key) in tools/lib/bpf/bpf.h. These are the same names as the BPF-side helpers but with an fd instead of a map pointer.
  • BPF_MAP_GET_NEXT_KEY: iteration. Pass NULL to get the first key. The kernel docs warn that if the current key is deleted during iteration, the next call returns the first key again, so use batch operations when deletes are mixed in.
  • BPF_MAP_LOOKUP_BATCH, BPF_MAP_LOOKUP_AND_DELETE_BATCH, BPF_MAP_UPDATE_BATCH: many elements per syscall.
  • BPF_MAP_LOOKUP_AND_DELETE_ELEM: atomic pop (queues and stacks since 4.20, hashes since 5.14).
  • BPF_F_LOCK on lookup/update: copy the value while holding the element's bpf_spin_lock (5.1).
  • BPF_MAP_FREEZE (5.2): make the map read-only for user space from now on. libbpf freezes .rodata after initialising it.
  • mmap(): array maps created with BPF_F_MMAPABLE (5.5), ring buffers and arenas can be mapped into the process. Then reads and writes are plain memory accesses with no syscall at all.

The higher-level libbpf API on struct bpf_map *, such as bpf_map__lookup_elem(map, key, key_sz, value, value_sz, flags), checks the sizes against what it knows from BTF. bpftool exposes the same operations on the command line: bpftool map dump, lookup, update, delete and pin.

Global variables: .data, .bss and .rodata

Until Linux 5.2 a BPF program had no global variables; every piece of configuration went through an explicit one-element array map. The 5.2 change "bpf: implement lookup-free direct value access for maps" (commit d8eca5bbb2be) lets a BPF_LD_IMM64 instruction load the address of a value inside an array map. libbpf builds on that: for each of the ELF sections .data (initialised globals), .bss (zero-initialised) and .rodata (const), it creates a one-element array map whose value is the whole section. Accesses to globals become loads and stores at fixed offsets into that value, with no helper call. The selftest exercises every flavour:

/* Relocation tests for __u64s. */
static       __u64 num0;
static       __u64 num1 = 42;
static const __u64 num2 = 24;
static       __u64 num3 = 0;
static       __u64 num4 = 0xffeeff;
static const __u64 num5 = 0xabab;
static const __u64 num6 = 0xab;

/* Relocation tests for strings. */
static const char str0[32] = "abcdefghijklmnopqrstuvwxyz";
static       char str1[32] = "abcdefghijklmnopqrstuvwxyz";
static       char str2[32];

Three details make globals more than a convenience:

  • const volatile in .rodata is load-time configuration. User space sets the value through the skeleton (skel->rodata->target_ppid = 42) after open and before load. libbpf then creates the map, writes the value and freezes the map. Because the map is frozen and marked BPF_F_RDONLY_PROG, the verifier treats the value as a known constant and can prune branches that depend on it as dead code. volatile stops the compiler from folding the initial value at compile time. In the bpftool output above, flags 0x480 is BPF_F_RDONLY_PROG | BPF_F_MMAPABLE, and the map is listed as frozen.
  • .bss and .data are mmap-ed. The skeleton maps them into the process, so skel->bss->dropped is a plain memory read of the value the BPF program increments.
  • Custom sections. A variable placed in SEC(".data.foo") gets its own map. That is useful for a global bpf_spin_lock, which must sit in its own map, or to size a buffer independently.

Getting events out: ring buffer versus perf buffer

Counters in maps are fine for aggregates. Tracing tools need a stream: one record per event, in order, delivered with low latency. Before 5.8 the only tool was the perf buffer.

Perf buffer: one ring per CPU

A BPF_MAP_TYPE_PERF_EVENT_ARRAY maps CPU numbers to perf event file descriptors, each with its own mmap-ed ring. The program calls bpf_perf_event_output(ctx, &map, BPF_F_CURRENT_CPU, data, size), which copies a record into the current CPU's ring. libbpf's perf_buffer__new(map_fd, page_cnt, sample_cb, lost_cb, ctx, opts) opens one ring of page_cnt pages per CPU and epolls all of them. Andrii Nakryiko's post on the BPF ring buffer describes two structural problems with this design:

  • Memory. Each CPU's buffer must be sized for that CPU's worst burst. With 64 CPUs you pay 64 times the buffer, mostly empty, or you drop data when one CPU spikes.
  • Ordering. Events from different CPUs land in different rings. A short-lived process that forks on CPU 3, execs on CPU 7 and exits on CPU 1 can be seen by the consumer in any order. Nakryiko says his own fork/exec/exit tracker suffered from exactly this.

A third, smaller problem is the extra copy: the record must be assembled somewhere (often a per-CPU array, because the stack is small) and then copied into the ring. If the ring is full, all that work is wasted.

BPF ring buffer: one MPSC ring for all CPUs

BPF_MAP_TYPE_RINGBUF (5.8) is a multi-producer, single-consumer circular buffer shared by all CPUs. Its key and value sizes are zero, and max_entries is the size of the data area in bytes, a power of 2 and a multiple of the page size. Shared means one buffer can absorb a spike on any CPU, and events come out in the order their space was reserved, across CPUs. Programs have two APIs:

  • bpf_ringbuf_output(&rb, data, size, flags): a copy, like bpf_perf_event_output(). The size may be variable.
  • bpf_ringbuf_reserve(&rb, size, 0) returns a pointer into the ring or NULL. The program fills the record in place and then calls bpf_ringbuf_submit(ptr, flags) or bpf_ringbuf_discard(ptr, flags). The size must be a constant known to the verifier. No extra copy, no scratch buffer, and the program learns the buffer is full before doing the work.

The verifier tracks a reserved record like any acquired reference (see chapter 03). Every path must submit or discard it. When I changed the example below so that one path skips bpf_ringbuf_submit(), the 6.1 verifier rejected the program at load time with:

How it works inside

The design notes in Documentation/bpf/ringbuf.rst and the code in kernel/bpf/ringbuf.c are short and worth reading. The ring keeps two ever-increasing logical counters, consumer_pos and producer_pos, and masks them with size - 1 to find a byte offset. Reservations are serialised by a spinlock, which today is a resilient queued spinlock (rqspinlock_t). Each record starts with an 8-byte header holding its length, a busy bit (still being filled), a discard bit, and the record's page offset from the start of the ring. The offset lets bpf_ringbuf_submit(ptr) find the ring from the record pointer alone. Commit simply clears the busy bit with no lock, so several CPUs can fill their records in parallel. In NMI context the reservation may fail to take the lock and then returns NULL even if there is space.

Records wrap around the end of the data area without special cases, because the data pages are mapped twice in a row. The kernel comment draws it:

	/* Each data page is mapped twice to allow "virtual"
	 * continuous read of samples wrapping around the end of ring
	 * buffer area:
	 * ------------------------------------------------------
	 * | meta pages |  real data pages  |  same data pages  |
	 * ------------------------------------------------------
	 * |            | 1 2 3 4 5 6 7 8 9 | 1 2 3 4 5 6 7 8 9 |
	 * ------------------------------------------------------
	 * |            | TA             DA | TA             DA |
	 * ------------------------------------------------------
	 *                               ^^^^^^^
	 *                                  |
	 * Here, no need to worry about special handling of wrapped-around
	 * data due to double-mapped data pages. This works both in kernel and
	 * when mmap()'ed in user-space, simplifying both kernel and
	 * user-space implementations significantly.
	 */
	array_size = (nr_meta_pages + 2 * nr_data_pages) * sizeof(*pages);
	pages = bpf_map_area_alloc(array_size, numa_node);
	if (!pages)
		return NULL;

	for (i = 0; i < nr_pages; i++) {
		page = alloc_pages_node(numa_node, flags, 0);
		if (!page) {
			nr_pages = i;
			goto err_free_pages;
		}
		pages[i] = page;
		if (i >= nr_meta_pages)
			pages[nr_data_pages + i] = page;
	}

Notifications pace themselves. After a commit the kernel wakes the consumer (through irq_work, so it is safe from any context) only if the consumer has already caught up to that record. If it is behind, it will see the record anyway. Programs that want manual control pass BPF_RB_NO_WAKEUP or BPF_RB_FORCE_WAKEUP; the ringbuf_bench.c selftest uses that to wake only after a batch. bpf_ringbuf_query() reports available data, ring size and the two positions, which is useful for such heuristics and for monitoring.

Mainline also has a newer BPF_F_RB_OVERWRITE map flag. In that mode a full ring overwrites the oldest records instead of failing reservations, which is useful for "flight recorder" diagnostics. It was posted to bpf-next in August 2025; I have not verified which release first shipped it.

Life of one record

1. Reserve

A program on CPU 2 calls bpf_ringbuf_reserve(&events, sizeof(*e), 0). Under the ring's spinlock the kernel checks that the record plus its 8-byte header (rounded up to 8 bytes) fits in the space between consumer_pos and producer_pos. If it does not, it returns NULL and the program counts a drop. Otherwise it writes a header with the busy bit set, advances producer_pos and returns a pointer just after the header.

2. Fill in place

The program writes fields directly into the ring: PID from bpf_get_current_pid_tgid(), the command name, a string read with bpf_probe_read_kernel_str(). The verifier allows writes only within the reserved size. Meanwhile CPU 5 can reserve the next record; it does not wait for CPU 2.

3. Submit (or discard)

bpf_ringbuf_submit(e, 0) atomically clears the busy bit. bpf_ringbuf_discard() sets the discard bit instead. If the consumer was waiting at exactly this record, the kernel queues an irq_work to wake it.

4. Wake up

The consumer's epoll_wait() inside ring_buffer__poll() returns. libbpf reads producer_pos from the read-only producer page with acquire semantics.

5. Consume

libbpf walks headers from consumer_pos. A busy header stops the walk: a slow producer holds back later records, and that is what preserves order. Discarded records are skipped silently. For each committed record libbpf calls your handle_event(ctx, data, size) on the mmap-ed memory, with no copy.

6. Release space

libbpf stores the new consumer_pos into the one writable page of the mapping. The producer's next space check sees the freed bytes. Your callback must therefore copy anything it wants to keep; the memory is reused.

A complete ring buffer program

int handle_exec(struct trace_event_raw_sched_process_exec *ctx)
{
	struct task_struct *task;
	struct event *e;
	unsigned int fname_off;
	int ppid;

	task = (struct task_struct *)bpf_get_current_task();
	/* BPF_CORE_READ expands to bpf_probe_read_kernel() calls with
	 * CO-RE relocations for task->real_parent->tgid */
	ppid = BPF_CORE_READ(task, real_parent, tgid);

		return 0;

	/* Reserve space first: if the buffer is full we learn it now,
	 * before doing any work. */

	if (!e) {
		__sync_fetch_and_add(&dropped, 1);
		return 0;

/* execsnoop.c - load execsnoop.bpf.o and print events from the ring buffer */
#include <errno.h>
#include <signal.h>
#include <stdio.h>
#include <stdlib.h>
#include <bpf/libbpf.h>
#include "execsnoop.h"
#include "execsnoop.skel.h"   /* generated by: bpftool gen skeleton */

static volatile sig_atomic_t exiting;

static void on_sigint(int sig)
{
	exiting = 1;
}

/* Called by libbpf once per committed record, in reservation order. */
static int handle_event(void *ctx, void *data, size_t len)
{
	const struct event *e = data;

	printf("%-8d %-8d %-16s %s\n", e->pid, e->ppid, e->comm, e->filename);
	return 0;   /* a negative value stops ring_buffer__poll() */
}

int main(int argc, char **argv)
{
	struct ring_buffer *rb = NULL;
	struct execsnoop_bpf *skel;
	int err;

	signal(SIGINT, on_sigint);
	signal(SIGTERM, on_sigint);

	skel = execsnoop_bpf__open();             /* parse ELF, no syscalls yet */
	if (!skel) {
		fprintf(stderr, "failed to open BPF skeleton\n");
		return 1;
	}
	if (argc > 1)                              /* patch .rodata before load */
		skel->rodata->target_ppid = atoi(argv[1]);

	err = execsnoop_bpf__load(skel);          /* create maps, verify, JIT */
	if (err) {
		fprintf(stderr, "failed to load BPF object: %d\n", err);
		goto cleanup;
	}
	err = execsnoop_bpf__attach(skel);        /* attach to the tracepoint */
	if (err) {
		fprintf(stderr, "failed to attach: %d\n", err);
		goto cleanup;
	}

	rb = ring_buffer__new(bpf_map__fd(skel->maps.events), handle_event,
			      NULL, NULL);
	if (!rb) {
		err = -errno;
		fprintf(stderr, "failed to create ring buffer: %d\n", err);
		goto cleanup;
	}

	printf("%-8s %-8s %-16s %s\n", "PID", "PPID", "COMM", "FILENAME");
	while (!exiting) {
		err = ring_buffer__poll(rb, 100 /* timeout, ms */);
		if (err == -EINTR) {
			err = 0;
			break;
		}
		if (err < 0) {
			fprintf(stderr, "ring_buffer__poll: %d\n", err);
			break;
		}
	}
	/* .bss is mmap()ed: reading it is a plain memory load */
	fprintf(stderr, "dropped: %llu\n",
		(unsigned long long)skel->bss->dropped);

cleanup:
	ring_buffer__free(rb);
	execsnoop_bpf__destroy(skel);
	return err < 0 ? 1 : 0;
}

Choosing

Use the ring buffer for new code on 5.8+ kernels. Keep the perf buffer only if you must support older kernels, or if you need its per-sample lost_cb (the ring buffer has none; count drops in a global as above). For extreme rates you can still shard: put several ring buffers in an ARRAY_OF_MAPS or HASH_OF_MAPS and pick one by CPU or by hashed TGID, as ringbuf.rst suggests. libbpf's ring_buffer__add() lets one consumer poll all of them.

The other direction: user ring buffer

BPF_MAP_TYPE_USER_RINGBUF (6.1) reverses the roles: user space produces with libbpf's user_ring_buffer__reserve()/__submit(), and a BPF program drains it with bpf_user_ringbuf_drain(&map, callback, ctx, flags), which calls a BPF callback once per sample. In the mapping, only the consumer-position page is read-only for user space, the reverse of the kernel-producer layout. The kernel must "carefully check and validate each sample", as the comments in ringbuf.c put it.

Helpers: the stable kernel API

What a helper is

A helper is a kernel C function with at most five 64-bit arguments that a program calls with call imm, where imm is a number from enum bpf_func_id (BPF_FUNC_map_lookup_elem = 1, and so on). The arguments go in R1–R5 and the result comes back in R0, the calling convention of chapter 02. In C you call it through a function-pointer constant that libbpf generates in bpf_helper_defs.h, for example static long (*bpf_map_update_elem)(void *map, const void *key, const void *value, __u64 flags) = (void *) 2;.

Each helper has a struct bpf_func_proto that tells the verifier the argument types (pointer to map, pointer to readable memory of the size in the next argument, constant, context pointer, ...), the return type and whether it is GPL-only. Each program type has a get_func_proto() callback that decides which helpers it may call. That is why bpf_skb_store_bytes() exists for tc programs but not for kprobes, and bpf_probe_read_kernel() exists for tracing but not for socket filters. Here is the whole of one helper:

BPF_CALL_0(bpf_get_current_pid_tgid)
{
	struct task_struct *task = current;

	if (unlikely(!task))
		return -EINVAL;

	return (u64) task->tgid << 32 | task->pid;
}

const struct bpf_func_proto bpf_get_current_pid_tgid_proto = {
	.func		= bpf_get_current_pid_tgid,
	.gpl_only	= false,
	.ret_type	= RET_INTEGER,
};

Note the naming trap: the kernel's task->pid is what user space calls a thread ID, and tgid is what user space calls the process ID. So bpf_get_current_pid_tgid() >> 32 is the PID that ps shows, and the low 32 bits are the TID. Both are in the initial PID namespace; inside containers use bpf_get_ns_current_pid_tgid().

A few helpers you will use constantly

  • Map access: bpf_map_lookup_elem, bpf_map_update_elem, bpf_map_delete_elem, plus push/pop/peek for queues and bpf_for_each_map_elem (5.13) to iterate with a callback.
  • Context: bpf_get_current_pid_tgid (4.2), bpf_get_current_uid_gid, bpf_get_current_comm, bpf_get_current_task and bpf_get_current_task_btf (5.11, returns a BTF-typed pointer the verifier lets you dereference directly), bpf_ktime_get_ns, bpf_get_smp_processor_id.
  • Memory reads: bpf_probe_read_kernel and bpf_probe_read_user (and their _str variants), split out of the older bpf_probe_read in 5.5 so that kernel and user address spaces are never confused. They "safely attempt to read" an arbitrary address: a fault returns an error instead of oopsing. They are GPL-only. CO-RE's BPF_CORE_READ() macro expands to these calls with relocatable field offsets (chapter 06).
  • Output: bpf_ringbuf_*, bpf_perf_event_output, bpf_trace_printk (debug only; it writes to the shared trace pipe).
  • Control flow: bpf_tail_call, bpf_loop (5.17).

Why helpers are frozen

The kernel's BPF design Q&A states that BPF has a stable ABI: "BPF instructions, arguments to BPF programs, set of helper functions and their arguments, recognized return codes are all part of ABI". A helper, once merged, can never change its signature or semantics, and its number is reserved forever. That promise makes every new helper expensive, because a mistake stays forever. So the same document adds: "New BPF functionality is generally added through the use of kfuncs instead of new helpers." LWN's summary of Alexei Starovoitov's 2024 LSFMM+BPF talk counted 211 helpers and 164 kfuncs at the time (LWN). The helper list has barely grown since, and nearly all new kernel interfaces arrive as kfuncs.

kfuncs: kernel functions exposed through BTF

What and why

Linux 5.13 let BPF programs call kernel functions directly (LWN, "Calling kernel functions from BPF"). The first users were BPF TCP congestion-control algorithms, which wanted to reuse helpers such as tcp_cong_avoid_ai() that in-kernel algorithms already call. Instead of a helper number, a kfunc is identified by its BTF ID in the kernel's (or a module's) BTF. The verifier reads the function's BTF prototype to type-check arguments, so no hand-written bpf_func_proto is needed. A kfunc is an ordinary C function, often a thin wrapper, that a subsystem chooses to expose. Kernel modules can register kfuncs too, which they cannot do with helpers.

The price is stability. The kfunc documentation is explicit: kfuncs "do not have a stable interface and can change from one kernel release to another". Their lifecycle is compared to EXPORT_SYMBOL_GPL. Maintainers weigh how widely a kfunc is used, and a KF_DEPRECATED flag announces a planned removal. Even so, "a kfunc will never have any hard stability guarantees".

Calling a kfunc from BPF

On the BPF side you declare the function extern with the __ksym attribute (__attribute__((section(".ksyms")))) and call it. libbpf resolves the name against the running kernel's BTF at load time and emits a call instruction with src_reg = BPF_PSEUDO_KFUNC_CALL and the BTF ID as immediate. Declare a kfunc __weak and test it with bpf_ksym_exists() to load on kernels that lack it; the verifier removes the dead branch. Recent vmlinux.h files generated by bpftool can include kfunc prototypes themselves, which is why some selftests define BPF_NO_KFUNC_PROTOTYPES.

/* ... */

static inline int tasks_kfunc_map_insert(struct task_struct *p)
{
	struct __tasks_kfunc_map_value local, *v;
	long status;
	struct task_struct *acquired, *old;
	s32 pid;

	status = bpf_probe_read_kernel(&pid, sizeof(pid), &p->pid);
	if (status)
		return status;

	local.task = NULL;
	status = bpf_map_update_elem(&__tasks_kfunc_map, &pid, &local, BPF_NOEXIST);
	if (status)
		return status;

	v = bpf_map_lookup_elem(&__tasks_kfunc_map, &pid);
	if (!v) {
		bpf_map_delete_elem(&__tasks_kfunc_map, &pid);
		return -ENOENT;
	}

	acquired = bpf_task_acquire(p);
	if (!acquired)
		return -ENOENT;

	old = bpf_kptr_xchg(&v->task, acquired);
	if (old) {
		bpf_task_release(old);
		return -EEXIST;
	}

	return 0;
}

This one function uses every concept in the chapter so far: a hash map, three map helpers, bpf_probe_read_kernel(), two kfuncs and a kptr. The map value contains a field tagged __kptr, a referenced kernel pointer stored in a map. The verifier knows that bpf_task_acquire() returns a reference that must be released. Storing it with bpf_kptr_xchg() (5.19) transfers ownership to the map, and the old value that comes back is a new reference the program must release. The kernel drops references still held in a map when the element or map is freed.

Two refinements are recent. First, the current documentation says "All kfuncs now require trusted arguments by default": a pointer argument must come straight from a hook argument or an acquire kfunc, not from walking another pointer. BPF-to-BPF calls

Before 4.16 every function in a BPF program had to be __always_inline. BPF-to-BPF calls added a real call to another function inside the same program (src_reg = BPF_PSEUDO_CALL, immediate = relative instruction offset). The callee gets its own stack frame; R1–R5 carry arguments, R0 the result, and R6–R9 are preserved, as in chapter 02. The verifier enforces a maximum call depth (MAX_CALL_FRAMES, currently 16 in include/linux/bpf_verifier.h; older kernels and documentation say 8) and a combined stack limit over the whole call chain.

C linkage decides how a subprogram is verified:

  • Static functions (static __noinline) are verified in the context of each call site, with the caller's exact register state. This is precise, but the function is re-verified at every call.
  • Global functions (non-static) are verified once, on their own, assuming only what their BTF prototype says about the arguments. That saves verification work and allows separately loaded code (freplace) to replace them. The cost is that the body must cope with any argument value: a pointer argument may be NULL unless it is annotated (for example __arg_nonnull).

Callbacks build on the same machinery. bpf_loop(), bpf_for_each_map_elem(), bpf_timer_set_callback() and bpf_user_ringbuf_drain() all take a pointer to a static BPF function, which the verifier checks as a subprogram.

Tail calls

A tail call, available since 4.2, is a jump into another program. The caller's frame is reused, so nothing comes back. bpf_tail_call(ctx, &prog_array, index) looks up a program in a BPF_MAP_TYPE_PROG_ARRAY and, if found, starts executing it with the same context. If the slot is empty, the call does nothing and the caller continues with the next instruction. The uapi documentation explains the two original motivations: "raising the maximum number of available eBPF instructions" (each program is verified separately) and executing "given programs in conditional blocks". Cilium, for example, uses tail calls to split its datapath into stages. To bound the run time, a chain may perform at most MAX_TAIL_CALL_CNT = 33 tail calls.

Because the prog array is a map, user space can replace a program at runtime by updating one slot, which is how some tools hot-swap parsing logic without detaching. The JIT turns a call with a constant index into a direct jump that is patched when the slot changes; libbpf's bpf_tail_call_static() forces the index to stay a constant in the generated code. Mixing tail calls with BPF-to-BPF calls was not allowed at first. It became possible on x86-64 in 5.10, arm64 in 6.0, s390 in 6.3 and LoongArch in 6.4. When a subprogram performs a tail call, the verifier caps the stack of the frames above it: it rejects the program with "tail_calls are not allowed when call stack of previous frames is N bytes. Too large" once that stack reaches 256 bytes. The reason is that each tail call in a nested frame can leave the caller's frames on the stack.

Concurrency: atomics, per-CPU data and spin locks

The same program runs on many CPUs at once, and user space can update maps concurrently. In order of preference, your tools are:

  1. Per-CPU maps: no sharing, no synchronisation, merge in user space.
  2. Atomic instructions: __sync_fetch_and_add and friends compile to BPF atomic ops (add, and, or, xor, xchg, cmpxchg). Fine for single counters.
  3. struct bpf_spin_lock (5.1): for updating several fields of one map value together. See LWN's "Concurrency management in BPF".

The lock lives inside the map value and is taken with bpf_spin_lock(&val->lock). The verifier enforces the rules listed in the helper's uapi documentation: a map value may hold one lock, a program may hold one lock at a time, every path must unlock before returning, BTF for the value is mandatory, and the lock field cannot be read or written directly. User space participates through BPF_F_LOCK on lookup and update; a plain syscall lookup does not copy the lock field. The selftest implements a small token-bucket "virtual queue":

struct bpf_vqueue {
	struct bpf_spin_lock lock;
	/* 4 byte hole */
	unsigned long long lasttime;
	int credit;
	unsigned int rate;
};

struct {
	__uint(type, BPF_MAP_TYPE_ARRAY);
	__uint(max_entries, 1);
	__type(key, int);
	__type(value, struct bpf_vqueue);
} vqueue SEC(".maps");

As always, the verifier of your target kernel has the final word.

Timers

Programs run only when an event fires. Some jobs need work later: expire an idle flow, re-arm a watchdog, poll something periodically. struct bpf_timer (5.15) is a field inside a map value, like a spin lock. The API is bpf_timer_init(timer, map, clockid) (CLOCK_MONOTONIC, CLOCK_REALTIME or CLOCK_BOOTTIME), bpf_timer_set_callback(timer, fn), bpf_timer_start(timer, nsecs, flags) and bpf_timer_cancel(timer). The callback is a static BPF function that receives the map, the key and the timer, and it can re-arm itself. Timers belong to the map. When the map loses its last user-space reference (all fds closed and no pin), the kernel cancels and frees its timers, and bpf_timer_init() returns -EPERM on a map that user space no longer holds.

Benefits and limitations

What this design gets right

  • Safety by typing. Every way out of the sandbox (map access, helper, kfunc, call) has a signature the verifier checks. Ownership of ring buffer records and kernel objects is tracked statically, so leaks are load-time errors, not production incidents.
  • Lifetimes via file descriptors. Maps and programs are ordinary kernel objects with refcounts, fds, IDs and bpffs paths, so standard tools (bpftool, ls /sys/fs/bpf) can inspect them.
  • Zero-copy paths. mmap-able arrays, globals, ring buffers and arenas let user space and programs share memory with no syscalls in the hot path.
  • Evolvability. The stable helper set keeps old programs running. kfuncs let subsystems, including modules, add capabilities without committing to them forever.

Where it hurts

  • Fixed sizes. Most maps are sized at creation. Full hash maps fail inserts, and an LRU evicts silently. (The new resizable hash addresses part of this.)
  • Feature skew. The table above spans 3.19 to 6.9 and later. Portable tools must probe for features (bpftool feature probe, libbpf_probe_bpf_map_type()) and have fallbacks, for example perf buffer when ring buffer is missing.
  • kfunc churn. A program using kfuncs may fail to load on the next kernel. The kfunc docs ask users to make their use cases known upstream.
  • Limited synchronisation. One spin lock at a time, no sleeping locks in non-sleepable programs, and user space can only join in through BPF_F_LOCK.
  • Data structures. Maps are not general data structures. Arenas, BPF linked lists and red-black trees fill the gap but are new, and their APIs are kfuncs and therefore unstable.
  • Ring buffer caveats. A single slow producer holds back all records reserved after it. Reservation can fail under NMI contention. Reserve sizes must be constants. There is no built-in lost-sample count.

Related work

  • Userspace eBPF runtimes must re-create maps outside the kernel. bpftime (chapter 14) implements shared-memory maps that kernel-style programs in different processes, and the kernel itself, can share.
  • eBPF for Windows and other platforms implement a compatible subset of map types and helper IDs; see chapter 08.
  • Higher-level frontends hide maps behind language constructs: bpftrace's @counts[comm] = count() becomes a per-CPU hash, and bcc's BPF_HASH/BPF_PERF_OUTPUT macros wrap the same types (chapter 08).
  • Reference documentation. The community-maintained eBPF Docs site has a page per map type, helper and kfunc with version information. It is a good companion to the kernel's own docs.
  • Program types decide which helpers and kfuncs you can call and which context you get; see chapter 05. The networking-specific maps are in chapter 07.

Check your understanding

Q1. A tracing tool must report fork, exec and exit events of short-lived processes in the order they happened. Which output mechanism fits best on a 6.x kernel?

The ring buffer is shared by all CPUs and delivers records in reservation order. The perf buffer has one ring per CPU, so events of a process that migrates between CPUs can arrive out of order, which is the motivating example in Nakryiko's post and in ringbuf.rst.

Q2. A program calls bpf_ringbuf_reserve(), checks for NULL, and on one branch returns without calling submit or discard. What happens?

Reserved records are tracked like acquired references. The verifier reports an unreleased reference (on 6.1: Unreleased reference id=3 alloc_insn=28) and refuses to load the program.

Q3. What is the main difference in guarantees between a helper and a kfunc?

Per bpf_design_QA.rst, helpers and their arguments are ABI. kfuncs.rst says kfuncs "do not have a stable interface". It is the other way round for typing: kfuncs are typed through BTF. Only kfuncs flagged KF_SLEEPABLE need sleepable programs.

Q4. Your loader sets skel->rodata->target_ppid before __load(). Why can the verifier remove the filtering branch when the value is 0?

libbpf writes .rodata, freezes the map and marks it BPF_F_RDONLY_PROG. The verifier can then read the value and prune dead branches. volatile only stops the compiler from folding the initial value.

Q5. You want per-thread state that disappears automatically when the thread exits, without hooking exit yourself. Which map type?

Task local storage hangs the value off the task_struct, and the kernel frees it when the task is freed. An LRU would evict by pressure, not by lifetime, and TIDs get reused.

Q6. What happens when bpf_tail_call() finds an empty slot in the prog array?

The uapi documentation: "If the call fails, then the helper has no effect, and the caller continues to run its subsequent instructions." It also fails after 33 chained tail calls (MAX_TAIL_CALL_CNT).
