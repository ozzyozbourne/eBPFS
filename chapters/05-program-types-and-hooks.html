Chapter 05

Program types and hooks: where eBPF runs

An eBPF program does nothing until it is attached to a hook. The hook decides when the program runs, what context pointer it receives, which helpers it may call, whether its return value means anything, and how much each run costs. This chapter goes through the hooks one family at a time.

Prerequisites: 03, 04Repos: libbpf-bootstrap, bpf-developer-tutorial~50 min

Why this matters

Chapters 02–04 described the eBPF machine: the instruction set, the verifier, and maps, helpers and kfuncs. None of that says when a program runs. The kernel answers that with the program type (for example BPF_PROG_TYPE_KPROBE, BPF_PROG_TYPE_LSM, BPF_PROG_TYPE_STRUCT_OPS) and, inside many types, an attach type (for example BPF_TRACE_FENTRY versus BPF_TRACE_FEXIT). Together they fix four things the verifier checks at load time:

  • The context. R1 holds a pointer to a type-specific structure: struct pt_regs for a kprobe, struct __sk_buff for a cgroup packet filter, struct bpf_sock_addr for a connect() hook, or the typed arguments of a kernel function for fentry and LSM programs.
  • Which helpers and kfuncs exist. bpf_override_return() exists for kprobes, bpf_sysctl_get_name() for sysctl hooks, and the scx_bpf_* kfuncs for sched_ext.
  • The meaning of the return value. For tracing it is mostly ignored. For cgroup hooks it is allow (1) or deny (0). For LSM it is 0 or a negative errno. For struct_ops it is the return value of the kernel callback the program implements.
  • Whether the program may sleep. Sleepable variants such as lsm.s, uprobe.s and fentry.s may call helpers that fault in user memory.

Choosing a hook is the first design decision in any eBPF tool. The same question ("which files does this process open?") can be answered with a kprobe, an fentry, a syscall tracepoint, an LSM hook or a uprobe on libc. These differ in stability, overhead and power by an order of magnitude or more.

Key idea

A hook is a contract with three parts. The kernel promises to call your program at a specific point with a specific context. The verifier lets you do only what that context allows. Your return value is either ignored (observability) or obeyed (policy and extension). Read every row of the comparison table below as a statement of that contract.

How libbpf names hooks: SEC()

With libbpf you rarely set the program type by hand. You put the function in an ELF section, and libbpf maps the section name to a program type, an attach type and, when the name carries enough detail, an auto-attach target. The kernel documentation table Program Types and ELF Sections is the authoritative list. A trailing + in that table means the name accepts extras after a /: SEC("kprobe/do_unlinkat") auto-attaches, while a bare SEC("kprobe") loads but needs a manual attach call. A .s suffix (lsm.s, uprobe.s, fentry.s) marks a sleepable program. How the skeleton turns these sections into bpf() calls is covered in chapter 06.

The map: hooks on the kernel/user stack

Figure 5.1 places every hook family covered in this chapter on the stack. Hooks in the left half observe: they read state and push events to maps or ring buffers and cannot change the outcome (with two narrow exceptions, fmod_ret and bpf_override_return). Hooks in the right half decide or implement: their return value, or the struct they fill in, changes what the kernel does.

Tracing the kernel

kprobe and kretprobe: attach anywhere

What it is. A kprobe is the oldest dynamic kernel probe. It can be placed on almost any instruction of almost any kernel function, by symbol name and optional offset. A kretprobe fires when that function returns. BPF programs have been able to attach to kprobes since Linux 4.1.

How it works. The classic mechanism replaces the first byte of the probed instruction with a breakpoint (int3 on x86). When the CPU hits it, the trap handler runs the attached handlers, then executes the displaced instruction out of line and resumes. Two optimisations make this cheaper in practice. A probe at a function's ftrace call site (the function entry on kernels built with ftrace) can use ftrace instead of a breakpoint. "Optprobes" can replace the breakpoint with a jump. A kretprobe swaps the return address on entry so that the function "returns" into a trampoline that runs the handler. BPF programs see struct pt_regs, so they must know the calling convention. The BPF_KPROBE and BPF_KRETPROBE macros in bpf_tracing.h hide that and give you named arguments.


SEC("kprobe/do_unlinkat")
int BPF_KPROBE(do_unlinkat, int dfd, struct filename *name)
{
    pid_t pid;
    const char *filename;

    pid = bpf_get_current_pid_tgid() >> 32;
    filename = BPF_CORE_READ(name, name);
    bpf_printk("KPROBE ENTRY pid = %d, filename = %s\n", pid, filename);
    return 0;
}

SEC("kretprobe/do_unlinkat")
int BPF_KRETPROBE(do_unlinkat_exit, long ret)
{
    pid_t pid;

    pid = bpf_get_current_pid_tgid() >> 32;
    bpf_printk("KPROBE EXIT: pid = %d, ret = %ld\n", pid, ret);
    return 0;
}

Pointer arguments are not trusted. name is just a number taken from a register, so the program reads through it with BPF_CORE_READ (a relocatable bpf_probe_read_kernel; see chapter 06). Without that, the verifier rejects the dereference.

Strengths and limits. Kprobes reach everything, including static functions and mid-function offsets, which no other hook can do. But function names and signatures are not a stable ABI. Inlined functions disappear, renamed functions break the attach, and functions marked NOKPROBE_SYMBOL cannot be probed. Variants soften some of this. ksyscall/<name> lets libbpf work out the architecture-specific syscall wrapper name. kprobe.multi (5.18) attaches one program to many functions through the fprobe/ftrace API with a single link, which is far faster to set up than thousands of single kprobes. kprobe.session (6.10) runs one program on both entry and return of each call.

fentry, fexit, fmod_ret: the BPF trampoline

Why it exists. Kprobes pay for a trap and give you raw registers. In November 2019 Alexei Starovoitov posted the BPF trampoline series, merged for 5.5. Its cover letter describes fentry/fexit programs as "roughly equivalent to kprobe/kretprobe", but "unlike k[ret]probe there is practically zero overhead to call a set of BPF programs before or after kernel function". The trampoline's stated goals are "to translate kernel calling convention into BPF calling convention" and "to call a set of programs efficiently".

How it works. Kernels built with ftrace start every traceable function with a 5-byte nop (on x86). Attaching an fentry program makes the kernel JIT a small piece of machine code, the trampoline, for that one function. It then uses register_ftrace_direct() and text patching to turn the nop into a call to it. The trampoline saves the argument registers into a stack array, calls each fentry program with a pointer to that array, then calls each fmod_ret program. Unless an fmod_ret program asked to skip it, the trampoline calls the original function body. Finally it calls each fexit program with the arguments and the return value. Because the target's BTF prototype is known, the verifier treats the arguments as typed, BTF-tracked pointers, so name->name is a plain load. The same machinery powers LSM programs, tp_btf, freplace (replace a global function inside another BPF program) and struct_ops.

Here is the fentry/fexit version of the kprobe example. Note the direct name->name dereference, and that fexit gets both the arguments and ret. A kretprobe only sees the return value, because the argument registers have been reused by the time the function returns.

SEC("fentry/do_unlinkat")
int BPF_PROG(do_unlinkat, int dfd, struct filename *name)
{
    pid_t pid;

    pid = bpf_get_current_pid_tgid() >> 32;
    bpf_printk("fentry: pid = %d, filename = %s\n", pid, name->name);
    return 0;
}

SEC("fexit/do_unlinkat")
int BPF_PROG(do_unlinkat_exit, int dfd, struct filename *name, long ret)
{
    pid_t pid;

    pid = bpf_get_current_pid_tgid() >> 32;
    bpf_printk("fexit: pid = %d, filename = %s, ret = %ld\n", pid, name->name, ret);
    return 0;
}

fmod_ret (attach type BPF_MODIFY_RETURN, 5.7) is the one tracing variant whose return value matters. A non-zero return skips the original function and becomes its return value. The verifier only allows it on targets where that is designed to be safe: check_attach_modify_return() in kernel/bpf/verifier.c accepts functions on the error-injection list (ALLOW_ERROR_INJECTION) and functions whose name starts with security_. (On kernels built without CONFIG_FUNCTION_ERROR_INJECTION, the error-injection list is replaced by the architecture's syscall entry functions, such as __x64_sys_*.) The kernel selftest shows the ordering fentry → fmod_ret → fexit:

__u64 fmod_ret_result = 0;
SEC("fmod_ret/bpf_modify_return_test")
int BPF_PROG(fmod_ret_test, int a, int *b, int ret)
{
    if (bpf_get_current_pid_tgid() >> 32 != test_pid)
        return ret;
    sequence++;
    /* This is the first fmod_ret program, the ret passed should be 0 */
    fmod_ret_result = (sequence == 2 && ret == 0);
    return input_retval;
}

__u64 fexit_result = 0;
SEC("fexit/bpf_modify_return_test")
int BPF_PROG(fexit_test, int a, __u64 b, int ret)
{
    if (bpf_get_current_pid_tgid() >> 32 != test_pid)
        return 0;
    sequence++;
    /* If the input_reval is non-zero a successful modification should have
     * occurred.
     */
    if (input_retval)
        fexit_result = (sequence == 3 && ret == input_retval);
    else
        fexit_result = (sequence == 3 && ret == 4);

    return 0;
}

fsession (BPF_TRACE_FSESSION, first in the v7.0 UAPI header) merges fentry and fexit into one program. The kernel gives each call an 8-byte cookie, so the program needs no hash map keyed by thread ID to carry a timestamp from entry to exit. bpf-developer-tutorial lesson 52 uses it to time vfs_read. bpf_session_is_return(ctx) tells the two runs apart:

SEC("fsession/vfs_read")
int BPF_PROG(measure_vfs_read, struct file *file, char *buf, size_t count,
         loff_t *pos, ssize_t ret)
{
    __u64 pid_tgid = bpf_get_current_pid_tgid();
    __u64 *started = bpf_session_cookie(ctx);
    struct latency_event *event;
    struct inode *inode;
    __u32 device;
    __u64 latency;

    if (!bpf_session_is_return(ctx)) {
        if (target_tgid && pid_tgid >> 32 != target_tgid) {
            *started = 0;
            return 0;
        }
        *started = bpf_ktime_get_ns();
        return 0;
    }

    if (!*started)
        return 0;

    latency = bpf_ktime_get_ns() - *started;
/* ... */
    return 0;
}
Limits of fentry

fentry needs BTF for the target (CONFIG_DEBUG_INFO_BTF), a JIT, and arch support for trampolines. It can only attach at function entry, never mid-function, and only to functions ftrace can trace (not inlined, not notrace). Each program is attached per function. A wildcard over thousands of functions is the job of kprobe.multi. When fentry works, prefer it to kprobe: it is faster and the code is simpler.

Static tracepoints, raw tracepoints and tp_btf

What they are. Tracepoints are hooks that kernel developers placed in the source on purpose: sched:sched_switch, syscalls:sys_enter_openat, block:block_rq_complete and thousands more. They are the closest thing to a stable tracing ABI the kernel offers. Their names and fields change far less often than internal function signatures, so production tools prefer them whenever a tracepoint exists for the event of interest.

There are three ways for BPF to consume the same tracepoint:

  • tp/<category>/<name> (BPF_PROG_TYPE_TRACEPOINT, 4.7). The program receives the tracepoint's formatted record, the same struct described in /sys/kernel/tracing/events/<cat>/<name>/format that ftrace and perf use. The kernel fills that record before calling you, which costs something, but the layout is the easiest to consume.
  • raw_tp/<name> (BPF_PROG_TYPE_RAW_TRACEPOINT, 4.17). The program receives the raw arguments the kernel passed to trace_<name>(), as an array of u64, with no record built. It is cheaper, but pointers are untyped and must be read through bpf_probe_read_kernel/CO-RE.
  • tp_btf/<name> (BPF_TRACE_RAW_TP inside BPF_PROG_TYPE_TRACING, 5.5). This is a raw tracepoint with BTF types: arguments arrive typed, as with fentry, and can be dereferenced directly.

The libbpf-bootstrap minimal example is the smallest program in this curriculum. It is a classic tracepoint on write(2), filtered by a PID that user space writes into a global variable before loading:

// SPDX-License-Identifier: GPL-2.0 OR BSD-3-Clause
/* Copyright (c) 2020 Facebook */
#include <linux/bpf.h>
#include <bpf/bpf_helpers.h>

char LICENSE[] SEC("license") = "Dual BSD/GPL";

int my_pid = 0;

SEC("tp/syscalls/sys_enter_write")
int handle_tp(void *ctx)
{
    int pid = bpf_get_current_pid_tgid() >> 32;

    if (pid != my_pid)
        return 0;

    bpf_printk("BPF triggered from PID %d.\n", pid);

    return 0;
}

For the scheduler, bpf-developer-tutorial's runqlat (lesson 9) uses raw tracepoints, and the wall-clock profiler (lesson 32) ships both a tp_btf and a raw_tp version of the same handler. The user-space loader picks tp_btf when the kernel supports it:

int BPF_PROG(handle_sched_wakeup, struct task_struct *p)
{
    return trace_enqueue(BPF_CORE_READ(p, tgid), BPF_CORE_READ(p, pid));
}

SEC("raw_tp/sched_wakeup_new")
int BPF_PROG(handle_sched_wakeup_new, struct task_struct *p)
{
    return trace_enqueue(BPF_CORE_READ(p, tgid), BPF_CORE_READ(p, pid));
}

SEC("raw_tp/sched_switch")
int BPF_PROG(handle_sched_switch, bool preempt, struct task_struct *prev, struct task_struct *next)
{
    return handle_switch(preempt, prev, next);
}
SEC("tp_btf/sched_switch")
int BPF_PROG(sched_switch, bool preempt, struct task_struct *prev, struct task_struct *next)
{

}

SEC("raw_tp/sched_switch")
int BPF_PROG(sched_switch_raw, bool preempt, struct task_struct *prev, struct task_struct *next)
{

When no tracepoint exists you fall back to fentry or kprobe. When one does, the tracepoint is the better choice for anything you plan to ship.

perf_event: sampling

A perf_event program (4.9) attaches to a perf event opened with perf_event_open(2): a CPU-clock timer, a hardware counter overflow (cycles, cache misses) or a software event. The kernel runs the program each time the event fires, often from NMI context for hardware counters. The context is struct bpf_perf_event_data, which wraps the interrupted registers and the sample period. The classic use is a CPU profiler: on each tick, capture kernel and user stacks and count them. libbpf-bootstrap's profile does exactly that:

SEC("perf_event")
int profile(void *ctx)
{
    int pid = bpf_get_current_pid_tgid() >> 32;
    int cpu_id = bpf_get_smp_processor_id();
    struct stacktrace_event *event;
    int cp;

    event = bpf_ringbuf_reserve(&events, sizeof(*event), 0);
    if (!event)
        return 1;

    event->pid = pid;
    event->cpu_id = cpu_id;

    if (bpf_get_current_comm(event->comm, sizeof(event->comm)))
        event->comm[0] = 0;

    event->kstack_sz = bpf_get_stack(ctx, event->kstack, sizeof(event->kstack), 0);

    event->ustack_sz =
        bpf_get_stack(ctx, event->ustack, sizeof(event->ustack), BPF_F_USER_STACK);

    bpf_ringbuf_submit(event, 0);

    return 0;
}

Overhead scales with the sample frequency, not with how busy the code is, which is why sampling profilers can run all the time in production. User space opens one perf event per CPU and attaches the same program to each with bpf_program__attach_perf_event(). Profiling with this hook is the subject of chapter 22.

Tracing user space: uprobes and USDT

What a uprobe is

A uprobe is a kprobe for user-space code. You name an ELF file and a function or offset (/bin/bash:readline, libc.so.6:malloc, /proc/self/exe:uprobed_sub), and the kernel runs your BPF program whenever any process (or one PID, if you ask) executes that address. A uretprobe fires on return. BPF has been able to attach to uprobes since Linux 4.3: the BPF call trace_call_bpf appears in kernel/trace/trace_uprobe.c in v4.3 and not in v4.2. The program type is still BPF_PROG_TYPE_KPROBE and the context is still struct pt_regs, now holding user registers. That is why the examples below use BPF_KPROBE even on a uprobe.

int BPF_KPROBE(uprobe_add, int a, int b)
{
    bpf_printk("uprobed_add ENTRY: a = %d, b = %d", a, b);
    return 0;
}

SEC("uretprobe")
int BPF_KRETPROBE(uretprobe_add, int ret)
{
    bpf_printk("uprobed_add EXIT: return = %d", ret);

}

The first tab shows both styles. A bare SEC("uprobe") needs a manual bpf_program__attach_uprobe_opts() call. A full SEC("uprobe//proc/self/exe:uprobed_sub") is auto-attached by the skeleton. The second tab shows that libbpf resolves func_name to a file offset by reading the ELF symbol table, and that the PID argument chooses between "this process" (0), any process (-1) and a specific PID. The third tab is the classic bashreadline tool: a uretprobe on bash's readline() copies the returned string with bpf_probe_read_user_str, so every command typed into any bash on the machine shows up in the trace pipe.

How a uprobe works inside the kernel

The details matter because they explain the cost, and that cost is why userspace eBPF runtimes such as bpftime exist. The walkthrough follows kernel/events/uprobes.c and arch/x86/kernel/uprobes.c at mainline commit d68ce4e7.

1. Register: an inode and an offset

A uprobe is keyed by (inode, file offset), not by process or virtual address. That is why one attach covers every process that maps the binary, including ones started later. install_breakpoint() runs for each existing mapping, and the mmap path (uprobe_mmap) installs it into new ones.

2. Write int3 into the process's copy of the page

uprobe_write_opcode() writes UPROBE_SWBP_INSN, which is 0xcc (int3, one byte) on x86, over the first byte of the probed instruction. The write goes into a copy-on-write copy of the page in that mapping. The file on disk and the page cache are unchanged, and unprobed processes keep sharing the original page. The displaced instruction is decoded and saved so it can be emulated or executed later.

3. The thread hits the breakpoint: a trap

When a thread executes the address, the CPU raises a breakpoint exception: a switch from user mode to kernel mode with a full register save. The notifier sets TIF_UPROBE. On the way back towards user space, uprobe_notify_resume() calls handle_swbp(), which finds the uprobe for the address with find_active_uprobe_rcu().

4. Run the consumers

handler_chain() runs every consumer, including your BPF program, with the trapped user pt_regs. For a uretprobe, prepare_uretprobe() saves the real return address and replaces it on the user stack with the address of a uretprobe trampoline in a special mapping.

5. Execute the displaced instruction

The original instruction is gone from the page, so the kernel must still run it. Many x86 instructions (nops, pushes, jumps, calls) are emulated in the kernel. Otherwise the instruction is single-stepped out of line in a per-process "[uprobes]" XOL (execute-out-of-line) page, which costs a second trap. Then the thread returns to user space after the probe.

6. Return probes and recent speed-ups

When the probed function returns, it lands in the trampoline. Historically that was another int3. Since Linux 6.11 on x86-64 the trampoline instead calls the dedicated uretprobe syscall (uretprobe(2), SIGILL if called from anywhere else). Kernelnewbies summarises the speed-up as "10-30%". Since 6.18 a probe on a 5-byte nop can be rewritten after its first hit into a call to a "[uprobes-trampoline]" page that issues the new uprobe syscall (syscall 336 in v6.18's syscall_64.tbl), avoiding the exception.

What it costs

A kprobe trap stays inside the kernel. A uprobe hit pays a user→kernel→user round trip per call of the probed function. That is fine for readline() but painful for malloc() or a per-request function in a busy server. The clearest public numbers come from Jiri Olsa's December 2024 patch series "uprobes: Add support to optimize usdt probes on x86_64". It reports loop throughput of a selftest benchmark on his machine (millions of hits per second, higher is better):

Benchmark (from the cover letter)M/s≈ ns per iteration
usermode-count (plain loop, no probe)233.8314
syscall-count (one cheap syscall per iteration)12.10783
uprobe-nop (int3 uprobe on a nop)3.246308
uprobe-nop5 (proposed syscall-based path)6.751148
uretprobe-nop (int3 entry + return through the 6.11 uretprobe syscall)1.740575

The nanosecond column is just 1/throughput, computed here. It includes loop and program overhead and holds only for that machine, so read it as a ratio. On that machine a breakpoint uprobe cost about four syscalls' worth of time and a return probe about seven. The syscall-based path that later reached mainline (6.18 for the entry probe, 6.11 for return probes) narrows the gap but does not close it: every hit still enters the kernel.

Why bpftime exists

Running the uprobe program inside the traced process removes the mode switch altogether. bpftime patches the target function with a jump into a userspace eBPF VM and shares maps with the kernel. Its OSDI '25 paper, "Extending Applications Safely and Efficiently", reports that bpftime "improves the throughput of profiling microservices by a factor of 1.5 compared to eBPF". The mechanism and its trade-offs are in chapter 14, and the attach modes in chapter 15. The steps above are the baseline they compare against.

USDT: static probes in user space

USDT (user statically defined tracing, the DTrace/SystemTap sdt.h convention) is to uprobes what tracepoints are to kprobes. The application author puts a macro such as DTRACE_PROBE2(provider, name, a, b) in the source. The compiler emits a nop at that point plus an ELF note (.note.stapsdt) that records the address and, for each argument, where it lives (register, stack slot or constant). An optional semaphore lets the application skip expensive argument preparation unless a tracer is attached. glibc, Python, OpenJDK, PostgreSQL, Node.js and others ship such probes.

At attach time libbpf reads the note, puts a uprobe on the nop, and stores an argument spec that bpf_usdt_arg() and the BPF_USDT macro (usdt.bpf.h) decode at run time. A USDT probe costs nothing when no one is attached and the same as a uprobe when someone is.

SEC("usdt/libc.so.6:libc:setjmp")
int BPF_USDT(usdt_auto_attach, void *arg1, int arg2, void *arg3)
{
    pid_t pid = bpf_get_current_pid_tgid() >> 32;

    if (pid != my_pid)
        return 0;

    bpf_printk("USDT auto attach to libc:setjmp: arg1 = %lx, arg2 = %d, arg3 = %lx", arg1, arg2,
           arg3);
    return 0;
}

Security hooks

BPF LSM

What it is. The Linux Security Module framework puts security_*() calls at every security-relevant decision: opening files, executing binaries, mmap/mprotect, socket connect and bind, the bpf() syscall itself and many more (the full list is in include/linux/lsm_hook_defs.h). SELinux, AppArmor and the others implement these hooks in C. Since 5.7, BPF_PROG_TYPE_LSM lets privileged users attach eBPF programs to the same hooks to build mandatory access control and audit policies at run time (kernel docs).

How it works. LSM programs attach through the BPF trampoline, like fentry, and get the hook's typed arguments plus a final ret argument holding the verdict of earlier BPF LSM programs on that hook. Returning 0 allows the operation, and a negative errno denies it. The examples pass a non-zero ret straight through so that they never turn an earlier BPF program's denial into an allow. A denial by another LSM such as SELinux cannot be overridden at all: the LSM framework (call_int_hook() in security/security.c) stops at the first module that returns a non-default value. Sleepable lsm.s/ programs may call helpers such as bpf_d_path() or bpf_ima_inode_hash() that can fault. Since 6.0, lsm_cgroup/ (BPF_LSM_CGROUP) attaches a hook to a cgroup instead of the whole system. Two conditions apply: the kernel needs CONFIG_BPF_LSM=y, and bpf must be in the active LSM list (cat /sys/kernel/security/lsm), usually set with the lsm= boot parameter.

#include "vmlinux.h"
#include <bpf/bpf_helpers.h>
#include <bpf/bpf_tracing.h>

char LICENSE[] SEC("license") = "GPL";

#define EPERM  1

SEC("lsm/bpf")
int BPF_PROG(lsm_bpf, int cmd, union bpf_attr *attr, unsigned int size, int ret)
{
    /* ret is the return value from the previous BPF program
     * or 0 if it's the first hook.
     */
    if (ret != 0)
        return ret;

    bpf_printk("LSM: block bpf() worked");
    return -EPERM;
}

That five-line policy makes every later bpf() syscall fail with EPERM, so it is a good way to lock a machine after loading its programs. It is also a reminder that LSM programs are policy: a bug locks you out. A more realistic one from the tutorial (lesson 19) blocks IPv4 connections to 1.1.1.1:

SEC("lsm/socket_connect")
int BPF_PROG(restrict_connect, struct socket *sock, struct sockaddr *address, int addrlen, int ret)
{
    // Satisfying "cannot override a denial" rule
    if (ret != 0)
    {
        return ret;
    }

    // Only IPv4 in this example
    if (address->sa_family != AF_INET)
    {
        return 0;
    }

    // Cast the address to an IPv4 socket address
    struct sockaddr_in *addr = (struct sockaddr_in *)address;

    // Where do you want to go?
    __u32 dest = addr->sin_addr.s_addr;
    bpf_printk("lsm: found connect to %d", dest);

    if (dest == blockme)
    {
        bpf_printk("lsm: blocking %d", dest);
        return -EPERM;
    }
    return 0;
}

Projects built on this hook include Tetragon and KubeArmor (chapter 08). Chapter 24 uses LSM-style enforcement for AI agents.

What about seccomp?

seccomp is often mentioned with BPF, and the name is accurate, but the filter language is classic BPF, not eBPF. A seccomp filter is a cBPF program installed by the process itself with seccomp(2) or prctl. It sees only struct seccomp_data (syscall number, architecture, instruction pointer and the six raw argument values), cannot dereference pointers, has no maps, and returns actions such as SECCOMP_RET_ALLOW, _ERRNO, _KILL_PROCESS or _USER_NOTIF. There is no eBPF seccomp program type in mainline. The design keeps seccomp usable by unprivileged sandboxes such as browsers, container runtimes and systemd. If you need pointer arguments (the path being opened, the address being connected to), use a BPF LSM hook, which runs after the kernel has copied and resolved them. That also avoids the time-of-check/time-of-use race of inspecting user memory. Chapter 01 covers where cBPF comes from.

cgroup programs

cgroup programs attach to a cgroup v2 directory instead of a kernel function. They run only for tasks or sockets in that cgroup and its descendants, so a container runtime or systemd can apply a policy to "this service" with no global hook. All of them are policy hooks: by convention, return 1 to allow and 0 to deny (the syscall then fails with EPERM). Attachment uses BPF_PROG_ATTACH or a BPF link on the cgroup's file descriptor. Flags such as BPF_F_ALLOW_MULTI control how programs in parent and child cgroups combine. The main families:

cgroup_skb

cgroup_skb/ingress|egress, ctx __sk_buff, 4.10. Per-packet allow/drop for sockets in the cgroup. Used for per-service firewalls and accounting.

sock and sock_addr

cgroup/sock_create, post_bind4; cgroup/connect4/6, bind4/6, sendmsg4/6, *_unix variants. They can deny, or rewrite the destination address and port. Cilium's socket-level load balancing uses this to translate service IPs at connect().

sockopt

cgroup/getsockopt|setsockopt, ctx bpf_sockopt, 5.3. Inspect, deny or rewrite socket options, for example to forbid a congestion-control choice or force a buffer size.

device

cgroup/dev, ctx bpf_cgroup_dev_ctx (access type, major, minor), 4.15. This is how cgroup v2 controls device access. Container runtimes generate these programs for their devices rules.

sysctl

cgroup/sysctl, ctx bpf_sysctl, 5.2. Allow or deny reads and writes under /proc/sys, and with bpf_sysctl_set_new_value() replace the value being written.

sock_ops

sockops, 4.13. TCP event callbacks (connection established, RTO, …) used to tune TCP and fill sockmaps. Covered with the networking hooks in chapter 07.

The tutorial's cgroup_guard example puts three of these into one object. Note the return-value comments, which differ in wording but follow the same 1/0 convention:

/* ===== 1) Network: block TCP connect4 to specified port =====
 * ctx: struct bpf_sock_addr
 * user_ip4/user_port: network byte order (need conversion)
 *
 * Return semantics:
 * - return 1: allow
 * - return 0: deny (userspace gets EPERM)
 */
SEC("cgroup/connect4")
int cg_connect4(struct bpf_sock_addr *ctx)
{
    if (blocked_tcp_dport == 0)
        return 1;

    if (ctx->protocol != IPPROTO_TCP)
        return 1;

    __u16 dport = bpf_ntohs((__u16)ctx->user_port);
    if (dport != blocked_tcp_dport)
        return 1;

    struct event *e = bpf_ringbuf_reserve(&events, sizeof(*e), 0);
    if (e) {
        fill_common(e, EVENT_CONNECT4);
        e->connect4.daddr = ctx->user_ip4; /* network order */
        e->connect4.dport = dport;         /* host order */
        e->connect4.proto = ctx->protocol;
        bpf_ringbuf_submit(e, 0);
    }

    return 0; /* deny -> userspace gets EPERM on connect */
}
/* ... */
/* ===== 2) Device: block access to specified major:minor =====
 * ctx: struct bpf_cgroup_dev_ctx { access_type, major, minor }
 *
 * Return semantics:
 * - return 0: deny (userspace gets EPERM)
 * - return non-zero: allow
 */
SEC("cgroup/dev")
int cg_dev(struct bpf_cgroup_dev_ctx *ctx)
{
    if (blocked_dev_major == 0 && blocked_dev_minor == 0)
        return 1;

    if (ctx->major != blocked_dev_major || ctx->minor != blocked_dev_minor)
        return 1;

    struct event *e = bpf_ringbuf_reserve(&events, sizeof(*e), 0);
    if (e) {
        fill_common(e, EVENT_DEVICE);
        e->device.major = ctx->major;
        e->device.minor = ctx->minor;
        e->device.access_type = ctx->access_type;
        bpf_ringbuf_submit(e, 0);
    }

    return 0; /* deny -> -EPERM */
}

struct_ops: implementing kernel interfaces in BPF

What it is. Much of the kernel is organised around tables of function pointers: struct tcp_congestion_ops, struct file_operations, scheduler classes, qdisc ops. BPF_PROG_TYPE_STRUCT_OPS (5.6, Martin KaFai Lau's "Introduce BPF STRUCT_OPS") lets a subsystem declare such a table as BPF-implementable. A BPF object then provides the whole implementation. The first user was TCP congestion control, with the stated aim of "a faster turnaround for testing algorithm in the production".

How it works. Each callback is a BPF program in SEC("struct_ops") (any name after the slash is ignored). The table is a global variable in SEC(".struct_ops"), or SEC(".struct_ops.link") for link-based attach that can be updated and auto-detached, which libbpf turns into a map of type BPF_MAP_TYPE_STRUCT_OPS. On attach the kernel builds a trampoline per slot to convert calling conventions (as LWN explains), fills the real kernel struct with those trampolines, and registers it with the subsystem as if a module had done so. Callbacks receive typed arguments and can call kfuncs the subsystem exports. Here is the kernel selftest's DCTCP:

SEC("struct_ops")

sched_ext: a CPU scheduler written in BPF

What it is. sched_ext, the extensible scheduler class, is a scheduling class whose behaviour "can be defined by a set of BPF programs" (kernel docs). It was merged for Linux 6.12. Linus Torvalds' 6.12-rc1 announcement lists it as one of two notable features, after more than a year of debate (LWN: "The extensible scheduler class"). It is the largest struct_ops user: a BPF object implements struct sched_ext_ops and from then on decides where and when every task in the class runs.

How it works. Tasks wait in dispatch queues (DSQs). There is one global FIFO (SCX_DSQ_GLOBAL), one local DSQ per CPU (SCX_DSQ_LOCAL), and any number of custom DSQs created with scx_bpf_create_dsq(), which can be FIFO or vtime-ordered. A CPU always runs from its local DSQ. The kernel calls ops.select_cpu() on wakeup, ops.enqueue() when a task becomes runnable, and ops.dispatch() when a CPU's local queue is empty. Further callbacks such as running, stopping, tick and enable let a scheduler keep accounting. Every callback is optional. Only ops.name is required.

Safety. The kernel docs promise that "system integrity is maintained no matter what the BPF scheduler does". On an error, a runnable task that stalls past the watchdog timeout, or the SysRq-S key, the BPF scheduler is ejected and all tasks go back to the fair class. /sys/kernel/sched_ext/state and /sys/kernel/sched_ext/root/ops show what is loaded. With SCX_OPS_SWITCH_PARTIAL only tasks that set policy SCHED_EXT are affected. Kernel config: CONFIG_SCHED_CLASS_EXT=y with BTF and JIT enabled. The interface carries an explicit "ABI instability" warning.

The tutorial's lesson 44 is a copy of the kernel's scx_simple: a weighted vtime scheduler with an optional FIFO mode.

    bool is_idle = false;

HID-BPF

HID (Human Interface Device) covers keyboards, mice, gamepads and tablets. Many devices are slightly broken: a wrong report descriptor, an inverted axis, a dead zone. A full kernel driver is a heavy way to fix three bytes. HID-BPF, merged in 6.3, lets a BPF program see and rewrite raw HID reports before the HID core parses them. Since 6.11 the programs are struct_ops on struct hid_bpf_ops: the 6.10 docs still show fmod_ret/hid_bpf_device_event, the 6.11 docs show struct_ops/hid_device_event. User-triggered actions use SEC("syscall") programs. Event programs run in IRQ context and so cannot talk back to the device. Device fixes ship as source in the kernel's drivers/hid/bpf/progs, and udev-hid-bpf loads them (HID-BPF docs). The tutorial's lesson 49 doubles mouse movement on a virtual device:

SEC("struct_ops/hid_device_event")
int BPF_PROG(hid_double_movement, struct hid_bpf_ctx *hctx, enum hid_report_type type)
{
    __u8 *data = hid_bpf_get_data(hctx, 0, 9);
    __s8 x, y;

    if (!data)
        return 0;

    /* Mouse HID report format (simplified):
     * Byte 0: Report ID
     * Byte 1: Buttons
     * Byte 2: X movement (signed byte)
     * Byte 3: Y movement (signed byte)
     */

    x = (__s8)data[2];
    y = (__s8)data[3];

    /* Double the movement */
    x *= 2;
    y *= 2;

    data[2] = (__u8)x;
    data[3] = (__u8)y;

    bpf_printk("Modified: X=%d Y=%d -> X=%d Y=%d",
           (__s8)data[2]/2, (__s8)data[3]/2,
           (__s8)data[2], (__s8)data[3]);

    return 0;
}

Iterators: pulling kernel state

Every hook so far is push: the kernel calls you when something happens. A BPF iterator (BPF_TRACE_ITER, 5.8) is pull. You write a program that is called once per kernel object (each task, each open file, each TCP socket, each map element), and it writes output through a seq_file. Nothing runs until a reader calls read() on the iterator's file descriptor, or cats the file if it is pinned in bpffs. Iterators replace parsing /proc with exactly the fields you want, in binary or text, at one consistent point. The ctx is struct bpf_iter__<object>, which holds meta->seq and the current object (it is NULL on the final call). See the BPF iterators docs.

Networking, briefly

The remaining large family is networking: xdp in the NIC driver, tcx/ingress|egress (and the older tc/classifier, now deprecated in libbpf's table) on the traffic-control layer, socket filters, sk_msg/sk_skb for sockmap redirection, sk_lookup, sockops, flow_dissector, netfilter, and netkit. Their contexts are packet buffers (xdp_md, __sk_buff), and their return values are packet verdicts (pass, drop, redirect, transmit). They have enough of their own machinery to need their own chapter: chapter 07.

Finding hook points on a running kernel

Before writing a SEC() name you need a target that exists on this kernel. These standard commands answer that (commands only; output depends on the machine). Each one corresponds to a hook family above:

# Tracepoints and the record layout a tp/ program receives
sudo ls /sys/kernel/tracing/events/sched/
sudo cat /sys/kernel/tracing/events/syscalls/sys_enter_openat/format
# Functions ftrace can trace (kprobe via ftrace, fentry/fexit also need BTF)

# The BTF prototype that fentry/fexit/LSM programs are typed against

# bpftrace lists probes and, with -v, their arguments

If available_filter_functions does not list a function, fentry cannot attach to it. If it was inlined, no hook can target it by name; if it is only notrace, a breakpoint kprobe may still work. The libbpf SEC() table, bpftool feature probe and these lists together tell you which hook is actually usable before you compile anything.

Choosing a hook

Choosing well matters more than micro-optimising the program afterwards. A practical order of preference:

  1. Need to enforce policy? If the policy is per container or per service and a cgroup hook covers the operation (socket, device, sysctl), use the cgroup hook. Otherwise use a BPF LSM hook, or lsm_cgroup for per-cgroup scope. Never build enforcement on kprobes: they observe and cannot reliably block.
  2. Need to replace an algorithm? Look for a struct_ops interface: TCP CC, sched_ext, HID, qdisc. If none exists, the subsystem has not opted in, and fmod_ret on an error-injection function is the only, deliberately narrow, alternative.
  3. Need to observe a kernel event? Use a tracepoint if one exists, as tp_btf for typed args or tp for the stable record format. Otherwise use fentry/fexit/fsession, and fall back to kprobe for mid-function offsets, old kernels without BTF, or wide wildcards (kprobe.multi).
  4. Need to observe an application? Prefer USDT if the program ships probes. Otherwise use uprobes, but budget for their per-call cost on hot functions and consider a userspace runtime (chapter 15) or sampling.
  5. Need "where is time going"? Use a perf_event sampling program, not probes on every function.
  6. Need a snapshot of kernel objects? Use an iterator, not a hook plus a map you keep in sync.

Benefits and limitations

Benefits

One VM, verifier and toolchain cover tracing, security, resource control and pluggable kernel policy. Hooks can be attached and detached at run time without a reboot or a module. Typed hooks (fentry, tp_btf, LSM, struct_ops) give near-native cost and plain C pointer access.

Limitations

Capabilities differ per type, so moving code between hooks means re-checking helpers and context access. Dynamic hooks (kprobe/fentry/uprobe) depend on unstable symbols. LSM needs boot-time enablement. sched_ext and kfunc APIs are explicitly unstable. Uprobes cost a trap per hit. Most types need CAP_BPF plus CAP_PERFMON or CAP_NET_ADMIN, or root.

Related work

DTrace (static and dynamic probes, the origin of USDT), SystemTap (kernel-module based), ftrace/perf (non-programmable or less programmable tracing), kernel modules (unrestricted, unsafe), seccomp (cBPF filters), and userspace runtimes (bpftime, llvmbpf).

Try it: build and run the examples

libbpf-bootstrap needs its submodules. These commands are adapted from its README (which builds one example at a time, e.g. make minimal):

git clone --recurse-submodules https://github.com/libbpf/libbpf-bootstrap
cd libbpf-bootstrap/examples/c
make minimal kprobe fentry uprobe usdt profile task_iter
sudo ./fentry            # in another terminal:
sudo cat /sys/kernel/debug/tracing/trace_pipe

To see which hooks are live on a machine, sudo bpftool prog show lists loaded programs with their type, sudo bpftool link show lists links with their attach targets, and sudo bpftool perf lists kprobe, uprobe and tracepoint attachments. bpf-developer-tutorial lessons build with make in each directory, or with ecc/ecli (chapter 10). Check your understanding

Q1. Why can an fexit program print the filename argument of do_unlinkat, when a kretprobe on the same function only gets ret?

The BPF trampoline saves the arguments to a stack array, calls the original body, then calls fexit with both the saved arguments and the return value.

Q2. You want to forbid a container from connecting to TCP port 9090 while other containers keep working. Which hook fits best?

cgroup sock_addr hooks are policy hooks scoped to one cgroup, and their 0 return makes connect() fail with EPERM. A kprobe's return value is ignored.

Q3. What is the main source of uprobe overhead?

int3 on the probed instruction traps into the kernel. Out-of-line single-stepping can add a second trap. Symbol lookup and verification happen once, at attach and load time.

Q4. In which mainline release did sched_ext land?

kernel/sched/ext.c is absent at v6.11 and present at v6.12, and the 6.12-rc1 announcement names sched_ext as a notable addition.

Q5. A security team wants to block openat() of paths under /secret and asks whether to write an eBPF seccomp filter. What do you tell them?

seccomp filters see only syscall number and raw argument values. LSM hooks see the resolved kernel objects and their return value is enforced.
