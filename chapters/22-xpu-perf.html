Chapter 22

xpu-perf: one flame graph for CPU and GPU

Your PyTorch job is slow, and nvidia-smi says the GPU is busy only part of the time. Is the CPU starving the GPU, or is one kernel eating the clock? A CPU profiler can't see GPU kernels. A GPU tracer shows kernels but not the Python or C++ code that launched them. This chapter covers the profiling basics you need first: sampling, stack unwinding, symbolization and flame graphs. Then it shows how xpu-perf joins the two views. It samples CPU stacks with a perf_event eBPF program, captures the stack at every CUDA launch with a uprobe, and reads GPU kernel timings from CUPTI. A CUPTI correlation ID links the two, and the result is a single flame graph.

Prerequisites: 05 (perf_event, uprobes), 04 (maps, tail calls), 15 (GPU attach, optional)Repo: eunomia-bpf/xpu-perf @ b4fcc885~60 min

Why this matters

A GPU program is really two programs running at the same time. A host thread on the CPU runs ordinary code: a Python interpreter, the PyTorch dispatcher, a tokenizer, data loading. Now and then that code calls cudaLaunchKernel, which puts a kernel in a GPU queue and returns at once. The kernel runs later, on different hardware, possibly for much longer than the call that launched it. The CPU and the GPU each have their own clock, their own idle time and their own bottlenecks.

The usual tools look at only one side:

  • A CPU profiler (Linux perf, Parca, the OpenTelemetry eBPF profiler) samples where the CPU's time goes. For a GPU workload it shows a little time in cudaLaunchKernel, and maybe a lot of time spinning in cudaDeviceSynchronize. It can't show which kernel the CPU is waiting for.
  • A GPU tracer (CUPTI-based tools, NVIDIA Nsight Systems) records every kernel's start and end time. It shows the kernel by its mangled name, such as _Z13softmaxKernelPKfPfmm, but not the 30 frames of application code that led to the launch.

Engineers end up laying a CPU flame graph next to a GPU timeline and lining up timestamps by eye. xpu-perf, an eunomia-bpf project whose GitHub description is "Continuous profiler for GPU & CPU with eBPF", automates that. Its output is one ordinary folded-stack file. Each GPU kernel appears as a leaf frame [GPU_Kernel]name on top of the exact CPU call stack that launched it, and its width is the kernel's GPU time converted into the same units as CPU samples.

Key idea

xpu-perf adds very little eBPF of its own. It reuses the OpenTelemetry eBPF profiler for perf_event sampling and stack unwinding, and CUPTI for GPU timing. The new piece is a join key. A tiny noinline function, XpuPerfGetCorrelationId(id), is called inside a CUPTI callback. A uprobe on that function stores the ID in a per-CPU map and tail-calls the profiler's unwinder, so every captured CPU stack carries the same correlation ID that CUPTI later writes on the kernel's activity record.

Profiling fundamentals

You need these terms to follow the rest of the chapter. If you already know perf record -g and flame graphs, skim this section.

Sampling versus tracing

A tracing tool records every event of interest, such as every function entry, every syscall or every kernel launch, usually with timestamps. You get exact counts and exact durations, but the cost grows with the event rate. Trace a function called ten million times a second and you slow the program down and fill your buffers.

A sampling profiler interrupts the program at a fixed rate, for example 50 times per second per CPU, and records what was running at that moment: the instruction pointer and, ideally, the whole call stack. Each sample stands for about 1/50 s of CPU time. Over thousands of samples, the share of samples that land in a function estimates the share of CPU time spent there. The cost depends on the sample rate, not on how busy the program is, which is why sampling profilers can stay on in production. Google-Wide Profiling (Ren et al., IEEE Micro 2010) is the classic description of fleet-wide continuous sampling.

xpu-perf uses both. It samples CPU stacks on a timer and traces every kernel launch: a uprobe fires on every launch, and CUPTI records every kernel's start and end. The GPU side has to be traced because a kernel is a discrete event with a duration. You can't sample "the current kernel" from the CPU.

On Linux, the timer interrupt for sampling comes from perf_event_open(2) with a software clock such as PERF_COUNT_SW_CPU_CLOCK. Since kernel 4.9 an eBPF program of type BPF_PROG_TYPE_PERF_EVENT can be attached to that event and runs at each sample, in the context of the interrupted thread (Chapter 05 shows the minimal libbpf version). That program has the interrupted registers, so it knows the instruction pointer, stack pointer and frame pointer of whatever was running.

Stack unwinding: frame pointers versus unwind tables

A single instruction pointer only tells you the leaf function. To build a flame graph you need the chain of callers: the call stack. Reconstructing it from a register snapshot and raw stack memory is called unwinding, and there are two main ways to do it.

Frame pointers. When code is compiled with frame pointers (-fno-omit-frame-pointer), every function prologue pushes the caller's %rbp and sets %rbp to the current stack position. The saved values form a linked list through the stack. Each frame holds a pointer to the previous frame and, next to it, the return address. An unwinder just follows the list, which is cheap enough to do inside an interrupt or an eBPF program. The catch is that, on x86-64, GCC and Clang drop frame pointers by default when optimizing, which frees %rbp as a general-purpose register. Many distribution libraries were built that way for about twenty years. Brendan Gregg's post "The Return of the Frame Pointers" (2024) describes the broken profiles this causes and the recent decisions by Fedora and Ubuntu to build packages with frame pointers again.

Unwind tables (DWARF CFI / .eh_frame). Almost every ELF binary carries .eh_frame, the call-frame information that C++ exception handling uses. For each range of instruction addresses it says how to compute the canonical frame address (CFA), for example "CFA = RSP + 16", and where the return address is saved. With that table you can unwind code that has no frame pointers. The table is large, though, and interpreting DWARF bytecode inside the kernel isn't practical. perf record --call-graph dwarf sidesteps this by copying a chunk of raw user stack into every sample and unwinding later in user space, which costs a lot of bandwidth.

The OpenTelemetry eBPF profiler, which xpu-perf builds on, takes a third approach. User space reads .eh_frame once per binary and converts it into compact stack deltas, which the project's doc/internals.md describes as "a mapping from each PC in an executable to instructions describing how to find the caller". These are loaded into eBPF maps. The eBPF unwinder then looks up the delta for each PC and walks the stack in the kernel, with or without frame pointers. Go binaries get their deltas from .gopclntab instead, and separate unwinders handle interpreted frames for Python, the JVM, Ruby, PHP, Node.js and Perl.

Symbolization

The unwinder produces addresses, not names. Symbolization turns (binary, address) into function+offset. For a position-independent executable or a shared library, the runtime address first has to be converted to an offset inside the file. Then it is looked up in the ELF symbol tables (.symtab if the binary isn't stripped, otherwise .dynsym), or in DWARF debug info if you want file and line. C++ and Rust names are then demangled, so _ZN17InferencePipeline10runRequestEv becomes InferencePipeline::runRequest. Continuous profilers usually symbolize away from the hot path, often on a central server that has the debug info, because symbol tables are big. xpu-perf does it in-process when the run finishes.

Folded stacks and flame graphs

Brendan Gregg's FlameGraph tools use a very simple text format. Each line is a call stack from root to leaf, joined by semicolons, followed by a count:

main;serve;tokenize 25
main;serve;forward;cudaLaunchKernel 8
main;load_model;read_weights 30

flamegraph.pl turns this into an interactive SVG. Every frame is a box. The box's width is the number of samples whose stack passes through that frame, and the boxes stack upward from the root. The x-axis is not time: siblings are sorted alphabetically so that identical stacks merge. A wide box near the top is a hot leaf; a wide plateau lower down is code whose callees eat the time. Gregg's article "The Flame Graph" (Communications of the ACM, 2016) is the standard reference. His 2024 "AI Flame Graphs" post applies the same picture to GPU hardware samples, which is the idea xpu-perf builds on.

Because the format is just text, a tool can add frames that never existed on the CPU. xpu-perf does exactly that: it appends a synthetic [GPU_Kernel]... leaf and gives it a count derived from the kernel's GPU time. The standard flamegraph.pl needs no changes to draw it.

Background: how you get data out of an NVIDIA GPU

eBPF runs on the CPU, in the kernel (or, with bpftime, in user space). It can see every host-side CUDA call through uprobes on libcudart or libcuda. It can't see when a kernel actually starts and finishes on the GPU. That information comes from the vendor's profiling interfaces. eunomia-bpf has two tutorial repositories on them that are good background reading for this chapter:

cupti-tutorial

"Tutorials for NVIDIA CUPTI samples". NVIDIA's CUPTI samples, each rewritten as a tutorial: the Activity API (activity_trace, activity_trace_async), the Callback API (callback_event, callback_timestamp), events and metrics, pc_sampling, sass_source_map, unified_memory, nvlink_bandwidth. Its suggested path starts with cupti_query and then activity_trace.

nvbit-tutorial

A blog-style guide to NVBit (based on NVBit 1.7.5), NVIDIA's research framework for dynamic binary instrumentation of GPU SASS code. A tool is a shared library loaded with LD_PRELOAD. It can inject calls before or after individual GPU instructions as each kernel is first loaded, for example to count instructions or to trace memory accesses.

CUPTI (CUDA Profiling Tools Interface) has two halves that matter here. The Callback API calls your function at the entry and exit of every CUDA runtime or driver API call, on the calling thread. The Activity API collects time-stamped records of GPU work, including kernels (CUPTI_ACTIVITY_KIND_CONCURRENT_KERNEL), memcpys and memsets, into buffers that CUPTI hands back to you asynchronously. Every API call gets a correlation ID. The callback for cudaLaunchKernel sees that ID, the runtime API activity record carries it, and the kernel activity record for the launched kernel carries it too. That ID is what lets you join "who launched it" to "how long it ran".

A tool doesn't need the application's cooperation to use CUPTI. If the environment variable CUDA_INJECTION64_PATH names a shared library, the CUDA driver loads it during initialization and calls its InitializeInjection() function, which can subscribe to callbacks and enable activity kinds. xpu-perf uses this mechanism.

NVBit goes further and instruments the GPU code itself, but with much higher overhead. bpftime's CUDA attach (Chapter 15) compiles eBPF programs to PTX and runs them inside kernels. Chapter 20 covers eBPF policies for the GPU driver's memory manager. xpu-perf is the lightest approach of the three: it never touches GPU code and only uses CUPTI's records.

Architecture

Four parties take part in a merge-mode run: the target process (with CUPTI and the injection library loaded into it), the GPU, the Linux kernel running eBPF programs, and the xpu-perf process.

The stepper below follows one merge-mode run from start to finish, in the order main() does things.

1. Parse the subcommand, check root, extract the CUPTI library

parseFlags() reads cpu|gpu|merge. Flags are parsed before the root check, so --help works without sudo. Unless -cupti-lib is given, ExtractEmbeddedCUPTILibrary() writes the //go:embed-ed libcupti_trace_injection.so to $TMPDIR/xpu-perf/libcupti_trace_injection_<pid>.so.

2. Create the FIFO and start the CUPTI parser

A named pipe /tmp/cupti_trace_<pid>.pipe is created with mkfifo. A goroutine opens it and parses one JSON event per line, keeping kernel records and *LaunchKernel* runtime records.

3. Load the eBPF profiler

tracer.NewTracer() loads the OpenTelemetry eBPF profiler's programs and maps with SamplesPerSecond: 50 and LoadProbe: true. The fork also loads custom__generic and its custom_context_map.

4. Attach perf_event sampling (cpu, merge)

trc.AttachTracer() opens one software CPU-clock perf event per online CPU at 50 Hz and attaches native_tracer_entry. Then EnableProfiling() switches the events on. The gpu mode skips this step.

5. Attach the correlation uprobe (gpu, merge)

By default xpu-perf loads correlation_uprobe.ebpf.c, hands it the profiler's custom_context_map, puts the FD of custom__generic into slot 0 of its own prog_array, and attaches a uprobe to XpuPerfGetCorrelationId in the extracted library. With -use-correlation-id=false it attaches the profiler's generic uprobe to cudaLaunchKernel* in libcudart instead.

6. Start the target with CUPTI injection

After a 500 ms pause to let the map monitors start, the target is started with CUDA_INJECTION64_PATH, CUPTI_TRACE_OUTPUT_FILE (the FIFO), CUPTI_ENABLE_MEMORY=1 and CUPTI_ENABLE_CORRELATION_UPROBE=1. Its PID becomes the filter for sampling traces.

7. Run: samples and launch stacks flow in

Every 20 ms per CPU, a sample from the target becomes a TRACE_SAMPLING trace. Every CUDA runtime callback calls XpuPerfGetCorrelationId; the uprobe turns it into a TRACE_CUSTOM trace whose ContextValue is the correlation ID. SimpleReporter collects both into the correlator. Statistics are logged every 5 s.

8. Target exits: flush, correlate, write

xpu-perf waits 200 ms for eBPF and 500 ms for CUPTI to flush, closes the tracer, then calls CorrelateTraces(). Sampling stacks count 1 each. Launch stacks get [GPU_Kernel]name appended and weight (end−start)·50/1e9. Counts are rounded and written as a folded file.

Code walkthrough 1: CPU sampling with perf_event eBPF

xpu-perf doesn't write its own sampler. It calls into the OpenTelemetry eBPF profiler, which Elastic donated to OpenTelemetry in 2024. The user-space side opens a software CPU-clock event per CPU at the configured frequency and attaches the entry program. The kernel side is the entry program itself:

func (t *Tracer) AttachTracer() error {
	tracerProg, ok := t.ebpfProgs["native_tracer_entry"]
	if !ok {
		return errors.New("entry program is not available")
	}

	perfAttribute := new(perf.Attr)
	perfAttribute.SetSampleFreq(uint64(t.samplesPerSecond))
	if err := perf.CPUClock.Configure(perfAttribute); err != nil {
		return fmt.Errorf("failed to configure software perf event: %v", err)
	}
	/* ... */
	for _, id := range onlineCPUIDs {
		perfEvent, err := perf.Open(perfAttribute, perf.AllThreads, id, nil)
		if err != nil {
			return fmt.Errorf("failed to attach to perf event on CPU %d: %v", id, err)
		}
		if err := perfEvent.SetBPF(uint32(tracerProg.FD())); err != nil {
			return fmt.Errorf("failed to attach eBPF program to perf event: %v", err)
		}
		*events = append(*events, perfEvent)
	}
	return nil
}
SEC("perf_event/native_tracer_entry")
int native_tracer_entry(struct bpf_perf_event_data *ctx)
{
  // Get the PID and TGID register.
  u64 id  = bpf_get_current_pid_tgid();
  u32 pid = id >> 32;
  u32 tid = id & 0xFFFFFFFF;

  if (pid == 0 && filter_idle_frames) {
    return 0;
  }

  u64 ts = bpf_ktime_get_ns();
  return collect_trace((struct pt_regs *)&ctx->regs, TRACE_SAMPLING, pid, tid, ts, 0);
}
// unwind_native is the tail call destination for PROG_UNWIND_NATIVE.
static EBPF_INLINE int unwind_native(struct pt_regs *ctx)
{
  /* ... */
  UNROLL for (int i = 0; i < NATIVE_FRAMES_PER_PROGRAM; i++)
  {
    unwinder = PROG_UNWIND_STOP;
    /* ... */
    error = push_native(
      trace,
      record->state.text_section_id,
      record->state.text_section_offset,
      record->state.return_address);
    /* ... */
    // Unwind the native frame using stack deltas. Stop if no next frame.
    bool stop;
    error = unwind_one_frame(&record->state, &stop);
    if (error || stop) {
      break;
    }
    /* ... */
    error = get_next_unwinder_after_native_frame(record, &unwinder);
    if (error || unwinder != PROG_UNWIND_NATIVE) {
      break;
    }
  }

  // Tail call needed for recursion, switching to interpreter unwinder, or reporting
  // trace due to end-of-trace or error. The unwinder program index is set accordingly.
  record->state.unwind_error = error;
  tail_call(ctx, unwinder);
  /* ... */
}

Notice the shape of unwind_native. The verifier limits loop sizes and program lengths (Chapter 03), so the unwinder handles a fixed number of frames per program and then tail-calls itself or another unwinder, for example the Python one when it reaches an interpreter frame. collect_trace starts this chain, and the finished trace is sent to user space. The frames it pushes are (file ID, offset) pairs, not names. Symbolization happens later in Go.

Everything a sample needs (stack deltas, interpreter offsets, process mappings) is pushed into maps by the profiler's user-space process manager as processes start and libraries load. That is why xpu-perf calls trc.StartPIDEventProcessor(ctx) and trc.StartMapMonitors(...) and then waits 500 ms before starting the target.

Code walkthrough 2: the CUPTI injection library

The injection library is the GPU half of the profiler. InitializeInjection() calls SetupCupti(), which opens the output named by CUPTI_TRACE_OUTPUT_FILE, subscribes a callback handler, and enables activity kinds:

    // Subscribe to CUPTI callbacks
    CUPTI_CALL(cuptiSubscribe(&g_state.subscriberHandle,
                              (CUpti_CallbackFunc)XpuPerfCallbackHandler, NULL));
    /* ... */
    // Optional: Enable eBPF correlation ID tracking via CUPTI_ENABLE_CORRELATION_UPROBE=1
    const char *enableCorrelation = getenv("CUPTI_ENABLE_CORRELATION_UPROBE");
    if (enableCorrelation && atoi(enableCorrelation) == 1) {
        // Enable all runtime API callbacks for correlation ID capture
        CUPTI_CALL(cuptiEnableDomain(1, g_state.subscriberHandle,
                                     CUPTI_CB_DOMAIN_RUNTIME_API));
        printf("Correlation ID uprobe tracking: ENABLED\n");
    }
    /* ... */
    // Register buffer callbacks
    CUPTI_CALL(cuptiActivityRegisterCallbacks(BufferRequested, BufferCompleted));

    // Enable activities
    EnableActivities();

EnableActivities() always turns on CUPTI_ACTIVITY_KIND_RUNTIME and CUPTI_ACTIVITY_KIND_CONCURRENT_KERNEL. It adds driver and overhead records with CUPTI_ENABLE_DRIVER=1, and memcpy/memset/memory records with CUPTI_ENABLE_MEMORY=1, which xpu-perf always sets. CUPTI asks for 32 MB buffers. When one fills, BufferCompleted prints each record as a JSON line and calls fflush, so records stream through the FIFO while the program runs.

The interesting part is the eBPF attachment point:

// Non-inline function for eBPF attachment
// This function is specifically designed to be attached to by eBPF probes
// The __attribute__((noinline)) and volatile counter ensure it's not optimized away
extern "C" __attribute__((noinline, used)) uint32_t XpuPerfGetCorrelationId(uint32_t correlationId) {
    // Increment global counter to prevent optimization
    g_correlationCallCounter++;

    // Return the correlation ID
    // eBPF can read the parameter or return value
    return correlationId;
}

static void CUPTIAPI XpuPerfCallbackHandler(void *userdata, CUpti_CallbackDomain domain,
                                      CUpti_CallbackId cbid, void *cbdata) {
    /* ... */
    const CUpti_CallbackData *callbackData = (CUpti_CallbackData *)cbdata;
    /* ... */
    // Call non-inline function for eBPF attachment point
    // This allows eBPF to capture the correlation ID
    if (callbackData) {
        XpuPerfGetCorrelationId(callbackData->correlationId);
    }
    /* ... */
}

This is a common trick: a function that does nothing useful, exported with C linkage, never inlined, and given an argument that the observer wants. It works like a hand-made USDT probe. Because the callback runs on the thread that called the CUDA API, while that call is in progress, the user stack at this point contains the whole application call path: main → … → TransformerLayer::forward → cudaLaunchKernel → libcupti → XpuPerfCallbackHandler → XpuPerfGetCorrelationId. The last few frames are noise, and xpu-perf filters them out later.

Code walkthrough 3: the correlation uprobe and the tail call

Now the eBPF side. The profiler can already capture a stack from a uprobe: upstream has a uprobe__generic program that calls collect_trace(ctx, TRACE_UPROBE, …, 0). But that trace has no slot for "which CUDA call was this?". The fork adds a second entry point that reads a 64-bit context value from a per-CPU map and stores it in the trace:

struct custom_context_map_t {
  __uint(type, BPF_MAP_TYPE_PERCPU_ARRAY);
  __type(key, u32);
  __type(value, u64);
  __uint(max_entries, 1);
} custom_context_map SEC(".maps");

// custom__generic serves as entry point for custom trace profiling with context_value.
// This can be called as a tail call from external eBPF programs.
// Not meant to be attached directly - just loaded for tail calling.
SEC("uprobe/custom__generic")
int custom__generic(struct pt_regs *ctx)
{
  u64 pid_tgid = bpf_get_current_pid_tgid();
  u32 pid      = pid_tgid >> 32;
  u32 tid      = pid_tgid & 0xFFFFFFFF;

  if (pid == 0 || tid == 0) {
    return 0;
  }

  u64 ts = bpf_ktime_get_ns();

  // Retrieve context_value from the shared per-CPU map
  u32 key0 = 0;
  u64 *context_value_ptr = bpf_map_lookup_elem(&custom_context_map, &key0);
  u64 context_value = context_value_ptr ? *context_value_ptr : 0;
  /* ... */
  return collect_trace(ctx, TRACE_CUSTOM, pid, tid, ts, context_value);
}

The same fork commit renames the trace field offtime (used by off-CPU profiling) to context_value and adds TRACE_CUSTOM to the TraceOrigin enum. In user space the value shows up as meta.ContextValue.

xpu-perf's own eBPF program is the small front end that fills that map and jumps:

SEC("uprobe/XpuPerfGetCorrelationId")
int capture_correlation_id(struct pt_regs *ctx)
{
	// Get the correlation ID from the first parameter
	// Use PT_REGS_PARM1 macro for portable parameter access
	__u32 correlation_id = (__u32)PT_REGS_PARM1(ctx);

	// Store the correlation ID in the shared map as a 64-bit value
	// custom__generic will read this value when collecting the trace
	__u32 key = 0;
	__u64 context_value = (__u64)correlation_id;

Three eBPF ideas from Part I meet here (Chapter 04):

  • Map sharing across objects. custom_context_map is declared in both C files, but cilium/ebpf's MapReplacements makes the second object use the profiler's existing map FD instead of creating a new one. Both programs read and write the same per-CPU slot.
  • Per-CPU scratch. The uprobe program and the program it tail-calls form one execution on one CPU (migration is disabled while a BPF program runs), so a one-entry PERCPU_ARRAY is a safe way to pass a value from one program to the next.
  • Tail calls between independently loaded programs. The prog array belongs to xpu-perf's collection, but its slot 0 holds the FD of a program loaded by the profiler library. The tail call reuses the same pt_regs context, so collect_trace unwinds the stack exactly as it was at the uprobe. The Go code keeps the collection open for the whole run. Closing it would destroy prog_array and silently break every tail call.

The alternative attacher, used with -use-correlation-id=false, is the older design. It runs ldd on the target to find libcudart.so, runs nm -D to list the undefined cudaLaunchKernel* symbols the target imports, and attaches the profiler's stock uprobe there. Those traces carry no correlation ID, so the correlator falls back to matching by order and time. If there are as many uprobe hits as *LaunchKernel* runtime records, it pairs them one-to-one in time order. Otherwise it walks both lists with a 10 ms tolerance.

Read it like any flame graph input. Of 419 total "samples", 318 (about 76%) are the softmax kernel. Four details are worth noting:

  • The __device_stub__… frames are host-side stubs that nvcc generates for each <<<…>>> launch. They show which kernel call site in the source did the launch.
  • The GPU leaf uses the raw mangled name (_Z13softmaxKernelPKfPfmm): kernel names come straight from CUPTI and are not demangled.
  • Frames that have a symbol keep a +0x… offset. The two layerNorm launches show up as separate towers under forward+0x107 and forward+0x385. That is useful for telling call sites apart, but it also means that one function sampled at different instructions becomes several sibling frames in the CPU part of a graph.
  • Frames with no symbol fall back to library+0xoffset, as with libcuda.so.575.57.08+0x51ccb5.

Build and run

What the README says

Prerequisites listed in the README: Linux 5.10+, Go 1.19+, the CUDA Toolkit, root, and Perl. (profiler/go.mod actually says go 1.24.0, so use a recent Go.) The documented commands:

# Install dependencies
sudo apt-get install -y libelf1 libelf-dev zlib1g-dev make clang llvm git perl golang-go

# Build the profiler
cd profiler && make

# ...
# Merge mode: CPU sampling + GPU kernels with call stacks
sudo ./profiler/xpu-perf merge -o merged_trace.folded ./your_cuda_app

# GPU-only: CPU→GPU causality (shows which CPU code launched kernels)
sudo ./profiler/xpu-perf gpu -o gpu_trace.folded ./your_cuda_app

# CPU-only: Pure CPU sampling without GPU overhead
sudo ./profiler/xpu-perf cpu -o cpu_trace.folded ./your_cuda_app

# Generate flamegraph
perl profiler/flamegraph.pl merged_trace.folded > flamegraph.svg

For PyTorch, the README's test section runs the interpreter as the target:

sudo -E env "PATH=$PATH" ./profiler/xpu-perf gpu -o pytorch.folded python3 test/pytorch/pytorch_longer.py
perl profiler/flamegraph.pl pytorch.folded > pytorch-flamegraph.svg

Practical notes from reading the build files:

  • Clone with submodules (git clone --recursive or git submodule update --init). The Go module points at ./opentelemetry-ebpf-profiler through a replace directive.
  • make in profiler/ runs go generate, which calls bpf2go -target amd64 on ebpf/correlation_uprobe.ebpf.c. That needs clang and the libbpf headers. The latest commit (b4fcc885) adds libbpf-dev to the CI dependencies for exactly this reason: without it the build fails with "bpf/bpf_helpers.h file not found". The README's apt line doesn't list it yet.
  • Next, make cupti builds the injection library with nvcc from CUDA_INSTALL_PATH ?= /usr/local/cuda-12.9. Override it for other CUDA versions: make CUDA_INSTALL_PATH=/usr/local/cuda (a standard make variable override; not documented by the repo).
  • The -cuda-lib fallback list in cuda_utils.go is hard-coded to /usr/local/cuda-12.9, cuda-13.0, cuda-12.8 and /usr/local/cuda. It only matters in the non-default -use-correlation-id=false path.
  • profiler/README.md and the profiler/Makefile test target still use the pre-November flag style (./profile -gpu-only …, --gpu-only). The current binary rejects that with "Unknown command". Use the subcommand form above.

Debugging a run

Pass -debug-dir DIR to save the parsed CUPTI events, the raw CPU traces and the correlation details (profiler/debug.go). The matched=, unmatched= and no_correlation= counters printed at the end say whether the join worked. A high no_correlation count means the uprobe traces arrived without an ID.

Benefits and limitations

What the design gets right

  • No changes to the application. CUPTI injection is enabled through an environment variable, and stacks come from eBPF. You don't recompile, add a library, or edit Python.
  • Exact joins. Joining on the correlation ID avoids guessing from timestamps, which breaks down when launches are queued, as they usually are.
  • Strong CPU unwinding for free. Building on the OpenTelemetry eBPF profiler brings .eh_frame-based native unwinding and interpreter unwinders. That's how Python frames can appear above PyTorch's C++ frames without frame pointers.
  • Lingua franca output. The output is folded stacks, so any flame graph tool can read it: flamegraph.pl, speedscope, or tools that convert to pprof.
  • Very little new eBPF. 61 lines of C plus a 43-line addition to the fork. The tail-call and map-replacement pattern (prototyped in documents/custom-example/) can carry any 64-bit context value, not only CUDA IDs.

Limitations and open questions

  • Launch-only, not attach. xpu-perf starts the target itself, and CUPTI injection only works at CUDA initialization. You can't profile a service that is already running.
  • x86-64, NVIDIA, root. bpf2go runs with -target amd64, CUPTI is NVIDIA-only, and both eBPF and uprobes need root. The README's overhead figures ("< 1% CPU overhead, < 5% GPU overhead") come with no benchmark in the repo.
  • Kernel time only. The parser keeps kernel and launch records. Memcpy and memset records are collected (CUPTI_ENABLE_MEMORY=1) but don't appear in the folded output. There is no stall-reason or PC-level GPU detail like iaprof's EU stalls or CUPTI PC sampling, although the repo has PC-sampling experiments in documents/pc_sampling_start_stop/.
  • Summed time is not wall time. Kernels on concurrent streams add up, as do CPU samples from several threads, so a merged graph's total can be more than the run time. Off-CPU time is not sampled (OffCPUThreshold: 0), so a thread blocked in a sleeping synchronize call disappears, while one spinning in it shows up as CPU.
  • Likely double counting (code reading, not run on a GPU). XpuPerfCallbackHandler calls XpuPerfGetCorrelationId unconditionally, before it looks at callbackSite, for every runtime-API callback it gets. CUPTI calls it at both API_ENTER and API_EXIT with the same correlation ID (the handler's own callbackSite == CUPTI_API_ENTER test shows it expects both). Nothing downstream deduplicates: SimpleReporter.ReportTraceEvent appends every custom trace with a non-empty stack, and correlateByCorrelationID adds the kernel's duration once per matching trace. So each kernel would be counted twice whenever both uprobe hits yield a stack. I couldn't run this without a GPU, and the committed gpu_trace.folded cannot show it either way. A uniform factor of two would leave the proportions among GPU kernels unchanged but would skew the CPU-versus-GPU ratio in merge mode.
  • Many uprobe hits. With cuptiEnableDomain(RUNTIME_API), every CUDA runtime call (not just launches) fires the uprobe and unwinds a stack. Uprobes trap into the kernel (Chapter 05). For launch-heavy workloads this is the main cost, and the kind that bpftime's user-space uprobes (Chapter 14) are meant to reduce.
  • Symbolization details. Frames keep +0x offsets, which splits one function into many frames. Symbolizer.Symbolize scans the symbol table linearly for every lookup (the README says "binary search"). Kernel names are not demangled.
  • Project hygiene. The docs and the CLI disagree in places, CI is red, the dockerfile points at a /root/src/bootstrap that no longer exists, and there are no tests beyond the sample apps.

Check your understanding

Q1. Why can't xpu-perf get GPU kernel durations from a uprobe on cudaLaunchKernel alone?

Kernel launches are asynchronous. The uprobe gives the who (the CPU stack). CUPTI's CONCURRENT_KERNEL records give the how long. The correlation ID joins them.

Q2. In merge mode, a kernel ran for 36.2 ms. How many "samples" does it add to its stack before rounding?

samples = durationNs × samplesPerSec / 1e9 with samplesPerSec = 50, the CPU sampling rate, so GPU time and CPU samples use the same unit.

Q3. How does the correlation ID get from the uprobe into the stack trace that the profiler reports?

See correlation_uprobe.ebpf.c and custom_trace.ebpf.c. MapReplacements makes both objects use the same custom_context_map.

Q4. Which unwinding method lets the OpenTelemetry eBPF profiler walk native stacks of libraries built without frame pointers?

doc/internals.md: deltas map each PC to how to find the caller. Go binaries use .gopclntab instead.

Q5. You run sudo xpu-perf merge -o out.folded ./app. Which statement is true?

There is no attach-to-PID option. CUPTI injection works at CUDA initialization, which is why the profiler launches the target.

Q6. In a flame graph, what does the horizontal position of a frame mean?

That is the key difference between a flame graph and a timeline such as Nsight Systems or a Chrome trace. Gregg's CACM article explains it.
