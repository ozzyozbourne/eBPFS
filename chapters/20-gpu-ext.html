Chapter 20

gpu_ext: eBPF policies inside the GPU driver

A 59 GiB model does not fit in a 32 GB GPU. The NVIDIA driver can still run it by paging memory between host RAM and the GPU on demand, but its built-in rules decide what to fetch early, what to evict and which process gets the GPU next. Those rules are the same for every workload. This chapter shows how gpu_ext replaces them with eBPF programs: the hooks it adds to the NVIDIA open kernel modules, the policies in the repo, the device-side half that runs eBPF inside CUDA kernels, and what its paper does and does not show.

Why this matters

On a CPU, Linux decides which pages stay in RAM, which get swapped out and which thread runs next. If you do not like those decisions you can tune them, and since sched_ext and cache_ext you can even replace them with eBPF (Chapter 05). On an NVIDIA GPU the same decisions are made by the GPU driver. The kernel module nvidia-uvm moves pages between host and device memory. The core module nvidia sets how long each GPU context may run before it is switched out. Both use fixed heuristics: a tree-based prefetcher with one threshold, roughly LRU eviction of 2 MB chunks, and a fixed timeslice per context.

Those heuristics work for some programs and not others. The paper behind this chapter (Figure 1 of arXiv:2512.12615) shows how different the page-fault patterns are. Building a Faiss index scans memory sequentially, while querying it is random. LLM prefill is periodic and sequential, decode is sparse, and DNN training touches memory in periodic blocks. A prefetcher tuned for one of these patterns hurts another. When two tenants share a GPU, the driver has no idea that one of them is a latency-critical inference server and the other a background training job.

There are two usual ways out. Both are poor. Frameworks such as vLLM or llama.cpp can manage offloading themselves, but each has to do it separately, none of them sees the other tenants, and none can touch the driver's fault handler or timeslices. Research systems such as GPREEMPT or TimeGraph modify the driver directly. That is powerful, but each new policy is a new kernel patch, and a bug in it can hang the GPU or crash the kernel.

gpu_ext takes the sched_ext approach. It adds a small number of hook points to the NVIDIA open GPU kernel modules, exposes them as struct_ops tables, and lets eBPF programs make the decisions. The kernel verifier checks those programs, and a validation step in the driver checks each decision before it is applied. It also has a second, newer half: eBPF programs compiled to PTX and injected into running CUDA kernels, so that policies can see what happens on the device and not only in the driver.

Key idea

gpu_ext does not let eBPF manage GPU memory. The driver still owns the page tables, the chunk lists and the hardware runlists. A policy only requests a choice the driver already makes: which pages to prefetch on this fault, whether this chunk goes to the head or the tail of the eviction list, what timeslice this context gets. It does so through a kfunc that records the request. After the callback returns, the driver validates the request against current state and either applies it or falls back to its native behaviour. The camera-ready paper calls this separating the effect of a callback from its trigger.

Status

This is research code for one vendor. It targets the NVIDIA open kernel modules only. It needs a custom-built nvidia-uvm.ko (and nvidia.ko for scheduling), loaded with insmod, and a kernel with BTF (the paper uses Linux 6.15). The README warns: "NEVER run make modules_install". The orb used to write this chapter has no GPU, so nothing here was run. The commands and outputs come from the repository's documentation.

GPU background a programmer needs

You do not need to know CUDA well to follow gpu_ext, but you need five ideas: kernels and warps, device memory, unified virtual memory, GPU page faults, and how the GPU time-slices between processes.

Kernels, blocks, warps and SMs

A CUDA kernel is a function that runs on the GPU. You launch it from the host with a grid of thread blocks, for example vectorAdd<<<blocks, threads>>>(a, b, c). Each block is assigned to a streaming multiprocessor (SM). An SM runs the threads of a block in groups of 32 called warps. All 32 threads of a warp execute the same instruction at the same time on different data. NVIDIA calls this SIMT (single instruction, multiple threads). When threads in a warp take different sides of an if, the warp runs both sides one after the other with some lanes masked off. This is called divergence, and it is the main reason a CPU-style eBPF program cannot simply be copied onto the GPU.

The host submits work through channels, which are command queues the GPU reads directly. A CUDA stream maps to a channel. Channels of one context are grouped into a TSG (Time-Slice Group). The hardware scheduler picks TSGs from a per-engine runlist and runs each one for its timeslice before switching. Submitting work does not involve the kernel: user space writes into a ring buffer and rings a doorbell. The driver therefore sees when a TSG is created, bound and destroyed, but not each kernel launch. This is why gpu_ext's scheduling hooks sit on TSG lifecycle events, and why it adds uprobes on cuLaunchKernel to see launches.

Device memory and unified virtual memory

A discrete GPU has its own memory (VRAM, 32 GB on the RTX 5090 used in the paper), connected to the host over PCIe. The classic CUDA model makes you allocate VRAM with cudaMalloc and copy data explicitly. Unified Virtual Memory (UVM, also called unified or managed memory) gives the CPU and GPU one virtual address range instead. cudaMallocManaged returns a pointer that is valid on both sides. Pages move to whichever processor touches them. You can allocate more managed memory than the GPU has. This is called oversubscription, and the driver then has to evict GPU-resident pages back to the host to make room.

On Linux the open-source nvidia-uvm.ko module implements this. Its units are worth memorising because they appear in every hook signature:

  • Page: 4 KB on the host side.
  • VA block: a 2 MB aligned piece of virtual address space (uvm_va_block_t), i.e. 512 pages. Faults are serviced per VA block, and the prefetcher only works inside one block.
  • Root chunk: a 2 MB piece of physical GPU memory managed by the PMM (physical memory manager, uvm_pmm_gpu.c). Eviction works on root chunks.

GPU page faults, replay and migration

Since Pascal, NVIDIA GPUs support replayable faults. When a warp touches a managed page that is not mapped in GPU memory, the GPU MMU writes a fault entry into a hardware fault buffer and stalls that warp. Other warps keep running. It then interrupts the host. The UVM driver's bottom half reads a batch of entries, groups them by VA block, decides where each page should live, allocates GPU chunks (evicting others if needed), copies the data over PCIe with the GPU's copy engine, updates the GPU page tables, and finally tells the GPU to replay the faulting accesses. Each round trip is expensive (an interrupt, driver work, a PCIe transfer and a replay), so the driver tries to prefetch: when it services a fault, it can also migrate neighbouring pages it expects to be used soon.

The stock prefetcher lives in uvm_perf_prefetch.c. For each VA block it keeps a bitmap tree of which pages are already resident. On a fault it walks from the faulting page up the tree, and picks the largest subregion in which more than uvm_perf_prefetch_threshold percent of pages are already resident (default 51, a module parameter). It then prefetches the rest of that subregion. That is the single global rule gpu_ext makes programmable.

Why eBPF, and why here

The driver is the only layer that sees every tenant, owns the fault handler and can set hardware timeslices. That makes it the right place for policy. But it is a large C codebase maintained by NVIDIA, and a bad pointer in it can take down the machine. Linux already solved the same problem for the CPU scheduler: sched_ext lets a verified eBPF program implement struct sched_ext_ops, and the kernel falls back to the fair scheduler if the program misbehaves. gpu_ext's README says it directly: "Inspired by Linux kernel's sched_ext, gpu_ext brings the same extensibility to GPU drivers."

What gpu_ext is

gpu_ext has two halves, built by the same group (eunomia-bpf, UC Santa Cruz and collaborators):

Host side: driver hooks

A fork of NVIDIA's open GPU kernel modules (gpu_ext-kernel-modules) that registers two struct_ops types, gpu_mem_ops in nvidia-uvm and nv_gpu_sched_ops in nvidia, plus seven kfuncs at the pinned commit (one more on the 575 branch). Policies are ordinary libbpf programs in gpu_ext/extension/.

Device side: eBPF in CUDA kernels

eBPF programs compiled to PTX by llvmbpf and patched into running CUDA kernels by bpftime's nv_attach_impl. This came from the eGPU prototype (HCDS '25), whose repository says it "has been merged into bpftime". It is covered in Chapter 15 and Chapter 16.

Glue: maps and uprobes

Host policies can also attach uprobes (for example on cuLaunchKernel or llama_decode) and kprobes. They can share maps with sched_ext CPU schedulers and with device-side programs, so one policy can see application phase, driver state and GPU state together.

Paper vs. code

Both paper versions show an interface that differs from the code. The arXiv design section lists struct gpu_mem_ops with gpu_activate/gpu_access/gpu_evict_prepare/gpu_prefetch taking gdrv_mem_*_ctx_t contexts, kfuncs bpf_gpu_move_head/_move_tail, a struct gpu_sched_ops with task_init/task_destroy, and kfuncs bpf_gpu_set_attr and gdrv_sched_preempt. The camera-ready implementation section still names bpf_gpu_set_attr and bpf_gpu_prefetch_async. None of these names exist in the pinned fork. Read the paper's listings as a vendor-neutral sketch and the headers quoted in this chapter as the real ABI. Neither paper defines new BPF program types: the code uses ordinary BPF_PROG_TYPE_STRUCT_OPS, plus kprobe/uprobe programs that call the kfuncs.

How the driver hooks work

Registering a struct_ops type from a module

If you read Chapter 05, this part will look familiar. A kernel subsystem (here, a module) declares a table of function pointers, provides stub implementations for control-flow integrity, says which helpers and kfuncs its programs may call, and registers it with register_bpf_struct_ops(). The memory table, as defined in the driver:

A few design choices are visible here:

  • One policy at a time. reg installs the table with a cmpxchg against NULL, so a second loader gets -EEXIST. The repo's CLAUDE.md says it bluntly: "BPF struct_ops is a global singleton — only one can be loaded at a time." To combine prefetching and eviction you write one program that implements both, which is why there are files such as prefetch_always_max_cycle_moe.bpf.c.
  • Raw driver types in the signature. Hooks receive pointers to uvm_pmm_gpu_t, uvm_gpu_chunk_t and the prefetch bitmap tree. The verifier allows reading them through BTF (bpf_tracing_btf_ctx_access), but gpu_mem_ops_btf_struct_access returns -EACCES, so any write through those pointers is rejected at load time. The decision_ctx argument is the only way to say anything back.
  • Helpers. get_func_proto returns bpf_base_func_proto(): maps, bpf_printk, time and similar basics.
  • kfuncs for kprobes too. uvm_bpf_struct_ops_init() registers the kfunc set for BPF_PROG_TYPE_STRUCT_OPS and also, as "non-fatal", for BPF_PROG_TYPE_KPROBE.
  • A test hook. gpu_test_trigger is called when you write to /proc/bpf_testmod_trigger, so you can check that a program attached without producing a GPU fault. extension/struct_ops.bpf.c is the hello-world for it.

The call into eBPF happens in small wrappers that read the RCU-protected table pointer. If no policy is loaded, the wrapper returns UVM_BPF_ACTION_DEFAULT and the driver behaves as stock. This is what the paper measures as "hooks enabled but no policy attached", with overhead "less than 0.2%".

NvS64 uvm_bpf_call_gpu_page_prefetch(
	uvm_page_index_t page_index,
	uvm_perf_prefetch_bitmap_tree_t *bitmap_tree,
	uvm_va_block_region_t *max_prefetch_region,
	nv_gpu_prefetch_decision_t *decision)
{
	struct gpu_mem_ops *ops;
	uvm_bpf_prefetch_decision_t decision_ctx = {0};
	int ret = UVM_BPF_ACTION_DEFAULT;

	rcu_read_lock();
	ops = rcu_dereference(uvm_ops);
	if (ops && ops->gpu_page_prefetch) {
		ret = ops->gpu_page_prefetch(page_index, bitmap_tree,
						       max_prefetch_region,
						       &decision_ctx);
	}
	rcu_read_unlock();

	*decision = decision_ctx.request;
	return (NvS64)ret;
}

The prefetch hook

Here is NVIDIA's original compute_prefetch_region() in 575.57.08. It walks the bitmap tree from the faulting page upward and keeps the largest subregion whose residency count exceeds the threshold:

static uvm_va_block_region_t compute_prefetch_region(uvm_page_index_t page_index,
                                                     uvm_perf_prefetch_bitmap_tree_t *bitmap_tree,
                                                     uvm_va_block_region_t max_prefetch_region)
{
    NvU16 counter;
    uvm_perf_prefetch_bitmap_tree_iter_t iter;
    uvm_va_block_region_t prefetch_region = uvm_va_block_region(0, 0);

    uvm_perf_prefetch_bitmap_tree_traverse_counters(counter,
                                                    bitmap_tree,
                                                    page_index - max_prefetch_region.first + bitmap_tree->offset,
                                                    &iter) {
        uvm_va_block_region_t subregion = uvm_perf_prefetch_bitmap_tree_iter_get_range(bitmap_tree, &iter);
        NvU16 subregion_pages = uvm_va_block_region_num_pages(subregion);

        UVM_ASSERT(counter <= subregion_pages);
        if (counter * 100 > subregion_pages * g_uvm_perf_prefetch_threshold)
            prefetch_region = subregion;
    }

    // Clamp prefetch region to actual pages
    /* ... */
    return prefetch_region;
}

gpu_ext rewrites the start of this function. It asks the policy first, validates the answer, and then takes one of three paths depending on the return code: BYPASS (1) uses the policy's region, ENTER_LOOP (2) runs the tree walk but asks gpu_page_prefetch_iter about each subregion, and DEFAULT (0) runs the original loop. The eviction hooks

The PMM keeps root chunks on lists. When it needs a free 2 MB chunk and the free lists are empty, pick_root_chunk_to_evict() takes the first chunk from the "unused" list, then from the "used" list. Upstream, a chunk moves to the tail of "used" when it becomes allocated and evictable, so the head holds the oldest chunks, which makes this roughly LRU by activation. gpu_ext adds three calls:

  • gpu_block_activate, from chunk_update_lists_locked() right after the native move to the tail of the used list. This is the main eviction hook.
  • gpu_block_access, from root_chunk_update_eviction_list() when a root chunk is marked used. Upstream calls that only from block_mark_memory_used(), when a whole 2 MB block becomes GPU-resident. That is much rarer than "every access", and it is why the extension README tells authors to put eviction logic in gpu_block_activate and says the access hook "从未被调用" (is never called).
  • gpu_evict_prepare, from pick_root_chunk_to_evict() after the free-list check and before the unused/used selection. It receives the two list heads, but only for reading.

A policy cannot choose a victim directly. It can only ask for the current chunk to go to the head (evict sooner) or the tail (evict later) of one of the two allocation lists, used or unused. The policies in the repo almost always use the used list. The paper says handlers "may reorder but never remove regions in the kernel-maintained eviction list". The kernel keeps eviction authority under memory pressure. With only head/tail moves, many textbook algorithms can only be approximated. SAFE_POLICY_ROUTES.md says its 2Q is "best described as two-hit segmented LRU", because the interface "cannot maintain a separately sized A1out ghost queue, insert at an interior queue boundary, or demote an arbitrary Am entry".

Request, then validate, then commit

The first eviction interface (commit b63e7fde, 2025-11-24) gave policies bpf_uvm_pmm_chunk_move_head(chunk, list) and _move_tail. Each was a bare list_move() on a list pointer the policy passed in, so it changed driver lists immediately. The September 2026 revision replaced those calls with request kfuncs. The commits in the kernel fork are "feat: validate UVM prefetch transitions", "feat: validate PMM policy transitions" and "feat: validate scheduler policy transitions", all from 2026-09-01. docs/revision-safety-design.md spells out the contract. The first request is recorded. Repeating the same request is idempotent. A different second request "latches a conflict", and the whole decision is then dropped. Before calling the hook, the driver records a snapshot: the owning PMM, the root chunk identity, the list it is on and a generation counter that changes whenever the chunk changes lists. After the callback, still under the PMM list lock, it checks that the snapshot still matches and that the request is one of the allowed moves (destination USED or UNUSED, position HEAD or TAIL; nv_gpu_transition_validate_pmm()). Only then does it move the chunk once, through the same helper the native code uses. For prefetch, the region must lie inside max_prefetch_region and fit the page-index type. An invalid initial request falls back to native prefetching. The pointer is marked KF_TRUSTED_ARGS, so the verifier only accepts the decision_ctx the hook was called with.

The camera-ready design section describes this from the policy's side: kfuncs restrict actions to "selection (choosing resources, e.g., eviction order, tenant preemption priority) and timing (when to act, e.g., proactive prefetch)". Policies "cannot allocate memory or remove tasks, and fall back to the driver's original behavior under resource pressure or misconfiguration." This is the same idea as sched_ext's watchdog and fallback to the fair class, applied to individual decisions instead of the whole scheduler.

A UVM page fault, step by step

Here is one fault on a 48 GB managed buffer, with an eBPF prefetch-and-eviction policy loaded. Step through it:

1. A warp touches a non-resident page

A thread in warp 1 of some SM loads from address p + 0x3a5000. The GPU MMU finds no valid mapping, writes a fault entry (address, access type, client) into the replayable fault buffer, and stalls that warp. Other warps keep running. The GPU raises an interrupt.

2. The UVM bottom half fetches a batch

uvm_parent_gpu_service_replayable_faults() calls fetch_fault_buffer_entries() to read many entries at once. It sorts them, removes duplicates and groups them by VA block. service_fault_batch() then walks the groups. This is a kernel worker thread, not the application, which is why bpf_get_current_pid_tgid() in a hook does not return the faulting process (extension README, rule 5).

3. Pick residency for the block

For the 2 MB VA block that contains the address, service_fault_batch_block_locked() asks uvm_va_block_select_residency() where each faulted page should live, which is the GPU here. Under the block lock, uvm_va_block_service_locked() starts servicing.

4. The prefetch hook runs

uvm_perf_prefetch_get_hint_va_block() updates the residency bitmap tree and reaches compute_prefetch_region(). The driver calls gpu_page_prefetch(page_index, tree, max_region, ctx). An always-max policy calls bpf_gpu_set_prefetch_region(ctx, max.first, max.outer) and returns 1 (BYPASS).

5. The driver validates the request

nv_gpu_transition_validate_region() checks that [first, outer) lies inside the block's maximum region and that there was a single, non-conflicting request. Here it passes, so the whole rest of the 2 MB block is added to the migration mask. Had it failed, the stock 51% threshold rule would have run instead.

6. Allocate GPU memory, maybe evict

The block needs a 2 MB root chunk on the GPU. If the free pool is empty, pick_root_chunk_to_evict() calls gpu_evict_prepare (observe only), takes the head of the unused list or else of the used list, and migrates that chunk's pages back to host memory. The policy's earlier head/tail requests decided which chunk is at the head.

7. Migrate and map

The copy engine moves the faulted and prefetched pages from host DRAM over PCIe. The driver updates the GPU page tables. The new root chunk goes to the tail of the used list, and the driver calls gpu_block_activate(pmm, chunk, ctx).

8. The eviction hook requests a position

An LFU policy sets the new chunk's frequency to 1 in a map and calls bpf_gpu_request_reorder(ctx, USED, HEAD). After the callback, the driver checks the PMM/root identity, the list state and the generation under the list lock, and then moves the chunk to the head once. A frequent chunk would instead be requested at the TAIL, the safest position.

9. Replay

push_replay_on_gpu() tells the GPU to replay the faulted accesses. Warp 1 resumes. Its neighbours' later accesses to the prefetched pages hit in GPU memory and do not fault, which is the whole point of a good prefetch policy.

A gpu_ext policy is a normal libbpf program. You include vmlinux.h and the extension headers, write SEC("struct_ops/NAME") functions with BPF_PROG(), and put the table in SEC(".struct_ops"). The device side: eBPF inside CUDA kernels

Host hooks see faults and TSGs, but not what happens inside a kernel: which warps are imbalanced, which addresses a loop is about to touch, when a thread block finishes. For that, gpu_ext uses device-side eBPF. The mechanics belong to bpftime and llvmbpf and are covered in Chapter 15 (the CUDA attach pipeline, GPU maps, bpftime trace late attach) and Chapter 16 (the eBPF→PTX backend). In outline: bpftime's agent hooks CUDA's fat-binary registration, extracts the PTX of the target kernel, compiles the eBPF program to PTX with llvmbpf, splices it in as a trampoline at kernel entry, exit or selected memory instructions, and hands the patched PTX back to the driver. The negative variant shows what the paper's SIMT-aware verifier is for. The branch condition depends on the lane ID, a value that differs between the 32 threads of a warp. The paper's rule is that branch conditions, loop bounds and map-update keys must be warp-uniform (the same for all lanes) or derived through a warp-level reduction. Lane-varying values may be computed with but must not steer control flow or side effects. The verifier propagates uniformity through the bytecode's dataflow, starting from BTF annotations that mark uniform context fields. It also bans GPU-wide barriers and non-uniform atomics and applies per-hook instruction budgets. The runtime then executes a verified handler once per warp: a warp leader is chosen with __ffs(__activemask()), inputs are gathered with __ballot_sync/__shfl_sync, and results are broadcast back.

Maps are the other device-side problem. A GPU thread reading a host map crosses PCIe. The arXiv paper's Figure 12(b) measures CPU map access as about 6000× slower than GPU-side operations. So gpu_ext describes hierarchical maps. Hot per-warp or per-SM state lives in GPU shared memory, frequently used state in GPU global memory, and cold state in host DRAM. Updates go in through warp leaders without atomics, and a daemon merges GPU shards into host-visible snapshots at kernel completion boundaries. Consistency is relaxed, which the paper argues is enough for statistics-driven policies.

Device code can also act. In the arXiv microbenchmark, a device-side handler issues prefetch.global.L2 instructions that raise non-blocking page faults early, and the host prefetch hook then extends them. A strided vector-add over 40 GB (1.25× oversubscribed) runs 1.34× faster with device-only prefetch and 1.77× with host plus device stride prefetch, while a mismatched sequential policy is 8% slower. On Blackwell GPUs, block-level scheduling policies (MaxSteals, LatencyBudget, 16 and 19 lines of code in Table 1) use cluster launch control to decide which work a block claims.

Read the repo's own audits

The device-side safety story is less finished than the paper's wording suggests, and the repo says so. docs/revision-safety-design.md (2026-09-03) records that the GPU SIMT verifier lives in a bpftime branch (revision/r5-safety-evidence), while the bpftime build used for experiments has ENABLE_EBPF_VERIFIER=OFF. It concludes that "strict verifier-to-device deployment is not established by the CPU tests". microbench/fig15-device/legacy-evidence-audit.md finds that the device-overhead figure comparing "eGPU-style" with warp-aggregated execution "has no pinned warp-aggregation implementation or official eGPU artifact behind its two labels". It recommends stopping that comparison until both implementations are pinned. Treat the 60–80% device-overhead reduction below in that light.

The last line exists because "bpftool struct_ops unregister 在 kernel 6.15.11 上 segfault" (segfaults on kernel 6.15.11). If a loader dies without destroying its link, the singleton stays taken and the next loader fails with -EEXIST. The newer "safe ABI" loaders are more careful: they "only destroy the links they create" and do not remove other processes' registrations.

Benefits and limitations

Benefit: policy without a driver fork per idea

Once the hooked driver is loaded, a new prefetch or eviction policy is a 100–500 line eBPF program you can swap without restarting the application or reloading the module. That is the sched_ext argument, applied to the GPU.

Benefit: application transparency

None of the evaluated frameworks were modified. Phase information comes from uprobes, and the policies act in the driver every tenant goes through.

Benefit: cross-layer state

A single policy can combine an application uprobe, a driver fault hook, a sched_ext CPU scheduler and (with bpftime) device-side counters through shared maps.

Benefit: decisions are validated

Since the revision, policies record requests and the driver checks them against current state before acting, so a buggy policy loses performance, not correctness, for the covered transitions.

Limit: it is still a forked driver

You must build and insmod a modified NVIDIA module that matches your kernel. Nothing here is upstream in NVIDIA's tree or in Linux. The paper's portability section maps the design onto HMM and DRM scheduler concepts, but there is no AMD or Intel implementation.

Limit: narrow, coarse interface

Prefetch stays inside one 2 MB VA block (cross-block migration was removed for safety). Eviction is head/tail only. There is one system-wide memory policy and one scheduling policy. The camera-ready calls independent per-tenant policies "future work".

Limit: context surprises

UVM hooks run in a driver worker thread, so you cannot filter by PID there. gpu_block_access fires only when a block becomes resident. Hash maps under eviction pressure caused Xid 31 errors in the authors' testing.

Limit: device safety still in progress

By the repo's own audit, the SIMT verifier was not enabled in the measured device runtime, and one device-overhead comparison lacks a pinned implementation.

Related work

  • sched_ext and cache_ext: the CPU-side models gpu_ext copies. sched_ext is in Chapter 05. cache_ext (SOSP '25) does the same for the Linux page cache, with eviction-list operations much like gpu_ext's.
  • bpftime, eGPU and llvmbpf: the device-side runtime (14, 15, 16).
  • NCCLbpf (Chapter 21) puts eBPF policies inside NCCL, and xpu-perf (Chapter 22) profiles CPU and GPU continuously. These are the other two Part V projects.
  • Driver-level GPU scheduling: TimeGraph (ATC '11), Gdev (ATC '12), GPREEMPT (ATC '25), GCAPS. These change the driver for one policy each.
  • User-space GPU schedulers and runtimes: XSched (OSDI '25), Paella (SOSP '23), LithOS (SOSP '25), KTransformers, and vLLM's PagedAttention. They are programmable but bound to one framework.
  • GPU binary instrumentation: NVBit (MICRO '19) and Neutrino (OSDI '25). They offer high visibility for profiling, but no safety checks and no control actions.
  • UVM studies: UVMBench, and the access-aware UVM management papers cited by gpu_ext, such as Forest (ISCA '25) and SUV (MICRO '24).

Check your understanding

Q1. An eBPF eviction policy wants chunk X evicted as late as possible. What can it do?

Policies may only request head/tail reordering of the chunk the callback is about. Writes through driver pointers are rejected (btf_struct_access returns -EACCES), and the driver keeps eviction authority.

Q2. What does returning 1 from gpu_page_prefetch mean?

enum uvm_bpf_action: DEFAULT 0, BYPASS 1, ENTER_LOOP 2. An invalid request falls back to native behaviour.

Q3. Why can't a UVM prefetch policy filter on the faulting process with bpf_get_current_pid_tgid()?

The extension README's rule 5 says so. TSG creation is different: it runs in the calling process, which is why gpu_sched_set_timeslices can use bpf_get_current_comm().

Q4. Why does the launch-time preemption program use SEC("uprobe.s/…")?

Preemption waits for the GPU. The alternative trigger from non-sleepable struct_ops hooks goes through bpf_wq.

Q5. Under the paper's SIMT-aware rules, which device-side code is rejected?

Branch conditions, loop bounds and map keys must be warp-uniform. Lane ID varies across the warp. The repo's DEVICE_SMOKE_NEGATIVE_LANE_BRANCH fixture is exactly this negative case.

Q6. You start eviction_lfu while prefetch_always_max is still running. What happens?

One gpu_mem_ops at a time. To combine prefetch and eviction, write one table that implements both, e.g. prefetch_always_max_cycle_moe.
