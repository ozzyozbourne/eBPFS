Chapter 07

eBPF in the networking stack: XDP, AF_XDP, tc/TCX and socket programs

A packet passes many points between the wire and recv(). Where can an eBPF program run along that path? What can it see and decide at each point? And why do the busiest load balancers and DDoS filters run their code in the NIC driver, before the kernel has even allocated an sk_buff?

Prerequisites: 04 (maps, helpers), 05 (program types), 06 (libbpf, bpftool)Repos: xdp-project/xdp-tutorial, eunomia-bpf/bpf-developer-tutorial~50 min

Why this matters

On a 10 Gbit/s link, minimum-size Ethernet frames can arrive at about 14.88 million packets per second. That leaves a CPU core roughly 67 nanoseconds per packet if it handles them alone. The normal Linux receive path allocates and fills a struct sk_buff (the kernel's packet object, around 200+ bytes of metadata), runs GRO, packet taps, traffic control, netfilter, routing and the socket layer. It is very flexible and much too slow for that budget. If the job is "drop this flood" or "send this packet on to backend #7", most of that work is wasted.

Before eBPF there were two answers, and both were poor. You could write a kernel module, which is fast but can crash the machine, is hard to upgrade, and is tied to kernel internals. Or you could do kernel bypass (DPDK, netmap, vendor libraries): a userspace driver takes the NIC away from the kernel and busy-polls it. Bypass is very fast, but the kernel's routing table, firewall, tcpdump, ip and the rest of the tooling no longer see the traffic. The cores spin at 100% even when idle, and any packet meant for the host has to be put back into the kernel by hand.

eBPF in the networking stack offers a third option: safe, verified programs at well-defined hooks inside the kernel's own data path. The earliest hook, XDP, runs inside the driver's receive loop, and the CoNEXT 2018 paper that describes it reports up to 24 million packets per second on a single core for a drop program [1]. Later hooks (tc, socket hooks) run less often per byte of decision but see more context, such as the full sk_buff, the owning socket and the cgroup. This chapter walks the packet path from the NIC to the application and stops at every eBPF hook on the way.

Key idea

Each networking hook makes a different trade between how early it runs and how much the kernel already knows. XDP is earliest and cheapest, but sees only raw bytes. tc sees an sk_buff with metadata and can also act on egress. Socket-level hooks see connections and messages. Pick the earliest hook that has the information your decision needs.

The packet path and its eBPF hooks

Figure 07.1 shows the receive path of a Linux host, simplified. Read it top to bottom. On the left are the kernel stages and on the right the eBPF program types that can attach there.

XDP: in the driver, before the sk_buff

When the NIC raises an interrupt, the driver schedules its NAPI poll routine. That routine runs in softirq context and pulls descriptors off the RX ring. A driver with native XDP support runs the attached XDP program on each received buffer right there, while the frame is still a page of DMA'd bytes. The program gets a tiny context (struct xdp_md) holding pointers to the packet start and end, and it returns a verdict. Only if the verdict is XDP_PASS does the driver go on to build an sk_buff and hand the packet to the stack. A dropped packet costs one program run and one page recycle, with no allocation, no GRO and no taps. One consequence is that tcpdump does not see packets that native XDP dropped.

tc: the first hook with an sk_buff

After skb allocation, __netif_receive_skb_core() delivers the packet to taps (packet sockets, which is how tcpdump sees it) and then to the tc ingress hook. Programs here are of type BPF_PROG_TYPE_SCHED_CLS and see a struct __sk_buff: the packet bytes plus metadata such as mark, priority, the VLAN tag, the hash and the ingress ifindex. tc also has an egress hook, run just before the packet goes to the driver's transmit queue. That makes tc the usual place for egress policy, NAT, encapsulation and container networking.

Netfilter, routing and the socket layer

Past tc, the packet enters IP: netfilter PREROUTING (iptables/nftables, and since 6.4 BPF programs of type BPF_PROG_TYPE_NETFILTER, covered below), the routing decision, then LOCAL_IN. For TCP/UDP, the transport layer then looks up the socket, and an sk_lookup program can pick the socket itself. On the socket, a socket filter can trim or reject the packet before it is queued, and sockmap's sk_skb verdict programs can splice it to another socket. On the send side, sk_msg programs see each sendmsg(). sockops programs, attached to a cgroup, are called on TCP events such as connection establishment, RTO and retransmit.

XDP in depth

The context: struct xdp_md

An XDP program is a function int prog(struct xdp_md *ctx). The context the program sees is a small "mirror" structure. The verifier rewrites each access to it into loads from the kernel's real struct xdp_buff (see chapter 03 for how context rewriting works).

enum xdp_action {
	XDP_ABORTED = 0,
	XDP_DROP,
	XDP_PASS,
	XDP_TX,
	XDP_REDIRECT,
};

/* user accessible metadata for XDP packet hook
 * new fields must be added to the end of this structure
 */
struct xdp_md {
	__u32 data;
	__u32 data_end;
	__u32 data_meta;
	/* Below access go through struct xdp_rxq_info */
	__u32 ingress_ifindex; /* rxq->dev->ifindex */
	__u32 rx_queue_index;  /* rxq->queue_index  */

	__u32 egress_ifindex;  /* txq->dev->ifindex */
};

data and data_end are declared as __u32 for ABI reasons, but at runtime they are pointers. Every XDP program begins with the same two casts: void *data = (void *)(long)ctx->data;. data_meta points to a scratch area before data. A program can grow it with bpf_xdp_adjust_meta() to pass information along, and a later tc program reads it through __sk_buff->data_meta. The kernel reserves XDP_PACKET_HEADROOM (256 bytes) in front of the packet so that bpf_xdp_adjust_head() can push encapsulation headers without copying.

The five actions

XDP_PASS

Continue normally. The driver builds an sk_buff and the packet goes up the stack. The program may have rewritten bytes first.

XDP_DROP

Discard silently. The page goes straight back to the driver's RX ring. This is the cheapest possible drop, and the basis of XDP DDoS filters.

XDP_TX

Transmit the (usually rewritten) frame back out of the same interface it arrived on. Used for "hairpin" load balancers and ICMP echo responders.

XDP_REDIRECT

Send the frame somewhere else: another NIC, another CPU, or an AF_XDP socket. The target is chosen beforehand by bpf_redirect() or bpf_redirect_map(), whose return value the program then returns.

XDP_ABORTED

Value 0: "the program hit an error". The packet is dropped and the xdp:xdp_exception tracepoint fires, so failures are visible. Unknown return codes are treated the same way.

The values are worth knowing because tools print them as numbers: XDP_ABORTED = 0, XDP_DROP = 1, XDP_PASS = 2, XDP_TX = 3, XDP_REDIRECT = 4. The xdp-tutorial's stats examples index a per-action counter array by exactly these values.

Native, generic and offloaded modes

The same XDP object file can run in three places. You choose one with a flag at attach time (XDP_FLAGS_DRV_MODE, XDP_FLAGS_SKB_MODE, XDP_FLAGS_HW_MODE in include/uapi/linux/if_link.h):

  • Native (driver) mode, xdpdrv. The driver calls the program in its NAPI poll loop. This is the fast path, and it needs driver support. Most 10G+ server NIC drivers (mlx5, i40e/ice, ixgbe, bnxt, ...) and virtual devices such as veth, virtio_net and tun support it.
  • Generic (skb) mode, xdpgeneric. Added in Linux 4.12, this runs the program from the core receive path after the sk_buff has been allocated. It works on every device, lo included, so it is ideal for learning and testing. It removes most of XDP's performance advantage, though, because the expensive allocation has already happened.
  • Offloaded (hardware) mode, xdpoffload. The NIC's own processors JIT and run the BPF program, and the host CPU never sees dropped packets. Support is rare. The xdp-tutorial documents Netronome Agilio SmartNICs (the nfp driver), which need a special BPF firmware (basic02-prog-by-name/xdp_offload_nfp.org). Offload supports only a subset of helpers and map types.

If you ask for plain xdp without a mode, ip and bpftool try native first and fall back to generic. Programs written for one mode run unchanged in the others; only speed and the set of supported helpers differ.

veth gotcha

Native XDP on veth works, but frames that are XDP_TX'd or redirected into a veth are only delivered if the receiving peer has NAPI enabled: it must have an XDP program attached, or (since Linux 5.13) GRO enabled with ethtool -K <peer> gro on; otherwise veth_xdp_xmit() drops them. That is why the eunomia tutorial's load balancer README loads a stub: sudo ip l set dev veth7 xdp obj ./stub.bpf.o sec .xdp (bpf-developer-tutorial/src/42-xdp-loadbalancer/README.md).

Parsing packets safely: data, data_end and the verifier

An XDP or tc program reads the packet through ordinary pointer dereferences ("direct packet access", Linux 4.7). The verifier must prove that every load stays within [data, data_end). It tracks each pointer derived from data as type PTR_TO_PACKET with a known offset range. When you compare ptr + N > data_end and branch away, the verifier records on the fall-through path that N bytes past ptr are safe to read. Access a byte beyond what you have checked and the program is rejected at load time with "invalid access to packet". The rejection happens at load time, never at run time.

The xdp-tutorial collects its bounds-checked parsers in one header that every packetXX lesson includes. They use a small cursor struct that walks forward through the headers. Here are the IPv4 and TCP parsers. Note the two-step check for variable-length headers: first iph + 1 (the fixed 20 bytes, so that ihl can be read at all), then nh->pos + hdrsize for the real length. The sanity check that ihl*4 is at least sizeof(*iph) also matters. Without it, a malicious ihl = 0 would make the cursor stand still, and the next "header" would overlap this one.

/* Header cursor to keep track of current parsing position */
struct hdr_cursor {
	void *pos;
};
/* ... */
static __always_inline int parse_iphdr(struct hdr_cursor *nh,
				       void *data_end,
				       struct iphdr **iphdr)
{
	struct iphdr *iph = nh->pos;
	int hdrsize;

	if (iph + 1 > data_end)
		return -1;

	hdrsize = iph->ihl * 4;
	/* Sanity check packet field is valid */
	if(hdrsize < sizeof(*iph))
		return -1;

	/* Variable-length IPv4 header, need to use byte-based arithmetic */
	if (nh->pos + hdrsize > data_end)
		return -1;

	nh->pos += hdrsize;
	*iphdr = iph;

	return iph->protocol;
}
/* ... */
/*
 * parse_tcphdr: parse and return the length of the tcp header
 */
static __always_inline int parse_tcphdr(struct hdr_cursor *nh,
					void *data_end,
					struct tcphdr **tcphdr)
{
	int len;
	struct tcphdr *h = nh->pos;

	if (h + 1 > data_end)
		return -1;

	len = h->doff * 4;
	/* Sanity check packet field is valid */
	if(len < sizeof(*h))
		return -1;

	/* Variable-length TCP header, need to use byte-based arithmetic */
	if (nh->pos + len > data_end)
		return -1;

	nh->pos += len;
	*tcphdr = h;

	return len;
}

The Ethernet parser in the same file also skips up to VLAN_MAX_DEPTH (default 2) 802.1Q/802.1ad tags. It does this in a loop marked #pragma unroll, which predates the verifier's support for bounded loops. The loop checks vlh + 1 > data_end on every iteration.

Learn from the deliberate bug

Lesson packet01-parsing/xdp_prog_kern.c ships with a bug planted on purpose as Assignment 1: if (nh->pos + 1 > data_end), where pos is a void *. That checks one byte, not 14, so the verifier rejects the later read of eth->h_proto. Pointer arithmetic on a typed pointer (eth + 1) advances by sizeof(*eth). On a void * it advances by bytes. Mixing the two up is the most common XDP verifier error.

A few further rules for parsing safely. Fields are in network byte order, so compare against bpf_htons(ETH_P_IP) rather than converting every packet. Do not trust length fields (tot_len, UDP len) as bounds; check against data_end. In tc programs, the linear area may not hold the whole packet, so use bpf_skb_pull_data() or bpf_skb_load_bytes() for bytes past data_end.

The smallest useful XDP program drops everything. The xdp-tutorial's basic02 lesson puts a pass and a drop program in one object, so that you can see how a loader selects a program by name:

A more realistic firewall parses headers and drops selectively. This is the reference solution of the parsing lesson, which lives in packet02-rewriting. It drops ICMP and ICMPv6 echo requests with an even sequence number, so ping shows exactly every other reply missing. Every decision is recorded in a per-action stats map by xdp_stats_record_action():

/* Solution to the parsing exercise in lesson packet01. Handles VLANs and legacy
 * IP (via the helpers in parsing_helpers.h).
 */
SEC("xdp")
int  xdp_parser_func(struct xdp_md *ctx)
{
	void *data_end = (void *)(long)ctx->data_end;
	void *data = (void *)(long)ctx->data;

	/* Default action XDP_PASS, imply everything we couldn't parse, or that
	 * we don't want to deal with, we just pass up the stack and let the
	 * kernel deal with it.
	 */
	__u32 action = XDP_PASS; /* Default action */

	/* These keep track of the next header type and iterator pointer */
	struct hdr_cursor nh;
	int nh_type;
	nh.pos = data;

	struct ethhdr *eth;

	/* Packet parsing in steps: Get each header one at a time, aborting if
	 * parsing fails. Each helper function does sanity checking (is the
	 * header type in the packet correct?), and bounds checking.
	 */
	nh_type = parse_ethhdr(&nh, data_end, &eth);

	if (nh_type == bpf_htons(ETH_P_IPV6)) {
		struct ipv6hdr *ip6h;
		struct icmp6hdr *icmp6h;

		nh_type = parse_ip6hdr(&nh, data_end, &ip6h);
		if (nh_type != IPPROTO_ICMPV6)
			goto out;

		nh_type = parse_icmp6hdr(&nh, data_end, &icmp6h);
		if (nh_type != ICMPV6_ECHO_REQUEST)
			goto out;

		if (bpf_ntohs(icmp6h->icmp6_sequence) % 2 == 0)
			action = XDP_DROP;

	} else if (nh_type == bpf_htons(ETH_P_IP)) {
		struct iphdr *iph;
		struct icmphdr *icmph;

		nh_type = parse_iphdr(&nh, data_end, &iph);
		if (nh_type != IPPROTO_ICMP)
			goto out;

		nh_type = parse_icmphdr(&nh, data_end, &icmph);
		if (nh_type != ICMP_ECHO)
			goto out;

		if (bpf_ntohs(icmph->un.echo.sequence) % 2 == 0)
			action = XDP_DROP;
	}
 out:
	return xdp_stats_record_action(ctx, action);
}

Note the "default to XDP_PASS" stance. Anything the program cannot parse goes to the normal stack, which knows how to handle it. A firewall that defaults to drop must also handle fragments, IP options, unknown EtherTypes and tunnels, or it will black-hole legitimate traffic.

Walkthrough: a packet meets the XDP firewall

Step through what happens to one ICMP echo request arriving at an interface running xdp_parser_func in native mode.

1. DMA into the RX ring

The NIC writes the frame (Ethernet + IPv4 + ICMP, 98 bytes for a default ping) into a page the driver posted on RX queue 3. It writes a completion descriptor and raises an interrupt. The driver masks the interrupt and schedules NAPI on that queue's CPU.

2. Driver builds an xdp_buff

In its NAPI poll loop the driver reads the descriptor and fills a stack-allocated struct xdp_buff: data points 256 bytes into the page (after XDP_PACKET_HEADROOM), data_end = data + 98, and rxq records ifindex and queue 3. No sk_buff exists yet. The driver then calls the JIT-compiled program.

3. Parse Ethernet

parse_ethhdr() checks nh->pos + 14 > data_end (false, since 98 bytes are present), advances the cursor and returns h_proto = htons(0x0800). No VLAN tag, so the unrolled VLAN loop exits at once. The verifier proved at load time that this read is safe; at run time the check is a single compare.

4. Parse IPv4

parse_iphdr() checks the fixed 20 bytes and reads ihl = 5 (20 bytes). It confirms 20 ≥ sizeof(struct iphdr), checks pos + 20 > data_end, advances, and returns protocol = IPPROTO_ICMP.

5. Parse ICMP and decide

parse_icmphdr() checks icmph + 1 > data_end and returns type = ICMP_ECHO. The program reads un.echo.sequence, converts it with bpf_ntohs() and finds 42, an even number. action = XDP_DROP.

6. Record and return

xdp_stats_record_action() looks up the per-CPU stats entry for key XDP_DROP and adds 1 to packets and 98 to bytes. It then returns the action. Userspace (xdp_stats) reads this map to print per-action rates.

7. Driver acts on XDP_DROP

The driver puts the page back on its RX recycle path; with page_pool drivers it never even reaches the page allocator. Total cost: one program run of a few dozen instructions. There is no skb, no taps (tcpdump never sees it), no netfilter, no socket. The next echo request (sequence 43, odd) instead returns XDP_PASS.

8. The XDP_PASS path for comparison

For sequence 43, the driver now allocates an sk_buff around the page (build_skb-style, no copy), runs GRO and calls netif_receive_skb. The packet then visits taps, tc ingress, netfilter PREROUTING, routing, LOCAL_IN and the ICMP handler, which generates the reply. Every one of those stages is work that step 7 skipped.

XDP_TX and XDP_REDIRECT: forwarding without the stack

XDP_TX sends a frame back out of the interface it came in on. The program must first rewrite it into something worth sending. The tutorial's packet03 lesson turns ICMP echo requests into replies by swapping MACs and IPs, changing the type and fixing the checksum, and then returns XDP_TX. Katran-style "load balancer on a stick" designs also use XDP_TX: they encapsulate the packet towards a backend and bounce it out of the same NIC.

XDP_REDIRECT is more general. The program calls a helper that records a target and returns XDP_REDIRECT (or a fallback action on failure), and the driver queues the frame to that target. Redirects are bulked: the driver flushes queued frames at the end of the NAPI poll, so the cost of a TX doorbell or a cross-CPU wakeup is shared across many packets. According to the kernel documentation, XDP_REDIRECT works with four map types [3]:

  • DEVMAP (4.14) and DEVMAP_HASH (5.4) hold net devices. Redirecting into one sends the frame out of another NIC through the driver's ndo_xdp_xmit, which is how an XDP router or bridge works. Entries can carry a second XDP program that runs just before transmit. The flags BPF_F_BROADCAST and BPF_F_EXCLUDE_INGRESS allow multicast to every entry.
  • CPUMAP (4.15) holds CPUs. Each entry has a kernel thread bound to that CPU. Frames redirected there are turned into sk_buffs on the remote CPU, which is a software RSS: one CPU does the cheap classification at line rate and spreads the expensive stack work. Since 5.9 an entry may run a second XDP program on the remote CPU [4].
  • XSKMAP (4.18) holds AF_XDP sockets, covered in the next section.

Here is the devmap variant from the tutorial. The program is short because userspace does the real configuration: it fills tx_port with the egress ifindex and redirect_params with a source-MAC → destination-MAC mapping.

struct {
	__uint(type, BPF_MAP_TYPE_DEVMAP);
	__type(key, int);
	__type(value, int);
	__uint(max_entries, 256);
	__uint(pinning, LIBBPF_PIN_BY_NAME);
} tx_port SEC(".maps");


struct {
	__uint(type, BPF_MAP_TYPE_HASH);
	__type(key,  unsigned char[ETH_ALEN]);
	__type(value, unsigned char[ETH_ALEN]);
	__uint(max_entries, 1);
	__uint(pinning, LIBBPF_PIN_BY_NAME);
} redirect_params SEC(".maps");
/* ... */
/* Assignment 3: nothing to do here, patch the xdp_prog_user.c program */
SEC("xdp")
int xdp_redirect_map_func(struct xdp_md *ctx)
{
	void *data_end = (void *)(long)ctx->data_end;
	void *data = (void *)(long)ctx->data;
	struct hdr_cursor nh;
	struct ethhdr *eth;
	int eth_type;
	int action = XDP_PASS;
	unsigned char *dst;

	/* These keep track of the next header type and iterator pointer */
	nh.pos = data;

	/* Parse Ethernet and IP/IPv6 headers */
	eth_type = parse_ethhdr(&nh, data_end, &eth);
	if (eth_type == -1)
		goto out;

	/* Do we know where to redirect this packet? */
	dst = bpf_map_lookup_elem(&redirect_params, eth->h_source);
	if (!dst)
		goto out;

	/* Set a proper destination address */
	memcpy(eth->h_dest, dst, ETH_ALEN);
	action = bpf_redirect_map(&tx_port, 0, 0);

out:
	return xdp_stats_record_action(ctx, action);
}

The final assignment of that lesson (solution in packet-solutions/xdp_prog_kern_03.c, xdp_router_func) turns this into a real IPv4/IPv6 router. It calls bpf_fib_lookup() to query the kernel's own routing table and neighbour cache, decrements the TTL, rewrites both MACs and returns bpf_redirect(fib_params.ifindex, 0). Destinations that are blackholed or unreachable become XDP_DROP, and "no neighbour yet" falls back to XDP_PASS, so the stack resolves ARP. Here XDP's kernel integration pays off: routes added with ip route take effect in the fast path at once.

Debugging silent redirect drops

A failed redirect (target down, driver without ndo_xdp_xmit, frame too big) drops silently. The kernel's redirect documentation recommends counting the XDP tracepoints: sudo bpftrace -e 'tracepoint:xdp:* { @cnt[probe] = count(); }', or extracting errno from xdp:xdp_redirect*_err and xdp:xdp_devmap_xmit [3]. The xdp-tutorial's tracing02-xdp-monitor lesson builds a monitor on the same tracepoints.

AF_XDP: packets to userspace, zero-copy

Sometimes the processing really belongs in userspace: a DPDK-style packet pipeline, an IDS, a userspace TCP stack. AF_XDP (Linux 4.18) gives userspace a socket whose packets come straight from an XDP redirect. They skip the whole stack and, in zero-copy mode, are never copied [2]. Unlike full kernel bypass, the NIC stays under the kernel's control. You choose per packet which traffic goes to userspace (XDP_REDIRECT into an XSKMAP) and which goes to the kernel (XDP_PASS).

The mechanics, from the kernel's AF_XDP documentation [2]:

  • The application allocates a UMEM, a contiguous region of equal-size frames (malloc, mmap, huge pages), and registers it with setsockopt(XDP_UMEM_REG).
  • A UMEM has two rings. The FILL ring carries frame addresses from userspace to the kernel ("you may write a received packet here"). The COMPLETION ring carries addresses back once the kernel has finished transmitting them.
  • Each socket has an RX and/or TX ring of descriptors (address + length). Rings are mmap'd and work as lock-free producer/consumer queues.
  • The socket is bind()-ed to one (netdev, queue id) pair. An XDP program then redirects into an XSKMAP whose key is normally the RX queue index. A frame from queue 3 can only be delivered to a socket bound to queue 3.
  • On bind, the kernel first tries zero-copy mode (the driver DMAs into UMEM pages) and falls back to copy mode (one copy into UMEM). XDP_ZEROCOPY or XDP_COPY force one mode or fail. XDP_SHARED_UMEM lets several sockets share a UMEM, and XDP_USE_NEED_WAKEUP lets the kernel tell the app when a syscall is needed, which avoids busy-polling.

The tutorial's README warns about one trade-off. Zero-copy needs explicit driver support for placing UMEM pages in the RX ring. In zero-copy mode, XDP_PASS is expensive, because the kernel must allocate an skb and copy out of UMEM. If an RX queue mixes AF_XDP and stack traffic, copy mode on a zero-copy-capable driver can be the better choice. Note also that the xsk ring helpers moved from libbpf to libxdp (<xdp/xsk.h>) when libbpf 1.0 removed them.

tc: cls_bpf and direct-action

Linux traffic control (tc) is the kernel's packet scheduling and classification framework. Its BPF classifier, cls_bpf (Linux 4.1), runs programs of type BPF_PROG_TYPE_SCHED_CLS. Two later additions made it the main programmable hook for skb-level work:

  • direct-action ("da", 4.4). Classically, a classifier returns a class id and separate tc actions decide what to do. In da mode, the program's return value is the action (TC_ACT_OK, TC_ACT_SHOT, TC_ACT_REDIRECT, ...), so one program both classifies and acts. Practically every modern tc BPF program uses da.
  • The clsact qdisc (4.5). It is a pseudo-qdisc that does no queueing and only provides an ingress and an egress attach point. tc qdisc add dev X clsact is the standard first step.

The context is struct __sk_buff, a mirror of a subset of struct sk_buff. Compared with xdp_md it is rich:

{

The checksum trick deserves a note. Adding 1 to a 16-bit field in network order lowers the ones'-complement checksum by 1, which the code does with check += htons(-1). A UDP checksum of 0 means "no checksum", hence the extra fix-up. A general program would use bpf_l4_csum_replace() instead.

tc return codes

In direct-action mode the common verdicts, from include/uapi/linux/pkt_cls.h, are: TC_ACT_UNSPEC (-1) use the default/next filter; TC_ACT_OK (0) accept; TC_ACT_SHOT (2) drop; TC_ACT_PIPE (3) continue to the next action; TC_ACT_REDIRECT (7) deliver to the device chosen by bpf_redirect().

TCX: link-based tc attachment (Linux 6.6)

cls_bpf works, but it was designed for an era of one admin and one tc command. Several BPF-based agents on one host (a CNI, an observability tool, a security agent) run into the same problems. Filters are identified by handle and priority, so one agent can replace or delete another's by accident. Nothing ties a filter's lifetime to the process that installed it. And there is no clean ordering ("run me before Cilium") or atomic replace.

TCX, written by Daniel Borkmann and merged in Linux 6.6 [9], fixes this with a qdisc-less, fd-based attach point for the same ingress and egress hooks. It is built on the generic bpf_mprog multi-program infrastructure:

  • Programs attach as BPF links (BPF_TCX_INGRESS/BPF_TCX_EGRESS). A link is owned by a file descriptor or a bpffs pin and disappears when its owner does; other users cannot silently detach it.
  • Ordering is explicit: BPF_F_BEFORE/BPF_F_AFTER relative to another program or link, or first/last. Each change bumps a revision counter, so updates can be made conditional (compare-and-swap).
  • New return codes make chaining explicit: TCX_NEXT (-1) runs the next program, TCX_PASS (0), TCX_DROP (2) and TCX_REDIRECT (7) are terminal. They match the numeric values of the TC_ACT_* equivalents, so existing programs keep working.
  • TCX programs run first, then any classic cls_bpf filters still present, so a gradual migration is possible.

Netfilter programs (Linux 6.4)

Florian Westphal's 6.4 series added BPF_PROG_TYPE_NETFILTER: a BPF program registered as a netfilter hook in its own right, next to the iptables/nftables chains instead of inside them. It runs where netfilter runs (PREROUTING, LOCAL_IN, FORWARD, LOCAL_OUT, POSTROUTING), so it sees packets after the stack has validated IP headers and, at a later priority, after conntrack. libbpf maps SEC("netfilter") to this type. The context is struct bpf_nf_ctx, which carries the nf_hook_state (family, hook, input and output devices) and the sk_buff. The verifier accepts only NF_DROP (0) and NF_ACCEPT (1) as return values. The kernel selftest is the smallest possible example:

There is no auto-attach from the section name. User space creates a BPF link with BPF_LINK_CREATE, or with libbpf's bpf_program__attach_netfilter() (libbpf 1.3), passing a struct bpf_netfilter_opts with pf (NFPROTO_IPV4 or NFPROTO_IPV6; other families are rejected), hooknum (for example NF_INET_LOCAL_IN) and priority. net/netfilter/nf_bpf_link.c refuses NF_IP_PRI_FIRST and NF_IP_PRI_LAST, so conntrack confirmation always runs last. Since 6.6 the BPF_F_NETFILTER_IP_DEFRAG flag asks for reassembled packets. Like other links, the hook disappears when its owner closes the link fd. libbpf-rs ships a netfilter_blocklist example built on this hook. Choose it over tc when the decision belongs at a netfilter point (after routing, or relative to conntrack) and you want it ordered by priority among existing nftables chains.

Socket-level programs

The last group of hooks works on sockets rather than devices. They are covered more briefly here; chapter 05 places them among the other program types.

Socket filters

BPF_PROG_TYPE_SOCKET_FILTER (3.19) is the direct descendant of classic BPF (chapter 01). A program attached with setsockopt(fd, SOL_SOCKET, SO_ATTACH_BPF, &prog_fd, ...) runs on each packet queued to that socket. It receives an __sk_buff and returns how many bytes to keep, where 0 means drop. Most often it filters raw AF_PACKET sockets, as tcpdump does with classic BPF. It is observation-only: it cannot change the packet or affect other sockets. bcc's early networking tools used it to tap traffic.

sockops, sk_msg and sockmap

sockops (BPF_PROG_TYPE_SOCK_OPS, 4.13) programs attach to a cgroup. They are called at TCP events (BPF_SOCK_OPS_ACTIVE_ESTABLISHED_CB, PASSIVE_ESTABLISHED_CB, RTO_CB, STATE_CB, header-option callbacks, ...). They can tune the connection with bpf_setsockopt(), for example to pick a congestion control or set initial windows, and they can insert the socket into a SOCKMAP/SOCKHASH (4.14/4.18). Programs attached to such a map then act on its sockets. sk_msg (4.17) runs on every sendmsg() and can redirect the data directly into another socket's receive queue with bpf_msg_redirect_hash(). sk_skb stream parser/verdict programs do the same on the receive side. For two processes talking over loopback, such as a service and its sidecar proxy, this skips the whole TCP/IP stack in both directions.

The eunomia tutorial's chapter 29 is a compact, complete example:

The sk_msg program attaches to the map (msg_verdict), not to a cgroup or device: every socket in the map inherits it. Projects such as Cilium and Merbridge have used this sockmap pattern to accelerate local, sidecar-style traffic.

sk_lookup: choosing the listening socket

BPF_PROG_TYPE_SK_LOOKUP (5.9) runs when TCP needs a listening socket, or UDP an unconnected one, for an incoming packet. Established connections do not trigger it. The program can pick any socket, normally from a SOCKMAP, with bpf_sk_assign(), and return SK_PASS or SK_DROP [6]. It attaches to a network namespace via a BPF link, and several programs run in attach order. The kernel documentation's motivating cases are serving a whole IP range (e.g. 192.0.2.0/24) on one socket when binding to INADDR_ANY is impossible because of a port conflict, and an L7 proxy accepting connections on all or many ports, which would otherwise need one bind() per address/port pair. Cloudflare, which needed exactly this for its edge, contributed the feature upstream.

Who runs this in production

Katran (Meta)

An open-source C++ library plus BPF program forming the forwarding plane of Meta's L4 load balancer, released in 2018 [7]. It runs in XDP (driver mode for speed; generic mode works at a cost). It checks whether the destination is a VIP and looks up existing flows in a connection table. For new flows it hashes the 5-tuple to pick a backend consistently, so different Katran instances agree without sharing state. It then IP-in-IP encapsulates the packet and sends it back out with XDP_TX. Backends reply directly (DSR). Its README documents the limits that come with the speed: no IP fragments, no IP options, and a bounded maximum packet size.

Cilium

The Kubernetes CNI whose datapath is built entirely from the hooks in this chapter [11]. tc (and, since Cilium 1.16 on 6.6+ kernels, TCX) programs sit on host devices and on the host side of each Pod's veth for policy, load balancing and encapsulation (bpf_lxc.c, bpf_host.c, bpf_overlay.c in cilium/bpf/). Optional XDP acceleration (bpf_xdp.c, loadBalancer.acceleration=native) handles NodePort/LoadBalancer traffic in the driver. Socket hooks (bpf_sock.c) do service translation at connect() time, and sockmap-based redirection is available as well. Its BPF and XDP Reference Guide is one of the best long-form references.

Cloudflare

Cloudflare's DDoS mitigation sends every packet arriving at a server first through a group of XDP programs. The first, L4Drop, applies mitigation rules from earlier detected attacks and samples packets for the detection daemon dosd. Packets that survive go to Unimog, Cloudflare's XDP-based L4 load balancer, and then to iptables [8]. The 2018 L4Drop post describes compiling rules into eBPF and keeping XDP "always on". Their sk_lookup and socket work fed the upstream kernel features described above.

The XDP paper itself evaluates three such use cases (layer-3 routing, inline DDoS protection and layer-4 load balancing) next to a DPDK baseline. In the paper's packet-drop test, XDP reached 24 Mpps on one core against 43.5 Mpps for DPDK on the same hardware. The authors argue that XDP's integration with the kernel, its lack of dedicated busy-polling cores and its safety make up for the gap [1]. Treat those numbers as the 2018 paper's measurements on its test hardware, not as a property of every NIC.

Beyond the kernel: eunomia-bpf's userspace XDP work

XDP programs are just eBPF bytecode with a known context and return contract, so nothing ties them to the kernel. Two eunomia-bpf research projects build on that idea:

  • userspace-xdp (moved from eunomia-bpf/XDP-eBPF-in-DPDK) runs unmodified XDP network functions in userspace. It uses bpftime as the loader and runtime for maps and helpers, llvmbpf or uBPF as the JIT/AOT back-end, and DPDK or AF_XDP as packet I/O. The existing control plane keeps working, and XDP can run where kernel eBPF is unavailable. Its README calls it a research prototype that currently supports an l2fwd setup (mainly XDP_DROP/XDP_TX), and says the component will move into the bpftime repository.
  • XDP-on-GPU explores batching packets from a DPDK poll-mode driver and running XDP-style programs over them on a GPU (CUDA/OpenCL back-ends), while keeping the DROP/PASS/TX/REDIRECT semantics. The README labels it work in progress that "does not work now". Read it as a design direction, not a usable tool. GPU-side eBPF is the subject of Part V.

Benefits and limitations

Benefits

  • Speed where it matters: XDP drops and forwards before any allocation, and redirects are bulked.
  • Kernel integration: XDP_PASS hands packets back to the normal stack. Helpers such as bpf_fib_lookup() reuse the kernel's routing and neighbour tables. The usual tools keep working for everything the program passes.
  • Safety and live updates: the verifier rejects out-of-bounds packet access, and programs can be replaced atomically (XDP_FLAGS_REPLACE, link updates) without dropping the interface.
  • No dedicated cores: XDP runs on interrupt/NAPI processing, so idle systems really are idle. The XDP paper stresses this against DPDK's busy polling.
  • Choice of layer: the same language and maps work from the driver up to the socket, so a system can split work across hooks (Cilium's XDP + tc + socket design).

Limitations

  • Ingress only for XDP. There is no XDP egress hook, so outgoing policy needs tc/TCX.
  • Raw bytes only in XDP: no socket, no cgroup, and no conntrack unless you build it yourself or use the conntrack kfuncs. Checksums, fragments, tunnels and IP options are your problem.
  • Driver dependence: native mode, redirect targets, zero-copy AF_XDP and multi-buffer support vary by driver. Generic mode works everywhere but is slow.
  • Large frames: classic XDP assumes the packet fits in one buffer. Jumbo frames need the multi-buffer ("frags") API of Linux 5.18, with programs declared SEC("xdp.frags") and helpers such as bpf_xdp_get_buff_len().
  • One XDP program per interface in the kernel. Sharing needs libxdp's dispatcher or cooperation between tools. For tc, TCX solves the equivalent problem.
  • Verifier constraints: complex parsers (IPv6 extension headers, TLVs) need careful bounded loops and can hit complexity limits (chapter 03).
  • Raw throughput ceiling: kernel-bypass frameworks still report more per-core packets in microbenchmarks, as the XDP paper's own DPDK comparison shows.

Related work

  • Kernel bypass: DPDK and netmap take the NIC away from the kernel. AF_XDP is the in-kernel answer, and DPDK has an AF_XDP poll-mode driver, so the two now meet. Karlsson and Töpel's LPC 2018 paper "The Path to DPDK Speeds for AF_XDP" describes the AF_XDP design and its performance work [10].
  • Classic BPF socket filters and tcpdump's compiler are the ancestors of everything here (chapter 01).
  • Netfilter (iptables/nftables) remains the general firewall. BPF can now also attach there as a hook of its own (BPF_PROG_TYPE_NETFILTER, above), and the older xt_bpf match (iptables -m bpf) runs a BPF filter inside an iptables rule.
  • Other hooks not covered in depth: flow dissector programs, lightweight tunnel (LWT) programs, cgroup_skb and cgroup socket-address hooks (connect4, bind4 …), and SO_REUSEPORT selection programs. The cgroup hooks are covered in chapter 05; the others are listed, with their SEC() names, in libbpf's program types table.
  • Tooling and libraries: xdp-tools (libxdp, xdp-loader, xdp-filter, xdpdump), and the Go, Rust and C libraries of chapter 08.

Check your understanding

Q1. An XDP program in native mode returns XDP_DROP. Which of these happened to the packet?

Native XDP runs in the driver's NAPI poll before skb allocation. Taps (tcpdump), tc and netfilter all run later on an sk_buff, so they never see a packet dropped by XDP.

Q2. Why does the verifier reject struct ethhdr *eth = data; if (data + 1 > data_end) return XDP_PASS; return eth->h_proto == 0 ? XDP_DROP : XDP_PASS;?

This is the planted bug from packet01. Arithmetic on void * advances bytes; use eth + 1 > data_end (or data + sizeof(*eth)) to prove all 14 bytes.

Q3. You need to rewrite the source port of packets your host sends. Which hook do you use?

XDP is receive-only, in every mode. tc/TCX has an egress hook with an __sk_buff and checksum helpers. The xdp-tutorial's tc_reply_kern_02.c does exactly this.

Q4. Which map lets an XDP program hand frames to another CPU, where they become sk_buffs and enter the normal stack?

Each CPUMAP entry has a kernel thread bound to that CPU, which builds skbs for redirected frames: a software RSS. DEVMAP targets other NICs, XSKMAP targets AF_XDP sockets, and SOCKMAP is for socket-level redirection.

Q5. What problem does TCX (Linux 6.6) solve compared with tc filter add ... bpf da?

Direct-action is from 4.4. TCX adds link-based ownership, BPF_F_BEFORE/AFTER ordering, revision checks and TCX_NEXT chaining, all without a qdisc.

Q6. An AF_XDP socket is bound to queue 0 of eth0, but no packets arrive even though the XDP program calls bpf_redirect_map(&xsks_map, ctx->rx_queue_index, 0). What is the most likely cause?

An XSK is bound to one (netdev, queue). RSS spreads flows across queues, so either bind a socket per queue or reduce queues (ethtool -L eth0 combined 1, as the tutorial suggests). The FILL ring must have frames for RX, not be empty.
