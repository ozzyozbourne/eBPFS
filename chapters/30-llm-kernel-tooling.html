Chapter 30

LLM agents for the kernel: schedcp, MCPtrace, GPTtrace

An LLM can write a bpftrace one-liner or a sched_ext scheduler. Letting it load that code into a running kernel is a different problem. You need an interface that tells the model what it may do, runs the privileged step for it, checks the result, and reports back. This chapter follows the eunomia-bpf projects that tried to build that interface, from a 2023 ChatGPT tracing script to a 2025 MCP server that tunes the Linux scheduler.

Prerequisites: 05 · program types and hooks (sched_ext), 08 · ecosystem (bpftrace), 17 · bpfixRepos: schedcp 730e2589, MCPtrace 1bd88555, GPTtrace a1f83c7b~50 min

Why this matters

eBPF has two properties that make it a good fit for machine-generated code. The verifier (chapter 03) rejects a program before it runs if it could crash the kernel. And many hooks can be attached and detached without rebooting, so trying a new policy is cheap. A sched_ext scheduler goes further: if it misbehaves, the kernel ejects it and moves every task back to the fair class (chapter 05). These properties are useful when the author of the code is a language model that is usually right but sometimes confidently wrong.

Writing the code is not the hard part. GPTtrace showed in 2023 that GPT-3.5 can produce a working bpftrace one-liner for "count page faults by process". The hard parts are around the code:

  • Context. Which probes exist on this kernel? Which schedulers are installed, and what do their flags mean? A model trained on old blog posts does not know.
  • Privilege. Loading BPF needs root (or CAP_BPF plus friends). Handing an agent a root shell is the naive answer, and an unsafe one.
  • Feedback. Did the program load? Did the workload get faster? The model needs measurements, not just exit codes.
  • Cost. The schedcp paper reports that an unaided Claude Code session needed 33 minutes, 221 API calls and about $6 to write one basic FIFO scheduler, and succeeded in only one of three attempts.

The org's projects answer these questions in different ways, and the answers changed as LLM tooling changed. GPTtrace (2023) hard-wires one model and one tool through OpenAI function calling. Kgent (eBPF '24) adds symbolic execution to check that the program does what the user asked. MCPtrace and schedcp (2025) move the model out of the tool: they are servers that any MCP-capable agent can call, and they own the privileged steps.

The Model Context Protocol in one section

MCPtrace and schedcp are both MCP servers, so we start with what MCP is. Anthropic announced the Model Context Protocol on 25 November 2024 as "an open standard for connecting AI assistants to the systems where data lives". The specification has dated revisions: 2024-11-05, 2025-03-26, 2025-06-18, 2025-11-25 and 2026-07-28 (the latest on the releases page). Both servers in this chapter negotiate the oldest one, 2024-11-05.

Roles

The spec names three roles, and it helps to keep them apart:

  • Host: the LLM application the user runs, for example Claude Code or Claude Desktop. It owns the conversation and the model.
  • Client: a connector inside the host, one per server.
  • Server: a program that offers capabilities. schedcp and MCPtrace are servers.

A server can offer three kinds of feature: tools ("functions for the AI model to execute"), resources (data for context) and prompts (templated messages). The client can offer sampling, roots and elicitation back to the server. The two kernel servers here use only tools. Nothing else is needed to let a model run a scheduler.

The wire format

MCP messages are JSON-RPC 2.0. The connection is stateful and starts with a handshake: the client sends initialize with its protocol version and capabilities, the server answers with its own, and the client sends a notifications/initialized notification. After that the client can discover tools and call them. These three messages are copied from the spec's Tools page (the weather tool is the spec's own example, not a kernel tool):

Three details from the spec matter for kernel tools.

  1. The description is the documentation. The model decides which tool to call from name, description and inputSchema alone. schedcp uses these strings as instructions ("Always use this tool to get the info of all schedulers first").
  2. Two kinds of error. A protocol error (unknown tool, bad arguments) is a JSON-RPC error. A tool that ran and failed returns a normal result with isError: true, so the model can read the message and try again. A compiler error from clang, or a verifier rejection, belongs in the second kind.
  3. stdio is strict. In the stdio transport the client launches the server as a subprocess, messages are newline-delimited, and "the server MUST NOT write anything to its stdout that is not a valid MCP message". Logging goes to stderr. MCPtrace's last commit, "Fix stdout logging breaking MCP protocol communication", fixed exactly this bug.
Tools are code execution

The spec says it plainly: "Tools represent arbitrary code execution and must be treated with appropriate caution", and hosts "must obtain explicit user consent before invoking any tool". An exec_program tool that runs any bpftrace script as root is root code execution with one extra step. MCP gives the host a place to ask the user. It does not make the tool safe.

Writing a server in Rust with rmcp

Both servers use rmcp 0.2.0, the official Rust SDK. A server is a struct. Each tool is an async fn marked #[tool(description = …)] that takes Parameters<T>, where T derives schemars::JsonSchema. The macro turns T into the tool's inputSchema, so the doc strings on the fields become the per-argument descriptions the model reads. Here are the request types for schedcp's list_schedulers and run_scheduler:

#[derive(Debug, Deserialize, schemars::JsonSchema)]
pub struct ListSchedulersRequest {
    #[schemars(description = "Filter by scheduler name (partial match). Should leave empty by default.")]
    pub name: Option<String>,
    #[schemars(description = "Filter by production readiness. Should leave empty by default.")]
    pub production_ready: Option<bool>,
}

#[derive(Debug, Deserialize, schemars::JsonSchema)]
pub struct RunSchedulerRequest {
    #[schemars(description = "Name of the scheduler to run, it should be one of the names returned by list_schedulers")]
    pub name: String,
    #[schemars(description = "Arguments to pass to the scheduler as a list of strings, as listed in the list_schedulers.")]
    #[serde(default)]
    pub args: Vec<String>,
}

schedcp: an MCP control plane for sched_ext

The problem: a semantic gap

Linux's default scheduler, EEVDF (which replaced CFS in 6.6), is one policy for every workload. sched_ext (merged in 6.12; see chapter 05) lets you replace it at run time with a BPF program, and the sched-ext/scx repository already ships many schedulers: scx_rusty for general servers, scx_lavd and scx_bpfland for interactive and gaming loads, scx_layered for explicitly configured layers, and so on. Each has a page of flags. The question "which of these, with which flags, for my workload?" needs two kinds of knowledge that rarely sit in one person: what the application does (a parallel build, a latency-sensitive server, a batch job with one straggler) and how each scheduler behaves.

The schedcp paper calls this the semantic gap between kernel policy and application needs. Its claim is that an LLM agent can close the gap, because it can read the application's code and the scheduler's documentation, if the system gives it a safe and cheap way to act. Earlier learned schedulers based on reinforcement learning map numeric state to a fixed set of actions. They cannot read a Makefile, and they cannot write new scheduling code.

Key idea

Keep the LLM out of the scheduling hot path. The agent works in the control plane: it reasons about the workload offline and produces a choice of scheduler, a set of flags, or a new .bpf.c file. The data plane is ordinary sched_ext BPF code making decisions in nanoseconds. The paper describes this as "zero LLM overhead in the critical path". The name SchedCP plays on "Context Protocol" (from MCP) and "Control Plane".

The paper

Towards Agentic OS: An LLM Agent Framework for Linux Schedulers, by Yusheng Zheng, Yanpeng Hu, Wei Zhang and Andi Quinn, is arXiv:2509.01245 (cs.AI, cross-listed cs.MA and cs.OS). v1 was posted on 1 September 2025 and v4 on 30 September 2025. arXiv lists the journal reference "MLforSystem 2025". The repository README links it as "SchedCP: Towards Agentic OS" and keeps a copy of v2 under document/2509.01245v2.pdf.

The paper has two parts:

  • SchedCP, the system interface, exposed over MCP and built from three services: a Workload Analysis Engine (tiered access to profiling data, from cheap summaries to perf, top and attachable eBPF probes, plus a feedback channel), a Scheduler Policy Repository (scheduler code with natural-language metadata and performance history, which the paper describes as a vector database), and an Execution Verifier (checks before deployment).
  • sched-agent, the AI side: four Claude Code subagents (Observation, Planning, Execution, Learning) arranged as an "in-context reinforcement learning" loop. The agent's context carries recent results, and no model weights are retrained.

What the code actually ships

The paper describes the design. The repository is a prototype of it, and its own document/AI_AGENTS.md says so: "Rather than having separate code files for each agent, the agent behaviors emerge from" the AI's reasoning, the MCP tools, the prompts that autotune provides, and the structured data in schedulers.json. It is worth knowing which parts of the design exist as code:

Design versus prototype

When you read the paper's safety story (the agent "doesn't need root access", rollback through a circuit breaker), remember that at this commit the agent's own host usually has a shell, and the server runs the scheduler under sudo with a password from an environment variable. The real safety net is sched_ext itself: the verifier at load, and the kernel's watchdog, which ejects a scheduler that stalls runnable tasks.

The tool descriptions are written as instructions for the model, and they shape its behaviour as much as the code does. Two examples, verbatim:

#[tool_router]

        &self,
        Parameters(request): Parameters<ListSchedulersRequest>,
    ) -> Result<CallToolResult, McpError> {
        /* ... */
        let result = self.inner.list_schedulers_impl(request).await?;
        Ok(CallToolResult::success(vec![Content::text(result)]))
    }

    #[tool(description = "Run a sched-ext scheduler. After you list_schedulers, you can use this tool to run a scheduler from the list. Run a new scheduler will stop any running scheduler first.")]
    async fn run_scheduler(
        &self,
        Parameters(request): Parameters<RunSchedulerRequest>,
    ) -> Result<CallToolResult, McpError> {
        /* ... */
        // Stop any currently running schedulers first
        {
            let manager = self.inner.scheduler_manager.lock().await;
            let stopped = manager.stop_running_schedulers().await;
            /* ... */
        }
        // Wait a bit to ensure clean shutdown
        sleep(Duration::from_millis(500)).await;
        let result = self.inner.run_scheduler_impl(request).await?;
        Ok(CallToolResult::success(vec![Content::text(result)]))
    }
    /* ... */
    #[tool(description = "Start or stop system monitoring to collect CPU, memory, and scheduler metrics. Use command 'start' to begin monitoring, 'stop' to end and receive a summary. Monitoring collects metrics every second including CPU utilization, memory usage, and scheduler statistics. Note: **You only use the tool if you find there is no other metrics you can measure.     async fn system_monitor(/* ... */) -> Result<CallToolResult, McpError> { /* ... */ }
}

Note the last description. It tells the model to prefer the workload's own metric (build time, the benchmark's printed latency) over generic CPU counters. This is the paper's "adaptive context provisioning" turned into a prompt: start cheap and specific, and fetch more only when needed.

Generating a scheduler: create_and_verify_scheduler

When no existing scheduler fits, the agent writes one. The tool takes the source as a string. scheduler_generator.rs writes it to <name>.bpf.c, compiles it with fixed flags, and test-runs it. The compile step:

fn compile_bpf_scheduler(&self, bpf_source: impl AsRef<Path>) -> Result<PathBuf> {
    /* ... validate the file exists and ends in .bpf.c ... */
    let output_name = file_name.replace(".bpf.c", ".bpf.o");
    let output_path = self.work_dir.join(&output_name);

    // Build include paths
    let scx_includes = self.build_scx_includes()?;
    let sys_includes = Self::build_sys_includes();

    // Build BPF compilation flags
    let mut clang_args = vec![
        "-g".to_string(),
        "-O2".to_string(),
        "-Wall".to_string(),
        "-Wno-compare-distinct-pointer-types".to_string(),
        "-D__TARGET_ARCH_x86".to_string(),
        "-mcpu=v3".to_string(),
        "-mlittle-endian".to_string(),
        "-target".to_string(),
        "bpf".to_string(),
        "-c".to_string(),
    ];
    /* ... add includes, input, -o output ... */
    let output = Command::new("clang")
        .args(&clang_args)
        .current_dir(&self.work_dir)
        .output()

        let stderr = String::from_utf8_lossy(&output.stderr);
        anyhow::bail!(
            "BPF compilation failed:\n{}",

    }
    /* ... */

Then the "execution verify" step runs a generic struct_ops loader under sudo, lets the scheduler run, kills it, and inspects stderr. Loading the object is what makes the kernel verifier check it:

async fn execution_verify(
    &self,
    bpf_object: impl AsRef<Path>,
    duration: Option<Duration>,
) -> Result<String> {
    let bpf_object = bpf_object.as_ref();
    let duration = duration.unwrap_or(Duration::from_secs(10));
    /* ... */
    let loader_path = self.get_loader_path()?;
    /* ... */
    // Start the scheduler process with sudo
    let cmd_args = vec![
        loader_path.to_string_lossy().to_string(),
        bpf_object.to_string_lossy().to_string(),
    ];
    let mut child = self.spawn_with_sudo(cmd_args).await?;
    /* ... */
    tokio::time::sleep(duration).await;

    // Kill the child process
    child.start_kill().context("Failed to kill scheduler process")?;

    // Wait for process to finish with timeout
    let output = timeout(Duration::from_secs(5), child.wait_with_output())
        .await
        .context("Timeout waiting for scheduler to stop")?
        .context("Failed to get scheduler output")?;
    /* ... */
    // Check if execution was successful
    // Note: Schedulers often exit with non-zero when killed, so we check stderr for errors
    if stderr.contains("error") || stderr.contains("Error") || stderr.contains("failed") {
        anyhow::bail!(
            "Scheduler execution failed:\nStdout: {}\nStderr: {}",
            stdout,
            stderr
        );
    }
    /* ... "Scheduler verification successful!" ... */
}

This is a smoke test, and it is honest about it. It shows that the program compiles, passes the verifier, attaches, and survives 10 seconds of real scheduling on this machine without the loader printing an error. It does not show that the scheduler is fair, avoids starvation under other loads, or beats EEVDF. Those are exactly the properties the paper's second-layer static checker and dynamic benchmark were meant to cover. A compile or verifier failure comes back to the agent as an McpError::invalid_params whose message contains clang's or the loader's stderr. Strictly, that is a JSON-RPC protocol error, not the isError: true result the spec recommends for execution failures, but the text still reaches the agent, which reads it and retries. The same loop is what bpfix improves by replacing the raw verifier log with a better diagnostic.

What a generated scheduler looks like

The paper's batch experiment ran 8 workloads, each 40 parallel tasks: 39 short ones and one long one. The agent recognised the pattern and wrote a "Longest Job First" policy. The generated schedulers are checked in under workloads/processing/schedulers/. They all follow the template in mcp/new_sched/example.bpf.c: two custom DSQs, with the "long" queue always dispatched first. Here is the one for the compression workload:

/* Detect if task is large compression by checking filename */
static bool is_large_compression(struct task_struct *p)
{
	pid_t pid = p->pid;
	struct filename_info *info;

	/* Get filename info for this PID */
	info = bpf_map_lookup_elem(&pid_to_filename, &pid);
	if (!info)
		return false;

	/* Check for ./large_compression.py */
	int is_large = (info->filename[0] == '.' && info->filename[1] == '/' &&
			info->filename[2] == 'l' && info->filename[3] == 'a' &&
			info->filename[4] == 'r' && info->filename[5] == 'g' &&
			info->filename[6] == 'e' && info->filename[7] == '_' &&
			info->filename[8] == 'c' && info->filename[9] == 'o' &&
			info->filename[10] == 'm' && info->filename[11] == 'p');
	return is_large;
}
/* ... is_small_compression() is the same for ./small_compression.py ... */

#define LARGE_DSQ  0    /* High priority DSQ for large compression */
#define SMALL_DSQ 1    /* Lower priority DSQ for small compression */

/* Time slice configurations */
#define SMALL_SLICE_NS  3000000ULL   /* 3ms for small compression tasks */
#define LARGE_SLICE_NS  15000000ULL  /* 15ms for large compression task */
#define DEFAULT_SLICE_NS 5000000ULL  /* 5ms for other tasks */
/* ... select_cpu: scx_bpf_select_cpu_dfl(), insert into SCX_DSQ_LOCAL if idle ... */

void BPF_STRUCT_OPS(compression_enqueue, struct task_struct *p, u64 enq_flags)
{
	/* Enqueue based on task type */
	if (is_large_compression(p)) {
		scx_bpf_dsq_insert(p, LARGE_DSQ, LARGE_SLICE_NS, enq_flags);
	} else if (is_small_compression(p)) {
		scx_bpf_dsq_insert(p, SMALL_DSQ, SMALL_SLICE_NS, enq_flags);
	} else {
		/* Other tasks go to global DSQ */
		scx_bpf_dsq_insert(p, SCX_DSQ_GLOBAL, DEFAULT_SLICE_NS, enq_flags);
	}
}

void BPF_STRUCT_OPS(compression_dispatch, s32 cpu, struct task_struct *prev)
{
	/* Priority dispatch: always try large compression first */
	if (!scx_bpf_dsq_move_to_local(LARGE_DSQ)) {
		/* If no large tasks, dispatch small compression tasks */
		if (!scx_bpf_dsq_move_to_local(SMALL_DSQ)) {
			/* Finally, dispatch other tasks */
			scx_bpf_dsq_move_to_local(SCX_DSQ_GLOBAL);
		}
	}
}
/* ... init: scx_bpf_create_dsq(LARGE_DSQ, -1), scx_bpf_create_dsq(SMALL_DSQ, -1); SCX_OPS_DEFINE ... */

How does the scheduler know a task's file name? task_struct->comm for a Python script is just python3. The helper header supplied to the agent adds a tracepoint program that records each process's exec file name in a hash map, which the scheduler then looks up. This is a good example of a non-scheduler BPF program feeding a scheduler through a map:

/* BPF hash map: PID -> filename */
struct {
	__uint(type, BPF_MAP_TYPE_HASH);
	__uint(max_entries, MAX_PID_ENTRIES);
	__type(key, pid_t);
	__type(value, struct filename_info);
} pid_to_filename SEC(".maps");

/* Tracepoint: capture filename when process exec's */
SEC("tp/sched/sched_process_exec")
int pid_filename_handle_exec(struct trace_event_raw_sched_process_exec *ctx)
{
	struct filename_info info = {};
	unsigned fname_off;
	pid_t pid;

	/* Get PID of the process */
	pid = bpf_get_current_pid_tgid() >> 32;

	/* Extract filename offset from the tracepoint data */
	fname_off = ctx->__data_loc_filename & 0xFFFF;

	/* Read the filename from the tracepoint context */
	bpf_probe_read_str(&info.filename, sizeof(info.filename), (void *)ctx + fname_off);

	/* Store PID->filename mapping */
	bpf_map_update_elem(&pid_to_filename, &pid, &info, BPF_ANY);
	return 0;
}
/* ... sched_process_exit deletes the entry ... */

Look at what the model was told to do. The generation prompt in workloads/processing/scripts/prompt.md says: "you are a experienced eBPF developer who already know what application you are going to run … you just need to make exact match for the processes name … For python program, you should use the filename to check the application, not the comm name." So the agent's job in this experiment was workload-specific policy with known process names, not a general-purpose scheduler. The character-by-character comparison is what such code tends to look like when the author wants the verifier to accept it without loops. Also notice that these schedulers have no starvation guard: a stream of "large" tasks would starve the small queue and the global queue. For 40 tasks that run to completion this is fine. On a general machine the sched_ext watchdog would eventually step in.

Read generated code critically

The template mcp/new_sched/example.bpf.c, which the agent is told to imitate, defines SHORT_SLICE_NS 30000000ULL /* 3ms for short tasks */. 30,000,000 ns is 30 ms, not 3 ms. Generated code inherits mistakes in its examples, and a 10-second smoke test will not catch a wrong constant.

Walkthrough: an agent tuning the scheduler for a kernel build

The steps below combine the autotune prompt, the tool implementations, and the kernel-compilation example in §5.2 of the paper. The numbers in steps 6 and 8 are the paper's reported results on its 172-thread machine, not something we ran.

1. The user starts autotune

autotune cc "make -C workloads/linux-build-bench/linux -j". autotune collects system facts (CPU model, cores and threads, memory, OS, kernel version, architecture) and starts Claude Code with the prompt above. Claude Code launches mcp/target/release/schedcp over stdio, sends initialize, then tools/list, and the model now sees seven tools.

2. Observe the workload

The model reads the Makefile and the source tree with its own file tools, and runs the build once under the default scheduler (EEVDF) to get a baseline time. It concludes, in the paper's words, that this is a "CPU-intensive parallel compilation task with short-lived processes, inter-process dependencies, and a goal to minimize makespan".

3. Record a profile

tools/call workload {"command":"create","description":"…"} returns a UUID. The profile is free text, stored in schedcp_workloads.json, so a later session can find it with workload list.

4. Read the catalog

list_schedulers returns the 20 JSON entries. The model matches its profile against descriptions and use cases ("throughput", "server_workloads") and shortlists at most three, as the prompt says.

5. Try a candidate

run_scheduler {"name":"scx_rusty","args":[…]}. The server stops any running scheduler, waits 500 ms, starts sudo scx_rusty … as a tracked process, and returns an execution_id. From now on, sched_ext tasks are scheduled by BPF code, not by the model.

6. Measure and record

The model reruns the exact build command and reads the wall-clock time. It calls get_execution_status to check that the scheduler is still alive and workload add_history to store the scheduler, its args and the result. In the paper, scx_rusty as the first attempt cut the build from 13.57 s to 8.31 s (1.63×).

7. Iterate

stop_scheduler, then the next candidate or a new flag set. Each iteration is one more tool call and one more build, which is cheap compared with writing code. If nothing fits, the model writes a .bpf.c and calls create_and_verify_scheduler, reading clang or verifier errors from the result until it passes.

8. Pick the winner and leave it running

The model summarises the history and chooses the best result. In the paper, after three iterations the agent moved to scx_layered, gaining 16% more for a total of 1.79× over EEVDF (7.60 s). Stopping the scheduler, or Ctrl-C, returns the machine to EEVDF.

MCPtrace: bpftrace as four MCP tools

MCPtrace is the tracing counterpart to schedcp, and it is much smaller: one 552-line src/main.rs. Its README describes it as "a minimal MCP (Model Context Protocol) server that provides AI assistants with access to bpftrace kernel tracing capabilities". It is published on crates.io as bpftrace-mcp-server (version 0.1.1, first published 2025-08-01). A Python version built on FastMCP (server.py) is still in the tree as the legacy implementation.

The design choice to notice: MCPtrace does not generate bpftrace. GPTtrace called a model itself. MCPtrace has no model and no API key. The host's model writes the bpftrace script, and the server only gives it the context it needs (which probes exist, what this kernel's bpftrace supports) and a controlled way to run the script. Generation moved from the tool into the agent.

The tools

Execution is asynchronous because tracing is: a useful trace often runs for seconds, and an MCP call should not block that long. exec_program starts a task, waits half a second to catch syntax errors, and returns an ID. The model polls get_result, and that is how it pages through a large histogram without filling its context window.

#[tool(description = "Execute a bpftrace program with buffered output")]
async fn exec_program(
    &self,
    Parameters(ExecProgramRequest { program, timeout }): Parameters<ExecProgramRequest>,
) -> Result<CallToolResult, McpError> {
    // Validate timeout
    let timeout = timeout.clamp(1, 60);

    // Generate execution ID
    let execution_id = format!("exec_{}", Uuid::new_v4().to_string()[..8].to_string());

    // Create buffer
    let buffer = ExecutionBuffer::new(10000);
    self.execution_buffers
        .insert(execution_id.clone(), buffer.clone());

    // Start execution in background
    let password = self.sudo_password.to_string();
    let exec_id = execution_id.clone();
    tokio::spawn(async move {
        BpftraceServer::run_bpftrace_program(
            exec_id,
            program,
            Duration::from_secs(timeout),
            password,
            buffer,
        )
        .await;
    });

    // Give it a moment to check for syntax errors
    sleep(Duration::from_millis(500)).await;

    // Check if it failed immediately (syntax error)
    if let Some(buffer) = self.execution_buffers.get(&execution_id) {
        let status = buffer.status.lock().await.clone();
        if status == "failed" {
            /* ... */
            return Err(McpError::internal_error(
                "Failed to start bpftrace program", 
                Some(json!({"error": error_msg})),
            ));
        }
    }

    Ok(CallToolResult::success(vec![Content::text(
        json!({
            "execution_id": execution_id,
            "status": "started",
            "message": format!("Program execution started with timeout of {}s", timeout)
        }).to_string()
    )]))
}

The runner pipes the sudo password to sudo -S on stdin, then reads stdout and stderr line by line in a tokio::select! loop that checks the deadline every 100 ms. stderr lines are kept but prefixed, so the model sees bpftrace's own error messages in the result:

let mut cmd = Command::new("sudo");
cmd.arg("-S")
    .arg("bpftrace")
    .arg("-e")
    .arg(&program)
    .stdin(Stdio::piped())
    .stdout(Stdio::piped())
    .stderr(Stdio::piped());
/* ... spawn, write password to stdin ... */
loop {
    tokio::select! {
        _ = sleep(Duration::from_millis(100)) => {
            if start_time.elapsed() > timeout {
                let _ = child.kill().await;
                buffer.add_line("[Execution timed out]".to_string()).await;
                buffer.mark_failed("Timeout".to_string()).await;
                break;
            }
        }
        line = stdout_reader.next_line() => {
            /* ... push line into the buffer, or break on EOF ... */
        }
        line = stderr_reader.next_line() => {
            match line {
                Ok(Some(line)) => {
                    if !line.starts_with("[sudo] password") {
                        buffer.add_line(format!("[Error] {}", line)).await;
                    }
                }
                Ok(None) => {}
                Err(_) => {}
            }
        }
    }
}

A background task removes buffers older than one hour, checking every five minutes. Nothing is persisted.

Security model

The README is direct: "No script validation - trust the AI client to generate safe scripts". It also says "AI never gets root access", which is true only in the narrow sense that the model does not hold the password. The model can still run any bpftrace program as root for up to 60 seconds, including ones that read kernel memory or, with --unsafe builtins such as system(), run commands. bpftrace's own safety (the verifier) prevents crashes, not data exposure. Treat the host's tool-approval prompt as the real gate, and read each script before you approve it.

Two details at 1bd88555. The src/tools/ directory ships 39 classic bpftrace tools (opensnoop.bt, biolatency.bt, …) and an examples.json, but main.rs does not expose them as a tool or resource. The README's "curated collection of production-ready bpftrace scripts" therefore reaches the model only if it reads the files some other way. And doc/COMPARISON_WITH_GPTTRACE.md lays out the differences from GPTtrace that the next section explains.

GPTtrace: the 2023 prompt pipeline

GPTtrace is the oldest project here and the most-starred (275). It predates MCP and agentic coding tools: the model is called directly through the OpenAI Python SDK, and the "tool use" is OpenAI function calling, introduced in mid-2023 with the gpt-3.5-turbo-0613 model that GPTtrace still names in its code. It is on PyPI as gpttrace (latest 0.1.2). The README now opens by redirecting readers to MCPtrace.

Step by step through the code

Retrieve examples. examples.py loads the bpftrace example corpus from tools/examples.json, embeds it with OpenAI embeddings into a FAISS index cached in data_save/, and returns the two most similar entries for the user's request:

def get_bpftrace_basic_examples(query: str) -> str:
    """Get basic bpftrace examples from vector database."""
    loader = JSONLoader(
        file_path='./tools/examples.json',
        jq_schema='.data[].content',
        json_lines=True
    )
    documents = loader.load()
    embeddings = OpenAIEmbeddings()

    # Check if the vector database files exist
    if not (os.path.exists("./data_save/vector_db.faiss") and
            os.path.exists("./data_save/vector_db.pkl")):
        db = FAISS.from_documents(documents, embeddings)
        db.save_local("./data_save", index_name="vector_db")
    else:
        # Load an existing FAISS vector store
        db = FAISS.load_local(
            "./data_save",
            index_name="vector_db",
            embeddings=embeddings,
            allow_dangerous_deserialization=True,
        )

    results = db.search(query, search_type='similarity')
    results = [result.page_content for result in results]
    return "\n".join(results[:2])

Run, retry, explain. run_bpftrace() sends the prompt with function_call="auto", builds ["sudo", "bpftrace", …] from the returned arguments, and runs it with a timer (default 300 s) after asking the user to type y. execute() is the loop. Any stderr output counts as failure and triggers a retry with the error appended, up to five times:

def execute(user_input: str, verbose: bool = False, retry: int = 5,
            previous_prompt: Optional[str] = None,
            output: Optional[str] = None) -> None:
    """
    Convert the user request into a BPF command and execute it.
    # ...
    """
    if retry == 0:
        print("Retry times exceeded...")
        return
    # ...
    if previous_prompt is None:
        prompt = construct_running_prompt(user_input)
    else:
        prompt = construct_prompt_on_error(
            previous_prompt, user_input, output)
    # ...
    res = run_bpftrace(prompt, verbose)
    if res["stderr"] != '':
        print("output: " + json.dumps(res))
        print("retry time " + str(retry) + "...")
        # retry
        execute(user_input, verbose, retry - 1, prompt, json.dumps(res))
        return

    # success
    print("AI explanation:")
    prompt = construct_prompt_for_explain(user_input, res["stdout"])
    # ...
    explain = call_gpt_api(prompt)
    print(explain)

Notice how the retry prompt grows: each attempt embeds the previous prompt, so five failures stack five copies of the examples and errors. A "warning" on stderr also counts as failure. KEN / Kgent and GPTtrace-web

KEN, published as Kgent

The research version of GPTtrace's idea appeared first as KEN: Kernel Extensions using Natural Language (arXiv:2312.05531, 9 December 2023) and then as Kgent: Kernel Extensions Large Language Model Agent in the Proceedings of the ACM SIGCOMM 2024 Workshop on eBPF and Kernel Extensions (eBPF '24, Sydney), pages 30–36, doi:10.1145/3672197.3673434. Authors: Yusheng Zheng, Yiwei Yang, Maolin Chen, Andrew Quinn.

Kgent asks a harder question than "does it load?": is the synthesised program the program the user asked for? Its abstract describes a combination of "LLM-empowered program comprehension, symbolic execution, and a series of feedback loops". The arXiv (KEN) version spells out four components:

  1. A Prompter wraps the user's request, asks for a bpftrace program, and appends every error message collected so far for this task.
  2. A Synthesis Engine retrieves similar prompt/program pairs from a vector database (few-shot in-context learning, as in GPTtrace) and asks the LLM for a candidate.
  3. A Comprehension Engine asks an LLM to annotate the candidate with Hoare-logic pre- and post-conditions (assume/assert) for every kernel function it touches. It starts from an automatically generated dataset of Z3 contracts for kernel functions.
  4. A Symbolic Verifier (SeaHorn over LLVM IR, Z3 as the solver) checks the annotated program. The authors added 51 lines to the bpftrace compiler for assume/assert. Only a program that passes goes on to the kernel's eBPF verifier.

Both a failed assertion (or a timeout) and a verifier rejection go back to the Prompter. After 3 failed trials (the default) KEN asks the user for more detail. The arXiv version's corpus, eBPFNLDataset, has 145 prompt/program pairs (79 bpftrace, 66 libbpf). On its 40-case test set KEN reached 80% accuracy against 30% for a ChatGPT-4 baseline (hence 2.67×), with a 2.5% false-positive rate for both. A false positive is a program that passes KEN's checks but that manual inspection shows to be wrong for the prompt. The ablation is instructive: adding feedback alone took the baseline to 60%, and adding comprehension plus symbolic execution took it to 77.5%. The published Kgent abstract repeats the 80% and 2.67× figures. The repository's dataset/spec/helper_spec.json and kprobe_spec.json are the Z3 specifications.

The KEN repository (last commit 2024-08-07) states that it is "only for evaluation scripts and code for the paper" and points users to GPTtrace. It contains the libbpf and bpftrace example databases with descriptions (dataset/libbpf/output.json, dataset/bpftrace/output.json), the Z3 specs, and evaluation/. Chapter 17 discusses Kgent's use of raw verifier messages as feedback, the signal that bpfix tries to improve.

GPTtrace-web

GPTtrace-web (last commit 2024-08-07) calls itself "GPT2Bpftrace". It is a small web app: type a sentence on the left, get a bpftrace program on the right, copy it, and run sudo bpftrace gpt-bpftrace.bt yourself. Local use is npm install and npm run dev. The README links a hosted demo at gpt-2-bpftrace.vercel.app (not checked for liveness) and gives a clone URL under the older name eunomia-bpf/GPT2Bpftrace. Its safety model is the simplest of all: the human is the executor, so the human decides what runs.

The table shows two shifts. The first is who owns the model. In 2023 each tool shipped its own prompt pipeline and API key. By 2025 the agent is a general coding agent, and the tool's job is to provide context and actions over a standard protocol. The second is what counts as success. GPTtrace stops when stderr is empty. Kgent checks semantics. schedcp checks a measured performance number. Each is a step closer to asking whether the result is what the user wanted, not just whether it loaded.

Benefits and limitations

Benefits

  • The LLM stays out of the hot path. sched_ext and bpftrace run native BPF. The model costs money and seconds only at decision time.
  • eBPF is a forgiving target. The verifier rejects unsafe code, and sched_ext reverts to the fair class on error or stall. Mistakes cost a retry, not a reboot.
  • Narrow tools beat a root shell. Seven typed tools are easier to audit and to approve than arbitrary shell access, and the descriptions steer the model.
  • Agent-agnostic. Any MCP host can drive both servers. The interface does not need to change when models improve.
  • Reported gains are real when the loop measures. The 1.79× and 2.11× results come from trying candidates and keeping the best, not from a single guess.

Limitations

  • Prototype gap. The paper's micro-VM, scheduler-specific static analysis, deployment tokens and circuit breaker are not in schedcp's code at 730e2589.
  • Passwords in environment variables. Both servers pipe a sudo password to sudo -S. A scoped NOPASSWD rule or a capability-limited helper would be safer.
  • The verifier proves safety, not intent. A scheduler can starve tasks and a trace can leak data while passing the verifier. Only Kgent checks semantics, and only for tracing programs.
  • Weak checks after load. schedcp's verify step greps stderr for "error". MCPtrace does not validate scripts at all.
  • Small evaluations. Three runs per case on two machines. A Claude Opus model was needed for the batch classification. Nothing in this chapter was reproduced here.
  • Maintenance. Low commit activity since early 2026. sched_ext kfunc names and the MCP spec have both moved since these servers were written; they still negotiate 2024-11-05.

Outside the org

  • Learned schedulers. RL-based job schedulers such as Decima (Mao et al., SIGCOMM 2019) learn policies from numeric state. The schedcp paper positions itself against this line: an LLM can read code and synthesise new policy, while RL maps state to predefined actions and needs retraining per workload. LWN covered a machine-learning load balancer for Linux in "Improved load balancing with machine learning" (2025), which is the pre-trained RL baseline the paper compared against.
  • sched_ext schedulers. The scx repository is both schedcp's policy repository and its competition: hand-written schedulers such as scx_rusty and scx_layered produced the best results in the paper's experiments. The agent chose and configured them; it did not write them.
  • MCP servers in general. The modelcontextprotocol/servers repository collects reference servers. The kernel servers here follow the same pattern with unusually dangerous tools.

Check your understanding

Q1. In MCP terms, what is schedcp?

The host (Claude Code) launches mcp/target/release/schedcp from .mcp.json as a stdio subprocess. schedcp advertises only the tools capability. The schedulers it starts are separate processes.

Q2. Why did MCPtrace's last commit disable logging unless RUST_LOG is set?

The spec says the server "MUST NOT write anything to its stdout that is not a valid MCP message". A stray log line corrupts the newline-delimited JSON-RPC stream. Logs belong on stderr, or nowhere.

Q3. What does schedcp's create_and_verify_scheduler actually check at commit 730e2589?

The first option is the paper's design. The code compiles, starts the generic loader under sudo, sleeps 10 seconds, kills it, and greps stderr. Performance is measured separately by the agent rerunning the workload.

Q4. In the paper's schbench experiment, what happened on the agent's first attempt?

The first configuration was 13% worse on P99 latency and 19% lower in throughput. After three observe-and-optimise iterations, scx_rusty reached 2.11× better P99 latency and 1.60× throughput. This is why the measurement loop matters.

Q5. What does Kgent add over GPTtrace's "retry until stderr is empty" loop?

The Comprehension Engine annotates kernel-function pre- and post-conditions, and SeaHorn/Z3 check them. This targets semantic correctness ("does it do what was asked?"), which neither the verifier nor an empty stderr can show. Accuracy rose from 30% (ChatGPT-4) to 80%.

Q6. MCPtrace's README says "AI never gets root access". What is the most accurate reading?

The server runs sudo -S bpftrace -e <program> with the model's program and, per its README, does "No script validation". The host's per-call approval is the real control.
