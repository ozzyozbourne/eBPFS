Chapter 13

bpf-compatible: CO-RE on kernels without BTF

CO-RE lets one compiled eBPF object run on many kernels, but only if the kernel can describe its own types through /sys/kernel/btf/vmlinux. Millions of machines run CentOS 8.1, Debian 10 or Ubuntu 20.04 kernels that cannot. How do you ship one binary that still runs there, without a compiler on the target and without carrying gigabytes of type data?

Prerequisites: 06, 10Repo: eunomia-bpf/bpf-compatible @ 4ed5e65~40 min

Why this matters

Chapter 06 explained CO-RE. When you compile an eBPF program, clang writes relocation records into the object's .BTF.ext section. Each record says, in effect, "this instruction reads field real_parent of struct task_struct". When the program is loaded, libbpf finds the same field in the running kernel's BTF and patches the instruction with the correct offset. Two inputs are needed: the program's own BTF, which the compiler always provides, and the kernel's BTF, which the kernel provides only if it was built with CONFIG_DEBUG_INFO_BTF=y.

Mainstream distributions turned that option on gradually. The BTFHub table of supported distributions shows, for example, that CentOS 8.0 and 8.1 (kernels 4.18.0-80 and 4.18.0-147) have neither BPF-ready settings nor BTF. From 8.2 on they have both. CentOS 7 kernels never have BTF. On those machines libbpf prints kernel BTF is missing at '/sys/kernel/btf/vmlinux', was CONFIG_DEBUG_INFO_BTF enabled?, and any object with CO-RE relocations fails to load. The relocation mechanism is in libbpf, in user space, so it works on those kernels. Only the type data is missing.

There are three ways to deal with this:

  1. Compile on the target. This is BCC's model. It ships C source and builds it with an embedded LLVM against the target's kernel headers at startup.
  2. Download the kernel's BTF at run time from a store such as BTFHub. That needs network access at startup and a few megabytes per kernel.
  3. Ship the BTF with the program, trimmed down to the handful of types and fields the program actually uses. This is what bpftool gen min_core_btf (BTFgen) makes possible, and it is what eunomia-bpf/bpf-compatible packages into a toolchain.
Key idea

A CO-RE program only touches a few kernel types. Strip every kernel's multi-megabyte BTF down to just those types and fields, and each file shrinks to a few hundred bytes. Compressed, the files for 85 kernels fit in about 2 KB (measured below). That is small enough to link into the executable. At startup the program reads /etc/os-release and uname, extracts the matching file, and gives its path to libbpf through bpf_object_open_opts.btf_custom_path.

bpf-compatible is small: 44 files, a ~110-line shell script, two little Rust crates, and a C header. It is worth a chapter because it shows the whole "portable eBPF on old kernels" pipeline from end to end. It is also the code behind ecc --btfgen and ecli's .tar packages (chapter 10).

What bpf-compatible is

The README describes it as "a set of toolchain to simplify the building and running eBPF program on kernels without native BTF support", built on BTFHub's archive. It has three parts:

script/btfgen

A bash script. fetch clones one or more btfhub-archive repositories into a cache. btfgen extracts each kernel's BTF, trims it against your .bpf.o files with bpftool, and packs the results into a .tar.gz.

bpf-compatible-rs

A Rust crate (crates.io 0.1.3). It builds the archive path for the running system from os-release and uname, and unpacks tar packages. ecli and bpf-loader-rs use it.

bpf-compatible-sys + btf_helpers.h

A Rust static library with a C ABI (libbpf_compatible.a) plus a header. It finds the right BTF inside a tar.gz embedded in the executable and sets btf_custom_path. It is a drop-in replacement for BCC libbpf-tools' ensure_core_btf().

example/

A copy of libbpf-bootstrap adapted to the toolchain, with two apps, bootstrap (ring buffer) and execsnoop (perf buffer). Their Makefile wires all the steps together.

In short, it works, it is maintained, and it is feature-frozen. None of these has been built. Read the repo as a compact reference implementation, not as a growing framework.

The problem in numbers

The figures in this section were measured in the orb used to write this chapter: Debian 12, kernel 6.1.189+ x86_64, clang 14.0.6, bpftool v7.1.0 linked with libbpf 1.1. The exact steps are in the hands-on section below.

Shipping full BTF for 85 kernels would mean 538 MB in the binary, or 94 MB compressed with xz. Trimmed, the same coverage costs about 2 KB. BTFHub's own write-up gives a similar figure for a much larger program: "a complex bpf object might support nearly 400 kernels by having BTF files summing only 1.5 MB". The repo's design document estimates about 10 MB for "hundreds of distributions". That is a projection, not a measurement.

How it works: the build-time pipeline

The build has four stages. Two of them are ordinary libbpf-bootstrap (compile, skeleton). The other two are new: trim-and-pack, and embed.

Stage 1: fetching the archive

BTFHub (Aqua Security) takes the debug-info packages that distributions publish for each kernel build, runs pahole on them to produce BTF, and stores the results in a separate repository, btfhub-archive. Files are laid out by os-release ID, version, architecture and kernel release, for example ubuntu/20.04/x86_64/5.4.0-26-generic.btf.tar.xz. The top-level directories are amzn, centos, debian, fedora, ol, rhel, sles and ubuntu. Some names, such as focal and buster, are symlinks to the numbered versions.

The fetch action of script/btfgen mirrors one or more such repositories into a local cache:

BTFHUB_CACHE_DIR="${BTFHUB_CACHE:-$HOME/.cache/eunomia/btfhub}"
BTFHUB_REPO_URL="${BTFHUB_REPO:-https://github.com/aquasecurity/btfhub-archive}"
/* ... */
fetch() {
  if [ -d "$BTFHUB_CACHE_DIR" ]; then
    echo "BTFHUB_CACHE_DIR does exist, skip fetch"
    return
  fi

  if ! command -v git &> /dev/null; then echo "Error: git is not installed."; exit 1; fi
  if ! command -v rsync &> /dev/null; then echo "Error: rsync is not installed."; exit 1; fi
  
  local repos repo repo_dir
  IFS=',' read -r -a repos <<< "$BTFHUB_REPO_URL"
  for repo in "${repos[@]}"; do
    repo_dir="$BTFHUB_CACHE_DIR/btfhub-archive-repos/${repo//[^A-Za-z0-9._-]/_}/"
    mkdir -p "$repo_dir"
    git clone --depth 1 "$repo" "$repo_dir"
    rsync -av --quiet --ignore-existing \
      --exclude 'LICENSE' \
      --exclude 'README.md' \
      --exclude '.gitignore' \
      --exclude '.git' \
      "$repo_dir" "$BTFHUB_CACHE_DIR/btfhub-archive/"
  done
}

Three details matter in practice:

  • The environment variables the script actually reads are BTFHUB_CACHE and BTFHUB_REPO. The README mentions BTFHUB_REPO_URL and BTFHUB_CACHE_DIR, but those are only the internal names. The script's --help text and the example Makefile use the right ones.
  • BTFHUB_REPO can be a comma-separated list. rsync --ignore-existing merges the repositories, and the first one listed wins when two contain the same path. You can therefore put your own archive of in-house kernels in front of the public one.
  • If the cache directory already exists, fetch does nothing. Nothing is updated. To pick up new kernels, delete the cache.

The full archive holds 6.69 GB of compressed files, so the example Makefile points at a small demo fork, eunomia-bpf/btfhub-archive. It holds 85 x86_64 kernels from CentOS 8, Debian 10 and Ubuntu 20.04 and was last pushed in May 2023.

Stage 3: trimming with bpftool gen min_core_btf

The btfgen action is where the work happens. After parsing its options, it runs three pipelines:

btfgen() {
  fetch
  if ! command -v bpftool &> /dev/null; then echo "Error: bpftool is not installed."; exit 1; fi
  short_args="j:f:o:"
	long_args="json:,file:,output:"
	/* ... getopt parsing: -j/--json, -o/--output, -f/--file, remaining args are BPF objects ... */

  if [ -z "$output" ]; then output="output.tar"; fi
 
  dir=$(pwd)

  find $BTFHUB_CACHE_DIR -name "*.tar.xz" -not -path "$BTFHUB_CACHE_DIR/btfhub-archive-repos/*" | \
  xargs -P 8 -I fileName sh -c 'tar xfJ "fileName" -C "$(dirname "fileName")"'
  find $BTFHUB_CACHE_DIR -name "*.btf" -not -path "$BTFHUB_CACHE_DIR/btfhub-archive-repos/*" | \
  xargs -P 8 -I fileName sh -c 'bpftool gen min_core_btf "fileName" "fileName" "$@"' _ "${files[@]}"

  if [ -n "$json" ]; then cp $json $BTFHUB_CACHE_DIR; fi

  cd $BTFHUB_CACHE_DIR && tar \
    --exclude="./btfhub-archive-repos" \
    --exclude="*.xz" \
    -czf $dir/$output .
}

Each .btf.tar.xz is extracted next to itself. Each full .btf is then trimmed in place: input and output are the same file. Finally the cache directory is tarred with gzip, leaving out the .xz originals and the mirrored repos. The trimming is not destructive across builds, because the next run extracts every .tar.xz again and overwrites the trimmed file with the full one before trimming. The output is always gzip, even with the default name output.tar. The README therefore uses -o min_core_btfs.tar.gz.

Trimming is done by bpftool, not by bpf-compatible. The subcommand came from Kinvolk's BTFGen prototype, built with Aqua Security and Elastic, and was merged into bpftool in 2022 (patch series "bpftool: Implement btfgen"). Its algorithm is described in a comment in bpftool's gen.c:

/* Create minimized BTF file for a set of BPF objects.
 *
 * The BTFGen algorithm is divided in two main parts: (1) collect the
 * BTF types that are involved in relocations and (2) generate the BTF
 * object using the collected types.
 *
 * In order to collect the types involved in the relocations, we parse
 * the BTF and BTF.ext sections of the BPF objects and use
 * bpf_core_calc_relo_insn() to get the target specification, this
 * indicates how the types and fields are used in a relocation.
 *
 * Types are recorded in different ways according to the kind of the
 * relocation. For field-based relocations only the members that are
 * actually used are saved in order to reduce the size of the generated
 * BTF file. For type-based relocations empty struct / unions are
 * generated and for enum-based relocations the whole type is saved.
 *
 * The second part of the algorithm generates the BTF object. It creates
 * an empty BTF object and fills it with the types recorded in the
 * previous step. This function takes care of only adding the structure
 * and union members that were marked as used and it also fixes up the
 * type IDs on the generated BTF object.
 */
static int minimize_btf(const char *src_btf, const char *dst_btf, const char *objspaths[])

The key call is bpf_core_calc_relo_insn(), the same libbpf function that does the real relocation at load time. bpftool runs every CO-RE record of your object against the target BTF, as libbpf will later, and records which target types and members the result touched. Marking is simple: the member's name_off in a scratch copy of the BTF is overwritten with the sentinel UINT32_MAX (MARKED). A second pass then copies only the marked types and members into a fresh BTF object, keeping their original bit offsets, and renumbers the type IDs.

So the trimmed file is a faithful slice. struct task_struct keeps its real size (7,616 bytes on the orb) and the true bit offsets of the two fields used, while every other member is dropped. Here is the trimmed BTF that execsnoop.bpf.o produces from the orb's own kernel:

Stage 4: embedding the archive in the executable

The tar.gz then becomes part of the program. GNU ld can wrap any file as a relocatable object with -r -b binary. It makes up symbol names from the file name, replacing . with _:

$ ld -r -b binary min_core_btfs.tar.gz -o min_core_btf_tar.o
$ nm min_core_btf_tar.o
00000000000007dc D _binary_min_core_btfs_tar_gz_end
00000000000007dc A _binary_min_core_btfs_tar_gz_size
0000000000000000 D _binary_min_core_btfs_tar_gz_start

(Captured in the orb. 0x7dc = 2,012, the archive size.) The file must be called exactly min_core_btfs.tar.gz, because the runtime library refers to those symbol names. The example Makefile copies each app's archive to that name before calling ld:

# Build application binary
$(APPS): %: $(OUTPUT)/%.o $(OUTPUT)/%-btf.tar.gz $(LIBBPF_OBJ) $(OUTPUT)/libbpf_compatible.a  | $(OUTPUT)
	cp $(word 2,$^) $(OUTPUT)/min_core_btfs.tar.gz
	$(call msg,LD,$(OUTPUT)/min_core_btf_tar.o)
	cd $(OUTPUT) && ld -r -b binary min_core_btfs.tar.gz -o min_core_btf_tar.o
	$(call msg,BINARY,$@)
	$(Q)$(CC) $(CFLAGS) $< $(LIBBPF_OBJ) $(OUTPUT)/libbpf_compatible.a $(OUTPUT)/min_core_btf_tar.o $(ALL_LDFLAGS) -lelf -lz -lzstd -o $@ -static

$(OUTPUT)/libbpf_compatible.a:
	make -C ../../bpf-compatible-sys
	cp ../../bpf-compatible-sys/libbpf_compatible.a $(OUTPUT)

$(OUTPUT)/btfhub-cache:
	BTFHUB_REPO=https://github.com/eunomia-bpf/btfhub-archive \
	BTFHUB_CACHE=$(OUTPUT)/btfhub-cache \
	../../script/btfgen fetch

$(OUTPUT)/%-btf.tar.gz: $(OUTPUT)/%.bpf.o $(OUTPUT)/btfhub-cache 
	BTFHUB_CACHE=$(OUTPUT)/btfhub-cache \
	../../script/btfgen btfgen $< -o $@

The result is a single static ELF. It carries the BPF object (through the skeleton, see chapter 06), libbpf, the Rust runtime, and a 2 KB tarball of type information. It does not need a compiler, kernel headers or a network connection on the target.

How it works: choosing the BTF at run time

On the target machine the program must answer one question: which of the 85 entries describes this kernel? bpf-compatible answers it the same way BCC's libbpf-tools does, with a path built from four strings:

/// Generate the btf archive path of the running kernel
/// It returns somethings like `ubuntu/20.04/x86_64/xxxxxxx.btf`
pub fn generate_current_system_btf_archive_path() -> Result<String> {
    let release_info = os_release::OsRelease::new().map_err(Error::OsReleaseError)?;
    let uname = uname_rs::Uname::new().map_err(Error::UnameError)?;
    let btf_path = format!(
        "{}/{}/{}/{}.btf",
        release_info.id, release_info.version_id, uname.machine, uname.release
    );
    Ok(btf_path)
}

ID and VERSION_ID come from /etc/os-release. The os-release crate strips surrounding quotes, so VERSION_ID="20.04" becomes 20.04. machine and release come from uname(2), the same values that uname -m and uname -r print. On an Ubuntu 20.04 box running the GA kernel, the key is ubuntu/20.04/x86_64/5.4.0-26-generic.btf.

The C-callable runtime: bpf-compatible-sys

libbpf-based programs are usually C, so the runtime is exposed through a C ABI. The core function takes a pointer to the tar.gz bytes and a length:

const VMLINUX_BTF_PATH: &str = "/sys/kernel/btf/vmlinux";

#[no_mangle]
pub extern "C" fn ensure_core_btf_with_tar_binary(
    path: *mut *const c_char,
    tar_bin: *const u8,
    tar_len: c_int,
) -> c_int {
    if PathBuf::from(VMLINUX_BTF_PATH).exists() {
        return 0;
    }
    let tar_bytes = unsafe { slice::from_raw_parts(tar_bin, tar_len as usize) };
    let decompressed_bytes = {
        let mut val = vec![];
        let mut gzip_reader = GzDecoder::new(tar_bytes);
        if let Err(e) = gzip_reader.read_to_end(&mut val) {
            eprintln!("Failed to decompress: {}", e);
            return -EINVAL;
        }
        val
    };

    let mut tar = Archive::new(&decompressed_bytes[..]);
    let local_btf_path =
        PathBuf::from("./btfhub-archive").join(match generate_current_system_btf_archive_path() {
            Ok(v) => v,
            Err(e) => {
                eprintln!("Failed to generate running kernel btf path: {:?}", e);
                return -ENOENT;
            }
        });
    /* ... iterate tar.entries() ... */
        // path of a entry looks like `./btfhub-archive/ubuntu/20.04/x86_64/5.4.0-40-generic.btf`
        /* ... */
        if path == local_btf_path {
            let mut temp_file = match mkstemp::TempFile::new("/tmp/eunomia.btf.XXXXXX", false) {
                /* ... */
            };
            let file_bytes = &decompressed_bytes[entry.raw_file_position() as usize
                ..(entry.raw_file_position() + entry.size()) as usize];
            if let Err(e) = temp_file.write_all(file_bytes) {
                /* ... */
            }
            btf_path = Some(temp_file.path().to_string());
        }
    /* ... */
    // The buffer will be passed to C program, so allocate it with malloc
    let holder = unsafe { malloc(btf_path_bytes.len() + 1) } as *mut u8;
    /* ... copy bytes, add trailing NUL ... */
    *unsafe { &mut *path } = holder as *const c_char;
    0
}

extern "C" {
    static _binary_min_core_btfs_tar_gz_start: c_char;
    static _binary_min_core_btfs_tar_gz_end: c_char;
}

#[no_mangle]
pub extern "C" fn ensure_core_btf_with_linked_tar(path: *mut *const c_char) -> c_int {
    let len = unsafe {
        &_binary_min_core_btfs_tar_gz_end as *const c_char as usize
            - &_binary_min_core_btfs_tar_gz_start as *const c_char as usize
    };
    ensure_core_btf_with_tar_binary(
        path,
        unsafe { &_binary_min_core_btfs_tar_gz_start as *const c_char } as *const u8,
        len as c_int,
    )
}

Why write the BTF to a temporary file? Because the libbpf API is file-based. The btf_custom_path field of bpf_object_open_opts takes a path, and libbpf parses that file itself. The string is allocated with malloc so that C code can later hand it back to clean_core_btf_rs(), which unlinks the file and frees the string.

The C header wraps these functions in the names that BCC's libbpf-tools made familiar:

#ifndef _BTF_HELPER_H
#define _BTF_HELPER_H

#include <bpf/libbpf.h>

int ensure_core_btf_with_tar_binary(const char** path,
                                    const char* tar_bin,
                                    int tar_len);

int ensure_core_btf_with_linked_tar(const char** path);

void clean_core_btf_rs(const char* path);

static int ensure_core_btf(struct bpf_object_open_opts* opts) {
    return ensure_core_btf_with_linked_tar(&opts->btf_custom_path);
}

static int ensure_core_btf_tar(struct bpf_object_open_opts* opts,
                               const char* tar_bin,
                               int tar_len) {
    return ensure_core_btf_with_tar_binary(&opts->btf_custom_path, tar_bin,
                                           tar_len);
}

static void cleanup_core_btf(struct bpf_object_open_opts* opts) {
    clean_core_btf_rs(opts->btf_custom_path);
}

// Allow for not linking the tar binary
char _binary_min_core_btfs_tar_gz_start __attribute__((weak));
char _binary_min_core_btfs_tar_gz_end __attribute__((weak));

#endif  // _BTF_HELPER_H

The last two lines are a linker trick. They are weak definitions of the two symbols. When min_core_btf_tar.o is linked in, its strong definitions win. When it is not, the weak ones keep the link from failing. Both weak symbols are then separate one-byte objects, so the computed "length" is whatever distance the linker puts between them. The gunzip would almost certainly fail and return -EINVAL instead of a clean "not supported" error. (That last point comes from reading the code. I did not test it.) If you want a cleaner way to load an archive that is not linked in, use ensure_core_btf_tar() with a buffer you read yourself, for example from a file next to the binary.

Note a naming slip in the README: it says to call clean_core_btf before exiting, but the header defines cleanup_core_btf. The example uses the header's name.

Using it from a libbpf program

Porting an existing libbpf-bootstrap app takes three lines: include the header, call ensure_core_btf() before the skeleton's __open_opts, and call cleanup_core_btf() on the way out. This is the example's execsnoop.c:

#include "btf_helpers.h"
/* ... */
int main(int argc, char **argv)
{
	LIBBPF_OPTS(bpf_object_open_opts, open_opts);
	/* ... */
	struct perf_buffer *pb = NULL;
	struct execsnoop_bpf *obj;
	int err;
	/* ... argp_parse ... */

	libbpf_set_print(libbpf_print_fn);

	err = ensure_core_btf(&open_opts);
	if (err) {
		fprintf(stderr, "failed to fetch necessary BTF for CO-RE: %s\n", strerror(-err));
		return 1;
	}

	obj = execsnoop_bpf__open_opts(&open_opts);
	if (!obj) {
		fprintf(stderr, "failed to open BPF object\n");
		return 1;
	}
	/* ... set rodata, load, attach, poll the perf buffer ... */

cleanup:
	perf_buffer__free(pb);
	execsnoop_bpf__destroy(obj);
	cleanup_core_btf(&open_opts);
	/* ... */
	return err != 0;
}

On a kernel with BTF, ensure_core_btf returns 0 straight away, and the program behaves exactly as the unmodified libbpf-bootstrap version would. The fallback costs nothing where it is not needed.

What libbpf does with btf_custom_path

The libbpf side was added for this purpose. BTFHub's README points to libbpf commit 4920031 as the start of support for external BTF files. The header comment states the contract and its limit:

	/* Path to the custom BTF to be used for BPF CO-RE relocations.
	 * This custom BTF completely replaces the use of vmlinux BTF
	 * for the purpose of CO-RE relocations.
	 * NOTE: any other BPF feature (e.g., fentry/fexit programs,
	 * struct_ops, etc) will need actual kernel BTF at /sys/kernel/btf/vmlinux.
	 */
	const char *btf_custom_path;

And in libbpf.c, the check that decides whether the kernel's BTF must be loaded at all:

static bool obj_needs_vmlinux_btf(const struct bpf_object *obj)
{
	struct bpf_program *prog;
	struct bpf_map *map;
	int i;

	/* CO-RE relocations need kernel BTF, only when btf_custom_path
	 * is not specified
	 */
	if (obj->btf_ext && obj->btf_ext->core_relo_info.len && !obj->btf_custom_path)
		return true;

	/* Support for typed ksyms needs kernel BTF */
	/* ... */

This sets the scope of the whole approach. bpf-compatible fixes CO-RE field and type relocations. It cannot help with fentry/fexit, tp_btf, LSM-BPF, struct_ops, typed ksyms or kfuncs. All of these need the kernel's real BTF, and kernels old enough to lack /sys/kernel/btf/vmlinux mostly lack those features anyway. A program meant for old kernels has to stick to kprobes, tracepoints, perf events and similar hooks (chapter 05).

Walk through one load

1. Start-up on Ubuntu 20.04, kernel 5.4.0-26-generic, no BTF

./execsnoop starts. LIBBPF_OPTS zero-initializes open_opts, so btf_custom_path is NULL.

2. ensure_core_btf()

/sys/kernel/btf/vmlinux is absent. The runtime gunzips the 2,012-byte blob between _binary_min_core_btfs_tar_gz_start and _end into memory: a tar of 85 small files (30,432 bytes of BTF plus tar headers).

3. Build the key

/etc/os-release gives ubuntu and 20.04, uname gives x86_64 and 5.4.0-26-generic. The key is ./btfhub-archive/ubuntu/20.04/x86_64/5.4.0-26-generic.btf.

4. Extract

The entry is found. Its 358 bytes go to /tmp/eunomia.btf.a1B2c3 (random suffix), and that path is stored in open_opts.btf_custom_path.

5. Open and load

execsnoop_bpf__open_opts(&open_opts) records the custom path. At load time libbpf parses the 358-byte file instead of the kernel's BTF and finds task_struct.real_parent at byte 2,280. It patches instruction #48 from the compile-time 1,416 to 2,280. The verifier accepts the program.

6. Clean up

On exit, cleanup_core_btf() unlinks the temp file and frees the string. If the process is killed with SIGKILL, the file is left behind in /tmp.

The offsets in step 5 are real. They come from libbpf's debug log when the Ubuntu 5.4.0-26 trimmed file is used, shown in the hands-on section.

There are two runtime crates because they serve two kinds of consumer. bpf-compatible-rs is a normal Rust library for Rust loaders. Through ecc and ecli

Chapter 10 introduced ecc (compile once into a JSON package) and ecli (load and run it). ecc has a -b, --btfgen flag and a --btfhub-archive <DIR> option. The compiler README shows them:

# Download btfhub archive and generate minimal BTF
ecc program.bpf.c --btfgen

# Use custom btfhub location
ecc program.bpf.c --btfgen --btfhub-archive /path/to/btfhub

ecc does not call script/btfgen. It has its own Rust copy of the same steps. If the directory is missing, fetch_btfhub_repo runs git clone --depth 1 https://github.com/aquasecurity/btfhub-archive into it. That is the full multi-gigabyte archive, so the first run is slow and needs disk space. generate_tailored_btf then extracts each file and runs bpftool gen min_core_btf, and package_btfhub_tar writes the package:

pub fn package_btfhub_tar(args: &Options) -> Result<()> {
    let tar_path = args.get_output_tar_path();
    let btf_path = args.get_output_directory().join("custom-archive");
    let package =
        fs::File::create(tar_path).with_context(|| anyhow!("Failed to create the tar"))?;

    let mut tar = Builder::new(package);
    /* ... open the .bpf.o and package.json ... */
    tar.append_dir_all(".", btf_path)
        .with_context(|| anyhow!("Failed to add btf archives into tar"))?;
    tar.append_file("package.json", &mut json)
        .with_context(|| anyhow!("Failed to add package.json into tar"))?;
    tar.append_file(&args.object_name, &mut object)
        .with_context(|| anyhow!("Failed to add target object into the tar"))?;
    tar.finish()
        .with_context(|| anyhow!("Failed to write out the tar"))?;
    Ok(())
}

The output is an uncompressed tar named <object_name>.tar, for example client.tar for client.bpf.c. It sits next to package.json and contains a btfhub-archive/ tree, package.json and the object. (The compiler README says "→ btfgen.tar.gz", but the code in options.rs writes {object_name}.tar.)

On the run side, ecli treats a file with a .tar suffix as ProgramType::Tar and unpacks it with bpf_compatible_rs::unpack_tar:

The TempDir is stored in the running task, so the extracted archive lives exactly as long as the program does. The archive root is then passed to bpf-loader-rs. Its selection order differs a little from the C runtime:

        let path_holder = if let Some(base_path) = self.btf_archive_path.as_ref() {
            let path = get_current_system_btf_file(PathBuf::from(base_path).as_path())?;

            }

        } else {

        };
        // Ditto

        /* ... vmlinux_btf_exists = /sys/kernel/btf/vmlinux exists and mode & 0o400 ... */

            // We have to manually modify open_opts and open bpf_object, because libbpf-rs currently doesn't support customizing this..

        } else if let Some(env_btf) = env_btf_file_path.as_ref() {
            open_bpts.btf_custom_path = env_btf.as_bytes().as_ptr() as *const _;

            bail!("All ways tried to find vmlinux BTF, but not found. /* ... */");

The order is: kernel BTF if readable; otherwise the archive entry; otherwise the file named by BTF_FILE_PATH; otherwise an error. There is one sharp edge. The "archive entry exists" check runs before the kernel BTF check. If a .tar package is run on a modern kernel that is not in the archive, loading fails with "BTF file not found for current system", even though /sys/kernel/btf/vmlinux would have worked. The C runtime checks kernel BTF first and does not have this problem. (This comes from reading the code at commit a5408a8. I did not test it with ecli.)

So, assuming ecli's usual run command from chapter 10, running such a package looks like sudo ./ecli run client.tar. The .tar form is inferred from the suffix handling in ecli-lib/src/config/mod.rs. The ecli README's own examples use package.json.

Run 1 shows the mechanism working: the compile-time offsets from the 6.1-based vmlinux.h (1,416 and 1,404) are rewritten to this kernel's 1,400 and 1,388. Run 2 shows that a trimmed file belongs to one object. Types another program never used are simply missing. BTFHub's docs warn about this too: the files "are specifically tailored to the given eBPF object and are incompatible with other eBPF objects".

Run 3 is the important warning. libbpf has no way to check that a custom BTF really describes the running kernel. Hand it the wrong kernel's file, and it patches in that kernel's offsets. The verifier accepts the program because bpf_probe_read_kernel-based reads are allowed to read any address, and you get garbage ppid values with no error. Exact-match selection by uname -r is what stops this from happening, which is why the runtime never "falls back to the closest kernel".

Danger

Never point btf_custom_path (or ecli's BTF_FILE_PATH) at a BTF file from a "similar" kernel. A different build of the same version can have a different task_struct, because configuration options change the layout. CO-RE is only as correct as the BTF you give it.

Trimming does not check compatibility

A last test compiled a tiny program that reads task->__state. The field was named state before Linux 5.14. Trimming it against Ubuntu's 5.4.0-26 BTF succeeded (exit 0) and wrote a 25-byte file with no types. Loading with it failed with relo #0: no matching targets found and <invalid CO-RE relocation>. In other words, btfgen builds an archive without complaint for kernels your program cannot run on. You find out only on the target. The script also never checks the exit status of each bpftool call it starts through xargs. Handling renamed fields remains your job, with the flavor structs and bpf_core_field_exists() covered in chapter 06. When you do, the trimmed BTF records both variants.

Comparisons

bpf-compatible vs. BCC libbpf-tools' own BTFgen support

BCC's libbpf-tools already had the same mechanism, built with make ENABLE_MIN_CORE_BTFS=1. bpf-compatible vs. BTFHub

These two are layers of one stack, not competitors. BTFHub is the data source. It is a Go tool (cmd/btfhub) that downloads distribution debug packages and converts them with pahole, and the archive repo holds the results. BTFHub also has a trimming script, tools/btfgen.sh (-a x86_64|arm64 -o obj.bpf.o [-j N]), which writes a custom-archive/ tree. Tracee is BTFHub's main user and does its own embedding and selection. What BTFHub does not ship is a runtime library for choosing and loading the right file. bpf-compatible adds that, plus an embed step and an example build.

One practical difference: script/btfgen trims every .btf in the cache whatever its architecture. With the full archive, an x86 object is also trimmed against the 1,396 arm64 kernels. That is harmless but slow, and the arm64 entries are useless to an x86 binary. BTFHub's -a filter and BCC's -iregex ".*x86_64.*" avoid it.

bpf-compatible vs. BCC runtime compilation

Classic BCC solves portability the other way round. It ships C source and compiles it on the target with an embedded clang/LLVM against that kernel's headers. Everything is then correct for the running kernel, including #ifdefs on kernel config. The cost is the toolchain and the headers on every host. The orb shows the scale: Debian's libbcc.so.0 (BCC 0.26) is 3.4 MB, but it links against libLLVM-14.so.1 (110 MB) and libclang-cpp.so.14 (59 MB). The orb also has no /lib/modules/$(uname -r)/build, so BCC would not find kernel headers at all. bpf-compatible's per-target cost for execsnoop is a 2 KB blob and a static library. The design document lists BCC's drawbacks: a compiler and kernel headers needed on the target, and CPU spent compiling, "which is not allowed or inconvenient in many production environments".

A kernel security update to 5.4.0-27-generic on a no-BTF Ubuntu host is a new key, and your binary will not find it until you rebuild against a refreshed archive. BTFHub has to publish the new kernel first, too. The design document's proposed online BTF store was meant to close that gap. It was not built.

Benefits and limitations

Benefits

  • Tiny overhead. Kilobytes, not hundreds of megabytes, for broad no-BTF coverage. Measured: 2,012 bytes for 85 kernels.
  • No target toolchain. One static binary, the same model as any CO-RE program.
  • Zero cost on modern kernels. The fallback returns at once when /sys/kernel/btf/vmlinux exists.
  • Three-line port for libbpf C programs, with an API that matches BCC libbpf-tools.
  • Merges archives, so in-house kernels can be added in front of the public archive.
  • Built into eunomia-bpf: ecc --btfgen produces a self-describing .tar that ecli runs.

Limitations

  • Exact-match lookup. The key is ID/VERSION_ID/machine/release. If any part differs from the archive's directory names, there is no match. Two cases worth knowing, both found by reading the code and the archive layout and not tested on real hosts:
    • On 64-bit ARM, uname -m prints aarch64, but btfhub-archive uses arm64 directories. Neither BCC's helper nor bpf-compatible translates the name.
    • RHEL-family VERSION_ID values often contain a minor version (such as 8.4), while the archive has rhel/8 and ol/8. Whether the lookup misses depends on the exact os-release on the host. Unverified.
  • CO-RE only. fentry/fexit, tp_btf, LSM, struct_ops, kfuncs and typed ksyms still need real kernel BTF (libbpf's own note).
  • Per-object archives. Rebuild the archive whenever the BPF code changes. Passing all of an app's objects in one btfgen call (PR #7) gives one archive that works for all of them.
  • Frozen at build time, and limited to what BTFHub has published. Kernels newer than the archive, or custom kernels, are not covered unless you add them.
  • Silent failure modes. btfgen ignores per-kernel failures and makes archives for kernels the program cannot run on. A wrong BTF file leads to wrong reads, not errors (run 3 above).
  • Temp files. The C runtime writes to a fixed /tmp/eunomia.btf.XXXXXX pattern and relies on cleanup at exit. A read-only or full /tmp makes it fail with -EIO.
  • Rough edges: README naming mismatches (BTFHUB_REPO_URL vs BTFHUB_REPO, clean_core_btf vs cleanup_core_btf); -j copies package.json into the cache and never removes it, so it ends up in later archives too (code reading); the ecli/bpf-loader-rs ordering issue described above.
  • CO-RE does not add features. An old kernel without ring buffer or a helper still rejects the program. The proposed bpf_buffer compatibility API was never built. BCC's libbpf-tools/compat.h is the working example of that idea.
Tip

Before shipping, test the archive the way the target will use it. On a build host with BTF you can still check each trimmed file: point btf_custom_path at it and run bpf_object__load() (as in the experiment above). A load that fails with <invalid CO-RE relocation> marks a kernel your program cannot support. Delete that entry, or add a flavor fallback in the BPF code. A load that succeeds proves only that relocation worked, not that the offsets suit this host.

Related work and where to go next

  • Upstream pieces: libbpf's btf_custom_path and bpftool gen min_core_btf (bpftool-gen), whose design is described in BTFHub's "BTFgen internals". The idea was presented in "Towards truly portable eBPF" at Linux Plumbers 2021.
  • BCC libbpf-tools: Makefile.btfgen and btf_helpers.c, the model this repo follows. compat.h handles feature differences between kernels.
  • eunomia-bpf/btf-relocate-demo (last commit January 2024). src/relo.c is bpftool's BTFgen marking code with printfs added ("marking member %s of type %s"), so you can watch which members a relocation pulls in. Its src/relocation.c and examples/ take the same machinery to user-space structs. It builds two programs with different struct data layouts and makes their BTF with pahole --btf_encode_detached. This is groundwork for CO-RE against application types in bpftime (chapter 14; tutorial "Expanding eBPF CO-RE to userspace compatibility").
  • eunomia-bpf/multiarch-relocate-example (last commit May 2024) pushes in another direction: one uprobe.bpf.o for x86_64 and aarch64. A Rust tool reads the .BTF.ext CO-RE records, rewrites struct pt_regs accesses to aarch64 offsets, and then removes .BTF.ext. The README says it was tested on Debian 12 ARM64.
  • Tracee (Aqua Security) is BTFHub's reference user. It embeds tailored BTFs in production.
  • Within this curriculum: 06 for CO-RE itself, 10 for ecc/ecli packaging, 11 for starter templates that this toolchain could be added to, and 12 for another eunomia packaging format.

Check your understanding

Q1. What does bpftool gen min_core_btf FULL.btf OUT.btf prog.bpf.o keep for a field relocation such as BPF_CORE_READ(task, real_parent)?

For field-based relocations BTFgen marks only the members actually used and writes them at their original offsets in the target kernel. The trimmed task_struct in the experiment had size=7616 vlen=2.

Q2. On a kernel that does have /sys/kernel/btf/vmlinux, what does ensure_core_btf() from bpf-compatible do?

The first statement of ensure_core_btf_with_tar_binary checks PathBuf::from(VMLINUX_BTF_PATH).exists() and returns 0. Native BTF always wins.

Q3. Why does the embedded archive have to be named exactly min_core_btfs.tar.gz when it is passed to ld -r -b binary?

ld -b binary turns min_core_btfs.tar.gz into _binary_min_core_btfs_tar_gz_{start,end,size}. The Rust code declares those exact externs.

Q4. You load execsnoop.bpf.o on a 6.1 kernel, but set btf_custom_path to the trimmed BTF for Ubuntu 5.4.0-26-generic. What happened in the experiment?

libbpf cannot tell whether a custom BTF matches the running kernel. It relocates against whatever you give it. This is why the lookup must be an exact match on the kernel release.

Q5. Which program would bpf-compatible not make work on a kernel without /sys/kernel/btf/vmlinux?

libbpf's own comment says btf_custom_path replaces vmlinux BTF only for CO-RE relocations. fentry/fexit and struct_ops still need the kernel's real BTF.

Q6. Compared with BCC's runtime compilation, what is the main thing a bpf-compatible binary gives up?

The archive is embedded and keyed by exact uname -r. BCC compiles against whatever headers are installed, at the cost of shipping LLVM and needing those headers.
