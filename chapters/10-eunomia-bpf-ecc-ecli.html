Chapter 10

eunomia-bpf: ecc and ecli

A libbpf tool has two halves. The kernel half is the interesting part. The userspace half parses flags, loads the object, attaches programs, polls a ring buffer and prints a struct, and you write it again for every tool. eunomia-bpf asks: if the compiler already knows the layout of the event struct and the names of the global variables, why write the userspace half at all? This chapter takes apart the compiler (ecc) and the runner (ecli) that implement that idea, and the package format that sits between them.

Prerequisites: 04, 06Repo: eunomia-bpf/eunomia-bpf @ a5408a8~50 min

Why this exists: the two halves of every libbpf tool

Chapter 06 built bootstrap from libbpf-bootstrap. It traces process exec() and exit, and sends one struct event per process to user space through a BPF ring buffer. At commit 820a1bd the example is three files: bootstrap.bpf.c (111 lines, the kernel side), bootstrap.h (19 lines, the shared event struct) and bootstrap.c (172 lines, the user side), plus a Makefile that runs bpftool gen skeleton.

Most of bootstrap.c is code that every tool needs and no tool cares about. Here is the core of it:

static int handle_event(void *ctx, void *data, size_t data_sz)
{
	const struct event *e = data;
	/* ... format a timestamp ... */
	if (e->exit_event) {
		printf("%-8s %-5s %-16s %-7d %-7d [%u]", ts, "EXIT", e->comm, e->pid, e->ppid,
		       e->exit_code);
		/* ... */
	} else {
		printf("%-8s %-5s %-16s %-7d %-7d %s\n", ts, "EXEC", e->comm, e->pid, e->ppid,
		       e->filename);
	}
	return 0;
}

int main(int argc, char **argv)
{
	/* ... */
	err = argp_parse(&argp, argc, argv, 0, NULL, NULL);
	/* ... */
	signal(SIGINT, sig_handler);
	signal(SIGTERM, sig_handler);
	skel = bootstrap_bpf__open();
	/* ... */
	skel->rodata->min_duration_ns = env.min_duration_ms * 1000000ULL;
	err = bootstrap_bpf__load(skel);
	/* ... */
	err = bootstrap_bpf__attach(skel);
	/* ... */
	rb = ring_buffer__new(bpf_map__fd(skel->maps.rb), handle_event, NULL, NULL);
	/* ... */
	while (!exiting) {
		err = ring_buffer__poll(rb, 100 /* timeout, ms */);
		/* ... */
	}
cleanup:
	ring_buffer__free(rb);
	bootstrap_bpf__destroy(skel);
	return err < 0 ? -err : 0;
}

Look at what this code actually encodes. It knows the program has a ring buffer called rb. It knows the ring buffer carries struct event and which fields to print. It knows there is a read-only global min_duration_ns that should be a command-line flag. It knows the programs can be auto-attached. All of that is already present, in machine-readable form, inside the compiled bootstrap.bpf.o: the map types are in the .maps section, the globals are in .rodata, and the field names, sizes and offsets of struct event are in the object's BTF (06).

There is a second, separate problem: distribution. A libbpf tool is a native executable. You build it per CPU architecture, link it against libbpf and libelf (or link statically), and ship it the way you ship any binary. Two people who want to share a 100-line tracing program still have to agree on a build system.

eunomia-bpf (org eunomia-bpf, docs at eunomia.dev/eunomia-bpf) attacks both problems with one move: put the compiled object and a description of it into one data file, and give the user one generic runner that can read any such file.

Key idea

ecc compiles only the kernel half. It then extracts what a userspace program would have hard-coded (maps, programs, attach points, global variables, the layout of the event struct, doc comments) and writes it as JSON next to a compressed copy of the object. ecli reads that JSON, builds a command line from the globals, loads and attaches with libbpf, picks the ring buffer, perf buffer or annotated hash map as the output channel, and prints each record using the struct layout from BTF. The kernel code is the same code you would write for libbpf-bootstrap; in the bootstrap example it differs from libbpf-bootstrap's file only in whitespace.

The price is generality. A generic runner prints events, histograms and key/value pairs; it does not run your custom aggregation logic. For that, eunomia-bpf lets you write the user half as a WebAssembly module instead of a native binary, which is the subject of chapter 12. This chapter covers the JSON path end to end and the Wasm path where it touches ecc and ecli.

The pipeline, end to end

Before the internals, here is the whole path for the bootstrap example, from source file to kernel. Every box is a function you can find in the source; the step-by-step walkthrough after the figure follows the same order.

ecc: what the compiler generates

ecc is a Rust binary (ecc-rs, crate version 0.3.4). It is not a compiler in the sense of having its own code generator. It is a driver around tools you already met in chapter 06: Clang for BPF code, llvm-strip, and bpftool. Two things make it self-contained. First, its build.rs clones a pinned eunomia fork of bpftool and a pinned set of vmlinux.h headers, builds bpftool, and embeds the result into the ecc binary with rust-embed. Every run unpacks this "workspace" (bin/bpftool, include/bpf/*.h, include/vmlinux/<arch>/vmlinux.h) into a temporary directory. So #include "vmlinux.h" works without you generating one. Second, it links the clang crate, which loads libclang at run time to parse your source for comments.

You still need clang and llvm-strip on PATH (or pass -c/-l). The command line, as printed by the v1.0.38 binary in our orb:

Walking through compile_bpf()

1. Make sure the event struct survives into BTF

Clang only emits BTF for types the program uses. In bootstrap.bpf.c the ring buffer is declared without a value type (ring buffers have none), and struct event is used only through a local pointer. To be safe, ecc copies your source to temp.c, finds every struct NAME { in the header with a regular expression, and appends a dummy global pointer for each. That is why every package has a .bss variable called __eunomia_dummy_event_ptr; the runtime skips it when building the command line.

2. Compile and strip

Clang runs with -g -O2 -target bpf -Wno-unknown-attributes -D__TARGET_ARCH_<arch>, the system include dirs as -idirafter (the same trick as libbpf-bootstrap's Makefile), the workspace include dirs, your -a flags and the source directory. Then llvm-strip -g removes DWARF but keeps .BTF and .BTF.ext, which CO-RE needs.

3. Skeleton as JSON

Upstream bpftool gen skeleton prints a C header. The eunomia fork adds -j, which prints the same information as JSON: object name, maps (with ident and whether they are mmaped data sections), programs (name, section/attach string, whether they produce a link) and the variables in .rodata/.bss with their C types. This becomes meta.bpf_skel.

4. Doc comments become configuration

document_parser.rs parses the original source with libclang and walks the top-level declarations. For each variable, map and program named in the skeleton it reads the /// comment. Plain text becomes description. A Doxygen-style command such as @sample becomes a key, and if the text after it parses as JSON it is stored as JSON. The comment on the LICENSE variable becomes the program's doc block (brief, details, version).

5. Export types from BTF

If you passed a header, bpftool btf dump file bootstrap.bpf.o format c -j (again the fork's JSON mode) lists every struct in the object's BTF. ecc keeps those whose names appear in the header and stores their members, size and BTF type id under meta.export_types.

6. Write the skeleton file

The merged object plus eunomia_version is written to <name>.skel.json (or .skel.yaml with -y). This file has no bytecode; it is the description alone.

7. Pack the object

The stripped ELF is compressed with zlib, base64-encoded, and wrapped with its uncompressed size and the metadata into package.json. Optional extra outputs run after this: --standalone, --wasm-header, --btfgen.

Here is the injection from step 1, and the packing from step 7, as they appear in the source:

const REGEX_STRUCT_PATTERN: &str = r#"struct\s+(\w+)\s*\{"#;

// find all structs in event header
pub fn find_all_export_structs(args: &CompileArgs) -> Result<Vec<String>> {
    let mut export_structs: Vec<String> = Vec::new();
    let export_struct_header = fs::read_to_string(&args.export_event_header)?;
    let re = Regex::new(REGEX_STRUCT_PATTERN).unwrap();

    for cap in re.captures_iter(&export_struct_header) {
        let struct_name = &cap[1];
        export_structs.push(struct_name.to_string());
    }
    Ok(export_structs)
}

/// add unused_ptr_for_structs to preserve BTF info
pub fn add_unused_ptr_for_structs(args: &CompileArgs, file_path: impl AsRef<Path>) -> Result<()> {
    /* ... read file_path into `content` ... */
    for struct_name in export_struct_names {
        content += &format!(
            "const volatile struct {} * __eunomia_dummy_{}_ptr  __attribute__((unused));\n",
            struct_name, struct_name
        );
    }
    fs::write(file_path, content)?;
    Ok(())
}
/// pack the object file into a package.json
fn pack_object_in_config(args: &Options) -> Result<()> {
    info!("Generating package json..");
    let output_bpf_object_path = args.get_output_object_path();
    let bpf_object = fs::read(output_bpf_object_path)?;

    let mut e = ZlibEncoder::new(Vec::new(), Compression::default());
    e.write_all(&bpf_object)?;
    let compressed_bytes = e.finish().unwrap();
    let encode_bpf_object = base64::encode(compressed_bytes);
    /* ... read the .skel.json (or .skel.yaml) back into meta_json ... */
    let package_config = json!({
        "bpf_object": encode_bpf_object,
        "bpf_object_size": bpf_object.len(),
        "meta": meta_json,
    });
    /* ... write package.yaml if -y, else package.json ... */
    Ok(())
}
fn get_export_types_json(
    args: &Options,
    output_bpf_object_path: impl AsRef<Path>,
) -> Result<String> {
    /* ... */
    command
        .args(["btf", "dump", "file"])
        .arg(output_bpf_object_path)
        .args(["format", "c", "-j"]);
    let output =
        handle_std_command_with_log!(command, "Failed to dump BTF from the compiled file!");
    // filter the output to get the export types json
    let export_structs = find_all_export_structs(&args.compile_opts)?;
    /* ... */
    let export_types_json = export_types_json["structs"]
        .as_array()
        .unwrap()
        .iter()
        .filter(|x| {
            let name = x["name"].as_str().unwrap();
            export_structs.contains(&name.to_string())
        })
        .map(|x| x.to_owned())
        .collect::<Vec<Value>>();
    Ok(serde_json::to_string(&export_types_json).unwrap())
}

Note what the struct filter implies: every struct in the header becomes an export type, in the order the header declares them. The loader (as we will see) uses export_types[0] unless you opt in to the multiple-export mode. So the header you pass should declare the event struct first, and ideally nothing else. The example headers follow this convention: <tool>.h holds only exported types, and shared constants go into <tool>.bpf.h (examples/bpftools/README.md).

Annotations you can write

Because step 4 turns any @command in a /// comment into a JSON key, the set of "annotations" is really the set of keys the loader's serde schema (bpf-loader-lib/src/meta/mod.rs) understands. These are the ones the examples use:

const volatile bool filter_cg = false;
const volatile bool targ_per_process = false;
const volatile bool targ_per_thread = false;
const volatile bool targ_per_pidns = false;
const volatile bool targ_ms = false;
const volatile pid_t targ_tgid = 0;
/* ... */
/// @sample {"interval": 1000, "type" : "log2_hist"}
struct {
    __uint(type, BPF_MAP_TYPE_HASH);
    __uint(max_entries, MAX_ENTRIES);
    __type(key, u32);
    __type(value, struct hist);
} hists SEC(".maps");

A map with sample is read by user space every interval milliseconds. The type can be log2_hist, linear_hist or default_kv (the default); optional keys are unit (default "(unit)") and clear_map. The six bool/pid_t globals become --filter_cg, … , --targ_tgid.

/// Process ID to trace
const volatile int pid_target = 0;
/// Thread ID to trace
const volatile int tgid_target = 0;
/// @description User ID to trace
const volatile int uid_target = 0;
/// @cmdarg {"default": false, "short": "f", "long": "failed"}
/// @description trace only failed events
const volatile bool targ_failed = false;
/* ... */
struct {
    __uint(type, BPF_MAP_TYPE_PERF_EVENT_ARRAY);
    __uint(key_size, sizeof(u32));
    __uint(value_size, sizeof(u32));
} events SEC(".maps");

The comment text becomes the help string. @cmdarg overrides the long name, adds a short name and a default. Output here goes through a perf event array instead of a ring buffer; the runtime handles both.

/// @ifindex 1
/// @flags 0
/// @xdpopts {"old_prog_fd":0}
SEC("xdp")
int xdp_pass(struct xdp_md* ctx) {
    void* data = (void*)(long)ctx->data;
    void* data_end = (void*)(long)ctx->data_end;
    int pkt_sz = data_end - data;

    bpf_printk("packet size is %d", pkt_sz);
    return XDP_PASS;
}

libbpf cannot auto-attach XDP or TC programs, because it does not know the interface. These comments land in the program's metadata (ifindex 1 is lo on most systems). In our build the resulting entry was {"attach": "xdp", "flags": 0, "ifindex": 1, "link": true, "name": "xdp_pass", "xdpopts": {"old_prog_fd": 0}}.

/// @tchook {"ifindex":1, "attach_point":"BPF_TC_INGRESS"}
/// @tcopts {"handle":1, "priority":1}
SEC("tc")
/* ... */

Same idea for TC: the hook (interface and direction) and the filter options go into metadata, and the loader creates the qdisc hook and attaches. The defaults in the schema are ifindex 1, ingress, handle 1, priority 1.

A few details are worth reading slowly:

  • bootstra.rodata is not a typo in this chapter. libbpf names internal maps from the first eight characters of the object name plus the section name, because kernel map names are limited to 15 characters plus NUL. The ident field (rodata) is the stable handle the loader uses.
  • The type_id (314) is an index into the program's own BTF, not the kernel's. The loader uses it to look the struct up again and check that the names and member count still match.
  • There are no offsets in members. Offsets and sizes come from BTF at run time; the JSON only names the fields.
  • exit_event is unsigned char because the repository's bootstrap.h declares it that way, so the runner prints 0/1. The template repository's copy of the header uses bool.

bpf-loader-rs: turning JSON back into a running tool

bpf-loader-lib is the part that replaces bootstrap.c. It is a library on top of libbpf-rs 0.20, structured in the same three phases as a libbpf skeleton: open, load-and-attach, poll. Its README calls them BpfSkeletonBuilder, PreLoadBpfSkeleton and BpfSkeleton.

Phase 1: open, and pick the kernel BTF

The builder opens the decompressed ELF from memory with bpf_object__open_mem. Before that it decides where CO-RE should find the kernel's types. The order matters for old kernels:

        let path_holder = if let Some(base_path) = self.btf_archive_path.as_ref() {
            let path = get_current_system_btf_file(PathBuf::from(base_path).as_path())?;
            /* ... bail if missing ... */
            Some(path)
        } else {
            None
        };
        let env_btf_file_path = std::env::var_os(BTF_PATH_ENV_NAME);
        /* ... vmlinux_btf_exists = /sys/kernel/btf/vmlinux is present and readable ... */
        if path_holder.is_some() && !vmlinux_btf_exists {
            open_bpts.btf_custom_path = path_holder /* ... */;
        } else if let Some(env_btf) = env_btf_file_path.as_ref() {
            open_bpts.btf_custom_path = env_btf.as_bytes().as_ptr() as *const _;
        } else if !vmlinux_btf_exists {
            bail!("All ways tried to find vmlinux BTF, but not found. Please provide the vmlinux btf using env `BTF_FILE_PATH`. /* ... */");
        };
        let open_result = unsafe {
            libbpf_sys::bpf_object__open_mem(
                self.bpf_object.as_ptr() as *const c_void,
                self.bpf_object.len() as libbpf_sys::size_t,
                &open_bpts,
            )
        };

On a normal modern kernel, /sys/kernel/btf/vmlinux exists and libbpf uses it. If it does not exist, the loader uses a BTF file from a tailored archive (the .tar package from ecc -b, matched to the running kernel by bpf-compatible-rs; see chapter 13), or a file you name in BTF_FILE_PATH. The builder also dumps the program's own BTF into a BtfContainer; that is what the printer will use later.

Phase 2: fill globals, load, attach

Before loading, the loader writes the initial contents of .rodata and .bss. It starts from the bytes in the ELF and overwrites each variable that has a value from the command line or from value in the JSON, using the variable's BTF type to encode it. In our run, --min_duration_ns 200000000 showed up in the log as received bytes [0, 194, 235, 11, 0, 0, 0, 0], which is 200,000,000 as a little-endian u64. This is the generic version of the libbpf-bootstrap line skel->rodata->min_duration_ns = ….

Then it calls load() (libbpf performs CO-RE relocation and the kernel verifier runs) and tries libbpf's auto-attach on each program. Programs libbpf cannot auto-attach fail with EOPNOTSUPP; the loader catches exactly that error and attaches them itself:

        for prog_meta in self.meta.bpf_skel.progs.iter() {
            /* ... */
            match bpf_prog.attach() {
                Ok(link) => links.push(AttachLink::BpfLink(link)),
                // EOPNOTSUPP 95 Operation not supported
                Err(_) if errno::errno().0 == 95 => {
                    // Not supported for auto-attaching, needs manually operations
                    not_attached.push(prog_meta);
                    continue;
                }
                Err(err) => bail!("Failed to attach program `{}`: {}", prog_meta.name, err),
            };
        }
        for prog_meta in not_attached.into_iter() {
            /* ... */
            match bpf_prog.section() {
                "tc" => links.push(attach_tc(bpf_prog, prog_meta)/* ... */?),
                "xdp" => links.push(attach_xdp(bpf_prog, prog_meta)/* ... */?),
                "perf_event" => {
                    let mut perf_links =
                        attach_perf_event(bpf_prog, prog_meta)/* ... */?;
                    links.append(&mut perf_links);
                }
                s => bail!("Unsupported attach type: {}", s),
            }
        }

This is where the @ifindex and @tchook comments end up. It is also the honest boundary of "no userspace code needed": a program type outside libbpf's auto-attach list and outside these three manual cases cannot be run this way.

Phase 3: choose the output channel and print

With no user code, the runtime has to guess where the output comes from. The rule, in the default single-export mode, is: walk the maps in order; a map with sample metadata is a sampled map; otherwise a BPF_MAP_TYPE_RINGBUF or BPF_MAP_TYPE_PERF_EVENT_ARRAY is an event stream. If several qualify, the last one wins (with a warning).

        let mut export_map: Option<(&MapMeta, ExportMapType)> = None;
        for map_meta in self.meta.bpf_skel.maps.iter() {
            /* ... look up bpf_map by name ... */
            if let Some(sample_meta) = &map_meta.sample {
                set_and_warn_existsing_map(
                    &mut export_map,
                    map_meta,
                    ExportMapType::Sample(sample_meta),
                );
            } else if let MapType::RingBuf = bpf_map.map_type() {
                set_and_warn_existsing_map(&mut export_map, map_meta, ExportMapType::RingBuffer);
            } else if let MapType::PerfEventArray = bpf_map.map_type() {
                set_and_warn_existsing_map(
                    &mut export_map,
                    map_meta,
                    ExportMapType::PerfEventArray,
                );
            }
        }
        if let Some((map_meta, export_type)) = export_map {
            /* ... */
            if self.meta.export_types.is_empty() {
                bail!(
                    "Export map named `{}` found, but no export type is provided",
                    map_meta.name
                );
            }
            /* ... build exporter for export_types[0], then poll in a loop ... */
        } else {
            self.wait_for_no_export_program()
                /* ... */;
        }

The exporter is built from export_types[0]. Before it prints anything, checker.rs looks the struct up by type_id in the program's BTF, requires the same name and member count, reads each member's bit offset and size, and rejects bitfields. Each record that arrives is then cut into fields at those offsets and printed either as a text row under a generated header (TIME PID PPID …) or, with ecli run -j, as one JSON object per line. For sampled maps the key and value types come from the map's own BTF (btf_key_type_id, btf_value_type_id) and a log2_hist value is drawn as the familiar BCC-style ASCII histogram.

A program with no exportable map (for example minimal or xdp, which only call bpf_printk) is simply kept loaded until you press Ctrl-C; you read its output from /sys/kernel/tracing/trace_pipe, as their READMEs say.

Multiple outputs

If you set "enable_multiple_export_types": true in the package's meta, the loader ignores export_types and instead uses each map's export_config (btf_type_id, custom_members or default) and can poll several maps at once through wait_and_poll_to_handler_with_multiple_exporter. ecc does not generate this; the repository's tests (assets/multiple_export_ringbuf/) write it by hand. A map can also declare "intepreter": {"stack_trace": …} (the field name is spelled that way in the schema) so that records are symbolized as stack traces with blazesym.

meta/arg_builder.rs builds a clap parser from the data section variables. Names starting with __eunomia_dummy are skipped. A bool with no default becomes a switch --name; one defaulting to false becomes --enable-name; one defaulting to true becomes --disable-name. Every other type takes a value, checked against the BTF type when it is written. A --verbose switch (libbpf debug output) is always added. The doc block from the LICENSE comment fills the version, the text before the options and the text after; without it you get "A simple eBPF program" and "Built with eunomia-bpf framework.". ecli: running from a file, a URL or a registry

ecli is a thin clap front end (ecli/client/src/main.rs) over ecli-lib. Since March 2026 (PR #377) it has exactly three subcommands. The older server mode (ecli client, ecli-server) was removed and lives on the archive/ecli-remote-http branch.

$ ./ecli -h
ecli subcommands, including run, push, pull

Usage: ecli [COMMAND_LINE]... [COMMAND]

Commands:
  run   run ebpf program
  push  Operations about pushing image to registry
  pull  Operations about pulling image from registry
  help  Print this message or the help of the given subcommand(s)

ecli run [-j] [-p json|tar|wasm] <prog> [args…] takes one program reference and passes the rest of the line to the program. The bare form ecli <prog> still works for compatibility. The reference is resolved by one function, which is worth reading because its fall-through order explains several confusing error messages:

/// Load the binary of the given url, and guess its program type
/// If failed to guess, will just return None
/// It will try the following order
/// - Test if the provided string is a local file. If matches, read it
/// - If the string is a URL, then treat it as a HTTP URL, and download it.
/// - If the string is not an url, treat it as an OCI image tag
pub async fn try_load_program_buf_and_guess_type(
    url: impl AsRef<str>,
) -> anyhow::Result<(Vec<u8>, Option<ProgramType>)> {
    let url = url.as_ref();
    // Is it a local path?
    let path = PathBuf::from(url);
    let (buf, prog_type) = if path.exists() && path.is_file() {
        /* ... read file ... */
        let prog_type = ProgramType::try_from(url).ok();
        (buf, prog_type)
    } else if let Ok(url) = url::Url::parse(url) {
        /* ... reqwest::get(url), read bytes, guess type from suffix ... */
        (data.to_vec(), prog_type)
    } else {
        debug!("Trying OCI tag: {}", url);
        let image = Reference::try_from(url)
            .with_context(|| anyhow!("Failed to parse `{}` into an OCI image reference", url))?;

        let data = pull_wasm_image(&image, &RegistryAuth::Anonymous, None)
            .await
            .with_context(|| anyhow!("Failed to pull OCI image from `{}`", url))?;
        (data, Some(ProgramType::WasmModule))
    };
    Ok((buf, prog_type))
}

Three consequences follow directly from this code:

  • The program type comes from the file suffix: .json → JSON package, .wasm → Wasm module, .tar → JSON package plus BTF archive. Anything else, or input from stdin (-), needs -p.
  • A local path that does not exist is not an error. It falls through to "is it a URL?" and then to "is it an image reference?". A mistyped pakage.json becomes a request to Docker Hub for library/pakage.json.
  • Anything pulled from a registry is treated as a Wasm module. The OCI path does not carry JSON packages. To publish a JSON-only tool to a registry you wrap it in a Wasm module first (next section).

The widget below replays that decision for any string you type. It is a small re-implementation for teaching, not code from the repository; its URL test approximates url::Url::parse as "starts with a scheme followed by a colon".

Tar packages and old kernels

ecc -b clones btfhub-archive (once, into ~/.local/share/eunomia/btfhub-archive by default), unpacks every .btf.tar.xz, runs bpftool gen min_core_btf on each one against your object, and tars the small results together with package.json and the object. This is the BTFGen technique from chapter 06, automated. On the target, ecli run tool.tar unpacks the tar, and the loader uses the matching tailored BTF only if /sys/kernel/btf/vmlinux is missing. The eunomia.dev page "supporting-external-BTF" describes the same flow. We did not run -b here; the archive is large.

The Wasm path, where it touches ecc and ecli

A JSON package is enough when "print the struct" is the whole user side. When you need logic, for example sigsnoop's mapping from signal numbers to names, you write the user side in C (or Rust, or Go) and compile it to WebAssembly. The full model is chapter 12. The connection to this chapter is small and concrete:

  1. ecc foo.bpf.c foo.h --wasm-header writes ewasm-skel.h, which is the whole package.json as one escaped C string: char* program_data = "{\"bpf_object\":\"eJyt…. (For the xdp example: 1,431-byte package, 1,630-byte header.)
  2. A Wasm module includes that header and passes the string to host functions provided by the runtime.
  3. ecli run app.wasm runs it with wasm-bpf-rs, which loads the embedded package through the same bpf-loader machinery and delivers events back into the module.

The smallest such module is in the repository's GitHub Pages build script. It wraps any JSON package into a Wasm module that just prints every event, which is how a JSON tool becomes something you can ecli push to a registry:

#include <stdio.h>
#include <string.h>

#include "ewasm-skel.h"

int create_bpf(char *ebpf_json, int str_len);
int run_bpf(int id);
int wait_and_poll_bpf(int id);

int bpf_main(char *env_json, int str_len)
{
    (void)env_json;
    (void)str_len;

    int res = create_bpf(program_data, strlen(program_data));
    if (res < 0) {
        printf("create_bpf failed %d\n", res);
        return -1;
    }
    res = run_bpf(res);
    /* ... same check ... */
    res = wait_and_poll_bpf(res);
    /* ... same check ... */
    return 0;
}

int process_event(int ctx, char *event_json, int str_len)
{
    (void)ctx;
    printf("%.*s\n", str_len, event_json);
    return -1;
}

The same script compiles it with wasi-sdk's clang: --target=wasm32-wasi -O0 -z stack-size=4096 -Wl,--initial-memory=65536 … -Wl,--export=bpf_main -Wl,--export=process_event -Wl,--strip-all,--no-entry -Wl,--allow-undefined. The --allow-undefined is what lets create_bpf and friends stay as imports for the host to supply. The sigsnoop example goes further: it adds ecc sigsnoop.h --header-only and the separate c-struct-bindgen tool to generate sigsnoop.wasm.h, so the Wasm code can read the event struct with the right layout, then builds with its build.sh. Its README shows:

{"pid":1641,"tpid":2368,"sig":23,"ret":0,"comm":"YDLive","sig_name":"SIGURG"}

"Compile once, run everywhere": what is actually portable

The README promises tools that run "without recompiling, kernel version and architecture independent". It helps to split that claim into parts and check each against the code.

Kernel version: yes, via CO-RE

The package carries the object with its .BTF and .BTF.ext. libbpf relocates field accesses against the target's BTF exactly as in chapter 06. Our package, built against eunomia's bundled vmlinux.h, read real_parent->tgid correctly on 6.1. Without kernel BTF, a .tar from ecc -b or BTF_FILE_PATH fills in.

Kernel features: no

CO-RE fixes offsets, not missing features. The ring buffer needs Linux 5.8; fentry, LSM and struct_ops need their own minimum versions (chapter 05). An older kernel rejects the program at load time, with the verifier or with an unknown map type.

Architecture: mostly, with a catch

BPF bytecode is the same on every CPU, so one package.json can load on x86-64 and arm64. But ecc compiles with -D__TARGET_ARCH_<build arch>, and bpf_tracing.h macros such as PT_REGS_PARM1 for kprobes expand to architecture-specific register fields. A tracepoint-only tool like bootstrap is portable; a kprobe tool compiled on x86 reads x86 register names. The Wasm-bpf paper names this problem and describes a CO-RE relocation pass for kprobe pt_regs accesses; neither ecc nor the wasm-bpf runtime implements such a pass at the studied commits (chapter 12).

Runner: per architecture

ecli itself is native code. Releases ship ecli (x86-64) and ecli-aarch64. The package is portable; the runner is not.

The in-browser compiler (ecli-webui)

ecli-webui is a Vue 3 + Vite playground, deployed at ecli-webui.vercel.app, that compiles eBPF C entirely in the browser. It uses Emception, a build of LLVM/Clang (and other tools) compiled to WebAssembly with Emscripten. On load the page fetches vmlinux.h and the libbpf headers (bpf_helpers.h, bpf_tracing.h, bpf_core_read.h, …) and writes them into Emception's in-memory file system. The repository's online-compile.md explains two fixes made in September 2026: the -D__TARGET_ARCH_x86 define (without it, bpf_tracing.h's register macros hit a _Pragma("GCC error")), and example code adjusted to the newer kernel's struct filename layout in the bundled vmlinux.h.

The browser only runs Clang. It does not run bpftool or libclang's comment parser, so the package it builds has empty maps and progs, no obj_name, no export types, and an object that is base64 but not zlib-compressed. Compare that with the loader's schema shown earlier. To check, we rebuilt the same JSON shape in Python from our bootstrap.bpf.o and gave it to ecli v1.0.38. It was rejected with Malformed json provided: missing field `obj_name`, and after adding obj_name, with Malformed compressed data: unknown ZLIB method CM=0xf (0x7f, the first byte of every ELF file, is not a valid zlib header). We did not run the web app itself, but as of 6816d61 its downloaded package.json should not load in the current ecli without changes. Treat the playground as a way to check that code compiles, not as a replacement for ecc.

Benefits and limitations

Benefit: kernel code only

For tools that emit events or histograms, the user side disappears. The kernel code stays standard libbpf C, so it moves to libbpf-bootstrap (or back) unchanged.

Benefit: one data file

A tool is one JSON file of a few KB to tens of KB. It can be inspected with jq, edited (defaults, poll interval) and served from any web server.

Benefit: one runner, many sources

Local file, URL, and OCI registry through the same ecli run; Wasm when you need real logic.

Benefit: small toolchain surface

ecc bundles bpftool, libbpf headers and vmlinux.h; you need clang and llvm-strip. A Docker image (ghcr.io/eunomia-bpf/ecc-<arch>) removes even that.

Limit: fixed output model

One export struct per program by default, chosen by a header file and map-walk order. No filtering, aggregation or joining in user space without Wasm. Bitfields are rejected.

Limit: attach coverage

What libbpf can auto-attach, plus manual TC, XDP and perf_event. Uprobes need an attach string libbpf can resolve; the compiler roadmap still lists "Better uprobe support" and "Enhanced XDP support" as open.

Limit: trust and privilege

ecli run https://… downloads bytecode and runs it as root. There is no signature check in the code path shown above. Pin versions, or host your own packages.

Limit: maintenance state

Main-repo work is now mostly dependency bumps; docs and READMEs lag the code in places; published example URLs 404; the latest ecc failed on our host's glibc. The core load path worked well.

The project also states figures we did not measure: the introduction page says the library is "<1MB" and can load and run a program in "<100ms". They are the project's claims.

Related work

  • libbpf-bootstrap (chapter 06) and the eunomia starter templates (chapter 11): you write the user side; maximum control.
  • BCC and bpftrace (chapter 08): also "kernel logic only" for the user, but they compile on the target (BCC) or use their own language (bpftrace). eunomia-bpf compiles ahead of time and runs plain libbpf C.
  • BumbleBee (Solo.io): the closest idea. It also packages libbpf programs as OCI images and generates the user side from map definitions, with a bee CLI. The repo's own internal-docs/POSITIONING.md compares the two.
  • bpfman: loads eBPF bytecode from OCI images and manages its lifecycle on a host or in Kubernetes. It is a deployment manager rather than a "no user code" runner.
  • wasm-bpf (chapter 12) and the paper below: the Wasm half of this design. bpftime (chapter 14) is the org's other runtime, which runs eBPF programs in user space instead of the kernel.
  • The bpf-developer-tutorial (chapter 09) uses ecc/ecli in many of its early lessons.

Check your understanding

Q1. You run ecc tool.bpf.c without a header. The program writes to a ring buffer. What happens when you run the package?

Export types only come from the header argument (step 5). Ring buffers have no value type to guess from. wait_and_poll_with_old_single_export bails when it finds an export map but export_types is empty.

Q2. Why does every package built with a header contain a .bss variable named __eunomia_dummy_event_ptr?

add_unused_ptr_for_structs appends one dummy pointer per struct in the header to a temporary copy of the source. The runtime skips these names when building the command line.

Q3. A global is declared as /// @cmdarg {"default": true} followed by const volatile bool verbose_mode = true;. Which flag does the generated command line offer?

A bool's default comes from cmdarg.default (or a value in the JSON). In arg_builder.rs, default true yields --disable-<name>, default false yields --enable-<name>, and no default yields --<name>. The C initializer alone does not count: the skeleton JSON records only the variable's name and type.

Q4. sudo ecli run ghcr.io/me/tool:v1. What kind of program does ecli expect to receive?

The OCI branch of try_load_program_buf_and_guess_type calls pull_wasm_image and always returns ProgramType::WasmModule. JSON tools are pushed by first wrapping them in a Wasm module.

Q5. A kprobe tool reads its first argument with PT_REGS_PARM1(ctx). You build the package with ecc on x86-64. Which statement is right?

CO-RE relocates struct field accesses by name; PT_REGS_* pick architecture-specific pt_regs fields at compile time. Tracepoint-based tools avoid the problem.

Q6. Why would a package.json downloaded from ecli-webui at 6816d61 fail to load in ecli v1.0.38?

BpfSkeletonMeta.obj_name is a required field and ComposedObject inflates bpf_object with zlib. The web UI writes plain base64 and empty skeleton fields.
