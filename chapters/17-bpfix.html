Chapter 17

bpfix: explaining and fixing verifier errors

When the eBPF verifier rejects a program, it reports the instruction where it gave up, not the place where your program lost the fact it needed. bpfix reads the verifier log you already have and rebuilds that story: which proof the verifier required, where the proof was established, where it was lost, and what to change. It prints the result as a Rust-style diagnostic. The same project ships a benchmark that measures whether that diagnostic helps an LLM repair the program.

Why this matters

Chapter 03 explained how the verifier walks every path through a program and tracks an abstract state for each register: a pointer type such as pkt or map_value_or_null, a known offset, a range of possible scalar values. If an instruction can't be proven safe from that state, the load fails, and with log_level=2 the kernel hands back a trace of every state it visited. The last line is the terminal error, for example R5 invalid mem access 'scalar'.

The terminal error is accurate, but it is a symptom. It names the operation that needed a proof (a load through r5) and the state that fell short (r5 is a plain number, not a packet pointer). It does not say why r5 is a number at that point, or which source line made it so. To find out, the developer reads the trace backwards through branch points, register copies and spills, and matches instruction numbers to C lines by hand. Experienced eBPF developers learn to do this. Everyone else, including LLM coding agents, tends to guess: add another bounds check, cast something, try -O1.

bpfix's authors measured how big that gap is. In their study of 235 reproduced rejections, 47% of rejections came back with the same errno, EINVAL. After normalising registers and offsets, one terminal message, R# invalid mem access 'scalar', covered 28 cases spread over nine different root causes (paper/sections/2-empirical-study.tex, table tab:fanout). So the message alone can't tell you which fix applies.

Key idea

A verifier rejection is a missing proof. bpfix treats it as such: it maps the terminal error to a required proof ("R1 must have packet range ≥ 14 bytes", "R5 must still be a packet pointer"), then searches the logged abstract states for the instruction where that proof first held (established) and the instruction where it stopped holding (lost). The gap between the loss point and the rejection point is what a raw log leaves you to find by hand.

What bpfix is, and what it is not

The repository (created March 2026, MIT licensed, about 475 commits on master when this chapter was written) contains four things that are easy to mix up:

bpfix CLI

A Rust command-line tool (crates/bpfix on top of the crates/bpfanalysis library) that reads a verifier, bpftool, libbpf, Aya or BCC log and prints one plain-text diagnostic. Published on crates.io; v0.1.10 at the time of writing.

bpfix-empirical

A corpus of 235 real verifier rejections from Stack Overflow, GitHub issues, fix commits and kernel selftests, each rebuilt and replayed on one pinned kernel/toolchain, with a hand-adjudicated label.

bpfix-bench

A frozen 75-task LLM repair benchmark. Each task has a rejected C file, its raw log, the bpfix diagnostic, a reference fix and an executable oracle. This is where "let an LLM fix it" is measured.

Agent skill

skills/ebpf-verifier-repair/: a portable instruction pack for coding agents (Codex, Claude Code, Copilot) that describes a repair workflow. It can use bpfix output but does not require it.

The README lists explicit non-goals. bpfix is not a kernel patch, not a verifier replacement, "not an automatic source-code repair tool", and not a checker for programs the verifier accepts. The CLI never edits your code and never calls a model. Repair happens elsewhere: in the benchmark runner, in the agent skill, or in your editor. The project tagline ("let LLM fix it") refers to that loop, and the benchmark exists to test whether a better diagnostic makes the loop succeed more often.

The first two tabs come from the 6.15 replay log shipped in the repository. I reproduced the second tab byte for byte by running a locally built bpfix 0.1.10 on that log. The third tab is my own run: I loaded the repo's examples/bpftool/quick-start.bpf.o (the same object) on Linux 6.1 with bpftool v7.1.0 and passed the log to the same binary.

Here is what happened, read from the log. clang lowered the if (ipv4_hdr) … else … into straight-line code. At pc 23 it set r5 = 0 (the still-NULL ipv6_hdr). At pc 30 it computed r5 += 40, which is ipv6_hdr + sizeof(struct ipv6hdr). At pc 31 it tested ipv4_hdr and, if non-NULL, replaced r5 with the real packet pointer. The verifier does not conclude that a packet pointer compared with zero is non-NULL, so it also explores the jump "from 31 to 34". On that path r5 is the number 40. The data_end check at pc 36 then compares a number, which proves nothing about memory, and the load at pc 37 is rejected. The program is safe at run time. The rejection comes from compiler lowering combined with verifier precision. This is why the paper's lowering-artifact table lists the upstream fix as "rederive the UDP pointer in each checked branch" (paper/tables/sec-5-lowering.tex).

Kernel version matters for source spans

The third tab has no source lines. bpfix does not read DWARF or BTF from the object in its default mode. It takes source locations from the comments the verifier writes into the log using the program's BTF line info. Since Linux 6.9, verbose_linfo() in kernel/bpf/log.c ends each comment with " @ file:line" (commit 7cc13adbd057, "bpf: emit source code file name and line number in verifier log", February 2024). Linux 6.8 and earlier print only the source text (on 6.1 the code is in verifier.c and prints "%s\n"). bpfix's parse_source_comment() needs that suffix. On an older kernel you still get the error ID, class, required proof and help, but the location is a line in the log rather than in your C file.

The empirical study behind it

bpfix's design comes from a dataset, so it is worth knowing how the dataset was built. bpfix-empirical/ is the replayable corpus, and the paper draft in the paper/ submodule describes how it was collected.

How the 235 cases were collected

The authors gathered 936 candidate reports from four places: Stack Overflow questions, GitHub issues, GitHub fix commits (Cilium, Aya, bcc, libbpf and others) and Linux kernel selftests. Each candidate was rebuilt and loaded on one pinned environment (bpfix-empirical/environment.yaml: kernel 6.15.11, clang 18.1.3, bpftool v7.7.0, verifier log level 2). A candidate entered the corpus only if it rebuilt, loaded, was rejected by the local verifier, and could be parsed again by the validator. 235 of the 936 qualified. The five-class taxonomy

Every case gets exactly one primary class. The rule in bpfix-empirical/taxonomy.yaml is: "ask which layer must change to make the failure disappear". The classes are checked in a fixed order: verifier false positive first, then environment, verifier limit, lowering artifact, and finally source bug.

lowering_artifactSource intent is fine; clang emitted verifier-hostile bytecode18

The paper groups these four ways (developer 191, compiler 18, environment 14, verifier 12) and splits the 191 developer bugs into 12 root causes. The largest are unclamped scalars used as an offset or length (24), corrupted or stale dynptrs (23), packet access without a bound on every path (22), and missing NULL checks (19). It counts 10 of the 12 root causes as eBPF-specific (paper/tables/sec-2-mechanisms.tex). The case file for the running example records the label and the adjudicated root cause:

Why the terminal message is too coarse

To measure how ambiguous terminal messages are, the authors replaced register numbers and offsets with placeholders. That collapsed 167 distinct strings into 82 templates. Fifteen templates map to more than one root cause. The four most common:

TemplateCasesDistinct root causes
R# invalid mem access 'scalar'289
invalid access to packet265
invalid access to map value184
R# !read_ok134

Even the layer is ambiguous. Of the 28 'scalar' cases, 24 are source bugs and 4 are compiler-lowering artifacts whose upstream fix changed how the program was compiled (paper/tables/sec-3-rejection-classes.tex, sec-5-lowering.tex). A tool that matches only on the message string can't tell the two apart. It needs the state history, and with log_level=2 the verifier prints that history.

How bpfix works

The paper describes three stages: log analysis, proof reconstruction and diagnostic generation. The code follows that split. bpfanalysis parses the log into typed records, and the bpfix crate turns them into a required proof, proof events and rendered text. The only required input is the log.

Stage 1a: find the rejection

Real logs are messy. A make run prints compiler warnings, libbpf prints relocation chatter, CI systems prefix timestamps, and some loaders retry and print several load logs. input.rs normalises all of this. It strips ANSI escapes and ISO-8601 timestamp prefixes, keeps the last -- BEGIN PROG LOAD LOG -- region, and then scans upward from the end for the first line that looks like a verifier error:

pub(crate) fn find_terminal_error(log: &str) -> Option<TerminalError> {
    let lines = log.lines().collect::<Vec<_>>();
    let mut idx = lines.len();
    while idx > 0 {
        idx -= 1;
        let line = lines[idx].trim();
        if !is_verifier_error_line(line) {
            continue;
        }

        let mut context_idx = idx;
        let mut message_start = line;
        while context_idx > 0 {
            let previous = lines[context_idx - 1].trim();
            if !is_terminal_error_continuation(message_start, previous) {
                break;
            }
            context_idx -= 1;
            message_start = previous;
        }
        let message = lines[context_idx..=idx]
            .iter()
            .map(|line| line.trim())
            .collect::<Vec<_>>()
            .join("; ");
        let pc = explicit_terminal_insn_pc(&message)
            .or_else(|| nearest_instruction_pc(&lines, context_idx));
        /* ... call_target, nearest_source_span ... */

is_verifier_error_line() in bpfanalysis/src/verifier_log.rs skips libbpf lines, instruction lines, state lines and the processed N insns summary. It accepts a line if it contains one of 54 lower-case markers ("invalid ", "unreleased reference", "!read_ok", "dynptr", …). Scanning backwards matters. When I loaded a small tracepoint program of my own on 6.1, the log began with an unrelated BTF complaint (reg type unsupported for arg#0 function count_openat#17) long before the real rejection. Because bpfix searches from the end, it picked the real one. Multi-line messages are joined with "; ". The packet case below shows invalid access to packet, off=12 size=2, R1(id=0,off=12,r=13); R1 offset is outside of the packet.

Stage 1b: parse every abstract state

The core of bpfanalysis is a line parser for the three shapes of state line the verifier prints at log level 2. The module comment lists them:

//! The verifier emits state snapshots in a few common forms:
//! - `from <prev> to <pc>: R0=... R1=...`
//! - `<pc>: R0=... R1=...`
//! - `<pc>: (..insn..) ... ; R0=... R1=...`
/* ... */
#[derive(Clone, Debug, PartialEq, Eq)]
pub struct RegState {
    pub reg_type: String,
    pub value_width: VerifierValueWidth,
    pub precise: bool,
    pub exact_value: Option<u64>,
    pub tnum: Option<Tnum>,
    pub range: ScalarRange,
    pub packet_range: Option<u32>,
    pub map_value_size: Option<u32>,
    pub mem_size: Option<u32>,
    pub offset: Option<i32>,
    pub source_frame: Option<usize>,
    pub id: Option<u32>,
    pub ref_id: Option<u32>,
}

Each parsed line becomes a VerifierInsn: the PC, the log line it came from, the call frame, an optional from_pc for branch states, and a map from register number to RegState. Stack slots and live reference IDs are parsed too. The fields are the same facts chapter 03 taught you to read by eye: pkt(off=34,r=42) becomes reg_type = "pkt", offset = 34, packet_range = 42, and scalar(umax=65535,var_off=(0x0; 0xffff)) becomes a ScalarRange plus a Tnum. If a line looks like a state but doesn't parse, the parser fails with an error and bpfix prints it as = warning: in the diagnostic. It does not skip the line silently. The running example yields 60 snapshots on both kernels. Different kernel versions print slightly different state syntax (for example pkt(off=0,r=0,imm=0) on 6.1 and pkt(r=0) on 6.15), and the parser handles both.

Stage 2b: instantiate the required proof

A generic help text ("add a bounds check") is what developers already get from a quick web search. bpfix tries to fill in the concrete parameters. For packet bounds it reads off, size and r from the terminal message itself:

fn packet_bounds_required_proof(message: &str, register: Option<u8>) -> RequiredProof {
    let proven_range = parse_i64_after(message, "r=");
    let required_end = packet_required_range(message).map(i64::from);
    let description = match (register, required_end, proven_range) {
        (Some(reg), Some(required), Some(range)) => format!(
            "prove R{reg} has packet range at least {required} bytes before this access; verifier currently has range {range}"
        ),
        /* ... weaker variants when some parameters are missing ... */
    };
    /* ... rejection_detail built the same way ... */
}

pub(crate) fn packet_required_range(message: &str) -> Option<u32> {
    let off = parse_i64_after(message, "off=")?;
    let size = parse_i64_after(message, "size=")?;
    u32::try_from(off.checked_add(size)?).ok()
}

For invalid access to packet, off=12 size=2, R1(id=0,off=12,r=13), the required end is 12 + 2 = 14 and the proven range is 13, so the diagnostic says "prove R1 has packet range at least 14 bytes before this access; verifier currently has range 13". Other obligations have similar instantiators for scalar ranges (from the register's logged bounds), nullable pointers, stack initialisation, references, dynptrs and environment capability.

Stage 2c: find where the proof was established and lost

This is the step a raw log can't do for you. For each obligation, proof_events.rs walks the parsed states and the source comments and emits ProofEvents with a role (ProofEstablished, ProofLost or Rejected) and an evidence kind (VerifierState, SourceComment or TerminalVerifier). The evidence kind records how strong the claim is. "The logged register type changed from pkt to scalar at pc 34" is a fact read from the verifier's own output. "There's an if on line 263 just above the rejected line" is a heuristic based on source text. For pointer provenance, the state-based part is this function:

pub fn reg_state_is_pointer_like(state: &RegState) -> bool {
    state.reg_type != "scalar" && state.reg_type != "fp"
}

pub fn latest_pointer_to_scalar_transition(
    states: &[VerifierInsn],
    terminal_pc: Option<usize>,
    reg: u8,
) -> Option<(usize, String)> {
    let mut latest_pointer: Option<(usize, String)> = None;
    let mut latest_loss = None;
    for state in states {
        if terminal_pc.is_some_and(|pc| state.pc > pc) {
            continue;
        }
        let Some(reg_state) = state.regs.get(&reg) else {
            continue;
        };
        if reg_state_is_pointer_like(reg_state) {
            latest_pointer = Some((state.pc, reg_state.reg_type.clone()));
        } else if reg_state.reg_type == "scalar" {
            if let Some((_, pointer_kind)) = latest_pointer.as_ref() {
                latest_loss = Some((state.pc, pointer_kind.clone()));
            }
        }
    }
    latest_loss
}

The register to track comes from the terminal message (R5). Across the 60 snapshots, R5 is pkt(off=34,r=34) on the fall-through path at pc 33 and pc 34, and the number 40 in the from 31 to 34 state. The last pointer-to-scalar change before pc 37 is at pc 34, which bpfix reports as the loss point. Through the source comments, pc 34 maps to line 267, the data_end check. That is the secondary label "verifier state changes from pkt to scalar before the rejected access" in the "after" tab. Figure 17.2 shows the whole lifecycle.

The source-comment heuristics fill in context around this. For pointer provenance, the nearest earlier if ( that doesn't mention data_end is labelled as "nearby source context" (line 263), and the nearest data_end check is a candidate establishment site. For packet bounds, bpfix looks for the latest state where the verifier had proved enough packet range, and then for the point where that range disappeared. Similar procedures exist for scalar ranges, nullable pointers, stack initialisation, references and environment capability.

Stage 2d: map PCs to source lines

Source mapping is short code, and you need to understand it to know when it fails:

pub(crate) fn collect_source_events(log: &str) -> Vec<SourceEvent> {
    let lines = log.lines().collect::<Vec<_>>();
    let mut events = Vec::new();
    for (idx, line) in lines.iter().enumerate() {
        let Some(source) = parse_source_comment(line) else {
            continue;
        };
        let pc = lines
            .iter()
            .skip(idx + 1)
            .take(4)
            .find_map(|next| parse_instruction_pc(next));
        events.push(SourceEvent {
            pc,
            log_line: idx + 1,
            source,
        });
    }
    events
}

pub(crate) fn parse_source_comment(line: &str) -> Option<SourceLocation> {
    let (source, tail) = line.rsplit_once(" @ ")?;
    let (path, line_no) = tail.trim().rsplit_once(':')?;
    Some(SourceLocation {
        path: path.to_string(),
        line: line_no.parse().ok()?,
        text: source.trim().trim_start_matches(';').trim().to_string(),
    })
}

The kernel writes these comments from the program's BTF line info (.BTF.ext, produced when you compile with -g; see chapter 06). A comment is bound to the first instruction PC printed within the next four log lines, and any PC maps to the latest comment at or before it. This is the "BTF line info" route to source mapping. bpfix does not read the object's DWARF and does not do its own line-table lookup in the default build. Here is the kernel side that makes it possible:

	/* leave only file name */
	fname = strrchr(s, '/');
	fname = fname ? fname + 1 : s;
	verbose(env, " @ %s:%u\n", fname, BPF_LINE_INFO_LINE_NUM(linfo->line_col));

Two practical consequences follow. First, compile with -g, or there's no line info at all. Second, on kernels before 6.9 the comments have no @ file:line, so parse_source_comment returns None for every line and you get the <verifier-log>:N fallback seen in the 6.1 tab. The 6.15 log also contains an empty ; @ prog.c:0 comment for compiler-generated instructions. One of the open pull requests (#9, October 2026) teaches bpfix to ignore it.

Stage 3: signals, spans and rendering

After the generic events, signal_pipeline.rs runs a long list of named predicates. Each looks for one specific mechanism: SharedInstructionPointerMerge, PointerShiftDropsProvenance, DynptrStackSlotWriteOverlap, IrqRestoreOrderMismatch, NullablePointerUseWithoutProof, SleepableCallInNonSleepableContext, and so on. A matching signal can replace the classifier's class, title, required proof and help. This is how the running example goes from the classifier's source_bug guess for 'scalar' to lowering_artifact. Which signal fires depends on the available evidence. With source comments (6.15), the packet-pointer signal fired ("compiler-lowered control flow hides an established packet-pointer proof"). Without them (6.1), a different, state-only signal fired ("one verifier path reaches this shared instruction with a valid pointer proof, but another path reaches it after the proof is clobbered"). Both reached the same class.

The header line span: reports how trustworthy the location is:

fn span_confidence(
    source_span: &SourceSpan,
    related_spans: &[RelatedSpan],
    proof_events: &[diagnostic::ProofEvent],
) -> &'static str {
    let has_non_source_comment_pc = proof_events
        .iter()
        .any(|event| event.pc.is_some() && event.evidence != ProofEventEvidence::SourceComment);
    if source_span.instruction_pc.is_some() && has_non_source_comment_pc {
        return "exact_pc";
    }
    if !related_spans.is_empty() || source_span.source_text.is_some() {
        return "nearest_source_comment";
    }
    if source_span.line_start.is_some() {
        return "terminal_line_only";
    }
    "none"
}

The renderer in output.rs then prints the result in rustc style. The first line is error[ID]: title. Four = header lines give the class, confidence, support/help-safety/span quality and the "next action" routing word (bounds, null, provenance, release, environment, budget, protocol, …). Then come the --> location, the source block (^^^ under the rejected line, --- under related lines), the raw terminal message as = verifier[N]:, notes, the required proof, and the help: lines. The format is plain text only. A JSON mode existed and was removed on 2026-06-19, and the README says there's "no stable JSON output mode in 0.1.x".

Walkthrough

Step through what happens to the 6.15 log of the running example:

1. Normalise and cut

load_input() strips wrappers and keeps the text between the last -- BEGIN PROG LOAD LOG -- and -- END PROG LOAD LOG --. The libbpf lines after the END marker (failed to load: -EACCES) are kept in full_log for signals that need them, but they are not the terminal error.

2. Terminal error

Scanning upward, processed 68 insns and verification time are skipped. R5 invalid mem access 'scalar' matches the "invalid " marker. The nearest instruction above it is pc 37, r2 = *(u16 *)(r5 +2).

3. Classify

The message matches the pointer-provenance pattern, which gives BPFIX-E006 and obligation PointerProvenance, with default required proof "preserve a verifier-recognized pointer type at the operation that requires a pointer". The register is parsed from R5.

4. Parse states

60 state snapshots (full states, per-instruction deltas and from X to Y branch states) become VerifierInsn records. Source comments become SourceEvents bound to PCs: line 263 → pc 30, 267 → pc 34, 270 → pc 37.

5. Lifecycle

latest_pointer_to_scalar_transition(states, 37, 5) finds R5 last seen as pkt and then as scalar at pc 34, giving a ProofLost event with VerifierState evidence, mapped to line 267. A SourceComment event points at line 263, and a Rejected event at pc 37 / line 270.

6. Signals

The lowering signal for a packet pointer whose proof is lost after a bounds check fires. It overrides the class to lowering_artifact, sets the title "verifier-visible compiler lowering hides the required proof", and inserts the help line about using the packet pointer that received the data_end proof.

7. Render

The rejected event has a PC and a state-based event exists, so span confidence is exact_pc. Spans are sorted by line and de-duplicated, help lines are de-duplicated, and the text in the "after" tab is printed. The whole run took about 3 ms on this orb.

The LLM repair loop: BPFix-Bench

bpfix makes no repair claims in its CLI. The claim lives in bpfix-bench/: given a rejected program, does an LLM produce a working fix more often when it sees the bpfix diagnostic than when it sees the raw log?

What a task looks like

Each of the 75 tasks in the frozen split bpfix-bench/splits/main.txt is a directory with six files. buggy.bpf.c is the rejected source. verifier.log is the raw log captured from it. diagnostic.txt is bpfix's output for that log. fixed.bpf.c is a reference repair, never shown to the model. test.py is the executable oracle, never shown either. README.md describes provenance. The benchmark doc lists 40 tasks designed around one mechanism and 35 minimised from real projects: Cilium (7), ActPlane (5), xdp-tools (5), AgentSight (4), bpf-developer-tutorial (4), bpftime (3), eunomia.dev (3), DatRail (2), NCCL-eBPF (1) and Tetragon (1). The skew toward XDP (62 of 75) is deliberate. XDP and TC programs can be run deterministically with bpftool prog run, which makes functional oracles possible.

A small task shows the shape. packet_eth_off_by_one_001 checks 13 bytes and reads the 2-byte h_proto at offset 12. The reference fix changes 13 to 14 and, further down, 20 to 21. The oracle is a list of packets and expected XDP return codes:

if __name__ == "__main__":
    raise SystemExit(
        run_case(
            argv=sys.argv[1:],

                "invalid access to packet",

            functional_tests=[
                ("ipv4_drops", lambda: frame(0x0800), 1),

                ("twenty_byte_ipv6_packet_passes", twenty_byte_ipv6_packet, 2),
            ],

A candidate passes only if every layer passes. It must compile with clang -target bpf -O2 -g, load with bpftool -d prog load, return the expected value for every bpftool prog run packet, and, where the case defines them, satisfy success-log predicates and hidden source-semantics predicates. Those predicates block "fixes" that pass the verifier by deleting behaviour, shrinking a copy window or weakening a helper protocol. I ran the oracle against the reference fix on this orb's 6.1 kernel with run_suite.py --case packet_eth_off_by_one_001 --candidate …/fixed.bpf.c, and it passed. One check, the 13-byte packet, is recorded as run_error_treated_as_pass: bpftool prog run on 6.1 refused the frame as too short (Invalid argument), and the oracle counts that as a pass. bpfix's output for this case on 6.15 (from the checked-in diagnostic.txt):

The prompt and the retry

The runner, bpfix-bench/tools/run_suite.py, talks to any OpenAI-compatible /chat/completions endpoint. The system prompt is one sentence. The user prompt holds the source and exactly one evidence block, whose label depends on the mode (raw verifier log, BPFix plain-text diagnostic, nothing for source-only, and so on):

SYSTEM_PROMPT = "You repair eBPF C verifier failures by returning a full corrected source file."
# ...
    return f"""You are fixing one eBPF verifier rejection.

Return only one complete replacement C source file in a fenced ```c block.
Do not explain. Do not output a diff. Preserve the intended packet/helper
semantics; do not remove the program, maps, SEC() section, or license.
{diagnostic_guidance}
{skill_block}

Source file:
```c
{source}
```
{diagnostic_block}
"""

With --repair-attempts 2, a failed candidate starts a second turn. oracle_retry_context() appends "Previous repair attempt failed.", the failure stage, the previous candidate source, and whichever outputs apply: compiler stderr, the new verifier log, or the failed functional checks as JSON. Each is truncated in the middle to a fixed character budget. The retry never includes the reference fix or the hidden source predicates, and audit_cases.py checks generated prompts for leaked case IDs and oracle snippets. The retry carries the new raw verifier log, not a new bpfix diagnostic, in both modes.

Is it just a shorter prompt? The August ablations

The most recent experiments (commits 306f6dd3 to 098cc270, 1–5 August 2026) address the obvious objection: maybe raw logs fail because they're long, and any short prompt would do as well. The runner gained token accounting and three ablation modes. bpfix-no-help drops the help: lines. matched-raw-tail keeps only as many complete lines from the end of the raw log as fit the same token budget. source-only sends no log at all. The report is explicit about its limits: one model, one deterministic run, a 32K-context server, and raw token totals that are lower bounds because some calls were rejected before usage was reported.

The agent skill

The July 2026 commits turned the repair workflow into an agent skill, skills/ebpf-verifier-repair/. It installs with gh skill install eunomia-bpf/bpfix ebpf-verifier-repair --agent codex --scope user or as a Claude Code plugin (/plugin marketplace add eunomia-bpf/bpfix). The skill describes the job as "Repair verifier failures as missing proof obligations, not as string-matched terminal errors". It gives an eight-step workflow: establish the failing load path, choose the evidence path, route by proof evidence, freeze the semantic contract, form a proof-obligation hypothesis, edit minimally and in a verifier-visible way, validate by reloading, and report in proof terms. Reference files cover raw-log triage, repair patterns, semantic preservation and failure-directed retries. It treats bpfix as optional: "A full verbose verifier log plus source is sufficient evidence to start; use bpfix only when it is available and helpful." scripts/extract_verifier_failure.py compacts oversized logs for the model's context. The benchmark has a matching --mode skills. I found no published results for that mode in the tree.

  • March 2026 — OBLIGE. The first commit is a research plan. The scaffold was called OBLIGE ("Add OBLIGE project scaffold: taxonomy, schema, collectors, agent harness"), the first corpus had 302 cases from three sources, and the implementation was in Python. It was renamed BPFix on 19 March.
  • April 2026 — corpus engineering. Raw backlog triage, reconstructing cases from Cilium and libbpf commits, and a mutually exclusive taxonomy.
  • May 2026 — Rust rewrite. "Add Rust BPFix workspace", "Render diagnostics in rust style", "Instantiate required proofs". The Python implementation was removed from the maintained tree, and the terminology changed from "proof obligation" to "required proof".
  • June 2026 — the benchmark. 352 of the 475 commits. Dozens of "Harden … case" commits tightened oracles so trivial verifier-only fixes fail, real-project seeds were admitted, and the 75-task split was frozen. Model runs, the paper submodule and the crates.io release pipeline followed, and the CLI contract was frozen at 0.1.x.
  • July–August 2026 — cost and agents. --doctor, the published skill, token and timing accounting, prompt ablations, and v0.1.10.
  • Since then. No new commits on master after 5 August. Three pull requests opened on 31 October (#8–#10) fix narrow diagnostic issues: whole-word matching for NULL-check identifiers, ignoring the line-0 source comment, and a Rust-idiom cleanup in instruction decoding.

The paper draft

The paper/ submodule (public repository yunwei37/ebpf27-bpfix, last commit 2 July 2026) is titled "Characterizing and Bridging the Diagnostic Gap in eBPF Verifier Rejections". Its authors are Yusheng Zheng, Zhengjie Ji, Weichen Tao, Xiangyu Gao, Jianchang Su, Wei Zhang, Andi Quinn and Dan Williams (UC Santa Cruz, eunomia-bpf, Virginia Tech, Telecom Paris, University of Washington, University of Connecticut). It uses the ACM sigplan template. A commented-out line names "eBPF '27, ACM SIGCOMM Workshop on eBPF and Kernel Extensions", which matches the repository name, but the draft states no acceptance, so treat the venue as unconfirmed. Benefits and limitations

Fits existing workflows

No kernel patch, no new loader, no re-run. It reads the log your build or CI already produced, from any loader. It runs in milliseconds, and the default build has no C dependencies.

Evidence, not guesses

Loss points come from the verifier's own logged states, and each event records whether it came from state or source text. span: and confidence: tell you how much to trust the location.

Separates layers

The same 'scalar' message can come out as source_bug or lowering_artifact. Knowing the compiler is involved changes which fix you try.

Measured, with oracles

The repair claim is backed by executable oracles that reject behaviour-deleting "fixes", frozen splits, published summaries and ablations against length effects.

The limitations are just as concrete:

  • Source spans need Linux 6.9 or later. On older kernels you get IDs, classes and required proofs but no C line numbers (shown on 6.1 above). Optional object analysis correlates CFG sites, but README says full BTF source correlation is still future work. I did not build the object-analysis feature.
  • Needs log level 2 and -g. The whole method reads per-instruction state. A log truncated by a small buffer, or a loader that prints only the last line, produces E000 or a weak diagnostic.
  • Heuristics on source text. Several events come from matching source text (looks_like_null_check tests for "!ptr", "== 0", …). Open PR #8 exists because such matching was too loose. Labels can be confusing, like the "0 bytes" span above.
  • Coverage is corpus-driven. The 73 signal kinds were written against the 235-case corpus, and the --reject-fallback gate checks support on that same corpus. New verifier messages in future kernels will start out as E099.
  • The benchmark is curated, not representative. Its own document says it is "not a natural-frequency sample". It is 62/75 XDP, built on one kernel, and does not cover CO-RE relocation failures, cross-kernel portability, or bugs in programs the verifier accepts.
  • Narrow model matrix. Three models, one deterministic run each. Some 27B and GLM runs were recorded from a dirty tree, which the doc discloses.
  • Docs drift. bpfix-empirical/README.md still says the evaluation driver calls bpfix --format json, but JSON output was removed and the driver parses text.

Related work

Explaining verifier errors

Pretty Verifier (Rizza, Sisto and Valenza, IEEE CSR 2025) is the closest prior tool. It post-processes the verifier log to connect the error to the C source and to explain it in plainer language with a suggested fix. The bpfix paper describes it as using regular expressions on the terminal error. The bpfix paper's distinction is that Pretty Verifier maps the terminal error to a line and a hint, while bpfix searches the trace for the loss point. bpfvv, the BPF Verifier Visualizer in the libbpf GitHub organisation, is an interactive front-end for reading per-instruction verifier state. It helps a human do the backward search but does not do it automatically. The model for bpfix's output is rustc's diagnostic system (primary and secondary spans, notes, help, stable error codes), documented in the rustc dev guide.

Studies of eBPF development pain

Deokar et al., An Empirical Study on the Challenges of eBPF Application Development (eBPF '24), classified eBPF questions on Stack Overflow along several eBPF-specific dimensions. "Error handling and verifier messages" is one of their categories. The bpfix paper cites this study for the observation that, without a way to find where the proof was lost, developers fall back on trial and error. bpfix's corpus goes further: each failure is reproduced on a pinned toolchain and labelled with the layer that must change.

LLMs that write eBPF

KEN (arXiv 2023), published as Kgent: Kernel Extensions Large Language Model Agent at eBPF '24, comes from the same group (Zheng, Yang, Chen, Quinn). It synthesises eBPF programs from English prompts and loops on failure: symbolic execution and the real verifier check the candidate, and their error messages are fed back to the LLM. In Kgent the raw verifier message was the feedback signal. bpfix asks whether a better signal makes such loops succeed more often. Later work from the org on agent-driven optimisation is covered in chapter 19, and the org's other LLM-for-kernel tools in chapter 30.

Checking or replacing the verifier

These works ask a different question: is the verifier right, or can we avoid it? PREVAIL (PLDI 2019) re-proves eBPF safety with abstract interpretation. Agni (CAV 2023) verifies the soundness of the verifier's range-analysis operators. State embedding (OSDI '24) found logic bugs in the verifier by embedding concrete states as checks. Chapter 03 covers all three. Rex (USENIX ATC '25) moves safety into a safe Rust subset to close the "language-verifier gap", the very gap that causes bpfix's lowering-artifact class. Chapter 18 covers the org's Z3-based translation-validation project (its early PREVAIL stage has since been removed). None of these explains a rejection to the developer, which is where bpfix fits.

Check your understanding

Q1. In bpfix's terms, what is the "loss point" of a rejection?

The rejection location is where verification stopped (pc 37 in the running example). The loss point is the transition bpfix finds in the state history, such as R5 going from pkt to scalar at pc 34. A raw log gives you the first and leaves you to find the second.

Q2. You run bpfix 0.1.10 on a log from Linux 6.1 and get --> <verifier-log>:180 with no source lines, even though you compiled with -g. Why?

The 6.1 log does contain ; if (udph + …) comments, but without @ prog.c:267. verbose_linfo() began printing " @ %s:%u" in Linux 6.9's kernel/bpf/log.c.

Q3. Why did the 6.15 diagnostic for SO 53136145 say class: lowering_artifact rather than source_bug?

The classifier's first guess is based on the message. Signals in signal_pipeline.rs can override the class from state evidence. bpfix never reads corpus labels at run time. The same message appears in 24 source-bug cases.

Q4. In BPFix-Bench, which of these would let a model's "fix" count as a pass?

The oracle (test.py via bpf_case.run_case) is layered on purpose, so that deleting behaviour to satisfy the verifier fails. The reference fix only shows that the task is solvable.

Q5. What did the August 2026 ablation suggest about why the bpfix prompt helps Qwen3.6 27B?

From bpfix-bench/results/ablation-main75-current-server/result-report.md. Source-only (24/75) did better than the earlier full-raw cost run (21/75).

Q6. Which statement about the bpfix CLI is true?

The README's non-goals exclude automatic repair and running loader commands. JSON output was removed in June 2026, and 0.1.x has no stable JSON mode.
