Chapter 19

bpf-benchmark and bpfperf: Agent-Driven eBPF Optimization

The kernel's eBPF JIT translates one instruction at a time and has no optimizer. Can you make production eBPF programs such as Cilium, Katran or Tetragon faster without touching their source, without trusting a new optimizer, and without growing the kernel? bpf-benchmark is eunomia-bpf's attempt at an answer. It is a measurement harness, a set of optimizers working at three levels (bytecode, the LLVM backend and the kernel JIT), and a benchmark in which LLM agents search for optimizations. This chapter reads the repository and explains what each part does, how results are measured, and which numbers the repository can back up.

Why this matters

An eBPF program runs on whatever the kernel JIT makes of it. Chapter 02 showed that the x86-64 JIT is a large switch over opcodes that emits a fixed short sequence for each instruction. It does not allocate registers across instructions, it does not fuse patterns, and it cannot emit any machine instruction that has no eBPF counterpart. A 64-bit rotate written in C as (x << n) | (x >> (64 - n)) becomes four eBPF instructions and then four or more x86 instructions, although the CPU has a single rol. A byte-by-byte little-endian load stays eight loads, shifts and ORs.

The size of the gap has been measured. The kernel RFC that came out of this repository reports that on 27 small compute benchmarks compiled from the same C source, "BPF ran 1.71x (x86-64) and 2.05x (arm64) slower than native code, while compiling the same BPF bytecode with LLVM came within 7% of native code", and concludes: "The loss is in the JIT, not in the bytecode" (cover letter, 2026-10-05). Chapter 16 showed the same effect from the userspace side, where llvmbpf compiles eBPF with LLVM's -O3.

Closing that gap in the kernel is slow and risky. Every peephole added to a JIT is new trusted code, has to be written once per architecture, and goes through upstream review. Optimizing bytecode before loading (K2, Merlin) avoids the kernel but cannot emit instructions that eBPF lacks, and it needs the .bpf.o file ahead of time. There is also a deeper problem that the repository documents with its own data: the same transformation helps one program and hurts another, and static counts of rewritten sites do not predict speed. So the useful question is not only "which optimizations exist" but "which ones should be applied to this program, on this kernel and CPU, under this workload". bpf-benchmark poses that as a search problem and lets LLM agents run the search against real measurements.

Key idea

bpf-benchmark is three things in one repository: (1) a harness that starts real eBPF applications in a KVM or AWS guest, loads their programs through their own loaders, applies an optimization plan, and records raw kernel counters; (2) action backends, namely the bpfopt bytecode optimizer with an LD_PRELOAD shim, and kinsn (BPF-Ext) kernel modules that add verified native operations to the JIT; (3) a benchmark framing in which an LLM agent chooses the actions and the harness is the oracle. Safety always comes from the stock kernel verifier; the optimizers only have to be correct.

What the repository contains

The README introduces the project as an "Auto-research framework and benchmark for agentic OS kernel extension optimization" and says that it "frames eBPF optimization as a closed-loop search problem for LLM agents. Agents choose optimization actions, the framework executes those actions against real applications and workloads in isolated Docker/KVM/AWS environments, and each iteration returns verifier, JIT, workload, and performance feedback for the next decision." It claims coverage of "six production eBPF applications, 146 comparable BPF program measurements, and 42 microbenchmark tasks".

Read further and you find that the repository hosts three separate research lines. An archived design hub calls them "three sister ideas" that "share the same evaluation infrastructure (the bpf-benchmark corpus, the micro suite and the measurement infrastructure), but solve different problems with different designs" (kinsn/docs/archive/paper-prototype-design.md, translated from Chinese):

Speculative ReJIT (bpfopt/, rejit/)

Fully userspace and needs a stock kernel only. An LD_PRELOAD shim captures each BPF_PROG_LOAD, runs bytecode-to-bytecode passes (map_inline, const_prop, dce, branch_flip…), and submits the result to the normal verifier.

kinsn / BPF-Ext (kinsn/)

Kernel modules define new operations (rotate, conditional select, bit extract, …). The verifier checks each one through an equivalent sequence of plain eBPF; the JIT emits the native instruction. This line is the ATC '26 paper.

kprog / NativeBPF (kprog/)

An eBPF program that simulates a native x86 or arm64 instruction stream, so the stock verifier can check native code before it runs. Comes with a large Lean 4 model.

Shared framework

runner/, corpus/, micro/, bpfperf/ and analysis/: the Make-driven harness, the six applications, the microbenchmarks, the branch profiler, and the post-hoc statistics.

The repository is busy and large: 859,843 KB on GitHub, around 4,900 commits since August 2023, and pushed minutes before this survey. Most of that size is raw results (corpus/results/ holds over 118,000 tracked files) and test binaries extracted from the applications (bpfopt/testbin/). For this chapter the repository was cloned sparsely, which skipped those trees and the vendored kernel and LLVM submodules.

The three optimization layers

The draft paper for the benchmark (public submodule docs/ebpf27-bpfoptbench) describes the action space as three layers of the compilation pipeline. Seeing them side by side is the easiest way into the code:

The last one "requires real per-site PMU profile input and is not part of the default runner policy". That PMU input comes from bpfperf, covered at the end of this chapter.

Architecture of the closed loop

Figure 19.1 shows how the pieces fit. An agent (in practice Claude Code or Codex, operating the repository under its AGENTS.md) never touches a BPF syscall. It edits policy, mostly pass YAML under runner/config/passes/, and runs make corpus or make micro. The Makefile builds a runtime image and boots a guest, and the runner starts each application twice. During the second start the shim inside the application rewrites programs as they load. The kernel verifier accepts or rejects each candidate, the JIT compiles it (with kinsn modules if loaded), and the runner collects run_cnt and run_time_ns per program and the workload's own throughput. Analysis scripts outside the harness turn those raw numbers into ratios, which feed the agent's next decision.

There is no LLM driver in the source tree, and the word "agent" means two different things in the code.

The integrity model: the agent is untrusted

If an agent is rewarded for speedups, the cheapest speedup is to shorten the workload, drop the programs that got slower, or edit the result file. The README states the rule plainly: "Paper experiments treat agents as untrusted optimizers. Agents should interact with the benchmark through make targets, not by editing workloads, shortening durations, filtering failed programs, bypassing application loaders, or fabricating result files." AGENTS.md turns that into concrete constraints, and they are worth reading because they define the benchmark as much as the code does:

  • Frozen launchers. "don't modify benchmark workloads, upstream app source, app runners, corpus/driver.py, benchmark Makefiles, or runtime-image launch wiring without explicit authorization, and never to amplify a reported speedup. Pass YAML under runner/config/passes/ is policy, not a frozen launcher — change it freely."
  • No filtering. "Never filter, skip, or exclude a BPF program from ReJIT — a failure (e.g. EINVAL) is recorded and surfaces naturally".
  • Real loaders. "Apps load their own BPF programs via real application startup; the framework never loads .bpf.o directly or ships a custom loader binary instead of the upstream one".
  • Raw results only. result.json holds per-program run_cnt_delta, run_time_ns_delta, id, name, type, bytes_jited, bytes_xlated and app output. "Any aggregation, ratio, geomean, win/loss tally, CI, or rollup is forbidden in framework code".
  • No fallbacks in code. "unsupported capability or command failure exits 1 with a clear message, never downgrades or returns partial results".

The draft paper adds that these constraints are enforced "via OS-level policy", citing ActPlane (Chapter 24). That is a claim in the draft; the enforcement setup itself is not in this repository.

Measurement methodology

Benchmarks of eBPF programs are noisy. A program may run a few times or millions of times during a sample, guests share host CPUs, and kernel statistics have overhead. The repository settles on a specific protocol, documented in rejit/docs/evaluation.md §5 and the artifact guide.

Two-start, load-time comparison

The corpus suite starts each application, runs the workload, records counters, and stops it. Then it starts the same upstream binary again with BPFREJIT_SHIM_LOADTIME_PLAN set, so the shim rewrites every program while it is being loaded, and runs the workload again. AGENTS.md calls this "the accepted protocol" and forbids replacing it with live swapping in the driver. The shim can replace programs in a running process (next section), but a result counts as "live-swap" only if its recorded lifecycle used that path.

1. Build and boot

make corpus builds the runtime image in layers (base OS, prebuilt apps, kernel and kinsn modules, C++ runner, shim and bpfopt, Python and configs) and boots a KVM guest with vng, or an AWS instance when PLATFORM=aws. BPFREJIT_CORPUS_APPS selects a subset of the six apps.

2. Baseline start

The runner starts, for example, Katran through its normal launcher. The application's loader issues BPF_PROG_LOAD for each program; the shim records state but does not rewrite anything. The workload (pktgen for Cilium and Katran, stress-ng for Tetragon, Tracee and BCC) runs for WORKLOAD_DURATION seconds.

3. Record and stop

Per-program run_cnt and run_time_ns come from bpftool prog show with bpf_stats_enabled=1; the workload's packets/s or ops/s come from the app side. The app is stopped.

4. Policy start

The same binary starts again with BPFREJIT_SHIM_LOADTIME_PLAN. For each load, the shim canonicalizes map references, runs each bpfopt step in the plan, and probes the stock verifier with the candidate.

5. Accept or fall back per program

If the verifier accepts, the optimized bytecode replaces the original in that same load. If it rejects, the log says verifier probe rejected candidate after step <pass> and the original program loads. If bpfopt itself fails, the load fails on purpose ("loadtime optimization failed").

6. Record raw results

Both phases go into corpus/results/<arch>_<platform>_corpus_<timestamp>/. Per-site reports go to details/loadtime-reports/; KEEP_WORKDIRS=1 keeps the before and after bytecode of each step.

7. Analyse outside the harness

analysis/corpus_analyze.py computes per-program ratios, filters, and geomeans. The agent reads these and decides on the next policy.

The per-program ratio

For BPF cost, the unit of comparison is one program's average time per run in each phase:

b_avg = baseline.run_time_ns_delta   /  baseline.run_cnt_delta
p_avg = post_rejit.run_time_ns_delta /  post_rejit.run_cnt_delta
ratio = p_avg / b_avg                          # < 1.0 ⇒ ReJIT faster

Three rules follow in the same section:

  • Threshold filter. "Drop programs where min(baseline.run_cnt, post_rejit.run_cnt) < 100." The document justifies the cut-off with the corpus noise: "CV 29.6 % unfiltered → 17.7 % at ≥ 100", and the CV stays flat above that, so 100 keeps the most programs ("127 vs 90 programs at ≥ 10 K").
  • Geometric mean over retained programs, because these are ratios; wins/losses/ties are reported alongside, and bootstrap confidence intervals are taken over the per-program ratios.
  • Tail calls. A program entered through bpf_tail_call skips the prologue that updates stats.cnt, so bpftool shows zero runs for it. Its cost appears in the directly attached caller's ratio instead. Tetragon, Tracee, Cilium and the OTEL profiler all rely heavily on tail calls, so this matters.

Application throughput is measured with BPF statistics off, because the per-run timestamping that bpf_stats_enabled adds is itself overhead. The artifact guide asks for one run with statistics off for throughput and one with BPFREJIT_CORPUS_BPF_STATS=1 for BPF cost. That is why its results table reports two numbers per experiment.

Backend 1: bpfopt and the shim (speculative ReJIT)

The userspace path has three roles with strict boundaries, described in rejit/docs/design.md §1.7 and AGENTS.md:

  • The runner owns policy. It reads runner/config/passes/<pass>/default.yaml and turns it into an ordered list of shell commands.
  • The shim, libbpfrejit_shim.so, lives in the application process. It intercepts BPF syscalls, keeps a table of programs, maps, links and attachments, runs the commands with LD_PRELOAD removed from the child environment, and submits candidates through the stock BPF_PROG_LOAD. It does not know what any pass does.
  • bpfopt is a pure bytecode CLI: "no BPF syscalls, must never call libc::syscall(SYS_bpf, ...) — one named pass per invocation over raw struct bpf_insn[]".

The design rule is that a new optimization costs one new bpfopt pass plus one YAML file, with zero shim changes and zero kernel changes. Earlier versions of the project had a bpfrejit-daemon and a custom BPF_PROG_REJIT syscall in a forked kernel; AGENTS.md marks those designs as historical and says that the removed binaries stay removed.

How the shim sees every load

Most eBPF loaders, including libbpf, reach the kernel through the libc syscall() function, so defining a syscall symbol in a preloaded library intercepts them. The shim forwards everything that is not SYS_bpf, with two exceptions: it tracks close and close_range so that it knows when the application drops a file descriptor, and it records perf_event_open results because perf events are an attachment path:

/* Intercept syscall(2). */
long syscall(long number, ...) {
    /* ... */
    ensure_syms_resolved();
    va_list ap;
    va_start(ap, number);
    long a0 = va_arg(ap, long);
    /* ... a1 .. a5 ... */
    va_end(ap);

    if (!in_shim && number == SYS_close)
        return shim_close_observed_fd((int)a0);

    if (!in_shim && number == SYS_close_range)
        return shim_close_range((unsigned int)a0, (unsigned int)a1,
                                (unsigned int)a2);

    if (in_shim || number != SYS_bpf) {
        if (number == SYS_perf_event_open && !in_shim) {
            /* ... record the perf event, then forward ... */
    /* ... */
        switch (cmd) {
        case BPF_PROG_LOAD:
            pending_prog = capture_prog_load(attr, size);
            break;
        case BPF_MAP_CREATE:
            pending_map = capture_map_create(attr);
            break;
        case BPF_LINK_CREATE:
            pending_link = capture_link_create(attr, size);
            /* ... */
        case BPF_LINK_UPDATE:
            on_link_update(attr);
            break;
        case BPF_PROG_ATTACH:
            on_prog_attach(attr);
            break;
        case BPF_RAW_TRACEPOINT_OPEN:
            pending_raw_tp = capture_raw_tp_open(attr);
            /* ... */

The in_shim flag prevents recursion when the shim issues its own BPF calls. Three of the six applications (Tetragon, the Cilium agent and the OTEL profiler) are statically linked Go binaries that do not go through libc. The design notes describe a compile-time fallback for them, a vendored fork of golang.org/x/sys/unix that calls the same shim handler ABI (this chapter did not check which forks carry it). The shim README warns not to infer coverage from linkage alone and to check the runner configuration and recorded lifecycle instead.

The candidate loop

Inside an intercepted load, loadtime_optimize_prog_load() in bpfopt/shim/shim_loadtime.h runs each step, substitutes ${INPUT}, ${OUTPUT}, ${REPORT}, ${MAP_IDS} and similar variables into the command template, and checks the output with a real verifier load before going on:

        uint64_t elapsed_ms = 0;
        if (loadtime_run_shell(resolved, step_log, &elapsed_ms) != 0) {
            snprintf(err, err_sz, "loadtime bpfopt step %s failed; log=%s",
                     name[0] ? name : "<unnamed>", step_log);
            /* ... free ... */
            return -1;
        }
        struct stat nst;
        if (stat(nxt, &nst) != 0 || nst.st_size == 0) {
            snprintf(err, err_sz,
                     "loadtime bpfopt step %s produced no output bytecode; log=%s",
                     name[0] ? name : "<unnamed>", step_log);
            /* ... */
            return -1;
        }
        if (loadtime_probe_bytecode_acceptance(attr, attr_size, nxt, target_arg,
                                               map_ids, map_n, verifier_log) != 0) {
            log_line("loadtime verifier probe rejected candidate after step %s "
                     "errno=%d log=%s; passing original BPF_PROG_LOAD through",
                     name[0] ? name : "<unnamed>", errno, verifier_log);
            /* ... free ... */
            return 0;
        }

Notice the asymmetry. A bpfopt crash or empty output returns -1 and fails the load, following the "no fallback" rule, so a broken pass is visible. A verifier rejection returns 0 and lets the original program through, because rejection is a normal, safe outcome that the benchmark wants to count (the draft paper reports 2,299 of them).

The running-process path

Each shim instance also opens a Unix socket at /var/run/bpfrejit/shim-<pid>.sock that accepts newline-delimited JSON: list_progs, dump_state and execute_plan. For execute_plan, the shim runs the passes on programs it already tracks and then calls reload_and_reattach(), which uses whichever stock mechanism fits the attachment: BPF_LINK_UPDATE, link recreation, BPF_PROG_ATTACH replacement, perf-event replacement, raw tracepoint reopen, program-array updates, or XDP netlink. A partial replacement is reported as RELOAD_PARTIAL_ATTACH rather than as success (bpfopt/shim/README.md).

bpfopt is an LLVM round trip

The C++ bpfopt in bpfopt/llvm/ is built on llvmbpf from Chapter 16. Every pass lifts raw kernel bytecode to LLVM IR with llvmbpf in kernel-compatible mode, optionally rewrites the IR, runs the O3 pipeline, lowers it with LLVM's own BPF backend, and extracts the relocated .text section as the new instruction stream:

std::vector<uint8_t> emit_bpf_object(llvm::Module &module)
{
	auto machine = create_bpf_target_machine(llvm::CodeGenOptLevel::Aggressive);
#if LLVM_VERSION_MAJOR >= 19
	module.setTargetTriple(llvm::Triple("bpfel"));
#else
	module.setTargetTriple("bpfel");
#endif
	module.setDataLayout(machine->createDataLayout());
	optimize_module(module, *machine);   /* buildPerModuleDefaultPipeline(O3) */
	/* ... addPassesToEmitFile(..., ObjectFile); return the bytes ... */
}

llvm::orc::ThreadSafeModule generate_llvm_module(const std::vector<uint8_t> &input)
{
	if (input.empty() || input.size() % INSN_SIZE != 0) {
		throw std::runtime_error(
			"input bytecode length must be a non-empty multiple of 8");
	}
	bpftime::llvmbpf_vm vm;
	if (vm.load_code(input.data(), input.size()) < 0) {
		throw std::runtime_error("llvmbpf load_code failed: " +
					 vm.get_error_message());
	}
	vm.set_kernel_compatible_mode(true);

	bpftime::llvm_bpf_jit_context context(vm);
	return expected_or_throw(
		context.generateModule(helper_symbols(input), {}, false));
}

std::vector<uint8_t> run_llvm_roundtrip(const std::vector<uint8_t> &input,
					const KinsnTargetMap *kinsn_targets)
{
	auto module = generate_llvm_module(input);
	return module.withModuleDo([&](llvm::Module &module) {
		auto machine = create_bpf_target_machine(
			llvm::CodeGenOptLevel::Aggressive);
		promote_register_allocas(module, *machine);
		return extract_relocated_text(emit_bpf_object(module), input,
					      kinsn_targets);
	});
}

A consequence spelled out in bpfopt/llvm/README.md: "noop is also an LLVM O3 roundtrip and is not byte-preserving." Even the "do nothing" pass re-optimizes the program, which is presumably why most policy groups start with noop: a noop-only run separates the effect of the LLVM round trip from that of the pass. The README is also strict about what happens after code generation: extraction "must not synthesize verifier proofs, insert bounds checks, delete instructions, or rewrite memory-address forms after backend codegen." If LLVM's output fails verification, that is a real failure to be fixed in the lift or lower step. map_inline is the main IR-level pass: with a snapshot of map values and a hint naming a map entry, it replaces a lookup with the value. The README reports that for Katran's balancer_ingress, 16 lookup sites are inlined and the program still passes verification and BPF_PROG_TEST_RUN.

Backend 2: kinsn, verified native operations (BPF-Ext)

Bytecode rewriting can make a program shorter, but it cannot make the JIT emit rol, cmov, bextr or movbe, because eBPF has no instruction that maps to them. kinsn ("kernel instruction"; earlier names in the repo are Kops, KOperation and kop) lets a kernel module add such an operation. The archived design doc gives the motivation as a list of idioms the ISA cannot express: rotate, conditional select, bitfield extract, load plus byte swap, arm64 load/store pairs, bulk copy, prefetch, and arm64 conditional-compare chains.

One operation, two forms

The central idea, in the words of the camera-ready abstract: "a new operation can be verified through an equivalent vanilla eBPF form, while the CPU runs its native code. The verifier checks the eBPF form but never sees the native code, so the code that generates it is the only code each operation adds to the TCB." Each operation is described by a struct bpf_kinsn descriptor with two callbacks:

  • instantiate_insn(payload, insn_buf) writes the proof sequence: ordinary eBPF instructions that compute the same result. The verifier analyses these, so it derives the result's bounds and the memory effects exactly as if the program had contained them.
  • emit_x86() / emit_arm64() write the native emit: the machine code that runs instead.

In the paper prototype, a kinsn site in bytecode is two instructions: a sidecar pseudo-instruction (BPF_PSEUDO_KINSN_SIDECAR) carrying the packed operands, followed by a CALL with src_reg = BPF_PSEUDO_KINSN_CALL whose immediate is the BTF id of a kfunc stub in the module. The verifier temporarily replaces the pair with the proof sequence, verifies, and restores the pair for the JIT, which dispatches to the module's emitter (kinsn/docs/archive/kinsn-design.md). The kernel side lives in eunomia-bpf/linux, branch kinsn-only; the design hub sizes that diff at "10 files, +869 / -101 LOC".

A real module: rotate on x86-64

The x86 modules live in kinsn/module/x86/ (15 C files) and the arm64 ones in kinsn/module/arm64/ (11). The rotate module shows all the parts. The kfuncs themselves are empty stubs; they exist so that the operation has a BTF id that programs can reference:

__bpf_kfunc_start_defs();
__bpf_kfunc void bpf_x86_roll(void) {}
__bpf_kfunc void bpf_x86_rolq(void) {}
__bpf_kfunc void bpf_x86_rorxl(void) {}
__bpf_kfunc_end_defs();

The two forms of a rotate-left by an immediate are below. Look at the proof sequence first: it does not use the obvious shl/shr/or with a scratch register. Instead it rotates by one bit, shift times, and keeps the bit that falls off the top in control flow: if the value is negative (top bit set), shift left and OR in a 1, otherwise just shift left. That is slow, but it never runs. Its job is to be a sequence the verifier can analyse that touches no register other than dst, so it matches the register footprint of the single native instruction.

/* Keep the shifted-out bit in control flow, not a scratch register. */
static int instantiate_rotate_leaf(u8 width, u8 dst_reg, u8 src_reg,
				   u8 shift, struct bpf_insn *insn_buf)
{
	int cnt = 0;
	int i;

	insn_buf[cnt++] = rotate_mov(width, dst_reg, src_reg);
	for (i = 0; i < shift; i++) {
		insn_buf[cnt++] = width == 64 ?
			BPF_JMP_IMM(BPF_JSLT, dst_reg, 0, 2) :
			BPF_JMP32_IMM(BPF_JSLT, dst_reg, 0, 2);
		insn_buf[cnt++] = rotate_alu_imm(width, BPF_LSH, dst_reg, 1);
		insn_buf[cnt++] = BPF_JMP_A(2);
		insn_buf[cnt++] = rotate_alu_imm(width, BPF_LSH, dst_reg, 1);
		insn_buf[cnt++] = rotate_alu_imm(width, BPF_OR, dst_reg, 1);
	}
	return cnt;
}
static void emit_rol_imm(u8 *buf, u32 *len, bool is64, u8 dst_reg, u8 imm8)
{
	kinsn_emit_rex_rr(buf, len, is64, 0, dst_reg);
	kinsn_emit_u8(buf, len, 0xC1);
	kinsn_emit_u8(buf, len, 0xC0 | kinsn_x86_code(dst_reg));
	kinsn_emit_u8(buf, len, imm8);
}
/* ... emit_rol_imm_x86() decodes the payload, maps the BPF register to the
 * x86 register the JIT assigned (kinsn_x86_reg_for_prog), then: */
	emit_rol_imm(buf, &len, width == 64, rot.dst_reg, rot.shift);

	return kinsn_emit_finish(image, off, emit, buf, len);

0xC1 /0 ib is the x86 encoding of ROL r/m, imm8, so the native emit is four bytes. Contrast max_insn_cnt = 10270: that bound covers the worst case of the register-count variant, which builds a binary tree of tests on each bit of the count register (instantiate_rotate_tree) with a bit-by-bit leaf at every node. Proof sequences can be enormous because the verifier processes them once per load; the CPU never sees them.

Proofs and selection

The emitter is trusted, so the project proves it. kinsn/lean/README.md states the theorem shape: for each operation with a specification spec : BitVec 64 → BitVec 64, executing the BPF proof sequence, the ARM64 sequence and the x86 sequence all yield spec of the source register, with a write-set bound on scratch registers. A refinement theorem then says that splicing the native block in place of the BPF block "preserves the whole machine state outside the scratch registers", instantiated at the real JIT register maps of arch/arm64/net/bpf_jit_comp.c and arch/x86/net/bpf_jit_comp.c. The build "fails if the axiom audit finds anything beyond propext, Classical.choice, Quot.sound". Note the scope: these are models of instruction semantics in Lean, not a proof about the C emitter's byte output.

Choosing where to use an operation happens in userspace, in two places. bpfopt's kinsn passes match patterns in lifted bytecode, guided by a target JSON listing which kinsn modules the running kernel has (kinsn/kinsnprober/ produces it). The LLVM fork bpf-kinsn-llvm selects them at compile time instead, from LLVM's canonical IR and machine instructions; llvm-backend/README.md describes the intended pipeline: collect candidates, check legality, score profitability, then let BPFAsmPrinter emit the sidecar plus a named kfunc call. The micro README records one current limitation: "the selector does not select kinsn inside local .text subprograms", because proof sequences use verifier stack and the verifier adds caller and callee stack depth against the 512-byte limit.

Not every idiom earned an operation. The design hub keeps a "won't do / deferred" table with corpus evidence: POPCNT has 0 sites because clang already expands __builtin_popcount; FPU SIMD on x86 loses because "kernel_fpu_begin/end XSAVE/XRSTOR ~200-800 cycles" exceed the gain for copies of at most 128 bytes; RDTSC is "not suitable for a transparent rewrite of bpf_ktime_get_ns()". The stated rule is that a new kinsn needs hundreds of corpus sites, a measurable win larger than the I-cache and re-verification cost, and a verifier-friendly proof sequence.

From prototype to upstream RFC

The prototype adds UAPI (two pseudo-instruction encodings). The upstream proposal is a redesign. On 2026-10-05 the first author posted [RFC PATCH bpf-next 0/7] bpf: Inline kfuncs that have a BPF body. There a kfunc set may give a kfunc a struct bpf_kfunc_body (BPF instructions plus an optional emit callback), programs use normal kfunc calls ("There is no new instruction encoding and no UAPI change"), and the verifier checks each call through its body. The RFC adds seven kfuncs under CONFIG_BPF_INSN_KFUNCS (bpf_rol64, bpf_select64, bpf_extract64, bpf_load_be64, bpf_prefetch, bpf_copy16, bpf_lea64), x86 emitters for five, and no arm64 native code yet (kinsn/docs/design.md).

The cover letter is candid about policy sensitivity: on one application, "21 chosen call sites gave 7.3% more throughput, but all 62 gave 0.5% less". Alexei Starovoitov's reply (2026-10-17) accepted the verifier approach ("yes" to replacing calls with bodies before analysis and restoring them afterwards) but answered the emit-callback question with "Copy only": keep the C kfunc as the only implementation, use KF_FASTCALL, and have the JIT copy the compiled kfunc. That would remove "bodies, emit, capture of __k constants, … register renaming, body table in btf". Where the RFC goes next is open; the repo notes that "Historical prototype measurements do not evaluate the October RFC."

Microbenchmarks

micro/ isolates "pure-bytecode execution, helpers, maps, packet parsing, branch behavior, and architecture-sensitive lowering under BPF_PROG_TEST_RUN" (README). The artifact guide counts 27 programs, "12 modeled on production programs and 15 synthetic, plus the simple and simple_packet baselines", in micro/programs/*.bpf.c. Names such as cilium_ct_nat_tuple_rewrite, katran_lb_consistent_hash_select and tetragon_process_event_arg_filter show where the production-modeled ones come from. The suite manifest micro/config/micro_pure_jit.yaml lists six runtimes: native, llvmbpf, kernel, kernel_rejit, native_kernel and native_proof, which is how the repository measures the JIT-versus-native gap in the first place.

Each program is written so that clang emits a specific idiom. The SipHash benchmark relies on a rotate helper that clang compiles to "the clean 4-insn rotate pattern (mov+lsh+rsh+or) without masking", which is exactly what the rotate kinsn targets:

static __always_inline u64 micro_rotl64(u64 value, u32 shift)
{
    shift &= 63U;
    if (shift == 0) {
        return value;
    }
    return (value << shift) | (value >> (64U - shift));
}
#define SIPROUND(v0, v1, v2, v3)                \
    do {                                        \
        (v0) += (v1);                           \
        (v1) = micro_rotl64((v1), 13U);         \
        (v1) ^= (v0);                           \
        (v0) = micro_rotl64((v0), 32U);         \
        (v2) += (v3);                           \
        (v3) = micro_rotl64((v3), 16U);         \
        (v3) ^= (v2);                           \
        (v0) += (v3);                           \
        (v3) = micro_rotl64((v3), 21U);         \
        (v3) ^= (v0);                           \
        (v2) += (v1);                           \
        (v1) = micro_rotl64((v1), 17U);         \
        (v1) ^= (v2);                           \
        (v2) = micro_rotl64((v2), 32U);         \
    } while (0)

Each program ships a .md file with the gcc native assembly and the original kernel JIT output side by side. For SipHash the difference is visible at a glance: native code loads each input word with one mov r9, QWORD PTR [rcx+0x8], while the kernel JIT output starts with a long run of movzx … BYTE PTR [r15+0x8], shl, or, because micro_read_u64_le reads bytes one at a time and the JIT cannot merge them. That is the opportunity wide_mem and the movq kinsn exist for.

Backend 3: bpfperf, branch profiles per BPF instruction

branch_flip reorders branch layout using real taken/not-taken counts, an old idea from profile-guided compilers. For eBPF the hard part is the profile: hardware counters see addresses in the JIT image, while the pass works on BPF instruction indices. bpfperf solves that mapping. It was split out of bpf-benchmark into eunomia-bpf/bpfperf on 2026-05-08 with one commit ("Initial archive of bpfprof + kernel-sys from bpf-benchmark @ HEAD") and the note "Source archived as-is. Not actively maintained or compiled here." (GitHub does not mark it archived.) A newer version still lives in bpf-benchmark/bpfperf/ and has changed design, as described below.

The archived design: an fexit sidecar reading LBR

Intel's Last Branch Record (LBR) is a small ring of recent (from, to) branch addresses kept by the CPU. Since Linux 5.16, BPF programs can read it with the helper bpf_get_branch_snapshot(), provided a perf event has LBR enabled on that CPU. bpfprof uses both halves. First it opens a perf event on every CPU that keeps LBR recording kernel branches:

            let mut attr = kernel_sys::perf_event_attr {
                type_: kernel_sys::PERF_TYPE_HARDWARE,
                size: std::mem::size_of::<kernel_sys::perf_event_attr>() as u32,
                config: kernel_sys::PERF_COUNT_HW_CPU_CYCLES as u64,
                sample_type: kernel_sys::PERF_SAMPLE_BRANCH_STACK as u64,
                branch_sample_type: (kernel_sys::PERF_SAMPLE_BRANCH_KERNEL
                    | kernel_sys::PERF_SAMPLE_BRANCH_ANY)
                    as u64,
                ..Default::default()
            };
            attr.set_disabled(1);
            attr.set_exclude_user(1);
            attr.set_exclude_hv(1);
            attr.__bindgen_anon_1.sample_period = 1;
            let fd = kernel_sys::perf_event_open(&mut attr, -1, cpu, -1, 0)
                .with_context(|| format!("open kernel LBR perf event on CPU {cpu}"))?;

Then it attaches a tiny fexit program to the target BPF program itself (fentry/fexit can attach to BPF programs, not only kernel functions; see Chapter 05). Every time the target returns, the sidecar snapshots LBR into a ring buffer record. The sidecar is not compiled from C; it is 19 hand-assembled instructions:

fn branch_snapshot_sidecar_insns(ringbuf_fd: BorrowedFd<'_>, prog_id: u32) -> Vec<bpf_insn> {
    let mut insns = Vec::with_capacity(19);
    insns.extend(ld_map_fd(BPF_REG_1, ringbuf_fd.as_raw_fd()));
    insns.push(mov64_imm(BPF_REG_2, BRANCH_SNAPSHOT_EVENT_SIZE as i32));
    insns.push(mov64_imm(BPF_REG_3, 0));
    insns.push(call_helper(BPF_FUNC_ringbuf_reserve));
    insns.push(jmp_imm(BPF_JEQ, BPF_REG_0, 0, 12));
    insns.push(mov64_reg(BPF_REG_6, BPF_REG_0));
    insns.push(st_mem_w(BPF_REG_6, 0, prog_id as i32));
    insns.push(mov64_reg(BPF_REG_1, BPF_REG_6));
    insns.push(add64_imm(
        BPF_REG_1,
        BRANCH_SNAPSHOT_EVENT_HEADER_SIZE as i32,
    ));
    insns.push(mov64_imm(
        BPF_REG_2,
        (BRANCH_SNAPSHOT_MAX_ENTRIES * BRANCH_SNAPSHOT_ENTRY_SIZE) as i32,
    ));
    insns.push(mov64_imm(BPF_REG_3, 0));
    insns.push(call_helper(BPF_FUNC_GET_BRANCH_SNAPSHOT));
    insns.push(stx_mem_dw(BPF_REG_6, BPF_REG_0, 8));
    insns.push(mov64_reg(BPF_REG_1, BPF_REG_6));
    insns.push(mov64_imm(BPF_REG_2, 0));
    insns.push(call_helper(BPF_FUNC_ringbuf_submit));
    insns.push(mov64_imm(BPF_REG_0, 0));
    insns.push(exit_insn());
    insns
}

It is loaded as BPF_PROG_TYPE_TRACING with expected_attach_type: BPF_TRACE_FEXIT, attach_prog_fd set to the target program and attach_btf_id set to the target's function BTF id, then attached with bpf_link_create (attach_branch_snapshot_sidecar in the same file). In userspace, bpfprof reads each record, looks up every (from, to) pair in the target's JIT image using prog_jited_line_info and the translated instructions from prog_xlated_insns, and accumulates per conditional-branch site the fields the AGENTS.md contract requires: branch_count, branch_misses, miss_rate, taken, not_taken.

The in-tree successor

The version in bpf-benchmark/bpfperf/crates/bpfprof/src/main.rs (4,564 lines) no longer contains bpf_get_branch_snapshot at all. It samples PERF_COUNT_HW_BRANCH_INSTRUCTIONS with PERF_SAMPLE_BRANCH_STACK directly, with a default period of 200,000, and explains why in a comment: "BPF JIT execution is a small fraction of all kernel branches. A million branch period can therefore produce a valid global LBR stream while yielding no BPF-mapped samples". An optional --precise-branch-direction mode uses precise retired-branch events "instead of LBR edges", and checks for an Arrow Lake core PMU. It decodes x86 conditional branches in the JIT image itself, maps translated PCs back to the shim's dumped source bytecode with a longest-common-subsequence alignment (the kernel rewrites some instructions during verification), and handles tail-call edges. Like the rest of the repo it is fail-fast: "Missing JIT metadata, unavailable PMU events, or perf ring loss are hard errors." The shared design doc calls it "External per-site PMU collection for profile-guided work".

Building and running

The artifact guide is explicit about cost: a first kernel and runtime-image build takes "1.5–3 hours" and "25–40 GB", and the full suites on both architectures take "more than a day; ARM64 needs AWS". Runs need KVM, Docker, vng and passwordless sudo -n, and the guide recommends a disposable machine. None of the following was run for this chapter.

git clone https://github.com/eunomia-bpf/bpf-benchmark.git
cd bpf-benchmark
git submodule update --init --recursive -- \
    vendor/linux-framework llvm-backend/llvm vendor/libbpf vendor/llvmbpf \
    vendor/repos/bcc vendor/repos/bpftrace vendor/repos/cilium \
    vendor/repos/cilium-ebpf vendor/repos/katran \
    vendor/repos/opentelemetry-ebpf-profiler vendor/repos/tetragon \
    vendor/repos/tracee

(cd kinsn/lean && lake exe cache get && lake build)   # the paper's proofs
make -C kinsn/paper/atc26                             # the paper's numbers and figures

Do not run a bare git submodule update --init --recursive: four submodules are private author repositories and fail without access. The two commands at the end need no VM. The Lean build checks the proofs; make -C kinsn/paper/atc26 regenerates the paper's numbers from shipped raw data and checks them against the camera-ready text. With a KVM host:

make check                                   # builds the runtime image and runs the tests

# Smallest end-to-end run: one application, one sample.
BPFREJIT_CORPUS_APPS=katran SAMPLES=1 WORKLOAD_DURATION=10 TIMEOUT=3000 make corpus

# All six applications.
SAMPLES=1 WORKLOAD_DURATION=10 TIMEOUT=7200 make corpus

Other knobs from the README and AGENTS.md: make micro BENCH="simple bitcount", make micro SAMPLES=1 WARMUPS=0 INNER_REPEAT=10, BPFREJIT_BENCH_PASSES=kinsn_all_prefetch to override the pass list, KEEP_WORKDIRS=1 to keep failure artifacts, and PLATFORM=aws ARCH=arm64 make corpus for Graviton. The AWS cost cap in AGENTS.md forbids instance types above medium.

Benefits and limitations

Benefits

Safety stays with the stock verifier: every candidate goes through BPF_PROG_LOAD, and a rejection just loads the original. Applications are unmodified and use their own loaders. The bytecode path needs no kernel changes. kinsn adds native instructions while keeping the per-operation trusted code to an emitter, backed by Lean proofs of the instruction semantics. Results are raw and reproducible from documented commands, and the integrity rules make the harness usable as an oracle for untrusted agents.

Limitations

Gains are modest and policy-sensitive: 7–12% on whole applications, some configurations slower, branch_flip not stable. The kinsn prototype needs a patched kernel, and the upstream RFC is a different design whose direction a maintainer has questioned. Correctness of a rewrite is not checked; only safety is (compare Chapter 18). The harness is heavy (hours, tens of GB). The "benchmark" has no frozen task set or hidden evaluator yet; the draft lists those as still needed.

Safety is not correctness

The design doc says it directly (Insight 3): the verifier guarantees the kernel is not harmed, but "If a pass or orchestration script has a bug, program behavior may change, but kernel safety is not affected". A map_inline that inlines a value which later changes would produce a wrong but safe program. The benchmark leans on workload checks and "hidden correctness checks" against this; the general problem is the subject of Chapter 18.

Related work

  • K2 (SIGCOMM '21) synthesizes faster equivalent BPF with stochastic search and an SMT equivalence checker, offline and single-version. Merlin (ASPLOS '24) optimizes at the LLVM IR and bytecode tiers before loading. Both are cited in the draft as baselines; neither can emit instructions outside the eBPF vocabulary, which is what kinsn adds.
  • Morpheus (ASPLOS '22) is the closest prior work to speculative ReJIT: runtime, guard-protected specialization of eBPF and DPDK data planes, reloaded through the verifier. rejit/docs/design.md says reviewers would ask "isn't this Morpheus?" and names the differences: general eBPF rather than match-action data planes, raw bytecode via an LD_PRELOAD shim rather than LLVM IR inside a framework, and PMU and run-statistics signals.
  • Jitterbug (OSDI '20) verifies the kernel's BPF JITs. kinsn's soundness argument is a small JIT-correctness obligation per operation, handled with Lean instead.
  • Kernel work on kfunc inlining: Leon Hwang's bitops kfuncs, Eduard Zingerman's inlinable kfuncs and Puranjay Mohan's iterator inlining are cited in the RFC as the lines it combines.
  • In this curriculum: llvmbpf (Chapter 16) is the lifter inside bpfopt; bpfix (Chapter 17) uses LLMs on verifier errors; the correctness verifier (Chapter 18) targets the gap left by "safety ≠ correctness"; ActPlane (Chapter 24) is cited as the agent-policy enforcement.

Check your understanding

Q1. In the load-time path, the shim runs a bpfopt step and the stock verifier rejects the candidate. What happens?

shim_loadtime.h logs "verifier probe rejected candidate after step %s … passing original BPF_PROG_LOAD through" and returns 0. Only a failure of bpfopt itself fails the load on purpose.

Q2. Why does the x86 rotate module's proof sequence rotate one bit at a time with conditional jumps instead of using lsh, rsh and or?

The comment reads "Keep the shifted-out bit in control flow, not a scratch register." The proof sequence's cost is verifier time only.

Q3. Which programs does the analysis drop before computing the per-program geomean?

rejit/docs/evaluation.md §5.2: drop when min(baseline.run_cnt, post_rejit.run_cnt) < 100. Dropping slow programs would be exactly the filtering the integrity rules forbid. Tail-called programs drop out only because they report zero runs.

Q4. What does the archived bpfperf attach to collect branch records?

attach_branch_snapshot_sidecar loads a tracing program with BPF_TRACE_FEXIT and attach_prog_fd = the target. The in-tree successor switched to perf branch-stack sampling.

Q5. The arXiv preprint reports 2.358× for whole-program native Cilium; the camera-ready reports 19%. Why?

Documented in corpus/results/cilium_x86_config_parity_counterbalanced_20261010/SUMMARY.md.

Q6. Where is the LLM agent's main action surface in the repository?

AGENTS.md: the driver and workloads are frozen; "Pass YAML under runner/config/passes/ is policy, not a frozen launcher — change it freely"; summaries are forbidden in framework code.
