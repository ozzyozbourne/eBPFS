Chapter 02

The eBPF Instruction Set and Virtual Machine

What does an eBPF program look like once the C compiler is done with it? This chapter covers the machine those bytes target: eleven 64-bit registers, a fixed 8-byte instruction format, a 512-byte stack, a calling convention built to match real CPUs, and two ways of executing it: an interpreter in kernel/bpf/core.c and a JIT compiler per architecture. Since October 2024 the instruction set has also been an IETF standard, RFC 9669.

Prerequisites: C, basic assembly, Chapter 01Sources: Linux kernel/bpf, arch/x86/net, RFC 9669~45 min

Why this matters

In Chapter 01 you saw that classic BPF (cBPF) was a tiny packet-filter machine with two 32-bit registers (an accumulator A and an index register X), a scratch memory area, and forward-only jumps. That was enough for tcpdump expressions, but it was a poor fit for what the kernel wanted from it after 2013: tracing filters that walk kernel data structures, network functions that rewrite packets, security policies, and later whole schedulers. Those programs need 64-bit pointers, more registers, a way to call kernel functions without paying for argument shuffling, and code generation good enough to run at line rate.

Extended BPF (eBPF) was designed as an answer to that. The kernel documentation states the main design goal in one line: "eBPF is designed to be JITed with one to one mapping, which can also open up the possibility for GCC/LLVM compilers to generate optimized eBPF code through an eBPF backend that performs almost as fast as natively compiled code" (classic_vs_extended.rst). Every design choice in this chapter follows from that goal. There are ten general registers because 64-bit CPUs have enough hardware registers to hold them. There are five argument registers because x86-64 passes six arguments in registers and other 64-bit ABIs pass more. The format is two-operand because x86 is two-operand. Instructions are 8 bytes because that is easy to decode and easy to verify.

Knowing the ISA pays off in practice. Verifier error messages (Chapter 03) print instruction numbers and register states such as R1 type=scalar expected=fp. To read them you have to know what the registers are for. llvm-objdump -d and bpftool prog dump xlated show you this instruction set. Userspace runtimes such as bpftime and llvmbpf (Chapter 14, Chapter 16) implement this same instruction set outside the kernel, so the details here apply to them too.

Key idea

eBPF is a small 64-bit RISC instruction set: 11 registers, 8-byte instructions with fields opcode | dst | src | off | imm, and a single 16-byte exception (lddw). Its register and calling conventions were chosen so a JIT can translate each eBPF instruction to one or a few native instructions with a fixed register mapping. Safety is not part of the ISA. It comes from the verifier, which checks every program before the interpreter or JIT ever sees it.

The register file

The kernel's ABI document (abi.rst, "BPF ABI Recommended Conventions and Guidelines v1.0") puts the register model in one sentence: "BPF has 10 general purpose registers and a read-only frame pointer register, all of which are 64-bits wide." They are numbered 0–10 and appear in the UAPI header as an enum:

/* Register numbers */
enum {
	BPF_REG_0 = 0,
	BPF_REG_1,
	BPF_REG_2,
	BPF_REG_3,
	BPF_REG_4,
	BPF_REG_5,
	BPF_REG_6,
	BPF_REG_7,
	BPF_REG_8,
	BPF_REG_9,
	BPF_REG_10,
	__MAX_BPF_REG,
};

/* BPF has 10 general purpose 64-bit registers and stack frame. */
#define MAX_BPF_REG	__MAX_BPF_REG

struct bpf_insn {
	__u8	code;		/* opcode */
	__u8	dst_reg:4;	/* dest register */
	__u8	src_reg:4;	/* source register */
	__s16	off;		/* signed offset */
	__s32	imm;		/* signed immediate constant */
};

What each register is for

RegisterConvention (abi.rst)What you see in practice
R0"return value from function calls, and exit value for BPF programs"Helper results such as the pointer returned by bpf_map_lookup_elem; the XDP verdict before exit.
R1–R5"arguments for function calls"On entry, R1 holds the context pointer (struct xdp_md *, struct pt_regs *, …). Clobbered by every call.
R6–R9"callee saved registers that function calls will preserve"LLVM moves the context into R6 or R7 right away so it survives helper calls.
R10"read-only frame pointer to access stack"All stack addresses are R10 - n. Writing to it is rejected with frame pointer is read only (from kernel/bpf/verifier.c).

Every register is 64 bits wide. The 32-bit ALU and JMP32 classes operate on the lower half of each register. LLVM prints that half as w0…w9. The kernel docs spell out the important rule: "All eBPF registers are 64-bit with 32-bit lower subregisters that zero-extend into 64-bit if they are being written to. That behavior maps directly to x86_64 and arm64 subregister definition, but makes other JITs more difficult." So w1 = w1 - w2 leaves the upper 32 bits of r1 zero. You will see below why that saves instructions.

The calling convention

eBPF has one calling convention for every call: helpers (fixed kernel functions identified by number), kfuncs (kernel functions identified by BTF ID, Chapter 04) and BPF-to-BPF calls between functions in the same program. The caller puts up to five arguments in R1–R5 and executes call. The result comes back in R0, and only R6–R10 are guaranteed to survive. The verifier enforces this: after a call it marks R1–R5 as unreadable, so a program that reads R1 after a call without reloading it is rejected. The classic_vs_extended document gives exactly this program as an example of an invalid one:

bpf_mov R1, 1
bpf_call foo
bpf_mov R0, R1
bpf_exit

Why five arguments? The same document explains: "Since 64-bit CPUs are passing arguments to functions via registers the number of args from eBPF program to in-kernel function is restricted to 5 and one register is used to accept return value from an in-kernel function. Natively, x86_64 passes first 6 arguments in registers, aarch64/sparcv9/mips64 have 7 - 8 registers for arguments." If BPF's argument registers are the hardware's argument registers, a JIT can compile call to a single native call with no moves before or after it. The interpreter shows the same contract in C:

	/* CALL */
	JMP_CALL:
		/* Function call scratches BPF_R1-BPF_R5 registers,
		 * preserves BPF_R6-BPF_R9, and stores return value
		 * into BPF_R0.
		 */
		BPF_R0 = (__bpf_call_base + insn->imm)(BPF_R1, BPF_R2, BPF_R3,
						       BPF_R4, BPF_R5);
		CONT;
/* ... */
	JMP_EXIT:
		return BPF_R0;

Two details are worth knowing. First, the program as a whole is called with one argument, the context pointer in R1 ("For practical reasons all eBPF programs have only one argument 'ctx' which is already placed into R1"). Second, the five-argument limit is no longer absolute in very recent mainline. v7.3 added a hidden BPF_REG_PARAMS pseudo-register to include/linux/filter.h, together with helpers such as is_stack_arg_ldx(), for arguments passed on the stack. The x86 JIT notes that "x86-64 uses R9 for both private stack frame pointer and arg6". Treat this as new, moving work. Everything RFC 9669 and older kernels define uses five register arguments.

The 512-byte stack

Each BPF function gets a stack frame of at most 512 bytes, addressed downward from R10:

/* BPF program can access up to 512 bytes of stack space. */
#define MAX_BPF_STACK	512
/*
 * Stack budget of a program on a JIT that lays out frames of that size.
 * The interpreter and JITs without such support keep MAX_BPF_STACK.
 */
#define MAX_BPF_STACK_JIT	2048

The first definition has been there since eBPF began. The second appeared in v7.4-rc1 (it is not in v7.3), and only JITs that implement bpf_jit_supports_large_stack() get it. x86-64 does. For portable programs, and for anything you write against a released distribution kernel today, plan for 512 bytes. The limit covers the whole call chain, not just one function. When the verifier adds up the frames of nested BPF-to-BPF calls and the total is too big, it fails with combined stack size of %d calls is %d. Too large. The stack is so small because BPF programs run on the kernel stack of whatever context triggered them, such as an interrupt, a syscall or a softirq, and kernel stacks are only a few pages. A small fixed bound lets the verifier prove that a program cannot overflow it.

Two consequences show up in everyday code. Large structs cannot live on the stack; you put them in a per-CPU array map (Chapter 04) instead. And every stack slot must be written before it is read, because the verifier tracks stack slots as carefully as registers.

Instruction encoding

Every eBPF instruction is 64 bits. RFC 9669 §3 calls this the basic instruction encoding; one instruction, lddw, uses a wide 128-bit encoding. The layout is the struct bpf_insn shown above: an 8-bit opcode, two 4-bit register numbers, a signed 16-bit offset and a signed 32-bit immediate.

The fields mean slightly different things in different instructions, but the pattern is consistent:

  • opcode: the low 3 bits are always the class. How the remaining 5 bits are split depends on the class (see the two layouts in Figure 02.2).
  • dst_reg / src_reg: register numbers 0–10. In lddw and call, src_reg is reused as a sub-type selector.
  • off: the memory offset for loads and stores, and the jump distance for conditional jumps. Jump distances count 8-byte instruction slots relative to the next instruction. In SDIV, SMOD and MOVSX it is a modifier (signed division, sign-extension width).
  • imm: a 32-bit constant. For calls it is the helper ID or relative target. For atomics it encodes the operation.

RFC 9669 requires that unused fields be zero ("Unused fields SHALL be cleared to zero"), and the Linux verifier rejects instructions with stray bits in reserved fields. That keeps the encoding space free for later extensions; the atomics section shows how it was used.

The wide instruction: lddw

A 32-bit immediate cannot hold a 64-bit pointer or constant, so eBPF has exactly one 16-byte instruction, {IMM, DW, LD}, opcode 0x18. In the second 8-byte slot the opcode, registers and offset are zero, and the remaining 32 bits (next_imm) supply the upper half. LLVM prints it as r1 = 0x... ll. The src_reg field selects what the immediate means:

src_regRFC 9669 pseudocodeLinux name / use
0x0dst = (next_imm << 32) | immplain 64-bit constant
0x1dst = map_by_fd(imm)BPF_PSEUDO_MAP_FD: libbpf patches in the map's file descriptor; the kernel swaps it for a struct bpf_map *
0x2dst = map_val(map_by_fd(imm)) + next_immpointer into an array map's value; global variables in .data/.bss use this
0x3dst = var_addr(imm)platform variable (on Linux: a kernel variable by BTF ID)
0x4dst = code_addr(imm)address of a BPF function (callbacks)

So a map reference in your source becomes a lddw with a relocation. The loader rewrites it, and the verifier turns it into a typed pointer (CONST_PTR_TO_MAP). This is how the VM supports maps without knowing anything about them at the ISA level.

Instruction classes

The three class bits split the instruction set into eight groups. The values come from classic BPF: eBPF kept cBPF's numbering where it could and reused cBPF's RET and MISC slots for JMP32 and ALU64.

ALU and ALU64

The arithmetic classes share one table of operation codes (upper 4 bits): ADD 0x0, SUB 0x1, MUL 0x2, DIV 0x3, OR 0x4, AND 0x5, LSH 0x6, RSH 0x7, NEG 0x8, MOD 0x9, XOR 0xa, MOV 0xb, ARSH 0xc (arithmetic shift) and END 0xd (byte swap). Bit 3 (s) chooses between the immediate (K) and src_reg (X) as the source operand. So 0x07 is ADD|K|ALU64 (dst += imm) and 0x0f is ADD|X|ALU64 (dst += src).

Several semantic choices exist so that every operation is total, with no traps and no undefined behaviour:

  • Division by zero does not fault: "If BPF program execution would result in division by zero, the destination register is instead set to zero." Modulo by zero leaves the destination unchanged (for ALU the upper 32 bits are zeroed).
  • LLONG_MIN / -1 yields LLONG_MIN instead of trapping as it would on x86.
  • Shift amounts are masked to 63 (64-bit) or 31 (32-bit). The interpreter applies the mask explicitly to avoid undefined behaviour in C. JITs rely on the hardware doing the same thing.
  • Immediates are sign-extended from 32 to 64 bits for ALU64, so r2 += -4 really subtracts 4.

Since ISA v4 (Linux 6.6) the off field works as a modifier for three operations: SDIV/SMOD (off = 1, signed division and modulo) and MOVSX (off = 8/16/32, move with sign extension). END converts to little- or big-endian under ALU, and does an unconditional bswap under ALU64.

JMP and JMP32

Jumps compare dst against src or imm and add off to the program counter if the condition holds. The codes are JA 0x0, JEQ 0x1, JGT 0x2, JGE 0x3, JSET 0x4 (dst & src), JNE 0x5, JSGT 0x6, JSGE 0x7, CALL 0x8, EXIT 0x9, JLT 0xa, JLE 0xb, JSLT 0xc, JSLE 0xd. The S variants compare signed. eBPF dropped cBPF's two-target jt/jf jumps in favour of "jump if true, else fall through", which is how real CPUs branch.

JMP32 compares only the low 32 bits. It was added (ISA v3) so 32-bit code does not need extra zero-extension instructions before each comparison. One quirk: {JA, K, JMP32} is the "long jump" gotol, which takes its 32-bit distance from imm instead of the 16-bit off. It is needed when a branch target is more than 32,767 instructions away.

CALL and EXIT only exist in the JMP class with K as the source. For a call, src_reg picks the target type:

src_regRFC 9669Linux constantimm holds
0call helper function by static ID(none)helper number, e.g. 1 = bpf_map_lookup_elem
1call PC += imm (program-local function)BPF_PSEUDO_CALLrelative offset of the callee
2call helper function by BTF IDBPF_PSEUDO_KFUNC_CALLBTF ID of a kfunc

EXIT returns from the current function. In the main program that ends the program and R0 becomes its return value. In a subprogram it returns to the caller.

LD, LDX, ST and STX

Memory instructions use the other opcode layout: mode | size | class. The size is W (4 bytes, 0x00), H (2, 0x08), B (1, 0x10) or DW (8, 0x18). The mode is IMM (0x00, only for lddw), ABS (0x20) and IND (0x40) for the legacy cBPF packet loads, MEM (0x60) for normal loads and stores, MEMSX (0x80) for sign-extending loads (v4), and ATOMIC (0xc0). Every access is base register plus 16-bit offset:

{MEM, <size>, STX}:  *(size *) (dst + offset) = src
{MEM, <size>, ST}:   *(size *) (dst + offset) = imm
{MEM, <size>, LDX}:  dst = *(unsigned size *) (src + offset)
{MEMSX, <size>, LDX}: dst = *(signed size *) (src + offset)

(Pseudocode quoted from RFC 9669 §5.1–5.2.)

Note the asymmetry: for stores the base address is in dst, for loads it is in src. The ISA has no "load from absolute address" instruction. Whether a base register holds a valid pointer, and which offsets are in bounds, is something only the verifier knows. It tracks every register's type (PTR_TO_CTX, PTR_TO_MAP_VALUE, PTR_TO_PACKET, …) as described in Chapter 03. The ABS/IND packet loads are kept only for converted cBPF filters. The RFC puts them in the deprecated "packet" conformance group.

Atomic operations

BPF programs run on many CPUs at the same time, and a shared counter in a map needs atomic updates. Early eBPF had a single atomic instruction, XADD (atomic add). Kernel 5.12 generalised it into the ATOMIC mode: the instruction is {ATOMIC, W|DW, STX}, and the operation sits in imm. XADD survives as a legacy alias, as this code shows:

/*
 * Atomic operations:
 *
 *   BPF_ADD                  *(uint *) (dst_reg + off16) += src_reg
 *   BPF_AND                  *(uint *) (dst_reg + off16) &= src_reg
 *   BPF_OR                   *(uint *) (dst_reg + off16) |= src_reg
 *   BPF_XOR                  *(uint *) (dst_reg + off16) ^= src_reg
 *   BPF_ADD | BPF_FETCH      src_reg = atomic_fetch_add(dst_reg + off16, src_reg);
 *   BPF_AND | BPF_FETCH      src_reg = atomic_fetch_and(dst_reg + off16, src_reg);
 *   BPF_OR | BPF_FETCH       src_reg = atomic_fetch_or(dst_reg + off16, src_reg);
 *   BPF_XOR | BPF_FETCH      src_reg = atomic_fetch_xor(dst_reg + off16, src_reg);
 *   BPF_XCHG                 src_reg = atomic_xchg(dst_reg + off16, src_reg)
 *   BPF_CMPXCHG              r0 = atomic_cmpxchg(dst_reg + off16, r0, src_reg)
 *   BPF_LOAD_ACQ             dst_reg = smp_load_acquire(src_reg + off16)
 *   BPF_STORE_REL            smp_store_release(dst_reg + off16, src_reg)
 */

#define BPF_ATOMIC_OP(SIZE, OP, DST, SRC, OFF)			\
	((struct bpf_insn) {					\
		.code  = BPF_STX | BPF_SIZE(SIZE) | BPF_ATOMIC,	\
		.dst_reg = DST,					\
		.src_reg = SRC,					\
		.off   = OFF,					\
		.imm   = OP })

/* Legacy alias */
#define BPF_STX_XADD(SIZE, DST, SRC, OFF) BPF_ATOMIC_OP(SIZE, BPF_ADD, DST, SRC, OFF)

The imm values reuse the ALU operation codes: ADD 0x00, OR 0x40, AND 0x50, XOR 0xa0. Bit 0 (BPF_FETCH 0x01) means "also return the old value in src". XCHG is 0xe1 and CMPXCHG is 0xf1. CMPXCHG uses R0 as the implicit expected value and returns the old value there, the same way x86's cmpxchg uses rax. RFC 9669 defines 32- and 64-bit atomics only (the atomic32 and atomic64 conformance groups) and states that 8- and 16-bit atomics are not supported.

The last two lines of that comment, load-acquire (imm = 0x100) and store-release (0x110), are newer than RFC 9669. LLVM added them under -mcpu=v4 in March 2025 (commit 17bfc00). Here is what clang 14 emits for the classic builtins, compiled in this orb with -mcpu=v3:

BPF-to-BPF calls

Until Linux 4.16 an eBPF program was a single function: everything had to be inlined, and the only calls were to helpers. (The classic_vs_extended document still says "there is only one eBPF program (== one eBPF main routine) and it cannot call other eBPF functions". That sentence predates the feature.) BPF-to-BPF calls added real subprograms. A call with src_reg = 1 (BPF_PSEUDO_CALL) jumps to PC + imm + 1, the callee's own exit returns, and the callee gets a fresh stack frame with its own R10. The registers follow the normal convention, so the callee may clobber R1–R5 but must preserve R6–R9.

The verifier analyses each subprogram in the context of its call site. It limits the depth of nesting with MAX_CALL_FRAMES in include/linux/bpf_verifier.h. That constant was 8 for years (v6.12 and v6.18 still have 8) and is 16 in v7.3 and later. The combined stack of all active frames must fit in the stack limit. For JITed programs, each subprogram is compiled as a native function, so a BPF-to-BPF call is an ordinary native call. In the interpreter, the verifier rewrites such calls to an internal opcode, JMP_CALL_ARGS, which recursively enters an interpreter instance sized for the callee's stack (interpreters_args[insn->off] in core.c).

Tail calls (bpf_tail_call) are a different mechanism: they replace the current program instead of calling and returning. They are capped at MAX_TAIL_CALL_CNT = 33 (include/linux/bpf.h) and covered in Chapter 04.

From C to bytecode: a real disassembly

Here is a complete program compiled with a real toolchain. The source was written for this chapter. It is an XDP program that counts bytes in a one-element array map. It calls a __noinline helper so that a BPF-to-BPF call appears in the output. The toolchain is Debian clang 14.0.6 and libbpf-dev 1.1.2, installed with apt in this orb. The outputs below are pasted verbatim.

// count.c - tiny XDP program used in Chapter 02 to show real eBPF bytecode
#include <linux/bpf.h>
#include <bpf/bpf_helpers.h>

struct {
	__uint(type, BPF_MAP_TYPE_ARRAY);
	__uint(max_entries, 1);
	__type(key, __u32);
	__type(value, __u64);
} pkt_count SEC(".maps");

static __noinline __u64 scale(__u64 bytes)
{
	return bytes * 3 + 7;   /* a BPF-to-BPF call target */
}

SEC("xdp")
int count_packets(struct xdp_md *ctx)
{
	__u32 key = 0;
	__u64 *val = bpf_map_lookup_elem(&pkt_count, &key);
	if (!val)
		return XDP_PASS;
	__u64 len = ctx->data_end - ctx->data;
	__sync_fetch_and_add(val, scale(len));
	return XDP_PASS;
}

Step through the default (v1) output one instruction group at a time:

1. Save the context: r7 = r1 (bf 17)

The program is entered with R1 = struct xdp_md *ctx. It is needed after the helper call, which clobbers R1–R5, so LLVM copies it to callee-saved R7. Opcode 0xbf = MOV (0xb0) | X (0x08) | ALU64 (0x7). Register byte 0x17: low nibble dst = 7, high nibble src = 1.

2. Build key on the stack: insns 1–4

bpf_map_lookup_elem takes a pointer to the key, so the key has to live in memory. r1 = 0 (0xb7 = MOV|K|ALU64), then *(u32 *)(r10 - 4) = r1 (0x63 = MEM|W|STX, off = 0xfffc = -4). The program uses 4 bytes of its 512-byte stack. r2 = r10; r2 += -4 computes the key's address into the second argument register. The immediate fc ff ff ff is −4, sign-extended to 64 bits.

3. Load the map: r1 = 0 ll (16 bytes)

This is the wide lddw (0x18). The compiler cannot know the map's address, so it emits zero and an ELF relocation R_BPF_64_64 pkt_count. At load time libbpf creates the map, writes its file descriptor into imm and sets src_reg = 1 (BPF_PSEUDO_MAP_FD). The kernel replaces the fd with the real struct bpf_map *. The instruction takes two slots, which is why the next index is 7 and not 6.

4. Helper call: call 1 (85 00 … 01 00 00 00)

Opcode 0x85 = CALL (0x80) | K | JMP (0x5), src_reg = 0, so imm = 1 is a helper ID: FN(map_lookup_elem, 1, …) in include/uapi/linux/bpf.h. Arguments are in R1 (map) and R2 (key pointer). The result comes back in R0 and is copied to callee-saved R6.

5. Null check: if r6 == 0 goto +7 (15 06 07 00)

0x15 = JEQ (0x10) | K | JMP, dst = 6, off = 7, imm = 0. The target is 9 + 1 + 7 = 17, the LBB0_2 label that returns XDP_PASS. This branch is required, not an optimisation: the verifier types R0 after this helper as map_value_or_null, and dereferencing it without the check is rejected.

6. Packet length: insns 10–14

0x61 = MEM|W|LDX: two 32-bit loads from ctx + 0 (data) and ctx + 4 (data_end). The verifier rewrites these context loads later into loads of the real xdp_buff pointers. The subtraction is 64-bit (0x1f = SUB|X|ALU64), but C says the result of subtracting two __u32 is a __u32. At the default -mcpu, LLVM truncates with a shift pair: r1 <<= 32; r1 >>= 32. Compare the -mcpu=v3 tab: there a single w1 -= w2 (0x1c = SUB|X|ALU) does the job, because 32-bit ALU ops zero-extend.

7. BPF-to-BPF call: call -1 (85 10 … ff ff ff ff)

Same opcode as a helper call, but the register byte is 0x10: src_reg = 1, BPF_PSEUDO_CALL. The imm = -1 is a placeholder with an R_BPF_64_32 .text relocation. scale() lives in the .text section, and libbpf appends it after count_packets and patches imm to the relative distance. The argument len is already in R1, and scale returns r0 = r1*3 + 7 in R0.

8. Atomic add and exit: insns 16–18

0xdb = ATOMIC|DW|STX, imm = 0 (BPF_ADD without FETCH, because the C code discards the result). On x86-64 this becomes lock add. Finally r0 = 2 (XDP_PASS) and exit (0x95 = EXIT|K|JMP).

Tip

The ISA level changes what code you get. The -mcpu=v3 build is two instructions shorter (17 slots instead of 19) because of 32-bit subregisters. The clang 14 used here defaults to v1 (generic), and defaults differ between LLVM releases, so pick a level your oldest target kernel supports (see ISA versions) and set it explicitly in your build.

What the kernel does with these bytes

The object file is not what runs. The loader (libbpf, Chapter 06) resolves relocations and calls bpf(BPF_PROG_LOAD). The verifier then checks the program and rewrites it: context field loads become real offsets, some helper calls are inlined, map fds become pointers, and division instructions gain zero-checks where needed. You can see both versions on a live system with bpftool. These commands are real but were not run in this orb, whose kernel does not allow loading BPF programs:

# load and pin (needs CAP_BPF / root)
sudo bpftool prog load count.o /sys/fs/bpf/count
sudo bpftool prog show pinned /sys/fs/bpf/count        # prints the program id
sudo bpftool prog dump xlated pinned /sys/fs/bpf/count # bytecode after verifier rewrites
sudo bpftool prog dump jited  pinned /sys/fs/bpf/count # native code produced by the JIT

Running the bytecode: interpreter and JIT

The interpreter

The reference implementation of the VM is ___bpf_prog_run() in kernel/bpf/core.c. It is a classic threaded interpreter that uses GCC's "labels as values" extension. A 256-entry table maps each opcode byte straight to a label, so dispatch is one indirect jump:

static u64 ___bpf_prog_run(u64 *regs, const struct bpf_insn *insn)
{
#define BPF_INSN_2_LBL(x, y)    [BPF_##x | BPF_##y] = &&x##_##y
#define BPF_INSN_3_LBL(x, y, z) [BPF_##x | BPF_##y | BPF_##z] = &&x##_##y##_##z
	static const void * const jumptable[256] __annotate_jump_table = {
		[0 ... 255] = &&default_label,
		/* Now overwrite non-defaults ... */
		BPF_INSN_MAP(BPF_INSN_2_LBL, BPF_INSN_3_LBL),
		/* Non-UAPI available opcodes. */
		[BPF_JMP | BPF_CALL_ARGS] = &&JMP_CALL_ARGS,
		[BPF_JMP | BPF_TAIL_CALL] = &&JMP_TAIL_CALL,
		/* ... */
	};
	/* ... */
#define CONT	 ({ insn++; goto select_insn; })
#define CONT_JMP ({ insn++; goto select_insn; })

select_insn:
	goto *jumptable[insn->code];
	/* ... */
	/* ALU (rest) */
#define ALU(OPCODE, OP)					\
	ALU64_##OPCODE##_X:				\
		DST = DST OP SRC;			\
		CONT;					\
	ALU_##OPCODE##_X:				\
		DST = (u32) DST OP (u32) SRC;		\
		CONT;					\
	ALU64_##OPCODE##_K:				\
		DST = DST OP IMM;			\
		CONT;					\
	ALU_##OPCODE##_K:				\
		DST = (u32) DST OP (u32) IMM;		\
		CONT;
	ALU(ADD,  +)
	ALU(SUB,  -)
	/* ... */

The (u32) casts in ALU_* are the zero-extension rule in executable form. DST, SRC and IMM are macros for regs[insn->dst_reg], regs[insn->src_reg] and insn->imm. The registers are a plain C array. The stack is a local array in a wrapper function, generated once for each stack size from 32 to 512 bytes in steps of 32:

#define PROG_NAME(stack_size) __bpf_prog_run##stack_size
#define DEFINE_BPF_PROG_RUN(stack_size) \
static unsigned int PROG_NAME(stack_size)(const void *ctx, const struct bpf_insn *insn) \
{ \
	u64 stack[stack_size / sizeof(u64)]; \
	u64 regs[MAX_BPF_EXT_REG] = {}; \
\
	kmsan_unpoison_memory(stack, sizeof(stack)); \
	FP = (u64) (unsigned long) &stack[ARRAY_SIZE(stack)]; \
	ARG1 = (u64) (unsigned long) ctx; \
	return ___bpf_prog_run(regs, insn); \
}
/* ... */
EVAL6(DEFINE_BPF_PROG_RUN, 32, 64, 96, 128, 160, 192);
EVAL6(DEFINE_BPF_PROG_RUN, 224, 256, 288, 320, 352, 384);
EVAL4(DEFINE_BPF_PROG_RUN, 416, 448, 480, 512);

This is the stack model made concrete: FP (R10) points one past the end of the array, so R10 - 4 is the last 4 bytes. bpf_prog_select_interpreter() picks interpreters[round_up(stack_depth, 32) / 32 - 1], using the stack depth the verifier computed. A program that uses 4 bytes of stack therefore runs in a 32-byte frame. There is no stack array larger than 512 bytes here, which is why the interpreter keeps the 512-byte limit even where the JIT now allows 2048.

The interpreter has costs. Every instruction pays for an indirect branch and memory-resident registers, and the interpreter itself is a target for speculative-execution gadgets. Kernels built with CONFIG_BPF_JIT_ALWAYS_ON leave it out altogether (#ifndef CONFIG_BPF_JIT_ALWAYS_ON around ___bpf_prog_run). Some distribution kernels enable that option; check your kernel config.

The x86-64 JIT

Each architecture that supports it has its own eBPF JIT under arch/*/net/. According to the sysctl documentation the list is x86_64, x86_32, arm64, arm32, ppc64, ppc32, sparc64, mips64, s390x, riscv64, riscv32, loongarch64 and arc. The x86-64 JIT is a single C file of about 5,200 lines at the revision studied. Its foundation is the fixed register mapping:

/*
 * The following table maps BPF registers to x86-64 registers.
 *
 * x86-64 register R12 is unused, since if used as base address
 * register in load/store instructions, it always needs an
 * extra byte of encoding and is callee saved.
 *
 * x86-64 register R9 is not used by BPF programs, but can be used by BPF
 * trampoline. x86-64 register R10 is used for blinding (if enabled).
 */
static const int reg2hex[] = {
	[BPF_REG_0] = 0,  /* RAX */
	[BPF_REG_1] = 7,  /* RDI */
	[BPF_REG_2] = 6,  /* RSI */
	[BPF_REG_3] = 2,  /* RDX */
	[BPF_REG_4] = 1,  /* RCX */
	[BPF_REG_5] = 0,  /* R8  */
	[BPF_REG_6] = 3,  /* RBX callee saved */
	[BPF_REG_7] = 5,  /* R13 callee saved */
	[BPF_REG_8] = 6,  /* R14 callee saved */
	[BPF_REG_9] = 7,  /* R15 callee saved */
	[BPF_REG_FP] = 5, /* RBP readonly */
	[BPF_REG_AX] = 2, /* R10 temp register */
	[AUX_REG] = 3,    /* R11 temp register */
	[X86_REG_R9] = 1, /* R9 register, 6th function argument */
	[X86_REG_R12] = 4, /* R12 callee saved */
};

The numbers are x86 register encodings (the low 3 bits; a REX prefix bit selects r8–r15). BPF's R1–R5 land on rdi, rsi, rdx, rcx, r8, the first five System V argument registers. R0 lands on rax, the return register, and R6–R9 on callee-saved registers. A helper call needs no argument shuffling: the JIT emits E8 rel32 (emit_call()) and the result is already in rax.

Most eBPF instructions become one x86 instruction because both ISAs are two-operand. The JIT is a large switch (insn->code) in do_jit(). Atomics are a good example of how direct the mapping is:

static int emit_atomic_rmw(u8 **pprog, u32 atomic_op,
			   u32 dst_reg, u32 src_reg, s16 off, u8 bpf_size)
{
	u8 *prog = *pprog;

	if (atomic_op != BPF_XCHG)
		EMIT1(0xF0); /* lock prefix */

	maybe_emit_mod(&prog, dst_reg, src_reg, bpf_size == BPF_DW);

	/* emit opcode */
	switch (atomic_op) {
	case BPF_ADD:
	case BPF_AND:
	case BPF_OR:
	case BPF_XOR:
		/* lock *(u32/u64*)(dst_reg + off) <op>= src_reg */
		EMIT1(simple_alu_opcodes[atomic_op]);
		break;
	case BPF_ADD | BPF_FETCH:
		/* src_reg = atomic_fetch_add(dst_reg + off, src_reg); */
		EMIT2(0x0F, 0xC1);
		break;
	case BPF_XCHG:
		/* src_reg = atomic_xchg(dst_reg + off, src_reg); */
		EMIT1(0x87);
		break;
	case BPF_CMPXCHG:
		/* r0 = atomic_cmpxchg(dst_reg + off, r0, src_reg); */
		EMIT2(0x0F, 0xB1);
		break;
	/* ... */

So the lock *(u64 *)(r6 + 0) += r0 in our program becomes lock add [rbx], rax, atomic_fetch_add becomes lock xadd, and cmpxchg becomes lock cmpxchg with BPF's R0 already in rax, where x86 expects it. (There is no lock for XCHG because x86's xchg with memory is implicitly locked.) AND/OR/XOR with fetch have no single x86 instruction and are lowered to a cmpxchg loop elsewhere in the file.

A few other things the JIT does:

  • Prologue. emit_prologue() emits a CFI hash, a 5-byte NOP that the BPF trampoline can patch, push rbp; mov rbp, rsp, endbr64 for IBT, and sub rsp, round_up(stack_depth, 8). Only the callee-saved registers the program actually uses are pushed.
  • Multiple passes. x86 jumps come in short (rel8) and long (rel32) forms, so instruction sizes depend on distances, which depend on sizes. bpf_int_jit_compile() re-runs do_jit() until the image size stops changing (#define MAX_PASSES 20).
  • Spectre hardening. The verifier can insert BPF_NOSPEC speculation barriers, which the JIT emits as lfence, and classic-BPF programs from unprivileged users get a branch-history barrier at exit.

Constant blinding

A JIT that copies user-chosen 32-bit immediates verbatim into executable kernel memory gives an attacker a way to plant machine code. That is JIT spraying. Write a BPF program full of mov $0xa8XXYYZZ, … instructions, load many copies, and if a separate memory-corruption bug lets you jump into the middle of one of those instructions, the immediate bytes run as your own instructions. Keegan McAllister demonstrated this against the Linux cBPF JIT in 2012, and Reshetova, Bonazzi and Asokan showed at Black Hat Europe 2016 that randomising where JIT images are placed does not stop it. The fix landed in Linux 4.7 as commit 4f3446bb809f, "bpf: add generic constant blinding for use in jits", by Daniel Borkmann.

The idea: before JITing, rewrite every instruction that carries an immediate so that the immediate never appears in the output. It is XORed with a fresh random value and decoded at run time through the hidden BPF_REG_AX register:

static int bpf_jit_blind_insn(const struct bpf_insn *from,
			      const struct bpf_insn *aux,
			      struct bpf_insn *to_buff,
			      bool emit_zext)
{
	struct bpf_insn *to = to_buff;
	u32 imm_rnd = get_random_u32();
	int off;
	/* ... */
	/* Constraints on AX register:
	 *
	 * AX register is inaccessible from user space. It is mapped in
	 * all JITs, and used here for constant blinding rewrites. It is
	 * typically "stateless" meaning its contents are only valid within
	 * the executed instruction, but not across several instructions.
	 * There are a few exceptions however which are further detailed
	 * below.
	 *
	 * Constant blinding is only used by JITs, not in the interpreter.
	 * ...
	 */
	/* ... */
	switch (from->code) {
	/* ... */
	case BPF_ALU64 | BPF_ADD | BPF_K:
	case BPF_ALU64 | BPF_SUB | BPF_K:
	/* ... */
	case BPF_ALU64 | BPF_MOD | BPF_K:
		*to++ = BPF_ALU64_IMM(BPF_MOV, BPF_REG_AX, imm_rnd ^ from->imm);
		*to++ = BPF_ALU64_IMM(BPF_XOR, BPF_REG_AX, imm_rnd);
		*to++ = BPF_ALU64_REG_OFF(from->code, from->dst_reg, BPF_REG_AX, from->off);
		break;
	/* ... */

Concretely, r1 += 0x11223344 becomes three instructions (an illustration, with a made-up random value):

/* illustrative: rnd = 0x5a5a1234, chosen per instruction by get_random_u32() */
ax  = 0x4b782170          /* 0x11223344 ^ 0x5a5a1234: the only value that reaches the JIT image */
ax ^= 0x5a5a1234          /* ax == 0x11223344 again, but only at run time                    */
r1 += ax                  /* ALU|X form of the original instruction                          */

Neither constant in the emitted code is the attacker's value, and both change every time the program is loaded. Jumps with immediates get the same treatment (with their offsets adjusted for the inserted instructions), and so do lddw and stores of immediates. A mov of zero becomes xor dst, dst. On x86-64, AX is mapped to r10, which is why the reg2hex[] comment says "x86-64 register R10 is used for blinding".

The price is roughly three instructions for every immediate-using instruction, and it disables bpf_jit_kallsyms. That is why blinding is opt-in through bpf_jit_harden. bpf_jit_blinding_enabled() in include/linux/filter.h applies it only when the JIT is in use, hardening is on, and (at level 1) the loader lacks CAP_BPF. If the rewrite fails, bpf_prog_jit_compile() falls back to the interpreter instead of running unblinded code.

Limits of blinding

Blinding stops the immediate-as-code trick. It does not address the attack class in EPF: Evil Packet Filter (USENIX ATC 2023), which uses BPF programs and data as payloads to bypass kernel isolation defences. Today the main defences are to keep unprivileged BPF disabled (kernel.unprivileged_bpf_disabled) and to require CAP_BPF.

The standard: RFC 9669

For its first decade the eBPF ISA was defined by "whatever Linux and LLVM do". That became a problem once other implementations appeared: eBPF for Windows, userspace VMs such as uBPF, rbpf and bpftime, and hardware offload. David Vernet's LWN article "Standardizing BPF" (2023) describes the push. NVMe vendors in particular wanted a stable target before investing in BPF offload, for example for XRP. The IETF formed a BPF working group, and the result is RFC 9669, "BPF Instruction Set Architecture (ISA)", edited by Dave Thaler and published in October 2024 on the Standards Track. LWN noted the publication on 5 November 2024 ("The BPF instruction set architecture is now RFC 9669").

The RFC was generated from Documentation/bpf/standardization/instruction-set.rst in the kernel tree, and the two documents are kept in sync. Its parts are:

  • Encoding and semantics (§3–5): everything in this chapter's encoding and class sections, written in MUST/SHALL language, including the corner cases such as division by zero and LLONG_MIN / -1.
  • Conformance groups (§2.4). An implementation does not have to support every instruction. It MUST support base32, and MAY support base64, atomic32, atomic64, divmul32, divmul64 and the deprecated packet group. A 32-bit microcontroller VM or a NIC can therefore claim conformance to a precise subset.
  • Two IANA registries (§7): "BPF Instruction Conformance Groups" and "BPF Instruction Set", with Appendix A as the initial opcode table. New instructions go into a new group. The RFC says "Once a conformance group is registered with a set of instructions, no further instructions can be added to that conformance group." Old groups therefore keep their meaning forever.

The RFC deliberately leaves things out. The register calling convention lives in a separate informational document (abi.rst). Helper functions, BTF, maps and the verifier are described only to the extent the encoding refers to them. The RFC calls their standardization "future work". Linux has also moved beyond the RFC: load-acquire/store-release, the BPF_JCOND (may_goto) pseudo-jump and the arena address-space casts are Linux extensions not in RFC 9669.

Why it matters to you

RFC 9669 is the reason a program compiled once with clang -target bpf can run in the Linux kernel, on Windows, and in userspace runtimes such as bpftime (Chapter 14) or llvmbpf (Chapter 16). Helpers, maps and attach points remain platform-specific.

LLVM groups instruction-set extensions into "CPU versions". The kernel's clang-notes.rst describes -mcpu=v3 as corresponding to "the current eBPF ISA". v4 came later. Benefits and limitations

Near-native speed

The register mapping and two-operand form let a JIT emit about one native instruction per BPF instruction, with no argument shuffling at calls.

Simple to verify and decode

Fixed 8-byte instructions (one exception), no indirect jumps in the base ISA, explicit stack. Analysis tools can walk the program trivially.

Total semantics

No traps: division by zero, overflow and over-wide shifts all have defined results, so the VM never needs exception handling.

Portable and standardised

RFC 9669 plus conformance groups give non-Linux runtimes a precise target. The same ELF object can feed the kernel, Windows or a userspace VM.

And the limitations, most of which are deliberate:

  • Tight resources. 512 bytes of stack (2048 on some JITs in the newest kernels), five register arguments, limited call depth. Large data must go into maps.
  • The ISA alone is not safe. Nothing in the encoding stops a wild pointer dereference. The verifier makes the guarantees, and it is complex. Its analysis, not the ISA, is where most of BPF's difficulty lies.
  • Extensions keep coming. v4 instructions, load-acquire, may_goto and arenas mean that "eBPF" depends on the kernel version. You need to pick an -mcpu and test on your oldest target.
  • A JIT per architecture. Each of the ~13 JITs is hand-written machine-code emission inside the kernel. They have had real bugs, which is the motivation for the verification work below.
  • 32-bit hosts pay for 64-bit registers. 32-bit JITs must emulate every 64-bit operation with register pairs.

Related work

Because JITs run inside the kernel and translate untrusted input, they have attracted formal-methods research:

  • Jitk (Wang, Lazar, Zeldovich, Chlipala, Tatlock, OSDI 2014) built a verified in-kernel JIT for classic BPF and INET-DIAG on top of the CompCert verified compiler. It proved that the native code preserves the filter's semantics, terminates, and has bounded stack usage. The authors note that their theorems do not prevent JIT spraying.
  • Jitterbug (Nelson, Van Geffen, Torlak, Wang, "Specification and verification in the field: Applying formal methods to BPF just-in-time compilers in the Linux kernel", OSDI 2020) targets the production eBPF JITs. It gives a precise specification of JIT correctness and an automated proof strategy built on the Rosette solver-aided language. With it the authors wrote a new verified JIT for 32-bit RISC-V, which was merged in Linux 5.7. They also found and fixed 16 previously unknown bugs in five deployed JITs and upstreamed new optimisations. For the paper they inspected every JIT commit from May 2014 to April 2020.
  • JitSynth (Van Geffen, Nelson, Dillig, Wang, Torlak, "Synthesizing JIT Compilers for In-Kernel DSLs", CAV 2020) goes a step further and synthesises a verified JIT, for example eBPF to RISC-V, from interpreters for the source and target ISAs.
  • Attacks. McAllister's 2012 kernel JIT-spraying write-up; Gawlik and Holz, "SoK: Make JIT-Spray Great Again" (WOOT 2018), which surveys JIT spraying across browsers and the kernel and discusses constant blinding as a defence; and EPF (ATC 2023), discussed above.
  • Verification of programs, not JITs. PREVAIL and other verifier research cover the other half of the trust story and are the subject of Chapter 03 and Chapter 18.

Check your understanding

Q1. A BPF program calls bpf_map_lookup_elem() and then wants to use the context pointer it received at entry. Where should the compiler have kept that pointer?

R1–R5 are caller-saved and unreadable after any call; R0 receives the return value; R10 is the read-only frame pointer. Only R6–R9 survive calls, which is why the disassembly starts with r7 = r1.

Q2. Decode 85 10 00 00 ff ff ff ff.

0x85 is CALL|K|JMP. The register byte 0x10 puts 1 in src_reg (high nibble), which is BPF_PSEUDO_CALL. imm = −1 is the placeholder LLVM emits before libbpf patches the relative offset. src_reg = 2 would be a kfunc.

Q3. Why does the default--mcpu build contain r1 <<= 32; r1 >>= 32 while the -mcpu=v3 build does not?

The C code subtracts two __u32 fields. In 64-bit arithmetic the result must be truncated explicitly. w1 -= w2 (ALU class) writes the low 32 bits and zeroes the rest, as RFC 9669 and the interpreter's (u32) casts specify.

Q4. What does constant blinding protect against?

Blinding XORs each immediate with a per-instruction random value and decodes it at run time via the hidden AX register, so attacker-chosen constants never appear in executable memory. It is controlled by net.core.bpf_jit_harden and applies only to JITed code.

Q5. Which statement about RFC 9669 is correct?

The RFC covers the instruction set only. Helpers, BTF and maps are left for future work, and the calling convention is in the separate abi.rst. It was generated from, and is kept in sync with, Documentation/bpf/standardization/instruction-set.rst.

Q6. Why does the interpreter keep the 512-byte stack limit even on kernels where the x86-64 JIT allows 2048 bytes?

DEFINE_BPF_PROG_RUN is instantiated for 32, 64, …, 512 and bpf_prog_select_interpreter() indexes that array by round_up(stack_depth, 32)/32 - 1. Off is a full s16 and the RFC does not fix a stack size.
