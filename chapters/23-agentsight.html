Chapter 23

AgentSight: system-level observability for AI agents

You start Claude Code or Codex, ask it to fix a failing test, and twenty minutes later it reports success. What did it actually send to the model? Which commands did it run, which files did it open, which hosts did it contact, and which of those actions came from which model reply? The agent's own logs are written by the agent. This chapter shows how AgentSight answers those questions from outside the agent. It uses uprobes on TLS libraries to read the plaintext of every model call, and kernel tracepoints to follow every process the agent spawns. A Rust pipeline then joins the two streams into one timeline.

Why this matters

An AI coding agent is a loop. It sends a prompt to a large language model (LLM) over HTTPS, gets back text and tool calls ("run npm test", "edit src/auth.ts"), carries those calls out on the local machine, and sends the results back to the model. Claude Code, Codex, Gemini CLI and similar tools all work this way, and so do agents built with frameworks such as LangChain or crewAI. Each tool call can start arbitrary programs. A single "run the tests" step may fork a shell, which runs npm, which starts node, which opens hundreds of files and maybe a network connection.

When such a run fails, stalls, burns tokens or does something unsafe, you want two views of it at once:

  • Intent. What the agent asked the model and what the model told it to do: the prompts, the replies, the tool calls with their arguments, the token counts.
  • Action. What really happened on the system: which processes ran with which arguments, which files were read or written, which sockets connected where, how much CPU and memory it all took.

Existing tools see one side. Application-level tracing (LangSmith, Langfuse, Phoenix, or OpenTelemetry instrumentation inside the agent) sees intent, but only if you own and instrument the agent's code. The trace stops at the process boundary: a bash -c that the agent spawns is a black box. Gateways and proxies such as Helicone see the model traffic when you can reroute it, but not the local effects. System monitors (Falco, Tracee, or plain strace) see every execve and openat, but they have no idea which model reply caused them. To such a tool, an agent writing a test script and an agent writing a malicious payload look the same.

The AgentSight paper calls this the semantic gap: "existing tools observe either an agent's high-level intent (via LLM prompts) or its low-level actions (e.g., system calls), but cannot correlate these two views" (Zheng et al., PACMI '25). There is also a trust problem. An agent that has been manipulated by a prompt injection, or that is simply buggy, can skip, truncate or falsify its own logs. An observer that lives outside the agent and reads from the kernel does not depend on the agent's cooperation.

Key idea

Agent frameworks change every week, but every agent must cross two stable boundaries: it talks to the model through a TLS library, and it acts on the machine through system calls. AgentSight puts eBPF probes on both: uprobes on SSL_read/SSL_write (and their equivalents) for the decrypted intent stream, and tracepoints and fentry/fexit hooks in the kernel for the action stream. A userspace engine then links the two by process lineage, time and content. The paper calls this approach boundary tracing.

Application-level tracing

SDKs or callbacks inside the agent. Rich semantics: prompts, tools, tokens. Needs code changes, breaks when the framework changes, cannot see subprocesses, and trusts the agent to report itself.

Proxies and gateways

Route model traffic through an endpoint you control. No agent changes, but you need the agent to honour a base URL or a proxy, a TLS interception certificate, or both, and you still see nothing local.

Generic system tracing

Kernel-level, complete, and hard to evade. But it has no notion of a "model reply" or a "tool call", so it cannot tell you why a process ran.

AgentSight

Kernel-level capture of both streams, no SDK, no proxy, no agent changes. Works for closed-source CLIs. The cost is Linux only (for live capture), root for the probes, and per-runtime work to find the TLS functions.

This chapter is about observing agents. Enforcing policies on them, by tracking where data flows and blocking violations in a BPF-LSM hook, is the subject of chapter 24, ActPlane, which grew out of AgentSight's code base. Measuring and limiting the OS resources an agent uses is chapter 25.

Boundary tracing: the design in one picture

AgentSight was released in July 2025 (the GitHub repository was created on 2025-07-07) and described in a six-page workshop paper, "AgentSight: System-Level Observability for AI Agents Using eBPF" by Yusheng Zheng, Yanpeng Hu, Tong Yu and Andi Quinn, at PACMI '25 (the 4th Workshop on Practical Adoption Challenges of ML for Systems, held with SOSP '25). Since then the repository has grown from a research prototype into a product with a top-style live view, background monitoring, saved sessions, reports, a hosted web app and a crates.io library. The core architecture has stayed the same.

The paper bases the design on two properties of the boundaries:

  • Comprehensiveness. Every action an agent takes, from process creation to file I/O, goes through the kernel, including actions of subprocesses that no in-process SDK can see.
  • Stability. "System call ABIs and network protocols evolve far more slowly than agent frameworks." A probe on SSL_write keeps working when an agent switches from one SDK to another.

Three facts about this picture are worth fixing in your head before looking at code.

  1. Intent comes from user space, actions from the kernel. TLS encryption happens inside the agent process. On the wire there is only ciphertext. The last place the request exists in plaintext is the buffer the agent passes to SSL_write, and the first place the reply exists in plaintext is the buffer SSL_read fills. A uprobe (chapter 05) on those functions reads the buffer with bpf_probe_read_user(). No certificate, proxy or key logging is needed.
  2. The probes are separate programs. Each eBPF tool in bpf/ is a classic libbpf application: a .bpf.c kernel part and a .c loader that prints one JSON object per event on stdout. The Rust binary embeds the compiled loaders, writes them to a temporary directory at start-up, and runs them as child processes (with sudo -n if it is not root). The agent itself keeps running as your normal user.
  3. Correlation happens in user space. The kernel side does only filtering and cheap aggregation. Parsing HTTP/2, reassembling Server-Sent Events, pairing requests with responses, extracting tool calls and building the process tree all happen in Rust.

The intent stream: reading TLS plaintext with uprobes

The SSL probe lives in bpf/sslsniff.bpf.c (831 lines) and its loader bpf/sslsniff.c (1,217 lines). The header credits the origin: it is "based on sslsniff from BCC by Adrian Lopez & Mark Drayton", rewritten for libbpf and CO-RE by Yusheng Zheng in 2023 (the same tool is a lesson in chapter 09's tutorial). AgentSight has since added several TLS libraries, a large-buffer event format, capture-loss counters and byte-pattern attachment for stripped binaries.

Why both an entry probe and a return probe

SSL_write(ssl, buf, num) receives plaintext in buf, so the entry probe could copy it right away. SSL_read(ssl, buf, num) is the opposite: at entry, buf is an empty buffer, and only when the function returns does it hold ret bytes of decrypted data. sslsniff treats both directions the same way. The entry probe saves the arguments in hash maps keyed by thread ID. The return probe reads the return value (the byte count), looks up the saved buffer pointer, copies the bytes and submits the event. Using the thread ID as key is safe because a thread can only be inside one SSL_read at a time.

static __always_inline int SSL_rw_enter(void *ssl, void *buf,
                                        u8 tls_library)
{
    u64 pid_tgid = bpf_get_current_pid_tgid();
    u32 pid = pid_tgid >> 32;
    u32 tid = pid_tgid;
    u32 uid = bpf_get_current_uid_gid();
    u64 ts = bpf_ktime_get_ns();
    u64 handle = (u64)ssl;

    if (!trace_allowed(uid, pid)) {
        return 0;
    }

    /* store arg info for later lookup */
    bpf_map_update_elem(&bufs, &tid, &buf, BPF_ANY);
    bpf_map_update_elem(&start_ns, &tid, &ts, BPF_ANY);
    bpf_map_update_elem(&transport_handles, &tid, &handle, BPF_ANY);
    bpf_map_update_elem(&tls_libraries, &tid, &tls_library, BPF_ANY);
    return 0;
}

static int SSL_exit(struct pt_regs *ctx, int rw) {
    /* ... pid/tid/uid/ts as above, trace_allowed() ... */
    u64 *bufp = bpf_map_lookup_elem(&bufs, &tid);
    if (bufp == 0)
        return 0;

    u64 *tsp = bpf_map_lookup_elem(&start_ns, &tid);
    if (!tsp)
        return 0;
    u64 delta_ns = ts - *tsp;
    /* ... */
    int len = PT_REGS_RC(ctx);
    if (len <= 0) { // no data
        /* ... delete the four map entries ... */
        return 0;
    }

    /* reserve space in ring buffer */
    struct probe_SSL_data_t *data = reserve_event();
    /* ... fill pid, tid, uid, len, rw, tls_library, process_start_ns ... */
    u32 buf_copy_size = clamp_probe_size((size_t)len, MAX_BUF_SIZE);

    bpf_get_current_comm(&data->comm, sizeof(data->comm));

    if (bufp != 0)
        ret = bpf_probe_read_user(&data->buf, buf_copy_size, (char *)*bufp);
    /* ... delete map entries, set buf_filled / buf_size ... */

    /* submit to ring buffer */
    bpf_ringbuf_submit(data, 0);
    return 0;
}

    __u64 delta_ns;

    __u64 ringbuf_reserve_failures; // cumulative capture-loss counter

    __u8 connection_closed;

Several details in this code are lessons in practical eBPF.

  • Fixed-size ring-buffer records. bpf_ringbuf_reserve() needs a size the verifier knows, so every event reserves the full sizeof(struct probe_SSL_data_t), about 256 KB, even for a 40-byte write. The comment in sslsniff.h records why the numbers are what they are: at an earlier 512 KB buffer, "a 2MB ring held only 3 concurrent events; the 4th reserve returned NULL and the handler dropped the event silently". With 256 KB records and a 16 MB ring, 63 worst-case events fit. Larger writes are truncated and flagged (truncated, bytes_lost) instead of vanishing.
  • Counting loss. reserve_event() increments a capture_loss array entry when a reservation fails and copies the running total into every later event (ringbuf_reserve_failures). A consumer can therefore tell that it missed something even though the missed event itself never existed.
  • Placating the verifier. clamp_probe_size() masks the length with 0x7ffff, clamps it, and calls barrier_var(), because "some 6.6 verifiers (including TencentOS 4) treat the size as signed-unbounded and reject with 'R2 min value is negative'". This is the kind of bounds-tracking issue explained in chapter 03.
  • Connection identity. The SSL* pointer is recorded as transport_handle, and process_start_ns comes from the thread-group leader's start_boottime. The pair (process instance, TLS object) identifies one connection, even when the connection moves between threads. The Rust side uses it to group the records of one HTTP exchange (commit 33390661, "correlate HTTP exchanges by TLS connection and stream").

In user space, handle_event() calls print_event(), which writes one JSON object per record: function (READ, WRITE or CLOSE), timestamp_ns, capture_seq, comm, pid, tid, len, buf_size, transport_handle, tls_library, latency_ms, the payload as both data (text) and data_hex (exact bytes, needed for HTTP/2 HPACK headers, per docs/ssl-capture.md), truncated, and container fields when the process is in one.

Static and stripped binaries

The hard part of TLS capture is not the BPF code but finding the functions. Many agent CLIs do not use the system libssl.so. The README FAQ explains: Claude Code is a Bun application with BoringSSL linked in statically, and "OpenSSL for all Node.js" builds (Gemini CLI, many others) is also statically linked. Codex is written in Rust and uses rustls. Attaching to libssl.so catches none of them.

For these, sslsniff takes --binary-path and tries, in order:

  1. Symbols. If the ELF has OPENSSL_is_boringssl it calls attach_boringssl(), else attach_openssl(), both by symbol name. Node.js exports its OpenSSL symbols, so this works there.
  2. rustls signatures. If the binary carries Codex or Grok TLS markers, it searches for rustls functions (codex_find_rustls_offsets() and friends) and attaches the probe_rustls_* programs by file offset. These programs read Rust ABI structures such as OutboundChunks, so they depend on the compiled layout.
  3. BoringSSL byte patterns. For a stripped binary, find_boringssl_offsets() reads the whole file and looks for the function prologues of SSL_read, SSL_write and SSL_do_handshake. The comment says the patterns "are derived from Bun v1.3.x profile builds". The offsets are then passed to bpf_program__attach_uprobe_opts() with no func_name.

If all three fail, the loader refuses to start rather than report "no traffic": "binary-path attach failed for %s; refusing to continue with partial SSL capture".

Thread names

A trap that cost the project real debugging time, documented in CLAUDE.md: bpf_get_current_comm() returns the thread name, not the process name. Claude Code does its TLS on a thread called "HTTP Client", so filtering sslsniff with -c claude drops every event. When --binary-path is set, build_trace_agent() in collector/src/cmd_trace.rs therefore passes the command filter only to the process tracer, not to sslsniff. The uprobe is already scoped to one ELF file.

The top-level record command hides all of this. With record -- <command> it resolves the launched executable itself. With record -c node it runs resolve_binary_path() and adopts the result only if binary_embeds_ssl() finds the string SSL_write in the file. With --binary-path docker://name or k8s://ns/pod/container it asks Docker or the CRI for the container's init PID and walks the descendant tree in /proc until it finds a process whose executable embeds TLS or maps libssl.so.

Exec: who ran what

The exec handler reads the parent through CO-RE, the executable name from the tracepoint's dynamic __data_loc field, and the full command line straight from the new process's memory:

SEC("tp/sched/sched_process_exec")
int handle_exec(struct trace_event_raw_sched_process_exec *ctx)
{
	/* ... */
	if (!is_scope_tracked())
		return 0;

	/* Get process info */
	pid = bpf_get_current_pid_tgid() >> 32;
	task = (struct task_struct *)bpf_get_current_task();

	/* remember time exec() was executed for this PID */
	ts = bpf_ktime_get_ns();
	bpf_map_update_elem(&exec_start, &pid, &ts, BPF_ANY);
	/* ... */
	e->type = EVENT_TYPE_PROCESS;
	e->exit_event = false;
	e->pid = pid;
	e->ppid = BPF_CORE_READ(task, real_parent, tgid);
	e->timestamp_ns = ts;
	bpf_get_current_comm(&e->comm, sizeof(e->comm));

	fname_off = ctx->__data_loc_filename & 0xFFFF;
	bpf_probe_read_str(&e->filename, sizeof(e->filename), (void *)ctx + fname_off);

	/* Capture full command line with arguments from mm->arg_start */
	struct mm_struct *mm = BPF_CORE_READ(task, mm);
	unsigned long arg_start = BPF_CORE_READ(mm, arg_start);
	unsigned long arg_end = BPF_CORE_READ(mm, arg_end);
	unsigned long arg_len = arg_end - arg_start;
	/* ...
	 * We always read exactly MAX_COMMAND_LEN-1 bytes (a compile-time
	 * constant) so that BPF verifiers on all kernel versions can
	 * prove the access is bounded.  This may read past arg_end into
	 * environment variables, but userspace trims to arg_len.
	 *
	 * NO LOOPS in BPF -- all post-processing (\0->space, trimming)
	 * is done in userspace to stay within the verifier instruction
	 * limit on kernel 5.15 (1,000,000 insns).
	 */
	long ret = bpf_probe_read_user(e->full_command,
				MAX_COMMAND_LEN - 1,
				(void *)arg_start);
	/* ... store arg_len in e->exit_code for userspace trimming ... */
	bpf_ringbuf_submit(e, 0);
	return 0;
}

The argv trick is worth noticing. argv is a block of NUL-separated strings, so bpf_probe_read_user_str() would stop after argv[0]. The program reads a fixed 255 bytes instead and lets user space replace the NULs with spaces and cut at arg_len. That keeps the BPF side loop-free. The exit handler is the mirror image: it computes the process lifetime from the exec_start map, reads exit_code and the peak RSS (signal->maxrss), and ignores thread exits (pid != tid).

File opens: resolved paths, not syscall arguments

Hooking sys_enter_openat gives you the string the program passed, which may be relative (../config.json), may fail, and misses opens done by execve, the ELF interpreter or io_uring. Commit 95612527 ("trace resolved file access in process probe", October 2026) added a better hook: fexit on the LSM function security_file_open, which runs after path resolution for every successful open.

/* security_file_open runs after path resolution for open/openat/openat2,
 * io_uring and exec, including the ELF interpreter. fexit excludes denied
 * opens. The old syscall hooks remain available on kernels lacking this hook
 * or bpf_d_path. */
SEC("fexit/security_file_open")
int BPF_PROG(trace_file_open_exit, struct file *file)
{
	/* ... */
	if (bpf_get_func_ret(ctx, &ret) || (int)ret || !is_scope_tracked())
		return 0;
	task = (struct task_struct *)bpf_get_current_task();
	if (BPF_CORE_READ(task, flags) & PF_KTHREAD)
		return 0;
	inode = BPF_CORE_READ(file, f_inode);
	if ((BPF_CORE_READ(inode, i_mode) & S_IFMT) != S_IFREG)
		return 0;
	/* ... skip nsfs/pidfs, detect overlay layer opens ... */
	mode = BPF_CORE_READ(file, f_mode);
	flags = BPF_CORE_READ(file, f_flags);
	if (mode & FMODE_READ)
		access |= FILE_ACCESS_READ;
	if (mode & FMODE_WRITE)
		access |= FILE_ACCESS_WRITE;
	/* ... FILE_ACCESS_EXEC, build dedup key from process+file+access ... */
	if (bpf_map_update_elem(&file_opens_seen, &key, &present, BPF_NOEXIST) == -EEXIST)
		return 0;

	e = bpf_ringbuf_reserve(&rb, sizeof(*e), 0);
	/* ... */
	path_len = bpf_d_path(&file->f_path, e->file_op.filepath,
			      sizeof(e->file_op.filepath));
	/* ... */
	bpf_ringbuf_submit(e, 0);
	return 0;
}

Three ideas are packed in here. bpf_get_func_ret() lets an fexit program see the return value, so denied opens are dropped. bpf_d_path() turns the struct path into an absolute path string; the kernel allows this helper only in a short list of functions, which is why the hook is on security_file_open. And the file_opens_seen LRU hash (65,536 entries) deduplicates: a build that opens the same header a thousand times produces one event per process, file and access mode, not a thousand. If the hook or helper is missing, the loader falls back to the syscall tracepoints and prints a notice, as bpf/README.md documents.

Aggregating in the kernel

Writes, connects, renames and signals can be extremely frequent. Instead of one ring buffer record per call, the process_ext handlers update a hash map event_agg_map (16,384 entries) keyed by process, event type and a short detail string, holding a count, a byte total and the last timestamp. User space flushes the map periodically (process_ext/map_flush.h) and emits summary events named FILE_DELETE, FILE_RENAME, WRITE, NET_CONNECT, NET_BIND, SIGNAL_SEND, PROC_FORK, COW_FAULT and so on. The connect handler shows the pattern:

SEC("tp/syscalls/sys_enter_connect")
int trace_connect(struct trace_event_raw_sys_enter *ctx)
{
	if (!trace_network)
		return 0;
	if (!is_event_tracked())
		return 0;

	struct agg_key key = {};
	key.pid = bpf_get_current_pid_tgid() >> 32;
	key.event_type = EVENT_TYPE_NET_CONNECT;

	u16 family = 0;
	const void *user_addr = (const void *)ctx->args[1];
	bpf_probe_read_user(&family, sizeof(family), user_addr);

	if (family == 2)
		read_and_format_sockaddr(ctx, key.detail, sizeof(key.detail));
	else
		format_family(key.detail, sizeof(key.detail), family);

	update_agg_map(&key, 1, 0);
	return 0;
}

Following only the agent

A machine runs many processes; you want the agent and everything it starts, nothing else. The paper describes this as "an aggressive, dynamic in-kernel eBPF filter" that tracks fork and execve to build "a complete lineage tree of the agent's activity". In the code it has two layers:

  • Scope (is_scope_tracked() in process_ext/bpf_common.h): an optional target PID namespace (the task must be visible in it, which also covers sandboxes nested inside it) and an optional cgroup (exact ID, or any ID in the tracked_cgroups map).
  • Lineage (is_pid_tracked()): a tracked_pids hash map. User space keeps a PID tracker (process_filter.h) and decides on every exec event whether the new process belongs to the agent. In the default filter mode a process is tracked if it is the target PID, if its parent is tracked, or if its name matches a -c filter. Tracked PIDs are written into the BPF map with bpf_map_update_elem(), so later high-volume events from untracked PIDs are dropped in the kernel.
	/* Mode 2 (FILTER): selective tracking */
	if (tracker->filter_mode == FILTER_MODE_FILTER) {
		/* Check if specific PID was requested */
		if (tracker->target_pid > 0 && pid == tracker->target_pid) {
			return true;
		}

		/* Check if parent is tracked */
		if (pid_tracker_is_tracked(tracker, ppid)) {
			return true;
		}

		/* Check if command matches any filter */
		if (tracker->command_filter_count > 0 &&
		    command_matches_any_filter(comm, tracker->command_filters, tracker->command_filter_count)) {
			return true;
		}
	}

Note the split: the lineage decision is made in user space, in ring-buffer order, while the cheap membership test runs in the kernel. A comment in the fexit handler explains why: it keeps "PID/comm filtering in the existing userspace tracker so an open racing the process exec event is handled in ring-buffer order". Our reading of the code: exec and resolved-open events are checked only against the scope in the kernel and filtered by lineage in user space, so a child that execs and opens files before its PID reaches tracked_pids is not lost. The aggregated events (is_event_tracked()) do depend on the map.

A third, smaller probe, bpf/stdiocap.bpf.c, hooks sys_enter/exit_read and write for one target PID and copies the bytes on file descriptors 0–2 (or all FDs with --all-fds). That captures Model Context Protocol (MCP) servers that talk JSON-RPC over stdio, which never touch TLS. An experimental browsertrace probe for NSS and Chrome exists but is not embedded in the collector.

The Rust collector: runners and analyzers

The three probes are ordinary libbpf loaders written in C. Each one prints one JSON object per line on stdout and knows nothing about HTTP, LLMs or sessions. Everything above that line lives in Rust: the agentsight binary built from collector/, on top of the library crate agentsight-capture (published on crates.io) and the analysis code in ext/analysis. The design is a small stream-processing framework with two traits: a runner produces a stream of events, an analyzer takes a stream and returns a new one.

One event type, two traits

All data, whatever its origin, travels as the same struct. The interesting payload is left as untyped JSON in data, so a new probe field does not need a Rust change until some analyzer wants to read it.

/// Raw event structure flowing from runners through analyzers.
#[derive(Debug, Clone, Serialize, Deserialize, PartialEq)]
pub struct Event {
    pub timestamp: u64,
    pub source: String,
    pub pid: u32,
    pub comm: String,
    pub data: serde_json::Value,
}

The two traits are just as small. An EventStream is a pinned, boxed asynchronous Stream (from the futures crate), so the whole pipeline is lazy: nothing is parsed until the stream is polled, and back-pressure from a slow sink propagates up to the pipe that reads the probe's stdout.

pub type EventStream = Pin<Box<dyn Stream<Item = Event> + Send>>;
pub type RunnerError = Box<dyn std::error::Error + Send + Sync>;

#[async_trait]
pub trait Runner: Send + Sync {
    async fn run(&mut self) -> Result<EventStream, RunnerError>;

    fn add_analyzer(self, analyzer: Box<dyn crate::analyzers::Analyzer>) -> Self
    where
        Self: Sized;
}
/// Stable processing boundary between native capture and extensions.
#[async_trait]
pub trait Analyzer: Send + Sync {
    async fn process(&mut self, stream: EventStream) -> Result<EventStream, AnalyzerError>;
}

The doc comment "stable processing boundary between native capture and extensions" is the point of the split. agentsight-capture owns the parts that touch the kernel (spawning probes, reading their output, resolving binaries), and the analyzers in ext/analysis can change freely on top of it.

From a probe's stdout to an Event

The probe binaries are compiled ahead of time and baked into the Rust executable with include_bytes! (agentsight-capture/src/binary_extractor.rs). At start-up they are written to a temporary directory, made executable, and launched as child processes. That is why a single ~25 MB release binary is all you install. BinaryExecutor in runners/common.rs starts each one:

        let mut cmd = if needs_sudo {
            let mut c = TokioCommand::new("sudo");
            c.arg("-n").arg(&self.binary_path);
            c
        } else {
            TokioCommand::new(&self.binary_path)
        };
        cmd.stdout(Stdio::piped()).stderr(Stdio::piped());
        cmd.kill_on_drop(true);
        #[cfg(unix)]
        cmd.process_group(0);

Three details matter here. sudo -n is non-interactive, so if you are not root and have no cached sudo ticket the probe fails right away instead of hanging on a password prompt; the error message tells you to run with sudo or sudo -v first. kill_on_drop and a separate process group mean that when the collector exits, the loaders (and so their BPF links) go with it. And because each probe is a separate process, a verifier rejection in one does not crash the others.

Each stdout line is parsed into an Event. A line that lacks the timestamp, pid or comm is not dropped silently; it becomes a diagnostic event and increments an error counter:

pub fn parse_json_event(
    runner: &'static str,
    timestamp_field: &'static str,
    raw: serde_json::Value,
    errors: &AtomicU64,
) -> Event {
    let Some(timestamp) = raw.get(timestamp_field).and_then(|v| v.as_u64()) else {
        return parse_error_event(runner, raw, format!("missing {timestamp_field}"), errors);
    };
    let Some(pid) = raw.get("pid").and_then(|v| v.as_u64()).map(|v| v as u32) else {
        return parse_error_event(runner, raw, "missing pid", errors);
    };
    let Some(comm) = raw.get("comm").and_then(|v| v.as_str()).map(str::to_string) else {
        return parse_error_event(runner, raw, "missing comm", errors);
    };

    Event::new_with_timestamp(timestamp, runner.to_string(), pid, comm, raw)
}

The constructors name the source and the timestamp field per probe: BinaryRunner::ssl(path) is ("SSL", "ssl", "timestamp_ns") and BinaryRunner::stdio(path) is ("Stdio", "stdio", "timestamp_ns"). The process probe has its own ProcessRunner (timestamp field timestamp), which also handles seed PIDs and the CLOCK_SYNC and PROBE_LIVENESS records the loader emits. A fourth runner, SystemRunner in ext/analysis/src/runners/system.rs, has no BPF at all: it samples CPU and memory from /proc at an interval.

A first analyzer: putting clocks in line

The BPF side stamps events with bpf_ktime_get_ns(), nanoseconds since boot. That is cheap and monotonic but useless for joining with an agent's own session log, which uses wall-clock time. The first analyzer on every runner converts it. It is also the simplest example of the Analyzer trait: map one stream into another.

#[async_trait]
impl Analyzer for TimestampNormalizer {
    async fn process(
        &mut self,
        stream: EventStream,
    ) -> Result<EventStream, Box<dyn std::error::Error + Send + Sync>> {
        let normalized_stream = stream.map(|mut event| {
            // Convert timestamp from nanoseconds since boot to milliseconds since UNIX epoch
            let timestamp_ms = boot_ns_to_epoch_ms(event.timestamp);
            event.timestamp = timestamp_ms;
            event
        });

        Ok(Box::pin(normalized_stream))
    }
}
pub fn boot_ns_to_epoch_ms(ns_since_boot: u64) -> u64 {
    let boot_time_secs = get_boot_time_secs();
    let boot_time_ms = boot_time_secs * 1000;
    let offset_ms = (ns_since_boot / 1_000_000) as i64;
    (boot_time_ms + offset_ms) as u64
}

The boot time is a whole number of seconds (from the sysinfo crate's System::boot_time(), cached once), so absolute times can be off by up to a second while the relative order of events from all probes stays exact. Keep that in mind when you compare AgentSight times with timestamps in an agent's JSONL transcript.

The HTTP chain on the TLS runner

The TLS runner gets the longest chain, because raw SSL_read chunks are far from "an LLM call". configure_ssl_runner() adds the timestamp normalizer and an optional SSLFilter, then this:

pub(crate) fn add_http_analyzers(
    runner: BinaryRunner,
    include_raw_data: bool,
    http_filter: &[String],
    disable_auth_removal: bool,
) -> BinaryRunner {
    let mut runner = runner.add_analyzer(Box::new(
        SSEProcessor::new_with_timeout(30000).defer_transport_to_http(),
    ));
    let parser = if include_raw_data {
        HTTPParser::new()
    } else {
        HTTPParser::new().disable_raw_data()
    };
    runner = runner.add_analyzer(Box::new(parser));
    runner = runner.add_analyzer(Box::new(HTTPDecompressor::new()));
    runner = runner.add_analyzer(Box::new(
        SSEProcessor::new_with_timeout(30000).defer_transport_to_http(),
    ));
    if !http_filter.is_empty() {
        runner = runner.add_analyzer(Box::new(HTTPFilter::with_patterns(http_filter.to_vec())));
    }
    if !disable_auth_removal {
        runner = runner.add_analyzer(Box::new(AuthHeaderRemover::new()));
    }
    runner
}

Read it as a pipeline:

  • HTTPParser (about 4,400 lines, the biggest analyzer) reassembles HTTP/1.1 messages and HTTP/2 frames from the plaintext chunks, keyed by the TLS transport handle the BPF side reports, and decodes HPACK headers.
  • HTTPDecompressor undoes gzip and similar content-encodings so bodies are readable JSON.
  • SSEProcessor handles server-sent events, the text/event-stream format both Anthropic and OpenAI use to stream a reply. It accumulates the deltas (Anthropic text and JSON blocks, OpenAI reasoning and tool_calls) into one response with a 30 s timeout. It appears twice for two input shapes. The first copy sees raw ssl events; with defer_transport_to_http() it leaves alone any chunk that carries a TLS transport identity, because, as its comment says, "exact-identity captures must be reconstructed by HTTPParser first" or concurrent responses would collapse onto one pid/tid key. The second copy, after the parser, assembles the streams of parsed http_parser responses.
  • AuthHeaderRemover strips headers such as authorization, x-api-key and cookie before anything is stored, unless you disable it. The plaintext of every request is visible to the probe, so this is the one thing standing between your API key and a SQLite file.

Wiring it together

AgentRunner is itself a Runner. It runs its child runners, merges their streams with select_all, and applies global analyzers to the merged stream:

        let mut streams = Vec::new();
        for runner in &mut self.runners {
            streams.push(runner.run().await?);
        }
        let mut stream = Box::pin(select_all(streams)) as EventStream;
        for analyzer in &mut self.analyzers {
            stream = analyzer
                .process(stream)
                .await
                .map_err(|error| format!("Global analyzer error: {error}"))?;
        }
        Ok(stream)

build_trace_agent_with_view() in collector/src/cmd_trace.rs assembles the whole thing for record and debug trace: a TLS runner (with the chain above), a stdio runner (only with --pid), a process runner, a system runner, and finally one global analyzer that feeds the shared view and its sinks:

    if let Some(path) = cfg.db_path.as_deref() {

Tip

select_all interleaves events in arrival order, not timestamp order. A TLS chunk and an execve that happened in the same millisecond may reach the view in either order. That is one reason the view pairs things by identifiers (exchange id, PID, TLS handle) wherever it can and treats time only as a fallback.

Correlating intent with actions

At this point the collector has two kinds of events in one stream: LLM exchanges (from TLS) and system events (exec, exit, file, network, stdio, resource samples). The whole point of AgentSight is to tie them together, so that "the model asked for bash -c 'npm test'" and "PID 41822 ran npm test, opened 312 files and exited 1" end up on the same row of the timeline.

What the paper proposes

The paper describes a two-stage design. First, a real-time engine links events using three signals:

  • Process lineage. The fork/execve tree from the process probe. Every child an agent spawns, however deep, is attributed to that agent.
  • Temporal proximity. Actions that start within a short window after an LLM response are candidates for having been caused by it. The paper uses a window of 100–500 ms.
  • Argument matching. Filenames, URLs and commands that appear in the model's reply are matched against the arguments of later syscalls (execve argv, openat paths, connect addresses).

Second, the correlated, condensed trace is handed to a separate "observer" LLM (the paper's phrase is using "AI to watch AI"), with a prompt that asks it to judge the behaviour, for example whether a sequence looks like a prompt-injection attack. It returns a natural-language explanation and a confidence score. The first stage cuts the volume down so that the second, slower and costlier stage only sees a summary.

What the code does today

The repository has moved on since the paper, and the correlation logic now lives in a materialized view (ext/analysis/src/view/). The MaterializingAnalyzer hands each Event to the MaterializedView, which turns it into a CanonicalEvent with a kind (LlmRequest, LlmResponse, ProcessExec, ProcessExit, FsOpen, FsWrite, FsMutation, StdioRpc, ResourceSample, …) and projects it into tables held in BTreeMaps: LLM calls, token usage, tool calls, process nodes, audit events, sessions, network targets and resource samples. Every row is also passed to the sinks (SQLite, OpenTelemetry), and the web UI reads the same view.

The first join is request ↔ response. When the HTTP layer has a stable identity for an exchange (HTTP/1.1 on a known TLS connection, or an HTTP/2 stream id), the pairing is exact and carries a confidence close to 1:

    fn ingest_llm_response(&mut self, event: &CanonicalEvent) -> ViewResult<()> {
        let Some(pid) = event.pid else {
            return Ok(());
        };
        if let Some(exchange_id) = event.http_exchange_id.as_deref()
            && let Some(req) = self.pending_by_exchange.remove(exchange_id)
        {
            let confidence = event.confidence.unwrap_or_else(|| {
                if event.correlation_method.as_deref() == Some("h2_stream") {
                    1.0
                } else {
                    0.98
                }
            });
            return self.upsert_llm_pair(req, event, confidence);
        }
        // Explicit HTTP identity must never silently fall back to a different
        // pending request on the same worker thread.
        if event.http_exchange_id.is_some() || event.correlation_version == Some(2) {
            return self.insert_orphan_llm_response(event);
        }
        if let Some(tid) = event.tid
            && let Some((req, confidence)) = self.take_matching_request(pid, tid, event)
        {
            return self.upsert_llm_pair(req, event, confidence);
        }
        self.insert_orphan_llm_response(event)
    }

Note the policy: a response that has an exchange identity but no matching request is stored as an orphan (correlation_status = "unlinked") rather than guessed onto some other request from the same thread. Older captures without that identity fall back to a PID/TID match. This was tightened in the most recent release (commit 33390661, "correlate HTTP exchanges by TLS connection and stream").

The second join is response → tool call. Once a response is complete, the view walks its body for tool requests in both vendor formats: OpenAI's tool_calls array and Anthropic's SSE content_block of type tool_use. Each becomes a ToolCallRow that records the PID that made the call and inherits the exchange's confidence:

The third join is process lineage. Every exec creates a process node with a stable id process-{pid}-{timestamp} (so PID reuse does not merge two different processes), every exit closes it, and parent PIDs from the probe link nodes into a tree. File and network events become audit rows tagged with the PID and comm, which places them under the right node.

The fourth join is session ↔ process, and the design note docs/design/view-session-process-model.md states the rule plainly: "Session-to-process mapping is core, but it is not Session == PID. It is a match between an agent session and a process tree, with evidence and confidence." An agent session (as described by the agent's own transcript file, for example under ~/.claude/projects/) is matched to a live process tree by evidence types such as proc_fd (the transcript path is open in /proc/<pid>/fd), ebpf_file (eBPF saw the process touch the transcript), llm_traffic, command_match and sticky (a previous high-confidence binding still holds). Paper vs. code

We did not find the paper's temporal-window and argument-matching heuristics as a separate engine in the current tree; the view joins by explicit identifiers (exchange id, PID lineage, session evidence) and puts events on a common clock, which leaves temporal reading to the timeline. The observer-LLM stage is not part of the runtime either. The closest thing is skills/ (agent-interaction-insights, agentsight-system-friction, evolve-agent-skills, …), which the repo itself calls "prototypes for a shareable skills pack, not AgentSight runtime code". Treating these skills as the successor of the observer LLM is our reading, not a statement from the project.

The web UI and the timeline

record starts a small hyper web server (collector/src/server/web.rs) on 127.0.0.1:7395 unless you pass --no-server; --server-port changes the port. The frontend is a Next.js app under ext/web/ (built through frontend/) whose static output is embedded in the binary, so there is nothing else to install. The README lists its pages: / (overview), /timeline, /tree, /logs and /metrics.

The API surface is small and versioned: GET /api/v1/info, POST /api/v1/capabilities, GET /api/v1/snapshot, GET /api/v1/overview, /api/v1/sessions/<id> and POST /api/v1/sessions/<id>/messages. The snapshot endpoint is guarded by an evidence.read capability check and serves the materialized view, the agent-native sessions and the SQLite database together. The browser client asks for it with an audit limit (/api/v1/snapshot?audit_limit=…, in frontend/src/lib/nodeClient.ts). agentsight report export -o snapshot.json writes a snapshot to a file "for web dashboard" (README; the schema is in docs/snapshot-schema.md), so a capture can be viewed away from the machine that recorded it.

The timeline (ext/web/components/timeline/) draws one horizontal lane per event source and lets you filter by source, comm and PID. The grouping is literally this:

A minimap and zoom controls help on long runs. The /tree page (ext/web/components/process-tree/) shows the same data the other way round: the process tree with LLM calls, tool calls, file and network events folded into each node.

There are also two text front ends. agentsight top is a live ranked view of sessions (sortable by cpu, rss, tokens, execs, fail, files, net or agent), and agentsight report prints summaries, token usage, audit trails or full prompts from a saved database.

One agent action, end to end

Here is a single step of a coding session followed through every layer: Claude Code decides to run the test suite. The function names, probe names, fields and analyzer names are the real ones from the sections above; the PIDs, paths and timings are illustrative.

1. The request leaves the agent

Claude Code serialises the conversation into a POST /v1/messages body and hands it to BoringSSL. Its SSL_write is stripped, so sslsniff found it by byte pattern and attached by offset. The entry probe stashes the buffer pointer under the thread id of the "HTTP Client" thread; the return probe reads the plaintext and submits a WRITE record to the ring buffer with timestamp_ns, pid, tid, transport_handle and the bytes.

2. The reply streams back

The API answers with text/event-stream. Each chunk arrives through SSL_read and becomes a READ record on the same transport handle. One of the events is a content_block_start whose block has "type": "tool_use", "name": "Bash" and, in following deltas, the input {"command": "npm test"}.

3. The collector turns chunks into a call

The SSL runner parses each JSON line into an Event. TimestampNormalizer moves it to epoch milliseconds, HTTPParser rebuilds request and response on that connection, HTTPDecompressor and SSEProcessor turn the stream into one response, and AuthHeaderRemover drops the API key. In the view, ingest_llm_response pairs it with the pending request by exchange id (confidence 0.98 for HTTP/1.1, 1.0 for an HTTP/2 stream), and ingest_sse_tools emits a ToolCallRow Bash with related_pid = the agent's PID.

4. The agent forks a shell

Claude Code spawns bash -c "npm test". The kernel fires tp/sched/sched_process_exec; the process probe records PID, parent PID, filename and full argv. User space sees that the parent is tracked, so the child is tracked too, and its PID goes into tracked_pids so in-kernel filters accept its later events. The same happens for npm and the node it starts.

5. The tests touch the system

node opens hundreds of files. fexit/security_file_open reports each resolved path once (the LRU dedup map suppresses repeats). Writes, renames and connect calls are counted per key in event_agg_map and flushed by user space as summaries instead of one record per call.

6. Exit codes close the loop

Each process ends with tp/sched/sched_process_exit, carrying exit code, duration and peak RSS. The view closes the matching process-{pid}-{ts} nodes. A non-zero exit from npm is now visible next to the tool call that caused it.

7. One story on screen

The next request the agent sends contains the tool result (the test output), which closes the intent side. On /timeline you see the LLM call, then the bash, npm and node bars starting just after it, then the next LLM call. On /tree the same processes hang under the agent node, and agentsight report audit --json lists them. Every row has already been written to agentsight-*.db and, with --otel, exported as gen_ai.* spans.

           "--set-rpath", formula_opt_lib("glibc"),
           bin/"agentsight"
  end
end

As of 2026-11-06 the formula pins v1.0.31 (last bumped 2026-09-16), while the latest GitHub release is v1.0.35, so Homebrew users are four releases behind.

From docs/build.md. You need Rust 1.88.0+; the eBPF capture path also needs Linux with eBPF, Node.js 18+, clang and LLVM, libelf and zlib headers, make, and the libbpf/bpftool submodules (hence --recursive). On Ubuntu/Debian make install installs the system dependencies.

Everyday commands

These lines and their comments are copied from the README's usage block, plus agentsight vis, which writes an animated replay of a Git worktree's agent file activity to output/agent-nebula.gif:

agentsight top                               # live ranked view; uses eBPF when sudo is already available
sudo agentsight record -- claude             # record a command
agentsight report                            # high-level latest-run summary (default)
agentsight report list                       # recorded sessions in this directory
agentsight report prompts --json             # full LLM request/response JSON
agentsight report token --group-by dir       # token usage by session/process working directory
agentsight report audit --json               # process spawns, file opens, API calls
agentsight report serve                      # open the web UI for the latest session in this directory
agentsight report export -o snapshot.json    # export for web dashboard; see docs/snapshot-schema.md
agentsight report --local                    # summarize native Claude/Codex/Gemini sessions
agentsight monitor install-service           # install/start the background monitor service
agentsight vis

record -- <command> resolves the command through $PATH, symlinks and shebang wrappers to the real ELF that contains the TLS code, derives the --comm filter from the command name, runs the agent with your terminal attached (as your user; only the probes are elevated), and stops when it exits. For other cases:

# Python tools (aider, open-interpreter, ...) and Node tools (Gemini CLI, ...)
sudo ./agentsight record -c "python"
sudo ./agentsight record -c node

# an agent in a container or a Kubernetes pod
sudo ./agentsight record -c node --binary-path docker://openclaw
sudo ./agentsight record -c node --binary-path k8s://agents/openclaw/gateway

# full trace with the web UI, exported as OpenTelemetry GenAI spans
sudo ./agentsight debug trace --server
sudo ./agentsight debug trace --otel --otel-endpoint http://localhost:4318

# the probes on their own
sudo ./bpf/sslsniff --binary-path ~/.local/share/claude/versions/2.1.39
sudo ./bpf/process -c python
sudo ./bpf/stdiocap -p 12345
What happened when we tried it

On this curriculum's build machine (Debian 12, glibc 2.36, Linux 6.1) the v1.0.35 release binary started (agentsight --version printed agentsight 1.0.35 after a "GLIBC_2.39 not found" warning), and agentsight top --once --plain worked from session files. Live capture did not: sudo ./agentsight debug process -- -c python3 failed because the embedded probe loaders need glibc 2.38 or newer. So we could not test the probes on this kernel. On an older distribution, build from source or use the Homebrew formula, which supplies its own glibc for the main binary; whether that also covers the extracted probe loaders we did not verify.

The paper

AgentSight was published as "AgentSight: System-Level Observability for AI Agents Using eBPF" by Yusheng Zheng (UC Santa Cruz), Yanpeng Hu (ShanghaiTech University), Tong Yu (eunomia-bpf Community) and Andi Quinn (UC Santa Cruz), in PACMI '25, the 4th Workshop on Practical Adoption Challenges of ML for Systems, co-located with SOSP '25 in Seoul (pages 110–115, DOI 10.1145/3766882.3767169). The preprint is arXiv:2508.02736 (v1 2 August 2025, v2 15 August 2025). It is a six-page workshop paper: it argues for boundary tracing and the two-stream model, sketches the correlation engine described above, and reports a small evaluation. The paper describes a prototype of roughly 6,000 lines of Rust and C plus a 3,000-line TypeScript frontend; the repository today is considerably larger.

Overhead

The authors measured Claude Code 1.0.62 (with Claude 4) on Ubuntu 22.04 and Linux 6.14.0, working on the bpf-developer-tutorial repository (chapter 9), three runs per task:

TaskBaseline (s)With AgentSight (s)Overhead
Understand repo127.98132.333.4%
Code writing22.5423.644.9%
Repo compilation92.4092.720.4%

The average is 2.9%. These are end-to-end task times, which are dominated by model latency, so they say little about per-event probe cost; the paper does not report micro-benchmarks. The README's "less than 3% CPU overhead" appears to come from this table.

Case studies

  • Prompt injection. A README points the agent at a URL that hides instructions; the agent then reads /etc/passwd and sends it out. The correlation engine merged 521 raw events into 37, and the observer LLM flagged the sequence as an attack with high confidence.
  • Reasoning loop. A crewAI research agent on gpt-4o-mini kept repeating a failing web search, a "try-fail-re-reason" loop that burns tokens and is visible as a repeating pattern of identical LLM calls and failed tool runs.
  • Multi-agent coordination. Six collaborating Claude Code subagents produced 3,153 events after correlation, and the trace exposed contention on file locks between them.

Benefits and limitations

Benefits

  • No SDK, proxy or code change; works on closed-source, statically linked CLIs such as Claude Code (Bun/BoringSSL) and Codex (rustls).
  • Sees both what the agent was told and what every descendant process did, including work the agent's own logs leave out.
  • Tamper-resistant relative to the agent: a manipulated agent cannot switch off a kernel hook it does not know about.
  • Stable hooks: SSL_write and sched_process_exec change far more slowly than agent frameworks.
  • One binary, local-first storage (SQLite), standard export (OTel GenAI), and a no-root fallback from session files on any OS.

Limitations

  • Linux only for live capture, and it needs root or CAP_BPF/CAP_SYS_ADMIN.
  • TLS capture depends on finding the right functions: stripped binaries rely on byte patterns and per-version offsets, which break when a new Bun or Codex build changes the code.
  • It recognizes LLM calls by JSON bodies; protobuf (Cursor's Connect protocol) or unknown APIs yield no LLM rows. Electron IDE agents are out of reach for eBPF.
  • Observation only. It explains, it does not block; enforcement is ActPlane's job (chapter 24).
  • Plaintext prompts, file contents and possibly secrets end up on disk; header stripping helps but bodies are stored as captured.
  • The semantic stage (observer LLM) is probabilistic and, in the current tree, lives outside the runtime as skills.
  • Release probes are linked against a recent glibc (≥ 2.38 in v1.0.35), so older distributions may need a source build.

Related work

Inside this curriculum. ActPlane turns AgentSight's question "what did the agent do?" into "what may it do?", tracking information-flow labels with BPF-LSM and blocking violations. RewardGuard and safe change uses AgentSight and ActPlane as the evidence and enforcement layers for a runtime integrity contract against reward hacking. Actime and Akeep compose AgentSight and ActPlane into one command and one run record and back up the session transcripts AgentSight reads. The uprobe and tracepoint mechanics are covered in chapter 5, and userspace uprobes in bpftime.

LLM observability. Langfuse, LangSmith and Helicone record prompts and responses through an SDK or proxy, and the OpenTelemetry GenAI semantic conventions standardize the gen_ai.* attributes AgentSight exports. AgentOps (Dong et al., 2024) proposes a taxonomy of what to observe in agent systems; Watson (Rombaut et al., 2024) targets observability of agent reasoning. All of these live inside the application and see intent but not system effects.

System security monitoring. Falco and Tracee use eBPF to watch syscalls and raise alerts against rules. They see actions but have no idea which LLM reply caused them.

Agent attacks. InjecAgent (Zhan et al., ACL Findings 2024) benchmarks indirect prompt injection in tool-using agents, and "Breaking Agents" (Zhang et al., 2024) studies malfunction amplification. They motivate the paper's first two case studies.

Quiz

Q1. Why does AgentSight hook SSL_write and SSL_read instead of capturing packets?

TLS encrypts everything below the library call. A uprobe on the entry and return of SSL_write/SSL_read sees the buffer before encryption or after decryption, with no proxy and no certificate tricks.

Q2. What does an Analyzer do in the Rust collector?

Analyzer::process(stream) -> Result<EventStream, _>. Runners produce streams, analyzers transform them, and AgentRunner merges runner streams with select_all before global analyzers run.

Q3. Why does every runner start with TimestampNormalizer?

bpf_ktime_get_ns() is monotonic since boot. Adding the boot time puts probe events on the same axis as session files and the timeline. It does not reorder anything.

Q4. An LLM response carries an HTTP exchange id but no pending request has that id. What does the view do?

"Explicit HTTP identity must never silently fall back to a different pending request on the same worker thread." Only captures without an identity use the older PID/TID match.

Q5. Which three signals does the paper's real-time correlation engine use?

Lineage from fork/execve, a short time window after an LLM response, and matching of filenames, URLs and commands in the reply against syscall arguments. A second-stage observer LLM then judges the condensed trace.

Q6. You want to prevent an agent from sending a secret file to the network. Is AgentSight the right tool?

AgentSight records and explains. Blocking needs hooks that can return an error, such as BPF-LSM; see chapter 24.
