Chapter 32

Glossary, reading list and learning paths

Thirty-one chapters bring in a lot of vocabulary and cite many papers. This appendix collects both in one place: each term gets a short definition and a link to the section that explains it, and each cited paper is listed once with the chapters that cite it. It ends with three routes through the curriculum and a short quiz that covers all of it.

Prerequisites: noneOrg: eunomia-bpfReference chapter

How to use this appendix

This chapter only collects material from chapters 01–31. Each glossary definition is a short version of what a chapter says, and the link next to it goes to the section with the full explanation, code and diagrams. If a definition and its chapter seem to disagree, trust the chapter: it was written from the source code and documents, and this page was written from the chapters.

The reading list was built from the References sections of chapters 01–31. Kernel documentation, LWN articles, blog posts, mailing-list patches and conference talks without a paper are left out, because each chapter already links them in context. Papers that a chapter only mentions in passing, with no entry in its reference list, are also left out. The research notes for this chapter (research/32-glossary-and-reading-list.md) list those mentions by name.

Key idea

The curriculum makes one argument across seven parts. eBPF is a verified extension mechanism: the verifier (03) is what makes it safe to load other people's code into a privileged context. The eunomia-bpf projects then carry the same idea to new places: user-space processes (14), GPU drivers and kernels (20), collective-communication libraries (21), path lookup (28) and the operating-system boundary of AI agents (24). Many glossary terms are either a piece of the verifier's safety argument or a new hook where that argument is reused.

Glossary

The 148 terms are in alphabetical order. Type in the box to filter them: the filter matches the term, its definition and a few synonyms, so loop finds bpf_loop, may_goto and open-coded iterators, and gpu finds everything from CUPTI to UVM. Every term has an anchor, so another page can link to it as 32-glossary-and-reading-list.html#g-slug (for example #g-tnum-tristate-number).

148 terms
512-byte stack
Each eBPF function has a stack frame of at most 512 bytes, addressed downward from the read-only frame pointer R10. Large buffers therefore live in maps (often a per-CPU array) instead. See 02 · The 512-byte stack.
Abstract interpretation
Running a program over abstract values (types, ranges, tnums) instead of concrete ones, so that one analysis covers every possible input. The kernel verifier, PREVAIL and NCCLbpf's rank-agreement check all work this way. See 03 · Pass 2: path-by-path symbolic execution; 03 · PREVAIL: abstract interpretation done "properly" (PLDI 2019).
Actime
A runner for agent sessions that starts ActPlane (policy), AgentSight (observability) and Akeep (backup) as child processes and gathers what they write into one run directory. Actime itself loads nothing into the kernel. See 27 · The three planes.
ActPlane
eunomia-bpf's information-flow enforcement engine for AI agent harnesses. eBPF programs put labels on processes and files, propagate them along fixed rules, and block or kill at sinks that a small rule language names. See 24 · The architecture in one picture; 24 · The policy language.
AF_XDP
A socket family that receives packets which an XDP program redirects into a memory area (UMEM) shared between kernel and user space, so user space gets packets without going through the normal network stack. See 07 · AF_XDP: packets to userspace, zero-copy.
AgentCgroup
A characterization study and controller for the OS resources AI coding agents use. It gives each tool call its own cgroup and reacts to short memory and CPU bursts with memcg_bpf_ops and a sched_ext scheduler. See 25 · Architecture; 25 · Three mismatches.
AgentSight
Observability for AI agents that watches two boundaries: the plaintext of the agent's TLS traffic with the LLM (captured with uprobes) and its kernel-visible actions (processes, file opens). The two streams are correlated afterwards. See 23 · AgentSight: system-level observability for AI agents.
Agent skill
A directory with a SKILL.md file of instructions that a coding agent loads when a task matches it. eunomia-bpf keeps its maintenance and research procedures in this form. See 31 · What a skill is; 17 · The agent skill.
Agni
The CAV 2023 work that checks the soundness of the kernel verifier's range-analysis code by turning it into SMT formulas. See 03 · Agni: verifying the range analysis (CAV 2023).
Akeep
A version-control-style backup tool for agent session history. It reads provider-native session files and stores them as BLAKE3-named chunks and manifests in a content-addressed archive. See 27 · Akeep: version control for agent history; 27 · The archive: content-addressed chunks.
ALU / ALU64
The two arithmetic instruction classes: ALU works on the low 32 bits (and zero-extends the result), ALU64 on the full 64-bit register. See 02 · ALU and ALU64.
Arena
BPF_MAP_TYPE_ARENA (Linux 6.9): a sparse memory region of up to 4 GB that a BPF program and a user-space process both map, so pointer-based data structures can be shared. qwen3-ebpf keeps a 1.5 GB model in one. See 04 · Arena: a heap shared with user space; 29 · Where the weights live: a 1.5 GB BPF arena.
Atomic operations
BPF_ATOMIC instructions that add, and, or, xor, exchange or compare-and-exchange a memory word, optionally returning the old value. ISA v4 adds load-acquire and store-release. See 02 · Atomic operations; 04 · Concurrency: atomics, per-CPU data and spin locks.
BCC
BPF Compiler Collection. Its tools embed Clang and compile the BPF C on the target machine at run time against the local kernel headers, the approach that BTF and CO-RE replaced for portable tools. See 06 · The old answer: compile on the target (BCC); 08 · How each framework builds and loads.
BPF (Berkeley Packet Filter)
The 1993 packet-filter design by McCanne and Jacobson: a small register-based virtual machine that runs a user-supplied filter on each packet in the kernel, so only matching packets are copied to user space. See 01 · The origin: the BSD Packet Filter (1993).
bpf-compatible
A eunomia-bpf toolchain that fetches BTF for kernels without native BTF from BTFHub, trims it to what your programs use, embeds the archive in the executable, and picks the right one at run time. See 13 · What bpf-compatible is.
BPF-Ext
An ATC '26 paper and prototype that adds new native operations (kinsn) to the eBPF pipeline: the verifier checks an equivalent ordinary eBPF sequence, and the JIT emits native code instead. See 19 · Backend 2: kinsn, verified native operations (BPF-Ext).
bpffs
The BPF pseudo-filesystem, usually mounted at /sys/fs/bpf. Pinning a map, program or link there keeps it alive after the loading process exits. See 04 · Pinning maps in bpffs; 06 · BPF links and pinning.
bpfix
A Rust command-line tool that reads a verifier log, finds where the proof the failing instruction needed was established and then lost, and prints a compiler-style diagnostic. The repository also contains a study of 235 real rejections and an LLM repair benchmark. See 17 · What bpfix is, and what it is not; 17 · How bpfix works.
BPF link
A kernel object, held through a file descriptor, that represents one attachment of a program to a hook. Closing the last reference detaches the program unless the link is pinned. See 06 · BPF links and pinning.
bpf_loop
A helper (Linux 5.17) that calls a callback up to n times. The verifier checks the callback body once, with the loop index as an unknown value, instead of unrolling the loop. See 03 · Loops.
BPF LSM
Programs of type BPF_PROG_TYPE_LSM attached to Linux Security Module hooks. A non-zero return (an error such as -EPERM) denies the operation. ActPlane and namei_ext's neighbours use it. See 05 · BPF LSM.
bpfopt
The bytecode-to-bytecode optimizer in bpf-benchmark: a command-line tool that lifts eBPF to LLVM IR, optimizes it, and lowers it back, without making BPF system calls itself. See 19 · bpfopt is an LLVM round trip.
bpf() system call
The single system call through which user space creates maps, loads programs and attaches them. A command argument such as BPF_PROG_LOAD, BPF_MAP_CREATE or BPF_LINK_CREATE selects the operation. See 06 · Underneath: the bpf() syscall.
bpftime
eunomia-bpf's userspace eBPF runtime. It intercepts the loader's bpf() calls, keeps maps in shared memory, and runs uprobe and syscall programs inside the target process through binary rewriting. It is described in an OSDI '25 paper. See 14 · What bpftime is; 15 · bpftime in practice.
BPF-to-BPF call
A call from one BPF function to another inside the same program (a subprogram), with its own stack frame. It is distinct from a helper call, a kfunc call and a tail call. See 02 · BPF-to-BPF calls; 04 · BPF-to-BPF calls.
BPF token
An object created from a specially mounted bpffs instance through which an administrator delegates a chosen subset of BPF permissions to a less privileged process, such as one inside a container. See 03 · Privileged and unprivileged loading.
bpftool
The kernel's own command-line tool for BPF: it lists and dumps programs and maps, generates vmlinux.h and skeletons, and trims BTF with gen min_core_btf. See 08 · The kernel's own tooling: bpftool and selftests; 06 · The Makefile, step by step.
bpftrace
A high-level tracing language with awk-like one-liners that compiles to BPF. MCPtrace exposes it as MCP tools, and bpftime can run its programs in user space. See 08 · How each framework builds and loads; 15 · bpftrace in userspace.
bpf_wq
A BPF workqueue item (Linux 6.10) embedded in a map value. The callback runs later from a kernel workqueue in process context, so it can do longer work than the hook that started it. See 29 · Which hook triggers computation: XDP, then bpf_wq.
BTF
BPF Type Format: compact type information (structs, fields, function prototypes) for the kernel, modules and BPF objects. It enables CO-RE, kfuncs, typed tracing and pretty-printed maps. See 06 · BTF: the BPF Type Format.
btf_custom_path
A libbpf open option that tells libbpf to read kernel BTF from a given file instead of /sys/kernel/btf/vmlinux; bpf-compatible uses it to supply trimmed BTF. See 13 · What libbpf does with btf_custom_path.
BTFHub
A community archive of BTF files for distribution kernels built without embedded BTF, used by tools that must run CO-RE programs on those kernels. See 06 · Kernels without BTF: BTFHub and minimized BTF; 13 · bpf-compatible vs. BTFHub.
Causal profiling
Profiling that estimates how much speeding up a piece of code would speed up the whole program by slowing down everything else running concurrently (Coz, SOSP '15). The megakernel feasibility notes study it for GPUs. See 31 · The two ideas being combined.
cBPF (classic BPF)
The original BPF: two 32-bit registers (A and X), a small scratch memory, and forward-only jumps. Linux still accepts it for socket filters and seccomp, and translates it to eBPF internally. See 01 · The classic BPF machine; 01 · Classic BPF in Linux: socket filters, a JIT, and seccomp.
CFG check
The verifier's first pass: it walks the control-flow graph and rejects unreachable instructions, jumps out of range and (unless loops are allowed) back edges. See 03 · Pass 1: the control-flow graph check.
cgroup programs
Program types attached to a cgroup v2 directory that apply to every task in it, for example packet filtering, socket address rewriting, sysctl access and device access. See 05 · cgroup programs.
cgroup v2
The unified Linux control-group hierarchy: a tree of directories, each with controller files (CPU, memory, I/O, pids) that limit and account for the processes inside. See 25 · A tree of directories; 25 · The four controllers that matter here.
Cilium
A Kubernetes networking, security and observability project whose datapath is built from tc, XDP and socket eBPF programs; Hubble is its flow-observability layer. See 08 · Networking: Cilium and Hubble.
cilium/ebpf
A pure-Go library for loading and managing eBPF programs and maps, with a bpf2go code generator. See 08 · One program, seven frameworks; 11 · The Go sibling: cilium-ebpf-starter-template.
Collective (NCCL)
A communication operation in which all ranks of a communicator take part, such as AllReduce or AllGather. NCCL implements collectives across GPUs. See 21 · Ranks, communicators and collectives.
Complexity limit
The verifier stops after processing 1,000,000 instructions across all explored paths (BPF_COMPLEXITY_LIMIT_INSNS) and rejects the program. Unprivileged programs are also limited to 4,096 instructions in size. See 03 · The complexity limits.
Constant blinding
A JIT hardening that XORs immediates from the program with a random value, so that attacker-chosen constants do not appear verbatim in executable memory (a defence against JIT spraying). See 02 · Constant blinding.
CO-RE
Compile Once – Run Everywhere. Clang records each field access as a relocation against BTF types, and libbpf rewrites the offsets at load time to match the running kernel's BTF. See 06 · CO-RE relocations: recording intent at compile time; 06 · How libbpf applies relocations at load time.
CUPTI
NVIDIA's CUDA Profiling Tools Interface. Its Activity and Callback APIs report kernel launches and timings. xpu-perf loads it as an injection library to collect GPU-side events. See 22 · Background: how you get data out of an NVIDIA GPU; 22 · Code walkthrough 2: the CUPTI injection library.
data / data_end
The two context fields that point to the start and end of a packet in XDP and tc programs. The verifier only allows a packet access after a comparison against data_end proves it is in bounds. See 07 · Parsing packets safely: data, data_end and the verifier; 03 · Packet bounds: data and data_end.
Dentry
The kernel's cached record that links a name in a directory to an inode. The path walk moves from dentry to dentry; a struct path pairs a dentry with a mount. See 28 · Dentries, inodes, mounts and struct path.
Device-side eBPF
eBPF programs compiled to PTX and run inside CUDA kernels on the GPU (through bpftime and llvmbpf), used by gpu_ext to see warp-level behaviour that host hooks cannot see. See 20 · The device side: eBPF inside CUDA kernels; 15 · GPU and CUDA probes.
Dynptr
A verifier-tracked pointer plus a run-time length, for memory whose size is only known at run time, for example variable-size ring-buffer records. See 04 · Variable-size records: dynptrs.
eBPF
Extended BPF (Linux 3.15 onward): eleven 64-bit registers, a verifier, a JIT, maps, helpers, and many hook types beyond networking. Today "BPF" in kernel usage usually means eBPF. See 01 · 2014: extended BPF; 01 · "eBPF" vs "BPF": what the names mean today.
eBPF for Windows
Microsoft's port of the eBPF toolchain to Windows. It verifies programs with PREVAIL instead of the Linux verifier, then either translates them to a signed native driver or JIT-compiles them with uBPF. See 08 · eBPF for Windows and PREVAIL.
ecc
The eunomia-bpf compiler. It builds a BPF C program with Clang and produces a package of the object plus JSON metadata (maps, globals, export types), which ecli can run without a hand-written loader. See 10 · ecc: what the compiler generates.
ecli
The eunomia-bpf runner. It loads a package from a file, a URL or an OCI registry, turns global variables into command-line options, attaches the programs and prints the exported events. See 10 · ecli: running from a file, a URL or a registry.
eGPU
An HCDS '25 workshop prototype for running eBPF on GPUs, since merged into the gpu_ext/bpftime line of work. See 20 · Related work; 15 · GPU and CUDA probes.
EIM (Extension Interface Model)
The OSDI '25 model in which an application developer declares which state, functions and hook points an extension may use as capabilities, and a deployer groups them into extension classes. bpftime enforces it. See 14 · EIM concepts; 14 · How the paper says bpftime enforces EIM.
fentry / fexit
Tracing programs that attach to the entry and exit of a kernel function through a BPF trampoline. Arguments are typed through BTF, and fexit also sees the return value. They are cheaper than kprobes. See 05 · fentry, fexit, fmod_ret: the BPF trampoline.
Flame graph
A visualization of sampled call stacks in which each box is a frame and its width is the share of samples passing through it. It is built from folded stacks: one semicolon-joined stack plus a count per line. xpu-perf adds GPU kernels as leaves. See 22 · Folded stacks and flame graphs; 22 · The output: folded stacks with GPU leaves.
fmod_ret
A trampoline program type that runs before a function and can make it return a chosen value without running its body. It is allowed only on functions marked for error injection. See 05 · fentry, fexit, fmod_ret: the BPF trampoline.
GPTtrace
The org's 2023 tool that asks an LLM (through OpenAI function calling) to write and run bpftrace programs from a natural-language request. MCPtrace is its successor. See 30 · GPTtrace: the 2023 prompt pipeline.
gpu_ext
eunomia-bpf's extension of the NVIDIA open GPU kernel modules with struct_ops hooks for UVM prefetching, eviction and scheduling, plus device-side eBPF, so GPU memory and scheduling policy can be written in BPF. See 20 · What gpu_ext is; 20 · How the driver hooks work.
Helper function
A kernel function with a fixed number that BPF programs call (for example bpf_map_lookup_elem). Helpers are a stable ABI and the list is frozen; new functionality is added as kfuncs. See 04 · What a helper is; 04 · Why helpers are frozen.
IFC (information-flow control)
Security that tracks where data came from (its labels) as it flows through the system and checks policy where it leaves, instead of only checking who may open what. ActPlane applies it to AI agents. See 24 · Information-flow control in ten minutes; 24 · IFC in operating systems.
Inline hook
bpftime's way of running a uprobe handler: it overwrites the start of the target function with a jump into the handler instead of a trap instruction, so no kernel entry is needed. See 14 · Binary rewriting for uprobes: inline hooks instead of traps.
JIT compiler
Translates verified BPF bytecode into native machine code at load time, so programs run at close to native speed. On x86-64 it maps BPF registers directly to CPU registers. See 02 · The x86-64 JIT; 02 · Controlling the JIT.
JIT spraying
An attack that hides machine code in the constants of JIT-compiled code and then jumps into the middle of an instruction. Constant blinding is the BPF mitigation. See 02 · Constant blinding.
JMP / JMP32
The branch instruction classes: conditional and unconditional jumps, calls and exit. JMP32 compares only the low 32 bits. See 02 · JMP and JMP32.
K2
A SIGCOMM 2021 program-synthesis optimizer for BPF that searches for shorter equivalent programs and checks equivalence and safety with an SMT solver. ebpf-correctness-verifier's encoding descends from its model. See 18 · K2: where the model comes from (SIGCOMM 2021).
KEN / Kgent
The org's research prototype that turns a natural-language request into an eBPF program with an LLM agent and checks it with symbolic execution and the verifier (arXiv 2023 as KEN, eBPF '24 as Kgent). See 30 · KEN, published as Kgent.
kfunc
A kernel function exposed to BPF and identified by its BTF ID rather than a fixed number (Linux 5.13 onward). kfuncs are not a stable ABI, and flags such as acquire and release tell the verifier about ownership. See 04 · kfuncs: kernel functions exposed through BTF; 04 · The flags: how the verifier learns ownership.
kinsn
A BPF-Ext operation with two forms: an instantiated sequence of ordinary eBPF instructions that the verifier checks (the proof sequence), and native machine code that the JIT emits instead. See 19 · One operation, two forms; 19 · A real module: rotate on x86-64.
kprobe / kretprobe
A dynamic probe on almost any kernel instruction (usually a function entry), or on function return for kretprobe. It is flexible, but tied to kernel internals that change between versions. See 05 · kprobe and kretprobe: attach anywhere.
KV cache
In transformer inference, the stored key and value vectors of earlier tokens, so each new token only computes its own. qwen3-ebpf keeps it in BPF maps. See 29 · The KV cache; 29 · Attention and the KV cache in BPF.
Label (IFC)
A tag attached to data or a process that records its origin or sensitivity, such as SECRET or AGENT. Sources add labels, propagation rules move them, and sinks check them. See 24 · Labels, sources, sinks and propagation; 24 · Label state in maps.
Landlock
A Linux security module that lets unprivileged processes restrict their own file and network access. It is a neighbour of BPF LSM and namei_ext. See 28 · Landlock and BPF LSM: the access-control neighbours.
LBR
Last Branch Record: a CPU feature that records recent taken branches. bpfperf reads it with bpf_get_branch_snapshot to profile branches per BPF instruction. See 19 · The archived design: an fexit sidecar reading LBR.
LDDW
The only 16-byte eBPF instruction. It loads a 64-bit immediate, and in special forms a map reference that the loader relocates. See 02 · The wide instruction: lddw; 16 · LDDW: how maps get in.
libbpf
The kernel-maintained C library that opens BPF ELF objects, applies CO-RE relocations, creates maps, loads and attaches programs. Most modern tools are built on it. See 06 · The libbpf object lifecycle.
LL / LL128 / Simple
NCCL's three wire protocols: LL and LL128 pack flags with data for low latency on small messages, and Simple uses larger chunks and fences for bandwidth. See 21 · Protocols: LL, LL128, Simple.
llvmbpf
eunomia-bpf's eBPF VM that lifts bytecode to LLVM IR and compiles it with LLVM, either at run time (JIT) or ahead of time to a native object, with PTX and SPIR-V GPU targets. bpftime uses it as a backend. See 16 · What llvmbpf is, and what it is not; 16 · Lifting eBPF to LLVM IR.
Map
A kernel key/value object, referred to through a file descriptor, that BPF programs and user space share. It is the only place where state persists between program runs. See 04 · What a map is; 04 · The map type zoo.
may_goto
An instruction (Linux 6.9) with a hidden run-time counter that bounds loop iterations, so the verifier need not prove termination. The can_loop macro wraps it. See 03 · Loops.
MCP (Model Context Protocol)
An open JSON-RPC protocol through which an LLM client discovers and calls tools that a server provides. schedcp and MCPtrace expose kernel tooling this way. See 30 · The Model Context Protocol in one section.
MCPtrace
A Rust MCP server that exposes bpftrace through four tools, so an agent can list probes and run tracing scripts. See 30 · MCPtrace: bpftrace as four MCP tools.
memcg_bpf_ops
A struct_ops type from an RFC kernel patch series that lets BPF callbacks influence memory-cgroup reclaim and throttling. AgentCgroup uses it to protect a high-priority session. See 25 · Memory: memcg_bpf_ops; 25 · The kernel side (RFC patches).
Memory controller limits
cgroup v2 memory files: memory.min/low protect memory from reclaim, memory.high throttles above a soft limit, and memory.max is the hard limit, past which the OOM killer runs. See 25 · memory.min, low, high, max.
Merlin
An ASPLOS 2024 multi-tier optimizer for eBPF that works on LLVM IR and on bytecode. See 18 · Merlin (ASPLOS 2024).
Mixed mode (bpftime)
bpftime configurations in which userspace programs cooperate with real kernel eBPF: either maps and verification go to the kernel, or a daemon captures a kernel tracer's bpf() calls. See 15 · Kernel-user mixed mode; 14 · Kernel–userspace interop.
namei_ext
An experimental kernel patch that adds a cgroup-attached program type to pathname lookup. Its return value chooses one of four actions: pass, hide, redirect, or select a policy-provided target. See 28 · What namei_ext adds to the kernel; 28 · Policy decision: one function, four actions.
NCCL
NVIDIA's Collective Communication Library, which implements AllReduce and other collectives across GPUs and picks an algorithm, protocol and channel count for each call. See 21 · NCCL background a programmer needs.
NCCLbpf
eunomia-bpf's NCCL plugins that run verified eBPF policies through bpftime to choose collective algorithm, protocol and channels, and to collect telemetry. See 21 · What NCCLbpf is; 21 · The architecture at a glance.
NVBit
NVIDIA's dynamic binary instrumentation framework for GPU code (MICRO '19). It is a common baseline for bpftime's GPU probes. See 15 · GPU probes vs NVBit.
Open-coded iterator
Iterator kfuncs (Linux 6.4) with new/next/destroy functions that let a program write a normal loop, such as bpf_for(i, 0, n). The verifier checks that the loop state converges. See 03 · Loops.
Operator mode / event mode
qwen3-ebpf's two ways to run a model. In operator mode, user-space C calls BPF programs for each operator. In event mode, an XDP packet starts inference and BPF schedules every layer itself through a workqueue, with weights in an arena. See 29 · Operator mode: C schedules, BPF computes; 29 · Event mode: XDP, a BPF arena and a self-requeuing workqueue.
Per-CPU map
Map variants that keep a separate value per CPU, so programs update them without atomics. User space reads all the copies and sums them. See 04 · Per-CPU variants.
Perf buffer
The older event channel: one ring per CPU, written with bpf_perf_event_output. Events from different CPUs can arrive out of order. See 04 · Perf buffer: one ring per CPU.
perf_event program
A program attached to a perf event, such as a CPU clock, that runs on every sample. It is the basis of eBPF CPU profilers such as xpu-perf's. See 05 · perf_event: sampling; 22 · Code walkthrough 1: CPU sampling with perf_event eBPF.
Policy domain
In ActPlane, the policy boundary for one process tree. A child domain can add rules and narrow its scope, but never remove what it inherits (monotonic tightening). See 24 · Policy domains.
Precision tracking
Verifier bookkeeping that marks which scalar registers' exact values mattered for safety. Other registers can then be ignored when comparing states, which makes pruning more effective. See 03 · Precision tracking.
PREVAIL
A BPF verifier based on abstract interpretation with numerical domains (PLDI 2019). It is used by eBPF for Windows, bpftime and NCCLbpf as an alternative to the kernel verifier. See 03 · PREVAIL: abstract interpretation done "properly" (PLDI 2019); 08 · eBPF for Windows and PREVAIL.
Program type
The kind of a BPF program (XDP, kprobe, LSM, struct_ops, ...). It decides where the program attaches, what its context argument is, and which helpers and kfuncs it may call. See 05 · The map: hooks on the kernel/user stack; 05 · Comparison table.
PSI (Pressure Stall Information)
Kernel accounting of how much time tasks spend stalled waiting for CPU, memory or I/O, reported system-wide and per cgroup. See 25 · PSI: measuring the pain.
PTX
NVIDIA's virtual GPU assembly language. llvmbpf can compile eBPF to PTX so that bpftime can run programs inside CUDA kernels. See 16 · GPU targets: PTX and SPIR-V.
Rank-agreement check
NCCLbpf's load-time analysis that rejects a policy unless its decision depends only on inputs that are the same on every rank, since ranks that choose different algorithms would deadlock. See 21 · Why divergent choices deadlock; 21 · The load-time rank-agreement check.
RCU-walk / ref-walk
The two modes of Linux pathname lookup. RCU-walk proceeds without taking references, under RCU; ref-walk is the slower fallback that takes references and locks. See 28 · RCU-walk and ref-walk.
Registers R0–R10
eBPF's eleven 64-bit registers: R0 holds return values, R1–R5 hold arguments, R6–R9 are callee-saved, and R10 is the read-only frame pointer. See 02 · The register file; 02 · What each register is for.
Register state types
The verifier's type for each register, such as SCALAR_VALUE, PTR_TO_CTX, PTR_TO_MAP_VALUE_OR_NULL or PTR_TO_PACKET. The type decides which operations and memory accesses are allowed. See 03 · Register state types; 03 · Reading the state in a log line.
Reward hacking
An agent raising its benchmark score by gaming the evaluator (reading hidden tests, editing scorers) instead of solving the task. See 26 · What reward hacking is; 26 · The enforceability taxonomy.
Reward integrity contract
RewardGuard's per-trial contract naming reward-private sources, reward-critical objects, reward-visible sinks and validation gates. It is enforced through AgentSight and ActPlane. See 26 · The reward-integrity contract; 26 · How RewardGuard uses AgentSight and ActPlane.
RFC 9669
The IETF standard (October 2024) that defines the BPF instruction set: encoding, instruction classes and conformance groups. See 02 · The standard: RFC 9669.
Ring buffer
BPF_MAP_TYPE_RINGBUF (Linux 5.8): one multi-producer, single-consumer buffer shared by all CPUs. Programs reserve and commit records in place, and events keep their order across CPUs. See 04 · BPF ring buffer: one MPSC ring for all CPUs; 04 · How it works inside.
Safe change (agent-check-restore-safety)
A runtime for agents whose external operations (such as a payment) may have taken effect when the reply never arrived. It decides from a hash-linked History which actions remain safe, with explicit Rules and Certificates. See 26 · Part B · Safe change after external operations; 26 · Five core terms.
schedcp
An MCP control plane that lets an LLM agent choose, configure, generate and verify sched_ext schedulers for a workload. See 30 · schedcp: an MCP control plane for sched_ext; 30 · The seven MCP tools.
sched_ext
The extensible scheduler class (Linux 6.12): a CPU scheduler written as a struct_ops BPF program. If the program misbehaves, the kernel falls back to the default scheduler. See 05 · sched_ext: a CPU scheduler written in BPF; 09 · Lesson 44: a CPU scheduler in BPF.
scx_flatcg
A sched_ext example scheduler that flattens the cgroup hierarchy into one level of weighted shares. AgentCgroup uses it for CPU control. See 25 · CPU: scx_flatcg under sched_ext.
SEC()
The libbpf macro that puts a function in an ELF section whose name, such as SEC("kprobe/do_unlinkat"), tells libbpf the program type and attach target. See 05 · How libbpf names hooks: SEC().
seccomp-bpf
System-call filtering with classic BPF programs that inspect the syscall number and arguments (Linux 3.5). It is still cBPF, not eBPF. See 01 · seccomp-bpf (Linux 3.5): BPF beyond networking; 05 · What about seccomp?.
Skeleton
A header that bpftool gen skeleton generates from a BPF object, with typed open/load/attach/destroy functions and direct access to maps and global variables. See 06 · BPF skeletons and global variables.
sk_lookup
A program type that chooses which listening socket receives a new connection or datagram, for example to serve many addresses from one socket. See 07 · sk_lookup: choosing the listening socket.
SMT solver / Z3
A solver that decides whether logical formulas over bit-vectors, arrays and other theories can be satisfied. ebpf-correctness-verifier encodes two programs in Z3 and asks for an input on which they differ. See 18 · Inside the SMT encoding; 18 · The query and the solver.
Socket filter
The original Linux BPF use: a filter program attached to a socket (SO_ATTACH_FILTER or SO_ATTACH_BPF) that decides how much of each packet the socket receives. See 01 · Linux Socket Filter; 07 · Socket filters.
sockops / sk_msg / sockmap
Socket-level program types: sockops reacts to TCP events, and sk_msg and sockmap redirect data between sockets inside the kernel without going through the full stack. See 07 · sockops, sk_msg and sockmap.
Spectre mitigations
Verifier and JIT changes (pointer-arithmetic masking, speculation barriers, restricted unprivileged features) that stop BPF programs from being used as Spectre gadgets. See 03 · Spectre mitigations.
Speculative ReJIT
bpf-benchmark's bytecode-only optimization path. A preloaded shim intercepts program loads, runs optimization passes, and submits each candidate through the normal verifier, keeping the original program if the candidate is rejected. See 19 · Backend 1: bpfopt and the shim (speculative ReJIT); 19 · The candidate loop.
State embedding
An OSDI 2024 technique for finding verifier bugs: it embeds the verifier's claimed abstract states into the program as run-time checks and executes it, so wrong claims show up. See 03 · Testing the verifier: state embedding (OSDI 2024).
State pruning
The verifier optimization that stops exploring a path when its state at an instruction is covered by a state already proven safe there. See 03 · State pruning.
struct_ops
A mechanism that lets a set of BPF programs implement a kernel ops table (TCP congestion control, sched_ext, HID-BPF, gpu_ext's UVM hooks, memcg_bpf_ops). See 05 · struct_ops: implementing kernel interfaces in BPF; 20 · Registering a struct_ops type from a module.
Tail call
A jump from one BPF program into another through a program-array map, without returning. The chain is limited to 33 calls. See 04 · Tail calls.
tc / cls_bpf
BPF programs attached to the traffic-control layer on ingress or egress, after the sk_buff exists. In direct-action mode the program's return code is the verdict. See 07 · tc: cls_bpf and direct-action; 07 · tc return codes.
TCX
The link-based tc attachment (Linux 6.6) that offers a link-based alternative to qdisc-based cls_bpf. It supports ordered multi-program attachment and BPF links. See 07 · TCX: link-based tc attachment (Linux 6.6).
tnum (tristate number)
The verifier's bit-level abstract value: a value/mask pair in which each bit is known 0, known 1 or unknown. It tracks alignment and masked values alongside numeric ranges. See 03 · Tristate numbers; 03 · Tristate numbers made rigorous (CGO 2022).
Tracepoint / raw tracepoint / tp_btf
Stable trace points compiled into the kernel. Classic tracepoints pass a formatted record, raw tracepoints pass the raw arguments, and tp_btf passes typed arguments through BTF. See 05 · Static tracepoints, raw tracepoints and tp_btf.
Trampoline (BPF trampoline)
Machine code that the kernel generates on the fly at a function's entry to call fentry, fexit and fmod_ret programs with typed arguments. It is cheaper than the breakpoint behind a kprobe. See 05 · fentry, fexit, fmod_ret: the BPF trampoline.
Translation validation
Instead of proving a compiler or optimizer correct once, checking each output against its input, for example with an SMT solver. ebpf-correctness-verifier does this for optimized eBPF. See 18 · Translation validation in one page; 18 · Translation validation outside eBPF.
Tuner plugin (NCCL)
An NCCL plugin interface that is asked, for each collective, which algorithm, protocol and channel count to use. NCCLbpf implements it with eBPF policies. See 21 · How NCCL picks, and where a tuner plugs in; 21 · Inside the tuner adapter.
uBPF / rbpf
Small userspace eBPF virtual machines (C and Rust respectively) with interpreters and simple JITs. bpftime can use uBPF as a backend. See 08 · Userspace VMs and runtimes: uBPF, rbpf, bpftime; 14 · The VM layer: ubpf or llvmbpf.
Unprivileged BPF / CAP_BPF
Loading rules by privilege: CAP_BPF (plus CAP_PERFMON or CAP_NET_ADMIN for tracing or networking) grants BPF without full root. Since Linux 5.13, CONFIG_BPF_UNPRIV_DEFAULT_OFF makes kernel.unprivileged_bpf_disabled default to 2 (disabled, re-enablable by an administrator). See 03 · Privileged and unprivileged loading.
uprobe / uretprobe
A dynamic probe on an instruction in a user-space binary or library. In the kernel it is a breakpoint trap, which bpftime replaces with an inline hook. See 05 · What a uprobe is; 05 · How a uprobe works inside the kernel.
USDT
User Statically-Defined Tracing: probe points compiled into applications (as nops plus ELF notes) that uprobe-based tools can attach to by name. See 05 · USDT: static probes in user space.
UVM (Unified Virtual Memory)
CUDA's single address space shared by CPU and GPU. Pages migrate on demand when the GPU faults, and the driver decides prefetching and eviction; gpu_ext adds BPF hooks for both. See 20 · Device memory and unified virtual memory; 20 · GPU page faults, replay and migration.
uXDP
Running unmodified XDP programs in user space (for example under DPDK or AF_XDP) with bpftime; the subject of an eBPF '25 workshop paper. See 15 · XDP programs in userspace; 07 · Beyond the kernel: eunomia-bpf's userspace XDP work.
Verifier
The kernel component that statically checks every program at load time: memory safety, termination, correct helper use and privilege rules. Programs it cannot prove safe are rejected. See 03 · Where the verifier sits; 03 · The eBPF verifier.
Verifier log
The trace of the verifier's per-instruction register states and its final error, requested with a log buffer at load time. It is the input to bpfix. See 03 · Reading common verifier errors; 17 · Get a log that bpfix can use.
vmlinux.h
One header with every type of the running kernel, generated from its BTF with bpftool btf dump file /sys/kernel/btf/vmlinux format c, so CO-RE programs need no kernel headers. See 06 · vmlinux.h: one header with every kernel type.
Wasm-bpf
eunomia-bpf's runtime that runs the user-space half of an eBPF tool as a WebAssembly module, which reaches libbpf through a small host ABI. The kernel half stays ordinary eBPF. See 12 · Architecture; 12 · The host ABI: seven functions.
XDP
eXpress Data Path: a hook in the network driver's receive path that runs a BPF program on each packet before the kernel allocates an sk_buff. See 07 · XDP in depth; 07 · XDP: in the driver, before the sk_buff.
XDP actions
An XDP program's verdict: XDP_PASS, XDP_DROP, XDP_TX (send back out the same interface), XDP_REDIRECT or XDP_ABORTED. See 07 · The five actions; 07 · XDP_TX and XDP_REDIRECT: forwarding without the stack.
xpu-perf
eunomia-bpf's continuous profiler that combines eBPF CPU sampling with CUPTI GPU events and joins them into CPU→GPU flame graphs. See 22 · xpu-perf at a glance; 22 · Architecture.
zpoline
A system-call hooking technique (USENIX ATC '23) that rewrites each syscall instruction into call *%rax and places a trampoline at virtual address zero. bpftime uses it for syscall tracepoints in user space. See 14 · Binary rewriting for syscalls: a zpoline in the target.

Paper reading list

These are the 97 distinct papers cited in the reference lists of chapters 01–31, deduplicated across chapters. Each entry gives the venue and year as the citing chapter states them. The Cited in column links to every chapter that cites the paper, and that chapter explains why it matters. Preprints are marked, and so are the few drafts and reports that have not been peer reviewed, so you can weigh them accordingly. RFC 9669 is a standard rather than a paper, but it is the primary source for the ISA, so it is included and marked.

Where to start reading

If you read only five papers: McCanne and Jacobson's BSD Packet Filter (1993) for the original design; the XDP paper (CoNEXT 2018) for eBPF in the data path; PREVAIL (PLDI 2019) for what a principled verifier looks like; Agni (CAV 2023) for how the kernel's own range analysis was checked; and the bpftime paper (OSDI '25) for how the org carries the model into user space.

How the section links were made

The table of contents and the heading anchors on every page are generated in the browser by the shared script. A heading's id is its text in lower case, with each run of non-alphanumeric characters replaced by a hyphen and leading and trailing hyphens removed:

const heads = [...document.querySelectorAll("main h2, main h3")];
/* ... */
heads.forEach((h, i) => {
  if (!h.id) h.id = h.textContent.trim().toLowerCase().replace(/[^a-z0-9]+/g, "-").replace(/(^-|-$)/g, "") || "s" + i;
  /* ... */
});

The glossary links in this chapter were computed with the same rule from each chapter's actual headings, and every target was checked to exist. If you rename a heading in another chapter, rerun that check. Chapter 23 was being written while this appendix was assembled, so its terms link to the chapter as a whole, not to a section.

Check your understanding

These questions each draw on two or more parts of the curriculum.

Q1. A CO-RE tool must run on an old distribution kernel with no /sys/kernel/btf/vmlinux. What does bpf-compatible do?

CO-RE needs the running kernel's types (06). bpf-compatible ships them for you: it fetches BTFHub archives, trims them with bpftool gen min_core_btf, embeds them, and picks one at run time (13).

Q2. How does bpftime implement a sys_enter_openat tracepoint inside an ordinary process?

A syscall can come from libc, a static binary or inline assembly, so hooking one function is not enough. bpftime rewrites every syscall instruction, as zpoline (ATC '23) does (14).

Q3. NCCLbpf runs PREVAIL on every policy and then a second, rank-agreement analysis. Why is PREVAIL not enough?

Safety here has a distributed part that per-program verification cannot see. The second pass is again an abstract interpretation (03), but it tracks where each value came from rather than its range (21).

Q4. A register's tnum is value 0b0100, mask 0b0011. Which concrete values can it hold?

Mask bits are unknown, and the other bits are known to equal value: bit 2 is 1, bit 3 and above are 0, bits 0 and 1 are free (03).

Q5. What does ebpf-correctness-verifier prove about an optimizer such as K2 or bpfopt?

Translation validation checks each output against its input instead of proving the transformer correct once (18). That fits optimizers that are themselves untrusted, such as an LLM agent (19).

Q6. gpu_ext and sched_ext add hooks with struct_ops. What does namei_ext add?

namei_ext follows the model of cgroup/sysctl: BPF_PROG_TYPE_NAMEI_EXT, attached to a cgroup v2 directory, with pass, hide, redirect or select-target as its result (28). Compare it with struct_ops in 05.
