Chapter 09

bpf-developer-tutorial: learning eBPF one small tool at a time

Part I explained the eBPF machine: the instruction set, the verifier, maps, hooks, CO-RE and the networking datapath. This chapter looks at the eunomia-bpf organization's most widely used repository, a set of short, runnable lessons that turn those ideas into working tools. We cover what the project contains, how it builds, how it is tested, and the order in which to read it.

Prerequisites: 01, 05, 06Repo: eunomia-bpf/bpf-developer-tutorial @ 110b91f8~45 min

What this project is

bpf-developer-tutorial describes itself as "eBPF Developer Tutorial: Learning eBPF Step by Step with Examples". It is a single Git repository of self-contained lessons. Each lesson is a directory under src/ with a README in English and Chinese, the eBPF kernel code, and usually a user-space loader and a Makefile. The README sets the scope plainly: the tutorial "does not cover complex concepts and scenario introductions". Its goal is to provide examples of eBPF tools that are "very short, starting with twenty lines of code", so that developers pick up the development method by running and changing real programs.

The project was created in December 2022. It is MIT-licensed and is mainly written by GitHub user yunwei37 (Yusheng Zheng, who also signs lesson 36 and founded eunomia-bpf), by far the largest committer, with a number of other regular contributors. When surveyed on 2026-11-06 it had about 4,300 GitHub stars and 600 forks, which makes it one of the most visible eunomia-bpf repositories. The same lessons are published as a website at eunomia.dev/tutorials and mirrored on Gitee.

Who it is for

The introductory lesson (src/0-introduce/README.md) names three audiences: developers building custom kernel solutions, system administrators who want better performance and security, and people exploring kernel technology. The stated prerequisites are a Linux kernel of 4.8 or newer (the README recommends 5.15+ or 6.9+ for features such as arena and tokens), basic C, familiarity with processes and system calls, root access, and clang, llvm and libelf-dev. That matches the audience of this curriculum: a C programmer who knows Linux but not eBPF.

The lessons favor modern toolchains. The README explains that the project was inspired by the bcc Python developer tutorial, but that "using libbpf to develop eBPF applications is a relatively better choice". Examples therefore use CO-RE with libbpf, libbpf-rs, cilium/ebpf and eunomia-bpf, not BCC's runtime compilation. (Chapter 08 compares those frameworks.)

Key idea

Treat the repository as a workbook, not a textbook. Each directory answers one question ("which files does this process open?", "how do I schedule tasks in BPF?") with the smallest program that answers it. Theory is kept short in the README and lives in references such as the chapters of this curriculum. For each lesson, read the code first, run it, change one thing, and run it again.

Why it exists: the gap between the docs and a working tool

Kernel documentation explains every program type and helper but rarely gives a complete program, with a loader, that runs on a stock distribution kernel. The kernel's own samples/bpf/ and selftests are complete but written to test the kernel, not to teach. BCC's tools are good teaching material, but they compile at run time and need kernel headers on the target. The bpf-developer-tutorial sits between these. It shows the libbpf-bootstrap style of development (chapter 06) applied to many domains, and each lesson's README explains the code line by line.

The project solves three practical problems for a beginner:

  • Setting up a build environment. The early lessons need only the .bpf.c file and two downloaded binaries (ecc and ecli). The later lessons ship libbpf, bpftool, blazesym and a vmlinux.h for each architecture in src/third_party, so make works without system-wide libbpf.
  • Finding a lesson-sized example for a hook. Every common hook family has at least one lesson: tracepoints, kprobes, fentry, uprobes, USDT, perf events, LSM, tc, TCX, XDP, sockops, struct_ops, sched_ext, HID-BPF and BPF qdisc.
  • Knowing whether a lesson will run on your kernel. Each lesson declares its minimum kernel, required config options, hardware and CI status. A generated compatibility matrix collects all of these.

Tip

Before you start a Depth lesson, open src/compatibility.md and check the lesson's minimum kernel and config options against uname -r and /boot/config-$(uname -r). The range is wide: lesson 1 declares 4.8, lesson 52 (fsession) declares 7.0 and lesson 54 declares 6.19.

A side effect of generating the index: a lesson whose .config lacks a type drops out of it. At 110b91f8, 32-wallclock-profiler has level=Depth and no type, so it does not appear in the README or SUMMARY. bpftrace-tutorial has no .config at all. Both directories still exist and are worth reading.

How lessons are built: two toolchains

The README sends readers to two lessons for setup. For eunomia-bpf lessons, see src/1-helloworld. For libbpf lessons, see src/11-bootstrap. The two paths differ in who writes the user-space half (Figure 9.3).

Path 1: eunomia-bpf, ecc and ecli

The Basic lessons use the eunomia-bpf toolchain, which chapter 10 covers in depth. ecc compiles the .bpf.c file and packs the object with a JSON description into package.json. ecli loads that package, attaches every program, turns const volatile globals into command-line flags, and prints the events the program emits. A lesson in this style is just the kernel file, the README and a .config. The setup commands, copied from src/1-helloworld/README.md:

$ ./ecli -h
Usage: ecli [--help] [--version] [--json] [--no-cache] url-and-args

$ wget https://github.com/eunomia-bpf/eunomia-bpf/releases/latest/download/ecc && chmod +x ./ecc

Path 2: libbpf, bpftool and a skeleton

From lesson 11 onward most lessons have a Makefile derived from libbpf-bootstrap. The important rules, copied from src/11-bootstrap/Makefile:

LIBBPF_SRC := $(abspath ../third_party/libbpf/src)
BPFTOOL_SRC := $(abspath ../third_party/bpftool/src)
/* ... */
VMLINUX := ../third_party/vmlinux/$(ARCH)/vmlinux.h
INCLUDES := -I$(OUTPUT) -I../third_party/libbpf/include/uapi -I$(dir $(VMLINUX))
/* ... */
# Build BPF code
$(OUTPUT)/%.bpf.o: %.bpf.c $(LIBBPF_OBJ) $(wildcard %.h) $(VMLINUX) | $(OUTPUT) $(BPFTOOL)
	$(call msg,BPF,$@)
	$(Q)$(CLANG) -g -O2 -target bpf -D__TARGET_ARCH_$(ARCH)		      \
		     $(INCLUDES) $(CLANG_BPF_SYS_INCLUDES)		      \
		     -c $(filter %.c,$^) -o $(patsubst %.bpf.o,%.tmp.bpf.o,$@)
	$(Q)$(BPFTOOL) gen object $@ $(patsubst %.bpf.o,%.tmp.bpf.o,$@)

# Generate BPF skeletons
$(OUTPUT)/%.skel.h: $(OUTPUT)/%.bpf.o | $(OUTPUT) $(BPFTOOL)
	$(call msg,GEN-SKEL,$@)
	$(Q)$(BPFTOOL) gen skeleton $< > $@
/* ... */
# Build application binary
$(APPS): %: $(OUTPUT)/%.o $(LIBBPF_OBJ) | $(OUTPUT)
	$(call msg,BINARY,$@)
	$(Q)$(CC) $(CFLAGS) $^ $(ALL_LDFLAGS) -lelf -lz -o $@

Each lesson's Makefile builds a static libbpf.a and a "bootstrap" bpftool from the submodules on first use, so a fresh clone needs git submodule update --init --recursive. The vmlinux.h comes from the repository and is not generated from the running kernel's BTF. This works because of CO-RE (chapter 06): the header only has to be close enough to compile, and libbpf relocates field offsets at load time. It also has a cost, which shows up in lesson 52 below. The master src/Makefile finds every directory with a Makefile and runs make -C on each.

A few lessons use other toolchains: lesson 12 and xpu/flamegraph/profiler are Rust crates (lesson 12 uses libbpf-rs = "0.24" and blazesym). Lesson 37 builds Rust targets with cargo build. Lessons 39, 40, parts of 47 and xpu/gpu-kernel-driver are bpftrace .bt scripts. Lesson 47 also contains CUDA .cu programs.

Warning

Neither path is safe to try on a laptop you care about without reading the lesson first. Security lessons such as 24-hide, 26-sudo, 27-replace and 34-syscall show attacker techniques: they hide processes, rewrite what read() returns, and change syscall arguments. Lesson 28 pins a program so that it outlives its loader. Run these in a VM. The repository's own agent skill test-bpf-tutorial-kvm runs every BPF-loading step inside a short-lived KVM guest for the same reason.

Building one lesson end to end

The stepper below follows lesson 11 through a build. I ran these steps in this curriculum's orb (kernel 6.1, Debian clang 14.0.6) at commit 110b91f8.

1. Clone with submodules

From the README: git clone https://github.com/eunomia-bpf/bpf-developer-tutorial.git, then git submodule update --init --recursive. This fetches third_party/bpftool (which contains libbpf as a nested submodule) and third_party/blazesym. third_party/libbpf is a symlink to bpftool/libbpf.

2. Install the host packages

Lesson 11 lists sudo apt install clang libelf1 libelf-dev zlib1g-dev for Debian/Ubuntu and sudo dnf install clang elfutils-libelf elfutils-libelf-devel zlib-devel for Fedora/CentOS.

3. make

The first run builds bpftool and libbpf (dozens of CC lines), then the four lesson steps: BPF .output/bootstrap.bpf.o, GEN-SKEL .output/bootstrap.skel.h, CC .output/bootstrap.o, BINARY bootstrap. In my build the generated skeleton header was 116,660 bytes. It embeds the whole BPF object as a byte array.

4. Run it

sudo ./bootstrap prints a header and one line per exec and exit. On the orb I saw lines such as EXEC git … /opt/git/bin/git followed by EXIT git … [128] (1ms). CI runs the same binary as sudo timeout -s 2 3 src/11-bootstrap/bootstrap and treats exit code 124 (timeout) as success.

5. Clean up

make clean removes .output/ and the binary. Generated artifacts are no longer tracked in Git (PR #215, July 2026).

The six walkthroughs below cover the main shapes of a lesson: a tracepoint with a parameter (4), a kprobe next to fentry (2 and 3), the move from ring buffer events to a real loader (8 and 11), packet programs (20 and 21), an LSM policy (19), a sched_ext scheduler (44), and CUDA tracing (47). All code is copied from the repository at 110b91f8, and the commands come from each lesson's README.

Lesson 1 and 4: a tracepoint, a filter, and a flag for free

Lesson 1 is the smallest complete program in the repository: one tracepoint handler that prints the PID of every process that calls write().

/* SPDX-License-Identifier: (LGPL-2.1 OR BSD-2-Clause) */
#define BPF_NO_GLOBAL_DATA
#include "vmlinux.h"
#include <bpf/bpf_helpers.h>
#include <bpf/bpf_tracing.h>

typedef unsigned int u32;
typedef int pid_t;
const pid_t pid_filter = 0;

char LICENSE[] SEC("license") = "Dual BSD/GPL";

SEC("tp/syscalls/sys_enter_write")
int handle_tp(void *ctx)
{
	pid_t pid = bpf_get_current_pid_tgid() >> 32;
	if (pid_filter && pid != pid_filter)
		return 0;
	bpf_printk("BPF triggered sys_enter_write from PID %d.\n", pid);
	return 0;
}

Everything that chapter 05 calls a "hook contract" is visible here. SEC("tp/syscalls/sys_enter_write") picks the program type and the attach point. The context is ignored (void *ctx). The return value means nothing for a tracepoint. bpf_printk writes to the shared trace pipe. The README notes that it accepts at most three arguments, that the pipe is shared by every program, and that production tools should use ring buffers or perf arrays instead. BPF_NO_GLOBAL_DATA is there for kernels older than 5.2, which lack global variable support.

Lesson 4 (opensnoop) adds one idea: a global that user space sets before load.

#define BPF_NO_GLOBAL_DATA
#include <vmlinux.h>
#include <bpf/bpf_helpers.h>

/// @description "Process ID to trace"
const volatile int pid_target = 0;

SEC("tracepoint/syscalls/sys_enter_openat")
int tracepoint__syscalls__sys_enter_openat(struct trace_event_raw_sys_enter* ctx)
{
	u64 id = bpf_get_current_pid_tgid();
	u32 pid = id >> 32;

	if (pid_target && pid_target != pid)
		return false;
	// Use bpf_printk to print the process information
	bpf_printk("Process ID: %d enter sys openat\n", pid);
	return 0;
}

/// "Trace open family syscalls."
char LICENSE[] SEC("license") = "GPL";

const volatile places pid_target in the read-only data section. The BPF program cannot write it, the compiler cannot constant-fold it, and the loader can patch it before load. Because the value is fixed at load time, the verifier sees a known constant and can prune the dead branch. The filter runs in the kernel, so events you do not want never cross into user space. The /// @description comment is eunomia-bpf specific: ecc records it, and ecli turns the global into a documented flag. From the lesson README:

$ ecc opensnoop.bpf.c
Compiling bpf object...
Packing ebpf object and config into package.json...
$ ecli package.json -h
Usage: opensnoop_bpf [--help] [--version] [--verbose] [--pid_target VAR]

Trace open family syscalls.

Optional arguments:
  -h, --help    shows help message and exits 
  -v, --version prints version information and exits 
  --verbose     prints libbpf debug information 
  --pid_target  Process ID to trace 
/* ... */
$ sudo ./ecli run package.json  --pid_target 618
Running eBPF program...

The eunomia CI workflow runs this lesson both ways: ecli run src/4-opensnoop/package.json and the same command with --pid_target 1.

Lessons 2 and 3: the same probe as kprobe and as fentry

Lessons 2 and 3 trace the same kernel function, do_unlinkat, with two hook families. Reading them side by side is the fastest way to see what BTF-typed hooks give you.

SEC("kprobe/do_unlinkat")
int BPF_KPROBE(do_unlinkat, int dfd, struct filename *name)
{
	pid_t pid;
	const char *filename;

	pid = bpf_get_current_pid_tgid() >> 32;
	filename = BPF_CORE_READ(name, name);
	bpf_printk("KPROBE ENTRY pid = %d, filename = %s\n", pid, filename);
	return 0;
}

SEC("kretprobe/do_unlinkat")
int BPF_KRETPROBE(do_unlinkat_exit, long ret)
{
	pid_t pid;

	pid = bpf_get_current_pid_tgid() >> 32;
	bpf_printk("KPROBE EXIT: pid = %d, ret = %ld\n", pid, ret);
	return 0;
}
SEC("fentry/do_unlinkat")
int BPF_PROG(do_unlinkat, int dfd, struct filename *name)
{
	pid_t pid;

	pid = bpf_get_current_pid_tgid() >> 32;
	bpf_printk("fentry: pid = %d, filename = %s\n", pid, name->name);
	return 0;
}

SEC("fexit/do_unlinkat")
int BPF_PROG(do_unlinkat_exit, int dfd, struct filename *name, long ret)
{
	pid_t pid;

	pid = bpf_get_current_pid_tgid() >> 32;
	bpf_printk("fexit: pid = %d, filename = %s, ret = %ld\n", pid, name->name, ret);
	return 0;
}

Three differences matter. In the kprobe, BPF_KPROBE unpacks the arguments from struct pt_regs, and the pointer must be read with BPF_CORE_READ because the verifier treats it as an untrusted kernel address. In fentry, the BTF-typed argument can be dereferenced directly (name->name). The kretprobe sees only the return value, while fexit sees the arguments and the return value. The lesson 3 README claims fentry/fexit "run about 10x faster than kprobes". That figure is the repository's claim and is not measured here; chapter 05 explains why the trampoline is cheaper. The README also has a troubleshooting section for failed to attach: ERROR: strerror_r(-524)=22 (ENOTSUPP). The usual causes are a kernel older than 5.5 on x86 or 6.0 on arm64, or a kernel without CONFIG_DEBUG_INFO_BTF.

Lessons 8 and 11: from ring buffer events to your own loader

Lessons 7 and 8 replace bpf_printk with structured events. Lesson 7 uses a BPF_MAP_TYPE_PERF_EVENT_ARRAY and bpf_perf_event_output. Lesson 8 uses the BPF ring buffer (chapter 04), which declares its minimum kernel as 5.8:

struct {
	__uint(type, BPF_MAP_TYPE_RINGBUF);
	__uint(max_entries, 256 * 1024);
} rb SEC(".maps");

SEC("tp/sched/sched_process_exit")
int handle_exit(struct trace_event_raw_sched_process_template* ctx)
{
	struct task_struct *task;
	struct event *e;
	pid_t pid, tid;
	u64 id, ts, *start_ts, start_time = 0;
	
	/* get PID and TID of exiting thread/process */
	id = bpf_get_current_pid_tgid();
	pid = id >> 32;
	tid = (u32)id;

	/* ignore thread exits */
	if (pid != tid)
		return 0;

	/* reserve sample from BPF ringbuf */
	e = bpf_ringbuf_reserve(&rb, sizeof(*e), 0);
	if (!e)
		return 0;

	/* fill out the sample with data */
	task = (struct task_struct *)bpf_get_current_task();
	start_time = BPF_CORE_READ(task, start_time);

	e->duration_ns = bpf_ktime_get_ns() - start_time;
	e->pid = pid;
	e->ppid = BPF_CORE_READ(task, real_parent, tgid);
	e->exit_code = (BPF_CORE_READ(task, exit_code) >> 8) & 0xff;
	bpf_get_current_comm(&e->comm, sizeof(e->comm));

	/* send data to user-space for post-processing */
	bpf_ringbuf_submit(e, 0);
	return 0;
}

The verifier forces the if (!e) return 0; check: reserve may fail when the buffer is full, and every path must either submit or discard the record. BPF_CORE_READ(task, real_parent, tgid) follows two pointers with CO-RE relocations. With eunomia-bpf you pass the header to ecc, which exports the struct event layout, and ecli prints each field as a column:

$ ecc exitsnoop.bpf.c exitsnoop.h
Compiling bpf object...
Generating export types...
Packing ebpf object and config into package.json...
$ sudo ./ecli run package.json 
TIME     PID     PPID    EXIT_CODE  DURATION_NS  COMM
21:40:09  42050  42049   0          0            which
21:40:09  42049  3517    0          0            sh

Lesson 11 (bootstrap, from libbpf-bootstrap) is the turning point. The kernel side joins exec and exit through a hash map and adds a min_duration_ns parameter. The new part is that you write the loader yourself:

struct {
	__uint(type, BPF_MAP_TYPE_HASH);
	__uint(max_entries, 8192);
	__type(key, pid_t);
	__type(value, u64);
} exec_start SEC(".maps");

struct {
	__uint(type, BPF_MAP_TYPE_RINGBUF);
	__uint(max_entries, 256 * 1024);
} rb SEC(".maps");

const volatile unsigned long long min_duration_ns = 0;

SEC("tp/sched/sched_process_exec")
int handle_exec(struct trace_event_raw_sched_process_exec *ctx)
{
	/* ... */
	/* remember time exec() was executed for this PID */
	pid = bpf_get_current_pid_tgid() >> 32;
	ts = bpf_ktime_get_ns();
	bpf_map_update_elem(&exec_start, &pid, &ts, BPF_ANY);

	/* don't emit exec events when minimum duration is specified */
	if (min_duration_ns)
		return 0;
	/* ... */
	fname_off = ctx->__data_loc_filename & 0xFFFF;
	bpf_probe_read_str(&e->filename, sizeof(e->filename), (void *)ctx + fname_off);

	/* successfully submit it to user-space for post-processing */
	bpf_ringbuf_submit(e, 0);
	return 0;
}
	/* Load and verify BPF application */
	skel = bootstrap_bpf__open();
	if (!skel) {
		fprintf(stderr, "Failed to open and load BPF skeleton\n");
		return 1;
	}

	/* Parameterize BPF code with minimum duration parameter */
	skel->rodata->min_duration_ns = env.min_duration_ms * 1000000ULL;

	/* Load & verify BPF programs */
	err = bootstrap_bpf__load(skel);
	/* ... */
	/* Attach tracepoints */
	err = bootstrap_bpf__attach(skel);
	/* ... */
	/* Set up ring buffer polling */
	rb = ring_buffer__new(bpf_map__fd(skel->maps.rb), handle_event, NULL, NULL);
	/* ... */
	while (!exiting) {
		err = ring_buffer__poll(rb, 100 /* timeout, ms */);
		/* Ctrl-C will cause -EINTR */
		if (err == -EINTR) {
			err = 0;
			break;
		}
		/* ... */
	}

cleanup:
	/* Clean up */
	ring_buffer__free(rb);
	bootstrap_bpf__destroy(skel);

The skeleton functions __open, __load, __attach and __destroy are the libbpf object lifecycle from chapter 06. Writing skel->rodata->min_duration_ns between open and load is how a libbpf program does what ecli did with --pid_target. The __data_loc_filename & 0xFFFF line decodes a tracepoint's variable-length field: the low 16 bits are the offset from the start of the record. Build and run, from the README:

Lessons 20 and 21: tc and XDP

The first two packet lessons are deliberately tiny and still use ecc. They show the one verifier rule every packet program must follow: prove that each header lies inside [data, data_end) before reading it (chapters 03 and 07).

#define TC_ACT_OK 0
#define ETH_P_IP 0x0800 /* Internet Protocol packet	*/

/// @tchook {"ifindex":1, "attach_point":"BPF_TC_INGRESS"}
/// @tcopts {"handle":1, "priority":1}
SEC("tc")
int tc_ingress(struct __sk_buff *ctx)
{
    void *data_end = (void *)(__u64)ctx->data_end;
    void *data = (void *)(__u64)ctx->data;
    struct ethhdr *l2;
    struct iphdr *l3;

    if (ctx->protocol != bpf_htons(ETH_P_IP))
        return TC_ACT_OK;

    l2 = data;
    if ((void *)(l2 + 1) > data_end)
        return TC_ACT_OK;

    l3 = (struct iphdr *)(l2 + 1);
    if ((void *)(l3 + 1) > data_end)
        return TC_ACT_OK;

    bpf_printk("Got IP packet: tot_len: %d, ttl: %d", bpf_ntohs(l3->tot_len), l3->ttl);
    return TC_ACT_OK;
}

Lesson 19: an LSM hook that says no

Lesson 19 is the first lesson whose return value the kernel obeys. It attaches to the socket_connect LSM hook and refuses IPv4 connections to 1.1.1.1:

#define EPERM 1
#define AF_INET 2

const __u32 blockme = 16843009; // 1.1.1.1 -> int

SEC("lsm/socket_connect")
int BPF_PROG(restrict_connect, struct socket *sock, struct sockaddr *address, int addrlen, int ret)
{
    // Satisfying "cannot override a denial" rule
    if (ret != 0)
    {
        return ret;
    }

    // Only IPv4 in this example
    if (address->sa_family != AF_INET)
    {
        return 0;
    }

    // Cast the address to an IPv4 socket address
    struct sockaddr_in *addr = (struct sockaddr_in *)address;

    // Where do you want to go?
    __u32 dest = addr->sin_addr.s_addr;
    bpf_printk("lsm: found connect to %d", dest);

    if (dest == blockme)
    {
        bpf_printk("lsm: blocking %d", dest);
        return -EPERM;
    }
    return 0;
}

The extra int ret argument is, in the kernel documentation's words, "the return value from the previous BPF program or 0 if it's the first hook". Returning it unchanged when it is non-zero is a convention, not something the kernel enforces: the hook's result is whatever the last BPF program returns, so a program that ignored ret and returned 0 could undo an earlier BPF program's denial. The code comment calls this the "cannot override a denial" rule. 16843009 is 0x01010101, which reads the same in either byte order, so the comparison works without bpf_htonl. This shortcut only works for that address. For any other address you need the byte-order conversion.

Lesson 44: a CPU scheduler in BPF

Lesson 44 brings in sched_ext, the struct_ops-based scheduler class merged in Linux 6.12 (chapter 05, which also quotes this lesson's select_cpu callback in its struct_ops section). The program is the kernel's scx_simple example, copied into the lesson with its own copy of the scx headers under include/. It implements a global weighted virtual-time scheduler that can switch to FIFO:

#include <scx/common.bpf.h>

char _license[] SEC("license") = "GPL";

const volatile bool fifo_sched;

static u64 vtime_now;
UEI_DEFINE(uei);
/* ... */
#define SHARED_DSQ 0
/* ... */
s32 BPF_STRUCT_OPS(simple_select_cpu, struct task_struct *p, s32 prev_cpu, u64 wake_flags)
{
	bool is_idle = false;
	s32 cpu;

	cpu = scx_bpf_select_cpu_dfl(p, prev_cpu, wake_flags, &is_idle);
	if (is_idle) {
		stat_inc(0);	/* count local queueing */
		scx_bpf_dispatch(p, SCX_DSQ_LOCAL, SCX_SLICE_DFL, 0);
	}

	return cpu;
}

void BPF_STRUCT_OPS(simple_enqueue, struct task_struct *p, u64 enq_flags)
{
	stat_inc(1);	/* count global queueing */

	if (fifo_sched) {
		scx_bpf_dispatch(p, SHARED_DSQ, SCX_SLICE_DFL, enq_flags);
	} else {
		u64 vtime = p->scx.dsq_vtime;

		/*
		 * Limit the amount of budget that an idling task can accumulate
		 * to one slice.
		 */
		if (vtime_before(vtime, vtime_now - SCX_SLICE_DFL))
			vtime = vtime_now - SCX_SLICE_DFL;

		scx_bpf_dispatch_vtime(p, SHARED_DSQ, SCX_SLICE_DFL, vtime,
				       enq_flags);
	}
}

void BPF_STRUCT_OPS(simple_dispatch, s32 cpu, struct task_struct *prev)
{
	scx_bpf_consume(SHARED_DSQ);
}
/* ... */
void BPF_STRUCT_OPS(simple_stopping, struct task_struct *p, bool runnable)
{
	if (fifo_sched)
		return;
	/* ... */
	p->scx.dsq_vtime += (SCX_SLICE_DFL - p->scx.slice) * 100 / p->scx.weight;
}
/* ... */
s32 BPF_STRUCT_OPS_SLEEPABLE(simple_init)
{
	return scx_bpf_create_dsq(SHARED_DSQ, -1);
}

SCX_OPS_DEFINE(simple_ops,
	       .select_cpu		= (void *)simple_select_cpu,
	       .enqueue			= (void *)simple_enqueue,
	       .dispatch		= (void *)simple_dispatch,
	       .running			= (void *)simple_running,
	       .stopping		= (void *)simple_stopping,
	       .enable			= (void *)simple_enable,
	       .init			= (void *)simple_init,
	       .exit			= (void *)simple_exit,
	       .name			= "simple");

The flow: on wakeup, select_cpu picks a CPU and, if it is idle, places the task directly in that CPU's local dispatch queue (DSQ). Otherwise enqueue puts the task in one shared DSQ, ordered by virtual time unless FIFO mode is on. When a CPU runs out of work, dispatch pulls the next task from the shared DSQ. stopping charges the task for the slice it used, scaled by the inverse of its weight, which is what makes the scheduler fair. SCX_OPS_DEFINE builds the struct sched_ext_ops that the loader registers as a struct_ops map. A per-CPU array counts local and global queueing, and the loader prints the counts every second.

From the README: the toolchain needs clang ≥ 16.0.0, pahole ≥ 1.25 and (for Rust schedulers) rust ≥ 1.70.0. The kernel needs CONFIG_SCHED_CLASS_EXT=y, CONFIG_DEBUG_INFO_BTF=y, CONFIG_BPF_JIT=y and related options. Then:

./scx_simple -f      # -f: FIFO mode; -v verbose; -h help

local=124 global=457
Version drift

This lesson uses the original kfunc names scx_bpf_dispatch, scx_bpf_dispatch_vtime and scx_bpf_consume, declared in its bundled include/scx/common.bpf.h. Linux 6.13 renamed them to scx_bpf_dsq_insert, scx_bpf_dsq_insert_vtime and scx_bpf_dsq_move_to_local (see the kernel's tools/sched_ext/include/scx/compat.bpf.h). According to docs.ebpf.io, the old names stayed as aliases until 6.17. The kernel source agrees: kernel/sched/ext.c still defines scx_bpf_dispatch and scx_bpf_consume at v6.16 and no longer mentions them at v6.17. The lesson declares them as plain (non-__weak) __ksyms, so libbpf should refuse to load it on 6.17 or later. I have not run the unmodified lesson on such a kernel. Expect to port it to the new names, or copy the current scx_simple from the kernel tree. CI only builds this lesson; it does not load it. The README's build section also says to "navigate to the kernel's tools/sched_ext/ directory and run make", although the lesson ships its own Makefile, and CI uses that Makefile (make -C src/44-scx-simple).

Lesson 47: tracing CUDA from the host

eBPF cannot run on the GPU in the mainline kernel. It can, however, watch the host side of a GPU program, the calls into the CUDA runtime library, with ordinary uprobes. Lesson 47 puts an entry uprobe and a return uprobe on eleven functions in libcudart.so. The kernel side is a set of tiny handlers that write tagged events to one ring buffer:

struct {
    __uint(type, BPF_MAP_TYPE_RINGBUF);
    __uint(max_entries, 256 * 1024);
} rb SEC(".maps");
/* ... */
/* Helper function for malloc event */
static inline int submit_malloc_event(size_t size, bool is_return, int ret_val)
{
    struct event *e;
    
    e = bpf_ringbuf_reserve(&rb, sizeof(*e), 0);
    if (!e)
        return 0;
    
    e->pid = bpf_get_current_pid_tgid() >> 32;
    bpf_get_current_comm(&e->comm, sizeof(e->comm));
    e->type = CUDA_EVENT_MALLOC;
    e->is_return = is_return;
    
    if (is_return) {
        e->ret_val = ret_val;
    } else {
        e->mem.size = size;
    }
    
    bpf_ringbuf_submit(e, 0);
    return 0;
}
/* ... */
/* Memory allocation/free operations */
SEC("uprobe")
int BPF_KPROBE(cuda_malloc_enter, void **ptr, size_t size)
{
    return submit_malloc_event(size, false, 0);
}

SEC("uretprobe")
int BPF_KRETPROBE(cuda_malloc_exit, int ret)
{

}

The design point is the bare SEC("uprobe"). The section name carries no binary or symbol, so the skeleton does not auto-attach, and the loader attaches each program by symbol name with bpf_uprobe_opts.func_name. This lets one binary trace whichever library or application you name with -p (the default is /usr/local/cuda/lib64/libcudart.so), which matters because CUDA applications often link the runtime statically. Coda: lesson 52 and the newest kernel features

The lessons added in 2026 (50–54) follow a stricter template: a real CLI, a tests/ directory with a Python integration test, and explicit operational limits. Lesson 52 uses fsession, new in Linux 7.0, where one program runs at both entry and exit of vfs_read and keeps a per-call cookie (the hook itself is explained in chapter 05). Its opening lines show the cost of shipping a frozen vmlinux.h:

#define bpf_session_is_return bpf_session_is_return_vmlinux_snapshot
#define bpf_session_cookie bpf_session_cookie_vmlinux_snapshot
#include "vmlinux.h"
#undef bpf_session_is_return
#undef bpf_session_cookie
/* ... */
/*
 * The repository vmlinux.h snapshot predates the ctx argument on these
 * kfunc prototypes. Rename those stale declarations while including the
 * snapshot, then provide the Linux 7.0 signatures below.
 */
extern bool bpf_session_is_return(void *ctx) __ksym;
extern __u64 *bpf_session_cookie(void *ctx) __ksym;

SEC("fsession/vfs_read")
int BPF_PROG(measure_vfs_read, struct file *file, char *buf, size_t count,
	     loff_t *pos, ssize_t ret)
{
	__u64 pid_tgid = bpf_get_current_pid_tgid();
	__u64 *started = bpf_session_cookie(ctx);
	/* ... */
	if (!bpf_session_is_return(ctx)) {
		/* ... */
		*started = bpf_ktime_get_ns();
		return 0;
	}
	/* ... */
	latency = bpf_ktime_get_ns() - *started;

CO-RE relocates struct fields, but kfunc prototypes in the header are only C declarations. If the snapshot is older than the kernel API you target, you have to override them yourself. The run command from the README is sudo ./fsession_latency --pid "$SERVICE_PID" --threshold-us 10000 --duration 30.

Benefits and limitations

Benefits

Short, runnable lessons with line-by-line READMEs in two languages. Broad coverage: almost every hook family, plus recent kernel features (fsession, BPF qdisc, tokens, arena) soon after they are merged. Vendored libbpf, bpftool and per-architecture vmlinux.h make builds reproducible. Per-lesson .config metadata and a generated compatibility matrix tell you what a lesson needs before you build it. CI builds every libbpf lesson and runs a subset, weekly as well as on every push. MIT license.

Limitations

Numbering reflects when a lesson was written, not difficulty, and some lessons fall out of the generated index (32, bpftrace). Depth is uneven: Basic lessons are twenty lines, while 47 and xpu/flamegraph are complete tools. Most "runtime" CI is a three-second smoke run on a GitHub runner kernel, and LSM, XDP, sched_ext and GPU lessons are build-only or not in CI. The frozen vmlinux.h and vendored headers lag behind kernel API changes (the sched_ext kfunc renames, the fsession prototypes). The Basic lessons depend on eunomia-bpf release binaries, and that CI job currently fails on Ubuntu 26.04 runners (PR #236). Performance figures in READMEs, such as "10x faster" for fentry and "2 µs" for CUDA tracing, come from the authors and are not independently measured.

Related work

  • libbpf-bootstrap: the upstream scaffold that lessons 11 and later copy their Makefile and examples from. Smaller, with no lesson text.
  • bcc Python developer tutorial and libbpf-tools in the bcc repository: the README names the bcc tutorial as its inspiration, and many lessons (opensnoop, execsnoop, runqlat, tcpconnlat, memleak, biopattern, funclatency) are versions of bcc tools.
  • docs.ebpf.io and the kernel BPF documentation: reference material for every helper, kfunc and program type the lessons use.
  • Within eunomia-bpf: the ecc/ecli toolchain (chapter 10), the starter templates the README advertises for C, Go and Rust (chapter 11), and GPTtrace, an LLM front end for writing eBPF that the README mentions (chapter 30).

Check your understanding

Q1. You add a new lesson directory with a README and code, but it does not appear in the generated README index. What is the most likely cause?

scripts/generate_toc.py indexes only directories with both .config and README.md, and files Depth lessons under their type. 32-wallclock-profiler (no type) and bpftrace-tutorial (no .config) are missing from the index for exactly this reason. Unnumbered directories such as features/bpf_arena are indexed.

Q2. In lesson 4, what lets ecli offer a --pid_target flag?

Lesson 4 has no user-space C file. const volatile puts the variable in rodata so a loader can set it before load, and eunomia-bpf turns rodata globals into CLI flags, using the doc comment as help text.

Q3. Why does lesson 2 use BPF_CORE_READ(name, name) while lesson 3 writes name->name?

fentry/fexit programs get typed arguments through the BPF trampoline, so pointer loads are checked as BTF-typed accesses. A kprobe gets pt_regs, so any pointer it holds is an unknown kernel address and must be read with a probe-read helper (here with CO-RE relocation).

Q4. In lesson 19, why does the program return ret early when it is non-zero?

The last argument of an LSM BPF program is the return value of the previous BPF program on that hook (0 for the first). The code comment says it is "satisfying 'cannot override a denial' rule": once another program has denied the call, this one passes the denial on. The kernel does not enforce this; each program has to follow the convention.

Q5. Lesson 47 declares its uprobes as a bare SEC("uprobe"). What follows from that?

Without a binary:function in the section name, libbpf does not know the target. cuda_events.c calls bpf_program__attach_uprobe_opts with func_name set, so the same programs can trace libcudart.so or an application that links the CUDA runtime statically.

Q6. Lesson 44 builds in CI but fails to load on your 6.18 kernel. Which explanation fits what you learned in this chapter?

CI only compiles lesson 44 (test_status=ci-build), and compiling does not check whether a kfunc exists in the running kernel; that check happens at load. The kfuncs were renamed in 6.13, and docs.ebpf.io reports the scx_bpf_consume alias removed in 6.17. Porting to scx_bpf_dsq_insert/scx_bpf_dsq_move_to_local is the likely fix. Loading on 6.18 itself was not tested for this chapter.
