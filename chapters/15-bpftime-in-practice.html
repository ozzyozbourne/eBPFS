Chapter 15

bpftime in practice: running eBPF tools in userspace

You have a libbpf tool, such as a malloc counter, opensnoop or sslsniff, and you want it to run inside the traced process instead of trapping into the kernel on every event. Maybe the machine has no root access, or the kernel is too old. This chapter shows how to do that with bpftime: install it, use its CLI, run four real examples from start to finish, inspect shared state, mix kernel and userspace eBPF, probe CUDA kernels, and read the repository's own benchmark numbers honestly.

Prerequisites: 05, 06, 14Repo: eunomia-bpf/bpftime @ 25e250d6~55 min

Why this matters

Kernel uprobes work by placing a breakpoint instruction in the traced binary. Every time the probed function runs, the CPU traps into the kernel, the kernel runs your eBPF program, and then it returns to userspace. That is two mode switches per event. For a function like malloc or SSL_read, which can run millions of times a second, those traps cost more than the eBPF program itself. Syscall tracepoints have a related problem: they need root (or CAP_BPF plus CAP_PERFMON) and a kernel with the right configuration.

bpftime is a userspace eBPF runtime from the eunomia-bpf organisation. It takes the same compiled eBPF object and the same libbpf loader you would use with the kernel, and runs the program inside the target process. It hooks functions with binary rewriting instead of traps, and it keeps maps in shared memory instead of kernel memory. Chapter 14 explains the design, the internals and the OSDI '25 paper. This chapter is the hands-on part: which commands to type, which files to look at, what output to expect, and where the sharp edges are.

Key idea

A bpftime session always has two sides. The loader (your libbpf tool) runs with libbpftime-syscall-server.so preloaded, so its bpf() and perf_event_open() calls go into a shared-memory segment instead of the kernel. The target runs with libbpftime-agent.so, either preloaded at start or injected later. The agent reads that segment, JIT-compiles the programs and patches the hooks. Neither side needs to be recompiled.

Status

The repository's own manual (usage.md) still opens with: "It's at an early stage and may contain bugs on more platforms and eBPF programs … It's not suitable for production use now." The GPU README says "GPU support is still experimental." Treat everything in this chapter as a developer tool unless you have tested it on your own workload.

The two-process workflow

Before any commands, here is what happens when you run the canonical example. You start a libbpf program (the loader) under bpftime load, and a victim program under bpftime start. Figure 15.1 shows the pieces and the data flow.

The order matters, and the top-level README says so directly: "You should always run the load first then run the start command, or the eBPF program will not be attached." With bpftime start, the agent attaches what it finds when the target starts. The newer bpftime trace command removes this restriction for long-running targets: it polls for links that appear later (see the CLI section).

Installing bpftime

There are three ways to get bpftime: the container image, a source build with the Makefile wrapper, or a source build with CMake directly. Check the releases page before you look for a tarball. As of 2026-11-06, the five most recent GitHub releases (v0.9.0 from 2026-08-14, v0.2.0, v0.1.0, v0.0.3 and v0.0.2) have no binary assets attached. The release workflow (.github/workflows/docker.yml) publishes a container image to ghcr.io/eunomia-bpf/bpftime, tagged with the release version, and then creates the GitHub release. In practice, the prebuilt option is the container.

Option A: the container image

From installation.md:

# run the container
docker run -it --rm --name test_bpftime -v "$(pwd)":/workdir -w /workdir ghcr.io/eunomia-bpf/bpftime:latest /bin/bash
# start another shell in the container (If needed)
docker exec -it test_bpftime /bin/bash

The Dockerfile builds on ubuntu:24.04 with clang-16 and llvm-16, configures with -DCMAKE_BUILD_TYPE=RelWithDebInfo -DBUILD_BPFTIME_DAEMON=1, runs make install, and adds /root/.bpftime/ to PATH. The image therefore contains the CLI, the daemon and the preload libraries. The docker exec line matters because the workflow needs two shells, one for the loader and one for the target.

Option B: build from source

The dependency list and build commands below are copied from installation.md. The docs were tested on Ubuntu 23.04 and recommend gcc ≥ 12 and clang ≥ 16:

sudo apt-get update && sudo apt-get install \
        libelf1 libelf-dev libssl-dev zlib1g-dev make cmake git libboost-all-dev \
        binutils-dev libyaml-cpp-dev ca-certificates clang llvm pkg-config llvm-dev
git submodule update --init --recursive

make release JOBS=$(nproc) # Build and install the runtime
export PATH=$PATH:~/.bpftime

The release target in the Makefile is a thin wrapper:

release: ## build the release version
	cmake -Bbuild  -DCMAKE_BUILD_TYPE:STRING=RelWithDebInfo \
				   -DBUILD_BPFTIME_DAEMON=1
	cmake --build build --config RelWithDebInfo --target install  -j$(JOBS)

The build is a large C++ project. It pulls in LLVM for the JIT, Frida for function hooking, Boost.Interprocess, libbpf and bpftool as submodules. Expect it to take a while and to use a lot of memory. When it finishes, ~/.bpftime/ contains:

Build options you will actually touch

All of these come from the option list in installation.md (cmake/StandardSettings.cmake has the full set):

  • BPFTIME_LLVM_JIT (default ON): the LLVM JIT/AOT backend from llvmbpf. BPFTIME_UBPF_JIT selects the uBPF backend.
  • ENABLE_EBPF_VERIFIER (default OFF): link the PREVAIL userspace verifier.
  • BPFTIME_BUILD_WITH_LIBBPF / BPFTIME_BUILD_KERNEL_BPF: turn these off to build without kernel eBPF support, for example on macOS.
  • BPFTIME_ENABLE_CUDA_ATTACH + BPFTIME_CUDA_ROOT: GPU support (see below).
  • BPFTIME_BUILD_STATIC_LIB: produce libbpftime.a for embedding.
  • BPFTIME_ENABLE_MPK, BPFTIME_ENABLE_IOURING_EXT: memory-protection keys for the shared segment, and io_uring helper extensions.

For a much smaller build that contains only the VM, with no runtime and no uprobes, use make build-vm or make build-llvm.

Walkthrough 1: counting malloc with a uprobe

example/malloc is the canonical first run. It is an ordinary libbpf program that counts malloc calls per PID. The same binary works unchanged against the kernel.

#define BPF_NO_GLOBAL_DATA
#include <vmlinux.h>
#include <bpf/bpf_helpers.h>
#include <bpf/bpf_tracing.h>

struct {
	__uint(type, BPF_MAP_TYPE_HASH);
	__uint(max_entries, 1024);
	__type(key, u32);
	__type(value, u64);
} libc_malloc_calls_total SEC(".maps");

static int increment_map(void *map, void *key, u64 increment)
{
	u64 zero = 0, *count = bpf_map_lookup_elem(map, key);
	if (!count) {
		bpf_map_update_elem(map, key, &zero, BPF_NOEXIST);
		count = bpf_map_lookup_elem(map, key);
		if (!count) {
			return 0;
		}
	}
	u64 res = *count + increment;
	bpf_map_update_elem(map, key, &res, BPF_EXIST);

	return *count;
}

SEC("uprobe/libc.so.6:malloc")
int do_count(struct pt_regs *ctx)
{
	u32 pid = bpf_get_current_pid_tgid() >> 32;

	bpf_printk("malloc called from pid %d\n", pid);

	increment_map(&libc_malloc_calls_total, &pid, 1);

	return 0;
}

char LICENSE[] SEC("license") = "GPL";

The loader is a standard libbpf skeleton program. There is nothing bpftime-specific in it, and that is the point:

	/* Load and verify BPF application */
	skel = malloc_bpf__open();
	/* ... */
	/* Load & verify BPF programs */
	err = malloc_bpf__load(skel);
	/* ... */
	LIBBPF_OPTS(bpf_uprobe_opts, attach_opts, .func_name = "malloc",
		    .retprobe = false);
	struct bpf_link *attach = bpf_program__attach_uprobe_opts(
		skel->progs.do_count, -1, "libc.so.6", 0, &attach_opts);
	/* ... */
	while (!exiting) {
		sleep(1);
		print_stat(skel);
	}

print_stat() iterates over the map with bpf_map_get_next_key, bpf_map_lookup_elem and bpf_map_delete_elem. Under bpftime, those libbpf calls still go through the bpf() syscall wrapper. The syscall server intercepts them and serves them from the shared map. The victim is a tight loop:

int main(int argc, char *argv[]) {
    while(1) {
        void *p = malloc(1024);
        printf("continue malloc...\n");
        usleep(100 * 1000);
        free(p);
    }
    return 0;
}

The stepper below walks through the whole session. Every command and every line of output is copied from the top-level README.md / usage.md.

1. Build the example

The example Makefile compiles malloc.bpf.c with clang, generates the skeleton with bpftool, and links malloc and victim.

make -C example/malloc # Build the eBPF program example
export PATH=$PATH:~/.bpftime/

2. Start the loader under the syscall server

bpftime load preloads libbpftime-syscall-server.so. When libbpf calls BPF_MAP_CREATE, BPF_PROG_LOAD and perf_event_open for the uprobe, the calls create handlers in shared memory. No kernel object is created.

bpftime load ./example/malloc/malloc

3. Start the target with the agent

In a second shell, start the victim. The agent finds the uprobe handler for libc.so.6:malloc, JIT-compiles do_count, and installs a Frida hook on malloc. The bpf_printk output appears in the victim's own terminal:

$ bpftime start ./example/malloc/victim
malloc called from pid 250215
continue malloc...
malloc called from pid 250215

4. Read the map from the loader

Every second, the loader walks the hash map in shared memory and prints the counts it finds:

$ bpftime load ./example/malloc/malloc
...
12:44:35 
        pid=247299      malloc calls: 10
        pid=247322      malloc calls: 10

5. Or attach to a process that is already running

Start the victim without bpftime, then inject the agent. This uses Frida's injector, so it needs ptrace permission over the target (usually root):

$ ./example/malloc/victim & echo $! # The pid is 101771
[1] 101771
101771
continue malloc...
continue malloc...
$ sudo bpftime attach 101771 # You may need to run make install in root
Inject: "/root/.bpftime/libbpftime-agent.so"
Successfully injected. ID: 1

6. Compare with the kernel

Run the same binary without bpftime and it loads into the kernel as usual. It then counts every malloc on the system, not only in processes that run the agent:

$ sudo example/malloc/malloc
15:38:05
        pid=30415       malloc calls: 1079
        pid=30393       malloc calls: 203
        pid=29882       malloc calls: 1076
        pid=34809       malloc calls: 8
Scope difference

A kernel uprobe on libc.so.6:malloc fires in every process that maps that library. A bpftime uprobe fires only in processes that run the agent. That difference is part of why it is cheap, and it also changes what the output means. If you expected system-wide numbers, the userspace run will look "missing". Step 6 shows the difference: the kernel run lists four unrelated PIDs.

Walkthrough 2: syscall tracing with opensnoop and -s

Syscall tracepoints are the second big event source. example/tracing/opensnoop is a port of bcc's libbpf-tools opensnoop. The BPF side attaches to the standard syscalls/sys_enter_openat / sys_exit_openat tracepoints and uses the same context structs it would use in the kernel:

SEC("tracepoint/syscalls/sys_enter_openat")
int tracepoint__syscalls__sys_enter_openat(struct trace_event_raw_sys_enter* ctx)
{
	u64 id = bpf_get_current_pid_tgid();
	/* use kernel terminology here for tgid/pid: */
	u32 tgid = id >> 32;
	u32 pid = id;

	/* store arg info for later lookup */
	if (trace_allowed(tgid, pid)) {
		struct args_t args = {};
		args.fname = (const char *)ctx->args[1];
		args.flags = (int)ctx->args[2];
		bpf_map_update_elem(&start, &pid, &args, 0);
	}
	return 0;
}

static __always_inline
int trace_exit(struct trace_event_raw_sys_exit* ctx)
{
	struct event event = {};
	struct args_t *ap;
	uintptr_t stack[3];
	int ret;
	u32 pid = bpf_get_current_pid_tgid();

	ap = bpf_map_lookup_elem(&start, &pid);
	if (!ap)
		return 0;	/* missed entry */
	ret = ctx->ret;
	/* ... */
	bpf_get_current_comm(&event.comm, sizeof(event.comm));
	bpf_probe_read_user_str(&event.fname, sizeof(event.fname), ap->fname);
	/* ... */
	bpf_get_stack(ctx, &stack, sizeof(stack),
		      BPF_F_USER_STACK);
	/* ... */
	/* emit event */
	bpf_perf_event_output(ctx, &events, BPF_F_CURRENT_CPU,
			      &event, sizeof(event));
	/* ... */
}

Syscalls cannot be hooked with a function trampoline, because the syscall instruction is not a function. The agent therefore needs the text segment transformer. It rewrites syscall instructions in the executable segments before main runs. The approach is inspired by zpoline and pmem/syscall_intercept; Chapter 14 covers the mechanism. You enable it with -s. From usage.md (the directory has since moved to example/tracing/opensnoop):

The log shows the order of events. The transformer takes over main ("Entering new main"), maps a page at address zero (that page is the landing pad for zpoline-style rewriting), rewrites the executable segments, and only then dlopens the agent named in AGENT_SO. Note the timestamps: rewriting took about three seconds in that run, so startup cost is real. example/README.md also notes that syscall tracepoints are "currently x86 only".

The victim is just a loop that opens and closes a file:

int main()
{
	while (true) {
		std::cout << "Opening test.txt" << std::endl;

		int fd = open("test.txt", O_RDONLY | O_CREAT);
		assert(fd != -1);

		std::cout << "test.txt opened, fd=" << fd << std::endl;
		usleep(1000 * 300);
		std::cout << "Closing test.txt..." << std::endl;
		close(fd);
		std::cout << "test.txt closed" << std::endl;
	}
	return 0;
}

The program uses a PERF_EVENT_ARRAY for output and calls bpf_get_stack(..., BPF_F_USER_STACK). Both are implemented in userspace: the perf buffer is a shared-memory ring, and stacks are unwound by Frida. The loader's perf_buffer__poll works because the syscall server also emulates the mmap and epoll calls libbpf makes on the perf event fds. A recent fix (#689, "return epoll readiness without duplicates") touched exactly that path.

Walkthrough 3: bashreadline, sslsniff and bpftrace

These three show that "unmodified" really means unmodified. Two are libbpf-tools ports and the third is a stock bpftrace. The tabs below hold the relevant BPF source for each example program in this chapter, so you can compare them side by side.

struct {
	__uint(type, BPF_MAP_TYPE_PERF_EVENT_ARRAY);
	__uint(key_size, sizeof(__u32));
	__uint(value_size, sizeof(__u32));
} events SEC(".maps");

SEC("uretprobe//bin/bash:readline")
int BPF_KRETPROBE(printret, const void *ret)
{
	struct str_t data;
	char comm[TASK_COMM_LEN];
	u32 pid;

	if (!ret)
		return 0;

	bpf_get_current_comm(&comm, sizeof(comm));
	if (comm[0] != 'b' || comm[1] != 'a' || comm[2] != 's' ||
	    comm[3] != 'h' || comm[4] != 0)
		return 0;

	pid = bpf_get_current_pid_tgid() >> 32;
	data.pid = pid;
	bpf_probe_read_user_str(&data.str, sizeof(data.str), ret);

	bpf_perf_event_output(ctx, &events, BPF_F_CURRENT_CPU, &data,
			      sizeof(data));

	return 0;
};
SEC("uprobe/do_handshake")
int BPF_UPROBE(probe_SSL_rw_enter, void *ssl, void *buf, int num) {
    u64 pid_tgid = bpf_get_current_pid_tgid();
    u32 pid = pid_tgid >> 32;
    u32 tid = pid_tgid;
    u32 uid = bpf_get_current_uid_gid();

bashreadline

The program is a uretprobe on /bin/bash:readline. It copies the returned string with bpf_probe_read_user_str and emits it through a perf event array. Under bpftime you run the loader with bpftime load and start a shell with bpftime start /bin/bash. Each command you type in that shell then shows up in the loader. The comm check (comm == "bash") works because the userspace bpf_get_current_comm reads the calling thread's name.

sslsniff: reading TLS plaintext

sslsniff is the most useful example in practice, and the one where userspace execution makes the biggest difference. It hooks SSL_read/SSL_write (and the GnuTLS and NSS equivalents) to capture plaintext before encryption and after decryption. The repo's README shows it against wget: first the probe, then, in another terminal, the traced program. The README wraps the library name across two lines; it is joined here. The paths predate the move to example/tracing/.

sudo LD_PRELOAD=build/runtime/syscall-server/libbpftime-syscall-server.so example/sslsniff/sslsniff
sudo LD_PRELOAD=build/runtime/agent/libbpftime-agent.so wget https://www.google.com

The output is the decrypted HTML of the response, framed by ----- DATA ----- markers and a line like READ/RECV 0.127135326 wget 165620 1228. In the benchmark/ssl-nginx experiment, the same tool is run against nginx serving HTTPS. That README's conclusion is that "kernel sslsniff can significantly reduce the performance of nginx, lead to a 2x performance drop". The userspace version is the comparison point.

Changing behaviour: override and error injection

Tracing only observes. bpftime also lets a uprobe program replace a function's return value with bpf_override_return. In the kernel, this helper only works on functions marked ALLOW_ERROR_INJECTION. In userspace, it works on any function the agent can hook. Look at the uprobe-override tab above: the program prints a line and forces target_func to return 0 without running its body. libbpf has no attach API for this, so the example opens the perf event by hand with a bpftime-specific type:

#define BPF_TYPE_UPROBE_OVERRIDE 1008
/* ... */
static int perf_event_open_with_override(const char *name, uint64_t offset,
					 int pid, size_t ref_ctr_off, int type)
{
	/* ... */
	attr.size = attr_sz;
	attr.type = type;
	attr.config |= (__u64)ref_ctr_off << PERF_UPROBE_REF_CTR_OFFSET_SHIFT;
	attr.config1 = ptr_to_u64(name); /* kprobe_func or uprobe_path */
	attr.config2 = offset; /* kprobe_addr or probe_offset */

1008 matches ATTACH_UPROBE_OVERRIDE in attach/frida_uprobe_attach_impl/include/frida_uprobe_attach_impl.hpp, next to ATTACH_UPROBE = 6, ATTACH_URETPROBE = 7 and ATTACH_UREPLACE = 1009. This is the one place where a bpftime program is not portable to the kernel. example/error-inject applies the same idea to syscalls, and example/hotpatch/redis and hotpatch/vim use it to patch real applications.

Inspecting shared state with bpftimetool

Because every object lives in one shared-memory segment, you can dump it, edit it and load it back. The subcommands come from tools/bpftimetool/arguments.hpp, which was rewritten on argparse in the most recent commit (#719):

	argparse::ArgumentParser load{"load", "", argparse::default_arguments::help};
	argparse::ArgumentParser export_cmd{"export", "", argparse::default_arguments::help};
	argparse::ArgumentParser import_cmd{"import", "", argparse::default_arguments::help};
	argparse::ArgumentParser remove{"remove", "", argparse::default_arguments::help};
	argparse::ArgumentParser run{"run", "", argparse::default_arguments::help};
	argparse::ArgumentParser cuda{"run-on-cuda", "", argparse::default_arguments::help};
	/* ... */
		run.add_argument("--repeat").action(integer("repeat", 1));
		run.add_argument("--type").choices("JIT", "AOT", "INTERPRET");

There is no dump subcommand. export is the dump. The typical debugging loop, from tools/bpftimetool/README.md:

bpftimetool export debug_state.json
cat debug_state.json | jq '.handlers[] | select(.type=="bpf_prog_handler")'
bpftimetool run 4 test_input.bin

The same README covers benchmarking one program under different engines, and restoring a saved state:

# Compare execution modes
bpftimetool run 4 input.bin repeat 1000 type JIT
bpftimetool run 4 input.bin repeat 1000 type AOT
bpftimetool run 4 input.bin repeat 1000 type INTERPRET
# Restore if needed
bpftimetool remove
bpftimetool import backup_20250930_120000.json

remove destroys all loaded programs, maps and state for every process using bpftime. AOT requires that the program was compiled with bpftime-aot first.

The exported JSON is a list of handlers keyed by fd. Each handler is a bpf_map_handler (with map_type, sizes and flags), a bpf_prog_handler (hex-encoded instructions plus attach_fds), a bpf_perf_event_handler (for a uprobe: _module_name and offset) or a bpf_link_handler. This gives you a workflow the kernel does not: capture a session on one machine, then import it elsewhere and start the target with the agent, with no loader at all. bpftimetool load <fd> <JSON> inserts a single handler. Fix #682 made it accept the same JSON that import reads. remove is the cleanup to use after a crash leaves a stale /dev/shm/bpftime_maps_shm behind.

Kernel-user mixed mode

"Userspace only" is one of three ways to run bpftime. The other two let userspace programs cooperate with real kernel eBPF.

Mode 2: run with the kernel

With BPFTIME_RUN_WITH_KERNEL=true, the syscall server forwards BPF_MAP_CREATE to the real bpf() syscall. It then records a bpftime handler whose type is the kernel type plus KERNEL_USER_MAP_OFFSET (1000):

	case BPF_MAP_CREATE: {
		if (run_with_kernel) {
			uint32_t translated_map_type =
				bpftime_translate_shared_map_type_to_kernel_map_type(
					attr->map_type);
			/* ... */
			int fd = orig_syscall_fn(__NR_bpf, (long)cmd,
						 (long)(uintptr_t)&new_attr,
						 (long)size);
			/* ... */
			if (translated_map_type == attr->map_type) {
				// Marks a kernel-user shared map, the
				// corresponding bpftime map type should be
				// added by KERNEL_USER_MAP_OFFSET
				bpftime_map_type =
					attr->map_type + KERNEL_USER_MAP_OFFSET;

			} else {
				// Marks a kernel-gpu shared map, the
				// corresponding bpftime map type should be the
				// map type before translating
				bpftime_map_type = attr->map_type;
			}
			return create_kernel_bpf_map(fd, bpftime_map_type);
		}

The agent's program then reads and writes the kernel's map. A kprobe or an XDP program in the kernel and a uprobe in userspace can share a hash map. Programs are also loaded into the kernel, so the kernel verifier checks them, but the agent still runs them in userspace. Programs the kernel would reject (userspace-only helpers such as ufuncs) can be excluded by name with a regex. From usage.md:

BPFTIME_NOT_LOAD_PATTERN=start_.* BPFTIME_RUN_WITH_KERNEL=true LD_PRELOAD=~/.bpftime/libbpftime-syscall-server.so example/malloc/malloc

The kernel-user map types handled in runtime/src/handler/map_handler.cpp are KERNEL_USER_HASH, KERNEL_USER_ARRAY, KERNEL_USER_PERCPU_ARRAY and KERNEL_USER_PERF_EVENT_ARRAY. The manual's requirement is that the kernel version "should be higher enough to support mmap eBPF map".

Mode 3: the daemon

bpftime_daemon goes one step further. You do not preload anything into the loader. The daemon loads its own kernel eBPF program (daemon/kernel/bpf_tracer.bpf.c) that traces bpf(), perf_event_open() and ioctl() system-wide. When a tool loads a uprobe program, the daemon copies its instructions into shared memory and changes the load and attach path so the kernel uprobe never fires. From daemon/README.md:

$ sudo SPDLOG_LEVEL=Debug build/daemon/bpftime_daemon
[2023-10-24 11:07:13.143] [info] Global shm constructed. shm_open_type 0 for bpftime_maps_shm

$ sudo example/malloc/malloc
libbpf: loading object 'malloc_bpf' from buffer
11:08:11 
11:08:12 

$ sudo SPDLOG_LEVEL=Debug ~/.bpftime/bpftime start example/malloc/victim

The loader prints empty timestamps at first. The README explains that this is "because we modify the load and attach process of bpf and perf event with eBPF in the kernel". Counts appear once a victim with the agent starts calling malloc. The daemon's flags (from the argp_option table in daemon/user/main.cpp) are -p/--pid, -u/--uid, -o/--open, -v/--verbose and -w/--whitelist-uprobe. The daemon needs root and a kernel that can run bpftime's own tracer. It is the option to use when you cannot change how an existing agent such as an observability collector is launched. example/otel-ebpf-profiler (#623) is a compatibility smoke test for exactly that "daemon mirror" case.

GPU and CUDA probes

The most active area of bpftime is GPU support, which came from the eGPU research prototype. The eunomia-bpf/eGPU repository now says it has been "merged into bpftime and will be maintained there". The GPU README in example/gpu/README.md describes it as running eBPF programs "within GPU kernels on NVIDIA and AMD GPUs". Chapter 20 covers the related gpu_ext work on UVM and scheduling, and Chapter 16 covers the eBPF→PTX compiler. This section covers using it.

Walkthrough 4: cuda-counter

The program is shown in the "cuda-counter" tab above. Two details are new. First, the section names reuse kprobe/ and kretprobe/ with a mangled CUDA kernel name (_Z9vectorAddPKfS0_Pf is vectorAdd(const float*, const float*, float*)). The GPU README admits "kprobe / kretprobe here is a bad name, we just use it as a placeholder". Late attach to a running CUDA process

Preload means restarting the GPU job, which is often not acceptable for a long training run. bpftime trace was added for this case. From example/gpu/threadscheduling_dynamic_hook/README.md:

example/gpu/threadscheduling_dynamic_hook/vec_add 4 64

Terminal 1 starts the target with no preload, as above. Terminal 2 starts probing later:

sudo BPFTIME_LOG_OUTPUT=console ./build/tools/cli/bpftime trace --pidof vec_add --auto-refresh-ms 500 \
  example/gpu/threadscheduling_dynamic_hook/threadscheduling

The trace branch in tools/cli/main.cpp does the following:

  1. Resolves --pidof through /proc/*/comm. The name must match exactly one process.
  2. If run as root, reads the target's uid/gid and plans to start the loader as that user. It relaxes ownership of /dev/shm/bpftime_maps_shm so the target can open it.
  3. Runs cuobjdump --extract-ptx all on the target executable into a private temp directory (BPFTIME_CUOBJDUMP or BPFTIME_CUDA_ROOT help it find the tool).
  4. Spawns the loader with the syscall server.
  5. Asks an agent that is already present to refresh over IPC, or injects one with Frida using the argument loader_pid=…;force_reinit=1;auto_refresh_ms=500;cuda_late_ptx_dir=….
  6. On Ctrl-C: sends detach to the agent first, then stops the loader, "to avoid CUDA IPC allocations being torn down while the target still uses them".

The README lists the practical constraints. Injection needs ptrace rights, so Yama ptrace_scope=1 blocks it unless the target opts in with BPFTIME_ALLOW_PTRACE=1. Use BPFTIME_CUDA_DEVICE for a non-zero GPU. The _dynamic_hook variant passes N as a kernel argument instead of __constant__ "to avoid relying on constant/global mirroring during late attach". The fix for that mirroring (#695) landed in 2026-10.

The example directory also includes real-framework smoke tests: pytorch-test, llama-cpp-test, faiss-test, cutlass, cudagraph. It also has directly_run_on_gpu (run an eBPF program as a GPU kernel, together with bpftimetool run-on-cuda) and an experimental rocm-counter for AMD. Commit #647 (2026-08) added NVIDIA GB300 (sm_103) and CUDA 13 support.

Userspace XDP, DPDK and the nginx module

XDP programs in userspace

example/xdp-counter loads an ordinary XDP program into the userspace runtime and attaches it with a bpf_link to a veth device. From its README:

sudo ip link add veth0 type veth peer name veth1
LD_PRELOAD=build/runtime/syscall-server/libbpftime-syscall-server.so example/xdp-counter/xdp-counter example/xdp-counter/.output/xdp-counter.bpf.o veth1 example/xdp-counter/base.btf

base.btf supplies BTF for relocating against the userspace xdp_md defined in runtime/extension/userspace_xdp.h. bpftime does not receive packets itself. example/attach_implementation shows how to embed bpftime in an application that you control, with a custom attach type. It has three parts. Benefits and limitations

Benefit: same tools

The libbpf skeleton, bpftrace and bcc-style tools run unchanged. The same binary still works on the kernel.

Benefit: cheap hooks

Function hooks and user-memory reads avoid the trap. The repo's own uprobe numbers show 13–16× lower overhead.

Benefit: no kernel eBPF needed

Userspace-only mode needs no CAP_BPF, works on old kernels, and builds on non-Linux targets with libbpf disabled.

Benefit: new hook types

CUDA kernels, nginx request phases, function override and replacement: places the kernel cannot reach.

And the limitations, each tied to something in the repo:

  • Only processes running the agent are traced. There is no system-wide view unless every process is started under bpftime or the daemon redirects probes.
  • No kernel context. No task_struct, no kprobes and no cgroup ID helper in userspace-only mode. Kernel events need mixed mode, with real kernel programs sharing maps.
  • Weaker safety by default. The verifier level defaults to WARNING, and PREVAIL is off unless you build it in. eBPF code also runs in the target's address space: the agent is a guest in someone else's process. The repo's AGENTS.md now writes down a "host-process contract" (no exit, no writes to the host's stdio, chain signal handlers). It exists because earlier versions broke these rules (#632, #634, #640).
  • Map performance. Some map operations are slower than in the kernel (see the table above). Shared memory has a fixed size (BPFTIME_SHM_MEMORY_MB), and perf-buffer allocation fails with ENOMEM when it runs out.
  • Platform scope. Syscall tracing is x86-only. Frida covers the function hooks on x86-64 and arm64. riscv64 got a trap-based backend in 2026-09 (#665). macOS and QNX ports are open PRs (#545, #661).
  • Startup and attach costs. Rewriting text segments for -s took about 3 s in the usage.md log. CUDA attach recompiles PTX. Late attach needs ptrace rights.
  • Ordering. With start, the loader must already be running. Use trace or attach for the other order.
  • Maturity. The documentation calls it "not suitable for production use now", and many of the last 50 commits fix correctness bugs (hash map collisions, ringbuf wraparound, fd bounds).
Troubleshooting checklist
  • Nothing happens in the target. Was the loader started first? Check ~/.bpftime/runtime.log, or rerun with BPFTIME_LOG_OUTPUT=console SPDLOG_LEVEL=debug.
  • "Global shm not found" from bpftimetool. No loader is running, so nothing has created the segment yet.
  • Stale state after a crash. bpftimetool remove, then start again.
  • Permission errors on /dev/shm/bpftime_maps_shm. The loader and the target run as different users. bpftime trace fixes this by running the loader as the target's uid.
  • "unsupported map type". Check the map table above, or use --allow-external-maps if you supply the map yourself.
  • Stripped binary, empty stacks. bpftime load --fuzzy-backtracer ….
  • Injection fails. Check /proc/sys/kernel/yama/ptrace_scope and run as root.

What is actively being worked on

Related work

  • uBPF and rbpf are userspace eBPF VMs without maps, loaders or hooks. bpftime can use uBPF as a backend. llvmbpf is the bpftime VM as a standalone library.
  • Frida provides the uprobe implementation. zpoline (ATC '23) and syscall_intercept inspired the syscall rewriting.
  • NVBit, CUPTI and Nsight are the GPU instrumentation baselines in the GPU README. The eGPU paper (HCDS '25) is the research origin of the CUDA backend.
  • DPDK's built-in BPF (librte_bpf, based on uBPF) is what the XDP README compares against. bpftime adds maps and control-plane loading.
  • Wasm, LuaJIT, RLBox, ERIM are the extension mechanisms compared in the nginx benchmark and in the OSDI '25 paper (Chapter 14). Chapter 12 covers the opposite direction: eBPF loaders compiled to Wasm.

Check your understanding

Q1. You run bpftime start ./victim first and then bpftime load ./malloc. Nothing is counted. Why?

The README says to run load first. Use bpftime trace, whose --auto-refresh-ms option discovers late-loaded links, or re-attach.

Q2. What does bpftime start -s change compared with plain start?

See the start branch in tools/cli/main.cpp and the "Rewriting executable segments.." log line in usage.md.

Q3. Which subcommand of bpftimetool writes all programs, maps and perf events to a file?

bpftimetool export <filename> writes JSON handlers. import reads them back. There is no dump subcommand.

Q4. According to benchmark/syscall/example_results.md, how does userspace syscall tracing compare with a kernel tracepoint?

The 10× figure applies to uprobes. For syscalls, bpftime's advantages are portability and scope, not speed.

Q5. With BPFTIME_RUN_WITH_KERNEL=true, where does a hash map created by the loader live?

See BPF_MAP_CREATE in runtime/syscall-server/syscall_context.cpp. This is what lets kernel kprobes and userspace uprobes share data.

Q6. In cuda_probe.bpf.c, what does SEC("kretprobe/_Z9vectorAddPKfS0_Pf") attach to?

The section prefix is reused as a placeholder (the GPU README says so). The CUDA backend inserts the eBPF code, translated to PTX, before the kernel returns.
