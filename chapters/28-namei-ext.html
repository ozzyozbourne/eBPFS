Chapter 28

namei_ext: programmable VFS name resolution

Agent sandboxes, build systems and service launchers often need the same pathname to mean different files for different processes, and they want that switch to happen right away. Today they get it with bind mounts, OverlayFS, symlink farms, or a FUSE daemon. namei_ext is a research prototype that tries something narrower: a cgroup-scoped eBPF program runs inside the kernel's path walk and picks which existing object a name resolves to. The VFS and the real filesystem still handle everything after that choice.

Why this matters

Some workloads keep asking the same question: which file should this pathname mean right now, for this process?

  • An AI coding agent works in /work/ws. When it forks, checkpoints or rolls back, the orchestrator wants /work/ws to point at a different snapshot of the tree. Two agents running at once should each see their own snapshot under the same path, because their tools, caches and prompts have that path baked in.
  • A build action in a sandbox should see only its declared inputs. An undeclared file should not exist from its point of view, even if it exists on disk.
  • A toolchain manager wants /opt/py/bin/python to mean Python 3.10 for one group of processes and 3.12 for another, and wants to switch and roll back without rewriting the tree.
  • A checkpoint/restart system restores a program whose remembered paths now live somewhere else.

Linux already has several ways to build these "views". They all bundle the choice of object together with something heavier. Mount namespaces and bind mounts build the view ahead of time, as mount-table state. OverlayFS builds a merged filesystem. FUSE sends every operation to a user-space daemon, which then owns caching, errors and availability. A custom or stackable filesystem means writing (and maintaining) a whole set of VFS methods. The namei_ext authors argue that many of these workloads only need the choice. After lookup, reads, writes, permissions, page cache and persistence could all stay with ext4 or tmpfs as usual.

Key idea

Dynamic filesystem views are a pathname late-binding problem, not necessarily a new-filesystem problem. namei_ext places one bounded eBPF decision function at three VFS spots: component lookup, final-component lookup in open(), and directory iteration. The function returns one of four actions: PASS, REDIRECT, HIDE or SELECT_TARGET. The kernel checks the action and then carries on with the normal path walk. The authors compare this to sched_ext: BPF supplies the policy, and the kernel keeps the machinery.

This chapter assumes you know what a BPF program type, an attach point and a map are (chapter 04, chapter 05). It first covers how Linux resolves a pathname, because that is where the hook lives. Then it reads the kernel patch and the policies, and ends with what the repository's own evaluation reports.

Background: how Linux turns a string into a file

Dentries, inodes, mounts and struct path

The Virtual File System (VFS) is the layer between system calls and individual filesystems. It caches names in dentries (directory entries). A dentry links a name inside a parent directory to an inode, the filesystem's object for a file or directory. Many dentries together form the dcache. One directory tree can be mounted in several places, so a dentry alone does not say "where" you are. The kernel pairs it with a struct vfsmount, and that pair, struct path { mnt, dentry }, is the kernel's idea of a location. Keep this in mind: namei_ext's SELECT_TARGET action works by swapping in a different struct path halfway through a walk.

The path walk: link_path_walk and walk_component

The kernel calls pathname resolution "namei" (name-to-inode). The code is in fs/namei.c. Neil Brown's kernel document Pathname lookup and his three LWN articles from 2015 describe it in detail. The outline goes like this. A struct nameidata holds the walk state: the current path, the component being looked at (nd->last, a qstr holding name, length and hash), lookup flags, the root, a symlink stack, and sequence numbers. link_path_walk() splits the string at /. For each component except the last, it calls walk_component(), which:

  1. handles . and .. separately (handle_dots), because .. has to respect the process root and mount boundaries;
  2. tries lookup_fast() in the dcache, and on a miss falls back to lookup_slow(), which calls the filesystem's ->lookup inode operation;
  3. calls step_into() to cross mount points and follow symlinks.

The last component gets different handling, because what to do with it depends on the system call: stat wants the object, open(O_CREAT) may create it, unlink wants the parent. For open, the final step is open_last_lookups(), called from path_openat().

RCU-walk and ref-walk

Taking a reference count on every dentry along a path makes cache lines bounce between CPUs. So Linux first tries RCU-walk. It walks without taking references or locks, relying on RCU to keep objects alive, and checks per-dentry and per-mount sequence counters (d_seq, mount_lock) to catch concurrent renames or unmounts. If something would need to block, or a sequence check fails, the walk tries try_to_unlazy() to switch to ref-walk in place, taking real references. If that also fails, the whole walk returns -ECHILD and restarts from the beginning in ref-walk mode. This matters for namei_ext for two reasons. A BPF program can run on the RCU fast path, and a full restart means the policy can run more than once for the same system call.

Mount namespaces and openat2() RESOLVE_* flags

A mount namespace gives a group of processes its own mount table, so bind mounts and overlay mounts can differ per container. This is the standard Linux way to give processes different views. But the view is built ahead of time: changing it means mounting or unmounting, it covers whole subtrees, and it applies to everything in the namespace.

openat2(2) (Linux 5.6) lets a caller restrict resolution with RESOLVE_* flags. RESOLVE_BENEATH rejects any path that escapes the starting directory. RESOLVE_IN_ROOT treats the directory as the root. RESOLVE_NO_XDEV forbids crossing mounts. RESOLVE_NO_SYMLINKS and RESOLVE_NO_MAGICLINKS limit link following. RESOLVE_CACHED (5.12) fails with EAGAIN unless everything is already in the dcache, which in practice forces an RCU-walk-only lookup. Inside the kernel, the first two flags become LOOKUP_BENEATH and LOOKUP_IN_ROOT (together LOOKUP_IS_SCOPED), and the third becomes LOOKUP_NO_XDEV. As shown below, namei_ext has to honour these flags when it swaps objects. Otherwise a policy could break a sandbox that the caller asked the kernel to enforce.

Landlock and BPF LSM: the access-control neighbours

Landlock lets an unprivileged process sandbox itself. It builds a ruleset of allowed access rights on file hierarchies and then restricts itself irrevocably. BPF LSM (chapter 05) attaches BPF programs to LSM hooks such as file_open and returns allow or -EPERM. Both are mediation: the name has already resolved to an object, and the hook only decides whether the access may go ahead. Neither can make /work/ws mean a different directory, or hide an entry from readdir while keeping the parent listable. namei_ext deliberately sits next to them, not on top of them: it changes which object a name denotes, and leaves the permission check on the result to the normal path.

What namei_ext adds to the kernel

One fact first, because a reader who has seen gpu_ext or sched_ext might expect otherwise: namei_ext is not a struct_ops interface, and it does not add kfuncs. It is a classic new program type plus cgroup attach type, built the same way as cgroup/sysctl or cgroup/dev:

  • program type BPF_PROG_TYPE_NAMEI_EXT, attach type BPF_CGROUP_NAMEI_EXT;
  • libbpf section name SEC("cgroup/namei_ext");
  • one context struct, struct bpf_namei_ext_ctx, with a fixed 64-byte name buffer;
  • the program's return value is the action, and the verifier limits it to the range 0–3;
  • the program is attached to a cgroup v2 directory with bpf_prog_attach(). It governs every task in that cgroup (and in descendants, through the effective program array).

The design document says this on purpose: "the kernel-facing BPF ABI exposes one decision function. Lookup and directory enumeration are event types passed to that one function." A struct_ops table with many callbacks was not the goal. The goal was one decision with a small fixed output.

Where the hook sits in the path walk

Here is the real change to walk_component(). The original body moved into walk_component_common(). The dispatcher keeps the ./.. special case before the hook, so a policy never sees, and can never redirect, the dot entries.

static __always_inline const char *walk_component(struct nameidata *nd, int flags)
{
	/*
	 * "." and ".." are special - ".." especially so because it has
	 * to be able to know about the current root directory and
	 * parent relationships.
	 */
	if (unlikely(nd->last_type != LAST_NORM)) {
		if (unlikely(nd->depth) && !(flags & WALK_MORE))
			put_link(nd);
		return handle_dots(nd, nd->last_type);
	}
	if (namei_ext_enabled() &&
	    namei_ext_parent_maybe_managed(&nd->path))
		return walk_component_namei_ext(nd, flags);
	return walk_component_common(nd, flags);
}

namei_ext_enabled() is just cgroup_bpf_enabled(CGROUP_NAMEI_EXT), the same static-key test every cgroup-BPF hook uses. When nothing is attached anywhere, it compiles down to a patched-out jump. namei_ext_parent_maybe_managed() is the second, finer filter that commit 8fd1fb52f added. It looks up the current parent struct path in a global RCU hash of "managed parents" and returns true only if some attached policy declared that exact directory, or if some policy runs in "global" scope. The design document spells out the contract: "A positive prefilter result still runs the authoritative attachment and scope checks; a false negative is forbidden." The slow-path function is marked noinline, so its stack frame and code stay out of the hot walk_component.

Inside the slow path

When the gate passes, walk_component_namei_ext() builds a context, runs the program, and applies the result. The code is short enough to read whole:

static noinline const char *
walk_component_namei_ext(struct nameidata *nd, int flags)
{
	struct namei_ext_redirect redirect;
	struct qstr saved_last;
	struct qstr redirected_last;
	bool redirected;
	const char *res;
	int error;

	error = namei_ext_lookup(&nd->path, nd->inode, &nd->last,
				 NAMEI_EXT_LOOKUP, nd->flags & ~LOOKUP_RCU,
				 &redirect);
	if (unlikely(error)) {
		if ((nd->flags & LOOKUP_RCU) && !try_to_unlazy(nd))
			return ERR_PTR(-ECHILD);
		return ERR_PTR(error);
	}
	if (redirect.target_pending) {
		error = namei_ext_resolve_target(&redirect,
						 nd->flags & LOOKUP_RCU);
		/* ... same error handling ... */
	}
	if (redirect.active && (nd->flags & LOOKUP_RCU) &&
	    !try_to_unlazy(nd))
		return ERR_PTR(-ECHILD);
	if (redirect.target_active) {
		error = namei_ext_apply_target(nd, &redirect,
					       flags & WALK_TRAILING);
		if (unlikely(error))
			return ERR_PTR(error);
		if (unlikely(nd->depth) && !(flags & WALK_MORE))
			put_link(nd);
		return NULL;
	}

	redirected = namei_ext_apply_redirect(nd, &redirect, &saved_last,
					      &redirected_last);
	if (redirected) {
		error = namei_ext_hash_redirect(nd);
		/* ... restore nd->last on error ... */
	}
	res = walk_component_common(nd, flags);
	if (redirected)
		nd->last = saved_last;
	return res;
}

Three details are worth noting.

  • PASS stays on RCU-walk. If the program returns PASS, nothing is active and the function drops straight into walk_component_common() in whatever mode the walk was in. That is commit c28220593eb0, "keep pass decisions in RCU walk".
  • REDIRECT leaves RCU-walk. Before swapping nd->last for the new name, it calls try_to_unlazy(). The redirected name is then rehashed (with the filesystem's d_hash if it has one, for case-insensitive filesystems for example), looked up through the normal code in the same parent directory, and the original name is restored afterwards. REDIRECT is "same-parent rename at lookup time", not "jump anywhere".
  • SELECT_TARGET returns NULL without calling step_into. The walk continues from the swapped-in nd->path, so the next component is looked up inside the selected directory.

open_last_lookups_namei_ext() has the same shape for the final component of open(). It first ORs in op->intent, so the policy sees whether this is a create (LOOKUP_CREATE), and then calls open_last_lookups_common(), which is the original open/create code.

Turning a BPF return value into a kernel action

namei_ext_lookup() in the new fs/namei_ext.c runs the program and checks what it asked for. This function is where "bounded actions" gets its meaning:

	namei_ext_init_ctx(&ctx, parent, parent_inode, event, lookup_flags, name);
	action = __cgroup_bpf_run_namei_ext(&ctx, parent);
	if (action < 0)
		return action;

	switch (action) {
	case BPF_NAMEI_EXT_PASS:
		return 0;
	case BPF_NAMEI_EXT_REDIRECT:
		if (lookup_flags & LOOKUP_CREATE)
			return -EOPNOTSUPP;
		if (!namei_ext_redirect_valid(&ctx))
			return -EINVAL;
		namei_ext_fill_redirect(parent, &ctx, redirect);
		return 0;
	case BPF_NAMEI_EXT_HIDE:
		return -ENOENT;
	case BPF_NAMEI_EXT_SELECT_TARGET:
		if (lookup_flags & LOOKUP_CREATE)
			return -EOPNOTSUPP;
		redirect->target_cgroup_id = ctx.cgroup_id;
		redirect->target_id = ctx.target_id;
		redirect->target_pending = true;
		return 0;
	default:
		return -EINVAL;
	}

namei_ext_redirect_valid() rejects an empty name, a name longer than 64 bytes, ".", "..", and any name containing '/' or NUL. So REDIRECT can never climb out of the parent or inject a multi-component path. HIDE is just -ENOENT: the process gets the same error as for a file that does not exist. Both object-changing actions refuse O_CREAT-style lookups with -EOPNOTSUPP, so a policy cannot redirect a create to somewhere else.

Accepting a policy-selected object

The authors call SELECT_TARGET the hard part, and the reason is in the code. A BPF program cannot return a pointer or a path string. It returns a small integer target_id. The kernel looks the ID up in a registry of struct paths that user space registered earlier (see below), keyed by (cgroup id, target id). Before the walk accepts that object, namei_ext_apply_target() enforces the caller's own constraints:

	borrowed = redirect->target_borrowed;
	if (unlikely(nd->flags & LOOKUP_IS_SCOPED))
		goto err_exdev;
	if (unlikely((nd->flags & LOOKUP_NO_XDEV) &&
		     nd->path.mnt != redirect->target.mnt))
		goto err_exdev;
	if (unlikely(!d_can_lookup(redirect->target.dentry) &&
		     !d_is_reg(redirect->target.dentry))) {
		error = -EOPNOTSUPP;
		goto err_target;
	}
	if (unlikely(!d_can_lookup(redirect->target.dentry) &&
		     (!final || (nd->flags & LOOKUP_DIRECTORY)))) {
		error = -ENOTDIR;
		goto err_target;
	}

	if (borrowed) {
		if (WARN_ON_ONCE(!(nd->flags & LOOKUP_RCU))) {
			/* ... */
			return -EINVAL;
		}
		nd->seq = read_seqcount_begin(&redirect->target.dentry->d_seq);
	} else {
		path_put(&nd->path);
	}
	nd->path = redirect->target;
	nd->inode = nd->path.dentry->d_inode;
	nd->state |= ND_JUMPED;

Reading the checks in order:

  • An openat2() caller that asked for RESOLVE_BENEATH or RESOLVE_IN_ROOT gets -EXDEV. A teleport to a registered object cannot be proved to stay beneath the start directory, so it is refused outright. RESOLVE_NO_XDEV is refused only when the target is on a different mount. The functional test suite checks all three (select_file_no_xdev_rejected, select_file_beneath_rejected, select_file_in_root_rejected, all expecting EXDEV).
  • Only directories and regular files can be targets. A regular file is allowed only as the final component and only when the caller did not ask for O_DIRECTORY.
  • In RCU-walk the registry entry is borrowed: no reference is taken, and the walk records the target dentry's d_seq so the usual legitimization step can either take real references or fail the walk. In ref-walk, namei_ext_get_target() already took a path_get, and the old position is path_put.
  • ND_JUMPED is the flag the kernel already sets when a walk jumps (for example through a /proc/self/fd magic link). Setting it tells later code that the walk did not simply descend.

After this, the selected object goes through ordinary VFS processing: permission checks on its inode and mount, may_open, the filesystem's open, and so on. The registry's comment in the design document is precise about what this does not do: "lookup does not replay traversal through the target's physical parents." If you could not search the target's real parent directory, you can still reach the target through the logical name. That is a deliberate grant of reachability, and it is why registration is a privileged operation.

Lifetime: the registry under RCU

Registry replacement uses the textbook RCU pattern. The writer swaps the hash-list node, waits a grace period, and only then drops the old struct path:

	hash_for_each_possible(namei_ext_targets, target, node, key) {
		if (target->cg_id != cg_id ||
		    target->target_id != target_id)
			continue;
		hlist_replace_rcu(&target->node, &new_target->node);
		old_target = target;
		break;
	}
	if (!old_target)
		hash_add_rcu(namei_ext_targets, &new_target->node, key);
out_unlock:
	mutex_unlock(&namei_ext_targets_lock);
	if (ret) {
		kfree(new_target);
	} else if (old_target) {
		synchronize_rcu();
		path_put(&old_target->path);
		kfree(old_target);
	}

So an RCU-walk that borrowed the old path before the swap can still use it safely until it either legitimizes (takes its own references) or drops out of RCU. The implementation notes describe a Phase 1 test that replaces a target 128 times while another process reads through it continuously, and a deterministic tracing-BPF "litmus" for the race window. The notes say the litmus had no repaired KVM result yet at the time they were written.

At-least-once

The design document states the semantics outright: in-place RCU-to-ref conversion reuses the saved action, but if namei returns -ECHILD and the VFS restarts the whole walk, "policy again" runs. "The ABI is therefore at-least-once across a full VFS restart; policy-visible side effects must be idempotent." Counting lookups in a map is fine. A policy that, say, grants one-shot access and then revokes it on first use is not.

Directory listings: iterate_dir

A view that hides secret on lookup but still lists it in ls is inconsistent, and tools notice. namei_ext therefore also hooks directory iteration. In fs/readdir.c the call to file->f_op->iterate_shared is wrapped behind the same gate. The wrapper swaps in its own dir_context whose actor runs the BPF program once for each entry the lower filesystem emits:

	namei_ext_init_ctx(&bpf_ctx, &namei_ctx->file->f_path,
			   file_inode(namei_ctx->file),
			   BPF_NAMEI_EXT_READDIR, 0, &qname);
	action = __cgroup_bpf_run_namei_ext_cgroup(namei_ctx->cgrp, &bpf_ctx);

	switch (action) {
	case BPF_NAMEI_EXT_PASS:
		/* ... forward entry unchanged to the caller's actor ... */
		return true;
	case BPF_NAMEI_EXT_REDIRECT:
		if (!namei_ext_redirect_valid(&bpf_ctx)) {
			namei_ctx->error = -EINVAL;
			return false;
		}
		/* ... forward entry under bpf_ctx.redirect_name ... */
		return true;
	case BPF_NAMEI_EXT_HIDE:
		return true;
	case BPF_NAMEI_EXT_SELECT_TARGET:
		namei_ctx->error = -EOPNOTSUPP;
		return false;
	default:
		namei_ctx->error = action < 0 ? action : -EINVAL;
		return false;
	}

HIDE in readdir skips the entry ("return true" means "keep iterating"). REDIRECT renames the entry in the listing. SELECT_TARGET makes no sense for a single listed name and fails the getdents call. Note who is responsible for consistency: the kernel does not tie lookup and readdir together. The design document says plainly that "the policy, not the kernel, is responsible for making directory visibility agree with lookup selection". That is why the sample policies handle both events. The prototype also cannot add a synthetic entry. The design says that "synthetic parent-directory aliases such as listing an otherwise nonexistent ws entry from its parent fail closed or remain unsupported."

Policy decision: one function, four actions

The context and the verifier

The UAPI struct is the whole interface:

#define BPF_NAMEI_EXT_NAME_MAX 64

#define BPF_NAMEI_EXT_LOOKUP 0
#define BPF_NAMEI_EXT_READDIR 1

#define BPF_NAMEI_EXT_PASS 0
#define BPF_NAMEI_EXT_REDIRECT 1
#define BPF_NAMEI_EXT_HIDE 2
#define BPF_NAMEI_EXT_SELECT_TARGET 3

struct bpf_namei_ext_ctx {
	__u32 event;
	__u32 flags;
	__u32 name_len;
	__u32 name_hash;
	__u64 cgroup_id;
	__u8 name[BPF_NAMEI_EXT_NAME_MAX];
	__u32 redirect_name_len;
	__u32 target_id;
	__u8 redirect_name[BPF_NAMEI_EXT_NAME_MAX];
	__u64 parent_dev;
	__u64 parent_ino;
	__u32 parent_generation;
	__u32 parent_flags;
};

The repository ships its own copy of this header for the policies (with hand-written __u32 typedefs and a SEC macro, so policies build without vmlinux.h or libbpf headers). The kernel's namei_ext_is_valid_access() enforces the read/write split. Programs may read every field. name[] and redirect_name[] may only be read one byte at a time. Writes are allowed only to redirect_name_len, target_id and bytes of redirect_name[]. The verifier's return-range check, added in verifier.c, pins the return value to [BPF_NAMEI_EXT_PASS, BPF_NAMEI_EXT_SELECT_TARGET]. As a second line of defence, the run loop turns anything above 3 into -EINVAL. Helpers are the cgroup-common set plus bpf_perf_event_output and the base protos (maps, atomics, and so on). There are no filesystem-specific helpers or kfuncs: a policy cannot read file contents or walk dentries itself.

Names longer than 64 bytes are truncated in name[], but name_len holds the true length, so an exact-match policy that compares name_len first (as all the shipped helpers do) will never match a truncated long name by mistake.

Which program runs: cgroups, owners and parent scopes

Dispatch in kernel/bpf/cgroup.c uses the calling task's default-hierarchy (v2) cgroup:

int __cgroup_bpf_run_namei_ext(struct bpf_namei_ext_ctx *ctx,
			       const struct path *parent)
{
	struct cgroup *cgrp;
	struct cgroup *owner;
	int action = BPF_NAMEI_EXT_PASS;

	rcu_read_lock_dont_migrate();
	cgrp = task_dfl_cgroup(current);
	owner = rcu_dereference(cgrp->bpf.namei_ext_owner);
	if (owner && namei_ext_policy_parent_matches(owner, parent))
		action = cgroup_bpf_run_namei_ext_locked(cgrp, ctx);
	rcu_read_unlock_migrate();
	return action;
}

The owner is the nearest ancestor cgroup (or the cgroup itself) that actually has a namei_ext program attached. activate_effective_progs() recomputes it on every attach and detach. The owner's parent scope is a list of up to eight exact directories (NAMEI_EXT_MAX_POLICY_PARENTS), or "global" (empty list, so every parent matches). User space sets it through /sys/kernel/debug/namei_ext/policy_parent. The run loop goes through the effective program array, and the first non-PASS result wins. It also stamps ctx->cgroup_id, so the policy can key maps by cgroup and give each cgroup its own view.

Attach semantics are kept simple. bpf_prog_attach() must pass zero attach_flags, relative_fd and expected_revision, and BPF_LINK_CREATE returns -EOPNOTSUPP, so there is no bpf_link support yet. The fork lists the type in is_net_admin_prog_type(), the same bucket as the other cgroup program types, so loading one needs the corresponding admin capability.

Walkthrough: one lookup, step by step

Take an agent-workspace setup modelled on the repository's agent_workspace_source_task policy. The logical path is /work/view/ws/src/main.py. The policy is attached to cgroup agentA, with parent scope exact /work/view. The controller has registered target ID 1 as /snap/a (an O_PATH fd to a real directory on ext4) and put (agentA, /work/view, "ws") → 1 into the agent_source_task_views map. A process in agentA calls open("/work/view/ws/src/main.py", O_RDONLY).

1. Enter the walk

do_sys_openat2 → path_openat → link_path_walk, starting in RCU-walk at /. The string is split into work, view, ws, src and the final main.py.

2. "work" and "view": unmanaged parents

For each component, walk_component tests the gate. The static key is on (some program is attached somewhere), but namei_ext_parent_maybe_managed() finds neither / nor /work in the exact-parent index. No context is built, no cgroup is looked up, and stock walk_component_common runs. This is the "skip unmanaged parents before dispatch" fast path.

3. "ws": managed parent, program runs

The parent is now /work/view, which is in the index, so control goes to walk_component_namei_ext. namei_ext_init_ctx copies "ws", its length and hash, and the parent's s_dev/i_ino/i_generation. The dispatcher finds the task's cgroup, its owner (agentA), checks that /work/view matches the owner's scope, sets cgroup_id, and runs the program.

4. The policy decides

The program checks namei_ext_is(ctx, "ws"), builds a namei_ext_component_key (cgroup, parent dev/ino, name), finds value 1 in the map, writes ctx->target_id = 1, and returns BPF_NAMEI_EXT_SELECT_TARGET. Had the map entry been missing, it would have returned HIDE, and the open would fail with ENOENT right here.

5. Kernel resolves the target in RCU mode

namei_ext_lookup marks the target pending (this is not a create, so no EOPNOTSUPP). namei_ext_resolve_target runs under RCU, finds (agentA, 1) in the registry hash, and borrows its struct path without taking a reference. If the ID were unregistered, the result would be ENOENT.

6. Validate and swap

namei_ext_apply_target checks: no LOOKUP_IS_SCOPED, no cross-mount LOOKUP_NO_XDEV, the target is a directory, and this is an intermediate component so a directory is required. It records the target's d_seq, sets nd->path = /snap/a, and marks ND_JUMPED. walk_component returns NULL, so there is no symlink to follow.

7. "src" inside the selected tree

The parent is now /snap/a. It is not a managed parent, so stock lookup runs again and finds /snap/a/src in the dcache. The policy is not called.

8. Final component and open

open_last_lookups for main.py: the parent /snap/a/src is unmanaged, so the original code runs. Legitimization converts the RCU walk into references. If a sequence check fails because a writer replaced target 1 in the meantime, the walk either drops to ref-walk in place or restarts with -ECHILD. On a restart, the policy runs again. may_open checks ext4 permissions on the real inode, and the file is opened.

9. After open

The descriptor refers to an ordinary ext4 file. Reads, writes, mmap, fsync and page cache are all ext4's. The BPF program never sees them. The RQ3 experiment states this directly: "an already selected namei_ext descriptor continued through lower-file operations without re-entering BPF." A process in agentB opening the same string meanwhile gets whatever its map entry selects, for example /snap/b.

The policies are plain C with no CO-RE and no BTF-typed kernel pointers, because the context is a flat UAPI struct. Start with the two smallest. pass_only.bpf.c (returns PASS) exists to measure the cost of an attached program that does nothing. hide_secret.bpf.c is the "hello world":

Looking up tool opens the sibling tool.real. Listing the directory shows tool.real under the name tool. The two directions mirror each other, so the view is consistent.

SEC("cgroup/namei_ext")
int namei_ext_policy(struct bpf_namei_ext_ctx *ctx)
{
	if (ctx->event == BPF_NAMEI_EXT_LOOKUP &&
	    namei_ext_is(ctx, "portal")) {
		ctx->target_id = 1;
		return BPF_NAMEI_EXT_SELECT_TARGET;
	}
	if (ctx->event == BPF_NAMEI_EXT_LOOKUP &&
	    namei_ext_is(ctx, "selected-file")) {
		ctx->target_id = 2;
		return BPF_NAMEI_EXT_SELECT_TARGET;
	}
	/* ... "selected-exec" → 3, "pinned-file" → 4 ... */

	return BPF_NAMEI_EXT_PASS;
}

The program knows only numbers. What 1 means (a directory) and 2 means (a regular file) is up to the controller's registrations. Note that portal does not have to exist on disk under its parent: a lookup of a name with no real dentry can still resolve, because the swap happens before the dcache lookup. That is why the functional suite checks select_portal_before_attach expecting ENOENT, and the same path succeeding afterwards.

A stateful policy: per-agent workspace views

The headline case study is agent_workspace_source_task.bpf.c. It turns the abstract question ("can two agents see different trees at one path?") into a map lookup keyed by cgroup, parent identity and name. Counters are kept so experiments can show that the policy actually took part:

struct {
	__uint(type, BPF_MAP_TYPE_HASH);
	__uint(max_entries, NAMEI_EXT_POLICY_MAX_STATE);
	__type(key, struct namei_ext_component_key);
	__type(value, __u32);
} agent_source_task_views SEC(".maps");
/* ... counter arrays, count_array() ... */

SEC("cgroup/namei_ext")
int namei_ext_policy(struct bpf_namei_ext_ctx *ctx)
{
	struct namei_ext_component_key key = {};
	__u32 *target_id;

	/* ... count total / lookup / readdir ... */
	if (!namei_ext_is(ctx, "ws")) {
		count_array(&agent_source_task_counters, AST_COUNTER_PASS);
		return BPF_NAMEI_EXT_PASS;
	}

	namei_ext_build_component_key(ctx, &key);
	key.event = 0;
	target_id = bpf_map_lookup_elem(&agent_source_task_views, &key);
	if (!target_id || !*target_id) {
		/* ... count hide ... */
		return BPF_NAMEI_EXT_HIDE;
	}

	if (ctx->event == BPF_NAMEI_EXT_READDIR) {
		count_array(&agent_source_task_counters, AST_COUNTER_PASS);
		return BPF_NAMEI_EXT_PASS;
	}

	ctx->target_id = *target_id;
	count_array(&agent_source_task_counters, AST_COUNTER_SELECT);
	/* ... per-target hit counter ... */
	return BPF_NAMEI_EXT_SELECT_TARGET;
}

Look at the readdir branch. When a view exists, the ws entry is listed as-is (PASS); when it does not, it is hidden. Lookup and listing agree. Switching an agent to another snapshot means one map update. Rolling back means another. Withdrawing the workspace means deleting the entry, after which ws disappears from both stat and ls for that cgroup only. The key includes cgroup_id, so one attached program serves many cgroups with different views. This is the "per-agent view of the filesystem" in its most literal form. Compare chapter 25, where cgroups are used to account agent resources, and chapter 24, where BPF LSM blocks agent actions. namei_ext uses the same cgroup grouping to choose what the agent sees.

The other policies

Each case study has its own policy, and the README stresses that they "intentionally contain different bounded decision structures tied to workload semantics":

application_file_sharing

Modelled on Flatpak's xdg-document-portal. A sharing_scopes map (keyed with cgroup_id = 0) marks a managed document by parent and name. A sharing_grants map keyed by the application's cgroup either selects the document or hides it. Revoking a grant means deleting one map entry.

build_action_sandboxing

Modelled on Bazel sandboxes: two concurrent actions see different declared-input roots at one logical path, and undeclared inputs are hidden in both lookup and listing.

toolchain_environment

Nix-style environment selection: one logical interpreter path, two installed trees, per-process-group switch and rollback.

kubernetes_configmap_publication

Selects among already-written ConfigMap payload generations (V0/V1) under a stable root, mirroring kubelet's AtomicWriter.

checkpoint_restore_migration

After a DMTCP restart, a remembered path is mapped from generation A to generation B.

spindle_staging

Maps exact source components to node-local cache files that the Spindle HPC loader populated.

rq3_invalid_action / rq3_invalid_ctx_write / rq3_fault_injection

Deliberately broken policies. Two must be rejected by the verifier (a return value out of range, and a write to a read-only ctx field). The rest exercise runtime failures such as unregistered IDs and bad redirect names.

table_redirect, *_view families

An older exact-table design that the project has retired (the docs say so explicitly), plus earlier policy families for build graphs, fixtures, checkpoints and cache locality.

The user-space side

There is no daemon and no policy language. User space does three things: load and attach the program, publish the objects it may select, and update maps. All of it is in runner/src/namei_ext_harness.c, a 700-line static library that the experiment runners share.

The registry is keyed by the writer's cgroup, so the harness forks a child, moves it into the target cgroup, and has the child write "<id> <fd>\n". The kernel turns the fd into a pinned struct path. Writing "clear" drops all of that cgroup's targets. Passing an fd instead of a path string means the kernel never parses a path on behalf of the policy.

static int fill_component_key(struct namei_ext_component_key *key,
			      uint64_t cgroup_id, const char *parent,
			      const char *name)
{
	struct stat st;
	size_t name_len = strlen(name);

	if (name_len > sizeof(key->name))
		return -ENAMETOOLONG;
	if (stat(parent, &st))
		return -errno;
	memset(key, 0, sizeof(*key));
	key->name_len = name_len;
	key->cgroup_id = cgroup_id;
	key->parent_dev = st.st_dev;
	key->parent_ino = st.st_ino;
	memcpy(key->name, name, name_len);
	return 0;
}

The kernel fills parent_dev with huge_encode_dev(sb->s_dev). The latest kernel commit, "expose stat-compatible parent device", makes that match st_dev from stat(2), so user space can build keys from an ordinary stat. The cgroup ID comes from name_to_handle_at() on the cgroup directory.

One more control file, /sys/kernel/debug/namei_ext/policy_parent, sets the owner cgroup's scope: exact <fd>, add <fd>, clear, or global. Both debugfs files are created with mode 0200, which means root-only. Using debugfs as the control plane marks this as a prototype. A mainline version would presumably use a syscall, a map type, or bpf_link attributes, but the repository does not discuss which.

Building and running it

Every workflow goes through Make, and the project's rules forbid shell-script control planes. On a suitable host (KVM available, enough RAM and disk to build a kernel), the documented entrypoints are:

git clone --recurse-submodules https://github.com/eunomia-bpf/namei_ext   # kernel/ is the Linux fork
cd namei_ext
make phase1        # ABI, BPF objects, userspace tests, kernel objects, KVM boot,
                   # policy load/attach, and the functional suite in the guest
make experiments   # development gates for the implemented case studies
make formal-case-studies    # paper-facing RQ1/RQ2/RQ3 case studies
make formal-performance     # paper-facing performance matrices
make experiment-agent-workspace-rq2   # e.g. the ten-pair namei_ext vs FUSE lifecycle

mk/kernel.mk checks that the built kernel's .config has CONFIG_NAMEI_EXT=y, CONFIG_BPF_SYSCALL=y, CONFIG_BPF_JIT=y, CONFIG_CGROUP_BPF=y, CONFIG_FUSE_FS=y and CONFIG_DEBUG_INFO_BTF=y. It also builds the fork's bpftool and checks that the binary knows the string cgroup/namei_ext.

What you can do without the custom kernel is compile the policies. The BPF Makefile is a single clang rule (clang -g -O2 -target bpf -D__TARGET_ARCH_x86 -Iinclude -c), and the policy headers are self-contained. For this chapter, make -C bpf OUTPUT=/tmp/ne28/bpfout produced all 25 objects (24 policies plus one tracing program) in the orb. Loading them fails on any stock kernel, because BPF_PROG_TYPE_NAMEI_EXT does not exist there.

Do not try this on your workstation kernel

The mechanism exists only in the fork. Building and booting a patched 7.1-rc kernel is real work: the project runs it inside KVM guests, never on the host. The orb used for this curriculum could not do it (stock 6.1 kernel, no nested KVM), so nothing in this chapter was observed running. All runtime behaviour described here comes from reading the code and the repository's recorded results.

Evaluation: what the repository reports

The evaluation is set up as three research questions (from docs/idea-story.md and docs/paper/sections/05-evaluation.tex):

  • RQ1, expressiveness: can the narrow hook express real, state-dependent path-view policies? The evidence is seven industrial workflows (W1–W7), each checked against a correctness "oracle" derived from the real source system, through the real cgroup/namei_ext attach path in KVM.
  • RQ2, cost versus FUSE: the same policy implemented as a feature-equivalent FUSE service and held to the same oracle.
  • RQ3, ownership boundary: compared with a stackable filesystem (a port of Wrapfs to the same kernel), which filesystem methods and runtime responsibilities each one takes on.

How to read these numbers:

  • The 11× lifecycle result is a mechanism microbenchmark of view operations, not an end-to-end agent speedup. The draft says so itself: "a mechanism-level lifecycle comparison, not an end-to-end agent-task speedup."
  • Against a cached FUSE (metadata and kernel caching on; the draft reports "only 0–19 measured requests per cell"), the cache-hot path-walk advantage is about 5–9%. That is a fair comparison, because FUSE is not being made to pay a daemon round trip on every lookup.
  • The cost of having a policy attached on a managed path is real. Attached PASS keeps 90–93% of unattached throughput on these walk-heavy microbenchmarks. Selecting a target adds little on top of PASS (SELECT/PASS 0.981–0.999).
  • The unused fast path result is what makes it plausible to put such a hook on a system-wide hot path: a patched kernel with nothing attached is statistically indistinguishable from stock on this benchmark and host. The draft limits the claim accordingly: "cold caches, other operations, tail latency, and other machines remain open."
  • The readdir result is reported honestly as mixed: with four workers sharing one directory, all variants converge and the advantage disappears.

Benefits and limitations

Benefits

  • Native semantics after selection. Once a name resolves, the file is an ordinary ext4/tmpfs object: page cache, mmap, locking, permissions and xattrs behave as usual, with no FUSE round trips on data.
  • Instant, per-cgroup views. Switching, rolling back or withdrawing a view is a map update. Two cgroups can see different objects at one path without separate mount namespaces.
  • Small, verifiable policy surface. Four actions, three writable fields, and a verifier-checked return range. The kernel validates every result (redirect names, target types, openat2 scoping) and fails closed.
  • Near-zero cost when unused, as measured on the reported host: a static key plus an exact-parent filter keep unrelated lookups on the stock path.
  • Consistent model across lookup and listing, since one function handles both events.

Limitations

  • Out-of-tree kernel patch against 7.1-rc7. The repository links no upstream submission, there is no bpf_link support, and the control plane is debugfs.
  • Selection only. No synthetic files or entries, no content transformation, no create redirection (LOOKUP_CREATE → EOPNOTSUPP), no symlink or special-file targets, and no cross-path transactions. The design document lists all of these.
  • Consistency is the policy's job. The kernel does not stop a policy that hides on lookup but lists on readdir.
  • At-least-once execution across -ECHILD restarts, so side effects must be idempotent.
  • Reachability grant. A registered target is reachable through the logical name even if the caller could not traverse its physical parents. Registration is therefore root-only (debugfs 0200), and a rename or unlink of the target does not revoke it: "the controller must replace or clear it."
  • Scoped walks refuse SELECT. RESOLVE_BENEATH/IN_ROOT callers get EXDEV, so sandboxed runtimes that resolve with those flags cannot use selected objects.
  • 64-byte names in the context; up to eight exact managed parents per owner cgroup.
  • Evaluation scope is cache-hot microbenchmarks plus case-study oracles on one host, with cold-cache, tail latency and multi-host results still open (per the draft).

Related work

  • Mount namespaces, bind mounts, OverlayFS. These are the standard kernel tools for per-container views. They build the view before lookup, at subtree granularity. namei_ext's authors treat them as related work rather than direct competitors, because changing a view means changing mount state.
  • openat2() RESOLVE_* flags. These restrict resolution for one call. namei_ext changes resolution for a cgroup, and defers to these restrictions when both apply.
  • Landlock and BPF LSM (chapter 05, chapter 24). These mediate access to an already-resolved object. namei_ext's design document calls BPF LSM "the neighboring security hook, not the same abstraction".
  • sched_ext (chapter 05) is the design analogy: BPF supplies policy inside a subsystem whose mechanism stays in the kernel. sched_ext uses struct_ops with many callbacks. namei_ext deliberately uses a single decision function.
  • FUSE, ExtFUSE (USENIX ATC '19), FUSE-BPF. These are the closest mechanisms. ExtFUSE lets eBPF handlers serve some FUSE requests in the kernel. FUSE-BPF (Android, discussed at LSFMM+BPF 2023) makes FUSE a stacked filesystem with BPF pre- and post-filters, and one of its uses is hiding directories. The namei_ext design document admits that FUSE-BPF's passthrough mode means "daemon elimination is not the distinction". The remaining difference it claims is that there is no mounted FUSE instance, no FUSE inodes, and no operation forwarding.
  • Stackable and custom filesystems: Wrapfs, Bento (FAST '21). Fully expressive, but the developer owns the filesystem methods. The RQ3 experiment quantifies this for one workload: 34 VFS slots registered by the Wrapfs port, against lookup and readdir decisions only.
  • "To FUSE or Not to FUSE" (FAST '17) is the standard reference for FUSE overheads. FxMark (USENIX ATC '16) is the benchmark suite used for the path-walk and readdir matrices.
  • Within this curriculum, gpu_ext is the sister project that applies the same "BPF policy, kernel mechanism" idea to GPU memory and scheduling.

Check your understanding

Q1. How does a namei_ext policy get into the kernel?

The fork adds BPF_PROG_TYPE_NAMEI_EXT and BPF_CGROUP_NAMEI_EXT, built like the other cgroup program types. The program's return value is the action. No struct_ops and no kfuncs.

Q2. A policy returns REDIRECT with redirect_name = "../etc". What happens?

namei_ext_redirect_valid() rejects empty names, names over 64 bytes, ., .., and any / or NUL byte. REDIRECT only renames a lookup within the same parent. The verifier cannot see string contents written at run time, so the check happens in the kernel at lookup.

Q3. Why does a policy that hides secret need to handle the READDIR event too?

The design document says "the policy, not the kernel, is responsible for making directory visibility agree with lookup selection". That is why the shipped policies check both events.

Q4. A program increments a map counter and, on its first call for a given name, flips a one-shot "grant" off. Why is the second part risky?

Converting in place from RCU-walk to ref-walk reuses the saved action, but a full restart calls the program again. The second call would see the grant already spent and hide the file from the same system call.

Q5. A sandboxed runtime opens files with openat2(..., RESOLVE_BENEATH), and the policy returns SELECT_TARGET for a component. What does the caller see?

namei_ext_apply_target() returns -EXDEV whenever LOOKUP_IS_SCOPED (BENEATH or IN_ROOT) is set, and for RESOLVE_NO_XDEV when the target is on another mount. The functional tests check all three cases.

Q6. What keeps namei_ext nearly free on a busy system where most paths are not managed?

The gate namei_ext_enabled() && namei_ext_parent_maybe_managed() sends everything else down the unchanged stock path. The repo's 60-boot experiment reports patched-unattached/stock throughput of about 1.00 with confidence intervals spanning 1.
