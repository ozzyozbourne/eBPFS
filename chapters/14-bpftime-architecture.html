Chapter 14

bpftime architecture: eBPF without the kernel round trip

A kernel uprobe traps into the kernel on every hit. bpftime takes an unmodified libbpf tool, intercepts its bpf() calls, keeps its programs and maps in shared memory, and patches the target process so the probe jumps straight into JIT-compiled eBPF in user mode. This chapter explains how each of those pieces works, using the source code, and what the OSDI '25 paper adds on top: the Extension Interface Model.

Why this matters

Chapter 05 showed what a uprobe costs. The kernel writes an int3 over the first byte of the probed instruction. Every call of the function raises a breakpoint exception, switches to kernel mode, runs the BPF program, emulates or single-steps the displaced instruction, and returns to user mode. That is acceptable for readline(). It is expensive for malloc(), SSL_read() or a per-request handler in a busy server, because most of the time goes into the mode switches, not into the BPF program.

The obvious fix is to run the probe in the traced process itself, the way a dynamic-instrumentation tool such as Frida or Pin does. The difficult part is keeping the eBPF model intact: programs written in restricted C, compiled by clang, loaded by libbpf, checked by a verifier, sharing maps with a control-plane process and even with kernel eBPF programs. bpftime is the eunomia-bpf project that does this. Its stated goal in the README is to be "a userspace runtime framework [that] includes everything to run eBPF in userspace: loader, verifier, helpers, maps, ufunc and multiple events". The project's OSDI '25 paper generalises the idea from tracing to application extensions and proposes a model for granting them least privilege.

Key idea

bpftime puts its compatibility layer at the system-call boundary that every eBPF tool already uses. The loader's bpf() and perf_event_open() calls are intercepted and turned into objects in a POSIX shared-memory segment. An agent library inside the target process reads that segment, JIT-compiles the programs, and attaches them with binary rewriting: an inline hook for function probes and a zpoline-style rewrite of syscall instructions for syscall tracepoints. Neither the eBPF program nor the libbpf loader needs any change.

This chapter covers the design and the code. Chapter 15 covers day-to-day use: the example tools, attach modes, and GPU support. Chapter 16 covers the LLVM-based VM that bpftime uses by default.

What bpftime is

bpftime is a C++20 code base (MIT licensed) that produces a handful of shared libraries and tools. The ones that matter for the architecture are:

libbpftime-syscall-server.so

Preloaded into the loader (the libbpf, bcc or bpftrace process). It overrides syscall(), mmap(), ioctl(), epoll_*, open() and a few more, and implements the eBPF syscall interface on top of shared memory.

libbpftime-agent.so

Loaded into the target process, either by LD_PRELOAD at start or by Frida's injector into a running process. It contains the attach backends, the helpers and the VM.

Shared memory segment

A Boost.Interprocess managed_shared_memory named bpftime_maps_shm. It holds the handler table (progs, maps, perf events, links), the map data and the runtime config.

libbpftime-agent-transformer.so

The syscall-hook bootstrap. It rewrites every syscall instruction in the target and then loads the agent into a fresh link-map namespace.

bpftime, bpftimetool

The CLI (load, start, attach, detach, trace) and a tool that exports, imports and runs the shared-memory state as JSON.

bpftime_daemon

Optional. A kernel eBPF program plus a user-space driver that watches real bpf() calls system-wide and mirrors uprobe programs into bpftime, so they run in user space after the kernel verifier has checked them.

The paper describes the same split in its own terms: a loader that is "a thin interposition layer between eBPF applications and the kernel", a runtime that "executes extensions in the same process as the original application", and maps with "three sharing modes: local process (nonshared), shared across multiple processes, and shared across processes and the kernel".

The architecture at a glance

The loader and the target are separate processes, which is deliberate. In kernel eBPF the control plane (the libbpf program that loads, attaches and reads maps) talks to the kernel, and the kernel runs the program in whatever process hits the hook. bpftime keeps that shape and replaces the kernel with a shared-memory segment. The loader still "creates a map" and gets back a file descriptor. The target still "runs the program when the hook fires". The two sides do not need to run at the same time: you can load first and start or attach later, and the README notes that "You should always run the load first then run the start command, or the eBPF program will not be attached".

The loader: intercepting bpf() with LD_PRELOAD

Why a preloaded library sees libbpf's system calls

libbpf does not issue the syscall instruction itself. It calls glibc's syscall() wrapper with __NR_bpf. When a shared library listed in LD_PRELOAD defines a symbol named syscall, the dynamic linker resolves libbpf's reference to that definition first, so every eBPF system call of the loader goes through bpftime. The preloaded library finds the real function with dlsym(RTLD_NEXT, "syscall"). Here is the dispatcher, trimmed:

extern "C" long syscall(long sysno, ...)
{
	// glibc directly reads the arguments without considering
	// the underlying argument number. So did us
	va_list args;
	va_start(args, sysno);
	long arg1 = va_arg(args, long);
	/* ... arg2 .. arg6 ... */
	va_end(args);
	if (!initialize_ctx())
		return fallback_syscall(sysno, arg1, arg2, arg3, arg4, arg5,
					arg6);
	auto call_original = [&]() {
		return context->orig_syscall_fn(sysno, arg1, arg2, arg3, arg4,
						arg5, arg6);
	};
	if (sysno == __NR_bpf) {
		/* ... */
		int cmd = (int)arg1;
		auto attr = (union bpf_attr *)(uintptr_t)arg2;
		auto size = (size_t)arg3;
		return handle_exceptions(
			[&]() {
				return context->handle_sysbpf(cmd, attr, size);
			},
			call_original);
	} else if (sysno == __NR_perf_event_open) {
		/* ... */
		return handle_exceptions(
			[&]() {
				return context->handle_perfevent(
					(perf_event_attr *)(uintptr_t)arg1,
					(pid_t)arg2, (int)arg3, (int)arg4,
					(unsigned long)arg5);
			},
			call_original);
	} /* ... dup3, memfd_create ... */
	return call_original();
}

Note handle_exceptions(..., call_original): if the emulation throws (for example a Boost bad_alloc because the segment is full) the shim falls back to the real system call instead of crashing the loader. The same file overrides mmap, munmap, ioctl, epoll_create1, epoll_ctl, epoll_wait, close, open, openat, read and the fopen family. libbpf uses each of these somewhere in the load path. It mmaps ring buffers and array maps, calls ioctl(PERF_EVENT_IOC_ENABLE) on probe fds, waits on ring buffers with epoll, and reads sysfs files to learn the uprobe PMU type.

The context constructor resolves all the original functions and then calls unsetenv("LD_PRELOAD"), with the comment "To avoid polluting other child processes". A loader that forks helper programs does not pass the shim on to them.

What each bpf() command becomes

syscall_context::handle_sysbpf() is a switch over the bpf_cmd. Map commands go to bpftime_maps_create, bpftime_map_lookup_elem and so on. BPF_LINK_CREATE and BPF_PROG_ATTACH record links. BPF_MAP_FREEZE is accepted and ignored ("we didn't implement this"). Unknown commands are passed to the real kernel. Program load is the interesting case:

The program is stored as raw eBPF instructions in the shared-memory handler table, and the returned "fd" is just the index of its slot. Nothing is compiled yet. Compilation happens later, in the target, because the JIT output has to live in the target's address space. The verifier part is covered in its own section below.

perf_event_open() and the files bpftime pretends exist

libbpf attaches a uprobe in two steps. It calls perf_event_open() with attr.type set to the dynamic PMU type of the uprobe event source, config1 pointing at the binary path and config2 holding the file offset. Then it links the program to the returned fd. libbpf learns the PMU type by reading /sys/bus/event_source/devices/uprobe/type. bpftime intercepts that too. handle_perfevent() compares attr->type with determine_uprobe_perf_type() and calls bpftime_uprobe_create(pid, name, offset, retprobe, ref_ctr_off). If the sysfs file does not exist, for example on a kernel without uprobes or in a container, the overridden open/fopen serve a mocked file containing MOCKED_UPROBE_TYPE_VALUE (9). That is one reason bpftime can run unmodified libbpf tools on systems where kernel eBPF is unavailable.

The same function handles tracepoints (PERF_TYPE_TRACEPOINT becomes bpftime_tracepoint_create, which is how sys_enter_openat programs are registered), software perf events (used for perf-buffer output), kprobes (recorded but only meaningful with the GPU and kernel modes) and two bpftime-specific types, BPF_TYPE_UREPLACE and BPF_TYPE_UPROBE_OVERRIDE, which replace a function or filter its return value.

Shared memory: the handler table and the maps

One segment, named objects

Everything the loader creates goes into one Boost.Interprocess managed_shared_memory segment. The segment is a file in /dev/shm that each process maps. Boost provides a heap allocator inside it (segment_manager), offset-based pointers that work at different mapping addresses, and named object lookup. The default name is bpftime_maps_shm (override with BPFTIME_GLOBAL_SHM_NAME) and the default size is 50 MB (BPFTIME_SHM_MEMORY_MB). The server creates it, and the agent opens it and looks up the same named objects:

This table is the hand-off point between the two processes. A bpf_prog_handler holds the instruction vector and name. A bpf_perf_event_handler holds "uprobe on libc.so.6 at offset X for pid P". A bpf_link_handler says "prog 4 is attached to perf event 5, with this cookie". The agent never receives a message from the loader. It scans this table.

The fds that bpftime hands to the loader are not real kernel fds. The overridden close(), mmap(), ioctl() and epoll_ctl() check whether an fd number belongs to a bpftime handler before deciding whether to emulate the call or pass it through. The calls pass -1 /* let the shm alloc fd for us */, and the handler manager picks an empty slot. How these numbers are kept from colliding with real descriptors that the loader opens later is not covered here; I did not trace that path completely.

Map implementations

Map values live inside the segment, so a loader reading a map does not need a system call: bpf(BPF_MAP_LOOKUP_ELEM) becomes a function call on shared memory. The userspace hash map, for example, is a Boost unordered_map whose allocator draws from the segment:

The should_lock flag tells the generic bpf_map_handler to wrap each operation in a spinlock guard (bpftime_lock_guard around pthread_spin_lock). That lock is one reason the paper's microbenchmark finds hash_map_lookup slower in bpftime than in the kernel (22.0 ns against 9.8 ns, see the evaluation section). The kernel's hash map lookup is RCU-protected and takes no lock. The comparison of the two designs is my reading; the paper does not explain that row.

The "kernel-user" variants in bpf_map/shared/ are the third sharing mode in the paper. The data lives in a real kernel map. A bpftime program in the target accesses it with bpf_map_lookup_elem() from libbpf (a real syscall) for hash maps, or by mmaping the kernel array for array maps. Their type numbers are the kernel's plus KERNEL_USER_MAP_OFFSET (1000) in bpftime_shm.hpp, e.g. BPF_MAP_TYPE_KERNEL_USER_HASH = 1001.

Sessions

A long-lived target can outlive many loader runs. The segment therefore carries a small seqlock, bpftime_global_epoch_state: odd values mean "server is resetting handlers", even values identify a stable session. On startup the syscall server calls begin_new_session(), and when the agent sees the epoch change it destroys its old attachments and rebinds. The segment also records alive agent and server PIDs so the last process out can remove it.

bpftime start ./prog forks and execs the program with LD_PRELOAD set to the agent. The agent's __libc_start_main wins symbol resolution, swaps main for bpftime_hooked_main, and so runs its initialisation before the program's own main. bpftime attach PID uses frida-core's injector instead. On Linux the injector attaches to the running process with ptrace, makes it load the library, and calls the named entry point bpftime_agent_main with a data string. The paper describes the same step: "The rewriter uses ptrace to pause the host application and load the bpftime user runtime ... which allows the system to support use-cases that extend live applications." The repo's usage.md likewise says the CLI "can work with ptrace to inject the runtime shared library into a running target process". Injection therefore needs ptrace permission over the target: the same user plus a permissive Yama ptrace_scope, or root. That is why the README writes sudo bpftime attach.

From handlers to live hooks

bpf_attach_ctx::init_attach_ctx_from_handlers() walks every allocated slot of the handler table. A program handler becomes a bpftime_prog: a VM instance with the helpers registered. A perf-event handler becomes "attach private data" (for a uprobe, the module and offset). A link handler joins the two: it looks up the attach implementation registered for that perf event's type and hands it a closure that runs the program:

The final comment shows a consequence of the design. The handler table is global, so every agent sees every link. An agent in a process that has no libc.so.6:malloc simply fails to attach that link, and that is not an error. Note also what the uprobe's private data contains: instantiate_perf_event_handler_at() builds it from the string module:offset only. In my reading, the PID that libbpf passed to perf_event_open() is stored in the handler but not used here, so any agent whose process maps that module attaches. Which process runs an agent is decided by start and attach.

Loading and attaching to a running process, end to end

1. Start the loader under the syscall server

bpftime load ./example/malloc/malloc forks and execs the tool with LD_PRELOAD=libbpftime-syscall-server.so. The first intercepted call runs start_up(): it creates the segment (or opens an existing one), starts a new session epoch, configures the verifier's helper list and sets BPFTIME_USED=1.

2. libbpf loads the object as usual

The skeleton creates the libc_malloc_calls_total hash map, loads do_count, resolves libc.so.6:malloc to a file offset, and calls perf_event_open() and BPF_LINK_CREATE. Each call returns a slot index from the handler table. libbpf cannot tell that no kernel was involved.

3. Inject the agent

sudo bpftime attach 101771 calls frida_injector_inject_library_file_sync(..., "bpftime_agent_main", ...). frida-core stops the target with ptrace, makes it load libbpftime-agent.so, and calls the entry point on a thread in the target. The README shows the output Successfully injected. ID: 1.

4. Instantiate the handlers

The agent opens the segment with open_only, and init_attach_ctx_from_handlers() builds a bpftime_prog for slot 4 (creating the VM named by BPFTIME_VM_NAME, default llvm), private data for slot 5, and for link 6 calls frida_attach_impl::create_attach_with_ebpf_callback().

5. Patch the function

frida-gum's Interceptor rewrites the first instructions of malloc with a branch to a generated trampoline and relocates the displaced instructions. From now on every malloc call runs the eBPF program in user mode.

6. Read results without a kernel

The loader's polling loop calls bpf_map_get_next_key and bpf_map_lookup_elem. The shim serves them straight from the shared hash map, and the loader prints pid=... malloc calls: 10.

The paper reports what step 3 costs: "We write an extension that monitors malloc in libc, load it into a running process, and observe a 48ms load latency. For comparison, we load the same extension using LD_PRELOAD, and observe a 30ms load latency." That is a one-time cost per attach. A newer bpftime trace subcommand at this commit combines both steps: it spawns the loader, then injects or refreshes the agent over its IPC socket, passing loader_pid=...;force_reinit=1;auto_refresh_ms=500 so the agent picks up links the loader creates later.

Binary rewriting for uprobes: inline hooks instead of traps

An inline hook is old dynamic-instrumentation technique. To hook function f, overwrite its first few instructions with a jump to a trampoline. The trampoline saves the registers, calls your handler, then executes copies of the overwritten instructions (relocated, because PC-relative operands change meaning at a new address) and jumps back to f after the patched bytes. The paper describes bpftime's version in exactly these terms: "it replaces the instructions that were originally at the hook point with a call into a preamble for the point's associated eBPF function and places the overwritten instructions at the end of its preamble."

bpftime does not implement its own x86-64 instruction relocator. On x86-64 and arm64 it uses frida-gum's GumInterceptor. An entry probe is a "probe listener" and a return probe is a "call listener" with only an on_leave callback:

void frida_internal_attach_entry::ensure_listener(int attach_type)
{

/* ... */
static void uprobe_listener_on_enter(GumInvocationContext *ctx,
				     gpointer user_data)
{
	auto *hook_entry = static_cast<frida_internal_attach_entry *>(user_data);
	bpftime::pt_regs regs;
	convert_gum_cpu_context_to_pt_regs(*ctx->cpu_context, regs);
	current_thread_gum_cpu_context = ctx->cpu_context;
	hook_entry->iterate_uprobe_callbacks(regs);
	current_thread_gum_cpu_context.reset();
}

Three details matter here:

  • The program still receives a struct pt_regs *. convert_gum_cpu_context_to_pt_regs builds a kernel-layout pt_regs from Frida's saved CPU context. That is why BPF_KPROBE(do_count, ...) and PT_REGS_PARM1(ctx) work unchanged: the context the eBPF code reads has the same layout in both runtimes.
  • Short functions are a real limitation. The patch needs room for a branch. The error message in the source suggests -O0, noinline, or hooking a larger wrapper. A kernel uprobe needs only one byte, so it can probe any instruction.
  • Override and replace go beyond kernel uprobes. For ATTACH_UPROBE_OVERRIDE and ATTACH_UREPLACE bpftime calls gum_interceptor_replace(). The replacement handler runs the program, and if the program called bpf_override_return (through bpftime_override_return), it returns that value without running the original function. This is how bpftime does error injection and hot patching in user space. The kernel's bpf_override_return works only on kprobes of functions on the error-injection allowlist.

Return probes still rewrite the return address, like kernel uretprobes. The trap backend's README notes that "unwinding through the probed function (C++ exceptions, backtrace() from inside it) sees the trampoline instead of the caller. This is the same limitation the frida backend and kernel uretprobes have."

The cost of an inline hook

The paper splits the uprobe cost into parts. "The average latency of calling the extension function with the trampoline is 190ns, without the trampoline but with the extension entry is 106ns, and without both is 1.35ns." In other words, the trampoline "adds an additional 84ns for every executed extension", while an unused hook site costs nothing because no patch exists until an extension is loaded. The paper calls these concealed extension entries. Compare the kernel row of the same table, 2561.57 ns per uprobe. By my arithmetic that is about 13.5× the bpftime figure, consistent with the README's "up to 10x" claim and the arXiv abstract's "10x speed enhancement".

Not on x86 or arm: the RISC-V trap backend

frida-gum has no RISC-V port, so cmake/StandardSettings.cmake forces BPFTIME_ENABLE_TRAP_UPROBE=ON and BPFTIME_ENABLE_FRIDA=OFF when the processor matches ^riscv. attach/trap_uprobe_attach_impl then does in user space what the kernel does: it writes ebreak/c.ebreak, catches SIGTRAP, builds pt_regs from the ucontext_t, and executes the displaced instruction out of line or emulates it. Because the program then runs inside a signal handler, the runtime only admits helpers audited as async-signal-safe and JIT-compiles eagerly (prepare_for_signal_execution() in bpftime_prog.cpp). Its README reports ~5.7 µs per uprobe hit on an SG2042 host, because there are "two signal deliveries per hit". That is slower than kernel uprobes on the x86 machine in the same table, which used different hardware. The table shows that an inline hook, not merely "running in user space", is what makes bpftime's uprobes fast.

Binary rewriting for syscalls: a zpoline in the target

A syscall tracepoint (tracepoint/syscalls/sys_enter_openat) cannot be implemented by hooking one function. A program may issue syscall from libc, from a static binary, from a Go runtime, or from inline assembly. bpftime's answer is the zpoline technique (Yasukata et al., USENIX ATC '23). It rewrites every syscall instruction in the process.

The trick is that syscall (0f 05) and call *%rax (ff d0) are both two bytes long, and at a syscall site %rax always holds the syscall number. If page 0 is mapped and filled with nops, the call lands at address N, slides down the sled, and reaches a jump into the hook. The paper: "Since sysenter is smaller than a trampoline, the system uses zpoline, which uses the zero page to accommodate two-byte call instructions." Here is the code, trimmed:

static inline void rewrite_segment(uint8_t *code, size_t len, int perm)
{
	// Set the pages to be writable
	if (int err = mprotect(code, len, PROT_READ | PROT_WRITE | PROT_EXEC);
	    err < 0) { /* ... */ }
	csh cs_handle;
	cs_err ret;
	ret = cs_open(CS_ARCH_X86, CS_MODE_64, &cs_handle);
	/* ... */
	while (curr_addr < (uintptr_t)code + len) {
		auto ok = cs_disasm_iter(cs_handle, &curr_code, &size,
					 &curr_addr, &curr_insn);
		if (!ok) {
			break;
		}
		auto insn_name =
			std::string(cs_insn_name(cs_handle, curr_insn.id));
		if (insn_name == "syscall" || insn_name == "sysenter") {
			if (curr_insn.address != (uintptr_t)&syscall_addr) {
				uint8_t *curr_pos =
					(uint8_t *)(uintptr_t)curr_insn.address;
				curr_pos[0] = 0xff;
				curr_pos[1] = 0xd0;
			}
		}
	}
	cs_close(&cs_handle);
	if (int err = mprotect(code, len, perm); err < 0) { /* ... */ }
}

Several design consequences follow from this code:

  • The rewrite is a linear sweep. Capstone disassembles each executable mapping from its first byte and stops at the first undecodable byte. Data embedded in .text, or a misaligned decode, can make it miss real syscalls or, in principle, patch bytes that only look like one. zpoline has the same property.
  • Page 0 must be mappable. zpoline's README tells users to run echo 0 > /proc/sys/vm/mmap_min_addr. bpftime makes the same MAP_FIXED mmap at address 0, so it has the same requirement unless the process may map low addresses anyway. Page 0 is then set to execute-only, so ordinary NULL loads and stores still fault.
  • The hook cannot hook itself. The transformer skips its own syscall_addr instruction, which is used to issue the real syscall. More subtly, agent-transformer.cpp loads the full agent only after rewriting, with dlmopen(LM_ID_NEWLM, agent_so, RTLD_NOW | RTLD_LOCAL). A new link-map namespace gets its own copy of libc. That copy was not present during the rewrite, so the agent's own logging and allocation make plain system calls and do not recurse into the hook. The dlmopen is in the source; the explanation of why it is used is mine.
  • It is x86-64 only. The assembly trampoline exists for __x86_64__; the __aarch64__ branch reads // TODO: implement syscall trace trampoline.
  • clone is special. The assembly sends clone and clone3 down an untraced path, because the child starts on a fresh stack with no return address for the hook's ret. It seeds the child stack so the child still resumes after the rewritten instruction.

The agent's _bpftime__setup_syscall_trace_callback stores the original hook pointer, puts its own syscall_callback in its place, and runs bpftime_agent_main. From then on each rewritten syscall calls syscall_trace_attach_impl::dispatch_syscall(), which runs the sys_enter programs, performs the real syscall through the saved function, and runs the sys_exit programs. On the CLI this is the -s flag: bpftime start -s ./victim preloads the transformer with AGENT_SO pointing at the agent, and bpftime attach -s PID injects the transformer with the agent path as Frida's data argument. The usage manual shows the effect: Page zero setted up.. followed by Rewriting executable segments...

Unlike the uprobe case, this hook is not faster than the kernel. Table 3 of the paper lists "Syscall Tracepoint" at 151 ns for eBPF and 232 ns for bpftime: "about 1.5x slower". The kernel tracepoint is a branch inside a syscall that is already in the kernel. bpftime adds a user-space detour in front of a syscall that still has to enter the kernel. That explanation is mine; the paper only gives the numbers. The gain lies elsewhere. Only the rewritten process pays for the hook. With kernel syscount, the paper says the overhead falls "on every process, even those that are not monitored", and bpftime "offers configurations that prevent monitoring overhead from affecting unmonitored processes, a feature eBPF cannot provide."

Kernel–userspace interop

bpftime does not try to replace kernel eBPF. It aims to work with it. Interop works at three levels:

  • Same programs. The same malloc object file runs under sudo example/malloc/malloc in the kernel and under bpftime load in user space. The README shows both outputs. The pt_regs context and the helper numbering are kept compatible for this reason.
  • Shared maps. Kernel-user maps let a kprobe in the kernel and a uprobe in user space use one hash map. The paper's FUSE use case relies on this: a user-space metadata cache whose consistency is maintained "using a kprobe extension on unlink in the kernel". DeepFlow "adds support for using process-kernel shared maps". The kernel-user perf event array (bpf_map/shared/perf_event_array_kernel_user.hpp) takes a roundabout route. According to its header comment, user-space programs write into a BPF user ring buffer, and a small kernel program "attached to an intervally triggered event (e.g a timer perf event)" copies the data into the real kernel perf event array, where an ordinary consumer reads it.
  • Kernel as verifier and loader. The run-with-kernel mode and the daemon both use the kernel for what it does well, verification and map management, and keep the hot path in user space.

What does not carry over: kernel data structures. The README says plainly that bpftime "does not support direct access to kernel data structures or functions like task_struct", and some helpers and kfuncs do not exist in user space. bpf_get_current_pid_tgid() works because the agent runs in the traced process. bpf_get_current_task() has no meaning there.

The OSDI '25 paper: the Extension Interface Model

Two papers, one system

The project has two papers. The first is the arXiv preprint "bpftime: userspace eBPF Runtime for Uprobe, Syscall and Kernel-User Interactions" (arXiv:2311.07923, November 2023, by Yusheng Zheng, Tong Yu, Yiwei Yang, Yanpeng Hu, Xiaozheng Lai and Andrew Quinn). It describes the runtime in roughly the terms used so far in this chapter: binary rewriting for uprobes and syscalls, "interprocess eBPF Maps within shared memory", toolchain compatibility, and a uprobe that is "10x" faster than the kernel's. The second is the peer-reviewed paper: "Extending Applications Safely and Efficiently" by Yusheng Zheng (UC Santa Cruz), Tong Yu (eunomia-bpf Community), Yiwei Yang (UC Santa Cruz), Yanpeng Hu (ShanghaiTech), Xiaozheng Lai (SCUT), Dan Williams (Virginia Tech) and Andi Quinn (UC Santa Cruz), in the 19th USENIX Symposium on Operating Systems Design and Implementation (OSDI '25), Boston, July 2025, pages 557–574. The OSDI paper reframes bpftime from "faster uprobes" to "a safe extension framework for applications".

The problem the paper poses

Applications are extended all the time: Nginx and Apache modules, Lua in Redis and OpenResty, browser add-ons, and tracing tools. The paper argues that every extension framework faces a trade-off between interconnectedness ("the ability to observe or modify the host application's state and to execute functions defined by the host") and safety ("an extension failure cannot harm the health of the host application and the underlying system"). It adds two more requirements: isolation (the host cannot corrupt the extension, which matters for security extensions) and efficiency (near-native speed). Table 1 motivates the need with real incidents: a Lua livelock that took down Bilibili's Nginx, CVE-2021-44790 in Apache's Lua module, and CVE-2024-31449 in Redis's Lua scripting.

The paper defines four roles. Application developers and extension developers are "trusted but fallible". The extension manager, the person who configures a deployment, is "both trusted and infallible". Users are untrusted and may send malicious inputs. The threat model also assumes that the application's control flow cannot be hijacked, "essentially equivalent to control flow integrity", since an attacker who controls control flow could skip the extension entirely.

EIM concepts

The Extension Interface Model describes what an extension may do as a set of resources, and grants access to them as capabilities. In the paper's words: "EIM's key idea is to represent the extension features that might be necessary for interconnectedness or restricted for safety as a resource ... EIM models the ability to use a resource as a capability." A specification has two halves, written by different people:

  name = "observeProcessBegin",
  extension_entry = "processBegin",
  allowed = {instructions<inf, nginxTime, readPid, read(r)})
Extension_Class(
  name = "updateResponse",
  extension_entry = "updateResponseContent"
  allowed = {instructions<inf, read(r), write(r)})

The point is least privilege per hook. An observability extension at processBegin can read the request and the PID and call one time function. A response-rewriting extension at another entry can write the request but sees nothing else. The same entry can carry different classes in different deployments, without changing Nginx.

How the paper says bpftime enforces EIM

The paper maps each part of EIM onto a piece of the system described in this chapter:

  • Development-time spec through source annotations "based upon eBPF's kfunc annotations". bpftime also adds generic entries automatically: uprobe and uretprobe entries "for every host-defined function", and sysenter and sysexit entries for syscalls.
  • Deployment-time spec through "a YAML configuration language", with two built-in class families: observability (read arguments, bounded instructions, a subset of helpers) and customizability (also write arguments, more helpers).
  • Verification as the enforcement mechanism. The loader checks the program's signature against its class. It then turns the class into eBPF verifier input. Host types come from DWARF converted to BTF. Each function capability becomes "a mock new eBPF kfunc". Constraints become assertions inserted before the call. Read-only state becomes const in the prototype, and resource bounds become verifier clauses. Because the check is static, "without any runtime overhead".
  • Isolation by ERIM-style MPK. The paper acknowledges the system "is currently susceptible to the syscall-based attacks on ERIM" and "only supports isolation on Intel x86".
  • Concealed extension entries by the binary rewriter covered above. The paper notes "the current implementation only supports a single extension per entry point".

The paper's trusted computing base is "the kernel eBPF verifier, the binary rewriter, the operating system, and hardware-supported intra-process memory protections".

Paper versus repository

At commit 25e250d6 I found no EIM YAML parser, no Extension_Class or capability annotations, and no DWARF-to-BTF constraint generator in the bpftime tree. A search for "EIM", "Extension_Class" and YAML handling in the non-third-party sources returned nothing beyond CITATION.cff. The shipping repo implements the runtime half: interposition, shared maps, rewriting, VMs, optional PREVAIL, optional MPK on the shared segment, and kernel-verifier modes. Where the EIM tooling used for the paper lives is not something I could verify. Read the paper's EIM sections as design and evaluation, not as documentation for bpftime load.

Reading the numbers

All of these numbers come from the authors' machines and builds, measured on the paper's version of the code. Two details of the current tree affect comparisons. The memory-read rows were presumably measured with a plain memcpy. At this commit ENABLE_PROBE_READ_CHECK and ENABLE_PROBE_WRITE_CHECK default to ON, and they route bpf_probe_read* and bpf_probe_write_user through process_vm_readv/writev, which are system calls. Also, the kernel's uprobe path has become cheaper since the paper (see the 6.11 and 6.18 changes in chapter 05). The bpf-benchmark repo (chapter 19) is where the project keeps its current benchmarks.

Benefits and limitations

Fast probes

Uprobes and uretprobes run as function calls in the target (190 ns vs 2561 ns in the paper). Reading user memory and maps needs no mode switch.

Unmodified toolchain

clang, libbpf, CO-RE, bcc and bpftrace work through syscall interposition. The same object runs in the kernel or in bpftime.

No kernel eBPF needed

Userspace-only mode runs where the kernel lacks eBPF or where the user is not root. The sysfs files libbpf needs are mocked.

More than tracing

Override and replace attaches, syscall filtering, ufuncs and new attach backends make it an extension framework, not just a faster uprobe.

Per-process cost

Only processes running the agent pay for hooks. A kernel syscall tracepoint taxes every process.

Kernel interop

Kernel-user maps, kernel verification and the daemon let user-space and kernel programs cooperate.

The limitations are mostly the reverse side of the same choices:

  • The program shares the host's fate. A kernel uprobe that misbehaves is stopped by the kernel. A bpftime program runs on the host's thread, in its address space. Safety depends entirely on verification. That verification is optional (PREVAIL is off by default and in WARNING mode when on) unless you use the kernel-verifier modes. Isolation (MPK) is also off by default and x86-only.
  • Injection needs ptrace rights, and the rewrite modifies code pages of a live process. Hardened environments (restricted ptrace_scope, seccomp filters, W^X policies) can block it.
  • Inline hooks need room. Very short functions, or functions whose first instructions are branch targets, may not be hookable. A kernel uprobe can probe any instruction.
  • Syscall hooks have the zpoline caveats: page 0 must be mappable, x86-64 only, a linear-sweep disassembly of all executable mappings, and a slower per-call path than a kernel tracepoint.
  • Visibility is per process. bpftime sees only processes that run the agent. A system-wide tool such as "trace malloc in every process" needs the daemon, an agent injected everywhere, or kernel uprobes.
  • No kernel context. There is no task_struct, kernel stacks or kfuncs, and some helpers are missing.
  • Loader limits. Interposition relies on the dynamic linker. That last point is my inference, not tested: a loader statically linked against libc, or one that issues bpf() with an inline syscall instruction (some Go libraries do), would bypass LD_PRELOAD. The daemon mode exists for such cases.
  • Maturity. usage.md opens with "It's at an early stage and may contain bugs on more platforms and eBPF programs ... It's not suitable for production use now."

Related work

  • Userspace eBPF VMs. uBPF (C, interpreter and x86-64/arm64 JIT) and rbpf (Rust) run eBPF bytecode but provide no loader compatibility, maps or attach mechanism. bpftime uses uBPF as one backend. llvmbpf is the eunomia-bpf LLVM VM split out of bpftime. Microsoft's eBPF for Windows (see chapter 08) also combines PREVAIL with uBPF, but in a kernel.
  • Making kernel probes cheaper. The kernel's own answer is the uretprobe syscall (6.11) and the optimised uprobe on nop5 (6.18), covered in chapter 05. Jia et al., "Fast (Trapless) Kernel Probes Everywhere" (USENIX ATC '24) does the same for kprobes. The OSDI paper says its concealed entries are "inspired by" that work.
  • Binary rewriting. frida-gum provides the function interceptor. Capstone provides disassembly. zpoline (USENIX ATC '23) and pmem/syscall_intercept inspired the syscall hook (README). Pin, DynamoRIO and Valgrind are heavier full DBI frameworks.
  • Extension isolation. ERIM (USENIX Security '19) and libmpk introduced MPK-based in-process isolation. RLBox (USENIX Security '20) sandboxes libraries with SFI or Wasm. Native Client, WebAssembly and Lua runtimes are the alternatives the paper compares with. KFlex (SOSP '24) is the kernel-side model for separating verification of the interface from runtime isolation.
  • Verifiers. PREVAIL (Gershuni et al., PLDI '19) is the userspace verifier. Chapter 18 covers eunomia-bpf's work on validating eBPF transformations with Z3 and PREVAIL.
  • Other eunomia-bpf runtimes. wasm-bpf runs the control plane in WebAssembly while programs stay in the kernel; bpftime moves the programs to user space. GPU extensions built on bpftime's nv_attach_impl are in chapter 20.

Check your understanding

Q1. An unmodified libbpf loader runs under LD_PRELOAD=libbpftime-syscall-server.so. How do its bpf() calls reach bpftime?

Symbol interposition: the first definition of syscall in load order wins. The real one is found with dlsym(RTLD_NEXT, ...). The daemon mode is a different mechanism, and it needs no preload on the loader.

Q2. The loader and the target are different processes. How does the agent in the target learn which programs to attach?

init_attach_ctx_from_handlers() walks every allocated slot. The loader's "fds" are slot indices in that shared table. An epoch seqlock tells the agent when a new session replaced the handlers.

Q3. Why does bpftime's syscall hook map page 0 and fill it with nops?

This is zpoline. The replacement fits in the original two bytes, so no instruction relocation is needed. Page 0 is then made execute-only, so NULL loads and stores still fault.

Q4. According to Table 3 of the OSDI '25 paper, which operation is slower in bpftime than in kernel eBPF?

Uprobes win because the trap disappears. A syscall tracepoint in the kernel is already on the syscall path, while bpftime adds a user-space detour before the real syscall. The paper reports the syscall row as "about 1.5x slower".

Q5. In EIM, who decides which capabilities an extension at ngx_http_process_request may use in a given deployment?

The application developer enumerates what is possible (state and function capabilities, extension entries). The extension manager picks what is allowed per entry, per deployment. bpftime enforces this by verification.

Q6. With BPFTIME_RUN_WITH_KERNEL=true, what happens on BPF_PROG_LOAD?

See create_kernel_bpf_prog_in_userspace(). The kernel is used as verifier and map store, and the hot path stays in user space. Fd numbers are process-local, so map IDs are used instead.
