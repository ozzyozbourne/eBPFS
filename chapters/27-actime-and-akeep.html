Chapter 27

Actime and Akeep: one runtime for agent policy, observability and backup

Chapters 23 and 24 built two eBPF engines for AI agents: AgentSight watches what an agent does, and ActPlane decides what it may do. A team that wants both still has to install them, start them in the right order, give them privileges, collect their output, and keep the agent's own transcript somewhere safe. This chapter studies the two projects that do that work. Actime is a Rust orchestrator that runs an agent under ActPlane and AgentSight and writes one run record. Akeep is a Git-like, content-addressed backup tool for agent session history. Neither one contains an eBPF program. The chapter is about what it takes to turn kernel mechanisms into something a team can run every day.

Prerequisites: 23, 24Repos: eunomia-bpf/actime @ 9c035981, eunomia-bpf/akeep @ 7d690362, eunomia-bpf/backup-client-sdk @ 2774aa0b~50 min

Why this matters

Coding agents such as Claude Code, Codex, Gemini CLI and OpenCode run on laptops, CI runners and cloud sandboxes. Each one can start shells, rewrite files, open network connections and use a lot of CPU. When something goes wrong, the usual record of what happened is the agent's own transcript. Actime's README puts the problem this way: the transcript is "written by the thing you are trying to audit."

The earlier chapters in this part give three answers to three questions:

  • What did the agent actually do? AgentSight uses eBPF to record process, file, network and decrypted TLS activity from outside the agent.
  • What is the agent allowed to do? ActPlane compiles a small policy language into an eBPF/BPF-LSM engine that kills, blocks or reports effects at the syscall boundary.
  • What did the agent decide, and can I get it back? The transcript lives in files such as ~/.claude/projects/…/*.jsonl and ~/.codex/sessions. These formats are undocumented and change between versions, and Claude Code's documentation describes a default 30-day cleanup of local transcripts. Akeep is the eunomia-bpf answer to this question.

Each tool is useful alone. Together they are harder to use. ActPlane has to start before the agent so the policy covers the whole process tree. AgentSight has to attach to the right pid. Both need root or CAP_BPF. Both write output in their own formats. The transcript backup has to run after the agent exits. If any engine is missing or lacks privileges, someone has to decide whether the run should continue. Actime is the code that makes these decisions once, the same way every time, and writes the outcome down.

Key idea

Actime composes; it does not reimplement. Its design document lists as a non-goal: "Actime does not build its own eBPF programs. It orchestrates ActPlane and AgentSight, which own their kernel code." The interesting engineering is in the contract around the engines: when a plane counts as active, what happens when one is missing, and why a policy in enforce mode refuses to run rather than enforce a subset of its rules.

Correction to the repository description

At the time of writing, the GitHub description of eunomia-bpf/actime still reads "Unified runtime for AI coding agents: sandbox isolation, kernel-enforced policy, system evidence, and session history in one command". The code no longer does sandbox isolation. Commit 3f29370 ("Remove sandbox management; attach to user process trees", 2026-08-05) deleted the actime-sandbox crate, including a bubblewrap backend (bwrap.rs), a Docker backend and a sandbox image. Current Actime uses no namespaces, no Landlock and no seccomp of its own. Its design document says "Exactly three planes. There is no isolation plane." Isolation is left to whatever sandbox you already run.

Actime in one paragraph

The README describes Actime as "the effect plane for AI coding agents: kernel-enforced policy, system observability, and session backup, attached to the agent you already run, wherever it already runs." You type actime run -- claude. Actime launches Claude Code under actplane run so the policy covers every process the agent starts. It attaches agentsight record to that process tree. When the agent exits, it runs akeep commit on the session files. It then reads back what the engines wrote and prints a report. That report is not built from what the agent says it did. It is built from what the kernel saw. The project sums up its role relative to a sandbox in one line:

The sandbox contains. Actime accounts.

The README states the one invariant: "Actime observes and enforces below the tool layer, at the syscall/effect boundary." A tool-layer guardrail can block a tool call, but it misses bash -c, a Python subprocess, or a subagent doing the same thing. An exec-level rule enforced in the kernel catches all of them, because each one eventually calls execve. Chapter 24 explains how.

The three planes

Policy · ActPlane (eBPF)

"What is the agent allowed to do?" Rules such as kill exec "git" "--force" if AGENT. Modes off, observe, enforce.

Observability · AgentSight (eBPF)

"What did the agent actually do?" Processes, files written, endpoints, LLM calls and tokens, peak RSS and CPU, all read from AgentSight's SQLite store.

Backup · Akeep (userspace)

"What did the agent decide, and can we replay it?" A versioned commit of the provider-native session files at run exit.

How a run works

The design document (docs/DESIGN.md §7) calls itself "the implementation contract" and lists the steps of actime run. The stepper below follows those steps, with the code that does each one in crates/actime-cli/src/planes.rs and run.rs.

1. Resolve configuration

The first match wins: --config FILE, then ./actime.yaml searched upward to the git root, then ~/.config/actime/actime.yaml, then the built-in balanced profile. Every field is optional. "actime run -- claude with no config file at all must work." CLI flags such as --policy observe are applied last. Actime then looks for the three engine binaries on PATH, in ~/.local/share/actime/bin and in ~/.cargo/bin, and records their versions.

2. Create the run directory

RunStore::create makes ~/.local/share/actime/runs/<run-id>/ (override the root with ACTIME_HOME). It writes the effective actime.yaml there, so the record shows the exact configuration that was in force. A run id looks like 20261106-010537-c2d2.

3. Compose the policy

The selected packs (built into the binary with include_str!) and any extra policy files are joined into one text. ${WORKSPACE} is replaced with the real working directory. The result is saved as policy.dsl (human-readable) and wrapped in policy.yaml, the project file that ActPlane's --policy flag accepts.

4. Decide which rules can be enforced

Before starting anything, Actime runs actplane --rule <dsl> compile --json and checks each rule against the feature budget of the installed ActPlane version. In enforce mode, if any rule cannot be enforced, the run stops here: the agent is never started, and the run directory is finalized as a refusal. In observe mode the run continues, and the unenforceable rules are recorded in the manifest.

5. Launch the agent under the policy

With policy on, the agent's argv becomes [sudo -n -E] actplane --policy <run>/policy.yaml run -- claude …. Starting the agent this way means every descendant inherits the policy scope from its first instruction. Actime then reads the engine log. If the log shows an install failure, the policy plane is changed from Active to Disabled, and in enforce mode the run aborts.

6. Attach observability

Once the child pid exists, Actime starts agentsight record --no-server --db <run>/observability.db --pid N. For a container target it passes --binary-path docker://… or k8s://… instead. This plane is always fail-soft: if it cannot start, the run continues.

7. Wait, then stop the engines in order

Actime waits for the agent and applies limits.wall_clock or --timeout. It lets the engines exit on their own first so their events reach disk. If they do not, it sends SIGTERM, waits a few seconds, then sends SIGKILL. "Nothing may hang a run forever."

8. Harvest, back up, report

Only after ActPlane has exited does Actime copy its scoped actplane/runs/run-<pid>-<ts>/events.jsonl into violations.jsonl. It reads AgentSight's SQLite database defensively, runs akeep init and akeep commit -m "actime run <id>", updates manifest.json, renders report.md and prints the summary. The exit code is the agent's own, or 3 with --fail-on-violation when a rule blocked or killed something.

Starting engines with privileges

Both eBPF engines need root or CAP_BPF (usually with CAP_PERFMON as well; see LWN's "A crop of new capabilities" for how these were split out of CAP_SYS_ADMIN). Actime itself runs unprivileged and adds sudo only to the engine commands. The helper is short, and the non-interactive case is what makes it safe to use in CI:

/// Build a command, prefixing `sudo` when the eBPF planes need privileges we
/// do not have.
///
/// Interactive password prompts are allowed only when [`may_prompt_sudo`] is
/// true. Otherwise `sudo -n` is used so a non-interactive run fails fast
/// instead of hanging forever on a prompt nobody will answer.
pub fn privileged(program: &Path, args: &[String]) -> Command {
    if is_root() {
        let mut c = Command::new(program);
        c.args(args);
        return c;
    }
    let mut c = Command::new("sudo");
    if !may_prompt_sudo() {
        // Non-interactive: never block on a password prompt.
        c.arg("-n");
    }
    c.arg("-E").arg(program).args(args);
    c
}

The policy plane does not attach after the fact. It wraps the agent. This is the argv Actime builds:

    /// Build argv that launches `agent` under `actplane run` (host wrap path).
    ///
    /// Prefixes `sudo -n -E` when not root and a password prompt is not safe.
    /// Invokes `actplane --policy <file> run -- <cmd>` so the engine installs
    /// the composed policy for that run (not a post-hoc attach delta alone).
    pub fn wrap_argv(actplane: &Path, policy_yaml: &Path, agent: &[String]) -> Vec<String> {
        let mut v = Vec::new();
        if !is_root() {
            v.push("sudo".into());
            if !may_prompt_sudo() {
                v.push("-n".into());
            }
            v.push("-E".into());
        }
        v.push(actplane.display().to_string());
        v.push("--policy".into());
        v.push(policy_yaml.display().to_string());
        v.push("run".into());
        v.push("--".into());
        v.extend(agent.iter().cloned());
        v
    }

The comment matters. In chapter 24, actplane run seeds the agent's pid before exec. Every child then inherits the "agent" label, and the AGENT source in the policy matches the whole tree. An attach to a running process sees only future events and only processes that are tracked from then on.

The observability plane is attached once a pid exists. Here is how its argv is built:

        let mut args = vec![
            "record".to_string(),
            "--no-server".to_string(),
            "--db".to_string(),
            spec.db.display().to_string(),
        ];
        match (&spec.target, spec.host_pid) {
            (Some(target), _) => {
                args.push("--binary-path".to_string());
                args.push(target.clone());
            }
            (None, Some(pid)) => {
                args.push("--pid".to_string());
                args.push(pid.to_string());
            }
            (None, None) => {
                plane.outcome = Outcome::Disabled(
                    "no host pid or container target to attach observability to".into(),
                );
                return plane;
            }
        }
        /* ... open the engine log ... */
        let mut cmd = privileged(binary, &args);

The backup plane is plain process execution with a timeout. It does not use sudo, because Akeep only reads the user's own home directory:

        // Akeep needs an initialized repository. `init` on an existing vault is
        // a no-op; bound it so a stuck vault cannot hang the run either.
        match run_with_timeout(
            Command::new(binary)
                .arg("init")
                .stdin(Stdio::null())
                .stdout(Stdio::null())
                .stderr(Stdio::null()),
            AKEEP_TIMEOUT,
        ) {
            /* ... timeout => Degraded, error => Disabled ... */
            Timed::Finished(_) => {}
        }

        let mut commit_cmd = Command::new(binary);
        commit_cmd
            .args(["commit", "-m", message])
            .stdin(Stdio::null())
            .stdout(Stdio::piped())
            .stderr(Stdio::piped());

The commit id is parsed from Akeep's output and stored in the manifest as akeep_commit. Later, actime keep restore <run> looks up that id and runs akeep checkout <commit> --to <dir>. The run record and the session backup stay linked even though they live in different stores.

Policy packs and "enforceable on this host"

Actime ships three ActPlane policy packs in policies/. They use the language from chapter 24: source lines attach labels, and rule blocks combine an effect (kill, block, notify), an operation and a target with a label condition and a because message that is shown to the agent.

source AGENT = exec "**/claude"
source AGENT = exec "**/codex"
source AGENT = exec "**/gemini"
source AGENT = exec "**/opencode"
source AGENT = exec "**/openclaw"
source AGENT = exec "**/aider"
source AGENT = exec "**/cursor-agent"
source AGENT = exec "**/actime-demo-agent"

# 1. History rewriting and forced pushes destroy work that is not the agent's.
rule destructive-vcs:
  kill exec "git" "--force" if AGENT
  kill exec "git" "--hard" if AGENT
  kill exec "git" "clean" if AGENT
  because "Force-pushing, hard-resetting, and cleaning discard work that cannot be recovered from the agent's own history. Use a non-destructive git command, or ask the user to run this."

# 2. Whole-tree deletion is never a step in a coding task.
#    Path-scoped `unless target` matches the exec object (the rm binary), not
#    argv paths, so the unrestricted form is the enforceable shape today.
rule mass-deletion:
  kill exec "rm" "-rf" if AGENT
  because "Recursive deletion is not a step in a coding task. Delete specific paths under ${WORKSPACE}, or ask the user."
rule no-publish:
  kill exec "git" "push" if AGENT
  kill exec "git" "tag" if AGENT
  because "This run may change the working tree but may not publish. Leave the changes staged and report what you did; the user pushes."

rule no-branch-churn:
  kill exec "git" "branch" if AGENT
  kill exec "git" "worktree" if AGENT
  because "This run does not create branches or worktrees. Work on the current checkout, or ask the user to prepare the branch."

# Commits are gated, not forbidden: the user writes the approval file when they
# have reviewed the diff, and the gate goes stale again after each commit.
rule gated-commit:
  kill exec "git" "commit"
    if AGENT unless after write "${WORKSPACE}/.actime/commit-approved"
      since exec "git" "commit"
  because "Commits need explicit approval. Show the user the diff; once they approve, they (or you, on their instruction) write ${WORKSPACE}/.actime/commit-approved, and the next commit is allowed."
source SECRET = file "**/.env"
source SECRET = file "**/.env.*"
source SECRET = file "**/.ssh/id_*"
source SECRET = file "**/.aws/credentials"
/* ... more secret-shaped paths ... */
source SECRET = file "**/*.key"

# A redaction step clears the label, so a deliberate, reviewed release path
# stays possible: run the data through your scrubber and the flow is allowed.
declassify SECRET by exec "**/actime-redact"

/* ... rules system-fence, run-record-integrity, credential-access ... */

# 4. Data labeled from a secret file may not reach the network.
rule no-secret-egress:
  kill connect endpoint "*" if AGENT and SECRET
  because "This process holds data derived from a secret file and tried to open a network connection. ..."

Two details are worth noticing. First, every argv-matching rule uses kill, not block. Actime's CLAUDE.md explains why: "block exec with an argv token cannot deny before the fact — argv is only available after exec — so argv-sensitive rules use kill." ActPlane reads argv at the exec tracepoint, after the new image is loaded, and a tracepoint can kill but cannot fail the syscall (chapter 24 covers the hook placement). The new program may start, but it is killed before it gets far. Second, gated-commit uses the temporal operators after and since. An approval file permits one commit, and the permission expires when that commit happens. A per-call permission prompt cannot express this.

Rules are a host property

A policy that compiles is not always a policy the kernel will install. Released ActPlane 0.1.8, on the path Actime uses, loads a host-wide eBPF engine with a fixed feature budget. Actime copies the feature bits from ActPlane's source and hard-codes the budget it expects:

// Feature bits mirror ActPlane `bpf/src/lib.rs` (released 0.1.8).
const FEAT_PATH_CONTAINS: u32 = 1 << 0;
const FEAT_PATH_SUFFIX: u32 = 1 << 1;
const FEAT_OPEN_RULES: u32 = 1 << 2;
const FEAT_WRITE_RULES: u32 = 1 << 3;
const FEAT_CONNECT: u32 = 1 << 4;
const FEAT_RECV: u32 = 1 << 5;
const FEAT_FILE_FLOW: u32 = 1 << 6;
const FEAT_BLOCK_EXEC: u32 = 1 << 7;
const FEAT_BLOCK_FILE: u32 = 1 << 8;
const FEAT_BLOCK_CONNECT: u32 = 1 << 9;

/// Feature budget of the ActPlane 0.1.8 pinned singleton (`supported=0x3f0`).
///
/// Path contains/suffix matchers and open/write sink rule classes are omitted.
pub const ENGINE_SUPPORTED_0_1_8: u32 = FEAT_CONNECT
    | FEAT_RECV
    | FEAT_FILE_FLOW
    | FEAT_BLOCK_EXEC
    | FEAT_BLOCK_FILE
    | FEAT_BLOCK_CONNECT;

For each clause reported by actplane compile --json, Actime computes the feature bits the clause needs and compares them with this mask:

fn features_for_clause(op: &str, target_kind: &str, pattern: &str) -> u32 {
    let mut f = 0u32;
    let op = op.to_ascii_lowercase();
    let kind = target_kind.to_ascii_lowercase();
    match (op.as_str(), kind.as_str()) {
        ("open", "file") => {
            f |= FEAT_OPEN_RULES;
            f |= path_match_features(pattern);
        }
        ("write" | "unlink", "file") => {
            f |= FEAT_WRITE_RULES | FEAT_FILE_FLOW;
            f |= path_match_features(pattern);
        }
        ("connect", _) => {
            f |= FEAT_CONNECT;
        }
        ("recv", _) => {
            f |= FEAT_RECV;
        }
        ("exec", _) => {
            // Exec sinks load under the pinned hook budget.
        }
        /* ... */
    }
    f
}

The repository says this plainly. The secret-egress rule, the idea that makes ActPlane interesting, is "expressible … not enforceable with released ActPlane 0.1.8." The two exec-only packs install and fire. No default profile includes the information-flow pack.

Fail closed, but only in enforce

The design document names the worst outcome: "Silent partial enforcement is the worst outcome." In enforce mode, Actime aborts before the agent starts if any requested rule cannot be enforced, or if the policy plane cannot start at all. In every other case it fails soft: a missing engine, missing root or an old kernel disables a plane and records the reason, and the run continues. The asymmetry is on purpose. A user who asked for enforcement must not get an unprotected run that looks protected. A user who asked for observation should still get a record.

Degradation: what happens when something is missing

Actime is designed to be useful on a laptop with no root and no container runtime, and stricter when the environment allows it. Here is the degradation matrix from DESIGN.md §8:

MissingEffect
root / CAP_BPFpolicy and observability disabled; backup still runs; doctor explains
running inside a container without CAP_BPFsame; doctor warns that this is deployment B without host-side tamper resistance

Where Actime sits relative to a sandbox

Because Actime no longer creates sandboxes, it has to work with whatever sandbox already exists. docs/deployment.md describes three positions and is open about how their guarantees differ:

Position B is the only option on managed sandbox platforms (the docs name E2B, Daytona, AWS AgentCore and managed Kubernetes), because you cannot attach from a host you cannot log into. The setup grants the eBPF capabilities to the container:

docker run --rm -it \
  --cap-add BPF --cap-add PERFMON \
  -v "$PWD":/workspace -w /workspace \
  your-agent-image \
  actime run -- claude

The tamper story for B is honest: "An agent that gets root inside the sandbox can interfere: it can kill the Actime process, delete the run directory, or (with the same capabilities you granted for eBPF) detach the probes." The last point is the eBPF detail to remember. CAP_BPF is not scoped to a container. Granting it so a recorder can load programs also lets anything else with that capability in the same container load or detach programs. actime doctor detects the in-container case from /.dockerenv, /run/.containerenv and markers in /proc/1/cgroup, and reads CapEff from /proc/self/status.

In position A, actime attach --container REF resolves the container's host pid through docker inspect or podman inspect, and --pod NS/POD resolves it through kubectl and then the container runtime. Attach binds the planes only to future events, and it does not commit a backup. The report shows the backup plane as Disabled with "attach does not commit a backup".

Building and using Actime

Actime is a small Rust workspace with no eBPF build step: it needs no clang and no libbpf. The largest C component it compiles is SQLite, bundled by rusqlite. On this orb (8 CPUs, rustc 1.99.1) a clean release build with two jobs took 1 minute 12 seconds:

git clone --depth 1 https://github.com/eunomia-bpf/actime
cd actime
cargo build --release -j2 --locked
./target/release/actime --help

The README also gives a one-line installer (curl -fsSL …/scripts/install.sh | sh) and says the engines are installed with cargo install actplane agentsight akeep. Actime requires actplane ≥ 0.1.8, agentsight ≥ 0.2.60 and akeep ≥ 0.2.0. Linux only; the eBPF planes need kernel 5.10+ with BTF, and 6.1+ is recommended.

Akeep: version control for agent history

Akeep's README opens with "Your agent history is not a cache." A long Claude Code or Codex session holds hours of decisions, commands, diffs and plans. The agent stores them in provider-local files that are "undocumented, mutable, and not a backup". Akeep finds those files, saves them as compressed, deduplicated commits, and gives them back byte for byte. It makes five promises: versioned (commits with messages and parents, HEAD~N, log, diff), cloud backup (S3, R2, a Git remote or local disk), exact (raw provider files stay the source of truth), private (no upload or telemetry by default, optional client-side encryption) and non-destructive (commits never edit provider state, and checkout goes to a separate directory).

Akeep uses no eBPF at all. It is a single Rust binary (v0.2.0, about 8.8k lines in src/) built on blake3, zstd, age, rusqlite (with its backup feature) and rayon. It shells out to the AWS CLI and the Git CLI for remote storage.

The archive: content-addressed chunks

The archive format (docs/archive-format.md) is "an application-level content-addressed store". Filesystem, S3 and Git targets all use the same four kinds of logical keys:

vault.json
objects/<first two BLAKE3 hex characters>/<remaining hex>.zst[.age]
manifests/<snapshot-id>.json[.age]
refs/latest

The format makes four choices:

  • Fixed-size 4 MiB chunks, not content-defined chunking. The docs explain: "coding-agent state is dominated by append-only JSONL and SQLite snapshots, it supports bounded memory, and it keeps the recovery implementation small enough to audit." An append-only JSONL file keeps the same leading chunks, so only its last chunk changes. Inserting bytes in the middle of a file would shift every following chunk. Tools such as restic use content-defined chunking to avoid that, and Akeep reserves "a future format" for it.
  • Object id = BLAKE3 of the uncompressed chunk. Identical chunks deduplicate across files, providers and commits. BLAKE3 is fast and produces a 256-bit digest (64 hex characters).
  • Compress, then optionally encrypt, each chunk on its own: zstd (level 3 by default) and then age to the vault's X25519 recipient.
  • Publish the manifest last. A commit becomes visible only when its manifest exists, and that happens only after every referenced object has been checked. "An interrupted commit can leave unreferenced immutable objects but cannot create a false-complete version."

Here is the chunk store. It is the content-addressing step in one function:

    pub fn store_chunk(&self, raw: &[u8], compression_level: i32) -> Result<StoredChunk> {
        let id = blake3::hash(raw).to_hex().to_string();
        let key = self.object_key(&id)?;
        let compressed = zstd::stream::encode_all(Cursor::new(raw), compression_level)
            .context("failed to compress archive chunk")?;
        let encoded = self.codec.encrypt(&compressed)?;
        let stored_size = encoded.len() as u64;
        let shard = usize::from(u8::from_str_radix(&id[..2], 16).context("invalid chunk id")?)
            % self.chunk_locks.len();
        let _chunk_lock = self.chunk_locks[shard]
            .lock()
            .map_err(|_| anyhow::anyhow!("chunk coordination lock is poisoned"))?;

        if let Some(metadata) = self.storage.metadata(&key)? {
            if metadata.size != stored_size {
                bail!(
                    "existing object {id} has size {}, expected {stored_size}",
                    metadata.size
                );
            }
            return Ok(StoredChunk {
                id,
                stored_size: metadata.size,
                is_new: false,
            });
        }

        self.storage.put(&key, &encoded, false)?;

        Ok(StoredChunk {
            id,
            stored_size,
            is_new: true,
        })
    }

Three details stand out. The lock is sharded by the first byte of the hash, so parallel rayon workers storing the same chunk do not race. An existing object is never rewritten (put(..., false)). Its stored size is compared as a cheap consistency check. That comparison works even in age mode, where encrypting the same plaintext twice gives different ciphertext of the same length. The full check, which decodes and re-hashes each chunk, is akeep fsck.

The manifest is a strict serde struct (deny_unknown_fields). A reader refuses a manifest with fields it does not know instead of silently ignoring them:

Live SQLite databases

Codex, Grok, OpenCode and AgentSight keep state in SQLite databases that may be open while a backup runs. Copying such a file byte for byte, especially in WAL mode, can produce a torn database. Akeep uses SQLite's online backup API inside a read transaction, then runs PRAGMA integrity_check on the copy:

fn snapshot_sqlite(source: &Path, destination: &Path, busy_budget: Duration) -> Result<()> {
    let source_connection =
        Connection::open_with_flags(source, OpenFlags::SQLITE_OPEN_READ_ONLY)
            .with_context(|| format!("failed to open SQLite source {}", source.display()))?;
    source_connection
        .execute_batch("BEGIN DEFERRED")
        /* ... */;
    let _: i64 = source_connection
        .query_row("SELECT COUNT(*) FROM sqlite_schema", [], |row| row.get(0))
        /* ... pins the read snapshot ... */;
    /* ... open destination with journal_mode=OFF, synchronous=OFF ... */
    {
        let backup = Backup::new(&source_connection, &mut destination_connection)
            .with_context(|| format!("failed to start SQLite backup for {}", source.display()))?;
        let deadline = std::time::Instant::now() + busy_budget;
        loop {
            match backup.step(-1) /* ... */ {
                StepResult::Done => break,
                StepResult::More => continue,
                StepResult::Busy | StepResult::Locked => {
                    if std::time::Instant::now() >= deadline {
                        bail!(/* "SQLite backup remained busy ..." */);
                    }
                    std::thread::sleep(Duration::from_millis(50));
                }
                _ => bail!("SQLite backup returned an unsupported step state"),
            }
        }
    }
    /* ... ROLLBACK, then PRAGMA integrity_check must return exactly ["ok"] ... */

The archived snapshot is a separate file kind (sqlite-snapshot). WAL, SHM and journal sidecars are never archived. For AgentSight, an invalid or busy database is skipped with a warning instead of failing the commit.

Bounded memory

archive_file reads each file in chunk-size pieces and hashes a small batch in parallel. It never holds a whole file in memory. Files are grouped into batches whose total size is capped (S3_UPLOAD_BATCH_BYTES), and each batch's objects are flushed before the next batch starts. The README says this change took the project's own installation, "more than 50 GB across agent providers", from an observed peak of 23.6 GiB down to about 243 MiB. That is the project's claim; I did not reproduce it. On this orb, akeep status estimated "peak memory 256.0 MiB" for 4 workers.

Storage backends and encryption

Filesystem

akeep init [--target DIR]. The default is ~/.local/share/akeep/vaults/default. Writes go to a temporary file, are synced, then atomically renamed.

S3 / R2

--s3-bucket --s3-prefix --aws-profile [--s3-endpoint-url]. Akeep runs AWS CLI v2 without a shell, checks bucket versioning, re-reads uploaded sizes before publishing, and "never issues a remote delete".

Git remote

--git-repository URL --git-branch akeep. One Git commit per snapshot. A non-fast-forward push is refused, so a stale writer cannot publish. Your SSH agent or credential helper does the authentication.

age encryption

--encryption age generates a mode-0600 X25519 identity next to the config. Encryption is optional and is checked with a self-test on every open. "If every copy is lost, nobody can decrypt the repository."

The encryption layer is thin. It wraps the age crate, and on open it checks that the identity matches the recipient and that a round trip works:

const SELF_TEST_PLAINTEXT: &[u8] = b"akeep age self-test v1";

Recovery drills and handoff

Recovery goes to an empty scratch directory, never into the live home. Akeep refuses a symlink target, a non-empty directory, or any target that overlaps the vault. To check that a recovered session is usable, the docs suggest pointing CLAUDE_CONFIG_DIR at claude-code/ and opening the native resume picker, or pointing CODEX_HOME at codex/ and running codex resume --all, and then exiting without starting a turn.

akeep handoff is the one command that goes beyond backup. It builds a Markdown bundle for moving work between Claude Code and Codex, in either direction:

akeep handoff HEAD \
  --from claude-code \
  --for codex \
  --goal "Finish the restore drill and fix any mismatch" \
  --decision "Keep remote encryption optional" \
  --open-task "Run the provider fixture smoke test" \
  --test-status "cargo test passes" \
  --repo . \
  --artifact target/recovery-report.json \
  --to handoff.md

The bundle keeps what the user supplied (goal, decisions, tasks) separate from what was captured (Git state, artifact hashes, bounded tails of up to three recent transcript files). The captured parts are labeled "as evidence rather than presented as an AI-generated interpretation." It does not write the target agent's internal files and does not claim "lossless native import".

akeep schedule install --weekly installs one systemd user service and timer per vault. The timer runs at low CPU and I/O priority with a randomized six-hour delay, and uses the same per-vault lock as a manual commit.

backup-client-sdk: the hosted control-plane boundary

Akeep's own backends are things you run yourself: a disk, a bucket, a Git remote. eunomia-bpf/backup-client-sdk (crate akeep-backup-client-sdk, v0.1.0) is the client side of a hosted service. Its README calls it "the public Rust boundary between a Backup Client and the Akeep Control Plane." It "is pre-release and has not been published to crates.io." Its Cargo.toml lists github.com/agent-sight/backup-client-sdk as the repository. The Control Plane itself is private, and Akeep 0.2.0 does not depend on this SDK: nothing in Akeep's src/ or docs/ refers to it. Treat the SDK as the start of a managed-storage option, not as a feature of the current Akeep CLI.

The boundary is drawn carefully. "The SDK does not create archives, hold backup encryption keys, encrypt, decrypt, or restore files." It also does not read credentials from disk or the environment. The caller must supply a CredentialStore, normally backed by the OS keychain:

#[async_trait]
pub trait CredentialStore: Send + Sync {
    async fn load_device_credential(
        &self,
    ) -> Result<Option<StoredDeviceCredential>, CredentialStoreError>;
    async fn save_device_credential(
        &self,
        credential: &StoredDeviceCredential,
    ) -> Result<(), CredentialStoreError>;
    async fn delete_device_credential(&self) -> Result<(), CredentialStoreError>;
}

The public surface is a builder and three sub-APIs, as shown in the README:

use std::sync::Arc;
use akeep_backup_client_sdk::{AkeepClient, MemoryCredentialStore};

let client = AkeepClient::builder()
    .base_url("https://control-plane.example/")
    .credential_store(Arc::new(MemoryCredentialStore::default()))
    .build()?;

let _auth = client.auth();
let _account = client.account();
let _objects = client.objects();

From src/client.rs: auth() has start_device_pairing, wait_for_approval, credential_status and sign_out. Pairing works like a device-code flow: the user approves a short code at a verification URI, and the client polls with a secret header x-akeep-poll-secret. account() has identity and usage. objects() has upload_encrypted_file, list, get, download_encrypted_file and delete. Uploads hash the file first and ask POST /api/v1/uploads for an authorization. The server answers with either a single signed PUT (which must carry the exact Content-Length, Content-MD5 and If-None-Match: *) or a multipart plan with fixed 64 MiB parts, "and retains at most one part body in memory." The OpenAPI contract lists these paths: /api/v1/device-authorizations[/{code}[/exchange]], /me, /usage, /objects[/{id}[/download-url]] and /uploads[/{id}[/abort | /complete | /parts/{n}/url]].

The example examples/backup_client_e2e.rs shows who owns what. The example, not the SDK, builds a tar file, encrypts it with ChaCha20-Poly1305, uploads it, downloads it, decrypts it, unpacks it, checks the content and deletes the object:

I did not build or run the SDK. It needs a Control Plane URL and a device token (AKEEP_E2E_BASE_URL, AKEEP_E2E_DEVICE_TOKEN), and the service is not public.

  --strict

It uses no eBPF and is not wired into Actime. The README describes the name as "a release-surface and supply-chain name for Eunomia's agent runtime QoS, profiling, and enforcement work". Read it as a name kept for future work, not as a part of the stack described above. I only read its README.

Benefits and limitations

What the design gets right

  • Honest state. Every plane ends Active, Degraded or Disabled with a reason. A plane is reported as Active only after the engine log confirms the policy installed. A refusal is a complete record, not a crash. This is the kind of detail that decides whether a security tool can be trusted in an audit.
  • Enforcement below the tool layer. The exec rules hold no matter how the agent reached execve: a tool call, bash -c, a Python subprocess or a subagent. That holds in every deployment position.
  • Small, auditable backup. Akeep's format fits in one page: fixed chunks, BLAKE3 ids, manifest published last, never overwrite, never delete remotely. Raw provider bytes are the source of truth, so a provider format change cannot corrupt the backup. At worst it makes a restored session unreadable by a newer agent.
  • Privacy by default. Akeep uploads nothing unless you configure a remote, can encrypt both manifests and objects, and keeps the AgentSight summary free of paths and command lines.

What to keep in mind

  • The flagship policy is not enforceable yet. With released ActPlane 0.1.8, only exec rules install on Actime's path. File fences, credential-read reporting and secret-egress labels compile but are reported as not enforceable. The feature budget is hard-coded in enforceability.rs (engine_supported_features ignores its version argument), so Actime has to be updated when ActPlane changes.
  • Coarse rules. mass-deletion kills every rm -rf by an agent, including one inside the workspace, because path-scoped matching on argv is not available. The pack comments say this outright.
  • Agent identification by executable path. AGENT is exec "**/claude" and similar. An agent started under a different binary name is not labeled unless you add a source line. (actime run wraps the command under actplane run; whether ActPlane then seeds the wrapped pid regardless of name is an ActPlane detail I did not verify.)
  • Position B is weaker. Inside a container, root can interfere with the recorder. CAP_BPF granted for the recorder is also available to anything else in that container with the capability.
  • Privileges. The eBPF planes need sudo or capabilities. Without them, the planes degrade; in enforce mode the run refuses to start.
  • Akeep limits. Single-writer per vault ("operators must not schedule the same S3 vault from multiple machines concurrently"). Fixed chunking deduplicates append-only files well but not files edited in the middle. Provider formats are not stable, so each adapter version needs new fixtures and a new recovery test. Losing the age identity means losing the data.
  • Young code. Actime 0.1.0 and Akeep 0.2.0 are a few months old. The SDK is unpublished and its server side is private.

Related work

  • Sandboxes. bubblewrap (namespaces), Landlock (unprivileged filesystem and network access control) and seccomp (syscall filtering with classic BPF) contain a process. Actime's early design had a bubblewrap backend and dropped it. The project chose to account for whatever sandbox is in use instead of being one.
  • BPF LSM. ActPlane's enforcement rests on LSM BPF programs; see chapter 24 and chapter 05.
  • Agent observability. AgentSight (chapter 23) is the engine behind Actime's report. For resource control of the same agent process trees, see chapter 25. For checkpoint and rollback safety of agent changes, see chapter 26.
  • Content-addressed backup. Akeep's layout follows Git's object model (hash-named immutable objects, a mutable ref) and the deduplicating backup tradition of restic, which uses content-defined chunking and encrypts all repository data. Akeep is narrower: it backs up a handful of known agent directories, so it can treat SQLite specially and offer provider-aware restore drills.
  • Building blocks. BLAKE3 for hashing, Zstandard (RFC 8878) for compression, age v1 for encryption, and the SQLite online backup API. The SDK's pairing resembles the OAuth 2.0 Device Authorization Grant (RFC 8628) in shape. The SDK does not claim to implement that RFC. Its uploads use R2 presigned URLs.

Check your understanding

Q1. Which of these components loads eBPF programs into the kernel?

Actime's design lists "does not build its own eBPF programs" as a non-goal. It runs actplane run and agentsight record. Akeep and the SDK are ordinary userspace code.

Q2. With the default balanced profile (policy mode enforce), actplane is not installed. What does actime run -- claude do?

enforce fails closed. The run is finalized as a refusal: ended_at set, exit_code 1, and the note "refused before agent launch". This chapter reproduced exactly that output on the orb. In observe mode the same situation only disables the plane.

Q3. Why does actime policy check report no-secret-egress as not enforceable even though it compiles?

enforceability.rs compares each clause's required feature bits with ENGINE_SUPPORTED_0_1_8 = 0x3f0, which omits the path-matcher and open/write sink classes. Enforceability is a property of the host and engine, not of the pack.

Q4. An agent appends one line to a 9 MiB session JSONL file, and you commit again. Roughly what new data does Akeep store for that file?

Chunks are fixed 4 MiB pieces named by the BLAKE3 hash of their uncompressed bytes. An append changes only the tail chunk, so earlier chunks deduplicate. The new manifest still lists all three chunk ids. There is no add command.

Q5. In an age-encrypted Akeep vault, what can someone with read access to the bucket learn?

In age mode the whole manifest is encrypted. Object and snapshot ids stay visible in key names. vault.json holds only the public recipient. The identity file stays local, and akeep clone does not copy it.

Q6. Why is deployment position B (Actime inside the agent's container) described as having a weaker tamper story?

The recorder and the agent share a container boundary. In position A the recorder, the eBPF programs and the record are on the host, outside the container's view.
