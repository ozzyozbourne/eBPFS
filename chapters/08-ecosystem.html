Chapter 08

The eBPF ecosystem map, and where eunomia-bpf fits

Chapters 01–07 covered what the kernel provides. This chapter covers the software around it: which framework to write a program in, which large projects already use eBPF in production, which runtimes run eBPF outside the Linux kernel, and how the eunomia-bpf organization's projects fit into that picture.

Prerequisites: 05, 06Repo: github.com/eunomia-bpf~45 min

Why this matters

The kernel exposes eBPF through a single system call, bpf(2), plus a few attach interfaces (perf events, netlink, cgroup files, BPF links). Nobody writes raw bpf() calls by hand. Between your idea and the kernel sit a compiler (almost always Clang/LLVM, sometimes rustc), an object format (ELF with BTF), a loader library that relocates and loads the object, and a user-space program that reads the results from maps or ring buffers. Each framework puts these pieces together differently. Those differences decide whether your tool ships as one static binary or needs a 100 MB compiler on every host, whether it runs unchanged on a different kernel, and which language your team writes.

The second reason to study the ecosystem is to avoid duplicating work. Container networking, runtime security, continuous profiling and L4 load balancing each already have mature eBPF projects. Knowing what Cilium, Tetragon, Falco or Katran do, and roughly how, tells you when to build on them and when to write your own program.

The third reason is specific to this curriculum. Chapters 09–31 cover the eunomia-bpf organization, whose projects sit at almost every layer of this map: a compiler and loader (ecc/ecli), a Wasm runtime for eBPF, a userspace eBPF runtime (bpftime), verifier tooling, GPU extensions and agent observability. This chapter places each of them on the map before later chapters cover them in detail.

Key idea

Every eBPF framework answers the same four questions: where does compilation happen (on the build machine or on the target), who relocates the object for the running kernel (CO-RE via BTF, or recompiling against local headers), which library issues the bpf() syscalls (libbpf, a pure-Go or pure-Rust reimplementation, or libbcc), and which language the user-space half is written in. Once you know a framework's answers, you can predict most of its strengths and limitations.

The map at a glance

Figure 08.1 arranges the ecosystem in layers. At the bottom is the kernel machinery from earlier chapters: the verifier (03), JIT (02), maps and helpers (04), and hooks (05, 07). Above it are the loader libraries that speak bpf(2). Above those are front-ends that hide the loader entirely (bpftrace, BCC's Python API, eunomia-bpf's ecli). At the top are complete products. On the side are runtimes that run eBPF bytecode without the Linux kernel at all.

One program, seven frameworks

The clearest way to compare frameworks is to look at the same program written in each. We use an exec tracer: a program that fires every time a process calls execve() and either prints the new command line or counts the calls. It is the classic first eBPF program, and every framework below has an official example close to it. Wherever possible the code is copied from the framework's own repository, trimmed with /* ... */ or # .... libbpf-rs has no official execve example, so its tab shows its port of BCC's runqslower, which has the same structure: a tracepoint program, global configuration, and a ring buffer consumer.

How to read the tabs

In each tab, look at three things: (1) the attach point (kprobe on sys_execve, the syscalls:sys_enter_execve tracepoint, or sched:sched_process_exec; see 05 for why they differ); (2) how data reaches user space (map polling, perf buffer, ring buffer, or log macros); (3) how much code exists only to compile and load the program.

bpftrace is the awk of eBPF. A probe description, an optional filter and an action block are compiled with LLVM on the target machine when you press Enter. This is the full official tool, minus its header comment:

#ifndef BPFTRACE_HAVE_BTF
#include <linux/sched.h>
#endif

BEGIN
{
  printf("%-15s %-7s %-7s %s\n", "TIME", "PID", "PPID", "ARGS");
}

tracepoint:syscalls:sys_enter_exec*
{
  printf("%15s %-7d %-7d ", strftime("%H:%M:%S.%f", nsecs), pid, ppid);
  join(args.argv);
}

The official one-liner tutorial (docs/tutorial_one_liners.md, Lesson 4) counts all syscalls per process with bpftrace -e 'tracepoint:raw_syscalls:sys_enter { @[comm] = count(); }'. Swapping in the execve tracepoint gives an "execs per process" counter. This line is our own adaptation, not copied from the repo:

# illustrative: Lesson 4 of the bpftrace tutorial with the probe changed
sudo bpftrace -e 'tracepoint:syscalls:sys_enter_execve { @[comm] = count(); }'

There is no user-space code to write. @ is a BPF hash map that bpftrace prints when you press Ctrl-C, and args.argv is typed from the tracepoint's format description (or BTF).

BCC (BPF Compiler Collection) was the first widely used framework. The kernel half is a C string inside a Python program. At run time, libbcc compiles it with an embedded Clang/LLVM against the running kernel's headers, so the struct offsets in task->real_parent->tgid are correct for that kernel without any relocation. Below is BCC's execsnoop, trimmed:

from bcc import BPF

# ... more text substitution for UID_FILTER / PPID_FILTER ...

Two BCC idioms appear here. Options are applied by string substitution (UID_FILTER is replaced with an if statement before compiling), and the C is not quite standard C: task->real_parent->tgid is a plain kernel memory dereference that BCC rewrites into bpf_probe_read_kernel() calls.

The same tool, ported to libbpf and CO-RE in BCC's own libbpf-tools/ directory. The kernel half is ordinary C compiled ahead of time with clang -target bpf -g. BPF_CORE_READ records a relocation that libbpf fixes up at load time using the running kernel's BTF (06).

#include <vmlinux.h>
#include <bpf/bpf_helpers.h>
#include <bpf/bpf_core_read.h>
#include "execsnoop.h"

const volatile bool filter_cg = false;
const volatile bool ignore_failed = true;
const volatile uid_t targ_uid = INVALID_UID;
const volatile int max_args = DEFAULT_MAXARGS;
/* ... cgroup_map ... */
struct {
	__uint(type, BPF_MAP_TYPE_HASH);
	__uint(max_entries, 10240);
	__type(key, pid_t);
	__type(value, struct event);
} execs SEC(".maps");

struct {
	__uint(type, BPF_MAP_TYPE_PERF_EVENT_ARRAY);
	__uint(key_size, sizeof(u32));
	__uint(value_size, sizeof(u32));
} events SEC(".maps");

static __always_inline int enter_exec(const char *filename, const char **args)
{
	/* ... uid / cgroup filters ... */
	id = bpf_get_current_pid_tgid();
	pid = (pid_t)id;
	tgid = id >> 32;
	if (bpf_map_update_elem(&execs, &pid, &empty_event, BPF_NOEXIST))
		return 0;

	event = bpf_map_lookup_elem(&execs, &pid);
	if (!event)
		return 0;

	event->pid = tgid;
	event->uid = uid;
	task = (struct task_struct*)bpf_get_current_task();
	event->ppid = (pid_t)BPF_CORE_READ(task, real_parent, tgid);
	/* ... copy filename and up to max_args arguments ... */
	return 0;
}

SEC("tracepoint/syscalls/sys_enter_execve")
int tracepoint__syscalls__sys_enter_execve(struct syscall_trace_enter* ctx)
{
	return enter_exec((const char*)ctx->args[0], (const char **)(ctx->args[1]));
}
/* ... sys_enter_execveat, and sys_exit_* handlers that emit the event ... */

cilium/ebpf ("ebpf-go") is a pure-Go loader. The kernel half is still C compiled with Clang, but compilation happens at go generate time through bpf2go. bpf2go embeds the resulting .o into the Go binary and generates typed Go accessors (bpfObjects, objs.KprobeMap). The official kprobe example counts sys_execve calls in a one-element array:

//go:build ignore

#include "common.h"

char __license[] SEC("license") = "Dual MIT/GPL";

struct {
	__uint(type, BPF_MAP_TYPE_ARRAY);
	__type(key, u32);
	__type(value, u64);
	__uint(max_entries, 1);
} kprobe_map SEC(".maps");

SEC("kprobe/sys_execve")
int kprobe_execve() {
	u32 key     = 0;
	u64 initval = 1, *valp;

	valp = bpf_map_lookup_elem(&kprobe_map, &key);
	if (!valp) {
		bpf_map_update_elem(&kprobe_map, &key, &initval, BPF_ANY);
		return 0;
	}
	__sync_fetch_and_add(valp, 1);

	return 0;
}
//go:generate go tool bpf2go -tags linux bpf kprobe.c -- -I../headers

const mapKey uint32 = 0

func main() {

	// Name of the kernel function to trace.
	fn := "sys_execve"

	// Allow the current process to lock memory for eBPF resources.
	if err := rlimit.RemoveMemlock(); err != nil {
		log.Fatal(err)
	}

	// Load pre-compiled programs and maps into the kernel.
	objs := bpfObjects{}
	if err := loadBpfObjects(&objs, nil); err != nil {
		log.Fatalf("loading objects: %v", err)
	}
	defer objs.Close()

	kp, err := link.Kprobe(fn, objs.KprobeExecve, nil)
	if err != nil {
		log.Fatalf("opening kprobe: %s", err)
	}
	defer kp.Close()
	/* ... */
	for range ticker.C {
		var value uint64
		if err := objs.KprobeMap.Lookup(mapKey, &value); err != nil {
			log.Fatalf("reading map: %v", err)
		}
		log.Printf("%s called %d times\n", fn, value)
	}
}

link.Kprobe("sys_execve", …) resolves the architecture-specific symbol name (for example __x64_sys_execve), much as BCC's get_syscall_fnname does. Run it with go run -exec sudo ./kprobe from examples/, as the examples README says.

aya writes both halves in Rust. The kernel half is a #![no_std] crate compiled by rustc's BPF target and linked by bpf-linker. The user half uses the aya crate, which issues syscalls through libc alone, with no libbpf and no BCC. This is the tracepoint example from the Aya book:

#![no_main]

    pub buf: [u8; 4096],

#[tracepoint]
pub fn tracepoint_execve(ctx: TracePointContext) -> u32 {

        Ok(ret) => ret,
        Err(ret) => ret as u32,

}

fn try_tracepoint_execve(ctx: TracePointContext) -> Result<u32, i32> {
    // To get the offset, see
    // /sys/kernel/debug/tracing/events/syscalls/sys_enter_execve/format
    const FILENAME_OFFSET: usize = 16;
    let filename: *const u8 = unsafe { ctx.read_at(FILENAME_OFFSET)? };
    let Buf { buf } = unsafe {
        let ptr = FILENAME_BUF.get_ptr_mut(0).ok_or(0)?;
        &mut *ptr

        core::str::from_utf8_unchecked(bpf_probe_read_user_str_bytes(
            filename, buf,
        )?)
    };
    /* ... read ctx.command() into `command` ... */
    info!(
        &ctx,
        "Tracepoint sys_enter_execve called by: {}, filename: {}",
        command,
        filename
    );

    Ok(0)
}

Note the hard-coded FILENAME_OFFSET taken from the tracepoint's format file, and the per-CPU array used as a 4 KiB scratch buffer because the BPF stack is only 512 bytes. Both reflect how close to the bare ABI Rust eBPF code still is. The example's README asks for stable and nightly Rust toolchains plus cargo install bpf-linker, then cargo run --release.

libbpf-rs is the opposite trade-off to aya: the kernel half stays in C, and the user half is idiomatic Rust over the real libbpf (linked in through libbpf-sys). libbpf-cargo runs Clang from build.rs and generates a Rust skeleton with typed maps and rodata fields. The repository has no execve example; its runqslower example, a port of the BCC tool, shows the same structure:

Compare it line by line with the libbpf C tab: open → write rodata → load → attach → poll. It is the same lifecycle with Rust ownership around it. The kernel side (src/bpf/runqslower.bpf.c) uses tp_btf/sched_switch and bpf_core_field_exists(t->__state) to handle the kernel 5.14 rename of task_struct::state, which is CO-RE at work.

eunomia-bpf (chapter 10) asks: what if you wrote only the kernel half? You write a libbpf-style .bpf.c plus a header that declares the event struct. ecc compiles it and records the BTF of the maps, event struct and globals in a package.json. ecli then loads the program, generates command-line flags from the const volatile globals, and prints ring-buffer events as a table. This is the repo's bootstrap example, which tracks exec() and exit:

struct {
    __uint(type, BPF_MAP_TYPE_RINGBUF);
    __uint(max_entries, 256 * 1024);
} rb SEC(".maps");

const volatile unsigned long long min_duration_ns = 0;

SEC("tp/sched/sched_process_exec")
int handle_exec(struct trace_event_raw_sched_process_exec* ctx) {
    struct task_struct* task;
    unsigned fname_off;
    struct event* e;
    pid_t pid;
    u64 ts;

    /* remember time exec() was executed for this PID */
    pid = bpf_get_current_pid_tgid() >> 32;
    ts = bpf_ktime_get_ns();
    bpf_map_update_elem(&exec_start, &pid, &ts, BPF_ANY);

    /* don't emit exec events when minimum duration is specified */
    if (min_duration_ns)
        return 0;

    /* reserve sample from BPF ringbuf */
    e = bpf_ringbuf_reserve(&rb, sizeof(*e), 0);
    if (!e)
        return 0;

    /* fill out the sample with data */
    task = (struct task_struct*)bpf_get_current_task();

    e->exit_event = false;
    e->pid = pid;
    e->ppid = BPF_CORE_READ(task, real_parent, tgid);
    bpf_get_current_comm(&e->comm, sizeof(e->comm));

    fname_off = ctx->__data_loc_filename & 0xFFFF;
    bpf_probe_read_str(&e->filename, sizeof(e->filename),
                       (void*)ctx + fname_off);

    /* successfully submit it to user-space for post-processing */
    bpf_ringbuf_submit(e, 0);
    return 0;
}
/* ... handle_exit() on tp/sched/sched_process_exit ... */

What the tabs show

Read side by side, the tabs show a spectrum. bpftrace and ecli hide user space completely, but you can only do what their output model allows. BCC hides the build but carries a compiler to every host. libbpf, libbpf-rs and cilium/ebpf all follow the same open → configure → load → attach → consume lifecycle from chapter 06, in three host languages. aya applies the same lifecycle in Rust on both sides. The kernel halves differ less than the user halves: libbpf, cilium/ebpf, libbpf-rs and eunomia-bpf all accept the same libbpf-style C (SEC(), BTF-defined maps, BPF_CORE_READ), so kernel code moves between them with little change.

Choosing one

1. Is this a question or a product?

If you want an answer in the next five minutes ("which process keeps exec'ing sh?"), use bpftrace or a BCC/libbpf-tools tool you already have installed. Do not write a loader for a question you will only ask once.

2. Will it run on hosts you don't control?

If yes, avoid compiling on the target. A compiler and kernel headers on every host is BCC's main operational cost, and the reason BCC itself rewrote its tools as libbpf-tools. Choose a CO-RE framework: libbpf, libbpf-rs, cilium/ebpf, aya or eunomia-bpf.

3. What does the rest of your agent use?

Pick the user-space language your team already ships: C → libbpf (start from libbpf-bootstrap or libbpf-starter-template); Go → cilium/ebpf; Rust → libbpf-rs if you want libbpf's exact behavior and C kernel code, aya if you want Rust on both sides and no C toolchain.

4. Is the user space boilerplate?

If user space would only print events or histograms, eunomia-bpf (10) generates it. If plugins must run inside another application under a sandbox, look at wasm-bpf (12).

5. Does it have to run outside the Linux kernel?

On Windows, use eBPF for Windows, which cilium/ebpf also supports. For user-space hooks without kernel round trips (uprobes, syscalls of one process, GPU kernels), use bpftime (14). For an embeddable VM only, use uBPF, rbpf or llvmbpf (16).

The major projects

A few large projects show what eBPF is used for in production. Each is summarized from its own README or documentation. Use them as references for your own design, or adopt them instead of writing your own.

Networking: Cilium and Hubble

Cilium is a Kubernetes CNI (container network interface) built on eBPF from the start. It replaces iptables-based service routing and network policy with programs on tc/TCX and XDP hooks and socket hooks (07), with per-identity state in maps. It was created by Isovalent, entered the CNCF as an incubating project in October 2021, and graduated on 11 October 2023. Its user space is Go, and the cilium/ebpf library above came out of this project. Hubble is the observability layer on top of Cilium: per the README, a "fully distributed networking and security observability platform" that answers which services talk to each other, which HTTP calls or Kafka topics are involved, and why connections fail. Hubble reads the flow events Cilium's datapath already produces, so it adds visibility without adding another datapath.

Security: Tetragon, Falco, Tracee

Tetragon (also in the Cilium family) provides "eBPF-based Security Observability and Runtime Enforcement". By default it emits process_exec/process_exit events (a production-grade version of the exec tracer above), and its tracing policies can hook kprobes, tracepoints and LSM hooks. Its enforcement documentation describes two actions, overriding a function's return value and sending a signal such as SIGKILL, both taken in the kernel "inline with the operation itself" rather than after a user-space round trip. It understands Kubernetes identities (namespaces, pods), so policies target workloads instead of PIDs.

Falco, created by Sysdig in 2016 and a CNCF graduated project since 29 February 2024, is a rule-based threat detector. Its capture stack lives in falcosecurity/libs: drivers (a kernel module and a "modern eBPF probe") put syscall events into a ring buffer, libscap reads them, and libsinsp enriches them with process and container state and evaluates rules. Falco shows a common split: eBPF does capture only, and all policy runs in user space. Tracee from Aqua Security is a "runtime security and observability tool" with a similar shape. Its eBPF programs produce raw system events plus higher-level behavioral detections, consumed as an event stream.

Observability and profiling: Pixie, Parca

Pixie is Kubernetes observability with "auto-telemetry": eBPF collects full-body requests, resource and network metrics, and profiles without changes to the applications. The data stays inside the cluster and is queried with PxL, a Pythonic language. Parca Agent is an always-on sampling profiler. Its README says it samples user and kernel stacks 19 times per second with eBPF, emits pprof profiles, and needs a kernel ≥ 5.3 with BTF. Profilers like this are where eBPF's low overhead matters most, because they run all the time on every node. Chapter 22 (xpu-perf) extends the same idea to GPUs.

Load balancing: Katran

Katran is Meta's "C++ library and BPF program to build high-performance layer 4 load balancing forwarding plane" on XDP. Its README lists XDP driver mode, performance that scales linearly with NIC RX queues, and RSS-friendly encapsulation. When Meta co-founded the eBPF Foundation, the Linux Foundation's press release noted that Meta used eBPF as the primary software load balancer in its data centers. Katran is the open-source form of that design, and a good codebase to read after chapter 07.

The kernel's own tooling: bpftool and selftests

bpftool lives in the kernel tree (tools/bpf/bpftool) and is mirrored on GitHub. It lists and dumps loaded programs and maps (bpftool prog show, bpftool map dump), generates vmlinux.h (bpftool btf dump file /sys/kernel/btf/vmlinux format c) and skeletons (bpftool gen skeleton), and probes kernel features. Chapter 06 used it throughout. The kernel's BPF selftests in tools/testing/selftests/bpf are the most complete collection of eBPF examples anywhere. Almost every new feature lands with tests there (test_progs, the verifier tests in progs/verifier_*.c), and the veristat tool for comparing verifier statistics lives in the same directory. When documentation is missing, the selftests are the specification.

eBPF beyond the Linux kernel

eBPF is a bytecode with a formal ISA specification (RFC 9669; see 02), so nothing ties it to Linux. Three groups of projects use that.

eBPF for Windows and PREVAIL

eBPF for Windows lets "existing eBPF toolchains and APIs familiar in the Linux ecosystem" run on Windows by pulling existing projects in as submodules and adding a shim layer. Its README describes three ways to execute a program. In the preferred native mode, bpf2c runs the bytecode through the PREVAIL verifier and translates each instruction into C, which is then compiled into a signed Windows driver (.sys). This is also the mode compatible with Hypervisor-enforced Code Integrity. In JIT mode, a user-mode service (eBPFSvc) verifies the program and JIT-compiles it with uBPF. An interpreter (from uBPF) exists only in debug builds. Applications use a libbpf-compatible API exported by ebpfapi.dll, so libbpf-style code and cilium/ebpf work with few changes.

PREVAIL, the "Polynomial-Runtime EBPF Verifier using an Abstract Interpretation Layer", comes from the PLDI 2019 paper by Gershuni et al. It verifies programs with abstract interpretation over a Zone domain (relations between pairs of registers) instead of the Linux verifier's path-by-path exploration, which lets it handle loops and scale polynomially. Chapter 03 compares the two approaches, and the eunomia-bpf transformation checker in chapter 18 builds on PREVAIL.

Userspace VMs and runtimes: uBPF, rbpf, bpftime

uBPF is an Apache-licensed user-space eBPF VM, created because the kernel's implementation is GPL and cannot be embedded in many projects. It ships an assembler, disassembler, interpreter and JIT (x86-64 and Arm64), and recently added a "safe" interpreter-only profile that tracks pointer provenance at run time. rbpf is a Rust VM based on uBPF, with an interpreter, an x86-64 JIT and a disassembler. Both are VMs only: you feed them bytecode and memory and get a return value. They have no verifier like the kernel's, no maps, and no hooks.

bpftime from eunomia-bpf goes further. In its own words, it is "not userspace eBPF VM, it's a userspace runtime framework", including loader, verifier, helpers, maps, ufuncs and event sources. It attaches programs to uprobes, USDT and syscalls by binary rewriting inside the target process, so uprobes no longer trap into the kernel. It keeps maps in shared memory, can share maps with kernel eBPF, and accepts unmodified clang/libbpf/bpftrace output. Its design is described in the OSDI '25 paper Extending Applications Safely and Efficiently. Its VM backend, llvmbpf, is an LLVM JIT/AOT compiler for eBPF that can also emit PTX and SPIR-V for GPUs. Chapters 14–16 cover both.

The eBPF Foundation

The eBPF Foundation was announced by the Linux Foundation on 12 August 2021 with founding members Meta (then Facebook), Google, Isovalent, Microsoft and Netflix. It provides vendor-neutral governance for eBPF across platforms (Linux, Windows), funds work through grants, and publishes material for the community. It does not own the Linux implementation, which is developed on the kernel's bpf mailing list. The ISA standardization that became RFC 9669 was done in the IETF BPF working group. The documentation hub ebpf.io lists projects across the whole ecosystem.

Where eunomia-bpf fits

eunomia-bpf is an open-source organization (its website is eunomia.dev) whose projects cover most of the layers in Figure 08.1. Some are developer tooling meant for daily use, and some are research prototypes behind recent systems papers. Six families cover the actively maintained repositories this curriculum follows, plus the learning material (bpf-developer-tutorial) and org meta repos (31). Click a box to jump to its chapter.

Tooling: eunomia-bpf, wasm-bpf, templates

The eunomia-bpf repository is "a compiler and runtime framework to help you build and distribute eBPF program easier". Its top level contains compiler/ (ecc), ecli/, bpf-loader-rs/ (the dynamic loader that turns the JSON package into libbpf calls), eunomia-sdks/ and examples/bpftools/ (bootstrap, opensnoop, runqlat, sigsnoop, tcpstates, xdp and more). Per the README, it can expose kernel data through ring buffer or perf events automatically, sample hash maps into histograms, generate CLI arguments from globals, and push and pull programs as OCI images. The README also notes that the old remote-HTTP mode (ecli client/ecli-server) was removed from the main branch and kept on archive/ecli-remote-http. wasm-bpf moves the user half into WebAssembly: a "Wasm library, toolchain and runtime" built on CO-RE libbpf, where guest SDKs in C, Rust and Go (chapter 12) compile user space to a .wasm module that the host runtime (cargo install wasm-bpf, or the WasmEdge plugin) loads together with its eBPF object. The templates (eunomia-template, libbpf-starter-template, libbpf-rs-starter-template) are GitHub template repos with a Makefile, Dockerfile and CI action already set up for each framework from the comparison table.

Runtimes: bpftime, llvmbpf

Covered above. bpftime is the user-space runtime with hooks and maps; llvmbpf is the VM/compiler alone, which "does not include maps implement, helpers, verifiers, or loaders". The GPU projects below use these two as their execution engine.

Verification and performance: bpfix, ebpf-correctness-verifier, bpf-benchmark

bpfix attacks the most common complaint about eBPF, verifier error messages. It parses the verifier log you already have (for example from bpftool -d prog load) and prints a Rust-compiler-style diagnostic with source spans, an error class, and a suggested repair. Its repo description adds that the output is meant to let an LLM fix the program. ebpf-correctness-verifier (ebpf-tv) answers a different question: given an original and a transformed object, are they equivalent? It returns PASS/FAIL/UNKNOWN using an SMT (Z3) model; the repo description says it is "based on Z3 and prevail". The README is explicit that it "does not prove program safety"; the verifier still does that. bpf-benchmark ("bpf-bench") treats eBPF optimization as a closed-loop search for LLM agents. It is also the artifact repository for the ACM ATC '26 paper BPF-Ext: Safely Extending the eBPF Compilation Pipeline with Native Operations.

GPU: gpu_ext, nccl-eBPF, xpu-perf

gpu_ext brings the sched_ext idea to GPU drivers. Modified NVIDIA open kernel modules expose eBPF struct_ops hooks so that UVM memory eviction and prefetch policies (FIFO, LFU, stride, …) and per-process timeslices are programmable (arXiv 2512.12615). nccl-eBPF ("NCCLbpf") runs bpftime inside NCCL's tuner, profiler and net plugins, so eBPF policies choose the collective algorithm, protocol and channel count. Its README calls it a research prototype targeting the eBPF Workshop at SOSP 2026. xpu-perf combines eBPF CPU sampling and uprobes with NVIDIA CUPTI into CPU→GPU flame graphs; its README marks it as work in progress.

AI agents: agentsight, ActPlane, agentcgroup

These projects use eBPF to watch and control AI coding agents. agentsight is a "top/strace-like observability tool for AI agents": it captures the agent's TLS traffic to the LLM (intent) and kernel events (effects) with eBPF, without an SDK or proxy, and correlates them (arXiv 2508.02736; PACMI '25). ActPlane enforces information-flow policies such as "no codex may run git push" in the kernel, following process lineage so a shell script cannot bypass them. It blocks through BPF-LSM where the kernel supports it, and otherwise notifies or kills (arXiv 2606.25189). agentcgroup characterizes the OS resource use of coding agents and controls it per tool call with sched_ext (CPU) and memcg_bpf_ops (memory) (arXiv 2602.09345). The ActPlane README notes that its eBPF program ships prebuilt as CO-RE, so users install only a Rust binary. That is the "compile once" column of the comparison table in practice.

Research prototypes: namei_ext, qwen3-ebpf

namei_ext prototypes a sched_ext-style BPF extension point in VFS path resolution. VFS, dcache and permission semantics stay in the kernel, and BPF policies decide lookups and directory enumeration; it ships a modified kernel as a submodule. qwen3-ebpf tests the limits of the platform: it runs the full Qwen3-0.6B forward pass (all 28 decoder layers, with a KV cache in a BPF map) as bounded eBPF programs. A separate XDP path keeps BF16 weights in a BPF arena and schedules inference from a BPF workqueue when a packet arrives. Its README is explicit that it is "a research prototype, not a production inference engine".

Maturity varies

Treat the families differently. eunomia-bpf/ecli, the templates, bpftime and llvmbpf are general tools with releases. The GPU, agent and kernel-research repositories are mostly paper artifacts: they may need a patched kernel or driver (gpu_ext, namei_ext, bpf-benchmark's BPF-Ext), a recent kernel (agentcgroup needs sched_ext, 6.12+), or specific hardware. Check each README's requirements before planning to deploy one.

Benefits and limitations of a fragmented ecosystem

Benefits. Because the kernel interface is stable (a syscall, ELF and BTF), a program's kernel half can move between frameworks, and new loaders can appear without kernel changes. That is why pure-Go and pure-Rust loaders exist, why eBPF for Windows can reuse libbpf's API, and why bpftime can run unmodified libbpf output in user space. Competition between loaders has also improved the reference implementation; for example, both cilium/ebpf and aya reimplemented CO-RE independently.

Limitations. Feature support differs. A new map type, program type or kfunc usually appears first in libbpf and the selftests, and reaches other loaders later. Error messages differ too: the same verifier rejection looks different in Go, Rust and C, which is part of what bpfix addresses. BCC-style tools and CO-RE tools also differ in portability. Code written for BCC (bare task->field dereferences, string substitution) cannot be pasted into libbpf, which is why BCC maintains two versions of its tools. Finally, userspace and non-Linux runtimes implement subsets: a helper or map type available in Linux may not exist in eBPF for Windows, uBPF or bpftime, so check each project's support list.

Related work and further reading

For the kernel side of everything here, the authoritative sources are the kernel's BPF documentation and the selftests. For a framework-neutral reference to program types and helpers, see docs.ebpf.io. Brendan Gregg's BCC and bpftrace tools (execsnoop, opensnoop, biolatency…) are the usual starting set for observability. Comparing the BCC and libbpf-tools versions of one tool, as we did above, is a quick way to learn CO-RE. Chapter 09 continues with eunomia-bpf's tutorial, which writes many of these tools in libbpf, Go and Rust. Chapter 32 collects the papers.

Check your understanding

Q1. Why does BCC's execsnoop.py work on a kernel without BTF, while the libbpf-tools version needs BTF (or an external BTF file)?

Compiling on the target replaces relocation. The cost is a compiler and kernel headers on every host. CO-RE moves compilation to the build machine and needs BTF on the target (or BTFHub/bpf-compatible for old kernels).

Q2. In the cilium/ebpf example, when does Clang run?

The //go:generate go tool bpf2go … line runs at development time. The shipped Go binary contains the bytecode and needs no compiler on the host.

Q3. Which pair of frameworks uses libbpf underneath?

libbpf-rs wraps libbpf via libbpf-sys, and eunomia-bpf's loader drives libbpf. aya (pure Rust, libc only) and cilium/ebpf (pure Go) are independent reimplementations.

Q4. In eBPF for Windows' preferred native mode, what happens to a verified program?

Native mode runs PREVAIL, then bpf2c, then the normal driver toolchain, which is compatible with HVCI. uBPF provides the JIT mode, and the interpreter exists only in debug builds.

Q5. How does bpftime differ from uBPF?

bpftime's README says it is "not userspace eBPF VM" but a runtime framework. It can use uBPF or llvmbpf as its VM backend.

Q6. You must ship an exec-monitoring agent in Go to thousands of hosts with mixed kernels that have BTF. What is the most natural choice?

There is no compiler on the hosts, a single Go binary, and CO-RE handles kernel differences. This is the pattern Cilium and Tetragon use.
