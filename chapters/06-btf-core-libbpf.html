Chapter 06

BTF, CO-RE and libbpf

A tracing program that reads task->real_parent->tgid needs to know where real_parent sits inside struct task_struct. That offset is different on almost every kernel. How can you compile the program once, ship one binary, and have it read the right bytes on all of them?

Prerequisites: 04, 05Repo: libbpf/libbpf-bootstrap @ 820a1bd~45 min

Why this matters: the portability problem

Earlier chapters showed that an eBPF program is bytecode the kernel checks and runs (02, 03). Bytecode does not contain field names. When C code says task->real_parent, the compiler turns it into "add a constant to a pointer and load 8 bytes". The constant is the byte offset of real_parent inside struct task_struct, and the compiler takes it from whatever header it was given.

Networking programs mostly read stable, user-facing structures: packet bytes, struct __sk_buff, struct xdp_md. The kernel keeps those fixed. Tracing and security programs are different: they read internal kernel structures such as task_struct, file, sock or mm_struct. These have no stability promise. Between versions, and between two builds of the same version with different Kconfig options, fields get added, removed, reordered, renamed, moved into nested structs, or compiled out.

Here is a concrete case measured in this curriculum's orb. The same libbpf-bootstrap program was compiled against the vmlinux.h that libbpf-bootstrap ships for x86 (generated from a Linux 6.18 kernel), and run on the orb's 6.1 kernel. The offsets the compiler baked in, and the offsets the running kernel actually uses, were:

Field of struct task_structOffset in the 6.18 header (compile time)Offset in the orb's 6.1.189 kernel
exit_code9241280
tgid10281388
real_parent10321400

The numbers differ because of both the kernel version and the kernel configuration; task_struct is 7,616 bytes on the orb kernel and contains many #ifdef CONFIG_… members. If the program used the compiled offsets as they are, it would read 368 bytes too early and report garbage as the parent PID, with no error at all. The verifier cannot catch this: reading kernel memory through bpf_probe_read_kernel() at a wrong offset is still a safe read, it is just the wrong one.

This chapter explains the three-part answer to this problem. BTF describes types. CO-RE relocations record, at compile time, which fields the program meant. libbpf rewrites the instructions at load time to match the running kernel. The chapter also covers the parts of libbpf that every libbpf-based tool in this curriculum relies on: the object lifecycle, the BPF skeleton generated by bpftool, global variables, the bpf() syscalls that do the real work, and BPF links and pinning.

The old answer: compile on the target (BCC)

Before CO-RE, the usual answer was BCC, the BPF Compiler Collection (covered with the rest of the ecosystem in 08). A BCC tool carries the C source of its BPF program as a string. When the tool starts on the target machine, BCC runs an embedded Clang/LLVM, compiles the string against that machine's kernel headers, and loads the result. The offsets are right because the compilation happened against the exact kernel that will run the code.

This works, and BCC is still a good tool for quick prototypes. Andrii Nakryiko's "BPF Portability and CO-RE" lists the costs that pushed production users away from it:

  • Clang/LLVM is a large library, so every tool ships a large binary.
  • Compiling at start-up uses a lot of CPU and memory. On a busy host it can disturb the workload, and it can be slow.
  • The target needs kernel headers installed (kernel-devel or similar). Custom-built kernels often have none.
  • Even trivial compile errors appear only at run time, on the target, after you have deployed.

CO-RE, "Compile Once – Run Everywhere", moves compilation back to the developer's machine and replaces "compile against the right headers" with "patch a few constants against the right type information".

Key idea

CO-RE splits the job into three parts. The kernel publishes an exact description of its own types (BTF, at /sys/kernel/btf/vmlinux). The compiler records, next to each instruction that touches a kernel structure, which field of which type it meant, by name. The loader (libbpf) matches those names against the kernel's BTF and rewrites the instruction's offset before the program is sent to the verifier. The kernel then sees a normal program that looks as if it had been compiled on that host.

BTF: the BPF Type Format

What it encodes

BTF is a compact binary format that describes C types, plus function and line information for BPF programs. The kernel documentation (docs.kernel.org/bpf/btf.html) defines it. It was designed as a smaller alternative to DWARF. With the deduplication algorithm Nakryiko describes in "BTF deduplication and Linux kernel BTF", the kernel's type information shrinks by up to about 100× compared to DWARF, small enough to keep inside every kernel image.

A BTF blob has a header, a type section and a string section:

struct btf_header {
    __u16   magic;
    __u8    version;
    __u8    flags;
    __u32   hdr_len;

    /* All offsets are in bytes relative to the end of this header */
    __u32   type_off;       /* offset of type section       */
    __u32   type_len;       /* length of type section       */
    __u32   str_off;        /* offset of string section     */
    __u32   str_len;        /* length of string section     */
};

The magic is 0xeB9F. On the orb, the first two bytes of /sys/kernel/btf/vmlinux are 9f eb: the little-endian form of that magic. The type section is a sequence of records. Each record starts with a 12-byte struct btf_type: a name (an offset into the string section), an info word that packs the kind (bits 24–30), a count vlen (bits 0–23) and a flag bit, then either a size or a reference to another type. Kind-specific data follows. A STRUCT is followed by vlen members, each with a name, a type ID and a bit offset. Types are numbered in order starting at 1; ID 0 is void.

The kinds are INT, PTR, ARRAY, STRUCT, UNION, ENUM, FWD, TYPEDEF, VOLATILE, CONST, RESTRICT, FUNC, FUNC_PROTO, VAR, DATASEC, FLOAT, DECL_TAG, TYPE_TAG and ENUM64 (kinds 1–19). Most map directly to C. Three are BPF-specific. FUNC describes a function (a subprogram), not a type. VAR describes a global variable. DATASEC describes an ELF data section, such as .bss or .rodata, and lists the variables inside it. These last two are what make the global variables and skeletons later in this chapter possible.

You can read BTF as text with bpftool btf dump. This is real output from the orb, trimmed to the lines this chapter uses:

Where BTF comes from

There are two producers, and they serve the two sides of CO-RE:

  • Kernel BTF. When a kernel is built with CONFIG_DEBUG_INFO_BTF=y, the build runs pahole (from the dwarves project), which converts the kernel's DWARF debug info into BTF, deduplicates it and embeds it in the .BTF section of vmlinux. Since Linux 5.4 the kernel exposes it at /sys/kernel/btf/vmlinux; loaded modules appear next to it as /sys/kernel/btf/<module>, stored as split BTF that refers to the base vmlinux types. Most current distribution kernels enable this option.
  • Program BTF. When Clang compiles for -target bpf with -g, it writes two ELF sections into the object file: .BTF with the types the program uses, and .BTF.ext with function info, line info and the CO-RE relocation records. Pahole does not produce CO-RE relocations; only the compiler knows which instruction accessed which field.

The kernel also uses BTF for its own purposes, independent of CO-RE: the verifier uses it to type-check fentry/tp_btf programs and kfunc calls (04, 05), map BTF lets bpftool map dump print values as typed structures, and line info lets bpftool prog dump show source lines.

vmlinux.h: one header with every kernel type

BTF can be turned back into C. bpftool btf dump ... format c writes a header that defines every type in the kernel, including internal ones that no installed header exposes. By convention it is called vmlinux.h:

$ bpftool btf dump file /sys/kernel/btf/vmlinux format c > vmlinux.h
$ wc -l vmlinux.h
117822 vmlinux.h
$ head -6 vmlinux.h
#ifndef __VMLINUX_H__
#define __VMLINUX_H__

#ifndef BPF_NO_PRESERVE_ACCESS_INDEX
#pragma clang attribute push (__attribute__((preserve_access_index)), apply_to = record)
#endif

libbpf-bootstrap wraps the same command in tools/gen_vmlinux_h.sh:

#/bin/sh

$(dirname "$0")/bpftool btf dump file ${1:-/sys/kernel/btf/vmlinux} format c

Two details matter. First, the #pragma at the top applies preserve_access_index to every struct and union in the file. That attribute is what makes Clang emit CO-RE relocations for every field access through these types, described next. Second, the header does not have to match the target kernel. It is the program's "local" view of the types. libbpf-bootstrap ships a pre-generated header per architecture (a git submodule pointing at libbpf/vmlinux.h), so you can build on a machine whose kernel has no BTF at all. BTF has no record of #define macros, so constants such as TASK_COMM_LEN or flag bits are missing from vmlinux.h. Programs define them locally, as bootstrap.h does below, or take them from libbpf's bpf_helpers.h and bpf_tracing.h.

CO-RE relocations: recording intent at compile time

The compiler built-ins

Clang's BPF backend has built-ins that compile an expression normally and, in addition, record a relocation in .BTF.ext:

  • __builtin_preserve_access_index(expr): compute the address of a field access such as &task->real_parent, and record a field byte offset relocation for it. The preserve_access_index attribute on a struct has the same effect on every access through that type.
  • __builtin_preserve_field_info(field, kind): return a property of a field (offset, size, whether it exists, signedness, bit-shift amounts for bitfields), as a constant that libbpf will patch.
  • __builtin_preserve_type_info(type, kind): whether a type exists, its size, or whether it matches.
  • __builtin_preserve_enum_value(value, kind): whether an enumerator exists and its integer value.
  • __builtin_btf_type_id(x, kind): the BTF type ID of something, in the program or in the kernel.

Each record is a struct bpf_core_relo. The kernel UAPI header that libbpf carries documents it:

enum bpf_core_relo_kind {
	BPF_CORE_FIELD_BYTE_OFFSET = 0,      /* field byte offset */
	BPF_CORE_FIELD_BYTE_SIZE = 1,        /* field size in bytes */
	BPF_CORE_FIELD_EXISTS = 2,           /* field existence in target kernel */
	BPF_CORE_FIELD_SIGNED = 3,           /* field signedness (0 - unsigned, 1 - signed) */
	BPF_CORE_FIELD_LSHIFT_U64 = 4,       /* bitfield-specific left bitshift */
	BPF_CORE_FIELD_RSHIFT_U64 = 5,       /* bitfield-specific right bitshift */
	BPF_CORE_TYPE_ID_LOCAL = 6,          /* type ID in local BPF object */
	BPF_CORE_TYPE_ID_TARGET = 7,         /* type ID in target kernel */
	BPF_CORE_TYPE_EXISTS = 8,            /* type existence in target kernel */
	BPF_CORE_TYPE_SIZE = 9,              /* type size in bytes */
	BPF_CORE_ENUMVAL_EXISTS = 10,        /* enum value existence in target kernel */
	BPF_CORE_ENUMVAL_VALUE = 11,         /* enum value integer value */
	BPF_CORE_TYPE_MATCHES = 12,          /* type match in target kernel */
};

/*
 * "struct bpf_core_relo" is used to pass relocation data form LLVM to libbpf
 * and from libbpf to the kernel.
 *
 * CO-RE relocation captures the following data:
 * - insn_off - instruction offset (in bytes) within a BPF program that needs
 *   its insn->imm field to be relocated with actual field info;
 * - type_id - BTF type ID of the "root" (containing) entity of a relocatable
 *   type or field;
 * - access_str_off - offset into corresponding .BTF string section. String
 *   interpretation depends on specific relocation kind:
 *     - for field-based relocations, string encodes an accessed field using
 *       a sequence of field and array indices, separated by colon (:). It's
 *       conceptually very close to LLVM's getelementptr ([0]) instruction's
 *       arguments for identifying offset to a field.
 /* ... */

A record says, in effect: "instruction #30 contains the offset of member #66 of type [34] struct task_struct (as this program saw it); please make it right." The access string 0:66 means "element 0 of the pointer, then member index 66". Member indices are what the compiler wrote down; libbpf resolves them back to member names through the program's own BTF, and then searches the kernel's BTF by name. Field order in the target therefore does not matter.

The libbpf macros you actually write

You rarely call the built-ins directly. libbpf's bpf_core_read.h wraps them. The base macro is just a probe-read whose source address goes through __builtin_preserve_access_index:

#define bpf_core_read(dst, sz, src)					    \
	bpf_probe_read_kernel(dst, sz, (const void *)__builtin_preserve_access_index(src))
/* ... */
#define bpf_core_field_exists(field...)					    \
	__builtin_preserve_field_info(___bpf_field_ref(field), BPF_FIELD_EXISTS)
/* ... */
#define bpf_core_type_exists(type)					    \
	__builtin_preserve_type_info(*___bpf_typeof(type), BPF_TYPE_EXISTS)
/* ... */
#ifdef __clang__
#define bpf_core_enum_value(enum_type, enum_value)			    \
	__builtin_preserve_enum_value(*(typeof(enum_type) *)enum_value, BPF_ENUMVAL_VALUE)
/* ... */
/*
 *	int x = s->a.b.c->d.e->f->g;
 * can be succinctly achieved using BPF_CORE_READ as:
 *	int x = BPF_CORE_READ(s, a.b.c, d.e, f, g);
 *
 * BPF_CORE_READ will decompose above statement into 4 bpf_core_read (BPF
 * CO-RE relocatable bpf_probe_read_kernel() wrapper) calls, logically
 * equivalent to:
 * 1. const void *__t = s->a.b.c;
 * 2. __t = __t->d.e;
 * 3. __t = __t->f;
 * 4. return __t->g;
 /* ... */
 * N.B. Only up to 9 "field accessors" are supported, which should be more
 * than enough for any practical purpose.
 */
#define BPF_CORE_READ(src, a, ...) ({					    \
	___type((src), a, ##__VA_ARGS__) __r;				    \
	BPF_CORE_READ_INTO(&__r, (src), a, ##__VA_ARGS__);		    \
	__r;								    \
})

The macros fall into three groups, following Nakryiko's BPF CO-RE reference guide:

Reading data

bpf_core_read(), bpf_core_read_str(), BPF_CORE_READ(t, mm, exe_file, path.dentry, d_name.name) (each comma is one pointer dereference), BPF_CORE_READ_INTO(), BPF_CORE_READ_STR_INTO(), the _USER variants for user memory, and BPF_CORE_READ_BITFIELD[_PROBED](), which reads any integer or bitfield and keeps working if its width changes.

Asking questions

bpf_core_field_exists(), bpf_core_type_exists(), bpf_core_enum_value_exists(), bpf_core_type_matches(), and the size and offset queries bpf_core_field_size(), bpf_core_type_size(), bpf_core_field_offset(). Each becomes a constant (0/1 or a number) that libbpf patches in.

Getting values

bpf_core_enum_value(enum cgroup_subsys_id, cpu_cgrp_id) returns the enumerator's value in the running kernel. This makes internal enums whose values depend on version or config safe to use: they are "CO-RE-relocatable enums".

Two limits are worth remembering. BPF_CORE_READ relocates the field's offset, not the size of what you copy, so the guide recommends reading primitive fields rather than whole structs. And BPF_CORE_READ returns 0 if any pointer on the chain is NULL or unreadable; use the lower-level bpf_core_read() when you need the error code.

In BTF-aware program types (fentry/fexit, tp_btf, LSM), the verifier tracks kernel pointer types and allows direct dereference: t->real_parent->tgid compiles to plain loads. Because vmlinux.h marks every struct with preserve_access_index, those loads also get CO-RE relocations, with no macro needed.

Handling changes the layout alone cannot hide

Offsets are the easy case. Harder cases are fields that were renamed, removed or changed type. CO-RE handles these with three tools that work together.

Existence checks plus dead-code elimination. bpf_core_field_exists(t->__state) compiles to a constant that libbpf sets to 1 or 0. The verifier sees if (0) and does not check the branch that cannot run. If that dead branch contains a relocation that could not be resolved, libbpf replaces the instruction with a deliberately invalid call (it "poisons" it) instead of failing the load.

Type and field "flavors". libbpf ignores everything from the last triple underscore onward when it matches names. struct task_struct___old is matched against the kernel's struct task_struct. You can then describe an old layout in the same source file as the new one. This comment in libbpf's relo_core.c states the rule:

/*
 * Calculate CO-RE relocation target result.
 *
 * The outline and important points of the algorithm:
 * 1. For given local type, find corresponding candidate target types.
 *    Candidate type is a type with the same "essential" name, ignoring
 *    everything after last triple underscore (___). E.g., `sample`,
 *    `sample___flavor_one`, `sample___flavor_another_one`, are all candidates
 *    for each other. Names with triple underscore are referred to as
 *    "flavors" and are useful, among other things, to allow to
 *    specify/support incompatible variations of the same kernel struct, which
 *    might differ between different kernel versions and/or build
 *    configurations.
 /* ... */

Kconfig externs. A program can declare extern int LINUX_KERNEL_VERSION __kconfig; or extern int CONFIG_HZ __kconfig;, and libbpf fills in the running kernel's value at load time. Like the existence checks, these become constants the verifier can use to remove dead branches.

The following program combines existence checks and flavors. It is illustrative code written for this chapter, adapted from the __state example in the CO-RE reference guide. Kernel commit 2f064a59a1 ("sched: Change task_struct::state", Linux 5.14) renamed the field from state to __state and changed its type. BCC's libbpf-tools/core_fixes.bpf.h uses the same pattern in production. The program was compiled and loaded on the orb:

/* Illustrative (not from a repo): state.bpf.c, built against the orb's vmlinux.h */
#include "vmlinux.h"
#include <bpf/bpf_helpers.h>
#include <bpf/bpf_core_read.h>

char LICENSE[] SEC("license") = "GPL";

struct task_struct___old {          /* flavor: matched against struct task_struct */
	long state;                     /* pre-rename name and type */
} __attribute__((preserve_access_index));

long last_state = -1;

SEC("tp/sched/sched_process_exec")
int read_state(void *ctx)
{
	struct task_struct *t = (void *)bpf_get_current_task();

	if (bpf_core_field_exists(t->__state)) {
		last_state = BPF_CORE_READ(t, __state);
	} else {
		struct task_struct___old *t_old = (void *)t;
		last_state = BPF_CORE_READ(t_old, state);
	}
	return 0;
}

The poison value is chosen to be easy to spot. If a poisoned instruction is reachable, for example because you forgot the existence check, the verifier rejects the program with invalid func unknown#195896080:

		insn[i].src_reg = 0;

Step through what happens to the single instruction that loads real_parent's offset in libbpf-bootstrap's bootstrap program when it was built against the 6.18 header and loaded on the orb's 6.1 kernel. Every number below comes from the real run.

1. Compile: Clang writes a guess and a note

BPF_CORE_READ(task, real_parent, tgid) compiles to instruction #30, r1 = 1032, followed by r0 += r1 and a bpf_probe_read_kernel() call. 1032 is the offset in the 6.18 header. Clang also writes a record into .BTF.ext: insn #30, local type [34] struct task_struct, access string 0:66, kind byte_off.

2. Open: libbpf parses the ELF

bootstrap_bpf__open() parses the embedded ELF: program sections, .maps, .rodata, .BTF and .BTF.ext. Nothing has touched the kernel yet, and the instruction still says 1032.

3. Load: find the kernel's BTF

bootstrap_bpf__load() reaches bpf_object__load_vmlinux_btf(). The log line is loaded kernel BTF from '/sys/kernel/btf/vmlinux'. If btf_custom_path was set in the open options, that file replaces vmlinux BTF for relocation purposes.

4. Find candidates by essential name

For local type task_struct, libbpf looks up every kernel type with the same kind and essential name and caches the result: found target candidate [187] struct task_struct in [vmlinux]. Module BTF is searched as well when the type is not in vmlinux.

5. Match the access path

libbpf turns 0:66 into names using the local BTF (member 66 is real_parent), then walks the candidate by name. It finds real_parent as member 82, at bit offset 11200, and checks the types are compatible (both pointers). Log: matching candidate #0 <byte_off> [187] struct task_struct.real_parent (0:82 @ offset 1400). If several candidates match with different results, libbpf reports an ambiguity error instead of guessing.

6. Patch the instruction

bpf_core_patch_insn() checks that insn #30 really holds the expected original value, then rewrites its immediate: patched insn #30 (ALU/ALU64) imm 1032 -> 1400. For a load such as r1 = *(u32 *)(r6 + 8) it patches the off field instead. If no candidate matched, it poisons the instruction (step shown in the previous section).

7. Hand a normal program to the kernel

After all relocations, libbpf calls BPF_PROG_LOAD. The verifier sees r1 = 1400, exactly what a compile against the orb's own headers would have produced. The kernel never learns that a relocation happened. The program then printed correct parent PIDs.

LWN's "Possible paths for signing BPF programs" explains why it matters: a program that is rewritten at load time is not byte-identical to the file you signed.

Kernels without BTF: BTFHub and minimized BTF

CO-RE needs the target kernel's types. Kernels built without CONFIG_DEBUG_INFO_BTF, which includes many older enterprise and embedded kernels, have no /sys/kernel/btf/vmlinux. libbpf then warns kernel BTF is missing ... was CONFIG_DEBUG_INFO_BTF enabled? and any program with CO-RE relocations fails to load. The relocation mechanism still works on those kernels; only the type data is missing. So the fix is to supply the BTF from elsewhere:

  • BTFHub, by Aqua Security, converts the debug-info packages of published distribution kernels into BTF files. It stores them in a separate repository, btfhub-archive, laid out by distribution, version, architecture and kernel release.
  • A full kernel BTF file is several megabytes (4.8 MB on the orb), and supporting hundreds of kernels that way is too much to ship. BTFgen, built by Aqua with Kinvolk and Elastic and later merged into bpftool as bpftool gen min_core_btf INPUT OUTPUT OBJECT..., reads your compiled object, works out which types and fields its relocations actually use, and writes a small BTF file with only those. The bpftool man page says the result can be "distributed together with an eBPF CO-RE based application".
  • At run time the application chooses the file that matches uname -r and passes it through bpf_object_open_opts.btf_custom_path. The libbpf header describes the limit: the custom BTF "completely replaces the use of vmlinux BTF for the purpose of CO-RE relocations", but features that need the real kernel BTF, such as fentry/fexit and struct_ops, still need it.

eunomia-bpf's bpf-compatible packages this workflow. Its btfgen script fetches btfhub-archive, generates minimized BTF for your object and packs the files into a .tar.gz. That archive is linked into the executable with ld -r -b binary, and a small runtime library picks the right entry and sets the custom BTF path. It also ships an adapted copy of libbpf-bootstrap. Chapter 13 covers it in depth.

Watch out

CO-RE fixes layouts, not features. A program that uses a helper, kfunc, map type or attach point the target kernel does not have will still fail in the verifier or at attach time. Feature checks such as bpf_core_type_exists(struct bpf_ringbuf) or bpf_core_enum_value_exists(enum bpf_func_id, BPF_FUNC_ringbuf_output), combined with dead-code elimination, let one object pick a fallback. You can also turn off whole programs from user space with bpf_program__set_autoload(prog, false) before loading.

The build pipeline

libbpf-bootstrap (github.com/libbpf/libbpf-bootstrap, commit 820a1bd, October 2026) is the reference layout for a C libbpf application. It is maintained by the libbpf authors, and most templates in this curriculum, including eunomia-bpf's starter templates (11), derive from it. The build has two compilers and one code generator:

Directory map

libbpf-bootstrap/
├── libbpf/        git submodule → libbpf/libbpf      (built as .output/libbpf.a)
├── bpftool/       git submodule → libbpf/bpftool     (built with the "bootstrap" target)
├── vmlinux.h/     git submodule → libbpf/vmlinux.h   (include/<arch>/vmlinux.h, pre-generated)
├── blazesym/      git submodule → libbpf/blazesym    (symbolizer, only for the "profile" example)
├── tools/         gen_vmlinux_h.sh, cmake helpers
└── examples/
    ├── c/         Makefile, CMakeLists.txt, xmake.lua and one pair per app:
    │              minimal.{bpf.c,c}  bootstrap.{bpf.c,c,h}  kprobe  fentry  uprobe
    │              usdt  ksyscall  tc  sockfilter  task_iter  lsm  profile  *_legacy
    └── rust/      the same idea with libbpf-rs (see chapter 08)

The pattern is one app per file pair: NAME.bpf.c is the kernel side and NAME.c the user side. A shared NAME.h holds structures that cross the boundary, such as ring-buffer events. The *_legacy examples avoid newer features so they run on older kernels.

The Makefile, step by step

The C examples' Makefile is short. These are the parts that implement Figure 06.2:

OUTPUT := .output
CLANG ?= clang
LIBBPF_SRC := $(abspath ../../libbpf/src)
BPFTOOL_SRC := $(abspath ../../bpftool/src)
LIBBPF_OBJ := $(abspath $(OUTPUT)/libbpf.a)
BPFTOOL_OUTPUT ?= $(abspath $(OUTPUT)/bpftool)
BPFTOOL ?= $(BPFTOOL_OUTPUT)/bootstrap/bpftool
# ...
VMLINUX := ../../vmlinux.h/include/$(ARCH)/vmlinux.h
# Use our own libbpf API headers and Linux UAPI headers distributed with
# libbpf to avoid dependency on system-wide headers, which could be missing or
# outdated
INCLUDES := -I$(OUTPUT) -I../../libbpf/include/uapi -I$(dir $(VMLINUX)) -I$(LIBBLAZESYM_INC)
CFLAGS := -g -Wall
# ...
CLANG_BPF_SYS_INCLUDES ?= $(shell $(CLANG) -v -E - </dev/null 2>&1 \
	| sed -n '/<...> search starts here:/,/End of search list./{ s| \(/.*\)|-idirafter \1|p }')
# ...
# Build libbpf
$(LIBBPF_OBJ): $(wildcard $(LIBBPF_SRC)/*.[ch] $(LIBBPF_SRC)/Makefile) | $(OUTPUT)/libbpf
	$(call msg,LIB,$@)
	$(Q)$(MAKE) -C $(LIBBPF_SRC) BUILD_STATIC_ONLY=1		      \
		    OBJDIR=$(dir $@)/libbpf DESTDIR=$(dir $@)		      \
		    INCLUDEDIR= LIBDIR= UAPIDIR=			      \
		    install

# Build bpftool
$(BPFTOOL): | $(BPFTOOL_OUTPUT)
	$(call msg,BPFTOOL,$@)
	$(Q)$(MAKE) ARCH= CROSS_COMPILE= OUTPUT=$(BPFTOOL_OUTPUT)/ -C $(BPFTOOL_SRC) bootstrap
# ...
# Build BPF code
$(OUTPUT)/%.bpf.o: %.bpf.c $(LIBBPF_OBJ) $(VMLINUX) | $(OUTPUT) $(BPFTOOL)
	$(call msg,BPF,$@)
	$(Q)$(CLANG) -g -O2 -target bpf -D__TARGET_ARCH_$(ARCH)		      \
		     $(INCLUDES) $(CLANG_BPF_SYS_INCLUDES)		      \
		     -MT $@ -MMD -MP -MF $(patsubst %.bpf.o,%.bpf.d,$@)		      \
		     -c $(filter %.c,$^) -o $(patsubst %.bpf.o,%.tmp.bpf.o,$@)
	$(Q)$(BPFTOOL) gen object $@ $(patsubst %.bpf.o,%.tmp.bpf.o,$@)

# Generate BPF skeletons
$(OUTPUT)/%.skel.h: $(OUTPUT)/%.bpf.o | $(OUTPUT) $(BPFTOOL)
	$(call msg,GEN-SKEL,$@)
	$(Q)$(BPFTOOL) gen skeleton $< > $@

# Build user-space code
$(patsubst %,$(OUTPUT)/%.o,$(APPS)): %.o: %.skel.h

$(OUTPUT)/%.o: %.c | $(OUTPUT)
	$(call msg,CC,$@)
	$(Q)$(CC) $(CFLAGS) $(INCLUDES) -MMD -MP -c $(filter %.c,$^) -o $@
# ...
# Build application binary
$(APPS): %: $(OUTPUT)/%.o $(LIBBPF_OBJ) | $(OUTPUT)
	$(call msg,BINARY,$@)
	$(Q)$(CC) $(CFLAGS) $^ $(ALL_LDFLAGS) -lelf -lz -o $@

Things to notice:

  • -g is required on the BPF compile. Without debug info Clang emits no .BTF or .BTF.ext, which means no CO-RE records and no skeleton. -O2 is required in practice too; unoptimized BPF code usually fails verification.
  • -D__TARGET_ARCH_$(ARCH) tells bpf_tracing.h which register layout to use for PT_REGS_PARM1() and similar macros in kprobes.
  • CLANG_BPF_SYS_INCLUDES adds the host compiler's include directories with -idirafter. Without it, examples that include <linux/bpf.h> fail on Debian-style systems. This was reproduced on the orb: compiling minimal.bpf.c without it stops with 'asm/types.h' file not found.
  • bpftool gen object is BPF's static linker. Here it links a single file. It exists so that several .bpf.o files, including BPF "libraries", can be combined into one object before skeleton generation.
  • The final binary links libbpf statically and needs only libelf and zlib at run time.

A complete minimal project

The smallest libbpf-bootstrap application has two files. The kernel side:

// SPDX-License-Identifier: GPL-2.0 OR BSD-3-Clause
/* Copyright (c) 2020 Facebook */
#include <linux/bpf.h>
#include <bpf/bpf_helpers.h>

char LICENSE[] SEC("license") = "Dual BSD/GPL";

int my_pid = 0;

SEC("tp/syscalls/sys_enter_write")
int handle_tp(void *ctx)
{
	int pid = bpf_get_current_pid_tgid() >> 32;

	if (pid != my_pid)
		return 0;

	bpf_printk("BPF triggered from PID %d.\n", pid);

	return 0;
}

SEC("tp/syscalls/sys_enter_write") puts the function in an ELF section whose name tells libbpf both the program type (tracepoint) and where to attach it. That is what lets __attach() work with no arguments. my_pid is a plain global variable; the compiler places it in .bss. This program reads no kernel structures, so it does not even need vmlinux.h.

The user side:

// SPDX-License-Identifier: (LGPL-2.1 OR BSD-2-Clause)
/* Copyright (c) 2020 Facebook */
#include <stdio.h>
#include <unistd.h>
#include <sys/resource.h>
#include <bpf/libbpf.h>
#include "minimal.skel.h"

{
	return vfprintf(stderr, format, args);
}

int main(int argc, char **argv)
{
	struct minimal_bpf *skel;
	int err;

	/* Set up libbpf errors and debug info callback */
	libbpf_set_print(libbpf_print_fn);

	/* Open BPF application */
	skel = minimal_bpf__open();
	if (!skel) {
		fprintf(stderr, "Failed to open BPF skeleton\n");
		return 1;
	}

	/* ensure BPF program only handles write() syscalls from our process */
	skel->bss->my_pid = getpid();

	/* Load & verify BPF programs */
	err = minimal_bpf__load(skel);
	if (err) {
		fprintf(stderr, "Failed to load and verify BPF skeleton\n");
		goto cleanup;
	}

	/* Attach tracepoint handler */
	err = minimal_bpf__attach(skel);
	if (err) {
		fprintf(stderr, "Failed to attach BPF skeleton\n");
		goto cleanup;
	}

	printf("Successfully started! Please run `sudo cat /sys/kernel/debug/tracing/trace_pipe` "
	       "to see output of the BPF programs.\n");

	for (;;) {
		/* trigger our BPF program */
		fprintf(stderr, ".");
		sleep(1);
	}

cleanup:
	minimal_bpf__destroy(skel);
	return -err;
}

The user program never names a file path, a section or a map. Everything goes through the generated struct minimal_bpf. skel->bss->my_pid = getpid() writes to the BPF program's global variable before load. Whatever value is there when __load() runs becomes the variable's initial value in the kernel.

The libbpf object lifecycle

The libbpf documentation (libbpf Overview) describes four phases. Every libbpf program, with or without a skeleton, goes through them:

  1. Open. libbpf parses the ELF and finds programs, maps and global variables. Nothing has been created in the kernel yet. This is the time to make changes: set global variable values, resize maps (bpf_map__set_max_entries), change a program's type or turn off autoload, set pin paths.
  2. Load. libbpf probes kernel features, loads kernel BTF, resolves externs, applies CO-RE and map relocations, loads the program's BTF, creates maps, and loads and verifies programs. After this step, programs are in the kernel but not running. You can fill maps without racing against running BPF code.
  3. Attach. libbpf attaches programs to their hooks and returns struct bpf_link objects. Programs start running.
  4. Tear down. Links are destroyed (programs detach), and the program, map and BTF file descriptors are closed, which frees the kernel objects unless something else holds a reference.

libbpf v1.9 also has bpf_object__prepare(), which does everything in the load phase except loading the programs. You can inspect or change the final instructions before the verifier sees them.

The skeleton wraps each phase in one generated function. This sequence is from minimal.c above:

	skel = minimal_bpf__open();
	/* ... */
	skel->bss->my_pid = getpid();
	/* ... */
	err = minimal_bpf__load(skel);
	/* ... */
	err = minimal_bpf__attach(skel);
	/* ... */
cleanup:
	minimal_bpf__destroy(skel);

Illustrative code written for this chapter (not from a repository): the same phases without a skeleton, loading the object file from disk and looking things up by name. Every function is a public libbpf API declared in libbpf.h.

	return 1;

	goto out;

	err = -errno;
	goto out;

/* ... run ... */
out:

bpf_object__close(obj);                                    /* free   */

BPF skeletons and global variables

A skeleton is a header that bpftool gen skeleton generates from a compiled object. The libbpf documentation lists what it gives you:

  • The object is embedded. NAME__elf_bytes() returns the whole .bpf.o as a byte array compiled into your binary, so there is no separate file to install or find at run time.
  • Typed access instead of string lookups. skel->progs.handle_tp, skel->maps.rb and skel->links.handle_tp are struct fields. If you rename a map in the BPF code and forget the user side, the build fails, instead of a lookup returning NULL at run time.
  • Global variables as C structs. For each data section, the skeleton declares a struct whose layout comes from the DATASEC BTF of the object. After load, libbpf memory-maps the section's backing map, so skel->bss->counter++ in user space and counter++ in BPF touch the same memory. The _Static_assert lines check that the user-side compiler lays the struct out the way BTF says.
  • Lifecycle functions. __open, __open_opts, __load, __open_and_load, __attach, __detach and __destroy. These are thin wrappers. The skeleton always exposes skel->obj, so anything the generic API can do is still available.

How do global variables work, when BPF programs have no .data segment of their own? libbpf turns each of .data, .rodata, .bss (and custom .data.*/.rodata.* sections) into a single-element BPF_MAP_TYPE_ARRAY whose value is the whole section. Instructions that reference a variable are relocated to "address of map value plus offset", which the verifier understands. The BTF dump of bootstrap.bpf.o shows the sections libbpf works from:

$ bpftool btf dump file bootstrap.bpf.o | grep -A2 DATASEC
[328] DATASEC 'license' size=13 vlen=1
	type_id=278 offset=0 size=13 (VAR 'LICENSE')
[329] DATASEC '.rodata' size=8 vlen=1
	type_id=281 offset=0 size=8 (VAR 'min_duration_ns')
[330] DATASEC '.maps' size=48 vlen=2
	type_id=15 offset=0 size=32 (VAR 'exec_start')
	type_id=21 offset=32 size=16 (VAR 'rb')

The three sections behave differently:

.bss / .data

Mutable from both sides. Used for counters, PIDs to filter on, and small amounts of state. Set the value before load to choose the initial value; read or write it after load through the mmap.

.rodata

const volatile variables. You can write them only before load (skel->rodata->min_duration_ns = …). libbpf then freezes the map, so the verifier knows the exact value and can remove branches that cannot run. The volatile stops Clang from folding the default value at compile time.

.maps

Not data. This section holds the BTF-defined map declarations (__uint(type, …), __type(key, …)) that libbpf reads to create real maps.

The .rodata behaviour is the user-space counterpart of CO-RE's dead-code elimination. Nakryiko's CO-RE post explains why it beats a configuration map: a value in a map is unknown to the verifier, so it must check every branch, including branches that use features the running kernel lacks. A frozen read-only value lets the verifier remove those branches. Read-write global variables accessible from user space need Linux 5.5 or later; for older kernels libbpf-bootstrap keeps minimal_legacy.bpf.c, which #defines BPF_NO_GLOBAL_DATA and uses a one-element array map "instead of a global variable which does not work with older kernels".

bpftool can generate two variants. A light skeleton (bpftool gen skeleton -L) contains a small BPF "loader program" that does the map creation and relocation in the kernel. The bpftool man page says it "does not use the majority of the libbpf infrastructure, and does not need libelf", which suits programs loaded from inside the kernel or from minimal environments, and it is the basis of --sign for signed skeletons. A subskeleton (bpftool gen subskeleton) gives a BPF library's own code typed access to its part of an object that the application opened.

Underneath: the bpf() syscall

libbpf is a user-space library. Everything it does in the kernel goes through one multiplexed system call, bpf(int cmd, union bpf_attr *attr, unsigned int size), plus a few helpers such as perf_event_open. Tracing bootstrap with strace -e trace=bpf,perf_event_open,ioctl on the orb shows each phase. This is real output, with the long attribute structs shortened:

The BPF_MAP_UPDATE_ELEM plus BPF_MAP_FREEZE pair is the .rodata freezing described above: the value written is whatever skel->rodata held when __load() ran. (The fd numbers do not line up because libbpf reserves a placeholder fd for each map at open time and moves the real fd onto it with dup3(), which this strace filter does not show.)

The commands that matter most:

  • BPF_BTF_LOAD uploads the program's BTF, after libbpf has removed parts the kernel would not understand ("sanitizing"). Maps and programs then refer to its fd so the kernel knows their key, value and function types.
  • BPF_MAP_CREATE creates each map. It returns a file descriptor. libbpf then rewrites every ld_imm64 instruction that referenced the map to carry that fd.
  • BPF_PROG_LOAD passes the fully relocated instructions, the program type, license, BTF fd, func and line info, and an optional log buffer. The verifier runs inside this call; if it fails, libbpf prints the verifier log.
  • BPF_LINK_CREATE (Linux 5.7 and later) attaches a program and returns a link fd. For a tracepoint, libbpf first opens a perf event for it and then links the program to that event. On kernels without perf-event links libbpf falls back to the older PERF_EVENT_IOC_SET_BPF ioctl.

Every EINVAL or EBADF in the trace is deliberate. libbpf tests what the running kernel supports by trying small operations, then adjusts: it drops BTF kinds the kernel does not know, picks an attach method that exists, and so on. This feature probing complements CO-RE. CO-RE adapts the program to the kernel's types; probing adapts the loader's behaviour to the kernel's features.

BPF links and pinning

Each kernel BPF object (program, map, BTF, link) is reference-counted and reached through a file descriptor. When the last reference goes away, the object is freed. That is why minimal loops forever: once it exits, its fds close, the link is released, and the program detaches.

A BPF link is a kernel object that represents one attachment of one program to one hook. Before links, many attachments were global state. A tc filter or an XDP program set with netlink stayed attached after the loading process died, and any other process could replace it by mistake. Links give attachments owner semantics:

  • Closing the last fd to a link detaches the program, so a crashed tool cleans up after itself.
  • A link can be updated atomically to a new program (bpf_link__update_program()), so a new version can replace the old with no window where nothing is attached.
  • A link can be listed and queried (bpftool link show), and anyone holding its fd can detach it explicitly with BPF_LINK_DETACH (libbpf: bpf_link_detach()).

To make an object outlive its process, you pin it: give it a name in the BPF filesystem, normally mounted at /sys/fs/bpf. Pinning uses the BPF_OBJ_PIN command and the pinned file holds a reference. Another process can later open it with BPF_OBJ_GET, and removing the file with rm drops the reference. libbpf provides bpf_link__pin(), bpf_program__pin(), bpf_map__pin(), bpf_object__pin_maps() and bpf_map__set_pin_path(). For maps it can also be declared in BPF code:

enum libbpf_pin_type {
	LIBBPF_PIN_NONE,
	/* PIN_BY_NAME: pin maps by name (in /sys/fs/bpf by default) */
	LIBBPF_PIN_BY_NAME,
};

A map declared with __uint(pinning, LIBBPF_PIN_BY_NAME) is pinned at /sys/fs/bpf/<name> when first created. When another object with the same declaration loads later, libbpf reuses the existing map instead of creating a new one, after checking that the type, key size, value size, max entries and flags match. This is how separate tools, or a new version of the same daemon, share state.

/* Illustrative (not from a repo): keep a program attached after the loader exits */
struct bpf_link *link = bpf_program__attach(skel->progs.handle_exec);
if (!link)
	return -errno;
err = bpf_link__pin(link, "/sys/fs/bpf/bootstrap_exec");   /* BPF_OBJ_PIN */
if (err)
	return err;
bpf_link__disconnect(link);   /* destroying the bpf_link struct will not detach */
bpf_link__destroy(link);      /* the pin keeps the attachment alive; rm the file to detach */

Pinning is how long-running systems such as Cilium (08) keep data-plane programs and maps in place across agent restarts and upgrades.

Benefits and limitations

Benefits

One small binary per architecture, with no Clang, LLVM or kernel headers on the target. Start-up costs a few BTF lookups instead of a compilation. Compile errors appear at build time. Programs can adapt to kernel versions and configurations with ordinary if statements, and the verifier removes the branches that do not apply. The same .bpf.o can be loaded by libbpf, libbpf-rs, cilium/ebpf and aya, which all implement CO-RE.

Limitations

The target needs BTF (built in, or supplied via BTFHub/min_core_btf). CO-RE fixes layouts, not missing features. Semantic changes, where a field keeps its name but changes meaning (for example a unit change), still need explicit code. Copying whole structs or arrays does not relocate sizes. Matching by name can be ambiguous or wrong when the kernel has several different types with the same name; bpftool emits ___2-style suffixes for those. And rewriting at load time makes it harder to sign programs.

Debugging tip

When a CO-RE program fails to load, install a print callback that shows LIBBPF_DEBUG messages, as bootstrap -v does. Look at the relo #N lines just before the failure. A verifier error mentioning unknown#195896080 points to a relocation that could not be resolved and was not guarded by an existence check.

Related work and where to go next

  • Other loaders. libbpf-rs, cilium/ebpf (Go) and aya (Rust) implement the same object format and CO-RE algorithm in their own languages: 08 · Ecosystem. BCC's libbpf-tools/ directory holds CO-RE ports of many classic BCC tools; Nakryiko's 2021 update counted more than 25.
  • Old kernels. 13 · bpf-compatible packages BTFHub plus min_core_btf into a build step and a small runtime.
  • Packaging. 10 · eunomia-bpf compiles CO-RE objects and ships them as JSON or WebAssembly packages that a generic runner loads. 12 · wasm-bpf moves the user-space half into WebAssembly.
  • Templates. 11 · Starter templates are ready-made libbpf-bootstrap-style repositories for C and Rust. 09 · bpf-developer-tutorial walks through many more programs built on this toolchain.
  • Userspace runtimes. 14 · bpftime loads the same libbpf objects into a user-space runtime and has to answer the same "which BTF?" question there.

Check your understanding

Q1. Which component emits the CO-RE relocation records saying which field an instruction accesses?

Only the compiler knows which instruction came from which field access. It writes a bpf_core_relo record (instruction offset, local type ID, access string, kind) into .BTF.ext. pahole produces the kernel's BTF, the other half of the match.

Q2. A program built against a 6.18 vmlinux.h reads task->real_parent with BPF_CORE_READ and is loaded on a 6.1 kernel where the field is at a different offset. What happens?

That is the whole point of a field byte-offset relocation. Without CO-RE (a plain bpf_probe_read_kernel with a hard-coded offset), the second option is what would happen.

Q3. Why does bootstrap.bpf.c declare const volatile unsigned long long min_duration_ns instead of storing the setting in a map?

A map value is unknown to the verifier, so every branch is checked. A frozen read-only global is a known constant. volatile stops Clang from folding the default 0 at compile time.

Q4. A target kernel was built without CONFIG_DEBUG_INFO_BTF. What is the standard way to still run a CO-RE program there?

The relocation mechanism works on such kernels; only the type data is missing. bpf-compatible (chapter 13) automates this. Features that need real kernel BTF, such as fentry, still will not work.

Q5. A tool attaches with bpf_program__attach() and exits without pinning anything. What happens to the program?

BPF links have owner semantics: the attachment lives as long as something holds a reference. Pin the link (bpf_link__pin) to keep it beyond the process.

Q6. In a BPF program, struct task_struct___old is declared with one field, long state. What does libbpf match it against?

Flavors let one source file describe several historical layouts of the same type. Combined with bpf_core_field_exists(), the branch that does not apply is poisoned and removed as dead code.
