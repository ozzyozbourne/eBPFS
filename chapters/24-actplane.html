Chapter 24

ActPlane: information-flow enforcement for AI agents

A coding agent reads .env while debugging. Twenty tool calls later, a Python script it wrote earlier opens a socket. Did the secret leave the machine? A tool-call filter cannot tell, and a sandbox cannot express "this data may not go there". This chapter shows how ActPlane uses eBPF to attach labels to processes, files and network endpoints, propagate them on every fork, read and write, and stop or explain the action that would violate a policy.

Prerequisites: 04, 05, 06Repo: eunomia-bpf/ActPlane @ bb89c77b~60 min

Why this matters

AI coding agents such as Claude Code and Codex run real commands on real machines. They read repositories, call compilers and test runners, fetch web pages, install packages and push commits. Each tool call can start arbitrary subprocesses. Projects try to steer this behaviour with instruction files (CLAUDE.md, AGENTS.md) that say things like "never push to main", "run the tests before committing", or "data read from .env must not reach the network". These are policies. The model follows them only probabilistically. Long contexts make it forget them. Planning errors route around them. Indirect prompt injection, where an attacker plants instructions in content the agent reads (Greshake et al., 2023), can override them on purpose.

There are three common ways to enforce such policies, and each one leaves a gap:

Prompt constraints

Instructions in the context window. Cheap and flexible, but not deterministic: the model can ignore them, and an injected instruction competes with them on equal terms.

Tool-layer guards

Hooks or gateways that inspect each tool call (a regex on the Bash command, an MCP gateway). Deterministic, but blind to what happens inside the tool: bash -c, a Python subprocess.run, or a script the agent wrote ten turns earlier.

Sandboxes

Containers, VMs, Landlock, seccomp. They cover every path, but they answer "may this process touch this resource?", not "may data derived from A flow to B?" or "did tests run since the last edit?". Their denials are a bare EPERM that tells the agent nothing.

ActPlane (repo, paper) sits below all three. It watches the operating-system actions of an agent's whole process tree with eBPF, so a rule holds whichever tool path the agent takes. Its rules are information-flow rules: labels mark where data came from, and they follow the data across fork, exec, file reads and writes and network connections. And when a rule fires, ActPlane sends a human-readable reason back to the agent, so a cooperative but fallible agent can try another way instead of retrying the same command.

The paper motivates this with a study of 64 popular repositories that contain CLAUDE.md or AGENTS.md (2,116 statements). 64% of the statements are policies. Of 1,361 policies, 83% concern something observable on the system, and 16% are cross-event: they depend on ordering or data lineage across operations ("run tests before committing"). 81% of the repositories contain at least one cross-event policy (paper §2.2). A per-call filter cannot enforce cross-event policies, because the facts it needs happened in earlier calls.

Key idea

ActPlane is runtime information-flow control (IFC) implemented as an eBPF state machine. Every process, file and IPv4 endpoint the agent touches carries a 64-bit label set in a BPF map. Fixed transfer functions update those sets on each hooked event, using only a bitwise OR, and compiled rules check them at the same hook. A block rule returns -EPERM from a BPF-LSM hook before the operation commits. A kill rule sends SIGKILL with bpf_send_signal(). A notify rule only reports. In every case the agent gets the rule's because text.

This chapter is about enforcement. Observing what an agent does (its prompts, TLS traffic and process tree) is the subject of chapter 23, AgentSight. ActPlane actually descends from AgentSight's code base. The repository's CLAUDE.md says the SSL/HTTP analyzers, web server and frontend were removed, leaving "the labeled information-flow engine plus a minimal Rust compiler/driver".

Information-flow control in ten minutes

Access control asks whether a subject may perform an operation on an object. Information-flow control asks a different question: where may information go? The difference matters when data is copied. If a process may read a secret and may also write to the network, access control allows both operations, and the secret leaks. IFC tracks the fact that the process now contains secret-derived information, so its later network write is a flow from secret to network, and the policy can forbid it.

Labels, sources, sinks and propagation

Dorothy Denning's 1976 paper "A Lattice Model of Secure Information Flow" gave the formal basis. Each object carries a security class, and classes form a lattice. When information flows from A to B, B's class must be at least A's (B ⊒ A), and a value computed from several inputs gets the join (least upper bound) of their classes. In practice the lattice is often the power set of a label set, and join is set union. That is the model ActPlane uses: a node's label set is a u64 bitmask, and join is |.

Four words are used throughout this chapter:

  • Source: where a label is introduced. Reading **/.env introduces SECRET. Executing codex introduces AGENT.
  • Propagation: the fixed rules that move labels along flows. A child inherits its parent's labels. A reader absorbs a file's labels. A written file absorbs the writer's labels.
  • Sink: an operation that a policy checks, such as connecting to an endpoint, writing under /shared, or executing git push.
  • Declassification / endorsement: a sanctioned way to remove a confidentiality label (a redactor clears SECRET) or to add an integrity label (a human-approval tool adds REVIEWED). Without these, everything ends up labeled and every rule fires.

IFC in operating systems

Language-level IFC (Myers' JFlow, 1999) checks flows inside one program at compile time. That cannot help when the "program" is an LLM that writes and runs new scripts on the fly. The OS-level line of work is the closer ancestor:

  • Asbestos (SOSP 2005) attached labels to processes and messages, so that a web server's per-user state could be isolated even from bugs in the server.
  • HiStar (OSDI 2006) built a new kernel whose objects all carry labels, and made every flow between them explicit. A Unix library ran on top of these objects.
  • Flume (SOSP 2007) brought decentralized IFC to stock Linux as a reference monitor in user space. Processes and files carry secrecy and integrity tags. Unprivileged processes can create tags and hold capabilities to add or drop them, which is how declassification is controlled.
  • TaintDroid (OSDI 2010) tracked taint through Android's Dalvik VM, files and IPC to detect apps that leak private data.
  • CamFlow (2017) and CamQuery (CCS 2018) recorded whole-system provenance with an LSM, and CamQuery ran analyses inline in the kernel that could prevent violations. ActPlane's own design notes call CamQuery "the single closest piece of prior art" (docs/design/related_work.md).

For agents, recent tool-level systems apply IFC at the harness boundary. FIDES labels data that tool calls return, and CaMeL separates trusted control flow from untrusted data. ActPlane's position is that these see only calls that go through the harness, while the kernel sees everything the agent's processes actually do. What ActPlane adds to the OS line is three things: an eBPF substrate that needs no kernel patch or module, a small policy language that an agent can write, and the feedback loop.

Taint vs IFC

The code still says "taint" (taint.h, taint_config, TAINT_VIOLATION). The CLAUDE.md explains the distinction the authors draw: classic taint analysis is "single-bit, usually offline, and aimed at finding vulnerabilities", while ActPlane keeps many labels at run time and enforces policy on them.

The architecture in one picture

There are four parts (README "How it works"):

  • Kernel engine (bpf/): hooks fork, exec, exit, open, read/write, unlink, rename, connect and receive. It keeps a label set per process, file and endpoint, propagates labels, evaluates compiled rules, and emits an event only when a rule matches.
  • Policy compiler (crates/actplane-ifc-compiler/): parses the policy language and lowers it to the fixed kernel ABI defined in bpf/taint.h.
  • Runtime (crates/actplane-runtime/): finds actplane.yaml, loads the prebuilt eBPF object with the aya Rust library (no clang or libbpf at run time), seeds the target process, and turns kernel matches into feedback.
  • CLI (crates/actplane-cli/): the actplane command with init, compile, doctor, run, watch, attach, mcp, control and feedback-hook.

One design choice runs through all of it: the kernel decides, user space only explains. The rule's name and its because string never enter the kernel. The kernel reports a numeric rule id, and the runtime maps it back to the text. So a bug in user-space formatting can make feedback worse, but it cannot let a forbidden operation through.

The policy language

A policy is a YAML file (actplane.yaml or .actplane/policy.yaml) with a DSL block under policy: |. The DSL has three kinds of declaration: source, rule, and the transforms declassify/endorse. The full grammar is in docs/rule-language.md §2 and in the paper's appendix A:

policy      := decl*
decl        := source_decl | sink_decl | xform_decl
source_decl := "source" IDENT "=" node_kind PATTERN          # node_kind: file|endpoint|exec
sink_decl   := "rule" IDENT ":" clause+ ["because" STRING]
clause      := EFFECT op_pattern ["if" expr] ["unless" cond]
EFFECT      := "block" | "notify" | "kill"                    # required
xform_decl  := ("declassify"|"endorse") IDENT "by" "exec" PATTERN
op_pattern  := "exec" PATTERN [ARG]
             | ("read"|"write"|"unlink"|"open") "file" PATTERN
             | ("connect"|"recv") "endpoint" PATTERN
expr        := term (("and"|"or") term)*
term        := ["not"] IDENT | "true"
cond        := "target" ["not"] PATTERN
             | "lineage-includes" "exec" PATTERN
             | "after" gate_event [ "exits" EXIT_CODE ] [ "since" since_event ("or" since_event)* ]

A clause matches an event when three things hold: the operation and its target match the pattern, the boolean expression after if holds over the subject's labels (the process doing the operation), and the unless condition is false. The unless conditions are what make rules usable:

  • target PAT / target not PAT: scope the rule to (or away from) a region, for example "writes anywhere except /work/**".
  • lineage-includes exec G: mandatory mediation. The operation is allowed only if the process or one of its ancestors executed G, for example "prod.db is reachable only through the migration tool".
  • after exec G [exits N] [since EV]: temporal ordering. The operation is allowed only if G ran earlier in this lineage (and exited with status N). With since, a later matching event makes the gate stale again, the way a build system treats foo.o as stale when foo.c changes.

Exec patterns without a / are basename matches (exec "git" means exec "**/git"). An optional second string is one argv token, so exec "git" "push" matches a git process with a push argument. If several clauses match one event, the strongest effect wins: kill > block > notify.

Real policies

The examples below are copied from the repository. The tabs show the three problem classes this curriculum cares about: exfiltration, prompt injection and destructive commands. The project's own default policy is a workflow rule.

version: 1
policy: |
  source SECRET = file "**/.env"
  source SECRET = file "/etc/secrets/**"

  rule no-exfil:
    block connect endpoint "*" if SECRET
    block write file "/shared/**" if SECRET
    because "secret data must not leave the host"

Any process that has read a .env file, or that descends from such a process, or that read a file such a process wrote, cannot connect anywhere or write under /shared. The companion file test/policies/08_secret_declassify.yaml adds declassify SECRET by exec "**/redact", so output that went through the redactor may leave.

version: 1
policy: |
  source UNTRUST = endpoint "*"
  source UNTRUST = file "**/downloads/**"

  rule no-injected-priv:
    block exec "git" "push" if UNTRUST and not REVIEWED
    block exec "**/deploy*" if UNTRUST and not REVIEWED
    because "untrusted input must not drive privileged actions"

  endorse REVIEWED by exec "**/human-approve"

Content that came from the network or from a downloads folder marks the reader UNTRUST. A privileged action by a process carrying that label needs the REVIEWED integrity label, which only a process that executed human-approve (or its descendants) gets. Note that the repo's support matrix says argv-token rules such as exec "git" "push" are observed after exec, so block is not a pre-op denial for them. The equivalent example E2 in docs/rule-language.md uses kill for the git push clause for that reason.

source AGENT = exec "**/codex"
rule confirm-destructive:
  kill exec "git" "--force"  if AGENT  unless after exec "**/confirm" since exec "git"
  kill write file "/data/**"         if AGENT  unless after exec "**/confirm"
  because "each force-push needs a fresh confirm; a stale confirm doesn't count"

Example E11. since exec "git" makes a confirmation single-use: any later git run makes it stale, so one confirm cannot authorize every future force-push.

version: 1

feedback:
  path: .actplane/last-violation.txt

policy: |
  source AGENT = exec "**/claude"
  source AGENT = exec "**/codex"

  # No auto-commit — agent must not commit without explicit user approval.
  # Gate: write .actplane/commit-approved to signal user approval; re-arms after each commit.
  rule no-auto-commit:
    block exec "git" "commit"
      if AGENT unless after write ".actplane/commit-approved"
        since exec "git" "commit"
    because "Write to .actplane/commit-approved after user says 'commit', then run git commit."

The policy the ActPlane repository applies to agents working on ActPlane itself. The gate is a file write, and every commit re-arms it.

source AGENT = exec "**/codex"
rule test-before-commit:
  kill exec "git" "commit"
    if AGENT  unless after exec "**/pytest" since write "src/**" or write "tests/**"
  because "tests are stale — you edited code after the last passing run; re-run the test suite, then commit"

Example E5, the canonical cross-event rule. A plain after would let edit → test → edit → commit slip through; since closes that hole.

The propagation model

Propagation is not part of the policy. It is the fixed meaning of a flow, defined in docs/rule-language.md §1.5. σ(n) is node n's label set, and every update happens before the sink check on the same event:

fork(p,c)    : σ(c) ∪= σ(p)                      # child inherits parent
exec(p,f)    : σ(p) ∪= σ(f) ∪ srcExec(f)         # process absorbs file + exec-source labels
read(p,f)    : σ(p) ∪= σ(f)                      # reader absorbs file labels
write(p,f)   : σ(f) ∪= σ(p)                      # written file inherits writer labels (derivation)
unlink(p,f)  : (no flow)
connect(p,e) : σ(e) ∪= σ(p)                      # egress: endpoint records writer labels
recv(p,e)    : σ(p) ∪= σ(e)                      # received data taints receiver

The invariant the document states is that label L is in σ(n) iff information from some L-source has reached n through a chain of these events. The state is the transitive closure of provenance, but it is maintained incrementally, in O(1) per event, with no graph walk. That is what makes it cheap enough to run inside a hook on every syscall.

Over-tainting is deliberate

A process that reads one byte of a secret is labeled SECRET for the rest of its life, and so is every file it writes, even if the output does not contain the secret. The support matrix says so directly: "ActPlane favors preserving provenance over silently missing a derived flow." The tools for controlling this are declassify, scoping rules with target, and keeping agent sessions short.

Inside the kernel engine

Which hooks, and why both kinds

ActPlane uses two families of program from chapter 05. It uses no kprobes and no cgroup programs (grep -i cgroup bpf/ finds nothing).

They can notify or kill, but they cannot stop the syscall.

Why keep tracepoints when LSM hooks exist? There are three reasons in the code and docs. First, there is no LSM hook for fork, and the exec tracepoint is where argv is available: handle_exec reads mm->arg_start to get the command line, which bprm_check_security does not have in a convenient form. That is why the docs say argv-token rules (git push) should use kill: the new image may have started, but it is killed before it gets far. Second, exit status is only known at sched_process_exit, which arms after exec G exits 0 gates. Third, many kernels, including stock distribution kernels, do not enable BPF LSM. On those, ActPlane still works as a notify/kill harness.

The rule ABI

The compiler and the kernel share one header. Each source, transform, gate and since invalidator becomes a taint_update; each lowered clause becomes a taint_rule. The label condition is just two masks:

#define TAINT_PAT_LEN     64
/* ... */
#define MAX_TAINT_LABELS  64   /* labels are a u64 bitmask */
/* Sized for 100+ rules in one policy. Table loops run via bpf_loop (callback
 * verified once), so these bounds cost memory, not verifier path count. */
#define MAX_TAINT_UPDATES 320
#define MAX_TAINT_RULES   128

/* sink operations */
enum taint_op {
	TOP_EXEC    = 0, /* exec comm */
	TOP_OPEN    = 1, /* open/read path */
	TOP_WRITE   = 2, /* write/unlink/rename path (mutation) */
	TOP_CONNECT = 3, /* connect host/ip */
	TOP_RECV    = 4, /* recv from endpoint (data ingress) */
};
/* ... */
struct taint_rule {
	unsigned char op;         /* enum taint_op */
	unsigned char match;      /* enum taint_match (target) */
	unsigned char cond_kind;  /* enum taint_cond */
	unsigned char cond_neg;   /* for TCOND_TARGET: invert the match */
	unsigned char cond_match; /* enum taint_match for cond_pat */
	unsigned char effect;     /* enum taint_effect */
	char target[TAINT_PAT_LEN];
	char arg[TAINT_ARG_LEN];  /* exec @arg token, "" = ignore */
	char cond_pat[TAINT_PAT_LEN];
	unsigned long long req;    /* all these label bits must be set */
	unsigned long long forbid; /* none of these may be set */
	unsigned long long gate;   /* gate bit for LINEAGE/AFTER */
	/* ... rule_id, ipv4/mask, cond_ipv4/mask, gate_idx, domain_id, since_mask ... */
};
/* ... */
/* boolean label predicate: required bits all set, forbidden bits all clear */
static __always_inline int taint_mask_ok(unsigned long long labels,
					 unsigned long long req,
					 unsigned long long forbid)
{
	return (labels & req) == req && (labels & forbid) == 0ULL;
}

A label expression like UNTRUST and not REVIEWED becomes req = UNTRUST_bit, forbid = REVIEWED_bit. An or cannot be expressed in one (req, forbid) pair, so the compiler expands the expression to disjunctive normal form and emits one kernel rule per disjunct:

/// expr -> disjunction of (req_mask, forbid_mask)
fn dnf(e: &Expr, ctx: &mut Ctx) -> Result<Vec<(u64, u64)>, String> {
    Ok(match e {
        Expr::True => vec![(0, 0)],
        Expr::Label(l) => vec![(ctx.label_bit(l)?, 0)],
        Expr::Not(l) => vec![(0, ctx.label_bit(l)?)],
        Expr::Or(a, b) => {
            let mut v = dnf(a, ctx)?;
            v.extend(dnf(b, ctx)?);
            v
        }
        Expr::And(a, b) => {
            let (da, db) = (dnf(a, ctx)?, dnf(b, ctx)?);
            let mut v = Vec::new();
            for (ra, fa) in &da {
                for (rb, fb) in &db {
                    v.push((ra | rb, fa | fb));
                }
            }
            v
        }
    })
}

Globs are lowered the same way, into one of five kernel match kinds (exact, prefix, suffix, contains, any). There is no regex engine in the kernel. Hostnames are resolved by the compiler to IPv4 addresses, so the kernel only compares numbers. The structs in lower.rs are #[repr(C)] copies of the C ones, and a test guards the total size. The CLAUDE.md warns that any change to taint.h must be mirrored in lower.rs.

Label state in maps

The engine's state lives in hash maps declared in bpf/taint_engine.bpf.h. A process entry holds labels and the gate bits seen in its ancestry; a file entry is keyed by a real (dev, inode) when the hook has a struct file, so a rename or a hard link does not lose the label:

struct proc_state {
	__u64 labels;
	__u64 lin_gates; /* gate bits seen in this pid's ancestor chain (incl self) */
};
/* ... */
struct file_id {
	__u64 ino;
	__u32 dev;
	__u32 _pad;
};
/* ... */
struct file_state {
	__u64 labels;
	__u32 last_write_epoch;
	__u32 _pad;
};
/* ... */
struct {
	__uint(type, BPF_MAP_TYPE_HASH);
	__uint(max_entries, 16384);
	__type(key, pid_t);
	__type(value, struct proc_state);
} ts_proc SEC(".maps");
/* ... */
struct {
	__uint(type, BPF_MAP_TYPE_HASH);
	__uint(max_entries, 65536);
	__type(key, struct file_domain_id);
	__type(value, struct file_state);
} ts_file SEC(".maps");
/* ... */
struct {
	__uint(type, BPF_MAP_TYPE_HASH);
	__uint(max_entries, 16384);
	__type(key, struct endp_domain_id); /* IPv4 (network order) + domain */
	__type(value, __u64);
} ts_endp SEC(".maps");

Other maps hold the rule and update tables (ts_rules, ts_updates, ts_counts), lineage roots (ts_root), per-session gate epochs (ts_sess), provenance records that let feedback say which file introduced a label (ts_*_prov), per-domain state (cap_*), and the output ring buffer rb. In tracepoint-only mode, when a hook only has a user-space path, files fall back to a key of (0, fnv1a(path)).

Propagation code

Fork is the simplest case. The tracepoint handler calls te_fork, which does nothing for processes outside the agent's tree and otherwise copies the parent's state for every domain depth and records the lineage root:

SEC("tp/sched/sched_process_fork")
int handle_fork(struct trace_event_raw_sched_process_fork *ctx)
{
	pid_t parent_tgid = bpf_get_current_pid_tgid() >> 32;

	te_fork(parent_tgid, ctx->child_pid);
	te_copy_fork_fds(parent_tgid, ctx->child_pid);
	return 0;
}
static __always_inline void te_fork(pid_t ppid, pid_t cpid)
{
	if (!te_pid_active(ppid))
		return;
	cap_fork(ppid, cpid);
	for (int i = 0; i < CAP_DOMAIN_DEPTH; i++) {
		__u32 domain_id = te_domain_for_depth(ppid, i);
		if (i > 0 && !domain_id)
			break;
		te_copy_proc_domain_state(ppid, cpid, domain_id);
	}
	pid_t r = te_root(ppid);
	bpf_map_update_elem(&ts_root, &cpid, &r, BPF_ANY);
}
/* write: file absorbs proc labels; stamp `since write` invalidators (this is
 * what makes a gate go stale when the agent edits an input again). The label
 * flow is gated on pl != 0, but invalidator stamping is not — editing an
 * unlabeled source file must still invalidate a prior gate. ... */
static __always_inline void te_write_flow_domain(pid_t pid, struct file_id *fid,
						 const char *path, __u32 domain_id)
{
	if (!te_pid_active(pid) || !cap_domain_matches_pid(pid, domain_id))
		return;
	struct te_update_ctx u = {
		.pid = pid,
		.domain_id = domain_id,
		.op = TOP_WRITE,
		.target = path,
	};
	te_collect_file_updates(&u);
	__u64 pl = te_labels_for_domain(pid, domain_id);
	if (!u.gates && !u.invals && !pl)
		return;
	pid_t r = te_root(pid);
	__u32 ep = te_tick(r, domain_id);
	if (u.gates || u.invals)
		te_stamp(r, domain_id, ep, u.gates, u.invals);
	if (pl) {
		struct file_domain_id *fdom = te_file_domain_tmp();
		if (!fdom)
			return;
		te_file_domain_key_for(domain_id, fid, fdom);
		struct file_state *fs = bpf_map_lookup_elem(&ts_file, fdom);
		if (fs) {
			fs->labels |= pl;
			fs->last_write_epoch = ep;
		} else {
			struct file_state ns = { .labels = pl, .last_write_epoch = ep };
			bpf_map_update_elem(&ts_file, fdom, &ns, BPF_ANY);
		}
		te_copy_proc_prov_to_file(pid, fdom, pl);
	}
}
static __noinline int te_after_satisfied(const struct taint_rule *r, pid_t pid)
{
	pid_t rt = te_root(pid);
	struct te_sess *s = te_sess_get(rt, r->domain_id);

	if (!s)
		return 0;
	if (r->since_mask == 0)
		return (s->gate_bits & r->gate) ? 1 : 0;
	__u32 gidx = r->gate_idx;
	if (gidx >= MAX_TAINT_GATES)
		return 0;
	__u32 ge = s->gate_epoch[gidx];
	if (ge == 0)
		return 0; /* gate never fired -> stale */
	__u32 last_inval = 0;
	for (int i = 0; i < MAX_TAINT_INVALS; i++) {
		if (r->since_mask & (1ULL << i)) {
			__u32 ie = s->inval_epoch[i];
			if (ie > last_inval)
				last_inval = ie;
		}
	}
	return ge > last_inval ? 1 : 0;
}

Staleness is a comparison of two counters. Each lineage root has a monotonic epoch. Running the gate stamps gate_epoch[g], and a matching since event stamps inval_epoch[s]. The gate is fresh iff it was stamped after every invalidator.

Two things stand out. Every helper starts with te_pid_active(), so processes outside an ActPlane domain cost one hash lookup and nothing else. And the code is written around the verifier (chapter 03). Rule tables are scanned with bpf_loop(), so a callback is verified once whatever the table size. Heavy helpers are __noinline so that each gets its own stack frame. The string matchers in taint.h are branchless, so that their verification cost does not depend on the bytes being compared. bpf/README.md and CLAUDE.md list these tricks under "eBPF verifier gotchas", and several recent commits are verifier stack-depth fixes.

The enforcement point

Every hook funnels into a small number of handlers (te_handle_event, te_handle_exec_event, and the exec tail-call pipeline). Each one computes the subject's labels, scans the rules for the strongest matching effect, and then acts. The hook's mode decides which effects it may act on:

static __always_inline __u32 te_tracepoint_mode(void)
{
	return TE_MODE_NOTIFY;
}

static __always_inline __u32 te_effect_mode(__u32 backend_mode, __u32 effect)
{
	if (effect == TEFFECT_NOTIFY)
		return TE_MODE_NOTIFY;
	if (effect == TEFFECT_KILL)
		return TE_MODE_KILL;
	if (effect == TEFFECT_BLOCK && backend_mode == TE_MODE_BLOCK)
		return TE_MODE_BLOCK;
	return TE_MODE_UNSUPPORTED;
}

static __always_inline __u32 te_supported_effects(__u32 backend_mode)
{
	if (backend_mode == TE_MODE_BLOCK)
		return (1U << TEFFECT_BLOCK);
	return (1U << TEFFECT_NOTIFY) | (1U << TEFFECT_KILL);
}

LSM programs pass TE_MODE_BLOCK; tracepoints pass TE_MODE_NOTIFY. As I read this code, the LSM hooks therefore evaluate only block clauses, and the tracepoints evaluate notify and kill clauses. A block rule with no LSM behind it maps to TE_MODE_UNSUPPORTED and does nothing, which matches the documentation: "Without BPF LSM, block is unsupported and tracepoints do not evaluate it." Here is the LSM hook for connect() and the decision code at the end of te_handle_event:

SEC("lsm/socket_connect")
int BPF_PROG(enforce_socket_connect, struct socket *sock, struct sockaddr *address,
	     int addrlen)
{
	(void)sock;
	(void)addrlen;
	return te_handle_net(TE_REF_SOCKADDR_KERN, address, 0,
			     TE_ACCESS_CONNECT, TE_MODE_BLOCK);
}

/* ... inside te_handle_event(), after the rule scan ... */
	if (rid >= 0) {
		action = te_effect_mode(ev->mode, effect);
		if (action != TE_MODE_UNSUPPORTED)
			emit_violation(ev->pid, rid, display,
				       ev->obj_kind == TE_OBJ_ENDPOINT ? ev->ip : 0,
				       ev->obj_kind, fid,
				       matched_domain_id, matched_labels,
				       matched_op,
				       action == TE_MODE_BLOCK ||
					       (action == TE_MODE_KILL && ev->mode == TE_MODE_BLOCK),
				       action == TE_MODE_KILL, effect);
		if (action == TE_MODE_BLOCK)
			return -EPERM;
		if (action == TE_MODE_KILL) {
			bpf_send_signal(SIGKILL);
			if (ev->mode == TE_MODE_BLOCK)
				return -EPERM;
		}
	}

	if (ev->obj_kind == TE_OBJ_FILE && (policy_features & TE_POLICY_FILE_FLOW)) {
		if (ev->access & TE_ACCESS_READ)
			te_read(ev->pid, fid, ev->target);
		if (ev->access & TE_ACCESS_WRITE)
			te_write_flow(ev->pid, fid, ev->target);
	} else if (ev->obj_kind == TE_OBJ_ENDPOINT) {
		if (ev->access & TE_ACCESS_CONNECT)
			te_connect_flow(ev->ip, ev->pid);
		if (ev->access & TE_ACCESS_RECV)
			te_recv_flow(ev->ip, ev->pid);
	}

	return 0;

Note the ordering. A denied operation returns before the flow functions run, so a blocked write does not label the file. Only allowed operations propagate. The LSM verdict convention is the one from chapter 05: 0 allows and a negative errno denies. The connect fails in the agent's process with EPERM, just as if SELinux had refused it.

Walkthrough: a blocked exfiltration attempt

This stepper follows policy 01_secret_no_exfil.yaml through the flow of figure 24.2, on a machine where BPF LSM is active. The kernel functions named are the real ones. The scenario (file names, the IP address) is illustrative.

1. Compile and launch

sudo -E actplane run -- codex. The compiler gives AGENT bit 0 and SECRET bit 1 and lowers block connect endpoint "*" if SECRET to one taint_rule with op = TOP_CONNECT, match any, req = 0b10, effect = BLOCK. The runtime loads the engine, sees bpf in /sys/kernel/security/lsm and sets the rodata enforce_mode = 1.

2. Start the agent stopped, then seed it

The runtime spawns /bin/sh -c 'kill -STOP $$; exec "$@"' as the invoking user, waits until it is stopped, writes its pid into ts_proc/ts_root and binds it to a domain in cap_task. It also marks its own pid as protected, then sends SIGCONT. Because seeding happens before the agent's first instruction, no early event escapes.

3. The agent debugs and reads .env

Codex runs bash -c 'python debug.py'. sched_process_fork copies {AGENT} to each child. When python opens /repo/.env, lsm/file_open runs: no block rule matches an open, so the hook returns 0. Then the read flow (te_read_domain) runs. The path matches the file "**/.env" source update, so SECRET is ORed into python's entry together with any labels stored for the file in ts_file, giving {AGENT, SECRET}. A provenance record notes that the label came from opening /repo/.env.

4. Derived data lands in a file

Python writes a summary to /tmp/out.json. lsm/file_permission with MAY_WRITE → no write rule matches outside /shared → allowed → te_write_flow_domain ORs {AGENT, SECRET} into the file's ts_file entry, keyed by its (dev, inode).

5. A later tool call reads the file

Many turns later, the model runs bash upload.sh, which reads /tmp/out.json. The new shell got {AGENT} by fork. The read flow adds the file's SECRET. A tool-call filter that looked only for .env in the command line saw nothing suspicious in either call.

6. The connect hits the sink

upload.sh runs curl https://203.0.113.7/. In curl's connect(), lsm/socket_connect calls te_handle_net(..., TE_MODE_BLOCK). The rule scan finds op = connect, IP matches any, and taint_mask_ok(labels, 0b10, 0) is true. The result is effect BLOCK and mode BLOCK.

7. Deny and report

emit_violation() puts a record with rule_id = 0, blocked = 1, the IP and the provenance of SECRET (the read of /repo/.env) in the ring buffer, and the hook returns -EPERM. te_connect_flow never runs. curl prints "Operation not permitted" and exits non-zero.

8. The agent learns why

The runtime maps rule 0 to no-exfil and writes the reason ("secret data must not leave the host") to the run's feedback mailbox. After the Bash tool call, Claude Code's or Codex's PostToolUse hook runs actplane feedback-hook, which injects the reason into the next model turn. The model can then pick a sanctioned path, such as running the redactor if the policy declares declassify SECRET by exec "**/redact".

Without BPF LSM

On a kernel without bpf in the LSM list, step 6 changes completely. The block clause is TE_MODE_UNSUPPORTED and nothing happens. actplane compile warns about this, and doctor prints "block rules will not fire". The repo's own e2e cases use kill connect endpoint "*" instead, which works from the sys_enter_connect tracepoint but is post-event: the documentation says that "the triggering syscall may already have completed".

Scoping: whose actions are checked

ActPlane scopes by process lineage, not by cgroup. A process is in scope iff its pid is bound in the cap_task map (te_pid_active(pid) is cap_task_bound(pid)). The fork tracepoint extends the binding to children, so everything the agent spawns, however many bash -c or python -c hops deep, is in scope, and nothing else on the host is. This is how the README can promise that "nothing descended from codex, however many hops, may run git" and still leave the developer's own terminal alone. Compare chapter 25, which looks at agents through cgroups for resource control.

There are three ways in:

  • actplane run -- <cmd>: strict. The target is started stopped and seeded before it runs (code below).
  • actplane mcp --auto-attach-parent: started by the agent as an MCP server. It tries passwordless sudo, loads the engine and seeds the parent Codex process.
  • actplane attach --pid <pid>: post-hoc. Future events are covered, but "ActPlane does not reconstruct labels or file/network history from before the attach".
fn spawn_stopped_target(
    cmd: &[String],
    feedback: &FeedbackPaths,
    policy_path: Option<&Path>,
    run_as_root: bool,
    new_process_group: bool,
) -> Result<Child> {
    /* ... */
    let drop_to = target_user(run_as_root);
    let mut target = Command::new("/bin/sh");
    target.arg("-c");
    target.arg("kill -STOP $$; exec \"$@\"");
    target.arg("actplane-target");
    target.args(cmd);
    /* ... stdio, ACTPLANE_FEEDBACK_FILE / ACTPLANE_HOOK_STATE env ... */
    unsafe {
        target.pre_exec(move || {
            mark_non_stdio_fds_cloexec()?;
            /* ... setpgid ... */
            if let Some((uid, gid)) = drop_to {
                if libc::setgid(gid) != 0 {
                    return Err(std::io::Error::last_os_error());
                }
                if libc::setuid(uid) != 0 {
                    return Err(std::io::Error::last_os_error());
                }
            }
            Ok(())
        });
    }
    let mut target = target.spawn()?;
    /* ... wait_for_stopped_process(pid, 5 s), else SIGKILL ... */
    Ok(target)
}

The kill -STOP $$ trick avoids a race: the shell stops itself before exec, the runtime seeds the pid, and only then does SIGCONT let the real command start. The target also runs as the invoking user (from SUDO_UID/SUDO_GID), not as root.

Policy domains

Agents spawn sub-agents, and a sub-agent may want its own rules: a reviewer should be read-only, a builder should not touch the network. docs/security_model.md defines a domain as "the runtime policy boundary for a process tree" with one invariant, monotonic tightening:

policy(D) = policy(parent(D)) + local(D)

policy(child) >= policy(parent)

A child domain can add bindings, labels and gates and can narrow its scope. It cannot remove an inherited rule, widen scope, or enable hook classes that were not reserved when the engine loaded. Deltas are compiled in user space and submitted through a BPF_MAP_TYPE_USER_RINGBUF (cap_req). The admission check runs in the kernel (bpf/capability.bpf.h), so a compromised compiler can only weaken the rules it was asked to add, never inherited ones. CLI shape:

actplane control bind-child --pid 1234 --child-id 1234
actplane control delta add --domain-id 1234 --delta rules/no-curl.dsl
actplane control launch-child --delta rules/no-curl.dsl -- codex --cd /work

Protecting the enforcer

An agent with sudo could simply kill ActPlane or detach its programs. When BPF LSM is active, three hooks close that door for processes inside a domain, uid 0 included: lsm/task_kill and lsm/ptrace_access_check refuse to signal or trace the protected control pid, and lsm/bpf refuses most bpf() commands:

SEC("lsm/bpf")
int BPF_PROG(enforce_bpf_syscall, int cmd, union bpf_attr *attr,
	     unsigned int size, bool privileged)
{
	pid_t caller = bpf_get_current_pid_tgid() >> 32;

	/* ... */
	if (!te_pid_active(caller))
		return 0;

	/* Runtime clients may need to open pinned maps while already managed.
	 * Map mutation is limited to protected pids or domains that already carry
	 * runtime authority. */
	switch (cmd) {
	case BPF_MAP_LOOKUP_ELEM:
	case BPF_MAP_GET_NEXT_KEY:
	case BPF_OBJ_GET:
	case BPF_OBJ_GET_INFO_BY_FD:
		return 0;
	case BPF_MAP_UPDATE_ELEM:
	case BPF_MAP_DELETE_ELEM:
		return te_pid_can_control_bpf(caller) ? 0 : -EPERM;
	default:
		return -EPERM;
	}
}

Processes outside every domain "remain ordinary host administrators and can still stop or unload the engine" (bpf/README.md). That is by design: the human operator is trusted, the agent is not.

Can agents write the rules?

RQ1: a Codex agent (GPT-5.5) translated all 607 OS-enforceable policies from the study into 1,283 rule lines in 34 minutes, at $0.028 per policy. 74% have at most two clauses. Effects split 66% notify, 29% block, 5% kill. 28% use an after/since gate. declassify/endorse were never used.

Safety benchmark

RQ5 runs the 361 OpenAgentSafety tasks, whose completion requires an unsafe side effect such as exfiltrating credentials or wiping configuration. A Codex agent generated a per-task policy from the task description, loaded as higher-authority policy. Of 106 baseline-unsafe tasks, ActPlane terminated 78 before the harmful effect completed and missed 28, a 74% prevention rate. The misses are described as hook-coverage gaps: the agent reached the effect through a path the current hooks do not observe. RQ4 (OctoBench, 21 in-scope tasks) reports +9.9 points on user-query reward and +2.8 on compliance reward.

Benefits and limitations

Covers every path

Rules attach to kernel events of the whole process tree. bash -c, python -c subprocess, a compiled helper and a script from ten turns ago all produce the same hooked exec, open and connect.

Cross-event policies

Labels, lineage gates and epochs express data flow, mandatory mediation and "tests since last edit". A per-call check cannot express any of these.

Feedback, not just EPERM

The because text reaches the model through hooks or MCP. The paper's ablation shows this is where much of the compliance gain comes from.

Cheap and deployable

Prebuilt CO-RE object, aya loader, no kernel module. Propagation is a map lookup and an OR. Monotonic domains let sub-agents tighten their own policy at run time.

Limitations, mostly from the repo's own support-matrix.md, the paper's threat model, and the code:

  • Hard denial needs BPF LSM. Without it, ActPlane can notify and kill, and a kill from a tracepoint may come after the syscall completed. Argv-token exec rules (git push) are never pre-op, even with LSM.
  • The orb case: the engine needs the BPF JIT, because the exec pipeline uses tail calls together with BPF-to-BPF calls.
  • Coarse, conservative labels. Labels are per process and per file, not per byte. One read taints a long-lived process. At most 64 labels, 128 kernel rules and 320 updates per config.
  • Matching is by name and number. Exec rules match the basename or argv tokens. A custom Git client avoids exec "git" rules (though its writes and connects are still visible). Endpoints are IPv4 numbers; hostnames are resolved at compile time, and IPv6, hostname globs and batch UDP syscalls are limited or unsupported.
  • Channel coverage. mmap, Unix sockets, pipes, SCM_RIGHTS, sendfile, splice and copy_file_range need the advanced hook profile. Shared memory is called out as limited. File contents are out of scope.
  • Trust model. Kernel compromise, CAP_BPF compromise and side channels are out of scope. Rules the agent writes for itself give compliance help, not security. Only higher-authority rules loaded before the agent starts carry guarantees. attach does not see history from before the attach.

Related work

  • eBPF security tools. Tetragon, Tracee and KubeArmor (chapter 08) enforce per-event predicates with LSM hooks or bpf_send_signal. The paper's related-work section says these offer "per-event predicates or single-channel lineage flags", while ActPlane propagates multi-label flows across channels. Lesson 19 of the bpf-developer-tutorial (chapter 05) is a five-line version of the same lsm/socket_connect idea.
  • Sandboxes. Landlock, seccomp, AppArmor, gVisor, containers. They complement ActPlane: they bound what the agent can reach, and ActPlane decides what reachable data may do. The paper borrows Landlock's and Capsicum's self-restriction principle for agent-authored rules.
  • OS IFC and provenance. Asbestos, HiStar, Flume, TaintDroid, CamFlow/CamQuery (covered above). ActPlane's model is closest to CamQuery's inline in-kernel analysis, rebuilt on BPF LSM, which landed in Linux 5.7 (LWN on KRSI, kernel docs).
  • Agent guardrails. FIDES and CaMeL (IFC at the tool or interpreter layer), AgentSpec, NeMo Guardrails, LlamaFirewall, and Claude Code/Codex approval hooks. These see harness-mediated requests; ActPlane is designed to be used alongside them.
  • Sibling chapters. 23 AgentSight observes agents with eBPF. 25 agentcgroup covers their resource use. 26 covers reward-hacking guards and safe change.

Check your understanding

Q1. Process A reads .env (a SECRET source) and writes /tmp/x. Process B, started later in another tool call of the same agent, reads /tmp/x and calls connect(). Under block connect endpoint "*" if SECRET with BPF LSM active, what happens?

Write propagates σ(f) ∪= σ(p) and read propagates σ(p) ∪= σ(f). The rule is checked at the connect sink, so the read is allowed and the connect is denied (example E7).

Q2. On a kernel whose LSM list is capability,landlock, which policy effect can still stop an agent's git push?

Without BPF LSM, block maps to TE_MODE_UNSUPPORTED. kill runs from tracepoints. Argv-token rules are post-exec anyway, so the docs recommend kill for them.

Q3. Why does a blocked write not add the writer's labels to the file?

In te_handle_event, the return -EPERM comes before te_read/te_write_flow/te_connect_flow.

Q4. How does ActPlane decide whether a process is subject to the policy at all?

te_pid_active(pid) is cap_task_bound(pid). There are no cgroup programs in bpf/. Scoping is by process lineage.

Q5. unless after exec "**/pytest" since write "src/**": the agent runs pytest, edits src/a.py, then commits. Is the commit allowed?

te_after_satisfied requires gate_epoch > last_inval. Without since the gate would be latching and the commit would pass. exits 0 is a separate qualifier.

Q6. In the paper's RQ2, what happened when semantic feedback was removed (ActPlane-opaque)?

The engine still detected violations, but an agent seeing only EPERM often did not recover toward compliance, so the judge counted many as FN.
