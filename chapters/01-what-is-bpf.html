Chapter 01

What is BPF? From packet filter to in-kernel VM

tcpdump uses BPF to filter packets, Chrome uses it to sandbox renderers, and Cilium uses it to route traffic in a Kubernetes cluster. How did a small packet-filter language from 1993 turn into the standard way to run your own code safely inside the Linux kernel?

Prerequisites: C, basic Linux, what a syscall isRepo: Linux kernel (kernel/bpf/, net/core/filter.c)~45 min

Why this matters

An operating-system kernel can see everything: every packet, every system call, every page fault and every context switch. It can also decide everything: which packet is dropped, which process runs next, which file open is denied. If you want visibility or control at that level, you need code that runs inside the kernel. For most of Unix history there were only two ways to get it there: get a patch merged upstream and wait years for it to reach your servers, or write a loadable kernel module and accept that one bad pointer can crash the machine.

BPF is a third way. You hand the kernel a small program in a restricted bytecode. The kernel checks it, compiles it to native machine code, and runs it when a chosen event happens. Results go into shared data structures that ordinary user-space programs can read. The kernel promises that the program will not crash it, will not loop forever, and will only touch memory it is allowed to touch. If it cannot prove that, it refuses to load the program.

This chapter tells the story in order, because each stage explains a design decision you will run into later:

  • 1992–93: McCanne and Jacobson design the BSD Packet Filter so that tcpdump can capture packets without copying every packet to user space.
  • 1990s–2012: Linux adopts the same filter machine for sockets ("Linux Socket Filter"), adds a JIT, and reuses it for system-call filtering (seccomp-bpf).
  • 2014: Alexei Starovoitov, working with Daniel Borkmann, rewrites the in-kernel machine into extended BPF: 64-bit registers, function calls, maps, a verifier and a JIT.
  • 2015 onward: new hook types arrive release after release: tracing, XDP, cgroups, LSM, and in 6.12 even CPU scheduling.

At the end you will run a real program, look at its bytecode, and watch the verifier reject a buggy one.

Key idea

BPF is a safe, verifiable instruction set that the kernel runs on events. The safety comes from a static check made before the program runs (the verifier), not from a sandbox at runtime. The speed comes from a JIT that turns the checked bytecode into native instructions. The usefulness comes from hooks (where programs attach), helpers (the kernel functions programs may call) and maps (shared state with user space).

The origin: the BSD Packet Filter (1993)

The problem: capturing packets without drowning

In the early 1990s Steven McCanne and Van Jacobson at Lawrence Berkeley Laboratory were building network monitoring tools, most famously tcpdump. A packet capture tool wants maybe one packet in a thousand, such as "TCP traffic to port 22" or "ARP requests". The rest should be ignored as cheaply as possible. If the kernel copies every packet to the user process and lets the process decide, most of the CPU time goes into copying packets that will be thrown away.

Their paper, "The BSD Packet Filter: A New Architecture for User-level Packet Capture" (USENIX Winter 1993, San Diego; the preprint is dated December 19, 1992), describes the answer. The user process supplies a filter program. The kernel runs that program on each packet "in place", where the network card's DMA engine put it, and copies only the packets the filter accepts. The paper's conclusion from its measurements: "filtering packets early and in place pays off".

Why a register machine

The idea of a programmable in-kernel filter was not new. The CMU/Stanford Packet Filter (CSPF) already ran filter programs, on a stack machine whose programs were boolean expression trees. McCanne and Jacobson argued that a stack machine is a poor fit for RISC CPUs whose bottleneck is memory: simulating an operand stack means memory loads and stores for every operation. They switched to two ideas:

  • A control-flow graph instead of an expression tree. Each node tests one packet field and branches. What the program has already learned about the packet is encoded in the path taken, so a field is parsed once instead of again for every sub-expression.
  • A register machine instead of a stack machine. The abstract registers can live in real CPU registers.

The paper lists five design constraints, and they still explain the shape of BPF today:

  1. It must be protocol independent: adding a new protocol must not require a kernel change. Packets are just byte arrays.
  2. It must be general enough to handle unforeseen uses.
  3. Packet data references should be minimised.
  4. Decoding an instruction should be a single C switch statement.
  5. The abstract machine registers should reside in physical registers.

The measured gains were large. The abstract claims a filter evaluator "up to 20 times faster" than CSPF and overall performance "up to 100 times faster than Sun's NIT" on the same hardware. On a SPARCstation 2 the fixed per-packet cost of a BPF tap call was about 6 µs against 89 µs for NIT.

The classic BPF machine

The "BPF pseudo-machine" in the paper is tiny:

  • A, a 32-bit accumulator, where all arithmetic and comparisons happen;
  • X, a 32-bit index register, used mainly to hold the variable length of the IP header;
  • M[], a small scratch memory (16 words in Linux, BPF_MEMWORDS);
  • an implicit program counter.

Every instruction has the same 64-bit format: opcode:16 jt:8 jf:8 k:32. jt and jf are the jump-if-true and jump-if-false offsets, counted from the next instruction. Because the offsets are unsigned and only point forward, a classic BPF program cannot loop. Every program finishes in at most as many steps as it has instructions. That property is the seed of everything the eBPF verifier later does. A read past the end of the packet ends the filter with return value 0 (drop), and so does a division by zero. A ret instruction ends the program and returns how many bytes of the packet to keep, where 0 means "reject".

Linux still defines exactly this structure in its user-space API header:

/*
 *	Try and keep these values and structures similar to BSD, especially
 *	the BPF code definitions which need to match so you can share filters
 */
 
struct sock_filter {	/* Filter block */
	__u16	code;   /* Actual filter code */
	__u8	jt;	/* Jump true */
	__u8	jf;	/* Jump false */
	__u32	k;      /* Generic multiuse field */
};

struct sock_fprog {	/* Required for SO_ATTACH_FILTER. */
	unsigned short		len;	/* Number of filter blocks */
	struct sock_filter __user *filter;
};
/* ... */
#define BPF_STMT(code, k) { (unsigned short)(code), 0, 0, k }
#define BPF_JUMP(code, k, jt, jf) { (unsigned short)(code), jt, jf, k }
/* ... */
#define BPF_MEMWORDS 16

tcpdump, libpcap and a real classic BPF program

Nobody writes classic BPF by hand if they can avoid it. tcpdump accepts a filter expression such as ip and tcp dst port 22, and its capture library, libpcap, compiles the expression into BPF, optimises it, and attaches it to the capture socket. (The 1993 paper says the compiler and optimiser were "part of tcpdump"; they later moved into libpcap.) tcpdump can show you the compiled program: -d prints it as readable assembly, -dd as a C array, -ddd as decimal numbers.

Here is real output, captured for this chapter with tcpdump 4.99.3 / libpcap 1.10.3. -y EN10MB selects the Ethernet link type, so the command works without a capture interface or root:

$ tcpdump -d -y EN10MB 'ip and tcp dst port 22'
(000) ldh      [12]
(001) jeq      #0x800           jt 2	jf 10
(002) ldb      [23]
(003) jeq      #0x6             jt 4	jf 10
(004) ldh      [20]
(005) jset     #0x1fff          jt 10	jf 6
(006) ldxb     4*([14]&0xf)
(007) ldh      [x + 16]
(008) jeq      #0x16            jt 9	jf 10
(009) ret      #262144
(010) ret      #0

Offsets are bytes from the start of the Ethernet frame. The Ethernet header is 14 bytes (6 destination MAC, 6 source MAC, 2 EtherType), so the IP header starts at byte 14. Instruction by instruction:

#InstructionMeaning
000ldh [12]Load the 16-bit half-word at offset 12, the EtherType, into A. Loads convert from network to host byte order.
001jeq #0x800 jt 2 jf 10Is it IPv4 (0x0800)? If yes go to 2, otherwise to 10 (reject).
002ldb [23]Load one byte at 14 + 9 = 23: the IP protocol field.
003jeq #0x6 jt 4 jf 10Protocol 6 is TCP. Not TCP: reject.
004ldh [20]Load 14 + 6 = 20: the IP flags and the 13-bit fragment offset.
005jset #0x1fff jt 10 jf 6jset tests A & k. A non-zero fragment offset means a later fragment that carries no TCP header, so reject it.
006ldxb 4*([14]&0xf)The special "MSH" addressing mode from the 1993 paper: X = 4 × (low nibble of byte 14), the IP header length in bytes (usually 20, more with IP options).
007ldh [x + 16]Indirect load at X + 16 = 14 (Ethernet) + IHL + 2, the TCP destination port. This is why X exists: the TCP header has a variable offset.
008jeq #0x16 jt 9 jf 10Port 0x16 = 22?
009ret #262144Accept and keep up to 262144 bytes (tcpdump's default snap length).
010ret #0Reject: keep 0 bytes.

Instructions 006–007 are almost exactly the header-parsing example in section 3.5 of the 1993 paper (ldx 4*([14]&0xf), ldh [x+16]). Thirty years later libpcap still emits the same idiom. The same program as raw instructions, which is what the kernel actually receives:

$ tcpdump -dd -y EN10MB 'ip and tcp dst port 22'
{ 0x28, 0, 0, 0x0000000c },
{ 0x15, 0, 8, 0x00000800 },
{ 0x30, 0, 0, 0x00000017 },
{ 0x15, 0, 6, 0x00000006 },
{ 0x28, 0, 0, 0x00000014 },
{ 0x45, 4, 0, 0x00001fff },
{ 0xb1, 0, 0, 0x0000000e },
{ 0x48, 0, 0, 0x00000010 },
{ 0x15, 0, 1, 0x00000016 },
{ 0x6, 0, 0, 0x00040000 },
{ 0x6, 0, 0, 0x00000000 },

Each line is one struct sock_filter {code, jt, jf, k}. In the raw form the jumps are relative: instruction 1 has jf = 8, meaning "skip 8 instructions after the next one", which is 1 + 1 + 8 = 10. The -d listing just prints the resolved targets. Opcode 0x28 is BPF_LD|BPF_H|BPF_ABS, 0x15 is BPF_JMP|BPF_JEQ|BPF_K, and 0x06 is BPF_RET|BPF_K.

Classic BPF in Linux: socket filters, a JIT, and seccomp

Linux Socket Filter

Linux adopted the BSD design under the name Linux Socket Filtering (LSF). The kernel documentation says it plainly: "LSF follows exactly the same filter code structure as BSD's BPF, so referring to the BSD bpf.4 manpage is very helpful in creating filters." Linux attaches the filter to a socket instead of to a /dev/bpf device as BSD does. LWN credits Jay Schulist with adding BPF support to Linux and notes that for years afterwards the interpreter "has been relatively static, seeing only a few performance tweaks and the addition of a few instructions for access to packet data" (LWN, 2014). Linux also added "BPF extensions": magic negative load offsets that return metadata such as the interface index, the VLAN tag or a random number. The kernel docs show ld ifidx, ld vlan_tci and ld rand. Do not confuse these with extended BPF; the docs warn about that too.

A JIT for packet filters (Linux 3.0)

In 2011 Eric Dumazet added a just-in-time compiler that translated classic BPF directly to x86-64 machine code, in Linux 3.0 (LWN, "A JIT for packet filters"). Because the BPF machine is so simple, "every BPF instruction maps to a straightforward x86 instruction sequence". That first JIT was hard-wired to x86-64. The idea that a checked program could be compiled to native code and still be safe is the second ingredient of modern eBPF.

seccomp-bpf (Linux 3.5): BPF beyond networking

The first big use of BPF outside networking was system-call filtering. The original seccomp mode (Linux 2.6.12) was all-or-nothing: a process could switch into a state where only read, write, exit and sigreturn were allowed. Sandboxes such as Chrome's needed something more flexible. After several rejected designs, Will Drewry proposed reusing the packet filter (LWN, January 2012): instead of a packet, the BPF program reads a struct seccomp_data holding the system-call number, the architecture and the arguments, and its return value says what to do: allow, return an errno, send a signal, kill the process, and so on. As one LWN commenter put it, "BPF is nice because it is trivial to verify and does not allow backwards branches." The feature shipped in Linux 3.5, released 21 July 2012, and kernelnewbies notes that Chromium already used it to sandbox plugins (kernelnewbies, Linux 3.5).

The kernel's own sample, written by Will Drewry, shows a complete seccomp-bpf filter built with the BPF_STMT and BPF_JUMP macros from filter.h:

static int install_filter(int arch, int nr, int error)
{
	struct sock_filter filter[] = {
		BPF_STMT(BPF_LD+BPF_W+BPF_ABS,
			 (offsetof(struct seccomp_data, arch))),
		BPF_JUMP(BPF_JMP+BPF_JEQ+BPF_K, arch, 0, 3),
		BPF_STMT(BPF_LD+BPF_W+BPF_ABS,
			 (offsetof(struct seccomp_data, nr))),
		BPF_JUMP(BPF_JMP+BPF_JEQ+BPF_K, nr, 0, 1),
		BPF_STMT(BPF_RET+BPF_K,
			 SECCOMP_RET_ERRNO|(error & SECCOMP_RET_DATA)),
		BPF_STMT(BPF_RET+BPF_K, SECCOMP_RET_ALLOW),
	};
	struct sock_fprog prog = {
		.len = (unsigned short)(sizeof(filter)/sizeof(filter[0])),
		.filter = filter,
	};
	/* ... */
	if (prctl(PR_SET_NO_NEW_PRIVS, 1, 0, 0, 0)) {
		perror("prctl(NO_NEW_PRIVS)");
		return 1;
	}
	if (prctl(PR_SET_SECCOMP, 2, &prog)) {
		perror("prctl(PR_SET_SECCOMP)");
		return 1;
	}
	return 0;
}

Read it as a CFG: load arch; if it is not the expected architecture, jump 3 ahead to ALLOW (this sample only filters calls for the given ABI); load the syscall number nr; if it matches, return SECCOMP_RET_ERRNO with the chosen errno, otherwise allow. The PR_SET_NO_NEW_PRIVS call is required (unless the caller has CAP_SYS_ADMIN) so that a filter can never be imposed on a more privileged program, such as a setuid binary, run by the filtered task (seccomp_filter docs). The 2 passed to prctl is SECCOMP_MODE_FILTER.

Still classic

seccomp filters are still written in classic BPF today: the API takes a struct sock_fprog. Internally the kernel converts them to eBPF before running them, like all classic programs (see below). Tools like Docker's default seccomp profile or systemd's SystemCallFilter= generate such programs for you, usually through libseccomp.

2014: extended BPF

Why classic BPF hit a wall

By 2013 the kernel used BPF for socket filters, seccomp, the cls_bpf traffic classifier, netfilter's xt_bpf, the team driver and the PTP classifier. But the machine was still the 1992 design: two 32-bit registers, no function calls, 16 scratch words. As Matt Fleming summarised in LWN, "the design of the virtual machine and its instruction set architecture (ISA) were left behind as modern processors moved to 64-bit registers and invented new instructions required for multiprocessor systems, like the atomic exchange-and-add instruction" (LWN, "A thorough introduction to eBPF", 2017). Every 64-bit value had to be split into halves, and the JIT could not map the abstract machine well onto CPUs with 16 or 31 general-purpose registers.

The rewrite (Linux 3.15)

Alexei Starovoitov's commit bd4cf0ed331a "net: filter: rework/optimize internal BPF interpreter's instruction set", which closes with "Joint work with Daniel Borkmann", replaced the kernel's interpreter with a new instruction set "modelled closer to mimic native instruction sets and ... designed to be JITed with one to one mapping". Its commit message lists the changes:

  • number of registers increases from 2 to 10;
  • register width increases from 32-bit to 64-bit;
  • conditional jt/jf targets replaced with jt/fall-through (better for CPU branch predictors);
  • adds signed > and >=, arithmetic right shift, endianness conversion;
  • 16 4-byte scratch slots replaced with up to 512 bytes of stack;
  • a bpf_call instruction and a register-passing convention "for zero overhead calls from/to other kernel functions";
  • an atomic add instruction; tax/txa replaced with a general mov.

The key compatibility trick: user space kept loading classic programs, and the kernel translated them into the new format before running them. tcpdump, seccomp and cls_bpf got faster without changing a line. LWN called this "internal BPF" at first ("BPF: the universal in-kernel virtual machine"); the name that stuck is eBPF. The x86-64 JIT was ported to the new instruction set in 3.16.

The new instruction, as defined today in the kernel's UAPI header, is still 64 bits, but laid out for a register machine:

enum {
	BPF_REG_0 = 0,
	BPF_REG_1,
	BPF_REG_2,
	BPF_REG_3,
	BPF_REG_4,
	BPF_REG_5,
	BPF_REG_6,
	BPF_REG_7,
	BPF_REG_8,
	BPF_REG_9,
	BPF_REG_10,
	__MAX_BPF_REG,
};

/* BPF has 10 general purpose 64-bit registers and stack frame. */
#define MAX_BPF_REG	__MAX_BPF_REG

struct bpf_insn {
	__u8	code;		/* opcode */
	__u8	dst_reg:4;	/* dest register */
	__u8	src_reg:4;	/* source register */
	__s16	off;		/* signed offset */
	__s32	imm;		/* signed immediate constant */
};

Compare it with struct sock_filter above: the 16-bit opcode and two 8-bit jump targets became an 8-bit opcode, two 4-bit register numbers and a signed 16-bit offset. R0 holds return values, R1–R5 carry function arguments, R6–R9 are callee-saved, and R10 is a read-only frame pointer. That mirrors the C calling convention of x86-64 and arm64, so a call from BPF to a kernel function needs no argument shuffling. Chapter 02 covers the ISA in detail.

Opening it to user space: bpf() and maps (Linux 3.18)

In 3.15 eBPF was internal: only the kernel produced it. The next step was to let user space load eBPF programs directly. That meant the instruction set would become ABI and could never change incompatibly again. LWN's Jonathan Corbet pointed this out in July 2014 ("Extending extended BPF"). The patch set added three things that define eBPF to this day:

  • The bpf() system call, a single multiplexer: int bpf(int cmd, union bpf_attr *attr, unsigned int size);. Commands include BPF_PROG_LOAD, BPF_MAP_CREATE, BPF_MAP_LOOKUP_ELEM and BPF_MAP_UPDATE_ELEM. The union-plus-size design, suggested by Ingo Molnar, lets new fields be added later; unused fields must be zero (LWN, "The BPF system call API, version 14").
  • Maps: kernel-resident key/value stores, each referenced by a file descriptor. A BPF program updates a map when an event fires; user space reads the map with bpf(). Maps are how state survives between program runs and how results reach user space.
  • The verifier, the largest part of the patch set: a static analyser that simulates the program, tracks the type and range of every register, and rejects anything that might read uninitialised registers, access memory out of bounds, or fail to terminate.

The series was accepted into net-next in late September 2014 and shipped in Linux 3.18. The bcc project's feature table lists the bpf() syscall and maps under 3.18 (commit 99c55f7d47c0), attaching eBPF to sockets plus hash and array maps under 3.19, and kprobes and the tc classifier under 4.1 (bcc kernel-versions.md).

How eBPF works: the lifecycle of a program

Every eBPF program, whether it comes from bpftrace, bcc, libbpf, cilium/ebpf or Aya, goes through the same pipeline. Learn this picture once; the rest of the curriculum fills in each box.

Step through what happens, with the real artifacts we will produce in the hello-world section:

1. Write the program in restricted C

A BPF program is a C function placed in an ELF section whose name tells the loader where to attach it, for example SEC("tp/syscalls/sys_enter_write"). "Restricted" means: no unbounded loops, no recursion, no arbitrary pointers, no libc, a 512-byte stack, and only kernel functions exposed as helpers or kfuncs. The program also declares a license string; helpers marked GPL-only require a GPL-compatible license.

2. Compile with clang -target bpf

LLVM has a BPF back end; GCC has one too. clang -g -O2 -target bpf -c hello.bpf.c -o hello.bpf.o produces BPF bytecode instead of x86 code. -g matters: it makes clang emit BTF, the compact type information the kernel and libbpf use for CO-RE relocations and readable verifier logs.

3. The ELF object

The .o file is an ordinary ELF relocatable file ("ELF 64-bit LSB relocatable, eBPF"). Each program is a code section. Global variables live in .bss/.data/.rodata, which libbpf turns into array maps. Map definitions live in .maps, and type information in .BTF and .BTF.ext. References to maps are still relocations at this point.

4. The loader prepares and calls bpf()

A loader library such as libbpf parses the ELF, creates the maps with BPF_MAP_CREATE, patches each map reference in the bytecode with the new map's file descriptor, applies CO-RE relocations against the running kernel's BTF (/sys/kernel/btf/vmlinux), and finally calls bpf(BPF_PROG_LOAD, …) with the instructions, program type, license and BTF.

5. The verifier

The kernel walks every possible path through the program, tracking each register's type (scalar, pointer to context, pointer to map value, pointer that may be NULL, …) and value range. It rejects out-of-bounds or unchecked memory accesses, reads of uninitialised registers, calls to helpers the program type may not use, and programs it cannot prove will terminate. Its complexity limit is one million processed instructions. If it fails, bpf() returns an error and a log explaining why. See chapter 03.

6. JIT compilation

The verified bytecode, after the kernel has rewritten some instructions (for example, helper IDs become real call addresses), is translated into native instructions. Because the ISA was designed to map one-to-one onto 64-bit CPUs, the result runs at close to the speed of compiled kernel C. Without a JIT the kernel falls back to its interpreter.

7. Attach to a hook

Loading only gives you a program file descriptor. Attaching connects it to an event: a tracepoint, a kprobe, an fentry hook, a network device (XDP), a tc qdisc, a cgroup, an LSM hook, a socket. Modern APIs return a BPF link, another file descriptor whose lifetime controls the attachment. Objects can be pinned in the BPF filesystem (/sys/fs/bpf) to outlive the loader process.

8–9. Run, and talk through maps

Each time the event fires, the kernel calls the program with a context pointer in R1. The program reads the context, calls helpers, updates maps, and returns a value whose meaning depends on the hook (drop or pass a packet, allow or deny an operation, or just 0 for tracing). User space reads the maps with bpf(BPF_MAP_LOOKUP_ELEM), by mmaping array maps, or by consuming a ring buffer.

"eBPF" vs "BPF": what the names mean today

The vocabulary is confusing because it changed while the technology grew:

  • BPF originally meant the Berkeley (or BSD) Packet Filter of 1993. In BSD it still means that: /dev/bpf and the classic instruction set.
  • cBPF / classic BPF is the retroactive name for the 1993-style instruction set. Linux still accepts it (socket filters, seccomp, SO_ATTACH_FILTER, xt_bpf) but converts it to eBPF internally. The kernel docs state that the new format "is being used for running user BPF programs, which includes seccomp BPF, classic socket filters, cls_bpf traffic classifier, ...", all of which are "internally converted by the kernel into the new instruction set representation".
  • eBPF / extended BPF is the 2014 instruction set and everything around it: verifier, maps, helpers, hooks, BTF.
  • BPF in Linux today almost always means eBPF. The syscall is bpf(), the source is in kernel/bpf/, the tool is bpftool, the mailing list is bpf@vger. The documentation lives at docs.kernel.org/bpf, and the IETF standard is titled "BPF Instruction Set Architecture".

ebpf.io puts it this way: "BPF originally stood for Berkeley Packet Filter, but now that eBPF (extended BPF) can do so much more than packet filtering, the acronym no longer makes sense. eBPF is now considered a standalone term that doesn't stand for anything. In the Linux source code, the term BPF persists, and in tooling and in documentation, the terms BPF and eBPF are generally used interchangeably." Brendan Gregg joked that it "should stand for something meaningful, like Virtual Kernel Instruction Set (VKIS)". This curriculum uses eBPF for the modern technology and classic BPF when it means the old instruction set.

Not only Linux any more

eBPF has spread beyond the Linux kernel: Microsoft's eBPF for Windows (built on the uBPF runtime and the PREVAIL verifier), user-space runtimes such as uBPF and bpftime (chapters 14–16), and offload to SmartNICs. RFC 9669 exists precisely so that these implementations agree on the instruction set. "BPF" in a paper title may therefore not mean "the Linux kernel".

#include <linux/bpf.h>
#include <bpf/bpf_helpers.h>

char LICENSE[] SEC("license") = "Dual BSD/GPL";

int my_pid = 0;

SEC("tp/syscalls/sys_enter_write")
int handle_tp(void *ctx)
{
	int pid = bpf_get_current_pid_tgid() >> 32;

	if (pid != my_pid)
		return 0;

	bpf_printk("BPF triggered from PID %d.\n", pid);

	return 0;
}
#include <bpf/libbpf.h>
#include "minimal.skel.h"
/* ... */
int main(int argc, char **argv)
{
	struct minimal_bpf *skel;
	int err;
	/* ... */
	/* Open BPF application */
	skel = minimal_bpf__open();
	if (!skel) {
		fprintf(stderr, "Failed to open BPF skeleton\n");
		return 1;
	}

	/* ensure BPF program only handles write() syscalls from our process */
	skel->bss->my_pid = getpid();

	/* Load & verify BPF programs */
	err = minimal_bpf__load(skel);
	/* ... */
	/* Attach tracepoint handler */
	err = minimal_bpf__attach(skel);
	/* ... */
	for (;;) {
		/* trigger our BPF program */
		fprintf(stderr, ".");
		sleep(1);
	}

cleanup:
	minimal_bpf__destroy(skel);
	return -err;
}

bpftrace is the fastest way in. Its language is "inspired by awk, C, and predecessor tracers such as DTrace and SystemTap" (ebpf.io), and bpftrace compiles each script to BPF bytecode with LLVM, loads it, attaches it and prints the maps when it exits. BEGIN is a special probe that fires once at start. In the second one-liner, @[comm] = count() is a BPF hash map keyed by process name. The kernel-side program increments a counter on every system call, and bpftrace prints the map at exit. Nothing is copied to user space per event; only the final totals are. That is the same "filter and aggregate in place" idea as the 1993 paper. The commonly shown tracepoint:syscalls:sys_enter_openat example needs the per-syscall tracepoints (CONFIG_FTRACE_SYSCALLS), which the kernel used here did not have. That is a small reminder that available hooks depend on kernel configuration.

libbpf is the C library maintained in the kernel tree (tools/lib/bpf) and mirrored at github.com/libbpf/libbpf. libbpf-bootstrap's minimal example is the smallest realistic program. The kernel side attaches to the sys_enter_write tracepoint, gets the current process ID from a helper, compares it with a global variable, and prints with bpf_printk into the kernel trace pipe. The user side uses a generated skeleton (minimal.skel.h, produced by bpftool gen skeleton) whose open / load / attach / destroy functions map directly onto steps 3–7 of the lifecycle. Note skel->bss->my_pid = getpid();: user space writes a BPF global variable before loading. Under the hood that global is an element of an array map. Chapter 06 explains skeletons, and chapter 11 covers eunomia-bpf's starter templates built on this layout.

Look inside: bytecode, bpftool and the verifier

To see the artifacts from the lifecycle diagram, compile the same minimal.bpf.c by hand and load it with bpftool (on Debian the extra -I was needed so clang finds asm/types.h):

$ clang -g -O2 -target bpf -D__TARGET_ARCH_x86 -I/usr/include/x86_64-linux-gnu \

$ llvm-objdump -d --no-show-raw-insn minimal.bpf.o

0000000000000000 <handle_tp>:
       0:	call 14
       1:	r0 >>= 32
       2:	r1 = 0 ll
       4:	r1 = *(u32 *)(r1 + 0)
       5:	if r1 != r0 goto +5 <LBB0_2>
       6:	r1 = 0 ll

0000000000000058 <LBB0_2>:

Thirteen instruction slots. call 14 is helper number 14, bpf_get_current_pid_tgid, which returns its result in R0. r0 >>= 32 keeps the upper half (the process ID, "tgid"). r1 = 0 ll is the 16-byte wide instruction that loads a 64-bit constant; here it is a placeholder relocation that will point at my_pid in the .bss map. Instructions 6–10 set up the three arguments of helper 6, bpf_trace_printk (format string, its length 28, the pid), and the program returns 0 in R0. The object's section list shows the rest of the ELF anatomy: tp/syscalls/sys_enter_write, license, .bss, .rodata (the format string), .BTF, .BTF.ext and DWARF debug sections.

Several lifecycle steps are visible here. The libbpf inside bpftool created two array maps from .bss and .rodata (IDs 9 and 10) and patched the placeholder loads into map[id:9] and map[id:10]. The kernel rewrote helper numbers into internal call targets (#172016). The source lines interleaved in the dump come from the BTF line info. "xlated" means the program after the verifier's rewrites. On the kernel used here the JIT was not enabled, so it reports not jited and runs in the interpreter. With the JIT enabled, bpftool also reports a jited size and bpftool prog dump jited shows native instructions. bpftool prog load loads and pins but does not attach; a skeleton's __attach() does that.

Finally, the most important behaviour of eBPF: refusing bad code. The program below is illustrative, not from a repository. It forgets that a map lookup can return NULL:

/* Illustrative example written for this chapter: the verifier must reject it. */
struct {
	__uint(type, BPF_MAP_TYPE_HASH);
	__uint(max_entries, 1);
	__type(key, __u32);
	__type(value, __u64);
} counts SEC(".maps");

SEC("tp/syscalls/sys_enter_write")
int bad(void *ctx)
{
	__u32 key = 0;
	__u64 *val = bpf_map_lookup_elem(&counts, &key);
	*val += 1;            /* BUG: val may be NULL */
	return 0;
}
char LICENSE[] SEC("license") = "GPL";
$ sudo bpftool prog load bad.bpf.o /sys/fs/bpf/bad
libbpf: prog 'bad': BPF program load failed: Permission denied
libbpf: prog 'bad': -- BEGIN PROG LOAD LOG --
...
; __u64 *val = bpf_map_lookup_elem(&counts, &key);
4: (18) r1 = 0xffff888103112c00       ; R1_w=map_ptr(off=0,ks=4,vs=8,imm=0)
6: (85) call bpf_map_lookup_elem#1    ; R0_w=map_value_or_null(id=1,off=0,ks=4,vs=8,imm=0)
; *val += 1;            /* BUG: val may be NULL */
7: (79) r1 = *(u64 *)(r0 +0)
R0 invalid mem access 'map_value_or_null'
processed 7 insns (limit 1000000) max_states_per_insn 0 total_states 0 peak_states 0 mark_read 0
-- END PROG LOAD LOG --
libbpf: prog 'bad': failed to load: -13

The verifier tracked that after call bpf_map_lookup_elem, R0 has type map_value_or_null, and a dereference of a maybe-NULL pointer is not allowed. The load fails with -13 (EACCES) before the program ever runs. A kernel module with the same bug would have compiled, loaded and crashed the first time the key was missing. Adding if (!val) return 0; makes the verifier narrow R0 to map_value on the fall-through path, and the program loads. Fighting and understanding such messages is a big part of eBPF development; chapter 03 explains the analysis, and chapter 17 looks at tools that explain verifier errors.

"JavaScript for the kernel": the analogy and its limits

The most quoted one-line explanation of eBPF comes from Brendan Gregg's 2019 tutorial: "eBPF does to Linux what JavaScript does to HTML. (Sort of.) So instead of a static HTML website, JavaScript lets you define mini programs that run on events like mouse clicks, which are run in a safe virtual machine in the browser. And with eBPF, instead of a fixed kernel, you can now write mini programs that run on events like disk I/O, which are run in a safe virtual machine in the kernel." He immediately qualifies it: "In reality, eBPF is more like the v8 virtual machine that runs JavaScript, rather than JavaScript itself." (Learn eBPF Tracing).

ebpf.io develops the same analogy along three axes: safety (untrusted code is sandboxed; eBPF's counterpart is the verifier), continuous delivery (new logic without shipping a new browser; for eBPF, new logic without a new kernel), and performance (a JIT in both cases). Where the analogy works:

  • Event-driven. Programs do not run on their own; they are callbacks on hooks, like onclick handlers.
  • The host stays in charge. A program can only use the APIs the host exposes for that event (helpers and kfuncs per program type, like the DOM API per page).
  • Frameworks on top. As Gregg notes, nobody writes v8 bytecode; people use JavaScript and frameworks. Likewise, few people write eBPF assembly; they use bpftrace, bcc, libbpf, Cilium or Tetragon (chapter 08).
  • It is a new kind of software. In "BPF: A New Type of Software" Gregg reports that Netflix ran 15 BPF programs on cloud servers by default and Facebook 40, programs that "are not processes or kernel modules, and don't appear in traditional observability tools" (2019).

Where it breaks, and these differences matter in practice:

  • It is not a general-purpose VM. The kernel's own BPF Design Q&A answers "Is BPF a generic virtual machine?" with "NO", and describes BPF as a "generic instruction set with C calling convention" (docs.kernel.org/bpf/bpf_design_QA). There is no garbage collector, no dynamic code, no exceptions in the JavaScript sense. Programs are short, bounded C-like functions. Five arguments maximum, one return value, 512 bytes of stack.
  • Safety is proven ahead of time, not enforced at runtime. A JavaScript engine can stop a runaway script. The kernel cannot afford that inside an interrupt handler, so the verifier must prove up front that the program terminates and touches only valid memory. The price is that correct programs are sometimes rejected because the verifier cannot prove them safe, and the only way to know is to load the program (Design Q&A: "The only way to know that the program is going to be accepted by the verifier is to try to load it").
  • The sandbox protects the kernel, not your secrets. Tracing programs can read arbitrary kernel memory with bpf_probe_read_kernel(), and see every process's arguments. Loading them is therefore a root-level privilege (CAP_BPF, CAP_PERFMON, CAP_NET_ADMIN or CAP_SYS_ADMIN depending on the program type), not something you hand to web visitors. Kernels have a kernel.unprivileged_bpf_disabled sysctl, and the BPF_UNPRIV_DEFAULT_OFF config option makes unprivileged bpf() disabled by default (sysctl docs).
  • The "web platform" is not stable everywhere. The instruction set, helper functions and program context types are stable ABI. But kprobe attachment points and tracepoints are explicitly not ABI, nor are kfuncs or the kernel's internal structs your program reads. Tracing programs can break when the kernel changes, which is why BTF and CO-RE exist (Design Q&A).
  • It runs in the most privileged context there is. A JIT or verifier bug is a kernel bug. The kernel hardens the JIT (constant blinding since 4.7 per the bcc table, and BPF_JIT_ALWAYS_ON as a Spectre mitigation), but "verified" is a strong engineering guarantee, not a formal proof of the whole system. Research on verifying the verifier is the topic of chapters 03 and 18.

Why not just write a kernel module or a kernel patch?

Before eBPF, "I need custom logic in the kernel" had two answers. ebpf.io summarises the costs: for a kernel change you must "convince the Linux kernel community that the change is required" and then "wait several years for the new kernel version to become a commodity". For a module you must "fix it up regularly, as every kernel release may break it" and "risk corrupting your Linux kernel due to lack of security boundaries" (ebpf.io). Side by side:

Kernel patch

Safest once merged and reviewed, fully general. But it needs upstream agreement that the feature belongs in everyone's kernel, then years to reach distribution and enterprise kernels. Changing your mind means another patch cycle.

Loadable kernel module

Runs arbitrary C with full privileges. One NULL dereference or use-after-free oopses or silently corrupts the kernel. No stable in-kernel API, so modules are rebuilt for each kernel version and break with internal changes. Often needs the kernel headers on every machine. Loading is frequently restricted (Secure Boot, module signing).

eBPF program

Restricted, but verified before it runs: it cannot crash the kernel or hang it. Loaded and unloaded at runtime without reboot. With BTF/CO-RE one binary runs on many kernel versions. Uses only the hooks, helpers and kfuncs the kernel exposes, so some things are simply not possible.

The two properties that made eBPF win in production are safety and upgradability. Safety means operators can deploy monitoring or a firewall rule to a fleet without fearing a kernel panic on some machines; the worst case is that the load is rejected. Upgradability means the logic ships with the application, not with the kernel: Cilium can release a new datapath every few weeks on top of whatever kernel the cluster runs, and a performance engineer can write a bpftrace script during an incident and remove it ten minutes later.

Modules are not dead, and the relationship is no longer either-or. The Design Q&A explains that modules cannot add core BPF functionality (program types, maps, helpers) but "can expose functionality to BPF programs by exporting kfuncs". If you need a new primitive, such as a driver-specific operation, a small kernel change can expose it as a kfunc, and the policy that uses it lives in BPF. That split, mechanism in the kernel and policy in BPF, is the design behind sched_ext, BPF LSM and much of the research in later parts of this curriculum (for example gpu_ext and namei_ext).

Benefits, limitations and related work

Benefits

  • Safe by construction: verified before execution; no kernel crash from a buggy program.
  • Fast: JIT to native code, runs in the context of the event, and aggregates in the kernel so only results cross to user space.
  • Dynamic: load, replace and unload at runtime, with no reboot and no module build.
  • Portable across kernel versions with BTF/CO-RE, and to some extent across operating systems through RFC 9669.
  • Broad reach: networking, tracing, security, scheduling, with one toolchain.

Limitations

  • Expressiveness: bounded execution, a small stack, limited calls, a complexity limit; some algorithms are awkward or impossible.
  • The verifier is conservative, and its acceptance can change with compiler versions and optimisation choices, so error messages are a common pain.
  • Kernel-version dependence: features arrive release by release, so a program written for 6.x may not load on an older enterprise kernel (chapter 13 addresses this).
  • Privilege: most useful program types need root-equivalent capabilities.
  • Attack surface: the verifier and JIT are complex kernel code; bugs there are kernel security bugs.

Related work

  • Predecessors: CSPF (stack-based filters) and NNStat (the first CFG-style filters), both cited by the 1993 paper; Sun's NIT.
  • Other kernel-extension approaches: loadable modules; SystemTap and DTrace for tracing (bpftrace's language borrows from both); netfilter/iptables for fixed packet-processing pipelines.
  • Other runtimes for the same ISA: uBPF, eBPF for Windows (uBPF + PREVAIL), and the user-space runtimes and compilers in Part III (bpftime, llvmbpf), and WebAssembly-hosted eBPF apps (wasm-bpf).

Check your understanding

Q1. Why did McCanne and Jacobson choose a register-based machine for BPF instead of CSPF's stack machine?

The paper argues the stack model "worked well on the PDP-11 but is a poor match to memory-bottlenecked modern CPUs". It also switched from expression trees to a control-flow graph so each packet field is parsed only once.

Q2. In the tcpdump program, what does ldxb 4*([14]&0xf) do?

Byte 14 is the first byte of the IP header; its low nibble is the header length in 32-bit words. The next instruction, ldh [x + 16], reads the TCP destination port.

Q3. What happens today when tcpdump or a seccomp sandbox loads a classic BPF program on Linux?

Since 3.15 classic programs (socket filters, seccomp, cls_bpf, xt_bpf …) are converted internally into the eBPF format. The classic API (struct sock_fprog) remains for compatibility.

Q4. Which of these was not part of the 2014 move from classic to extended BPF?

eBPF has a 512-byte stack and maps, and no garbage collector. The Design Q&A explicitly says BPF is not a generic virtual machine.

Q5. The verifier rejected a program with R0 invalid mem access 'map_value_or_null'. What is the fix?

A lookup returns NULL when the key is missing. After if (!val) return 0; the verifier knows R0 is a valid map_value pointer on the other path and accepts the load.

Q6. Why is an eBPF tracing program usually easier to deploy across a fleet than a kernel module doing the same job?

eBPF runs in the kernel but is checked first. Kprobe and tracepoint locations are explicitly not stable ABI, which is why CO-RE exists. Loading tracing programs still requires privileges.
