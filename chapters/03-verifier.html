Chapter 03

The eBPF verifier

The kernel runs your eBPF program only after the verifier has proved it safe. How does a static analyzer inside the kernel prove that arbitrary bytecode will not crash the machine, read memory it should not, or run forever? And why does it sometimes reject code that looks fine to you?

Prerequisites: 01, 02Source: kernel/bpf/ at Linux master d68ce4e7 (2026-11-05)~60 min

Why this matters

An eBPF program is code that someone outside the kernel hands to the kernel, and the kernel then runs with full kernel privilege: in the network receive path, on every system call, inside the scheduler. A kernel module can do the same, but a module is trusted. If it dereferences a bad pointer the machine panics, and if it leaks a kernel address that is a security bug. eBPF's promise is that you can load new code into a running production kernel without making the kernel any less safe. The verifier is what keeps that promise. It is a static analyzer in kernel/bpf/ that runs on every BPF_PROG_LOAD and either accepts the program or refuses it with an error log.

A kernel could protect itself in three ways. It could trust the author, as with modules. It could check every memory access at run time, as a software sandbox or a WebAssembly runtime does. Or it could prove before the first run that no bad access can ever happen, then run the code at native speed with no checks. eBPF mostly takes the third option. That choice explains almost everything that makes eBPF programming feel strange: you write if (!val) return 0; after every map lookup, and you compare packet pointers against data_end before every header access. These checks are how you hand the verifier the facts it needs for its proof.

The verifier does not have to be perfect, but it has to be sound. A program can be safe in fact and still be rejected; that is a false positive, and it is annoying. If an unsafe program is accepted, that is a soundness bug, and in practice a kernel vulnerability. Rice's theorem tells us that no analyzer can decide every safety property exactly, so the verifier errs on the side of rejection. This chapter shows where those approximations are and how to write code that survives them.

Key idea

The verifier is an abstract interpreter. It runs the program on abstract values instead of real ones. Each register holds a type (pointer to context, pointer to map value, pointer into the packet, plain number, and so on) and, for numbers, a set of possible values described by known bits (a tnum) and by signed and unsigned ranges. It walks every path through the program, and on each path it checks that every memory access, helper call and return is safe for all concrete values that the abstract state allows.

What the verifier guarantees, in the words of the kernel's own documentation and code comments, comes down to a list of properties:

  • Termination. The program reaches exit on every path within a bounded number of steps. Since Linux 5.3 loops are allowed when the verifier can prove they end.
  • Memory safety. Every load and store goes through a pointer of a known type, inside the bounds of the object it points to, and with acceptable alignment.
  • No uninitialised reads. A register that was never written is NOT_INIT and cannot be read. Stack bytes cannot be read before they are written, unless the loader has CAP_PERFMON.
  • Type-correct calls. Every helper and kfunc is called with arguments whose types match its prototype. For example, bpf_map_lookup_elem() needs a map pointer and a pointer to initialised stack memory of at least key_size bytes.
  • Resource safety. References acquired from the kernel, such as sockets, ring buffer reservations or task references, are released on every path, and locks are unlocked (the acquire/release APIs are covered in Chapter 04).
  • No pointer leaks for unprivileged users. A program loaded without CAP_PERFMON cannot store a kernel pointer into a map, compare pointers in ways that reveal addresses, or return one.

Where the verifier sits

The entry point is bpf_check() in kernel/bpf/verifier.c, called from bpf_prog_load() in kernel/bpf/syscall.c. It receives the program's instructions, the attach type, the BTF information that libbpf passed along (see Chapter 06), and an optional user buffer for the verifier log. When it returns 0, the program is rewritten (context accesses converted, helper calls patched, Spectre masks inserted) and handed to the JIT described in Chapter 02.

Pass 1: the control-flow graph check

The first pass never looks at values. It treats the program as a directed graph: each instruction is a node, and edges go to the next instruction and to jump targets. A non-recursive depth-first search (bpf_check_cfg()) labels each node discovered when it is pushed and explored when all its successors are done. During the walk it rejects:

  • jumps outside the program (jump out of range from insn 3 to 99);
  • jumps into the second half of a 16-byte ld_imm64 instruction;
  • instructions that no path reaches (unreachable insn 7). Classic BPF allowed dead code, but eBPF does not, because an unverified island of code is a gadget waiting to be reached by a bug elsewhere;
  • a back-edge, which is an edge to a node that is still discovered (on the DFS stack). A back-edge means a loop. Since 5.3, back-edges are allowed for privileged loaders (CAP_SYS_ADMIN at first, CAP_BPF since 5.8), and the second pass then has to prove the loop terminates. Unprivileged programs must still be loop-free.
	if (insn_state[w] == 0) {

The same walk also records prune points and jump points: jump targets and the instructions after calls are marked with mark_prune_point(). Pass 2 saves states for pruning only at these points, so this cheap graph pass decides where the expensive pass may stop early.

Pass 2: path-by-path symbolic execution

The second pass, do_check(), is where the real work happens. It starts at instruction 0 with an initial state: R1 holds a pointer to the program's context (type PTR_TO_CTX), R10 is the read-only frame pointer, and every other register is NOT_INIT. Then it steps through instructions one at a time. For each one it checks that the operation is legal on the current abstract state and computes the next state:

  • An ALU instruction updates the destination's type and value bounds. Pointer plus constant stays a pointer with a larger offset. Arithmetic between two pointers is rejected (R1 pointer += pointer prohibited), with one exception: pointer minus pointer becomes a plain scalar, and only for loaders allowed to leak pointers (CAP_PERFMON).
  • A load or store is checked against the base register's type. A context access is checked by the program type's is_valid_access() callback, a stack access against the 512-byte frame and the slot's initialisation state, a map-value access against value_size, a packet access against the proven range.
  • A call checks every argument register against the helper's prototype, then marks R1–R5 NOT_INIT (caller-saved) and sets R0 to the helper's return type.
  • A conditional jump is the interesting case. If the verifier can decide the outcome from the abstract values, for example if r0 > 10 when r0 is known to be at most 5, it follows only that branch (is_branch_taken()). Otherwise it copies the whole state, refines each copy with what the branch condition implies, follows the fall-through side, and pushes the other side on a stack (push_stack()) to explore later.
  • exit checks that R0 holds a legal return value for the program type and that no references are leaked. Then the verifier pops the next pending branch and continues from there.

When the stack is empty, every path has been checked and the program is accepted. This is path-sensitive analysis: unlike a classic compiler data-flow analysis, it does not merge states at join points by default. That makes it very precise; it knows that on this path r0 was NULL-checked. The price is a number of paths that is exponential in the number of branches. Pruning, covered below, is what makes this affordable.

Reading the state in a log line

With log_level 1 or 2, the verifier prints the state after each instruction. The notation is compact:

6: (85) call bpf_map_lookup_elem#1    ; R0_w=map_value_or_null(id=1,off=0,ks=4,vs=8,imm=0)
1: (63) *(u32 *)(r10 -4) = r1         ; R1_w=0 R10=fp0 fp-8=0000????
12: (25) if r0 > 0xf goto pc+5        ; R0_w=scalar(umax=15,var_off=(0x0; 0xf))
  • 6: is the instruction index, (85) the opcode byte, then the disassembly.
  • R0_w: the _w suffix means "written in the current state". Older logs also print _r and _rw; these are liveness marks.
  • id=1 ties together registers that hold copies of the same pointer or scalar, so that a check on one also refines the others.
  • ks/vs are the map's key and value sizes.
  • fp-8=0000???? describes the 8-byte stack slot at fp-8 byte by byte, highest address first: 0 is a known zero, ? is uninitialised, m is "misc" (written with unknown data), r would be a spilled register.
  • scalar(umax=15,var_off=(0x0; 0xf)) is a number with unsigned maximum 15 and known bits given as a tnum (value; mask). Bounds that are not interesting (for example umin=0) are left out.
  • P before a type (Pscalar()) marks a register as precise; see precision tracking.

Tracking numbers: tnums and ranges

Types alone cannot prove that array[i] is safe. For that the verifier must know something about the value of i. Every register of type SCALAR_VALUE, and the variable part of every pointer's offset, is described by two kinds of abstraction at once, kept in sync after every operation:

  1. a tnum ("tracked" or "tristate" number), which records which bits are known to be 0, known to be 1, or unknown;
  2. ranges: signed and unsigned minimum and maximum, each in a 64-bit and a 32-bit version. That is eight numbers: smin/smax, umin/umax, s32_min/s32_max, u32_min/u32_max.

Edward Cree introduced the current design in Linux 4.14 (2017, commits f1174f77b50c "bpf/verifier: rework value tracking" and b03c9f9fdc37 "bpf/verifier: track signed and unsigned min/max values"). John Fastabend added explicit 32-bit bounds in 2020 (3f50f132d840), because BPF has 32-bit ALU instructions (w0 += 1) whose results wrap at 232 and are then zero-extended.

Tristate numbers

A tnum is two 64-bit words. A bit set in mask is unknown; where mask is 0, the bit's value is given by value. The invariant is value & mask == 0.

/* tnum: tracked (or tristate) numbers
 *
 * A tnum tracks knowledge about the bits of a value.  Each bit can be either
 * known (0 or 1), or unknown (x).  Arithmetic operations on tnums will
 * propagate the unknown bits such that the tnum result represents all the
 * possible results for possible values of the operands.
 */
/* ... */
struct tnum {
	u64 value;
	u64 mask;
};

Bitwise operations are easy to define on tnums. AND, for instance, gives a known 0 wherever either input has a known 0. Shifts by a constant move both words. Addition is the clever one, because carries can turn known bits into unknown bits. The kernel's version runs in constant time with no loop over bits:

struct tnum tnum_add(struct tnum a, struct tnum b)
{
	u64 sm, sv, sigma, chi, mu;

	sm = a.mask + b.mask;
	sv = a.value + b.value;
	sigma = sm + sv;
	chi = sigma ^ sv;
	mu = chi | a.mask | b.mask;
	return TNUM(sv & ~mu, mu);
}

sv is the sum with every unknown bit taken as 0; sigma is the sum with every unknown bit taken as 1. Any bit where those two extremes differ (chi) might have been reached by a carry, so it becomes unknown. Bits unknown in either input stay unknown.

A worked tnum example. Let a = 0b1xx, so the value is one of 4, 5, 6 or 7 (value=0b100, mask=0b011), and add the constant b = 1:

sm    = 0b011 + 0b000          = 0b0011
sv    = 0b100 + 0b001          = 0b0101
sigma = sm + sv                = 0b1000
chi   = sigma ^ sv             = 0b1101
mu    = chi | 0b011 | 0b000    = 0b1111
result: value = sv & ~mu = 0,  mask = 0b1111   →  "xxxx" (any of 0..15)

The true results are {5, 6, 7, 8}. The tnum xxxx is the smallest tnum that contains all four (the CGO 2022 paper below proves that tnum_add is optimal in this sense), yet it also contains 0 and 15. That is why the verifier does not rely on tnums alone. The interval domain computes umin = 4+1 = 5, umax = 7+1 = 8 for the same addition, and the two domains then tighten each other. In the other direction, tnums are better at bit-level facts that intervals cannot express. After x &= 0xf0, an interval says "0 to 240", while the tnum says "a multiple of 16 that is at most 240", and the alignment check needs exactly that.

Signed and unsigned, 64-bit and 32-bit ranges

Why keep both signed and unsigned bounds? Because BPF has both signed and unsigned comparisons (JSGT and JGT), and the same 64 bits mean very different things under each. The value 0xffff_ffff_ffff_fff0 is a huge unsigned number and the signed number −16. A bounds check written with a signed comparison, if ((s64)i < 64), teaches the verifier nothing about the unsigned range, because −16 passes it. This is the source of the error min value is negative, either use unsigned index or do a if (index >=0) check.

After every ALU operation and every branch, reg_bounds_sync() runs a small fixed sequence of reductions: derive bounds from the tnum, derive signed from unsigned and back, 32-bit from 64-bit and back, then tighten the tnum from the bounds. The CAV 2023 paper discussed below found that this reduction is what keeps the verifier sound even where single operators, taken alone, are not.

static void reg_bounds_sync(struct bpf_reg_state *reg)
{
	/* If the input reg_state is invalid, we can exit early */
	if (range_bounds_violation(reg))
		return;
	/* We might have learned new bounds from the var_off. */
	__update_reg_bounds(reg);
	/* We might have learned something about the sign bit. */
	__reg_deduce_bounds(reg);
	__reg_deduce_bounds(reg);
	/* We might have learned some bits from the bounds. */
	__reg_bound_offset(reg);
	/* Intersecting with the old var_off might have improved our bounds
	 * slightly, e.g. if umax was 0x7f...f and var_off was (0; 0xf...fc),
	 * then new var_off is (0; 0x7f...fc) which improves our umax.
	 */
	__update_reg_bounds(reg);
/* ... */
	__update_bounds_from_step(reg);
}
2026: circular numbers

If you read struct bpf_reg_state on current master you will not find the eight fields smin_value … u32_max_value. Since Linux v7.2 (commit 256f0071f9b6, Eduard Zingerman, April 2026) the ranges are stored as two circular numbers, struct cnum64 r64 and struct cnum32 r32. Each is a base and a size describing an arc on the wrap-around number circle, so a single value captures both the signed and the unsigned view. The commit message says the idea came from a post by Shung-Hsi Yu and the wrapped-intervals work of Navas et al., and that the operations were checked with the CBMC model checker. Code now reads bounds through accessors such as reg_umax(reg), the log still prints umax= and friends, and the model in this section still holds. Recent master also adds a base/step pair to describe values of the form base + k·step.

Branches refine bounds

A conditional jump is where most bounds come from. On the fall-through side of if r0 > 15 goto L, the verifier sets umax = min(umax, 15); on the taken side it sets umin = max(umin, 16). reg_bounds_sync() then converts the new umax=15 into the tnum (0x0; 0xf). If both operands are registers that share an id with other registers (because one was copied from another), the refinement is applied to all of them. For pointer comparisons against pkt_end the verifier records a packet range instead; more on that below.

Read it line by line:

  • 9. The helper returns a 64-bit scalar about which nothing is known: tnum (0; 0xffff…ffff), full ranges.
  • 10–11. Clang zero-extends the __u32 by shifting left and then right by 32. After the left shift the low 32 bits are known zeros, which you can see in the tnum mask 0xffffffff00000000 and in u32_max=0. After the logical right shift the high 32 bits are known zeros: umax=4294967295, tnum mask 0xffffffff.
  • 12. On the fall-through path of if r0 > 0xf, the verifier learns umax=15, and the reduction turns that into the tnum (0x0; 0xf): only the low four bits are unknown.
  • 13. r0 <<= 3 (×8, the element size) shifts the tnum to (0x0; 0x78), so the value is a multiple of 8 between 0 and 120.
  • 14–15. Adding the scalar to the map-value pointer moves the bounds into the pointer's variable offset. At the 8-byte load the verifier checks the worst case: off + umax + size = 0 + 120 + 8 = 128 ≤ vs = 128. The access is safe, and the tnum also shows it is 8-byte aligned.

NULL checks after a map lookup

bpf_map_lookup_elem() returns NULL when the key is absent. The verifier marks the result PTR_TO_MAP_VALUE | PTR_MAYBE_NULL and gives it a fresh id. The type forbids both dereference and pointer arithmetic, so the only useful things you can do with it are compare it with 0, copy it, or pass it to a helper that accepts NULL. When a comparison against 0 is seen, mark_ptr_or_null_regs() visits every register and spilled stack slot in all frames that carries the same id, and converts it either to a plain pointer (non-NULL branch) or to the scalar 0 (NULL branch):

				 struct bpf_reg_state *reg, u32 id,
				 bool is_null)
{
	if (type_may_be_null(reg->type) && reg->id == id &&
	    (is_rcu_reg(reg) || !WARN_ON_ONCE(!reg->id))) {
/* ... */
		if (is_null) {
			/* We don't need id from this point
			 * onwards anymore, thus we should better reset it,
			 * so that state pruning has chances to take effect.
			 */

		}

Two practical consequences follow. First, you cannot do pointer arithmetic before the check: p = lookup(...) + 8; if (!p) ... is rejected. CVE-2022-23222 was a bug in exactly this area: some *_OR_NULL types allowed arithmetic, and an attacker could turn a NULL into a non-NULL "valid" pointer. Second, compilers sometimes move the check somewhere the verifier cannot connect to the pointer, for example by testing a value derived from it. Keeping the check directly on the returned pointer avoids that.

Packet bounds: data and data_end

Networking programs (XDP, tc; see Chapter 07) read packet bytes directly through two pointers in the context: data (first byte) and data_end (one past the last). The packet length is only known at run time, so the verifier cannot check a packet access against a constant size as it does for map values. Instead it gives every PTR_TO_PACKET register a range r: the number of bytes after the packet start that this path has proven to exist. It starts at 0. The only way to grow it is to compare a packet pointer against pkt_end.

The function that applies a successful comparison is find_good_pkt_pointers(). Its comment lists the four comparison shapes the verifier recognises:

State pruning

Without pruning, a program with 30 independent ifs would need 230 paths. Pruning rests on one observation. If the verifier has already proven that, starting from instruction i in abstract state Sold, every continuation is safe, then any new state Scur at i that is contained in Sold (every concrete state it describes is also described by Sold) is safe too, and needs no further exploration.

bpf_is_state_visited() runs at every prune point. It looks up the states saved at that instruction, compares each with the current one via states_equal(), which calls regsafe() per register and stacksafe() per stack slot, and either prunes or saves the current state as a new checkpoint. The scalar case in regsafe() shows the containment test directly:

	if (rold->type != rcur->type)
		return false;

	switch (base_type(rold->type)) {
	case SCALAR_VALUE:
/* ... */
		if (!rold->precise && exact == NOT_EXACT)
			return true;
/* ... */
		return range_within(rold, rcur) && tnum_in(rold->var_off, rcur->var_off);
/* ... */
	case PTR_TO_PACKET_META:
	case PTR_TO_PACKET:
		/* We must have at least as much range as the old ptr
		 * did, so that any accesses which were safe before are
		 * still safe.  This is true even if old range < old off,
		 * since someone could have accessed through (ptr - k), or
		 * even done ptr -= k in a register, to get a safe access.
		 */

A scalar is safe if its range and known bits fit inside the old ones. A packet pointer is safe if it has at least as much proven range as before. A register that the old state never read (NOT_INIT in the old state, or found dead by liveness analysis) matches anything. The documentation gives a small example of why liveness matters: two paths reach instruction 4 with r0=1 and r0=0, but instruction 4 overwrites r0 before reading it, so the two states are equivalent. In real logs a pruned path shows up as from 7 to 11: safe.

Saved states cost memory and comparison time, and the 2019 bounded-loops work reported that most saved states never prune anything (LWN, "Bounded loops in BPF for the 5.3 kernel"). The verifier therefore saves states only at prune points, drops states that never matched, and when it is inside a loop it adds new checkpoints only now and then.

Precision tracking

Pruning has a tension built in. To prune often, the comparison should ignore differences that do not matter: whether r7 was 3 or 4 is irrelevant if r7 is only ever stored into a map. If r7 is later used as an array index, the difference matters a lot. Since Linux 5.3 (b5dc0163d8fd, "bpf: precise scalar_value tracking") the verifier tracks which scalars actually influence a safety decision.

All scalars start imprecise. When a scalar's value is used in a way that affects safety (as a pointer offset, a memory access size, a helper argument that must be a constant, a return value with a required range, or a branch that is pruned because its outcome was known), the verifier calls bpf_mark_chain_precision(). That function walks backward through the recorded jump history and instructions, marking the register and every register or stack slot it was computed from as precise, across parent states. In the log this is the block of lines like:

regs=1 is a bitmask: bit 0, which is R0. The walk stops at the call that produced the value. regsafe() then compares ranges only for precise scalars (the if (!rold->precise …) return true; line above). The kernel comment in backtrack.c explains why it is enough to set precision on checkpointed parent states:

 * One important and subtle aspect is that precise marks *do not matter* in
 * the currently verified state (current state). It is important to understand
 * why this is the case.
 *
 * First, note that current state is the state that is not yet "checkpointed",
 * i.e., it is not yet put into env->explored_states, and it has no children
 * states as well. It's ephemeral, and can end up either a) being discarded if
 * compatible explored state is found at some point or BPF_EXIT instruction is
 * reached or b) checkpointed and put into env->explored_states, branching out
 * into one or more children states.

Precision tracking is subtle and has had its share of fixes. A GitHub commit search for "precision" in the kernel's BPF history turns up fixes in 2019, 2023 and 2026. Bugs here are dangerous because a missing precision mark means a state is pruned when it should not be, which makes the verifier unsound.

BPF tokens (Linux 6.9)

The table above has a gap. CAP_BPF only counts in the initial user namespace, so a container running as root inside its own user namespace has no BPF rights at all. Giving the container real CAP_BPF would hand it every program type, including tracing programs that can read any kernel memory. A BPF token closes the gap. Andrii Nakryiko wrote it over many revisions in 2023 (LWN covered the first design in June 2023 and the bpffs-based design in October 2023), and it first shipped in Linux 6.9. kernel/bpf/token.c exists at the v6.9 tag and not at v6.8. The uapi comment for BPF_TOKEN_CREATE says the token is "associated" with the user namespace that owns the bpffs instance it came from. Later capability checks (CAP_BPF, CAP_PERFMON, CAP_NET_ADMIN, CAP_SYS_ADMIN) are then made in that namespace. A token does not grant anything by itself. It lets the kernel run ns_capable() instead of capable(), and only for the commands and types the administrator delegated.

Each option is a bit mask over one uapi enum. It is written as colon-separated names, the word any, or a number. Names are matched without case and without the enum prefix, which is BPF_ for delegate_cmds and delegate_attachs, BPF_MAP_TYPE_ for delegate_maps and BPF_PROG_TYPE_ for delegate_progs. So delegate_cmds=prog_load:map_create:btf_load and delegate_progs=xdp:socket_filter are valid. Setting a non-zero mask needs CAP_SYS_ADMIN in the initial namespace. A plain mount -t bpf -o delegate_... on the host does not work. That superblock belongs to init_user_ns, so a token made from it fails with -EOPNOTSUPP. The kernel selftest (tools/testing/selftests/bpf/prog_tests/token.c) shows the intended handoff using the new mount API:

1. Container: new user and mount namespaces

The child calls unshare(CLONE_NEWUSER), maps its uid and gid to 0 through /proc/self/uid_map and gid_map, then calls unshare(CLONE_NEWNS). Then it calls fsopen("bpf", 0). bpffs is FS_USERNS_MOUNT, so this fs context belongs to the container's namespace. The test checks that setting delegate_* from here fails with -EPERM.

2. Hand the fs context to the host

The child sends the fs-context fd to the privileged parent over a Unix socket (SCM_RIGHTS).

3. Host: set the delegation and create the superblock

The parent calls fsconfig(fs_fd, FSCONFIG_SET_STRING, "delegate_cmds", ...) and the same for maps, programs and attach types, then fsconfig(..., FSCONFIG_CMD_CREATE, ...). Creating a bpffs owned by a non-initial namespace also needs host CAP_SYS_ADMIN (bpf_fill_super()).

4. Container: mount and derive a token

The child calls fsmount(), opens the mount root, and calls bpf(BPF_TOKEN_CREATE) with that fd (bpf_token_create(bpffs_fd, NULL) in libbpf). Trying to add delegation later through fspick() fails with -EPERM.

5. Use the token

The token fd goes in prog_token_fd, map_token_fd or btf_token_fd, with BPF_F_TOKEN_FD set in the command's flags. Every check then goes through bpf_token_capable(), which you can see in the bpf_check() excerpt above. Commands, map types and program/attach types outside the masks are refused.

Applications built on libbpf usually need no token code. When an object is prepared for loading (bpf_object_prepare_token(), called from bpf_object_prepare()), libbpf tries to create a token from /sys/fs/bpf on its own and quietly skips the step when that mount has no delegation (-ENOENT). The bpf_token_path open option, or the LIBBPF_BPF_TOKEN_PATH environment variable, names a different bpffs and makes the token mandatory. An empty string turns the automatic attempt off. LSMs see tokens through security_bpf_token_create, security_bpf_token_cmd and security_bpf_token_capable, so a policy can narrow a delegation further. The selftest attaches such a BPF LSM before it enters the namespace. For a hands-on lesson, see the features/bpf_token example in Chapter 09.

Signed BPF programs (Linux 6.18)

Kernel modules have been signable for a long time. BPF programs had nothing comparable: any sufficiently privileged process could load any program that passed the verifier. The obstacle was relocation. The bytes the kernel finally verifies are not the bytes the developer built. libbpf patches map fds into ld_imm64 instructions, rewrites CO-RE field offsets for the running kernel (Chapter 06), and resolves kfunc and ksym ids. A signature over the .o file therefore cannot match what reaches BPF_PROG_LOAD. Two competing designs were posted in 2025 (LWN, "Possible paths for signing BPF programs"). KP Singh's series "Signed BPF programs" was merged for 6.18. The LWN merge-window summary adds that "security policies that can take advantage of this are still in progress".

The design: sign the loader, chain the hash. The cover letter calls it a trusted hash chain. The program is not signed directly. libbpf's gen_loader (the "light skeleton", bpftool gen skeleton -L) produces a small BPF_PROG_TYPE_SYSCALL loader program. Its body makes the bpf() calls that create maps, apply relocations and load the real programs. Everything it installs (programs, relocation records, initial map values) sits in one array map, the metadata map (__loader.map). In 6.18:

  1. At build time bpftool computes H_meta = SHA256(metadata). It embeds that hash as immediates in the first loader instructions (load map word, compare with immediate, bail on mismatch), then signs the loader instructions. The signature therefore covers I_loader || H_meta.
  2. At load time user space creates the metadata map as an exclusive map. A new BPF_MAP_CREATE field, excl_prog_hash, carries the SHA-256 of the one program allowed to use the map. To make this possible, the program tag (bpf_prog_calc_tag()) moved from SHA-1 to SHA-256. User space then fills the map and freezes it.
  3. BPF_PROG_LOAD of the loader passes the signature. The kernel checks a PKCS#7 signature over the loader instructions against the selected keyring. The verifier refuses to bind the exclusive map to any program whose digest does not match.
  4. The now-trusted loader runs and compares the frozen map with its embedded hash before doing anything else.

The uapi change is three fields at the end of the BPF_PROG_LOAD part of union bpf_attr:

What a signature does not give you

A signature proves where the bytes came from and that nobody changed them. It does not prove the program is safe. That is still the verifier's job. Protection also ends once loading succeeds: a signed program can be detached or unloaded like any other. At LSFMM+BPF 2026, Christian Brauner described the work systemd needs to keep its BPF LSM programs and their maps from being tampered with after load (LWN, "Securing BPF LSMs against tampering").

Spectre mitigations

The verifier proves that an access is in bounds on every architectural path. A CPU that speculates past a bounds check can still execute the access transiently and leak data through the cache (Spectre variant 1), and a CPU can speculatively load stale data before a preceding store resolves (variant 4, speculative store bypass). Because unprivileged users could load programs, the verifier gained mitigations starting in January 2018:

  • Array index masking (b2157399cc98, v4.15): map lookups in array maps are rewritten to AND the index with a mask, so a speculated out-of-range index still lands inside the array.
  • Pointer arithmetic sanitation (979d63d50c0c, 2019, and later rework): for pointer ± unknown scalar, the verifier computes an alu_limit, the largest offset that stays inside the object, and emits extra instructions that clamp the offset to that limit without a branch. It also simulates the speculative path where a branch goes the "wrong" way, as a special state with speculative = true, to make sure even that path cannot reach out of bounds.
  • Speculative store bypass (af86ca4e3088, v4.17): the verifier inserts a speculation barrier (nospec) after certain stack stores, so that a later load cannot speculatively read the stale value that was there before.

Privileged loaders with CAP_PERFMON, and systems booted with mitigations=off, skip all of this (bypass_spec_v1/v4).

eBPF itself as an attack surface

This chapter has already covered most of the defences: loading without privilege is off by default (kernel.unprivileged_bpf_disabled, above), Spectre sanitation applies to anyone without CAP_PERFMON, and "Verifier bugs in the wild" below shows the main threat they guard against. Those bugs are mistakes in bounds tracking that let a verified program read or write kernel memory. A few more mechanisms complete the picture:

  • The bpf() LSM hooks. include/linux/lsm_hook_defs.h defines eight checking hooks for BPF. bpf runs on every syscall command, bpf_map and bpf_prog run when an fd is handed out, bpf_map_create and bpf_prog_load run at creation, and the three bpf_token_* hooks cover tokens. SELinux and BPF LSM programs use these hooks to control who may load what. They are also where a signature policy would be enforced.
  • Lockdown. enum lockdown_reason in include/linux/security.h lists LOCKDOWN_BPF_WRITE_USER before LOCKDOWN_INTEGRITY_MAX, and LOCKDOWN_BPF_READ_KERNEL before LOCKDOWN_CONFIDENTIALITY_MAX. Integrity lockdown therefore removes bpf_probe_write_user. Confidentiality lockdown also removes bpf_probe_read_kernel and its _str and legacy variants. In both cases the helper's func_proto returns NULL (kernel/bpf/helpers.c, kernel/trace/bpf_trace.c), so the verifier rejects any program that calls it.
  • BPF in the attacker's hands. A privileged attacker gets the same powers as a legitimate tracer. That means reading kernel and user memory, changing user memory with bpf_probe_write_user (which needs CAP_SYS_ADMIN; see Chapter 05), and interfering with other BPF programs. LWN's 2026 summit report points out that a program can often be steered by changing the data it keeps in its maps, and that an attached program goes away when its last reference is closed. The tools for fencing BPF itself are the hooks above, tokens, signatures and exclusive maps. No single one of them makes a loaded program tamper-proof.

Using the verifier: real commands

You never call the verifier directly. It runs when the program is loaded. These are the practical ways to see its output.

Compile with debug info so the log interleaves C source lines (; *val += 1;), which needs BTF line info:

clang -O2 -g -target bpf -c prog.bpf.c -o prog.bpf.o

bpftool loads and pins an object. Its -d/--debug option prints "logs from libbpf as well as from the verifier, when attempting to load programs":

sudo bpftool -d prog load prog.bpf.o /sys/fs/bpf/prog

libbpf prints the verifier log on failure by default. To get the full log on success too, set a log level when opening the object, or per program with bpf_program__set_log_level() and bpf_program__set_log_buf(). This is the core of the loader used for this chapter's logs:

/* Illustrative loader (written for this chapter). Build: gcc loader.c -lbpf -lelf -lz */
LIBBPF_OPTS(bpf_object_open_opts, o, .kernel_log_level = 1);
struct bpf_object *obj = bpf_object__open_file(argv[1], &o);
static char buf[1 << 22];
struct bpf_program *p;

bpf_object__for_each_program(p, obj) {
	bpf_program__set_log_buf(p, buf, sizeof(buf));
	bpf_program__set_log_level(p, 2);	/* 1 = log, 2 = full log of every path */
}
int err = bpf_object__load(obj);
fputs(buf, stdout);

Log level 1 (BPF_LOG_LEVEL1) prints the failing path, level 2 prints every instruction of every path, and the flag 4 (BPF_LOG_STATS) prints only the summary statistics. Level 4 is what you want for a loop that burns through a million instructions; at level 1 the 4 MB buffer in the loader above overflowed (-ENOSPC).

veristat lives in tools/testing/selftests/bpf/ and is mirrored as a standalone project at libbpf/veristat. It loads every program in one or more object files and reports verdicts and complexity in a table, which makes it the standard tool for "did my change make verification harder?". Options at the studied commit include -v (verbose), -l LEVEL (verifier log level), -e SPEC (columns to emit), -C (compare two CSV runs) and -f (filter):

sudo veristat prog.bpf.o                      # verdict, insns, states per program
sudo veristat -e file,prog,verdict,insns,states -o csv old.bpf.o > old.csv
sudo veristat -e file,prog,verdict,insns,states -o csv new.bpf.o > new.csv

sudo veristat -v -l 2 -f count_packets prog.bpf.o   # full log of one program

Benefits and limitations

Benefit: zero run-time cost

Once accepted, the program runs as native JIT code with no bounds checks beyond the ones you wrote, plus the few Spectre masks. That is why XDP can run at line rate.

Benefit: precise

Path sensitivity and the combined tnum + range domains accept a lot of real-world C, including pointer arithmetic, variable-length parsing and loops.

Benefit: one gatekeeper

Every program type, from socket filters to sched_ext schedulers, goes through the same checker, parameterised by per-type callbacks and helper prototypes.

Limit: false positives

Safe programs get rejected, often after compiler optimisations reorder or spill values in ways the verifier cannot follow. Programs end up shaped to please the verifier.

Limit: complexity cliffs

Small changes can multiply the number of states, and a program that verified yesterday can hit the 1M limit after a new if. Verification time is not linear in program size.

Limit: a large trusted base

Tens of thousands of lines of intricate C run in the kernel. Bugs in it are kernel vulnerabilities, and the history of CVEs below shows they happen.

What the verifier does not check is just as important. It does not check that your program is correct, that it does what you meant. It does not prevent a tracing program from reading any kernel memory through bpf_probe_read_kernel() when the loader has the right capabilities; that is a policy question. And it treats helpers and kfuncs as trusted code: a bug inside a helper is not the verifier's to find.

Research: checking and replacing the verifier

Because the verifier is both security-critical and hard to get right, it has drawn steady attention from the programming-languages and verification communities. Four lines of work stand out.

PREVAIL: abstract interpretation done "properly" (PLDI 2019)

Gershuni, Amit, Gurfinkel, Narodytska, Navas, Rinetzky, Ryzhyk and Sagiv, Simple and Precise Static Analysis of Untrusted Linux Kernel Extensions, PLDI 2019. The paper argues that the Linux verifier's design, which enumerates paths with pruning, is fragile and scales badly. It describes it as relying on "syntactic pattern matching and ad hoc case analysis". PREVAIL instead uses classic abstract interpretation: states are joined where paths merge and widened at loop heads, so the analysis runs in polynomial time and handles loops naturally. For numeric facts the authors evaluated several relational domains and chose the zone domain, which tracks constraints of the form x − y ≤ c, such as "packet pointer + 14 ≤ data_end". On their 192 benchmark programs (from the Linux samples, Open vSwitch, Suricata and Cilium) plain intervals failed 64 programs, while zones verified all but one. PREVAIL proves safety of programs with loops but, in the paper's version, not termination. The authors report that Linux's verifier was faster on those mostly-Linux-tuned benchmarks, while PREVAIL scaled linearly on a synthetic loop where Linux's time grew until it hit its limit. PREVAIL lives on as vbpf/prevail and is the verifier used by eBPF for Windows (see Chapter 08). Its command-line tool runs on ELF objects, for example bin/prevail ebpf-samples/cilium/bpf_lxc.o 2/1 from its README. Chapter 18 uses PREVAIL together with Z3 to validate program transformations.

Tristate numbers made rigorous (CGO 2022)

Vishwanathan, Shachnai, Narayana and Nagarakatte, Sound, Precise, and Fast Abstract Interpretation with Tristate Numbers, CGO 2022. The paper formalises the tnum domain and gives the first proofs that the kernel's tnum_add and tnum_sub are sound and optimal: no smaller tnum contains all possible results. It also presents a new tnum multiplication that is more precise and, by the paper's measurement, 33% faster on average than the kernel's previous algorithm. That algorithm was merged into Linux as commit 05924717ac70 ("bpf, tnums: Provably sound, faster, and more precise algorithm for tnum_mul", v5.14). It is the loop you can see in tnum_mul() today.

Agni: verifying the range analysis (CAV 2023)

Vishwanathan, Shachnai, Narayana and Nagarakatte, Verifying the Verifier: eBPF Range Analysis Verification, CAV 2023. The same group built Agni, which extracts the semantics of the verifier's value-tracking code directly from the kernel's C source (through LLVM IR) into SMT formulas and asks Z3 whether each abstract operator is sound for every input. A key finding: many operators, taken alone, are not sound. The verifier stays sound only because the shared reduction (reg_bounds_sync() above) preconditions their inputs. With that refinement, Agni checked 16 kernel versions from 4.14 to 5.19, proved the range analysis sound for versions newer than 5.13, and found 27 previously unknown bugs in older versions. When a check fails, Agni synthesises a short eBPF program that shows the mismatch between abstract and concrete execution; it managed this for about 97% of the violations.

Testing the verifier: state embedding (OSDI 2024)

Hao Sun and Zhendong Su, Validating the eBPF Verifier via State Embedding, OSDI 2024. Instead of proving operators sound, this work tests the whole verifier. It takes a program the verifier accepted, records concrete states, and embeds checks into the program that the verifier itself must prove. If the verifier then "proves" something that a concrete run contradicts, it has a logic bug. The authors report 15 previously unknown bugs found in one month, 10 already fixed, two of them exploitable for local privilege escalation.

Check your understanding

Q1. What does pass 1 (bpf_check_cfg()) look at?

Pass 1 is a depth-first search over the instruction graph. It never computes values; it rejects out-of-range jumps, unreachable instructions and (for unprivileged loaders) back-edges, and marks prune points for pass 2.

Q2. After if r0 > 0xf goto L on the fall-through path, and then r0 <<= 3, what is r0's tnum, assuming r0 started as an unknown u32?

The branch gives umax=15, which becomes tnum (0x0; 0xf). Shifting left by 3 moves the four unknown bits to positions 3–6: mask 0x78, so the value is a multiple of 8 in [0, 120]. The real log above shows exactly this.

Q3. Why does the verifier keep both signed and unsigned bounds?

A signed check like if ((s64)i < 64) leaves negative values, which are huge as unsigned offsets. Tracking both views, and deducing one from the other, lets each kind of comparison contribute what it actually proves.

Q4. When may the verifier stop exploring a path at a prune point?

regsafe() tests containment: ranges and tnums inside the old ones, packet range at least as large, same pointer types. Imprecise scalars match anything, which is why precision tracking exists. Exact equality is used only to detect infinite loops.

Q5. A privileged XDP program loops for (i = 0; i < n; i++) with n from bpf_get_prandom_u32(), and the body is branch-free. What is the most likely result?

Privileged loaders may use back-edges, so pass 1 passes. Pass 2 simulates iterations; with an unknown bound the exit never becomes certain, and the 1M processed-instruction budget runs out. The fix is a constant bound, bpf_loop(), an iterator, or can_loop.

Q6. What did the CAV 2023 Agni paper find about the kernel's abstract operators?

Agni extracted the operators from kernel C code and checked them with Z3. With a specification that accounts for reg_bounds_sync()-style preconditioning, kernels newer than 5.13 were proven sound; older ones had 27 new bugs, mostly demonstrated with synthesised programs.
