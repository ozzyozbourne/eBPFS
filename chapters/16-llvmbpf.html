Chapter 16

llvmbpf: an LLVM JIT/AOT Compiler for eBPF

The kernel's eBPF JITs are small, fast, single-purpose code generators that live inside Linux. What if you want to run the same bytecode in an ordinary process, on a different CPU, ahead of time, or on a GPU? llvmbpf answers that by translating each eBPF instruction into LLVM IR and handing the result to LLVM. From one lifter you get an in-process JIT, a native ELF object, NVIDIA PTX and SPIR-V. This chapter reads that lifter line by line, runs it, and shows where bpftime plugs it in.

Why this matters

An eBPF program is a list of 8-byte instructions for a small virtual machine. It has eleven 64-bit registers, a 512-byte stack and a calling convention that matches x86-64 and arm64 on purpose (Chapter 02). In the kernel, after the verifier accepts a program, an architecture-specific JIT such as arch/x86/net/bpf_jit_comp.c turns it into machine code. That JIT is a large switch over opcodes with a fixed register map. It emits one or a few native instructions per eBPF instruction (Chapter 02, "The x86-64 JIT").

Userspace runtimes need the same thing outside the kernel. bpftime (Chapter 14) runs uprobe, syscall-tracepoint and XDP-style programs inside the target process. Every probe hit runs the program, so execution speed matters. The established userspace VMs, uBPF (C) and rbpf (Rust), each ship an interpreter and a hand-written JIT for one or two architectures. Their JITs use the kernel's style: a direct, per-instruction translation. That design is simple and compiles quickly. It cannot do the things an optimising compiler does: keep stack slots in registers, fold constants across instructions, recognise loops, inline a helper, or target an instruction set nobody wrote a backend for.

llvmbpf takes the opposite route. It does not write any machine code itself. It lifts eBPF bytecode into LLVM IR, runs LLVM's standard -O3 pipeline, and lets LLVM's backends do the rest. Once the program is LLVM IR, other outputs cost little extra. The same module can be JIT-compiled with ORC, written out as a relocatable ELF object, or lowered to PTX or SPIR-V for a GPU.

Key idea

llvmbpf is a compiler front end for eBPF bytecode whose back end is all of LLVM. It is deliberately only the VM: the README says it "does not include maps implement, helpers, verifiers, or loaders". Safety and the runtime environment come from whoever embeds it. In practice that is usually bpftime, which uses llvmbpf as its default VM.

What llvmbpf is, and what it is not

The repository describes itself as a "high-performance, multi-architecture JIT/AOT compiler and virtual machine (VM) based on LLVM". It began as the vm/llvm-jit directory of bpftime; the first commit in the standalone repository (10 August 2024) is literally "Init project from bpftime". Today it is a separate repo again pulled back into bpftime as a git submodule. Its capabilities, according to the README and confirmed in the code:

  • a C++ library, bpftime::llvmbpf_vm, that loads raw eBPF bytecode, JIT-compiles it and runs it;
  • AOT compilation of eBPF bytecode into a native relocatable ELF object exporting bpf_main, which can be linked into a C program or loaded back into the VM;
  • emission of the lifted LLVM IR itself (-emit-llvm), for inspection or further optimisation;
  • hooks for helpers (by index) and for the five LDDW pseudo-instruction variants that reference maps and globals;
  • PTX generation for NVIDIA GPUs and SPIR-V generation for other GPUs;
  • a small CLI, bpftime-vm, with build and run subcommands.

What it does not do matters as much. There is no verifier. load_code() only checks that the length is a multiple of 8. There is no interpreter: exec() compiles on first use. No map types and no helpers are built in. There is also no memory-bounds checking in the generated code. A load from r1 + 4096 becomes a plain LLVM load from that address. Running unverified bytecode with llvmbpf therefore means running unverified native code inside your process.

Lifting eBPF to LLVM IR

Everything interesting happens in generateModule(). It receives the list of helper symbols and LDDW helpers that exist, plus flags saying whether map addresses may be baked in at compile time and whether the target is a GPU. It returns a ThreadSafeModule containing one function, by default named bpf_main. The function has four phases. It declares external symbols, finds basic-block boundaries, builds a frame that models the eBPF machine, and then walks the instructions.

Modelling the machine in IR

LLVM IR has unlimited virtual registers in SSA form, but eBPF registers are mutable. The lifter takes the standard compiler-front-end shortcut. Each eBPF register becomes a stack slot (alloca), and every instruction loads its operands from those slots and stores its result back. LLVM's SROA and mem2reg passes later promote the slots to SSA values, so the slots cost nothing after optimisation. The eBPF stack is another alloca, and r10 is initialised to point at its top:

	// Stack used to save return address and saved registers

			regs.push_back(builder.CreateAlloca(
				builder.getInt64Ty(), nullptr,
				"r" + std::to_string(i)));
		}
		/* ... kernel-compatible and GPU variants elided ... */

				builder.getInt64Ty(),

The constants are defined at the top of the file. STACK_SIZE = (EBPF_STACK_SIZE + 7) / 8 is 64 (eight-byte slots in 512 bytes), MAX_LOCAL_FUNC_DEPTH is 32 and CALL_STACK_SIZE is 64. The stack is therefore alloca i64, i32 2058, a little over 16 KiB, enough for 32 frames of 512 bytes. You can see these numbers in the real IR below. The second argument, the memory length, goes into r2, a uBPF convention: programs get (ctx, ctx_len) rather than the kernel's single context pointer.

Finding basic blocks

Before emitting anything, the lifter needs to know where control can enter. A block starts at instruction 0, after any jump (the fall-through), and at every jump target. That is one linear scan:

	std::vector<bool> blockBegin(insts.size(), false);
	// Split the blocks
	blockBegin[0] = true;
	for (uint16_t i = 0; i < insts.size(); i++) {
		auto curr = insts[i];
		SPDLOG_TRACE("check pc {} opcode={} ", i,
			     (uint16_t)curr.opcode);
		if (i > 0 && is_jmp(insts[i - 1])) {
			blockBegin[i] = true;
			SPDLOG_TRACE("mark {} block begin", i);
		}
		if (is_imm_jmp(curr)) {
			SPDLOG_TRACE("mark {} block begin", i + curr.imm + 1);
			blockBegin[i + curr.imm + 1] = true;
		} else if (is_jmp(curr) &&
			   i + curr.offset + 1 < blockBegin.size()) {
			SPDLOG_TRACE("mark {} block begin",
				     i + curr.offset + 1);
			blockBegin[i + curr.offset + 1] = true;
		}
	}

For each marked index it then creates an LLVM BasicBlock named bb_inst_<pc> and stores it in a std::map<uint16_t, BasicBlock*>. Jump targets are looked up in that map, and a jump to an index that is not a block start returns an error ("is going to jump to an illegal position"). This is the closest thing to validation in the lifter. Note the uint16_t program counter: programs are limited to 65,535 instructions, and a comment in the source calls this "a pre-existing limitation of this codebase".

The translation loop

The heart of the lifter is a for loop over the program counter with a switch on the opcode. It looks a lot like the kernel's do_jit(). The difference is that each case calls IRBuilder rather than emitting bytes:

	// Iterate over instructions
	BasicBlock *currBB = instBlocks[0];
	IRBuilder<> builder(currBB);
	for (uint16_t pc = 0; pc < codegen_end_pc; pc++) {
		auto inst = insts[pc];
		if (blockBegin[pc]) {
			if (auto itr = instBlocks.find(pc);
			    itr != instBlocks.end()) {
				currBB = itr->second;
			} else {
				return llvm::make_error<llvm::StringError>(
					"pc=" + std::to_string(pc) +
						" was marked block begin, but no BasicBlock* found",
					llvm::inconvertibleErrorCode());
			}
		}
		builder.SetInsertPoint(currBB);
		/* ... optional DILocation from BTF line info ... */
		// Precheck for registers
		if (inst.dst > 10 || inst.src > 10) {
			return llvm::make_error<llvm::StringError>(
				"Illegal src reg/dst reg at pc " +
					std::to_string(pc),
				llvm::inconvertibleErrorCode());
		}
		switch (inst.opcode) {
			// ALU
		case EBPF_OP_ADD64_IMM:
		case EBPF_OP_ADD_IMM:
		case EBPF_OP_ADD64_REG:
		case EBPF_OP_ADD_REG: {
			emitALUWithDstAndSrc(
				inst, builder, &regs[0],
				[&](Value *dst_val, Value *src_val) {
					return builder.CreateAdd(dst_val,
								 src_val);
				});

			break;
		}
		/* ... SUB, MUL, DIV, OR, AND, LSH, RSH, NEG, MOD, XOR, MOV, ARSH,
		       LE/BE/BSWAP, ST/STX, LDX/LDXS, LDDW, JA, CALL, EXIT,
		       sixteen conditional jumps, atomics ... */
		default:
			return llvm::make_error<llvm::StringError>(
				"Unsupported or illegal opcode: " +
					std::to_string(inst.opcode) +
					" at pc " + std::to_string(pc),
				llvm::inconvertibleErrorCode());
		}
	}

	// Add br for all blocks
	for (size_t i = 0; i < allBlocks.size() - 1; i++) {
		auto &currBlk = allBlocks[i];
		// LLVM 24 getTerminator() requires a well-formed block. During
		// construction, inspect the last instruction without that assumption.
		if (currBlk->empty() || !currBlk->back().isTerminator()) {
			builder.SetInsertPoint(allBlocks[i]);
			builder.CreateBr(allBlocks[i + 1]);
		}
	}

Notice how one case covers four opcodes: the 32- and 64-bit forms, with an immediate or register source. The opcode byte encodes these as independent bits (class in the low three bits, source in bit 3; Chapter 02, "Instruction encoding"). The helper decodes the bits again when it fetches operands. The final loop adds a fall-through br to any block that does not end in a terminator, because LLVM requires every block to end in one. Afterwards verifyModule() runs (except for GPU targets), so malformed IR is rejected before it reaches a backend.

ALU instructions: width is the only subtlety

The ALU helpers in compiler_utils.cpp encode the eBPF rule that 32-bit operations zero the upper half of the destination. Operands are loaded as i32 (via trunc) or i64 depending on the class, and 32-bit results are zero-extended before being stored:

void emitStoreALUResult(const ebpf_inst &inst, llvm::Value **regs,
			llvm::IRBuilder<> &builder, llvm::Value *result)
{
	if ((inst.opcode & 0x07) == EBPF_CLS_ALU64) {
		builder.CreateStore(result, regs[inst.dst]);
	} else {
		// For 32-bit ALU operations, clear the
		// upper 32bits of the 64-bit register
		builder.CreateStore(builder.CreateZExt(result,
						       builder.getInt64Ty()),
				    regs[inst.dst]);
	}
}
/* ... */
void emitALUWithDstAndSrc(
	const ebpf_inst &inst, llvm::IRBuilder<> &builder, llvm::Value **regs,
	std::function<llvm::Value *(llvm::Value *, llvm::Value *)> func)
{
	using namespace llvm;
	Value *dst_val = emitLoadALUDest(inst, &regs[0], builder, false);
	Value *src_val = emitLoadALUSource(inst, &regs[0], builder);
	Value *result = func(dst_val, src_val);
	emitStoreALUResult(inst, regs, builder, result);
}

The interesting cases are the ones where eBPF semantics differ from LLVM's. In LLVM, udiv by zero is undefined behaviour. In eBPF, division by zero yields 0 and modulo by zero leaves the destination unchanged. So the DIV case wraps the division in select(src == 0, 0, dst / src). For signed division (the v4 sdiv, flagged by offset == 1) it also tries to handle INT_MIN / -1. Shifts are masked with urem src, 64 (or 32), because a shift by the full width or more is also undefined in LLVM. None of these guards is optional. Without them, LLVM's optimiser would be entitled to assume the bad case never happens and miscompile the program.

Observed bug (found in review)

The shift guard works, but the division guards do not. A select picks between two values that have both already been computed. The udiv/sdiv/urem/srem instruction therefore still executes when the divisor is 0 (or for INT64_MIN / -1), which is undefined behaviour in LLVM IR, and on x86-64 the div/idiv instruction traps. Tested at 7e384db with LLVM 15.0.6 and hand-assembled programs that read the operands from the context buffer (illustrative, not from the repo): 64-bit unsigned divide by 0, unsigned modulo by 0, signed divide by 0 and INT64_MIN / -1 all killed the host process with SIGFPE, at the default -O3 and at -O0. With a non-zero divisor the same programs returned the right result. When the divisor is a constant 0 (as in mov r1, 0; div r0, r1) LLVM folds the expression and the program returns 0. bpf_conformance's *-by-zero-reg tests use constant zeros, so they pass. A correct lowering would branch around the division, or divide by select(src == 0, 1, src). Newer LLVM versions were not tested.

Memory: loads and stores without checks

Loads and stores are one getelementptr i8 plus a load or store of the right width:

llvm::Value *emitLDXLoadingAddr(llvm::IRBuilder<> &builder, llvm::Value **regs,
				const ebpf_inst &inst)
{
	// [rX + OFFSET]
	return builder.CreateGEP(builder.getInt8Ty(),
				 builder.CreateLoad(builder.getPtrTy(),
						    regs[inst.src]),
				 { builder.getInt64(inst.offset) });
}
/* ... */
void emitLoadX(llvm::IRBuilder<> &builder, llvm::Value **regs,
	       const ebpf_inst &inst, llvm::IntegerType *srcTy,
	       bool sign_extend)
{
	using namespace llvm;
	Value *addr = emitLDXLoadingAddr(builder, &regs[0], inst);
	Value *result = builder.CreateLoad(srcTy, addr);
	emitLDXStoringResult(builder, &regs[0], inst, result, sign_extend);
}

That is the whole memory model: the register value is a host pointer. Nothing checks it against the context buffer, the stack, or a map. This is the same choice the kernel JIT makes, but the kernel can make it because the verifier has already proved every access safe (Chapter 03). In userspace that proof has to come from somewhere else. bpftime has a userspace verifier for this (Chapter 14). Note its default, though: in runtime/include/bpftime_config.hpp the mode BPFTIME_VERIFIER_WARNING is marked "(default)", with the comment "Program loading continues even if verification fails". Strict rejection needs BPFTIME_VERIFIER_LEVEL=STRICT (runtime/src/bpftime_config.cpp).

Warning

Because loads become plain IR loads, LLVM also applies its normal assumptions to them: no data races on non-atomic accesses, natural alignment as declared (align 4 in the output below), and so on. An eBPF program that the kernel would accept but that relies on unaligned access, or on another thread changing memory between two loads, can behave differently after -O3. Commit 256540e ("Fix atomic operation alignment causing uprobe failures", February 2026) is an example of such alignment issues surfacing in practice.

Jumps, exit and BPF-to-BPF calls

Conditional jumps are a comparison and a CondBr to two blocks found by program counter. JSET becomes (dst & src) != 0. JMP32 variants compare i32 loads. EXIT is where the lifter's design shows. eBPF has local function calls (call with src_reg = 1; Chapter 02), but the lifter emits a single LLVM function. Subprograms are not split out. Instead it implements calls by hand:

  • A local call pushes five words onto the IR-level callStack: the return address as an LLVM blockaddress of the block after the call, plus r6–r9. It moves r10 down, then branches to the callee's block.
  • EXIT checks callItemCnt. At depth zero it branches to exitBlock, which returns r0. Otherwise it branches to localFuncReturnBlock, which pops the saved registers and does an indirectbr to the saved return block.
		case EBPF_OP_EXIT: {
			if (kernel_compatible_mode) {
				builder.CreateBr(exitBlk);
			} else {
				builder.CreateCondBr(
					builder.CreateICmpEQ(
						builder.CreateLoad(
							builder.getInt64Ty(),
							callItemCnt),
						builder.getInt64(0)),
					exitBlk, localRetBlk);
			}
			break;
		}

This keeps everything in one function, which helps the optimiser: LLVM sees the whole program and can propagate constants across "calls". The cost is an indirectbr, which limits some optimisations, and a hand-rolled frame discipline that has to be exactly right.

Observed bug

On a local call the lifter executes r10 = r10 - STACK_SIZE, and localFuncReturnBlock adds it back. STACK_SIZE is 64, the number of 8-byte slots in 512 bytes, but it is applied to r10 as a byte offset. So a callee's frame starts only 64 bytes below the caller's, not 512. I tested this at commit 7e384db with an eight-instruction hand-assembled program (illustrative, not from the repo). The caller stores 7 at r10-128 and calls a subprogram that stores 99 at its own r10-64. Back in the caller, r10-128 is read. The JIT returned 99; spec semantics (each frame owns its own stack) give 7. Moving the callee's store to r10-520 returned 7, as expected. (Rerun during review with LLVM 15.0.6: same results, 99 and 7.) The call_local and rfc9669_call_local tests in bpf_conformance do not touch the stack at all, so they do not catch this. Kernel-compatible mode is not affected, because it lowers local calls to external symbols (see below).

Helper calls

A helper call (call imm with src_reg = 0) becomes a call to an external function named _bpf_helper_ext_%04d, so helper 1 is _bpf_helper_ext_0001. Every helper has the same LLVM type, i64 (i64, i64, i64, i64, i64), and receives r1–r5. This matches the eBPF calling convention exactly, so no argument shuffling is needed:

		// calls, so keep the historical "exit after helper 12" behavior there.
		if (inst.imm == 12 && !kernel_compatible_mode) {

			llvm::inconvertibleErrorCode());

Two things follow. First, a helper must be registered before compilation, otherwise lifting fails with "Ext func not found". One of the unit tests checks exactly this error. Second, helper 12 is bpf_tail_call in the kernel's numbering, and here it is approximated as "call the helper, then exit". The embedder's helper does the tail call by running the next program itself. bpftime keeps a thread-local current_thread_tail_call_ret for this purpose. The symbol names are the binding contract: when you link an AOT object into a C program, you provide functions with exactly these names, as the standalone example below does.

When JIT-compiling, the process that compiles is the process that runs, so the address of a map's value area can be baked into the code as a constant. An AOT object, though, may be linked into a different binary or loaded in a different process, so the address is not known yet. The lifter instead emits a call to an external __lddw_helper_map_val that the final program must define. You will see this function in the standalone example.

Worked example: a loop from bytecode to x86-64

The repository ships a tiny compiled program, .github/assets/sum.bpf.o, used by the AOT CI job. Its C source is not in the repo. From the disassembly it is equivalent to the following (reconstructed, illustrative):

/* Illustrative reconstruction, not from the repo */
int test(int *a)
{
	int sum = 0;
	for (int i = 1; i <= a[0]; i++)
		sum += a[i];
	return sum;
}

It was compiled without optimisation, so every variable lives on the stack: the pointer at r10-8, the sum at r10-12 and i at r10-16. That makes it a good test of how much LLVM can recover. All outputs below were produced in this orb with LLVM 15.0.6 on x86-64, using the bpftime-vm CLI built from commit 7e384db.

1. Decode and split

32 instructions. Block starts are 0, 6 (target of the back edge at 29 and of goto +0 at 5), 14 (after the conditional jump at 13), 15, 26 and 30 (target of if r1 s> r2 goto +16). Each becomes bb_inst_N. The goto +0 instructions come from unoptimised clang output and turn into empty blocks.

2. Build the frame

setupBlock allocates %r0…%r10, the 2,058-slot stack and the call stack, stores stackBegin + 2048 into %r10, and stores the two arguments into %r1 and %r2.

3. Lift each instruction

*(u64 *)(r10 - 8) = r1 becomes load %r1, load %r10 as a pointer, getelementptr i8 … -8, store i64. r1 <<= 32; r1 s>>= 32 (sign extension in eBPF v1) becomes shl then ashr. if r1 s> r2 goto +16 becomes icmp sgt plus br i1. The raw IR is about 150 lines, plus 1,000 helper declarations (the CLI pre-registers helpers 0–999).

4. Optimise

SROA promotes the register slots and the three stack slots to SSA values. The shift pair folds into a sext, the empty blocks vanish, and the loop is rotated so the bound check runs once before entry. The call-stack machinery is never used and disappears. The result is the 20-line function in the "Optimised IR" tab.

5. Emit

The x86-64 backend emits 11 instructions, 31 bytes. The loop body is addl (%rdi,%rdx,4), %eax: the eBPF stack, the address arithmetic and the register file have been compiled away.

In GPU mode bpf_main returns void, because a kernel entry cannot return a value. r0 is therefore dead and LLVM deletes everything that computes it, leaving only the loop counter. A GPU-side eBPF program must publish results through memory: a map, the context, or a helper. The section on GPU targets below explains how.

From IR to machine code

The optimisation pipeline

optimizeModule() builds LLVM's standard per-module pipeline at the requested level (default 3). On LLVM 17 and newer it uses the new pass manager (PassBuilder::buildPerModuleDefaultPipeline); on 15 and 16 it uses the legacy PassManagerBuilder. Since March 2026 the embedder can tune this. set_optimization_level(0..3), set_disabled_passes({...}) (skips any pass whose name contains one of the given strings, through a PassInstrumentationCallbacks hook) and set_log_passes(true) were added "for ablation study", according to the commit messages. set_target_cpu() and set_target_features() let a deployment pick, say, a CPU model for the JIT target machine instead of the host's.

JIT: ORC LLJIT and symbol binding

The JIT path uses LLVM's ORC LLJIT, the current recommended in-process JIT API (LLVM ORC v2 docs). do_jit_compile() is short:

llvm::Error llvm_bpf_jit_context::do_jit_compile()
{
	spin_lock_guard guard(compiling.get());
	auto [jit, extFuncNames, definedLddwHelpers] =
		create_and_initialize_lljit_instance();
	if (!jit) {
		return llvm::make_error<llvm::StringError>(
			"jit initialization failed",
			llvm::inconvertibleErrorCode());
	}
	// Handle the error from generateModule
	auto bpfModuleOrErr =
		generateModule(extFuncNames, definedLddwHelpers, true);
	if (!bpfModuleOrErr) {
		return bpfModuleOrErr.takeError();
	}
	// If successful, get the module
	auto bpfModule = std::move(*bpfModuleOrErr);
	// Optimize the module
	bpfModule.withModuleDo([&](auto &M) {
		optimizeModule(M, vm.optimization_level, vm.disabled_passes_,
			       vm.log_passes_);
		if (inline_array_map_lookup_helpers(M)) {
			optimizeModule(M, vm.optimization_level,
				       vm.disabled_passes_, vm.log_passes_);
		}
	});
	// Handle the error from addIRModule
	if (auto err = jit->addIRModule(std::move(bpfModule))) {
		return err;
	}
	// If everything succeeds, move the JIT instance
	this->jit = std::move(jit);
	return llvm::Error::success();
}

The third argument to generateModule, true, is patch_map_val_at_compile_time: in the JIT, map value addresses become constants. Binding helpers happens in create_and_initialize_lljit_instance(). For each registered helper it defines an absolute symbol in the JIT's main dylib whose name is _bpf_helper_ext_NNNN and whose address is the C function pointer the embedder registered:

	auto &mainDylib = jit->getMainJITDylib();
	std::vector<std::string> extFuncNames;
	// insert the helper functions
	SymbolMap extSymbols;
	for (uint32_t i = 0; i < std::size(vm.ext_funcs); i++) {
		if (vm.ext_funcs[i].has_value()) {
			auto sym = JITEvaluatedSymbol::fromPointer(
				vm.ext_funcs[i]->fn);
			auto symName = jit->getExecutionSession().intern(
				ext_func_sym(i));
			sym.setFlags(JITSymbolFlags::Callable |
				     JITSymbolFlags::Exported);
			/* ... LLVM < 17 and >= 17 variants ... */
			extSymbols.try_emplace(symName, symbol);
			extFuncNames.emplace_back(ext_func_sym(i));
		}
	}
	/* ... */
	if (auto err = mainDylib.define(absoluteSymbols(extSymbols)); !err) {
		SPDLOG_DEBUG("LLVM-JIT: failed to define external symbols");
	}

When ORC links the compiled module, the call @_bpf_helper_ext_0001 is resolved to that absolute address, so a helper call in JITed code is a direct native call into the host. (The !err in the condition logs on success rather than failure, but it only affects a debug message.) Finally get_entry_address() calls jit->lookup("bpf_main") and casts the result to uint64_t (*)(void *mem, size_t mem_len), the type the embedder calls directly.

Several recent commits concern this setup rather than code generation. They pre-register ORC's EH-frame and GDB-loader wrapper symbols before creating LLJIT (#49), so the JIT works when LLVM is statically linked into a shared library such as libbpftime-agent.so with hidden symbols. A unit test checks this by loading the library with dlopen. Another change (#52) links and initialises only the host backend plus NVPTX instead of every backend in the distro LLVM. Its commit message reports libbpftime-agent.so shrinking from 140 MB to 79 MB on LLVM 17 (figures from the commit message, not reproduced here).

AOT: a native ELF object

The AOT path reuses the lifter with patch_map_val_at_compile_time = false, runs the same optimisation, and asks the host TargetMachine to emit an object file into memory:

	if (auto module = generateModule(extFuncNames, lddwHelpers, false);
	    module) {
		return module->withModuleDo([&](auto &module)
						    -> std::vector<uint8_t> {
			if (print_ir) {
				module.print(llvm::outs(), nullptr);
			}
			optimizeModule(module, vm.optimization_level,
				       vm.disabled_passes_, vm.log_passes_);
			auto targetMachine =
				create_host_target_machine_or_throw(vm);
			/* ... setTargetTriple / setDataLayout ... */
			SmallVector<char, 0> objStream;
			std::unique_ptr<raw_svector_ostream> BOS =
				std::make_unique<raw_svector_ostream>(
					objStream);

			legacy::PassManager pass;
			/* ... LLVM-version-specific addPassesToEmitFile(..., ObjectFile) ... */
			pass.run(module);
			std::vector<uint8_t> result(objStream.begin(),
						    objStream.end());
			return result;
		});

The result is an ordinary relocatable ELF. For sum.bpf.o it is 544 bytes, with one global symbol T bpf_main and undefined references to any helpers it calls. You can use it in two ways:

  • Load it back with load_aot_object(). This creates a fresh LLJIT, binds the same helper symbols, calls addObjectFile() and looks up bpf_main. The CLI's run command works this way. The point is to compile once (for example at build time or on a powerful machine) and load quickly later, without running the optimiser again. bpftime's bpftime-aot tool uses this to compile programs held in its shared memory and load the native code back.
  • Link it into a C program like any other object. Define _bpf_helper_ext_NNNN and, if maps are used, __lddw_helper_map_val, and you get a standalone binary that needs neither LLVM nor any eBPF runtime. The README pitches this for deployment and for microcontrollers or systems without an OS.

Because the AOT output (or its -emit-llvm IR) is just LLVM, you can also go further than the JIT does. The example/inline recipe compiles the helper and map implementations to IR, merges them with llvm-link, runs opt -passes=always-inline, and compiles the result. The helpers are then inlined into the eBPF program and constant-folded with it. Since March 2026 the JIT can do a narrower version of this itself. If the embedder describes an array map with register_array_map(), inline_array_map_lookup_helpers() replaces _bpf_helper_ext_0001(const_handle, key) (bpf_map_lookup_elem) with a bounds check and address arithmetic, and the module is optimised a second time. The commit calls this a proof of concept.

GPU targets: PTX and SPIR-V

PTX support was developed on a separate repository, eunomia-bpf/llvmbpf-nvptx, whose description now reads "This branch has been merged into https://github.com/eunomia-bpf/llvmbpf". The last argument, is_gpu = true, changes three things in the lifter. The entry function returns void. Its pointer parameter lives in address space 1 (global memory). The stack and call stack are fixed-size array allocas instead of variable-length ones, which GPU backends handle poorly. Everything else, including the instruction translation, is shared. The PTX that comes out is a .func calling external _bpf_helper_ext_NNNN functions. That is not runnable as is: there is no host to call into. The example (example/ptx/ptx_test.cpp) and bpftime's GPU attach code post-process it as follows:

  • they rename .func bpf_main to .entry bpf_main so it can be launched as a kernel (or, in bpftime, keep it as a function and splice it into an existing CUDA kernel's PTX);
  • they rename helper references and prepend a trampoline PTX module, compiled from example/ptx/example_trampoline/default_trampoline.cu, that implements the helpers;
  • the trampoline helpers place a request in host-mapped shared memory (CommSharedMem with flag1/flag2 handshake fields) and spin until a host thread services it. Map lookups, trace_printk and the like therefore cross the PCIe bus;
  • the result is assembled with NVIDIA's PTX compiler API and launched through the CUDA driver API.

bpftime's GPU support (Chapter 15) and gpu_ext (Chapter 20) build on this path. In bpftime/attach/nv_attach_impl/pass/ptxpass_core/src/core.cpp, compile_ebpf_to_ptx_from_words() constructs an llvmbpf_vm, registers placeholder helpers including GPU-specific ones (501 puts, 503 get_block_idx, 505 get_thread_idx, 510 get_warp_id, …) and calls generate_ptx(). The placeholders only make the symbols exist; the real implementations come from the trampoline.

SPIR-V output (added in b8e4eea, October 2025) uses the triple spirv64-unknown-unknown and LLVM's in-tree SPIR-V backend. The README lists LLVM 18+ (20+ recommended) and OpenCL as requirements and shows an example run on an Intel GPU. I did not run either GPU path on hardware. The orb has no GPU, and Debian's LLVM 15 has no SPIR-V backend. PTX text generation needs no GPU, and the output in the tab above is real.

Tip

The PTX tab shows the kind of surprise to expect. Lifting to a void GPU entry point makes r0 dead, so a program that "returns" its result computes nothing. Programs written for GPU hooks must write to maps or call helpers. The same applies to any target where the entry signature differs from the eBPF calling convention.

uint64_t run_ebpf_prog(const void *code, size_t code_len)
{
	uint64_t res = 0;
	llvmbpf_vm vm;
	printf("running ebpf prog, code len: %zd\n", code_len);

	res = vm.load_code(code, code_len);
	if (res) {
		fprintf(stderr, "Failed to load: %s\n",
			vm.get_error_message().c_str());
		exit(1);

	if (!func) {

	int err = vm.exec(&bpf_mem, sizeof(bpf_mem), res);
	if (err != 0) {
		fprintf(stderr, "Failed to exec.");
		exit(1);
	}
	printf("res = %" PRIu64 "\n", res);
	return res;
}

I did not run that example, because it needs a bpftime build to produce the IR. The .ll file is checked in, though.

Newer features

Most of the code paths above are a year old or more. Several features added in 2026 extend what you can do with the lifted IR:

BTF line info → DWARF

load_line_info() (#50, September 2026) attaches DILocation metadata to every emitted IR instruction, using the .BTF.ext line records clang writes. The CLI parses .BTF.ext itself because "libbpf only populates bpf_program__line_info() after bpf_object__load()". Native code can then be mapped back to C source lines.

Kernel-compatible lift

set_kernel_compatible_mode(true) (March 2026) changes the lift to one that can be lowered back to valid kernel eBPF. Map references become external symbols such as __llvmbpf_pseudo_map_fd_XXXXXXXX. Local calls become calls to __llvmbpf_pseudo_call_pc_XXXXXXXX. The stack is sized to exactly what the program uses, and registers are zero-initialised. A branch named codex/bpfopt-llvm-roundtrip-… suggests the purpose is a bytecode → IR → optimise → bytecode round trip (see Chapter 19); I have not verified this beyond the code and the branch name.

Inspection and ablation

get_compiled_code() returns the native code pointer and size. The size comes from the symbol size of bpf_main in the object, which is how the driver above reported "31 bytes". Pass logging, disabling passes and target CPU overrides make it possible to study which LLVM passes matter for eBPF code.

LLVM version range

LLVM ≥ 15 is required. The code carries #if LLVM_VERSION_MAJOR branches up to 24, and #54 (October 2026) supports ROCm's LLVM 24 snapshot, which ships without NVPTX. In that case PTX generation reports an explicit error instead of failing to link.

Tests and conformance

Three layers of tests exist:

  • Unit tests (Catch2, test/unit-test/): conditional jumps, helper registration, AOT compile/load, error paths for bad code and missing helpers, sign-extending loads, atomics, array-map inlining, BTF line info and NVPTX availability. A separate module checks JIT and AOT from a dlopen-ed shared library with private LLVM symbols. Built with -DBPFTIME_ENABLE_UNIT_TESTING=1 in the orb, llvm_jit_tests reported All tests passed (92 assertions in 15 test cases).
  • bpf_conformance: the CI job builds a plugin (test/bpf_conformance_runner) and runs Alan Jowett's bpf_conformance suite with --cpu_version v4. The results file the README links (bpf_conformance_results.txt, fetched 6 November 2026) ends with Passed 313 out of 313 tests, including the rfc9669_* cases. That file shows no date or commit. An older snapshot checked into .github/assets/ (last changed August 2024) reports 168 of 172, failing le16-high, le32-high and lock_xchg, which later commits fixed. I did not run the conformance suite myself.
  • ubpf-style data tests (test/test_framework, pytest, 132 .data files with assembly and expected results), carried over from uBPF.

As the call-frame and division bugs above show, the suites test instruction semantics thoroughly but not every multi-frame stack layout, and not divisors that are only known at run time. A test that writes deep into a callee's stack, and a division test that loads its zero divisor from memory, would catch them.

How bpftime uses llvmbpf

In bpftime (Chapter 14), vm/llvm-jit is a git submodule pointing at llvmbpf. At bpftime commit 25e250d (3 November 2026) it is pinned to llvmbpf 87bac39 (21 September 2026), two commits behind llvmbpf's main. bpftime does not call llvmbpf directly from its runtime. It goes through a small VM abstraction so that uBPF can be swapped in:

The adapter is under a hundred lines. It subclasses llvmbpf_vm, forwards each method, and registers itself under the name "llvm" from a static constructor:

std::unique_ptr<bpftime_vm_impl> create_llvm_vm_instance()
{
	SPDLOG_DEBUG("create llvm vm instance");
	return std::make_unique<llvm::bpftime_llvm_vm>();
}
/* ... */
std::optional<compat::precompiled_ebpf_function> bpftime_llvm_vm::compile()
{
	return bpftime::llvmbpf_vm::compile();
}
/* ... */
std::optional<std::string> bpftime_llvm_vm::generate_ptx(const char *target_cpu)
{
	return bpftime::llvmbpf_vm::generate_ptx(target_cpu);
}
/* ... */
__attribute__((constructor(0))) void register_llvm_vm_factory()
{
	register_vm_factory("llvm", create_llvm_vm_instance);
	SPDLOG_DEBUG("llvm register vm factory\n");
}

In runtime/include/bpftime_config.hpp, DEFAULT_VM_NAME is "llvm", and the environment variable BPFTIME_VM_NAME overrides it (runtime/src/bpftime_config.cpp). Each bpftime_prog creates a VM by that name and calls ebpf_set_lddw_helpers(vm, map_ptr_by_fd, nullptr, map_val, nullptr, nullptr). This is how bpftime's shared-memory maps (Chapter 14) get into the lifted code: map_ptr_by_fd turns a map fd into bpftime's internal handle at compile time, and map_val returns the address of an array map's value area. Loading then calls ebpf_compile. If JIT compilation fails, the runtime logs "falling back to interpreter", which only helps when the backend has one (uBPF does, llvmbpf does not). At execution time a JITed program is a direct call: val = fn(memory, memory_size).

Two other consumers bypass the abstraction. bpftime-aot (tools/aot, "For the underlying library, see llvmbpf") exposes build, compile (programs already in bpftime shared memory), load and run. GPU attach constructs an llvmbpf_vm and an llvm_bpf_jit_context to call generate_ptx() with a chosen function name and SM version, as described above. Chapter 15 shows these from the user's side.

Benefits and limitations

Benefits

  • Quality of code. The worked example shows the effect: an unoptimised 32-instruction loop with 13 stack accesses becomes an 11-instruction register-only loop. A per-instruction JIT cannot recover that, because the information it needs, such as which stack slots never escape, spans instructions.
  • Many targets from one lifter. x86-64 and arm64 come from LLVM, and GPUs need only a different TargetMachine and a few signature changes. The PTX feature was a few hundred lines in the core library; most of its 3,100-line commit is trampoline and demo code.
  • AOT and standalone deployment. Compile once, ship a .o, link it into a C program with your own helper implementations, and run without any eBPF runtime or LLVM.
  • Helper inlining. Because helpers are ordinary external functions in IR, they can be merged and inlined (manually via llvm-link, or automatically for array maps).
  • Inspectability. -emit-llvm, DWARF line info from BTF, get_compiled_code() and pass logging make the compilation transparent.

Limitations

  • No safety of its own. No verifier, no bounds checks, no interpreter fallback. Anything the bytecode does, the native code does.
  • LLVM is heavy. Binaries embedding it are tens of megabytes, even after #52 trimmed unused backends. Compilation runs the full LLVM pipeline at run time, which costs far more than a direct emitter. The cost amortises when a program runs many times, and AOT removes it.
  • Semantic gaps from LLVM's assumptions. The lifter must add guards (division, shifts) wherever eBPF defines behaviour that LLVM leaves undefined. At the studied commit the division guards are ineffective for run-time zero divisors (SIGFPE on x86-64, see above). Alignment and data-race assumptions on plain loads and stores remain.
  • Hand-rolled calls in one function. BPF-to-BPF calls go through an IR-level call stack and indirectbr, with a 32-frame limit. As shown above, the frame offset is wrong at the studied commit.
  • Userspace calling convention. bpf_main(mem, mem_len) puts the length in r2. Kernel programs expect only a context pointer, though for most programs the extra register is harmless. Tail calls are approximated as "call helper 12, then exit".
  • GPU paths need external pieces. The PTX is not self-contained. It needs the trampoline, PTX patching and a host thread servicing helper requests over shared memory. Results must go through memory, not r0.
  • 65,535-instruction limit from the uint16_t program counter.

Check your understanding

Q1. How does the lifter represent eBPF register r3 in LLVM IR?

setupBlock creates %r0…%r10 with CreateAlloca. That makes lifting a mutable register machine easy, and costs nothing after optimisation, as the optimised IR in the worked example shows.

Q2. Why does an lddw map-value reference (src_reg = 2) become a constant in JIT mode but a call to __lddw_helper_map_val in AOT mode?

do_jit_compile passes patch_map_val_at_compile_time = true; do_aot_compile passes false. The standalone example therefore has to define __lddw_helper_map_val itself.

Q3. You AOT-compile a program that calls helper 6 and link the object into a C program. Which symbol must you define?

ext_func_sym() formats _bpf_helper_ext_%04d. The name passed to register_external_function is only a label; the index determines the symbol.

Q4. The PTX for sum.bpf.o contains a loop counter but no addition. Why?

With is_gpu the entry function type is void(ptr addrspace(1), i64) and exitBlock is ret void. GPU eBPF programs must communicate through memory or helpers.

Q5. An llvmbpf-JITed program executes r0 = *(u64 *)(r1 + 100000) on an 8-byte buffer. What happens?

emitLoadX is a GEP plus a load with no checks, and llvmbpf has no interpreter. Safety is the embedder's job; bpftime's userspace verifier only rejects programs when it is built in, runs in strict mode and covers the program type.

Q6. How do you make bpftime use uBPF instead of llvmbpf for a run?

bpftime_config.cpp reads BPFTIME_VM_NAME; DEFAULT_VM_NAME is "llvm"; compat_llvm.cpp registers the "llvm" factory from a constructor.
