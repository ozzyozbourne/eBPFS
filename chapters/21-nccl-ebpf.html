Chapter 21

NCCLbpf: verified eBPF policies inside NCCL

NVIDIA's collective communication library chooses an algorithm, a protocol and a channel count for every AllReduce. You can change that choice with a plugin, but the plugin is native code that can crash the training job. NCCLbpf replaces the native plugin logic with eBPF programs run by bpftime. This chapter covers the NCCL background you need, how the plugin calls a policy, and a problem kernel eBPF never had: every rank must make the same decision, or the collective hangs.

Prerequisites: 03, 04, 14Repo: eunomia-bpf/nccl-eBPF at 9a6006e2~50 min

Why this matters

Large-model training spends much of its time moving data between GPUs. Data-parallel training sums gradients across all GPUs after every step. Tensor-parallel inference sums partial activations inside every layer. Both of these are collective operations, and on NVIDIA hardware almost every framework (PyTorch, Megatron-LM, DeepSpeed, inference engines) runs them through NCCL, the NVIDIA Collective Communication Library.

Each NCCL call has to answer three questions: which algorithm moves the data (ring, tree, NVLink SHARP, …), which protocol signals that data has arrived (LL, LL128, Simple), and how many channels (roughly, how many GPU thread blocks and parallel connections) to use. NCCL answers them with a built-in cost model. The model is good, but it does not know your workload, your other jobs, or the quirks of a new machine. NCCL therefore lets you load a tuner plugin: a shared library whose function is called for every collective and can change the answer.

That plugin is ordinary native code inside the training process. A null pointer dereference in it kills a job that may have been running on thousands of GPUs for days. Changing its logic means restarting the job. This is the same situation the Linux kernel was in before eBPF: an extension point that only accepts trusted native modules. NCCLbpf, a research prototype from eunomia-bpf (presented at the eBPF '26 workshop), applies the eBPF answer. Policies are small restricted-C programs that are verified when loaded, JIT-compiled, and run through NCCL's existing plugin interfaces. It uses bpftime as the userspace runtime, without changing NCCL itself.

Key idea

A kernel verifier checks one program running on one machine. A collective runs the same program on many ranks, and every rank must reach the same decision. NCCLbpf therefore adds a second check at load time. It is an information-flow analysis that rejects any policy whose collective-wide action can depend on rank-local data such as this GPU's measured latency, a timer, or an ordinary map.

NCCL background a programmer needs

Ranks, communicators and collectives

A rank is one participant, usually one GPU driven by one process or thread. A communicator is a group of ranks created together (for example with ncclCommInitRank). Every rank in the communicator calls the same collective with buffers of the same size. NVIDIA's documentation defines the main operations (Collective Operations):

  • AllReduce: every rank provides N values and receives the element-wise reduction (sum, max, …) over all ranks: out[i] = in0[i] + in1[i] + … + in(k-1)[i].
  • AllGather: every rank provides N values, and every rank receives all k·N values ordered by rank.
  • ReduceScatter: the reduction is computed, and rank j keeps only the j-th block. The docs note that ReduceScatter followed by AllGather is equivalent to AllReduce.
  • Broadcast and Reduce have a root rank: one sends, or one receives.

The nccl-tests benchmarks report two bandwidths. algbw is bytes divided by time. busbw scales it by the amount of data each link must carry, so that numbers can be compared across rank counts. For AllReduce the factor is 2(n-1)/n, for AllGather and ReduceScatter (n-1)/n (nccl-tests PERFORMANCE.md). The evaluation numbers later in this chapter are busbw.

Algorithms: ring and tree (and friends)

A ring arranges the ranks in a cycle. AllReduce on a ring is a ReduceScatter phase followed by an AllGather phase. The buffer is cut into n chunks. In each of n−1 steps every rank sends one chunk to its right neighbour and adds the chunk it received from the left. After those steps, every rank owns one fully reduced chunk. Another n−1 steps circulate the finished chunks. Each rank sends about 2(n−1)/n of the buffer, which is optimal for bandwidth. The latency, however, grows linearly with n, because a chunk must travel around the whole ring.

A tree reduces up to a root and broadcasts back down, so the latency is logarithmic in n. In a single binary tree the leaves only send and the root only receives, which wastes half the link bandwidth. NCCL 2.4 introduced double binary trees: two complementary trees in which each rank is an inner node in at most one of them, each tree carrying half of the data. The result is "full bandwidth and a logarithmic latency" (Jeaugey, NCCL 2.4 blog). Newer NCCL versions add more algorithms. The pinned header lists seven: Tree, Ring, CollNetDirect, CollNetChain, NVLS, NVLSTree and PAT. NVLS and NVLSTree use NVLink SHARP, in which the NVLink switch performs the reduction with hardware multicast (NCCL_ALGO docs).

Protocols: LL, LL128, Simple

Moving bytes is half the job. The receiver must also learn that the bytes have arrived. NCCL has three ways to do this, and the Hu et al. analysis describes their trade-offs in detail (Demystifying NCCL):

  • LL (low latency): every 8 bytes written carry 4 bytes of data and a 4-byte flag. The pinned device.h defines union ncclLLFifoLine as data1, flag1, data2, flag2. The receiver spins on the flag and needs no separate synchronisation, so latency is very low, but half of the bandwidth goes to flags.
  • LL128: the same idea on 128-byte lines with one 8-byte flag per line (NCCL_LL128_LINESIZE 128, NCCL_LL128_DATAELEMS = LINEELEMS-1). It is much more efficient, but it depends on the hardware writing 128-byte lines atomically. NVIDIA warns that "enabling LL128 on platforms that don't support it can lead to data corruption" (NCCL_PROTO).
  • Simple: large chunks followed by a memory fence and a flag. It reaches the highest bandwidth, at the cost of higher per-step latency.

So the right protocol depends on message size and topology. Small messages want LL. Large ones want Simple, and LL128 sits in between where the hardware supports it.

Channels

A channel is one parallel lane of a collective. Each channel has its own ring or tree connections and its own CUDA block on each GPU, and the buffer is split across channels. More channels use more links and SMs at the same time. Fewer channels leave more SMs for compute. NCCL_MIN_NCHANNELS and NCCL_MAX_NCHANNELS bound the count. Their doc entry notes that fewer channels also means fewer CUDA blocks used for communication. Because the channel count decides how each rank partitions the buffer, it is collective-wide state, just like the algorithm.

How NCCL picks, and where a tuner plugs in

Inside ncclGetAlgoInfo in src/enqueue.cc, NCCL builds a small 2-D table collCostTable[algorithm][protocol] of predicted times. It lets the tuner edit the table and then takes the cheapest entry:

  float collCostTable[NCCL_NUM_ALGORITHMS][NCCL_NUM_PROTOCOLS];
  initCollCostTable((float **)collCostTable);
  NCCLCHECK(updateCollCostTable(comm, info, nBytes, collNetSupport, nvlsSupport, numPipeOps, (float **)collCostTable));
  if (comm->tuner != NULL) {
    /* ... compute regBuff from buffer registration ... */
    NCCLCHECK(comm->tuner->getCollInfo(
          comm->tunerContext, info->func, nBytes,
          numPipeOps, (float **)collCostTable, NCCL_NUM_ALGORITHMS, NCCL_NUM_PROTOCOLS,
          regBuff, &nMaxChannels));
    NCCLCHECK(topoGetAlgoInfo(comm, info, nBytes, (float **)collCostTable, simInfo));
  } else {
    /* ... */
  }

  info->nMaxChannels = nMaxChannels == 0 ? info->nMaxChannels : nMaxChannels;

updateCollCostTable fills only the cells this communicator can actually run. For example, it skips NVLS without NVLS support and CollNet without CollNet support, and a one-rank communicator gets only Ring/Simple. All other cells stay at −1. topoGetAlgoInfo then scans for the smallest non-negative cell:

  for (int a=0; a<NCCL_NUM_ALGORITHMS; a++) {
    for (int p=0; p<NCCL_NUM_PROTOCOLS; p++) {
      if (table[a][p] == NCCL_ALGO_PROTO_IGNORE) continue;
      if (table[a][p] >= 0.0 && table[a][p] < minTime) {
        algorithm = a;
        protocol = p;
        minTime = table[a][p];
      }
    }
  }

A tuner steers the choice by lowering a cell's cost, usually to 0. It caps channels by writing *nChannels, where 0 means "keep NCCL's choice". The plugin ABI at the pinned NCCL 2.29.7 is tuner v5:

typedef struct {

  //                    NCCL core sets ignored algo/proto cost table entries to -1.0 (NCCL_ALGO_PROTO_IGNORE).

  // Also, the plugin is allowed to not set any output, or set only the
  // algorithm and protocol, but not only the algorithm or only the protocol.
  ... */
  ncclResult_t (*getCollInfo)(void* context, ncclFunc_t collType, size_t nBytes,

NCCL finds the plugin library through NCCL_TUNER_PLUGIN and looks up the symbol ncclTunerPlugin_v5 with dlsym (src/plugin/tuner/tuner_v5.cc). Two details of this interface matter later. First, init receives the communicator id, rank and node counts, and NVL-domain info, but not this process's rank number. Second, every rank loads its own copy of the plugin and decides on its own. Nothing in the ABI makes the ranks agree.

The other plugin types

NCCL also loads net plugins (NCCL_NET_PLUGIN, symbol ncclNetPlugin_v11 in the pinned tree). These implement the transport with listen/connect/accept/isend/irecv/test and let vendors ship network code separately from NCCL (plugins/net). Profiler plugins (NCCL_PROFILER_PLUGIN) receive start/stop events for collectives and lower-level operations. NCCLbpf uses all three: tuner v5, profiler v6 and net v11.

What NCCLbpf is

NCCLbpf's README describes it as bringing "verified eBPF policy execution to NCCL". Concretely, the repo contains:

Tuner + profiler plugin

libnccl-policy.so exports ncclTunerPlugin_v5 ("eBPFPolicy") and ncclProfiler_v6. On each getCollInfo it runs an eBPF policy and applies the returned action.

Net plugin

libnccl-net-ebpf.so wraps NCCL's Socket transport and runs an eBPF program on transport events. Currently it only traces.

Policy library

src/ebpf-policies/: size-aware, NVLink-aware and telemetry policies, plus intentionally unsafe bad_* programs for verifier tests.

Rank-agreement checker

A load-time bytecode analysis that rejects policies whose action could differ across ranks, plus an experimental "agreed map".

The paper is Y. Zheng, "NCCLbpf: Verified, Composable Policy Execution for GPU Collective Communication", eBPF '26 (arXiv 2603.11438). The README is careful to call the code "a research prototype". The limitations section lists what that means in practice.

The architecture at a glance

NCCLbpf uses bpftime as a library. It does not use bpftime's LD_PRELOAD syscall server or its binary-rewriting uprobes from Chapter 14. The plugin itself plays the role of the attach point: it creates bpftime maps from the ELF object, runs bpftime's verifier, builds a bpftime_prog with the llvm VM (the llvmbpf JIT), and calls bpftime_prog_exec(&ctx, sizeof ctx, &ret) directly. Policies are tagged SEC("uprobe") because that is a section bpftime's verifier already knows. The context is plain memory that the plugin passes in.

The policy ABI: context in, action out

The context struct

A policy is a function that takes a pointer to struct nccl_policy_ctx and returns a uint64_t. The struct is versioned by appending fields. Static asserts pin the offsets, and the reserved field holds the struct size, so a policy can tell an old 72-byte host from the current 88-byte one:

#define NCCL_POLICY_CTX_ABI_V1_SIZE 72U
#define NCCL_POLICY_CTX_ABI_V2_SIZE 88U

enum nccl_policy_coll_type {
  NCCL_POLICY_COLL_BROADCAST = 0,
  NCCL_POLICY_COLL_REDUCE = 1,
  NCCL_POLICY_COLL_ALLGATHER = 2,
  NCCL_POLICY_COLL_REDUCESCATTER = 3,
  NCCL_POLICY_COLL_ALLREDUCE = 4,
};

struct nccl_policy_ctx {
  uint64_t n_bytes;
  /* Populated from profiler-fed telemetry_map snapshots when available. */
  uint64_t last_latency_ns;
  uint64_t avg_latency_ns;
  uint64_t rolling_p99_ns;
  uint64_t call_count;
  uint32_t coll_type;
  uint32_t num_pipe_ops;
  uint32_t reg_buff;
  uint32_t n_ranks;
  uint32_t n_nodes;
  uint32_t current_channels;
  /* Total context size in bytes; zero when populated by a v1 host. */
  uint32_t reserved;
  /* NVL topology supplied by the NCCL tuner v5 initialization ABI. ... */
  uint32_t n_nvl_domains;
  uint32_t min_ranks_per_nvl_domain;
  uint32_t max_ranks_per_nvl_domain;
  uint32_t reserved2;
};

The fields fall into two groups, and the rest of the chapter depends on this split. n_bytes, coll_type, num_pipe_ops, n_ranks, n_nodes and the NVL-domain fields come from getCollInfo arguments or from communicator-wide values, so they are the same on every rank. The latency fields, call_count, reg_buff and current_channels are measured or computed by this process alone.

The packed action

The return value packs five bytes. The flags say which fields the host should apply, so returning 0 means "do nothing, keep NCCL's choice":

enum nccl_policy_action_flags {
  NCCL_POLICY_ACTION_SET_ALGO = 1u << 0,
  NCCL_POLICY_ACTION_SET_PROTO = 1u << 1,
  NCCL_POLICY_ACTION_SET_CHANNELS = 1u << 2,
  NCCL_POLICY_ACTION_SET_AGGRESSIVENESS = 1u << 3,
};

static inline uint64_t nccl_policy_pack_action(uint8_t algo, uint8_t proto,
                                               uint8_t n_channels,
                                               uint8_t aggressiveness,
                                               uint8_t flags)
{
  return (uint64_t)algo |
         ((uint64_t)proto << 8) |
         ((uint64_t)n_channels << 16) |
         ((uint64_t)aggressiveness << 24) |
         ((uint64_t)flags << 32);
}

The algorithm and protocol enums in the same header mirror NCCL's numbering (Tree 0, Ring 1, …, PAT 6; LL 0, LL128 1, Simple 2), so the host can use them directly as indices into the cost table.

Paper vs. repo

Listing 1 in the paper shows a SEC("tuner") program that assigns ctx->algorithm and ctx->n_channels. The code in the repo does not work that way. Every policy returns the packed u64, and the rank-agreement checker rejects any store to the context ("write to policy context"). Read the paper's listing as illustrative and the repo headers as the real ABI. Two more differences: the paper says the tuner sets preferred cells to zero and the others to a sentinel (1e9), but apply_policy_action only zeroes the chosen cell and leaves NCCL's other costs alone; and the paper says the native baseline layer clamps channel requests to NCCL's maximum, which the eBPF path does not do (see the channels callout below).

A real policy

This is the policy behind the paper's main GPU result, tuned for one 8×B300 NVLink node:

/* nvlink_ring_mid_v2.bpf.c -- Refined NVLink-aware policy for B300 8-GPU
 *
 * v1 finding: Ring/Simple only beats NVLS at 64M-128M. At 4M-32M,
 * Ring/Simple is worse than NVLS because NCCL's auto-protocol for Ring
 * would choose LL128, not Simple.
 *
 * v2 strategy:
 *   4M-32M:   Ring/LL128 (matches what NCCL_ALGO=Ring auto-selects)
 *   64M-192M: Ring/Simple (proven +5-10% over NVLS)
 *   else:     no override (NCCL uses NVLS)
 */
#include "bpf_compat.h"
#include "policy_action.h"
#include "policy_context.h"

SEC("uprobe")
uint64_t nvlink_ring_mid_v2_policy(struct nccl_policy_ctx *ctx) {
  if (!ctx)
    return 0;

  /* 4M-32M: Ring with LL128 protocol */
  if (ctx->n_bytes >= (4ULL << 20) && ctx->n_bytes <= (32ULL << 20)) {
    return nccl_policy_pack_action(
        NCCL_POLICY_ALGO_RING, NCCL_POLICY_PROTO_LL128, 0, 0,
        NCCL_POLICY_ACTION_SET_ALGO | NCCL_POLICY_ACTION_SET_PROTO);
  }

  /* 64M-192M: Ring with Simple protocol */
  if (ctx->n_bytes >= (64ULL << 20) && ctx->n_bytes <= (192ULL << 20)) {
    return nccl_policy_pack_action(
        NCCL_POLICY_ALGO_RING, NCCL_POLICY_PROTO_SIMPLE, 0, 0,
        NCCL_POLICY_ACTION_SET_ALGO | NCCL_POLICY_ACTION_SET_PROTO);
  }

  return 0;
}

char LICENSE[] SEC("license") = "GPL";

The policy reads only n_bytes and never sets a channel count. Note that 32–64 MiB and anything above 192 MiB are left to NCCL. The repo has no libbpf headers here: bpf_compat.h defines SEC, __uint/__type and the three map helpers (ids 1–3) by hand. Inside the tuner adapter

Loading a policy

On tuner init, pluginInitImpl starts the bpftime runtime and creates a per-communicator shared state. It then loads the object named by NCCL_POLICY_BPF_PATH. If that variable is unset, it uses a built-in noop. If it is set and loading fails, init returns an error. The pipeline in load_program_from_object, trimmed:

  std::unique_ptr<struct bpf_object, decltype(&bpf_object__close)> obj(
      bpf_object__open_file(path, nullptr), &bpf_object__close);
  /* ... */
  if (!extract_program_spec(shared, obj.get(), &spec)) { /* ... */ return false; }
  if (!create_bpftime_maps(shared, policy_state, obj.get()))
    return false;
  /* ... distributed-map opt-in checks (NCCL_POLICY_EXPERIMENTAL_DIST_MAP) ... */
  attach_kernel_maps(shared, policy_state);
  if (!relocate_program_maps(shared, path, policy_state, &spec))
    return false;
  if (!verify_program(shared, policy_state, spec))
    return false;
  if (spec.section_name.rfind("profiler", 0) != 0) {
    std::unordered_set<int> agreed_fds;
    auto agreed = policy_state->map_fds.find("agreed_map");
    if (agreed != policy_state->map_fds.end())
      agreed_fds.insert(agreed->second);
    std::string agreement_error;
    if (!rank_agreement::check(spec.insns, agreed_fds, &agreement_error)) {
      log_plugin_message(shared ? shared->log_function : nullptr, NCCL_TUNING,
                         NCCL_LOG_WARN,
                         "cross-rank agreement rejected %s: %s",
                         path, agreement_error.c_str());
      return false;
    }
  }

  config.set_vm_name("llvm");
  policy_state->prog = std::make_unique<bpftime::bpftime_prog>(
      spec.insns.data(), spec.insns.size(), spec.name.c_str(),
      std::move(config));
  /* ... register_helpers(): kernel-utils + shm-maps helper groups ... */
  if (policy_state->prog->bpftime_prog_load(true) < 0) { /* "failed to JIT-load policy" */ return false; }

verify_program calls bpftime::verifier::verify_ebpf_program, bpftime's wrapper around the PREVAIL verifier (Chapter 03). It passes the map descriptors and the exact list of allowed helper ids. Its strictness comes from NCCL_POLICY_VERIFY_MODE: strict (the default) rejects, warning logs and loads anyway, and none skips verification. Sections the verifier does not know are checked with uprobe rules. Note the order. Memory safety is proven first, then cross-rank agreement, and only then does any machine code exist.

The host, not the policy, then writes into NCCL's memory. This is where the paper's "verification boundaries" are enforced. The table's dimensions and which cells are available are only known at call time, so they are checked here:

void apply_policy_action(uint64_t action, float **coll_cost_table, int num_algo,
                         int num_proto, int *n_channels) {
  const uint8_t flags = nccl_policy_action_flags_get(action);
  const int algo = nccl_policy_action_algo(action);
  const int proto = nccl_policy_action_proto(action);
  const int channels = nccl_policy_action_channels(action);

  if ((flags & NCCL_POLICY_ACTION_SET_CHANNELS) && channels > 0)
    *n_channels = channels;

  if (!coll_cost_table)
    return;

  /* NCCL passes collCostTable as float (*)[NCCL_NUM_PROTOCOLS] cast to float**.
   * It is a contiguous 2D array, NOT an array of float* pointers. ... */
  if ((flags & NCCL_POLICY_ACTION_SET_ALGO) &&
      (flags & NCCL_POLICY_ACTION_SET_PROTO) && algo >= 0 && proto >= 0 &&
      algo < num_algo && proto < num_proto && algo < NCCL_NUM_ALGORITHMS &&
      proto < NCCL_NUM_PROTOCOLS) {
    float (*table)[NCCL_NUM_PROTOCOLS] = (float (*)[NCCL_NUM_PROTOCOLS])coll_cost_table;
    if (table[algo][proto] != NCCL_ALGO_PROTO_IGNORE) {
      /* Set this algo/proto to cost 0.0 so NCCL selects it as best */
      table[algo][proto] = 0.0f;
    }
  }
}

Three rules are visible here. Algorithm and protocol apply only as a pair, which follows the v5 contract. Indices are bounds-checked. An unavailable cell (−1) is never overwritten, so a policy cannot make NCCL run a combination it did not build. The comment about float** records a real pitfall. The size_aware_v5.bpf.c header mentions an earlier crash: asking for Tree in a configuration where Tree's entry was unavailable caused a null-pointer dereference in the plugin. The IGNORE check exists to prevent exactly that.

Channels, by default

last_channels starts at 0 and is written back after each call, so a policy that never sets channels always reports 0 to NCCL. NCCL then keeps its own channel count (nMaxChannels == 0 ? info->nMaxChannels : nMaxChannels). The design notes point out that NCCL does not clamp a non-zero tuner channel value in some paths, such as CollNet and allgatherv. The plugin cannot see comm->nChannels, so a bounded channel request remains an open item.

Walkthrough: one AllReduce decision

Follow one 16 MiB AllReduce on the paper's 8×B300 node with nvlink_ring_mid_v2 loaded on all eight ranks.

1. The application calls NCCL

Each of the 8 ranks calls ncclAllReduce on a 16 MiB buffer. NCCL computes nBytes = 16777216 inside ncclGetAlgoInfo (enqueue.cc). The size is the same on every rank because the collective contract requires matching counts.

2. NCCL builds its cost table

initCollCostTable sets all 7×3 cells to −1.0. updateCollCostTable asks ncclTopoGetAlgoTime for every supported algorithm/protocol pair. On this node NVLS is available, and per the repo's sweep it is NCCL's default at every size. Its predicted time is the minimum.

3. NCCL calls the tuner

Because a tuner is loaded, NCCL calls comm->tuner->getCollInfo(ctx, ncclFuncAllReduce, 16777216, numPipeOps, table, 7, 3, regBuff, &nMaxChannels) with nMaxChannels = 0. This lands in pluginGetCollInfoImpl.

4. The plugin builds the context

It fills n_bytes=16777216, coll_type=4 (AllReduce), n_ranks=8, n_nodes=1, the NVL-domain counts, any telemetry snapshot, current_channels=0 and reserved=88. All of this is ordinary stack memory in the plugin.

5. bpftime runs the JIT'd policy

bpftime_prog_exec jumps into the LLVM-compiled code with r1 = &ctx. 16 MiB is within [4 MiB, 32 MiB], so the policy returns 0x300000101: algo=Ring(1), proto=LL128(1), channels=0, flags=SET_ALGO|SET_PROTO. The paper reports the dispatch itself at 33 ns.

6. The host applies the action

apply_policy_action sees both flags, checks bounds, checks that table[RING][LL128] is not −1, and writes 0.0 there. No channel flag is set, so *nChannels stays 0.

7. NCCL picks the cheapest cell

Back in ncclGetAlgoInfo, topoGetAlgoInfo scans for the smallest non-negative cost and finds Ring/LL128 at 0.0. NCCL then sizes threads and keeps its own channel count, because the tuner returned 0.

8. All ranks agree, so the kernels match

The policy read only n_bytes, which is identical on all 8 ranks. Every rank therefore launches the Ring/LL128 kernel with the same peers and chunking, and the ring completes. If one rank had chosen NVLS, it would wait on a different exchange and the collective would never finish. The next section is about preventing that.

The cross-rank problem

Why divergent choices deadlock

The repo's design notes put it plainly: "Every rank of a communicator must pick the same algorithm and protocol, and the same channel count, for the same collective call. Each algorithm fixes who sends what to whom; if rank 0 runs Ring and rank 1 runs Tree, each waits for data that never comes." (docs/cross-rank-agreement.md). The three outputs matter for different reasons:

  • Algorithm: selects the kernel and peer pattern. A new algorithm can even trigger transport connection setup inside ncclGroupEnd.
  • Protocol: selects the buffer format. An LL receiver spinning on 4-byte flags will never see them if the sender writes Simple chunks.
  • Channels: decide how the buffer is partitioned (enqueue.cc per the notes). Peers that split the same buffer differently disagree on which bytes travel on which channel.

NCCL keeps itself consistent by aligning inputs once, at communicator init. It runs an AllGather of per-rank graph info and takes minimums and maximums, with the comment "Make sure we align all ranks so that the tuning is consistent across ranks". Its per-call choice is then a deterministic function of those aligned values. A tuner plugin breaks this model. Each rank's copy decides alone, and the v5 ABI does not even give it the rank id. As soon as a policy reads something local, such as its own measured latency or a clock, ranks can diverge. The notes record an internal two-rank run in which the ranks logged 10 and 9 channels for the same call. Whether that run hung, corrupted data or was clamped is listed as an open experiment, so do not read it as a demonstrated deadlock.

The load-time rank-agreement check

rank_agreement_verifier.h is a header-only analysis of about 260 lines that runs on the relocated bytecode after PREVAIL accepts it. It is a forward abstract interpretation, the same technique the kernel verifier uses (Chapter 03), but the abstract value it tracks is "where did this come from", not "what range is this in". Every register and each of the 512 stack bytes carries a label: shared, local, context, stack, agreed_map, local_map, agreed_value or local_value. At entry r1 is context and r10 is stack. Loads from the context are shared only for specific byte ranges:

inline bool shared_context_access(int offset, int size) {
  // Collective arguments and communicator-wide values, including the NCCL
  // NVL-domain profile provided at communicator initialization. Timing, call
  // count, registration and previous channels remain rank-local.
  constexpr int ranges[][2] = {
      {0, 8}, {40, 48}, {52, 60}, {64, 80}};
  for (auto &range : ranges)
    if (offset >= range[0] && offset + size <= range[1]) return true;
  return false;
}

Compare these with the struct offsets. n_bytes is at 0–8, coll_type and num_pipe_ops at 40–48, n_ranks and n_nodes at 52–60, and reserved plus the three NVL fields at 64–80. The latency fields (8–32), call_count (32), reg_buff (48) and current_channels (60) are local. Note that regBuff counts as local even though it is an NCCL argument, because it reflects this rank's buffer registration. Arithmetic on two shared values stays shared; anything touching a local value becomes local. bpf_map_lookup_elem on the host-published agreed_map yields an agreed_value. Every other lookup and every other helper, timers included, yields a local value. A helper that receives a stack pointer marks the whole stack local, since it may have written there. The verdict is decided at exit and at branches:

      if (op == BPF_EXIT) {
        if (s.reg[0].kind != Kind::shared)
          return fail(pc, "rank-local action");
        if (s.local_control && !s.zero[0])
          return fail(pc, "rank-local control flow");
        exiting = true;
      } else if (op == BPF_CALL) {
        if (in.src_reg != 0) return fail(pc, "subprogram call is unanalysed");
        /* ... map_lookup on agreed_map -> agreed_value, else local_value;
               map_update/delete on agreed_map -> "policy writes agreed snapshot" ... */
      } else if (op == BPF_JA) {
        /* ... */
      } else {
        Value rhs = BPF_SRC(in.code) == BPF_X ? s.reg[in.src_reg] : scalar();
        bool local_condition =
            rank_local(s.reg[in.dst_reg]) || rank_local(rhs);
        /* ... null checks (JEQ/JNE 0) on ctx or agreed pointers are allowed ... */
        s.local_control |= local_condition;
        conditional = true;
      }

Data flow and control flow are both covered. A policy cannot return a local value, and it cannot branch on one and then return a non-zero action. Branching on local data and returning 0 on every path is fine: "local data may be computed, but it cannot affect a nonzero action". Paths are merged at join points until a fixpoint is reached, with a 200,000-step cap. Stores into the context or the agreed snapshot are rejected outright. The analysis is deliberately conservative. For example, current_channels could in principle be treated as shared by induction, since every earlier decision was checked, but today it is treated as local.

Gap found in review

The checker trusts every agreed_map lookup, whatever the key. load_memory returns shared for any load through an agreed_value pointer, the key's label is never checked, and a null test on that pointer is exempt from the control-flow rule. So a policy can compute key = ctx->last_latency_ns & 1 (no branch), look it up in a one-entry agreed_map, return 0 when the result is NULL and a channel action otherwise. Ranks with an odd latency get NULL and return 0, the others set 4 channels. I compiled exactly this program with clang 14 and fed it to rank_agreement::check through the same scratch harness used for the table below: it was accepted. A variant keyed by call_count was accepted too. This is a code reading plus a CPU-only test of the header. It was not run inside NCCL, and the plugin only loads an object with agreed_map when the experimental distributed-map opt-in, the other two distributed maps and a dist_merge section are present. Not reported upstream.

SEC("uprobe")
uint64_t adaptive_channels_policy(struct nccl_policy_ctx *ctx) {
  struct nccl_policy_telemetry_key key = {};
  struct nccl_policy_telemetry_value next = {};
  struct nccl_policy_telemetry_value *prev;
  uint32_t channels;

  if (!ctx)
    return 0;

  key.coll_type = ctx->coll_type;
  key.n_nodes = ctx->n_nodes;

  prev = bpf_map_lookup_elem(&telemetry_map, &key);
  /* ... */
  next = *prev;
  channels = clamp_channels(prev->recommended_channels);
  if (prev->samples > prev->applied_samples) {
    if (prev->last_latency_ns > prev->avg_latency_ns + 32) {
      channels = clamp_channels(channels - 1);
    } else if (ctx->n_bytes >= (1ULL << 20) &&
               prev->last_latency_ns <= prev->avg_latency_ns) {
      channels = clamp_channels(channels + 1);
    }
    next.applied_samples = prev->samples;
  }

  next.recommended_channels = channels;
  bpf_map_update_elem(&telemetry_map, &key, &next, BPF_ANY);

  return nccl_policy_pack_action(0, 0, (uint8_t)channels, 0,
                                 NCCL_POLICY_ACTION_SET_CHANNELS);
}
SEC("uprobe")
uint64_t distributed_max_latency_policy(struct nccl_policy_ctx *ctx) {
  uint32_t key = 0;
  uint64_t *max_latency;

    return 0;

  if (!max_latency)
    return 0;
  /* The same agreed value yields the same action on every rank. */
  return nccl_policy_pack_action(0, 0, *max_latency > 1000000 ? 4 : 8,
                                 0, NCCL_POLICY_ACTION_SET_CHANNELS);
}

The experimental agreed map

Rejecting all local telemetry is safe, but it throws away the closed loop. The September 2026 commits add a way to keep the loop: make the telemetry the same on every rank before the tuner reads it. In distributed_max_latency, each rank writes its own latency into local_latency. Every 1024 tuner calls the plugin exchanges these slots asynchronously, over a Unix socket on one host or over TCP to an explicit rank-0 endpoint given in NCCL_POLICY_DIST_COORDINATOR. It fills rank_slots identically on every rank, runs the verified SEC("dist_merge") program, and publishes agreed_map at the next 1024-call boundary. A second checker, rank_merge_verifier.h, ensures that the merge reads only the exchanged slots and writes only the agreed result. Agreement then follows from determinism: the same verified program on the same inputs gives the same output on every rank.

Before the first action, a round-0 exchange compares a hash of the BPF object and the plugin runtime, and a mismatch fails getCollInfo. Because tuner v5 has no rank id, the rank comes from the profiler v6 plugin, so the same library must be loaded as both. The path is opt-in (NCCL_POLICY_EXPERIMENTAL_DIST_MAP=1), supports 1–8 ranks with one rank per process, may block up to the exchange deadline (30 s by default), and refuses hot reload. The README lists its gaps in detail. NCCL does not call getCollInfo uniformly on every path: CUDA Graph replay skips it, and the symmetric-kernel and allgatherv paths add calls. The TCP COMMIT step is not atomic, so a failure partway through can leave some ranks committed and others failed. Only CPU tests exist so far, with no GPU or multi-host measurement.

Telemetry: the profiler adapter

The profiler v6 half of the library times collectives from start/stop events. In the default native mode, C++ code updates telemetry_map. In ebpf mode (NCCL_POLICY_PROFILER_MODE=ebpf plus NCCL_POLICY_PROFILER_BPF_PATH), a separately verified program does the update:

SEC("profiler")
uint64_t record_latency(struct nccl_profiler_ctx *ctx) {
  struct nccl_policy_telemetry_key key = {};
  struct nccl_policy_telemetry_value next = {};
  struct nccl_policy_telemetry_value *prev;

  if (!ctx || ctx->latency_ns == 0)
    return 0;

  key.coll_type = ctx->coll_type;
  key.n_nodes = ctx->n_nodes;
  prev = bpf_map_lookup_elem(&telemetry_map, &key);
  if (prev)
    next = *prev;

  next.last_latency_ns = ctx->latency_ns;
  next.avg_latency_ns =
      prev ? (next.avg_latency_ns == 0
                  ? ctx->latency_ns
                  : (next.avg_latency_ns * 7 + ctx->latency_ns) / 8)
           : ctx->latency_ns;
  /* ... p99 estimate, last_n_bytes, observed_channels, samples++ ... */
  bpf_map_update_elem(&telemetry_map, &key, &next, BPF_ANY);
  return 0;
}

Profiler programs skip the rank-agreement check (section_name.rfind("profiler", 0) != 0), because recording local measurements is harmless. Only a tuner action that depends on them is dangerous. This is the output-scoped idea from the design notes. Tuner outputs must agree across the communicator. A net plugin's per-connection choice must agree between the two ends. Profiler writes need no agreement at all.

The net plugin: tracing the transport

The second library implements ncclNet_v11 with .name = "Socket" and forwards every call to NCCL's built-in Socket backend. After each successful init/listen/connect/accept/isend/irecv/finalize, it runs an eBPF program with a small event context:

ncclResult_t pluginIsendImpl(void *send_comm, void *data, size_t size, int tag,
                             void *mhandle, void *phandle, void **request) {
  auto *ctx = unwrap_ctx(send_comm);
  ncclNet_t *base =
      resolve_socket_backend(ctx ? ctx->log_function : nullptr);
  ncclResult_t ret;
  /* ... */
  ret = base->isend(unwrap_comm(send_comm), data, size, tag, mhandle, phandle,
                    request);
  if (ret == ncclSuccess && request && *request)
    exec_policy_hook(ctx, NCCL_NET_EBPF_HOOK_ISEND, unwrap_dev(send_comm), size,
                     tag);
  return ret;
}

The default program only counts:

SEC("uprobe")
uint64_t net_trace_policy(struct nccl_net_ebpf_ctx *ctx) {
  uint32_t key;
  struct nccl_net_ebpf_stat *stat;

  if (!ctx)
    return 0;

  key = ctx->hook;
  if (key >= NCCL_NET_EBPF_HOOK_COUNT)
    return 0;

  stat = bpf_map_lookup_elem(&stats_map, &key);
  if (!stat)
    return 0;

  stat->calls += 1;
  stat->bytes += ctx->size;
  stat->last_comm_id = ctx->comm_id;
  stat->last_tag = ctx->tag;
  return 0;
}

The return value is ignored, so this hook cannot rate-limit or reject anything yet. There is also a practical catch. resolve_socket_backend looks up ncclNetSocket with dlsym, trying RTLD_DEFAULT, then dlopen(..., RTLD_NOLOAD) by soname, then the path found in /proc/self/maps. The pinned NCCL builds with hidden symbols and does not export it. The recorded experiment patched one line of NCCL to export the symbol and rebuilt. So, unlike the tuner/profiler plugin, the net wrapper is not demonstrated on unmodified NCCL. Check your library with nm -D nccl/build/lib/libnccl.so | grep -w ncclNetSocket.

Hot reload

The active policy is a std::shared_ptr read with std::atomic_load_explicit. Reload goes through the debug export ncclPolicyPluginDebugReloadPolicy. It runs the full load pipeline (verify, rank check, JIT) on the new object and only then calls std::atomic_exchange_explicit. In-flight calls keep their reference to the old program, and a failed load leaves the old policy in place. The paper describes this as a compare-and-swap on a function pointer, which is the same idea. Note the limit the design notes point out. The paper's claim that briefly running different policies is fine "because calls are independent" holds within one process, but not across ranks. Ordinary reload is per process and not coordinated, and distributed-policy reload is refused.

Composability and the net plugin

With the profiler feeding telemetry_map, adaptive_channels ramped from 2 to 12 channels over 100,000 calls, dropped to 2 under injected 10× latency, and recovered to 12. As shown above, the current checker rejects this policy, so treat the experiment as a demonstration of the map mechanism, not of a deployable policy. The net-plugin experiment ran on an RTX 5090 with two ranks sharing one GPU over Socket at 128 MB. The mean was 2.134 GB/s baseline vs 2.094 GB/s wrapped (about 1.87% slower), and the medians were 2.13 vs 2.15, which the notes read as roughly noise-level.

Benefits and limitations

What you get

  • Crash-proof policy code. Memory-safety and termination bugs are rejected before execution. The native-vs-eBPF null-dereference comparison is the clearest demonstration.
  • No NCCL changes for the tuner and profiler paths: they use the stock v5/v6 ABIs.
  • Per-call, per-size decisions that environment variables cannot express, at a cost of tens to a hundred-odd nanoseconds.
  • Verified hot swap within a process, plus typed maps shared between profiler and tuner.
  • A distributed-consistency check that is, as far as the paper claims, new for eBPF. The repo's prior-art section compares it to Titanium's single qualifier and PARCOACH-style taint analysis in MPI.

What it does not do (yet)

  • Verification covers safety, not quality: bad_channels passes and loses 87–95% of throughput.
  • The trusted computing base includes the host plugin, bpftime's JIT and the PREVAIL-based verifier. Policies are assumed to come from platform operators, not hostile tenants.
  • The rank check is conservative and has known gaps: host-side availability can still differ per rank (for example a per-process NCCL_ALGO), channel requests are not bounded by comm->nChannels, and only tuner programs are checked.
  • The agreed map is experimental, limited to 8 ranks, has non-atomic COMMIT, and does not handle CUDA-graph replay or the symmetric-kernel call-count paths.
  • The net plugin only observes, and it needs an NCCL build that exports ncclNetSocket.
  • All GPU results come from one node with 8 GPUs on NVLink. Multi-node InfiniBand runs are future work, as the paper says.
  • Policies can only choose among NCCL's built-in algorithms. They cannot change ring order or tree shape, which NCCL fixes at init.

Related work

  • Other NCCL tuners. AutoCCL (NSDI '25) searches NCCL's low-level parameters online, built on a modified NCCL. Per the repo's notes, rank 0 decides and broadcasts versioned schedules, so its agreement comes from a leader deciding (the notes: "They agree by a leader or manager deciding"). NCCLbpf's agreed map instead runs the same verified merge on every rank. NVIDIA ships an example CSV-driven tuner in plugins/tuner/.
  • Collective synthesis. TACCL (NSDI '23) and MSCCL synthesise schedules offline. NCCLbpf only picks among built-in algorithms, and the paper describes the two as complementary.
  • Understanding NCCL. Hu et al., "Demystifying NCCL" (HOTI 2025 / arXiv 2507.04786), is the best reference for protocols, channels and algorithms.
  • eBPF beyond the CPU. Chapter 20 (gpu_ext) puts eBPF policies in the GPU driver for memory and scheduling. NCCLbpf works one layer up, in the communication library. Chapter 22 covers CPU+GPU profiling.
  • The runtime. Chapter 14 (bpftime design, verifier options, shared maps) and Chapter 16 (the LLVM JIT used here). Chapter 15 shows bpftime's own attach modes, which NCCLbpf does not use.

Check your understanding

Q1. How does an NCCLbpf policy make NCCL use Ring/LL128 for a given call?

apply_policy_action zeroes table[algo][proto] if the cell is not −1, and topoGetAlgoInfo selects the lowest non-negative cost. Context writes are rejected by the rank-agreement check.

Q2. Why is it dangerous for a tuner policy to choose channels from this rank's measured p99 latency?

Algorithm, protocol and channel count are collective-wide. Each rank's plugin decides on its own, so decisions must depend only on inputs that are the same on every rank.

Q3. Which context field is treated as shared by rank_agreement_verifier.h?

The shared byte ranges are 0–8, 40–48, 52–60 and 64–80. n_nodes is at offset 56. reg_buff reflects local buffer registration, and current_channels and call_count are per-process state.

Q4. A policy branches on last_latency_ns but returns 0 on both paths. What does the checker say?

At exit it fails only if local_control && !zero[r0]. The repo test benign_local_branch checks exactly this case.

Q5. What can the current net plugin's eBPF program do?

exec_policy_hook discards the return value, and the README says it "does not enforce transport decisions". The wrapper also needs ncclNetSocket to be exported, which the pinned default NCCL build does not do.

Q6. How does the experimental agreed map keep ranks consistent while still using measured latency?

Agreement follows from determinism: the same program on the same data gives the same value. Round 0 also compares object and runtime hashes. The README calls the path experimental, for example because TCP COMMIT is not atomic.
