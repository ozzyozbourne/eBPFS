Chapter 29

qwen3-ebpf: a language model forward pass inside eBPF

Can the kernel's verified BPF virtual machine do the arithmetic of a real 0.6-billion-parameter language model, rather than just watch one run? The eunomia-bpf experiment qwen3-ebpf says yes. All 28 decoder layers of Qwen3-0.6B, a KV cache, the 151,936-row vocabulary projection and the final argmax run as BPF programs that a stock Linux 6.17 verifier accepts. The project then measures why you would not want to do this. This chapter teaches just enough about transformers to follow the code. Then it shows how the repo maps each piece onto maps, arenas, bpf_loop, XDP and a BPF workqueue, and what the experiment says about where eBPF stops.

Prerequisites: 03 (verifier limits), 04 (maps, bpf_loop, arena, kfuncs), 07 (XDP) Repo: eunomia-bpf/qwen3-ebpf (studied at commit 3999b88, 2026-10-27)~55 min

Why this matters

Most eBPF programs are small and quick. They count a system call, drop a packet or pick a CPU, and they finish in microseconds. When the kernel community talks about "machine learning in the kernel", it usually means a decision tree or a tiny quantized network that makes one decision per event. Large language models stay in user space, on a GPU or in a CPU inference engine, and eBPF at most traces them (see 22 · xpu-perf) or feeds them signals.

qwen3-ebpf turns the question around and pushes it as far as it goes. Its four-page report, Can eBPF Run a Real Language Model? Lessons from a Kernel-Resident Qwen3 Forward Pass, calls the system bpfllm. The point is not to serve chat from the kernel. The point is to find out which limit binds first when verified BPF code tries to do dense numerical work:

  • the verifier, with its one-million-instruction budget, bounded loops and 512-byte stack (chapter 03);
  • the instruction set, which has 64-bit integer arithmetic but no floating point and no vector instructions (chapter 02);
  • the execution model: programs run to completion from a hook, and every trip from user space into a BPF program is a system call.

The answer the repo reaches is worth knowing before you read the code. The verifier shaped the code but never stopped it. Crossing the user/kernel boundary mattered at first, then stopped mattering. What finally limits speed is the instruction set: one ordinary CPU core running the BF16 model in PyTorch was 1.8 to 4.8 times faster than the eBPF path on the sequences the authors measured.

Key idea

A transformer forward pass is mostly matrix-vector products plus a few small nonlinear steps. qwen3-ebpf rewrites every step in integer fixed-point arithmetic and splits it into bounded units (128 matrix rows, a 128-element tile, one attention head) that a bpf_loop callback can do. A scheduler then chains those units together: a C loop in user space, or a BPF workqueue item that requeues itself.

Research prototype

The README is explicit: "Do not use this on production kernels." The recorded test host was Linux 6.17 on arm64. No model weights are in the repository. Everything below that cites a number comes from the repo's docs/experiments.md or its report. Those are mostly single runs on a shared host, and the authors describe them that way.

Transformer forward pass in fifteen minutes

You do not need deep learning background to read this repo. You do need to know what one "forward pass" computes, because every BPF program in the repo implements one line of the following recipe. The model is Qwen3-0.6B, the smallest dense model described in the Qwen3 Technical Report (arXiv 2505.09388, 2025). The report says Qwen3's dense models use grouped-query attention, SwiGLU, rotary position embeddings and RMSNorm with pre-normalization, drop the QKV bias of Qwen2, and add QK-Norm.

Step by step

A token is an integer ID produced by the tokenizer (for example, the text Hello, world! becomes [9707, 11, 1879, 0] with the official tokenizer). To predict the next token, the model does the following for each input position:

  1. Embedding. Look up row token_id of a 151,936 × 1,024 table. The result is the 1,024-element hidden vector h. This is a memory read, not arithmetic.
  2. RMSNorm. Before each sub-block, rescale the vector so its root mean square is 1, then multiply element-wise by a learned weight vector g: yi = gi · xi / sqrt(mean(x²) + ε), with ε = 10-6. You need a sum of squares, a square root and a division.
  3. Q, K, V projections. Three matrix-vector products turn the normalized vector into a query (2,048 values = 16 heads × 128), a key (1,024 = 8 heads × 128) and a value (1,024 = 8 heads × 128).
  4. QK-Norm. Qwen3 applies a second RMSNorm to each 128-wide query and key head, with its own small weight vectors.
  5. RoPE (rotary position embedding). Position is encoded by rotating pairs of query/key coordinates by an angle that depends on the token's position p and the pair index i: angle = p · θ−i/64. Each pair (a, b) becomes (a cos − b sin, b cos + a sin). Dot products between rotated queries and keys then depend on the relative distance between positions.
  6. Causal attention with GQA. For each query head, compute a score against the key of every earlier position (and the current one): q·k / sqrt(128). Turn the scores into weights with softmax, and output the weighted sum of the value vectors. In grouped-query attention (GQA), several query heads share one key/value head. Qwen3-0.6B has 16 query heads and 8 KV heads, so query heads 2j and 2j+1 both read KV head j.
  7. Output projection and residual. A 1,024 × 2,048 matrix maps the concatenated heads back to 1,024 values, which are added to h (the residual connection).
  8. SwiGLU MLP. RMSNorm again, then two 3,072 × 1,024 projections called gate and up. Apply SiLU to the gate (SiLU(x) = x · sigmoid(x)), multiply element-wise by up, project back down with a 1,024 × 3,072 matrix, and add the result to h.
  9. Repeat steps 2–8 for all 28 layers, each with its own weights.
  10. Logits and argmax. A final RMSNorm, then multiply by the 151,936 × 1,024 embedding matrix again (Qwen3-0.6B ties input and output embeddings). The result is one score ("logit") per vocabulary entry. Greedy decoding picks the largest.

The KV cache

Step 6 needs the keys and values of all earlier positions. Recomputing them for every new token would repeat the whole prompt each time, so inference engines keep a KV cache: after computing K and V for a position, they store them per layer and per KV head. The next token only computes its own Q/K/V and reads the history. In Qwen3-0.6B one position adds 28 layers × 8 KV heads × (128 + 128) values. qwen3-ebpf stores each value as a 4-byte integer, which gives the repo's figure of 1 KiB per (position, layer, head) slot and about 224 KiB per position.

Quantization in one paragraph

The official weights are BF16 ("brain float 16"): the top 16 bits of an IEEE float32, with 1 sign bit, 8 exponent bits and 7 mantissa bits. Quantization means storing numbers in a cheaper format. Integer quantization (INT8, INT4) stores small integers plus a floating-point scale per group of weights. Fixed point (Qn) stores a real number x as the integer round(x · 2n). A Q16 value of 65,536 means 1.0. Fixed point needs no floating-point unit at all: adding two Q16 numbers is an integer add, and multiplying a Q16 by a Q24 gives a Q40 product that you shift right by 24 to get back to Q16. That is the trick the whole repo depends on.

Where the arithmetic is

Count the multiply-accumulates (MACs). Per layer: Q 2,048×1,024 + K and V 1,024×1,024 each + O 1,024×2,048 + gate, up and down 3,072×1,024 each = about 15.7 million. Over 28 layers that is about 440 million, and the vocabulary projection adds 151,936 × 1,024 ≈ 155.6 million. The total is about 596 million MACs per token, which matches the report's figure ("about 596 million ... 26% of them in the vocabulary projection"). Attention itself is tiny for short contexts: 16 heads × 128 MACs per earlier position for the scores, plus the same again for the values. So this is a matrix–vector product machine with some decoration. Every weight is read once per token, which is about 1.2 GB of BF16 per token.

Operator mode (default)

make builds build/infer. C owns the schedule: for every layer it fills a memory-mapped map, runs one BPF program with BPF_PROG_RUN, and reads the result. Needs only bpf_loop (Linux 5.17+) and mmapable array maps.

Arena operator mode (optional)

make build/infer-arena-bf16. The same C schedule, but the full BF16 model is copied once into a BPF arena and the BPF matrix program converts weights itself. Needs arena support (Linux 6.9+), Clang 19 and an arena-capable libbpf/bpftool.

Event mode (optional)

make build/serve-xdp. A UDP packet hitting XDP queues a BPF workqueue item, which walks all 28 layers and the vocabulary head with no user-space dispatch, and the result comes back through XDP_TX. Needs bpf_wq (Linux 6.10+) as well.

Integer arithmetic for a float model

The report summarizes the number formats in one sentence: "Activations use Q16, matrix weights Q24 and normalization scales Q20, because some official norm weights are too large for Q24 in 32 bits. Products accumulate in 64 bits." A Q16 activation times a Q24 weight is a Q40 product. Summing up to 3,072 of them in a signed 64-bit accumulator and shifting right by 24 gives a Q16 result.

Why Q24 and not the INT8 that every inference engine uses? The repo measured it on one real row of the layer-0 Q projection. The BF16 reference dot product was -0.00837016106. Q24 gave -0.0083770752. Q8 gave -0.0366821289, more than four times too large, because large terms cancel and the rounding errors do not. The experiments that tried group-scaled INT8 and INT4 across the whole model changed the generated tokens (more on that under performance), so the default path keeps Q24.

The matrix operator

Here is the program that does nearly all of the arithmetic in operator mode. The map value is a 1.51 MiB struct holding one input vector, 128 rows of Q24 weights and 128 outputs:

#define QWEN3_BATCH_ROWS 128
#define QWEN3_BATCH_COLS 3072

/* One BPF invocation computes up to 128 complete rows. */
struct qwen3_batch_work {
    __s32 input_q16[QWEN3_BATCH_COLS];
    __s32 weight_q24[QWEN3_BATCH_ROWS][QWEN3_BATCH_COLS];
    __s64 output_q16[QWEN3_BATCH_ROWS];
    __u32 rows;
    __u32 cols;
    __u32 completed;
    __u32 track_argmax;
    __u32 base_index;
    __u32 best_index;
    __s64 best_q16;
};
struct {
    __uint(type, BPF_MAP_TYPE_ARRAY);
    __uint(map_flags, BPF_F_MMAPABLE);
    __uint(max_entries, 1);
    __type(key, __u32);
    __type(value, struct qwen3_batch_work);
} batch SEC(".maps");

static long compute_row(__u32 row, void *ctx)
{
    const __u32 key = 0;
    struct qwen3_batch_work *work = bpf_map_lookup_elem(&batch, &key);
    __s64 sum = 0;
    __u32 bounded_row = row & (QWEN3_BATCH_ROWS - 1);
    int i;

    (void)ctx;
    if (!work || row >= work->rows)
        return 1;
#pragma clang loop unroll(disable)
    for (i = 0; i < QWEN3_BATCH_COLS; i++) {
        if (i >= work->cols)
            break;
        sum += (__s64)work->input_q16[i] * work->weight_q24[bounded_row][i];
    }
    work->output_q16[bounded_row] = sum >> 24;
    if (work->track_argmax && work->output_q16[bounded_row] > work->best_q16) {
        work->best_q16 = work->output_q16[bounded_row];
        work->best_index = work->base_index + row;
    }
    work->completed++;
    return 0;
}

SEC("socket")
int qwen3_batch_rows(struct __sk_buff *skb)
{
    const __u32 key = 0;
    struct qwen3_batch_work *work = bpf_map_lookup_elem(&batch, &key);
    __u32 callback_ctx = 0;

    (void)skb;
    if (!work || !work->rows || work->rows > QWEN3_BATCH_ROWS ||
        !work->cols || work->cols > QWEN3_BATCH_COLS)
        return 0;
    bpf_loop(work->rows, compute_row, &callback_ctx, 0);
    return 0;
}

Read it with the verifier in mind (chapter 03):

  • bpf_loop(work->rows, compute_row, ...): the row loop is not BPF code at all. The kernel helper calls compute_row up to rows times. The verifier checks the callback once with an unknown row argument instead of walking 128 iterations (see bpf_loop in chapter 04).
  • row & (QWEN3_BATCH_ROWS - 1): row is only known to be some u32. Masking with 127 gives the verifier a provable bound for the 2D array index. The earlier row >= work->rows check is against a value in map memory, which the verifier cannot use as a constant bound.
  • #pragma clang loop unroll(disable) keeps the 3,072-iteration column loop as a real bounded loop (Linux 5.3+). Unrolled, it would be thousands of instructions per callback.
  • Fused argmax. For the vocabulary projection, C sets track_argmax, and the callback keeps the best logit as it goes. That removed a separate pass and cut one-token bpf() calls from 16,043 to 12,482.
  • The program type is a lie, on purpose. SEC("socket") makes it a socket filter, but it is never attached to a socket. A socket filter is simply a program type that BPF_PROG_RUN can execute on demand with a dummy packet.

Square roots, exponentials and SiLU without floats

RMSNorm needs 1/sqrt(mean(x²) + ε). The norm program sums squares of Q16 values (giving Q32), adds ε in Q32 (10-6 · 232 ≈ 4,295), and runs a fixed 24-iteration Newton square root:

static __always_inline __u64 isqrt64(__u64 value)
{
    __u64 root = 1ULL << 20;
    int i;

#pragma clang loop unroll(disable)
    for (i = 0; i < 24; i++) {
        root = (root + value / root) >> 1;
        root |= 1;
    }
    return root;
}
/* ... accumulate_tile() and apply_tile() are bpf_loop callbacks over 128-wide tiles ... */

SEC("socket")
int qwen3_rms_full(struct __sk_buff *skb)
{
    /* ... */
    bpf_loop(work->total_tiles, accumulate_tile, &callback_ctx, 0);
    if (work->completed_tiles != work->total_tiles)
        return 0;
    /* eps=1e-6, expressed in Q32 as 4295. */
    root = isqrt64(work->sum_sq_q32 /
                   (work->total_tiles * QWEN3_TILE_WIDTH) + 4295);
    work->inv_rms_q16 = (1ULL << 32) / root;
    if (!work->inv_rms_q16)
        return 0;
    bpf_loop(work->total_tiles, apply_tile, &callback_ctx, 0);
    return 0;
}

Note the root |= 1: it keeps the divisor nonzero, which matters because the verifier does not reject division by zero. BPF defines x / 0 = 0, but a zero root would silently produce garbage. The shape of the program (two bpf_loop passes around a scalar step) was forced by the verifier. docs/architecture.md records that "An earlier monolithic implementation exceeded the verifier's one-million-instruction processing budget on the test kernel; the callback-based version passed."

SiLU needs sigmoid, which needs e−|x|. The repo uses the textbook limit e−a = lim (1 − a/n)n with n = 1,024 = 210, so the power is just ten squarings in Q32:

static __always_inline __s32 silu_q16(__s32 x)
{
    __u64 magnitude = x < 0 ? -(__s64)x : x;
    __u64 exponential, denominator, sigmoid;
    int i;

    if (!x)
        return 0;
    if (magnitude >= (16ULL << 16))
        return x > 0 ? x : 0;
    /* exp(-|x|) = lim_n (1 - |x|/n)^n, n=1024, in Q32. */
    exponential = (1ULL << 32) - (magnitude << 6);
#pragma clang loop unroll(disable)
    for (i = 0; i < 10; i++)
        exponential = (exponential * exponential) >> 32;
    denominator = (1ULL << 32) + exponential;
    sigmoid = x >= 0
        ? (1ULL << 48) / denominator
        : (exponential << 16) / denominator;
    return (__s32)(((__s64)x * (__s64)sigmoid) >> 16);
}

magnitude << 6 is |x|/1,024 converted from Q16 to Q32 (232/216/210 = 26). Beyond |x| ≥ 16, SiLU is treated as x or 0. The repo's smoke test reports a maximum absolute error of 0.000634 over [−8, 8] against a C floating-point reference. The same exponential, as exp_negative_q32, drives the attention softmax. Converting weights: the 65,536-entry table

The weights arrive as BF16. On the default path, C converts each active matrix row to Q24 before handing it to BPF. Because BF16 has only 65,536 bit patterns, safetensors.c builds a table of all of them once and converts a row with one load per weight. An exhaustive test checks that the table matches the floating-point formula for every finite pattern. The repo measured this change at 1.425/1.576/1.476 s → 1.154/1.258/1.049 s per token, with byte-identical logits. The same table is what made BF16 weights usable inside BPF. The report says "Converting BF16 to Q24 inside the 3,072-column loop failed with 'The sequence of 8193 jumps is too complex'; a 65,536-entry lookup table indexed by the BF16 bit pattern replaced the branches with a single load." In the arena path, that table (q24_by_bf16, 256 KiB) lives in the arena next to the weights.

Operator mode: C schedules, BPF computes

The default build/infer keeps the model's control flow in user space. Think of the six BPF objects as a tiny instruction set of "kernel ops" (matrix batch, RMSNorm, QK-Norm, RoPE, attention, SiLU, add, multiply). src/infer.c is the program that calls them in order. The architecture doc is careful about the boundary: "C chooses the operator order and supplies the current weights and vectors." It also says the user-space driver "cannot substitute user-space model math for kernel forward computation". Embeddings and RoPE sin/cos values are prepared in C, and every multiply-accumulate happens in BPF.

Three pieces of host code make this work. First, the "run one operator" primitive. It is the standard BPF_PROG_RUN test-run command with a zeroed 64-byte packet, because a socket filter needs some packet:

static int call_kernel(int fd)
{
    const uint8_t packet[64] = {0};
    struct bpf_test_run_opts opts = {
        .sz = sizeof(opts),
        .data_in = packet,
        .data_size_in = sizeof(packet),
        .repeat = 1,
    };
    return bpf_prog_test_run_opts(fd, &opts);
}

static void *map_shared(int fd, size_t bytes, size_t *length)
{

bpf_map__set_max_entries between open and load is how the KV cache gets its size: libbpf creates the map with the new size when the object is loaded. The completed counter is a cheap integrity check. bpf_loop stops early if a callback returns 1, and the C side refuses results unless every row ran. Third, the layer loop itself reads like any textbook transformer, with every arithmetic step a kernel call:

            kernel_vector(&engine, 1, activated, up,
                          QWEN3_INTERMEDIATE, product))
            goto layer_fail;
        /* ... down_proj + residual ... */
        }
        /* ... */
        engine.batch_work->track_argmax = 1;
        engine.batch_work->best_q16 = INT32_MIN;
        engine.batch_work->best_index = 0;
        if (kernel_norm(&engine, "model.norm.weight", hidden,
                    QWEN3_HIDDEN_SIZE, normed) ||
            kernel_matrix(&engine, "model.embed_tokens.weight",
                      QWEN3_VOCAB, QWEN3_HIDDEN_SIZE,
                      normed, 0, logits)) {
            /* ... */
        }
        next_id = engine.batch_work->best_index;

So where are the weights? On this path they never become kernel-resident. They sit in the page cache behind a read-only file mapping, and C copies 128 converted rows at a time into the batch map. Output comes back the same way: C reads output_q16[] and best_index straight from the shared pages, with no bpf_map_lookup_elem syscall. Reading results is just a memory load.

One token through the operator programs

Step through what happens for one token at position p < 256 on the default path. The call counts per layer are my own count from src/infer.c, using 128-row batches. They add up to about 105 program runs per layer plus 1,188 for the output head, about 4,128 in total. That is consistent with the 4,169 bpf() calls the repo measured, which also include setup.

1. Embedding (C)

load_embedding() reads row token_id of model.embed_tokens.weight from the mapped file and converts its 1,024 BF16 values to Q16. No BPF runs yet. This is a lookup, not arithmetic.

2. Input RMSNorm — 1 run

C writes the hidden vector and the layer's norm weights (as Q20) into the mmapped norm map and runs qwen3_rms_full. Two bpf_loops over eight 128-wide tiles do the sum of squares and the scaling, with isqrt64 in between.

3. Q, K, V projections — 32 runs

qwen3_batch_rows runs 16 times for Q (2,048 rows) and 8 times each for K and V (1,024 rows). Each run is a bpf_loop over 128 rows of 1,024 Q24 weights: 131,072 MACs per run.

4. QK-Norm and RoPE — 2 runs

qwen3_qk_norm_heads normalizes all 16 query and 8 key heads in one call (24 callback iterations). qwen3_rope_apply rotates the same 24 heads. C computed the 64 cos/sin pairs for position p with libm and stored them as Q20.

5. Attention and KV cache — 1 run per 256 positions

qwen3_attention_all_heads first stores the new K/V for all 8 KV heads into the kv map at slot (p·28 + layer)·8 + h. Then it walks positions 0..p with bpf_loop. Each KV pair it looks up feeds two query heads (GQA), using an online softmax so no score array is needed.

6. Output projection and residual — 9 runs

8 batch runs for the 1,024 × 2,048 O matrix, then qwen3_vector_add adds the result into the hidden vector (8 tiles in one call).

7. MLP — 60 runs

Post-attention RMSNorm (1), gate and up projections (24 + 24 batch runs of 3,072 rows in total each), qwen3_silu_apply over 3,072 values (1), qwen3_vector_multiply (1), down projection (8 runs of 128 rows × 3,072 columns, the widest callbacks) and the second residual add (1).

8. Repeat 28 times

Steps 2–7 run for layers 0–27, each with its own tensors named model.layers.N.*. The KV map now holds this position's keys and values for every layer, ready for the next token.

9. Output head — 1,188 runs

Final RMSNorm (1 run), then 1,187 batch runs over the 151,936 rows of the tied embedding matrix with track_argmax = 1. Each callback compares its logit with best_q16.

10. Read the answer

C reads best_index and best_q16 from the mmapped batch map. With --tokenizer, it decodes the ID to bytes in user space. With --generate N, the ID becomes the next input and the loop runs again from step 1. Only the new position is computed, because the history is in the KV map.

Getting a transformer past the verifier

The report's headline lesson is "The verifier shapes the code but is not a wall." It names only two rejections that needed a redesign: the monolithic RMSNorm (over the one-million budget) and in-loop BF16 conversion ("8193 jumps is too complex"). The rest is a set of habits applied to every program. Here they are as a checklist you can reuse for any heavy BPF code:

  1. Size the unit of work for one callback. A bpf_loop callback is verified once, whatever the iteration count. The repo batches 128 matrix rows, up to eight RMSNorm tiles, 24 Q/K heads, 24 SiLU tiles or 256 attention positions per invocation. The architecture doc gives the reason: "Bounded units keep verifier complexity and per-invocation runtime manageable."
  2. Keep inner loops rolled. Every fixed-trip loop carries #pragma clang loop unroll(disable). The verifier's bounded-loop support handles it, and the instruction count stays small.
  3. Mask indexes to powers of two. row & 127, head & 31, index & 4095u. The vector map even uses a capacity of 4,096 for a maximum of 3,072 elements, with the comment "Power-of-two backing keeps callback indices verifier-bounded."
  4. Stop the compiler from undoing the mask. When Clang can prove a mask is redundant, it deletes it, and the verifier then sees an unbounded index. The arena code uses an empty asm volatile as an optimization barrier: 
    static __always_inline __u32 event_q_slot(__u32 base, __u32 offset)
{
    __u32 index = base + offset;

    asm volatile ("" : "+r"(index));
    return index & 2047;
}
  5. No large stack objects. All vectors live in single-entry array map values. Each callback looks the map up again (bpf_map_lookup_elem(&work, &key)) instead of receiving a pointer through ctx, so the verifier sees a fresh map-value pointer of known size in every callback.
  6. Replace branchy math with tables. The BF16 decode became a lookup; the RoPE inverse frequencies in the XDP path are a 64-entry constant table (rope_freq_q48).
  7. Split across programs, not tail calls. The repo never uses bpf_tail_call or BPF-to-BPF calls beyond the bpf_loop callbacks. "Program splitting" means separate BPF objects per operator, chained by a scheduler outside the program.

Attention and the KV cache in BPF

Softmax over scores s0 … sp normally needs all scores first (to find the maximum, for numerical stability), then a second pass. qwen3-ebpf uses the online form (Milakov and Gimelshein, 2018) that also underlies FlashAttention. Keep a running maximum m, a running mass d = Σ es−m and a running output o. When a new score arrives, rescale what you have if the maximum grew, then blend the new value vector in with weight α = w / (d + w). Only O(head_dim) state per head is needed, however long the history:

static __always_inline void attention_accumulate(struct qwen3_attention_state *work,
                                                  const __s32 *key_q16,
                                                  const __s32 *value_q16)
{
    /* ... */
#pragma clang loop unroll(disable)
    for (i = 0; i < QWEN3_TILE_WIDTH; i++)
        dot += (__s64)work->query_q16[i] * key_q16[i];
    /* Q16 dot scaled by 1/sqrt(128), also Q16 (5793/65536). */
    score = ((dot >> 16) * 5793) >> 16;
    /* ... first position: output = value, max = score, mass = 1.0 ... */
    delta = score - work->max_score_q16;
    if (delta > 0) {
        __u64 factor = exp_negative_q32((__u32)delta);
        mass = ((work->mass_q16 >> 16) * factor) >> 16;
        mass += ((work->mass_q16 & 65535) * factor) >> 32;
        weight = 1ULL << 16;
        work->max_score_q16 = work->score_q16;
    } else {
        mass = work->mass_q16;
        weight = exp_negative_q32((__u32)-delta) >> 16;
    }
    new_mass = mass + weight;
    if (!new_mass)
        return;
    alpha_q24 = (weight << 24) / new_mass;
#pragma clang loop unroll(disable)
    for (i = 0; i < QWEN3_TILE_WIDTH; i++) {
        __s64 difference = (__s64)value_q16[i] - work->output_q16[i];
        __s64 next = (__s64)work->output_q16[i] +
                     ((difference * (__s64)alpha_q24) >> 24);
        work->output_q16[i] = (__s32)next;
    }
    work->mass_q16 = new_mass;
    work->seen++;
}

5,793 / 65,536 ≈ 0.08839 ≈ 1/√128. The blend o += (v − o) · α is the running weighted average written so that only one division per position is needed. GQA appears in the callback that walks the history: one KV lookup per KV head feeds two query-head states.

struct {
    __uint(type, BPF_MAP_TYPE_ARRAY);
    __uint(max_entries, 1);
    __type(key, __u32);
    __type(value, struct qwen3_kv_pair);
} kv SEC(".maps");
/* ... */
static long cached_all_heads_step(__u32 index, void *ctx)
{
    /* ... */
    past = work->base_position + index;
    if (past >= QWEN3_ATTENTION_CONTEXT_LIMIT ||
        work->layer >= QWEN3_ATTENTION_LAYERS)
        return 1;
#pragma clang loop unroll(disable)
    for (kv_head = 0; kv_head < QWEN3_ATTENTION_KV_HEADS; kv_head++) {
        __u32 bounded_kv_head = (__u32)kv_head &
                               (QWEN3_ATTENTION_KV_HEADS - 1);
        slot = (past * QWEN3_ATTENTION_LAYERS + work->layer) *
               QWEN3_ATTENTION_KV_HEADS + bounded_kv_head;
        pair = bpf_map_lookup_elem(&kv, &slot);
        if (!pair)
            return 1;
        attention_accumulate(&work->heads[bounded_kv_head * 2],
                             pair->key_q16, pair->value_q16);
        attention_accumulate(&work->heads[bounded_kv_head * 2 + 1],
                             pair->key_q16, pair->value_q16);
    }
    work->completed_positions++;
    return 0;
}

The kv map is declared with max_entries 1 and resized by the loader to positions × 28 × 8 slots. Each qwen3_kv_pair is 128 keys plus 128 values of 4 bytes, so 1 KiB per slot, 224 KiB per position, and, as the docs note, 8.75 GiB for the full 40,960-position limit "before weights and other buffers". The map is an ordinary array, not mmapable. Since a later revision, the host no longer touches it. The attention program stores the new K/V (store_current_kv) before scanning, so the cache is truly kernel-owned.

Accuracy of these pieces, from the repo's operator tests: online attention max abs error 0.000905 over 1–257 positions (257 crosses the 256-position chunk boundary), Q/K RMSNorm 0.000597, RoPE 1.56e-05, layer-0 input RMSNorm 7.4e-05.

Event mode: XDP, a BPF arena and a self-requeuing workqueue

Operator mode leaves an obvious objection standing: user space still runs the model loop, so is this really "in the kernel"? The optional src/bpf/qwen3_arena_bf16.bpf.c answers it. After loading, a packet starts inference, BPF schedules all 28 layers itself, and the answer goes back in a packet. The README states the boundary: "Neither path calls a user-space LLM from an eBPF hook", and on the XDP path "A loader must remain running to hold the XDP link."

Where the weights live: a 1.5 GB BPF arena

A BPF arena (BPF_MAP_TYPE_ARENA, Linux 6.9; see the arena section of chapter 04) is a region of pages shared between a BPF program and user space. Pointers into it are valid on both sides. Pointers are tagged with __arena, which is address_space(1), and the verifier relaxes its pointer checks inside it. The repo declares an arena large enough for the whole model, plus globals that Clang 19 places in the arena: a 128-row staging buffer and three 65,536-entry BF16 lookup tables (to Q24, Q16 and Q20):

#define __arena __attribute__((address_space(1)))

struct {
    __uint(type, BPF_MAP_TYPE_ARENA);
    __uint(map_flags, BPF_F_MMAPABLE);
    __uint(max_entries, QWEN3_ARENA_MODEL_MAX_BF16 / 2048u + 512u);
#ifdef __TARGET_ARCH_arm64
    __ulong(map_extra, 0x1ull << 32);
#else

#endif

max_entries counts pages: 768 Mi BF16 elements / 2,048 per 4 KiB page, plus 512 pages for the globals. map_extra is the user-space address where the arena is mapped. The loading sequence in src/serve_xdp.c is short:

Note the pattern: a SEC("syscall") program, run once with BPF_PROG_RUN, calls the bpf_arena_alloc_pages kfunc. User space then reads the returned arena pointer out of .bss and memcpys the raw safetensors payload straight into kernel-backed pages. That works because the arena is mapped at the same address in both worlds. The weights stay BF16 in the arena. A map (event_layer_weights) holds, for each layer, the element offsets of its eleven tensors, and BPF converts each weight with one load from q24_by_bf16 as it multiplies:

#pragma clang loop unroll(disable)
    for (i = 0; i < QWEN3_ARENA_BF16_COLS; i += 2) {
        if (i >= state->cols)
            break;
        even += (__s64)state->input_q16[i] * q24_by_bf16[weights[i]];
        if (i + 1 < state->cols)
            odd += (__s64)state->input_q16[i + 1] *
                   q24_by_bf16[weights[i + 1]];
    }
    state->output_q16[bounded_row] = (even + odd) >> 24;

The two accumulators are a late micro-optimization. Splitting one serial dependency chain into two cut a 131-token run's median from 93.170 s to 87.149 s (about 6.5%) with identical outputs. The report reads this as evidence that the loop is limited by instruction latency.

Which hook triggers computation: XDP, then bpf_wq

XDP runs in the driver's receive path in softirq context (chapter 07), where you cannot spend hundreds of milliseconds. So the XDP program only validates the request, claims the single global session with a compare-and-swap, and starts a BPF workqueue item. bpf_wq (Linux 6.10) is a struct bpf_wq embedded in a map value. You give it a callback with bpf_wq_set_callback_impl and start it with bpf_wq_start. The callback runs later from a kernel workqueue, in process context. Here is the end of the XDP handler:

    old_status = __sync_val_compare_and_swap(&job->status,
                                              QWEN3_EVENT_READY,
                                              QWEN3_EVENT_RUNNING);
    if (old_status != QWEN3_EVENT_READY &&
        (old_status != QWEN3_EVENT_DONE ||
         __sync_val_compare_and_swap(&job->status,
                                      QWEN3_EVENT_DONE,
                                      QWEN3_EVENT_RUNNING) !=
                                      QWEN3_EVENT_DONE))
        return XDP_PASS;
    state->base_index = 0;
    state->event_token_id = token_id;
    state->event_position = position;
    state->event_emit_logits = payload[3] == 'P';
    /* ... */
    if (state->event_qkv) {
        if (event_begin_layer(state, 0)) {
            job->status = QWEN3_EVENT_ERROR;
            return XDP_PASS;
        }
    }
    /* ... */
    job->requests++;
    job->start_ns = bpf_ktime_get_ns();
    /* ... */
    if (bpf_wq_start(&job->work, 0))
        job->status = QWEN3_EVENT_ERROR;
    return XDP_PASS;

The callback event_callback is a state machine over event_stage = Q, K, V, ATTENTION, O, GATE, UP, DOWN, FINAL_NORM, LOGITS. One invocation does one bounded step: one 128-row matrix batch, or one past position of attention for all 16 heads. Then it records where it is and calls bpf_wq_start on itself again. When a matrix finishes, it moves to the next stage. When DOWN finishes, it calls event_begin_layer(layer + 1), which loads the next layer's tensor offsets. After layer 27 it runs the final norm and 1,187 vocabulary batches with argmax tracking:

            if (state->event_layer_count &&
                state->event_layer + 1 < state->event_layer_count) {
                if (event_begin_layer(state, state->event_layer + 1) ||
                    bpf_wq_start(&job->work, 0))
                    job->status = QWEN3_EVENT_ERROR;
                return 0;
            }
            /* ... final RMSNorm, then: */
                state->event_stage = QWEN3_EVENT_STAGE_LOGITS;
                state->weight_first_bf16 = state->embedding_first_bf16;
                state->matrix_total_rows = QWEN3_EVENT_VOCAB;
                /* ... */
                state->track_argmax = 1;
                state->best_q16 = -2147483648LL;
                state->best_index = 0;
                if (bpf_wq_start(&job->work, 0))
                    job->status = QWEN3_EVENT_ERROR;
                return 0;
    /* ... */
        job->finish_ns = bpf_ktime_get_ns();
        job->completed_requests++;
        job->status = QWEN3_EVENT_DONE;
        return 0;
    }
    state->base_index = base;
    state->rows = total - base < QWEN3_ARENA_BF16_ROWS ?
        total - base : QWEN3_ARENA_BF16_ROWS;
    if (bpf_wq_start(&job->work, 0))
        job->status = QWEN3_EVENT_ERROR;
    return 0;
}

This is the "loop" of the whole model expressed without a loop. No single BPF invocation does more than one bounded step, so each stays inside what the verifier analyzed. The total amount of work is unbounded in principle, and is bounded in practice by the stage logic and the 256-entry position cap. The same callback also computes the RoPE sin/cos itself, from rope_freq_q48. It reduces the angle into [−π/2, π/2] and then runs a Taylor series (the first term plus six more) in Q30. In operator mode, C did that with libm.

How the result is read back

Because the work item finishes long after the request packet has been passed up the stack, XDP cannot rewrite that packet into a reply. The protocol therefore has a poll step (from docs/usage.md):

Request (UDP/49002)PayloadWhat BPF doesReply
Q3BPbig-endian token ID, positionall 28 layers, KV update, final norm, 151,936 logits, argmaxnone (passes up the stack)
Q3BFsame28 layers and KV update only (prompt prefill)none
Q3BR20 bytes, expected completed-request counter in bytes 4–7if done and counter matches, rewrite packet in placeQ3BA + token (4 B) + signed Q16 logit (8 B) + counter, or Q3BK for prefill, via XDP_TX

The reply path swaps MAC addresses, IP addresses and UDP ports and zeroes the UDP checksum, which IPv4 allows. Valid polls that arrive too early are dropped rather than passed up, because passing them produced ICMP port-unreachable replies from the unbound port. Positions must be consecutive: a position-zero packet starts a new sequence. The KV map holds 256 positions, and there is one global session.

Performance: what the repo measured

Every number in this section is copied from docs/experiments.md or the report, which takes all its numbers from that file. The host was Linux 6.17 on an arm64 machine with Cortex-X925 and Cortex-A725 cores. Most results are single runs or medians of three on a shared host, and the authors say plainly that they are "not a controlled throughput benchmark". None of them were reproduced here (see the next section).

  • Token 0 → 9 and token 1 → 14582, matching Hugging Face Transformers BF16. Over all 151,936 logits, mean absolute error was 0.052 / 0.030 and RMSE 0.065 / 0.038, and the top three IDs agreed.
  • Hello, world! ([9707, 11, 1879, 0]) → 1096 (" This"), the same as BF16, with all top-five IDs agreeing. MAE 0.035.

So event mode beats operator mode for a single token, by 29% on the X925 core and 34% on the A725 core, because no user-space dispatch sits between steps. That advantage disappears over sequences. Against ordinary user-space BF16 inference on one core, the eBPF path was 1.8–4.8× slower. The report's explanation is per-MAC cost. Each BPF MAC is a chain of scalar instructions: load the BF16 bits, load their Q24 value from the table, a 64-bit multiply, an add, and a loop bound check. A user-space engine does the same work with SIMD fused multiply-adds.

The message comes from fixup_call_args() in kernel/bpf/verifier.c. When JIT compilation is not done, it rejects any program with a callback ("interpreter doesn't support them yet"), and in the same function it rejects kfunc calls ("calling kernel functions are not allowed in non-JITed programs"). So on a kernel without a JIT, neither path can load: the default path needs bpf_loop callbacks, and the event path needs the arena and bpf_wq kfuncs. Linux 6.1 also predates arenas (6.9) and BPF workqueues (6.10). Because nothing past the matvec tile could load, I did not download the 1,503,300,328-byte model, which is also just over the 1.5 GB limit set for this chapter. No inference was run, and no repo number was reproduced here.

Lesson for your own projects

bpf_loop, bpf_for_each_map_elem, timers, workqueues and every kfunc quietly assume a JIT. Distribution kernels almost always ship with the JIT enabled (often with CONFIG_BPF_JIT_ALWAYS_ON), but containers, sandboxes and some embedded kernels may not. If your heavy BPF code has to run there, check bpf_jit_enable first, or keep a callback-free fallback such as the repo's experiments/qwen3_matvec.bpf.c.

What the experiment teaches about eBPF's limits

The verifier is a design constraint, not a wall

Bounded callbacks, rolled loops, masks and lookup tables were enough for every operator, including softmax, square roots and a KV cache. The largest default program used about 5% of the instruction budget in this orb's build.

Crossings matter, until they don't

Going from 143,667 to 50,667 syscalls per token roughly halved latency. Going a further 12× lower, to 4,169, changed nothing measurable. Removing user-space scheduling altogether (event mode) helped single tokens, not sequences.

The ISA sets the ceiling

No floats and no SIMD means several scalar instructions per weight. The report suggests vector instructions or verified kfuncs for matrix kernels as the way forward, and calls how to add them without weakening the verifier's guarantees an open question.

Memory is the other limit

A dense integer KV cache costs 224 KiB per position. The event path caps it at 256 positions and one session. The arena holds a 1.5 GB kernel-resident copy of the weights on top of the file mapping.

Benefits

  • A concrete, reproducible upper bound on what verified BPF can compute, with every operator differential-tested against an independent C reference. That testing even caught a signed/unsigned bug in the C reference itself, at layer four.
  • A reusable event pattern: XDP admits a request, a self-requeuing bpf_wq computes, and a poll answered with XDP_TX returns the result, with no user-space worker. The report suggests it suits "a small model that makes one decision per packet or per kernel event far better than it suits LLM serving."
  • A worked catalogue of verifier-friendly numerical kernels (integer sqrt, exp, SiLU, online softmax, Taylor sin/cos) that apply to much smaller in-kernel models too.

Limitations

  • No speed benefit over one-core user-space BF16 inference. The README says this in bold.
  • Validated on one kernel and architecture (6.17, arm64). Verifier acceptance on other kernels and compilers is unverified, and a JIT is required.
  • The tokenizer stays in user space, and so do (in operator mode) the schedule, the embedding lookup and the RoPE trigonometry.
  • Event mode: one session, 256 positions, a fresh loader per sequence, raw token IDs.
  • Fidelity evidence is a handful of prompts and two text excerpts, not a benchmark.

Related work

  • ML in the kernel. LiteFlow (SIGCOMM 2022) runs integer-quantized neural network snapshots in the kernel datapath. LAKE (ASPLOS 2023) offloads kernel ML to GPUs. KML brings a small ML framework into the kernel for storage tuning. Bachl et al. run decision trees in eBPF for intrusion detection. All of these models are orders of magnitude smaller than Qwen3-0.6B.
  • Integer inference. I-BERT shows integer-only approximations of GELU, softmax and LayerNorm for transformers. Its motivation is close to this repo's fixed-point operators.
  • Small engines. qwen3.c (CPU, single file C) and qwen3.cu (CUDA) implement the same model. The bpf-developer-tutorial's CUDA Qwen3 profiling example uses eBPF only to observe it (chapter 09).
  • The opposite placement. KernelX feeds eBPF signals to a user-space LLM, which is closer to the org's LLM-for-kernel tools in chapter 30.
  • Other ways to run BPF outside the kernel. If what you want is eBPF-programmable compute without the kernel's ISA ceiling, see the userspace runtime bpftime and the LLVM-based llvmbpf, whose JIT/AOT and GPU targets address exactly the "no vector instructions" problem.

Check your understanding

Q1. In the default build/infer path, where are the model's matrix weights while a token is computed?

Operator mode never makes the weights kernel-resident. Only the optional arena builds (infer-arena-bf16, serve-xdp) copy the BF16 payload into a BPF arena.

Q2. Why do the matrix weights use Q24 rather than Q8?

Precision, not speed or verifier rules. The whole-model INT4 and INT8 experiments also changed generated tokens.

Q3. How does event mode run all 28 layers when XDP must finish quickly?

The repo uses no tail calls. The workqueue callback is a state machine (Q, K, V, ATTENTION, O, GATE, UP, DOWN, then FINAL_NORM and LOGITS) that requeues itself.

Q4. On this chapter's 6.1 kernel without a JIT, why did qwen3_batch_rows fail to load?

"callbacks are not allowed in non-JITed programs". The same function rejects kfunc calls without a JIT, which rules out the arena/workqueue path too.

Q5. According to the repo's measurements, what finally limits speed?

Reducing crossings below about 50,000 stopped helping. The roughly 2 GB/s of weight reads is far below memory bandwidth. A lookup-table change and an extra accumulator, which changed no crossings, did help.

Q6. How does the event path return a token to the client?

The original request packet has long since passed up the stack, so a later poll packet is turned around in place.
