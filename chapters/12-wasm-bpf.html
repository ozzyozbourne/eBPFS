Chapter 12

wasm-bpf: eBPF user space in WebAssembly

An eBPF tool has two halves. The kernel half is portable bytecode that the verifier checks. The user-space half, the loader that opens the object, attaches programs, reads maps and prints results, is an ordinary native binary built for one CPU architecture and one libc, usually run as root. What happens if that second half is also compiled to a portable, sandboxed bytecode, so a whole eBPF application ships as one 70 KB .wasm file?

Prerequisites: 04, 06, 10Repo: eunomia-bpf/wasm-bpf @ 01f1419~50 min

Why this matters: the native half of every eBPF tool

Chapter 06 showed how CO-RE makes the kernel half of an eBPF application portable: one .bpf.o file, compiled once, is patched by libbpf at load time to fit the running kernel. The user-space half does not get that treatment. In libbpf-bootstrap's bootstrap example, bootstrap.c is compiled with the host C compiler, linked against libbpf, libelf and zlib, and produces an x86-64 (or arm64, or riscv64) ELF executable. To ship that tool you build it once per architecture, pick a libc, and decide between static linking and runtime dependencies.

That is manageable for a single tool on a single server. It gets harder in three situations that the wasm-bpf authors put at the centre of their design.

  • Heterogeneous fleets. A Kubernetes cluster can mix x86-64 and arm64 nodes and several kernel versions. Each eBPF tool then needs a matrix of builds and a container image per architecture.
  • Heavy packaging for small programs. The usual way to deploy a tracing tool to a cluster is a privileged DaemonSet whose container image holds the loader, its libraries and a base distribution. The program that does the work may be a few kilobytes of bytecode; the image is megabytes.
  • Plugins. Observability agents and proxies want to load third-party probes at run time. If a probe's user-space logic is native code, loading it means running arbitrary native code inside the agent's process, with the agent's privileges.

WebAssembly (Wasm) was designed for exactly the "portable, sandboxed user code" problem. A Wasm module is architecture-neutral bytecode. A Wasm runtime compiles or interprets it, confines it to its own memory, and lets it do nothing except call functions the host explicitly provides. The WebAssembly System Interface (WASI) standardises a set of such functions for files, clocks, arguments and so on. wasm-bpf, from the eunomia-bpf community, adds a small set of extra host functions for eBPF: load an object, attach a program, operate on a map, poll a ring buffer. With them, the user-space half of an eBPF tool can be compiled to Wasm and run by any runtime that implements those functions.

Key idea

wasm-bpf does not run eBPF bytecode inside WebAssembly. The kernel still verifies and runs the eBPF programs. What moves into the Wasm sandbox is the control plane: the code that libbpf-based tools normally run as a native process. The Wasm guest embeds the .bpf.o bytes in its own memory and asks the host runtime, through seven imported functions in a module called wasm_bpf, to hand them to libbpf. The host owns every kernel object (file descriptors, links, ring buffers); the guest only ever holds opaque handles and integer file descriptor numbers.

The project started in November 2022. The README describes it as "a WebAssembly eBPF library, toolchain and runtime powered by CO-RE libbpf". Its design and evaluation are written up in the arXiv preprint "Wasm-bpf: Streamlining eBPF Deployment in Cloud Environments with WebAssembly" (Zheng, Yu, Yang and Quinn, 2024), and it was presented at KubeCon + CloudNativeCon North America 2023 as "eBPF + Wasm: Lightweight Observability on Steroids" (Michael Yuan of WasmEdge and Yusheng Zheng of eunomia-bpf). This chapter reads the code at commit 01f1419 (4 September 2026) and the three guest SDK repositories, and builds and runs the C++ runtime and a C guest on the curriculum's orb (Linux 6.1, x86-64).

A WebAssembly primer for eBPF readers

You need five Wasm facts to follow the rest of the chapter. They are all in the core specification (webassembly.github.io/spec); Haas et al., "Bringing the Web up to Speed with WebAssembly" (PLDI 2017), explains the design.

  1. Linear memory. A module's data lives in one contiguous, growable byte array. Pointers in C or Rust code compiled to wasm32 are 32-bit offsets into this array. The host can read and write it, and can turn an offset into a real host pointer by adding the array's base address. The guest cannot address anything outside it.
  2. Imports and exports. A module declares the functions it needs as imports, each named by a module name and a field name with a fixed signature of i32, i64, f32 and f64 values. The host must supply every import before the module can be instantiated. Exports work the other way: the module names functions, its memory or its tables for the host to use.
  3. Function tables. Wasm code cannot jump to an address. A C function pointer compiled to Wasm is an index into a table of functions, usually exported as __indirect_function_table. A host that wants to call a guest callback calls "table entry N" with type-checked arguments.
  4. WASI. A standard set of imports (module names starting with wasi_) for arguments, environment, clocks, random numbers and file descriptors. WASI is capability-based: a guest cannot open /etc/passwd by name; it can only use directories the host preopened for it, and only with the rights the host granted.
  5. Engines. A Wasm runtime can interpret, JIT-compile or ahead-of-time compile the module. wasm-bpf ships runtimes built on two engines from the Bytecode Alliance: Wasmtime (Rust, Cranelift JIT) and WAMR, the WebAssembly Micro Runtime (C, interpreter and AOT). A third, a plugin for WasmEdge, lives in the WasmEdge repository.

It is worth placing the two virtual machines side by side, because they are easy to confuse.

Architecture

Figure 12.1 shows the pieces. The guest is a normal WASI command module (it has a _start export, like a main). Its data section contains the bytes of the compiled .bpf.o, embedded at build time. It imports WASI functions for printing and sleeping, and the wasm-bpf functions for everything eBPF. The host runtime is a native program that links a Wasm engine and libbpf. When the guest calls an import, the engine transfers control to a host function, which translates the guest's 32-bit offsets into host pointers (after bounds-checking them), calls libbpf, and returns an integer.

Three consequences follow from this split and come back throughout the chapter.

  • The guest needs no libelf and no syscalls. ELF parsing, BTF handling and CO-RE relocation happen in the host's libbpf, exactly as in a native tool (06). The guest is small because it only carries the object bytes and its own logic.
  • Data has to cross a boundary twice: between the kernel and host memory (as in any eBPF tool) and between host memory and the guest's linear memory. wasm-bpf arranges for the second crossing to be a plain copy or a direct pointer, never serialisation.
  • The kernel sees an ordinary libbpf user. The verifier, the JIT, the program types and the map types are the same ones described in Part I. Nothing in the kernel knows a Wasm module is involved.

Note the comment "should be externref": the object handle is a plain 64-bit integer today. Wasm's externref type, an opaque host reference the guest cannot forge or do arithmetic on, would be the cleaner choice, but it is not usable from C without extra toolchain support.

The C++ runtime registers the same functions with WAMR, using WAMR's signature strings. They are the most compact statement of the ABI: i is i32, I is i64, * is a guest pointer that WAMR bounds-checks and converts to a host pointer, ~ is the length of the preceding buffer, and $ is a NUL-terminated string.

    static NativeSymbol native_symbols[] = {

        EXPORT_WASM_API_WITH_SIG(wasm_attach_bpf_program_fd, "(I$i)i"),
        EXPORT_WASM_API_WITH_SIG(wasm_bpf_buffer_poll, "(Iiii*~i)i"),
        EXPORT_WASM_API_WITH_SIG(wasm_bpf_map_fd_by_name, "(I$)i"),
        EXPORT_WASM_API_WITH_SIG(wasm_bpf_map_operate, "(ii***I)i"),
        EXPORT_WASM_API_WITH_SIG(wasm_close_bpf_object, "(I)i"),

    /* ... */

This is a deliberately small surface. There is no "create a map", "load one program" or "pin" call: the unit of work is a whole ELF object, and the guest otherwise sees only the four map commands. The README invites anyone to implement the same interface "in any languages, any eBPF libraries and any Wasm runtimes", and the eunomia-bpf author proposed it for standardisation as WASI issue #513, "WASI proposal for eBPF related API" (opened February 2023; still open).

Watch the documented signatures

The README and the WasmEdge plugin README list wasm_bpf_map_operate(u64 fd, …), but both runtimes and the C SDK use an i32 fd, as the import above shows. The Rust (wasm-bpf-binding) and Go SDKs declare the three pointer arguments of wasm_bpf_map_operate as i64, while the runtimes take 32-bit pointers. Wasmtime checks import types when it instantiates a module, so a Rust or Go guest that calls this function through those bindings would probably be rejected at start-up. I found this by reading the source and did not test it (no Rust or TinyGo toolchain on the orb). None of the shipped Rust or Go examples call map operations.

Inside the runtime

Both runtimes follow the same structure: an instance-wide table maps object handles to a libbpf object plus its links and its poller, and each host function is a thin wrapper that validates guest memory and calls libbpf. The Rust runtime is the more complete of the two (the runtime README notes it is the only one that runs TinyGo modules), so most excerpts below come from it, with the C++ version where the two differ.

Start-up and linking

WasmBpfModuleRunner::new builds a Wasmtime engine, adds WASI to the linker, and registers each host function under the module name wasm_bpf via the add_bind_function! macro (which expands to linker.func_wrap("wasm_bpf", stringify!(f), f)):

        let engine_config = wasmtime::Config::new()
            .epoch_interruption(true) // It must be enabled
            .to_owned();
        let engine = Engine::new(&engine_config)?;
        let mut linker = Linker::new(&engine);
        wasmtime_wasi::add_to_linker(&mut linker, |s: &mut AppState| &mut s.wasi)
            .with_context(|| anyhow!("Failed to add wasmtime_wasi to linker"))?;
        /* ... WASI context with stdin/stdout/stderr, args, preopens ... */
        store.set_epoch_deadline(1);
        store.epoch_deadline_callback(move |v| {
            // There should call `unwrap`.
            match v.operation_rx.recv()? {
                ProgramOperation::Resume => Ok(1),
                ProgramOperation::Terminate => Err(anyhow!("Wasm program terminated")),
            }
        });
        let main_module = Module::from_binary(&engine, module_binary)
            .with_context(|| anyhow!("Failed to read wasm module file"))?;
        add_bind_function!(linker, wasm_load_bpf_object)?;
        add_bind_function!(linker, wasm_close_bpf_object)?;
        add_bind_function!(linker, wasm_attach_bpf_program)?;
        add_bind_function!(linker, wasm_attach_bpf_program_fd)?;
        add_bind_function!(linker, wasm_bpf_buffer_poll)?;
        add_bind_function!(linker, wasm_bpf_map_fd_by_name)?;
        add_bind_function!(linker, wasm_bpf_map_operate)?;

The epoch settings implement pause, resume and terminate for embedders. Wasmtime's epoch interruption inserts cheap checks into compiled code; when the host calls engine.increment_epoch() (that is what WasmProgramHandle::pause() and terminate() do), the next check runs the deadline callback, which blocks on a channel until it receives Resume or Terminate. This is how ecli's task manager stops a running Wasm eBPF program: it calls run_wasm_bpf_module_async and keeps the returned handle.

Loading: the object never leaves guest memory

pub fn wasm_load_bpf_object(
    mut caller: CallerType,
    obj_buf: WasmPointer,
    obj_buf_size: u32,
) -> u64 {
    debug!("Load bpf object caller");
    let memory = caller.get_memory().expect("Expected exported `memory`");
    let mut buf = vec![0u8];
    if let Err(err) = memory.read(
        &mut caller,
        obj_buf as usize + obj_buf_size as usize - 1,
        &mut buf[..],
    ) {
        /* ... log and return 0 ... */
        return 0;
    }
    let open_object = match ObjectBuilder::default().open_memory(
        "",
        &memory.data(&mut caller)[obj_buf as usize..(obj_buf + obj_buf_size) as usize],
    ) {
        Ok(v) => v,
        /* ... */
    };
    let object = match open_object.load() {
        Ok(v) => v,
        /* ... */
    };
    let mut state = caller.data_mut();
    let next_id = state.next_object_id;
    state.next_object_id += 1;
    state.object_map.insert(
        next_id,
        WrapperObject {
            object: Rc::new(RefCell::new(object)),
            poll_buffer: None,
        },
    );
    next_id
}

The host checks that the last byte of the buffer is inside linear memory (reading it with a bounds-checked memory.read), then gives libbpf a slice of linear memory directly. From there it is the libbpf load path of chapter 06: parse ELF, find kernel BTF, apply CO-RE relocations, create maps, send programs to the verifier. If anything fails, the guest just gets 0; the reason is in the host's debug log (wasm-bpf --verbose). Handles in the Rust runtime are a counter starting at 1. The C++ runtime uses the address of its wasm_bpf_program object as the handle, but only ever uses it as a key in an unordered_map, so a forged handle just fails the lookup.

Attaching, and why attach targets became file descriptors

Most program types need no target at all: libbpf's bpf_program__attach() reads the section name (tp/sched/sched_process_exec, lsm/path_rmdir, kprobe/…) and picks the hook (05). The runtime calls it when the target is null or empty. Two section names get special treatment because they need something only the caller knows: sockops needs a cgroup and xdp needs a network interface. With the original API, the guest passed a string: a cgroup path such as "/sys/fs/cgroup/" (see examples/sockops/sockops.c) or an interface name.

A path string from the guest is a problem in a sandbox. The runtime runs with root-level privileges and opened whatever path the guest named, which is the opposite of WASI's capability model. Issue #48 ("Pass file descriptor instead of file path at wasm_attach_bpf_program") recorded this in March 2023. It was fixed in two pull requests in August–September 2026, #160 for the Rust runtime and #163 for the C++ runtime, with matching SDK updates. The new wasm_attach_bpf_program_fd takes a WASI descriptor instead:

  • The operator preopens directories with wasm-bpf --dir /sys/fs/cgroup:/guestmnt (Rust CLI) or --dir /sys/fs/cgroup (C++ CLI).
  • The runtime gives each preopen no rights at all. The guest can discover it (via fd_prestat_get) and hold its number, but cannot open, list or create anything beneath it. The C++ runtime goes further and injects the preopens only after instantiation, so that module initialisation code never sees them; a test called hostile_init_test checks this.
  • The host resolves the guest's fd only through its own registry of preopens. stdout, an unopened number, or anything the guest opened itself is refused. XDP targets are interfaces, not files, so the fd path rejects xdp programs and they keep using the string API.
/// Pick the [`FdAttachAction`] for a section. Runs before any descriptor is resolved, so it
/// sees only whether a target was passed, never what it resolves to.
pub(crate) fn fd_attach_action(section: &str, has_target_fd: bool) -> FdAttachAction {
    match (section, has_target_fd) {
        ("sockops", true) => FdAttachAction::AttachCgroupByFd,
        ("xdp", _) => FdAttachAction::RejectXdp,
        _ => FdAttachAction::AutoAttach,
    }
}

The C SDK exposes this as bpf_set_prog_attach_target_fd(prog, fd) next to the older bpf_set_prog_attach_target(prog, path). Its README warns about a compatibility side effect worth knowing: bpf_object__attach_skeleton() contains both calls, so any C guest rebuilt with the new header imports wasm_attach_bpf_program_fd even if it never uses it, and will not instantiate on a runtime older than #160/#163. I confirmed it: a bootstrap.wasm built on the orb from the current sources imports six wasm_bpf functions, while the prebuilt one in the repository imports five.

Map operations: the kernel copies straight into guest memory

For maps, wasm-bpf avoids copies entirely. The host asks the kernel for the map's key and value sizes, checks that the guest's pointers have that many bytes available, and passes host pointers into linear memory to libbpf's syscall wrappers. The kernel's copy_to_user/copy_from_user then read and write guest memory directly.

    let (key_size, value_size) = {
        // SAFETY: The fd is only used to query map info, which will not be used to write or read
        let map_info = match MapInfo::new(unsafe { BorrowedFd::borrow_raw(fd) }) {
            /* ... */
        };
        (
            map_info.info.key_size as usize,
            map_info.info.value_size as usize,
        )
    };

    match cmd as u32 {
        /* ... BPF_MAP_GET_NEXT_KEY ... */
        BPF_MAP_LOOKUP_ELEM => {
            ensure_enough_memory!(caller, key, key_size, EINVAL);
            ensure_enough_memory!(caller, value, value_size, EINVAL);
            // SAFETY: memory addresses are checked to be valid
            let ret_val = unsafe {
                bpf_map_lookup_elem_flags(
                    fd,
                    caller.raw_pointer_at_unchecked(key as usize) as *const _,
                    caller.raw_mut_pointer_at_unchecked(value as usize) as *mut _,
                    flags,
                )
            };
            /* ... */
        }
        /* ... BPF_MAP_UPDATE_ELEM, BPF_MAP_DELETE_ELEM ... */
        // More syscall commands can be allowed here
        s => {
            debug!("Map operation `{}` currently not supported", s);
            return -EINVAL;
        }
    };

Only commands 1–4 (LOOKUP_ELEM, UPDATE_ELEM, DELETE_ELEM, GET_NEXT_KEY) are allowed; batch operations, LOOKUP_AND_DELETE and per-object commands are not exposed. The C SDK turns these into the libbpf names a C programmer expects (bpf_map_lookup_elem, bpf_map_get_next_key, …), which is why runqlat.c's histogram loop compiles to Wasm unchanged. One detail to keep in mind if you build a runtime for untrusted guests: the fd argument is a raw host descriptor number, and the runtime does not check that it belongs to one of the guest's objects. A guest could pass the number of some other BPF map the host process has open.

Polling: callbacks across the boundary

Ring buffers and perf buffers are where the two worlds meet most often. The guest wants libbpf's callback style ("call handle_event for every sample"), but its callback is Wasm code, and a C function pointer in Wasm is a table index. Figure 12.2 shows the full sequence from start-up to the first event.

On its first call, wasm_bpf_buffer_poll looks at the map type and creates either a libbpf ring buffer (BPF_MAP_TYPE_RINGBUF) or a perf buffer (BPF_MAP_TYPE_PERF_EVENT_ARRAY, 64 pages per CPU in the C++ runtime). The guest code is the same for both, which mirrors the bpf_buffer compatibility wrapper in BCC's libbpf-tools that the C++ runtime credits. The C++ runtime's sample callback does the copy and the call back into Wasm:

int bpf_buffer::bpf_buffer_sample(void* data, size_t size) {
    size_t sample_size = size;
    if (max_poll_size < size) {
        sample_size = max_poll_size;
    }
    memcpy(poll_data, data, sample_size);
    wasm_module_inst_t module_inst =
        wasm_runtime_get_module_inst(callback_exec_env);
    uint32_t argv[] = {wasm_ctx,
                       wasm_runtime_addr_native_to_app(module_inst, poll_data),
                       (uint32_t)size};
    // call the wasm callback handler
    if (!wasm_runtime_call_indirect(callback_exec_env, wasm_sample_function, 3,
                                    argv)) {
        printf("indirect call sample_function failed\n");
        return -EINVAL;
    }
    return 0;
}

Two details. First, the record is copied into a buffer that lives in guest memory (the C SDK uses a 4,096-byte stack array in bpf_buffer__poll); records longer than that are truncated, but the size passed to the callback is the untruncated one, so callbacks should not trust size beyond their buffer. Second, the call goes through the function table, which is why every example links with -Wl,--export-table (C) or cargo:rustc-link-arg=--export-table in build.rs (Rust): without that flag wasm-ld does not export __indirect_function_table, and the Rust runtime's error message says so.

The Rust runtime takes a different route because of Rust's borrowing rules: it cannot call into the Wasm store from inside libbpf-rs's callback while the poll holds a borrow. Instead the libbpf-rs callback stores the sample in a shared cell, and the guest is called once after poll() returns:

            MapType::RingBuf => {

A consequence worth testing

replace() overwrites the cell. libbpf's ring-buffer poll consumes every record available when it wakes up, so if several events arrive within one poll, this code delivers only the last one to the guest. That is what the code says; I did not build the Rust runtime to measure it. The C++ runtime calls the guest once per record and does not have this behaviour. If you depend on every event, check this with the Rust runtime and your event rate before relying on it.

TinyGo adds one more wrinkle. A Go function cannot be passed as a raw table index, so the Go SDK imports wasm_bpf_buffer_poll from a separate module, callback-wrapper, without the callback argument, and exports the callback under a fixed name, go-callback. The Rust runtime registers a wrapper (bpf_buffer_poll_wrapper) under that module name, and when it is used, calls the export by name instead of a table entry. The CLI's -m and -c options set those two names; the defaults match the Go SDK. (Embedders should set them explicitly: the library's Config::default() assigns the two strings the other way round from the CLI.)

Memory, struct layout and code generation

A user-space eBPF program and its kernel half share data structures: the event in the ring buffer, the key and value of every map, the read-only configuration in .rodata. In a native tool, both sides are compiled for a 64-bit target and agree on the layout by construction. In wasm-bpf, the kernel side is compiled for -target bpf (64-bit) and the user side for wasm32, a 32-bit target. C types that depend on the pointer width change size. Here is a measurement with the orb's Clang 14 for the same struct on both targets:

/* illustrative test struct, not from the repo */
struct exec_start_t { int pid; long start_ns; const char *name; char comm[16]; };

Bootstrap's struct event happens to be safe: it uses int, unsigned, unsigned long long and char arrays, whose sizes and alignments agree on both targets (offsets 16, 24 and 167 for duration_ns, comm and exit_event; 168 bytes total in both). Structs with long, size_t, pointers, or kernel typedefs built on them are not. wasm-bpf offers three answers, in increasing order of automation.

1. Hand-written packed structs

The bootstrap README's advice: write the shared structs yourself with __attribute__((packed)), fixed-width types and explicit padding, and turn pointers into uint64_t. For simple events this is easy and it is what the Rust and Go examples do (the Rust Event below is #[repr(C, packed)] with an explicit __pad0: [u8; 4]).

2. A layout header generated from BTF

The BPF object already contains BTF describing every type the kernel side uses, with exact byte offsets. The eunomia-bpf bpftool fork used to turn that into a header of packed, explicitly padded structs with a static_assert on each size. The committed examples/bootstrap/bootstrap.wasm.h is such output:

/* THIS FILE IS AUTOGENERATED BY BPFTOOL! */
#ifndef _BPF_WASM_EVENT_H_
#define _BPF_WASM_EVENT_H_

#include <stdint.h>
#include <stddef.h>
#include <stdbool.h>
#include <assert.h>

struct event {
    int pid;
    int ppid;
    unsigned int exit_code;
    char __pad0[4];
    unsigned long long duration_ns;
    char comm[16];
    char filename[127];
    char exit_event;
} __attribute__((packed));
static_assert(sizeof(struct event) == 168, "Size of event is not 168");

#endif /* __VMLINUX_H__ */

The generator (dump_btf_wasm in the wasm-bpftool branch's src/btf.c) walks the members of each struct, emits char __padN[k] wherever the BTF offset is ahead of the running offset, prints pointer members as integers of the BPF pointer size, and, at this stage of the tool, skips bitfields and nested structs. The struct event type only appears in the object's BTF if some code mentions it; the example's Makefile first runs ecc bootstrap.h --header-only (chapter 10) to add BTF for every struct in the header. Two caveats from building on the orb: in the bpftool revision pinned at the studied commit, the documented command bpftool btf dump file bootstrap.bpf.o format c -j now prints a JSON description of struct layouts rather than this header; and the Makefile does not make bootstrap.wasm depend on bootstrap.wasm.h, so a normal make uses the committed file. Treat the generated header as a starting point you check in, not as a build step.

For other guest languages, the same BTF can drive other code generators. btf2wit converts BTF to WIT, the interface definition language of the WebAssembly Component Model, so that wit-bindgen can generate Rust (or other) types. The rust-bootstrap example generates both its event record and its import declarations this way:

generate: install-deps import.wit
	clang -target bpf -g event-def.c -c -o event.def.o
	cargo install btf2wit
	btf2wit event.def.o -o event-def.wit --world-name event-def
	cp *.wit ../wit/

import.o: import.c
	gcc import.c -c -o import.o -g 
	pahole -J import.o

import.wit: import.o
	btf2wit import.o -o import.wit --world-name import
	
	# Currently, WIT doesn't support identifiers with two continuous `-`
	sed -i 's/--/s-/g' import.wit

The second half is a neat trick: compile the C prototypes of the host functions with gcc -g, convert DWARF to BTF with pahole -J, and turn that BTF into a WIT world of imports. The resulting wit/import.wit uses the pre-1.0 WIT syntax (default world %import { … }) and a wit-bindgen pinned to a 2023 git revision; the example's README calls the Wasmtime/WIT path experimental, and by default the example uses the hand-written wasm-bpf-binding crate instead. A third tool, c-struct-bindgen, is a proof of concept that generates C struct bindings and JSON marshalling functions from the same information. btf2wit and c-struct-bindgen were last updated in early 2023.

3. The Wasm skeleton and the .rodata trick

libbpf skeletons (06) give typed access to global variables: after bootstrap_bpf__open(), skel->rodata->min_duration_ns points into a memory-mapped copy of the .rodata map that libbpf writes into the kernel at load time. A Wasm guest has no libbpf and no mmap of kernel maps, so the forked bpftool generates a different skeleton with bpftool -w gen skeleton. It includes libbpf-wasm.h instead of bpf/libbpf.h, embeds the ELF bytes as usual, and records one extra number: the file offset of the .rodata section inside those bytes. From the skeleton generated on the orb:

/* bootstrap.skel.h, generated on the orb by: bpftool -w gen skeleton bootstrap.bpf.o */
	s->sz = sizeof(*s);
	s->name = "bootstrap_bpf";
	s->rodata_offset = 1264;
/* ... */
	map = (struct bpf_map_skeleton *)((char *)s->maps + 2 * s->map_skel_sz);
	map->name = "bootstra.rodata";
	map->map = &obj->maps.rodata;
	map->mmaped = (void **)&obj->rodata;

readelf -S bootstrap.bpf.o on the same object shows .rodata at file offset 0x4f0, which is 1264. The SDK's bpf_object__open_skeleton then points the rodata pointer straight into the embedded ELF image:

        if (str_has_surfix(map_skel->name, "rodata") && map_skel->mmaped) {
            // set the address to mmaped rodata variable
            *map_skel->mmaped = s->data + s->rodata_offset;
        }
        // it will not work for bss, because bss is not mmaped
        // if (str_has_surfix(map_skel->name, "bss") && map_skel->mmaped) {
        //     *map_skel->mmaped = s->data + s->bss_offset;
        // }

So skel->rodata->min_duration_ns = … patches the bytes of the object file in guest memory, and the subsequent wasm_load_bpf_object hands the patched ELF to the host's libbpf, which creates the .rodata map with the new value and freezes it. Configuration through const volatile globals works with no extra host function. .bss and .data are not supported this way, because the guest would need to see the live kernel map, not the initial image. On the orb, bootstrap.wasm -d 50 printed only EXIT events with durations of about 200 ms or more, which shows the patched constant reached the kernel.

What to notice:

  • The C guest is nearly line-for-line the libbpf-bootstrap program. The differences are the extra bootstrap.wasm.h include, bpf_buffer__open/bpf_buffer__poll instead of ring_buffer__new/ring_buffer__poll, and hand-written argument parsing, because wasi-libc has no argp and the guest cannot install a SIGINT handler (WASI has no signals). Ctrl-C is handled by the host: the C++ runtime installs a handler that prints Ctrl C exit... and exits, which is what you see at the end of the run above.
  • The raw Rust guest shows what the C SDK hides. Strings are passed as guest offsets and must be NUL-terminated by hand ("handle_exec\0"); the callback is passed as handle_event as i32, which in Wasm is its table index; the entry point is exported as __main_argc_argv with #![no_main]. The packed Event has the explicit 4-byte pad that the BTF header generator would add.
  • The libbpf-rs-like SDK (wasm-bpf-libbpf-rs, added June 2023) wraps the same calls in Object, Map and Poll types. Its callback is a Rust closure: the SDK passes a fixed trampoline (call_sample_cb) as the table index and a pointer to the boxed closure as ctx.
  • The Go guest uses TinyGo's //go:embed for the object and the special callback-wrapper import with an exported go-callback. The CI builds Go examples with TinyGo 0.29 and runs them only under the Rust runtime (examples/go-execve/Makefile skips the test for IMPL=cpp).

Packaging and deployment: OCI, WasmEdge and Kubernetes

Because a wasm-bpf application is one self-contained file, it can be distributed like any other artifact. The repository shows three deployment styles.

A runtime container

The Dockerfile is ubuntu:22.04 plus libelf1 plus the Rust wasm-bpf binary as the entry point. The module is mounted in: docker run --rm -it --privileged -v $(pwd):/examples ghcr.io/eunomia-bpf/wasm-bpf:latest /examples/runqlat.wasm. One generic image serves every tool; only the 50–100 KB module changes.

OCI artifacts

CI builds each example and pushes it with ecli-rs push -m $(ls *.wasm) ghcr.io/$REPO_OWNER/<example>:latest -a org.opencontainers.image.title=<example>. ecli (10) can pull an image reference and run it directly.

Wasm containers

The WasmEdge wasm_bpf plugin implements the same host functions inside WasmEdge. With a crun built against WasmEdge, podman can run the module as a --platform=wasi/wasm container; docs/podman.md walks through it and offers a prebuilt ghcr.io/eunomia-bpf/wasm-podman image.

The OCI format is the standard Wasm artifact convention, not something wasm-bpf invented. ecli's push uses the bpf-oci crate, which builds a manifest with a single layer of media type application/vnd.wasm.content.layer.v1+wasm (the module bytes) and a config of type application/vnd.wasm.config.v1+json containing {}; both constants come from the oci-distribution crate. Any OCI registry (ghcr.io, Docker Hub, Harbor) can store it, and tools such as ORAS can copy it.

For Kubernetes, the pitch in the paper and the KubeCon talk is: instead of a privileged DaemonSet with one fat image per tool, nodes run a Wasm-capable container runtime (crun or a containerd shim with WasmEdge and the eBPF plugin), and eBPF tools become small Wasm OCI artifacts that the usual tooling can schedule, version and roll back. The paper describes replacing the standard containerd shim with a WasmEdge shim. The repository contains the podman/crun recipe, not Kubernetes manifests, so treat the Kubernetes integration as a direction rather than a packaged feature. Two points apply however you deploy:

  • The node-side runtime still needs eBPF privileges (--privileged in every example) and a kernel with BTF for CO-RE. Wasm does not remove those requirements.
  • Embedding is a first-class mode. A host application written in Rust can link wasm-bpf-rs and run plugins with run_wasm_bpf_module_async, redirect their stdout/stderr through Config, register extra host functions with register_host_function, and pause or kill them through the returned handle. ecli's task manager (ecli/ecli-lib/src/runner/task_manager) does exactly this. The c-wrapper crate exposes the same thing to C.

Security model: what the sandbox does and does not protect

It is easy to read "Wasm sandbox" as "safe eBPF". The real picture has two parts.

What Wasm gives you

The guest's user-space code cannot touch host memory, open files, make network connections or call syscalls except through WASI and the seven functions. Every pointer it passes is bounds-checked against its linear memory before the host dereferences it. A crash in the guest is a trap, not a host segfault. Since #160/#163, attach targets follow WASI's capability model: the operator decides which cgroup directories exist for the guest at all.

What it does not give you

The guest chooses which eBPF object to load, and the host loads it with its own privileges. A malicious module can load an LSM program that denies operations system-wide, a kprobe that reads kernel memory, or an XDP program that drops traffic. The kernel verifier guarantees the programs are memory-safe and terminate; it does not judge what they do (03). Map access by raw fd, as noted above, is not scoped to the guest's objects.

Rule of thumb

Running a wasm-bpf module is equivalent to granting it the eBPF privileges of the runtime process. The sandbox protects the host from bugs and misbehaviour in the user-space half; it does not make an untrusted kernel half safe. A runtime meant for third-party plugins would need policy on top: allow-lists of program types and attach points, signed objects, or a review step. None of this exists in wasm-bpf today.

Benefits and limitations

Benefits

  • One artifact per tool. The .wasm file contains the kernel object and the control plane and runs on any architecture the runtime supports. CO-RE handles kernel differences, Wasm handles CPU and libc differences.
  • Small and fast to deploy. 40–110 KB for C tools, compiled in well under a second, versus a container image per tool.
  • No serialisation layer. Map keys and values are read and written by the kernel directly in guest memory; ring-buffer records cost one memcpy.
  • Familiar programming model. C guests are near copies of libbpf-bootstrap code with the same skeleton API; Rust and Go guests are possible.
  • Embeddable. The Rust library gives an application a plugin system for eBPF tools with pause/resume/terminate and captured output.
  • Small, re-implementable ABI. Seven functions; there are already three independent implementations (Wasmtime, WAMR, WasmEdge).

Limitations

  • Narrow ABI. Four map commands; no batch operations, no bpf_link management, no pinning, no per-program load, no access to .bss/.data globals, no arbitrary syscalls (sockfilter's socket creation is a TODO). Attach targets are special-cased for two section types.
  • Layout care. Shared structs must be written or generated for the 32-bit guest. The generator path has drifted (the pinned bpftool's format c -j now prints JSON; btf2wit uses pre-1.0 WIT).
  • Runtime differences. The Rust runtime appears to deliver at most one ring-buffer record per poll; only the Rust runtime runs TinyGo modules; the Rust and Go SDK signatures for wasm_bpf_map_operate disagree with the runtimes; the documented ABI in the README differs from the implemented one.
  • No signals, no argp, limited WASI. Ported tools need small edits.
  • Same privileges as native. The runtime needs eBPF capabilities and a BTF-enabled kernel, and the sandbox does not constrain the kernel half.
  • Release lag. The crates on crates.io date from 2023 (wasm-bpf 0.2.0, wasm-bpf-rs 0.3.2), and the Rust runtime still uses Wasmtime 5. Issue #157 (June 2026) tracks refreshing the package channels.

Project status

After its main development burst in 2022–2023 (Rust runtime, SDK split, libbpf-rs-style Rust SDK, XDP and uprobe support, OCI publishing), the repository was quiet from late 2023 to 2026, apart from documentation links. Work resumed in 2026: a February–March batch of CI and lint fixes (including strlcpy conflicts with glibc 2.38 and Wasm skeleton generation), dependency bumps in July, and in August–September the fd-based attach work for both runtimes and all three SDKs (#160, #163, SDK commits on 9 September 2026), followed by CI fixes that restored TinyGo example builds. It is maintained, and recent work has gone into hardening the existing ABI rather than adding features.

Related work and where to go next

  • eunomia-bpf, ecc and ecli (10): the sibling project. ecc can package a BPF object plus JSON metadata so ecli runs it with no user-space code at all; ecli also runs and distributes wasm-bpf modules. Choose ecc/ecli when the "user space" is just printing events, and wasm-bpf when you need real logic.
  • libbpf and skeletons (06) and the starter templates (11): the native baseline that wasm-bpf mirrors.
  • bpftime (14): the opposite move. bpftime runs the eBPF programs in user space; wasm-bpf runs the control plane in Wasm. The wasm-bpf paper lists bpftime as a fallback runtime.
  • bpfman and Inspektor Gadget: Kubernetes-native approaches that the paper contrasts with wasm-bpf. bpfman is a daemon that loads and manages eBPF programs on behalf of applications through an API; the paper groups it with Inspektor Gadget and bpfd as the "dedicated BPF daemon over RPC" model, which adds a critical component that must be upgraded in step with the kernel features it exposes. Inspektor Gadget is a framework of eBPF "gadgets" for Kubernetes and Linux hosts; this chapter did not examine its design.
  • WALI, the WebAssembly Linux Interface (arXiv:2312.03858): a different answer to "Wasm needs more of the OS", exposing Linux syscalls almost directly to Wasm instead of a small purpose-built ABI.
  • WASI and the Component Model: WASI is moving from the "preview 1" function imports used here to components described in WIT. A component-model version of the eBPF interface, as hinted at by btf2wit and WASI issue #513, would give typed, language-neutral bindings and real resource handles instead of u64 integers. See the Component Model book.

Check your understanding

Q1. In wasm-bpf, which component runs the eBPF bytecode of handle_exec?

Only the user-space control plane is compiled to Wasm. The guest hands the embedded .bpf.o bytes to wasm_load_bpf_object, and the host's libbpf loads them into the kernel exactly as a native tool would.

Q2. A guest calls bpf_map_lookup_elem(fd, &key, &value) from libbpf-wasm.h. How does the value reach the guest's value variable?

wasm_bpf_map_operate gets key_size/value_size from the map info, checks that much guest memory is valid, and passes raw pointers into linear memory to bpf_map_lookup_elem_flags.

Q3. Why does every C example link with -Wl,--export-table?

A C function pointer in Wasm is an index into the function table. The host calls the callback with wasm_runtime_call_indirect (WAMR) or by looking up the table export (Wasmtime). Unresolved imports are handled by --allow-undefined.

Q4. How does skel->rodata->min_duration_ns = … in a Wasm guest reach the kernel?

bpftool -w gen skeleton records s->rodata_offset (1264 for the orb build, matching readelf), and bpf_object__open_skeleton in libbpf-wasm.h sets *mmaped = s->data + s->rodata_offset. .bss is not supported this way.

Q5. What problem did wasm_attach_bpf_program_fd (2026) fix?

Issue #48. With the string API, sockops attach opened whatever path the guest sent. The fd API resolves only descriptors in the runtime's own preopen registry; XDP is explicitly rejected on this path and keeps the interface-name string.

Q6. A colleague says "it's in a Wasm sandbox, so a third-party wasm-bpf plugin can't harm the host". What is the flaw?

The sandbox isolates the user-space half. The kernel half runs with the runtime's eBPF privileges, and the verifier checks safety, not intent.
