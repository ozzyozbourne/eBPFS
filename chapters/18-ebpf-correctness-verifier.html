ebpf-correctness-verifier: Translation Validation for eBPF Rewrites

The kernel verifier tells you a program is safe. It does not tell you that the program still does what it did before someone rewrote it. When the rewrite comes from a new compiler flag, a superoptimizer, a hand edit or an LLM agent, you want a second question answered: does the new bytecode return the same verdict, write the same maps and touch the packet the same way as the old one, for every input? ebpf-tv asks Z3 exactly that. This chapter explains the idea, reads the encoding, runs the tests, and measures where the model still has holes.

Why this matters

Every eBPF program that reaches the kernel passes the verifier first (Chapter 03). The verifier walks every path, tracks the type and range of each register, and rejects the program if any path could read out of bounds, leak a kernel pointer, run forever or call a helper with the wrong arguments. That is a strong guarantee, but it is a guarantee about safety. A program that drops every packet is perfectly safe. So is a program whose if (proto == IPPROTO_TCP) became if (proto == IPPROTO_UDP) after an "optimization". The verifier accepts both without complaint.

That gap used to matter mostly to compiler writers. It matters more now, because eBPF bytecode is increasingly rewritten by tools after the programmer has finished writing it:

  • Superoptimizers such as K2 and EPSO search for shorter instruction sequences that compute the same result.
  • Post-compilation optimizers such as Merlin rewrite bytecode with peephole rules before loading.
  • Agent-driven loops such as bpf-benchmark (Chapter 19) let an LLM propose rewrites and keep whichever ones the verifier accepts and the benchmark rewards.
  • Ordinary toolchain changes do it too. Upgrading clang, or moving from -mcpu=v1 to -mcpu=v3, produces different bytecode from the same C.

In all of these cases there is an old object that you trust because it has been running in production, and a new object that is supposed to behave the same. Benchmarks and tests check a handful of inputs. What you would like is a proof that holds for all inputs. Getting that proof for a single concrete pair of programs, instead of for the tool that produced them, is called translation validation. eunomia-bpf's ebpf-correctness-verifier repository builds a small translation validator for eBPF object files. The CLI is called ebpf-tv.

Key idea

ebpf-tv check old.bpf.o new.bpf.o encodes both programs as bit-vector formulas over the same symbolic inputs (context register, packet bytes, initial map contents, helper return values). It then asks Z3 whether any input makes their observable outputs differ. "No such input" is PASS. "Here is one" is FAIL. Anything the model cannot express is meant to be UNKNOWN, which callers treat as a rejection.

Translation validation in one page

There are two ways to trust a program transformer. Compiler verification proves once, ahead of time, that the transformer is correct for every possible input program. CompCert does this for C, and Jitterbug does it for the kernel's BPF JITs (see Related work). It is the strongest guarantee. It is also very expensive, and it has to be redone whenever the transformer changes. Translation validation, introduced by Pnueli, Siegel and Singerman in 1998, gives up on the transformer. After each run, a separate checker proves that this one output matches this one input. The transformer can be a heuristic, a random search or a language model. Only the checker has to be trusted. Necula applied the idea to gcc in 2000, and Alive2 does it today for LLVM IR.

For loop-free code the check reduces to one satisfiability question, often drawn as a "miter": feed the same inputs to both programs and ask whether their outputs can differ.

  1. Give every input a symbolic name. For eBPF that means the initial registers (r1 holds the context pointer, r10 the frame pointer), the packet or context bytes, the initial contents of every map, and the value each helper call returns.
  2. Translate each program into a formula P(in, out) that holds exactly when running the program on in produces out. Registers become 64-bit bit-vectors, so wrap-around and shifts behave as they do on the machine.
  3. Ask the solver for an assignment where P_old(in, out₁) ∧ P_new(in, out₂) ∧ out₁ ≠ out₂. If the solver says unsat, no input distinguishes the programs. If it says sat, its model is a concrete counterexample input.

A worked example

Strength reduction replaces a multiply by a power of two with a shift. In eBPF assembly (Chapter 02), with r1 as the input:

bf 10 00 00 00 00 00 00   r0 = r1
27 00 00 00 08 00 00 00   r0 *= 8
95 00 00 00 00 00 00 00   exit
bf 10 00 00 00 00 00 00   r0 = r1
67 00 00 00 03 00 00 00   r0 <<= 3
95 00 00 00 00 00 00 00   exit
bf 10 00 00 00 00 00 00   r0 = r1
67 00 00 00 02 00 00 00   r0 <<= 2
95 00 00 00 00 00 00 00   exit

The question "can these return different values?" is short in SMT-LIB, the solver's input language. This query is illustrative and hand-written, not code from the repository:

(declare-const r1 (_ BitVec 64))
(define-fun old_r0 () (_ BitVec 64) (bvmul r1 #x0000000000000008))
(define-fun new_r0 () (_ BitVec 64) (bvshl r1 #x0000000000000003))
(assert (not (= old_r0 new_r0)))
(check-sat)

Running it with Z3 (the Python z3-solver package, inside the orb) gives unsat: there is no 64-bit r1 for which r1*8 and r1<<3 differ, overflow included. Changing the shift to 2 gives sat and the model r1 = 2305843009213693952, which is 261. Z3 does not hunt for a "nice" input such as 1. It returns any assignment that satisfies the formula.

The same two pairs, written as raw 8-byte instructions and passed to the repository's backend, give the same answers:

$ smt_ebpf_equiv --old mul8.ins --new shl3.ins --map empty.maps --desc constant.desc
  "result": "PASS",
  "reason": "smt_equivalent",
$ smt_ebpf_equiv --old mul8.ins --new shl2.ins --map empty.maps --desc constant.desc
  "result": "FAIL",
  "reason": "smt_counterexample",

Real programs need more than one register. They branch, read packets, update maps and call helpers. The rest of this chapter shows how ebpf-tv encodes each of those, and what it leaves out.

Why this works for eBPF

Translation validation is hardest for loops and unbounded memory, because no finite formula captures them exactly. Classic eBPF programs avoid both. The verifier historically rejected back edges, the stack is 512 bytes, and maps have fixed key and value sizes. That is why a straight-line SMT encoding covers a useful share of real eBPF. K2 used the same observation in 2021.

What the repository is, and what it is not

The repository is young and small. It was created on 2026-06-30. At the commit studied (59ca424, 2026-09-16) it has 64 commits and about 19,700 lines of C++ and shell. It contains:

ebpf-tv

A C++17 CLI (tools/ebpf_tv.cc) with check, doctor, capabilities and selftest. It reads ELF objects, extracts the program section and map metadata, runs the backend and merges stage results.

smt_ebpf_equiv

The equivalence backend (tools/smt_equiv.cc + lib/ebpf_smt). It takes raw instructions plus map and input descriptions and calls Z3 in-process. Exit code 0/1/2 = PASS/FAIL/UNKNOWN.

lib/ebpf_smt

The SMT model of eBPF. It was extracted from the K2 superoptimizer (smartnic/superopt, commit f50ee1f), with K2's search code removed. K2's MIT notice is kept in LICENSE.origin.

Tests

CLI smoke tests, 190 instruction-level SMT checks, raw pass/fail smoke tests, ELF integration tests, and a 62-case corpus of real C programs compiled with clang.

The project's own documents are explicit about scope. docs/mvp-architecture.md lists as non-goals: proving load-time safety, running BPF_PROG_RUN, orchestrating an optimizer, synthesizing programs, comparing C or Rust source, and full CO-RE/BTF modelling. The tool does not generate transformations. It only judges them. The transformation can be anything that turns one object into another for the same section.

The pipeline

The stepper below follows one real run: the repository's XDP example, in which the old object returns 1 directly and the new one computes 0 + 1.

1. Choose a backend

With the default --equiv-backend identity, the only check is same_file_bytes(old, new). Identical files pass. Anything else is UNKNOWN with reason non_identical_requires_equivalence_backend. That default is deliberate: a tool that says nothing is better than one that says "pass" without proof. Passing --equiv-backend smt (or the aliases builtin and experimental-smt) selects the Z3 backend.

2. Check the section types match

infer_section_program_type() maps section prefixes to program types (xdp, tracepoint/, classifier or tc, kprobe/, uprobe/). Comparing an XDP section with a tracepoint section is FAIL (program_type_mismatch), because the two would get different contexts.

3. Build a shared environment

The CLI tries llvm-objcopy --dump-section=maps=… for legacy struct bpf_map_def maps and --dump-section=.BTF=… for libbpf-style SEC(".maps") maps. It reads R_BPF_64_64 relocations with llvm-readelf -r so each map reference in the bytecode becomes a map index. In the example there are no maps, so the stages report legacy_maps_not_found, btf_section_not_found and map_relocations_not_found (each a PASS), and the stage smt_env reports generated_smt_environment.

4. Describe the input

A .desc file states the input kind. infer_smt_input_type() chooses pkt for xdp* sections, skb for TC classifiers and constant otherwise. Packet inputs default to 64 bytes (SMT_DEFAULT_PACKET_SIZE). The backend's log line confirms it: program input type set as 1, maximum packet size set as 64 bytes.

5. Extract raw bytecode

llvm-objcopy --dump-section=xdp=old.ins writes the section as raw 8-byte instructions. This is the form the backend reads. Here that is 2 instructions for the old object and 3 for the new one (old_len: 2, new_len: 3).

6. Encode and solve

smt_ebpf_equiv loads both programs, builds their control-flow graphs and per-block formulas, checks K2's model-level memory safety for each, and hands Z3 the implication "same inputs ∧ old ∧ new ⇒ same outputs". Z3 proves it valid, so the stage result is PASS with reason smt_equivalence_pass.

7. Combine and run rules

combine() folds all stages (FAIL > UNKNOWN > PASS). Only if the result is PASS do the --rule-command hooks run, with {old}, {new}, {section} and similar placeholders substituted. The process exits 0 only for an overall PASS.

Inside the SMT encoding

The encoding is K2's (Xu et al., SIGCOMM 2021, §5 of the paper). Reading it in this repository's trimmed form is easier than reading the full superoptimizer. Figure 18.2 shows the overall shape. The subsections take each part of eBPF state in turn.

Registers: static single assignment

Each of the eleven registers is a 64-bit bit-vector constant. Each write creates a new version, named r_<prog>_<block>_<reg>_<version>, so a block becomes a conjunction of equalities. This is SSA form, written as logic. inst::smt_inst is one large switch. Here are a few of its cases:

  z3::expr curDst = sv.get_cur_reg_var(_dst_reg);
  z3::expr curSrc = sv.get_cur_reg_var(_src_reg);
  z3::expr newDst = string_to_expr("false");
  // update register according to the opcode type
  if (_opcode == CALL) {
    newDst = sv.update_reg_var(0); // r0 contains return value
  } else if ((op_type == OP_OTHERS) || (op_type == OP_LD)) {
    newDst = sv.update_reg_var(_dst_reg);
  }
  /* ... */
  switch (_opcode) {
    case ADD64XC: sv.mem_var.add_ptr(NEWDST, CURDST, IMM, path_cond); return predicate_add(CURDST, IMM, NEWDST);
    case ADD64XY: sv.mem_var.add_ptr(NEWDST, CURDST, CURSRC, path_cond); return predicate_add(CURDST, CURSRC, NEWDST);
    case SUB64XY: return predicate_sub(CURDST, CURSRC, NEWDST);
    case MUL64XC: return predicate_mul(CURDST, IMM, NEWDST);
    /* ... */
    case LDXB: return predicate_ld8(CURSRC, OFF, sv, NEWDST, block, enable_addr_off, is_win);
    /* ... */
    case CALL: return predicate_helper_function(imm, R1, R2, R3, R4, R5, R0, sv, block, enable_addr_off, is_win);
    default: return string_to_expr("false");
  }

The predicate_* helpers are macros over Z3's C++ operators, for example #define ADD_EXPR(in1, in2, out) (out EQ in1 + in2) in inst_codegen.h. 32-bit ALU operations use SET_HIGHER32_ZERO(...) to zero the upper half, as the ISA requires. Note the add_ptr calls: when an add or move derives one register from another, the model records that the result may point into the same memory region. Later loads use that to pick which memory table to read.

Control flow: blocks, path conditions and no loops

graph::gen_graph (verify/cfg.cc) splits the program into basic blocks and runs a DFS. Any back edge is an error:

  for (size_t i = 0; i < gnodes_out[cur_gnode_id].size(); i++) {
    unsigned int next_gnode_id = gnodes_out[cur_gnode_id][i];
    if (visited[next_gnode_id] && (!finished[next_gnode_id])) {
      string err_msg  = "illegal input: loop from node " + \
                        to_string(cur_gnode_id) + gnodes[cur_gnode_id].to_str() + \
                        " to node " + \
                        to_string(next_gnode_id) + gnodes[next_gnode_id].to_str();
      throw (err_msg);
    }
  }

The exception propagates to smt_equiv.cc, which reports UNKNOWN. This is the right answer: bounded loops (allowed by the kernel since 5.3) and bpf_loop are outside the model. Loop-free control flow is encoded in smt_prog::gen_smt. Blocks are visited in topological order. Each block gets its own register versions, and incoming edges are joined with an implication from the edge's path condition:

  for (size_t i = 0; i < blocks.size(); i++) {
    unsigned int b = blocks[i];
    // reset register version for different basic blocks, while memory tables
    // don't need to be reset for being shared among basic blocks.
    sv.set_new_node_id(b, g.nodes_in[b], path_con[b], post_reg_val);
    /* ... */
    gen_block_prog_logic(f_bl, f_mem, f_sc, sv, b, inst_lst);
    f_block[b] = f_block[b] && f_mem;
    if (b == 0) {
      /* ... */
      f_block[0] = f_block[0] && f_bl;
    } else {
      for (size_t j = 0; j < g.nodes_in[b].size(); j++) {
        // generate f_iv: the logic that the initial values are fed by the last basic block
        expr f_iv = string_to_expr("true");
        get_init_val(f_iv, sv, g.nodes_in[b][j], num_regs);
        reg_iv[b][j] = f_iv; // store
        // f_block[b] = f_block[b] && f_mem && implies(path_con[b][j], f_iv && f_bl);
        f_block[b] = f_block[b] && implies(path_con[b][j], f_iv && f_bl);
        f_block_pc = f_block_pc || path_con[b][j];
      }
    }
    p_sc = p_sc && implies(f_block_pc, f_sc);
    store_post_reg_val(sv, b, num_regs);
    gen_post_path_con(sv, b, inst_lst[g.nodes[b]._end]);
  }

The branch condition itself comes from smt_inst_jmp. The taken edge gets c_in ∧ e and the fall-through edge gets c_in ∧ ¬e. This function will come up again under limitations, so here it is in full:

z3::expr inst::smt_inst_jmp(smt_var & sv) const {
  // If opcode is valid, then define curDst, curSrc, imm
  if (get_opcode_type() != OP_COND_JMP) return string_to_expr("false");
  z3::expr curDst = sv.get_cur_reg_var(_dst_reg);
  z3::expr curSrc = sv.get_cur_reg_var(_src_reg);
  int64_t imm = (int64_t)_imm;

  switch (_opcode) {
    case JEQXC: return (CURDST == IMM);
    case JEQXY: return (CURDST == CURSRC);
    case JGTXC: return (ugt(CURDST, IMM));
    case JGTXY: return (ugt(CURDST, CURSRC));
    case JGEXC: return (uge(CURDST, IMM));
    case JGEXY: return (uge(CURDST, CURSRC));
    case JNEXC: return (CURDST != IMM);
    case JNEXY: return (CURDST != CURSRC);
    case JSGTXC: return (CURDST > IMM);
    case JSGTXY: return (CURDST > CURSRC);
    case JEQ32XC: return (CURDST_L32 == IMM_L32);
    case JEQ32XY: return (CURDST_L32 == CURSRC_L32);
    case JNE32XC: return (CURDST_L32 != IMM_L32);
    case JNE32XY: return (CURDST_L32 != CURSRC_L32);
    default: return string_to_expr("false");
  }
}

Initial state

The precondition fixes the starting registers. r1 equals a symbolic input, r10 equals the top of a 512-byte stack, and for packet programs r1 also equals the packet's start address:

z3::expr inst::smt_set_pre(z3::expr input, smt_var & sv) {
  z3::expr f = string_to_expr("true");
  f = (sv.get_cur_reg_var(1) == input) &&
      (sv.get_cur_reg_var(10) == sv.get_stack_bottom_addr()) &&
      sv.mem_layout_constrain();
  // add the relationship of r1 and address according to the program inpu type
  int pgm_input_type = mem_t::get_pgm_input_type();
  if ((pgm_input_type == PGM_INPUT_pkt) || (pgm_input_type == PGM_INPUT_skb)) {
    f = f && (sv.get_cur_reg_var(1) == sv.get_pkt_start_addr());
  } else if (pgm_input_type == PGM_INPUT_pkt_ptrs) {
    f = f && (sv.get_cur_reg_var(1) == sv.get_pkt_start_ptr_addr());
  }
  return f;
}

The three input kinds match the program types. pkt makes r1 point directly at the packet bytes. The corpus's XDP programs are written that way (__u8 *data = (__u8 *)ctx), which is a simplification of the real struct xdp_md. pkt-ptrs models a context holding data and data_end pointers, which is what real XDP programs read. skb models TC programs. Section-name inference never picks pkt-ptrs, so for a real XDP program you have to pass --smt-input-type pkt-ptrs yourself. Measurements are below.

Memory: tables of writes and reads

Arrays would be the obvious encoding of memory, but they are slow in SMT solvers. K2 instead keeps a separate table for each memory region (stack, packet, skb, packet-pointer context, each map's values). Each table holds a list of writes, the "wt", with a validity condition (the path condition of the block that did the write), an address or offset, and a byte. A load compares its address against every earlier write in the table and takes the latest matching one. If none matches, the load reads the region's initial contents, which are recorded in a second list (the "urt"). Every store becomes byte stores:

  for (int i = 0; i < ids.size(); i++) {
    z3::expr is_valid = sv.update_is_valid();
    z3::expr cond = path_cond && info_list[i].path_cond;
    f = f && (is_valid == cond);
    /* ... BPF_ST into the input packet is rejected ... */
    if (is_addr_off_table) { // addr in the entry is offset
      z3::expr addr_off = off + info_list[i].off;
      sv.mem_var.add_in_mem_table_wt(ids[i], block, is_valid, addr_off, in.extract(7, 0));
    } else {
      sv.mem_var.add_in_mem_table_wt(ids[i], block, is_valid, addr + off, in.extract(7, 0));
    }
  }

Pointer tracking (add_ptr above) lets the model use offsets within a region instead of absolute addresses for the stack and packet (enable_addr_off = true). This is one of the "domain-specific techniques" the K2 paper credits for speeding up equivalence checking "by 6 orders of magnitude".

The same tables give the safety side condition. smt_inst_safety_chk emits, for each load and store, a formula saying the access stays inside a modelled region. validator::safety_check proves pre ∧ PL ⇒ p_sc for each program. If the original fails, set_orig throws "original program is unsafe". If the candidate fails, is_equal_to returns -2. Both end as UNKNOWN in smt_equiv.cc. This is the model's own sanity check, not the kernel verifier.

Maps

A map is modelled as a key-value table with the same kind of write and read lists. bpf_map_lookup_elem returns either NULL or the address of a value in the map's memory table, depending on whether the key is present. update and delete add entries with the kernel's return codes. The interesting part is how the two programs see the same initial maps. Their read lists are tied together: if both programs look up equal keys, then either both see the key absent or both see it present with equal values:

      z3::expr f_k_both_inexist = (addr_v1 == NULL_ADDR_EXPR) && (addr_v2 == NULL_ADDR_EXPR);
      z3::expr f_k_both_exist = (addr_v1 != NULL_ADDR_EXPR) && (addr_v2 != NULL_ADDR_EXPR);
      // set the constrains on addr_v1, addr_v2, v1, v2
      f = f && z3::implies((map1_urt.is_valid[i] == Z3_true) &&
                           (map2_urt.is_valid[j] == Z3_true) &&
                           (k1 == rhs_key),
                           f_k_both_inexist ||
                           (f_k_both_exist && f_v1 && f_v2[j] && (v1 == v2[j])));

Map contents are part of the output too. smt_one_map_eq_chk requires that, after both programs run, every key either program touched has the same presence and value in both. So a rewrite that keeps the return value but forgets a counter update is a FAIL. The front end reads map shapes from legacy struct bpf_map_def sections and from libbpf's BTF __uint/__type form. Modelled types are hash, array, LRU hash and their per-CPU variants, plus prog-array, stack-trace, cgroup-array, ringbuf and perf-event-array, which are used only by the specific helpers that need them. Per-CPU maps are modelled as the current CPU's view. Anything else, such as BPF_MAP_TYPE_QUEUE, makes the loader throw "unsupported map type: …", which becomes UNKNOWN. The corpus tests this.

Helpers

Most of the July commits model one helper each. The idea is the same every time: a helper result that the program cannot predict becomes a fresh symbolic value, and both programs get the same value for their k-th such call. The shared values are named variables, rand_u32_0, rand_u32_1, …, created once and handed out in call order:

void smt_var::init_static_variables() {
  randoms_u32.clear();
  for (int i = 0; i < mem_t::_layout._n_randoms_u32; i++) {
    string name = "rand_u32_" + to_string(i);
    randoms_u32.push_back(to_expr(name, 32));
  }
}

z3::expr smt_var::get_next_random_u32() {
  assert(rand_u32_cur_id < randoms_u32.size());
  z3::expr rand_u32 = randoms_u32[rand_u32_cur_id];
  rand_u32_cur_id++;
  return rand_u32;
}
z3::expr predicate_symbolic_u32_helper(z3::expr out, smt_var& sv) {
  z3::expr f = (out == z3::concat(to_expr((int32_t)0, 32), sv.get_next_random_u32()));
  return f;
}

z3::expr predicate_symbolic_u64_helper(z3::expr out, smt_var& sv) {
  z3::expr low = sv.get_next_random_u32();
  z3::expr high = sv.get_next_random_u32();
  return out == z3::concat(high, low);
}

So bpf_get_prandom_u32() & 7 in both programs is equivalent, even though the value is random. That is the corpus case xdp_prandom_equivalent. docs/backend-contract.md is honest about what this leaves out: no monotonic clocks, no ranges, no stability between calls. Because values are matched by call position, a rewrite that reorders two helper calls should come out as FAIL rather than PASS. That is inferred from the code and was not tested. Helpers that write memory, such as bpf_get_current_comm, bpf_probe_read*, bpf_skb_load_bytes and bpf_xdp_store_bytes, write that many symbolic or copied bytes into the destination table. They are only modelled when the size is a constant in a small range: exactly 4 bytes for probe_read, and 1–16 bytes for most of the others. raw_program_loader.cc enforces this with a small constant propagation pass that throws messages like "unsupported bpf_probe_read size; expected constant 4". An unknown helper ID gives unsupported helper id. bpf_trace_printk and bpf_redirect are tested to produce that.

Exits and tail calls

An ordinary exit sets ret_val = r0 and pgm_exit_type = 0. A bpf_tail_call ends the program with pgm_exit_type = tail_call and records r1..r3 as the call's arguments. The final comparison handles both cases:

z3::expr smt_pgm_eq_chk(smt_var& sv1, smt_var& sv2, bool is_win) {
  z3::expr f = smt_pgm_mem_eq_chk(sv1, sv2, is_win);

  smt_output& out1 = sv1.smt_out, out2 = sv2.smt_out;
  // registers equivalence check
  z3::expr same_regs = Z3_true;
  if (! is_win) {
    same_regs = (out1.ret_val == out2.ret_val);
  } else {
    /* ... window mode: compare live-out registers ... */
  }
  if ( (! out1.pgm_has_tail_call) && (! out2.pgm_has_tail_call) ) {
    f = f && same_regs;
  } else {
    z3::expr same_exit_type = (out1.pgm_exit_type == out2.pgm_exit_type);
    z3::expr same_tail_call_paras = (out1.tail_call_args[0] == out2.tail_call_args[0]) &&
                                    (out1.tail_call_args[1] == out2.tail_call_args[1]) &&
                                    (out1.tail_call_args[2] == out2.tail_call_args[2]);
    f = f && same_exit_type &&
        z3::implies(out1.pgm_exit_type == PGM_EXIT_TYPE_default, same_regs) &&
        z3::implies(out1.pgm_exit_type == PGM_EXIT_TYPE_tail_call, same_tail_call_paras);
  }
  return f;
}

"Observable behaviour" is therefore defined as: the return value, or the tail-call target and arguments, plus the final contents of maps, packet and skb memory. Stack contents at exit do not count, because they are dead. Side effects outside this list do not count either, and that matters for helpers like bpf_perf_event_output, which is not modelled and therefore yields UNKNOWN.

The query and the solver

With both program formulas built, validator::is_equal_to forms the implication and checks whether it is valid:

  expr pre_mem_same_mem = smt_pgm_set_same_input(_post_sv_orig, post_sv_candidate, _is_win);
  expr post = string_to_expr("true");
  smt_post(post, VLD_PROG_ID_ORIG, VLD_PROG_ID_CANDIDATE, post_sv_candidate);
  expr smt = implies(pre_mem_same_mem && _pre_orig && pre_candidate && _pl_orig && pl_candidate, post);
  /* ... */
  int is_equal = is_smt_valid(smt, mdl);
    z3::tactic t = z3::tactic(smt_c, "bv");
    z3::solver s = t.mk_solver();

    s.add(!smt);
    // cout << "Running the solver..." << endl;

A formula is valid when its negation is unsatisfiable, so "unsat" means "equal". Z3's bv tactic bit-blasts the bit-vector formula to SAT, which is usually the fastest approach for fixed-width arithmetic. On sat, gen_counterex turns the model into a concrete input and runs K2's interpreter on it. The wrapper currently reports only "smt_counterexample" and does not print the input. Adding a counterexample to the JSON output would be a natural next step for agent use.

The wrapper maps all of this to an exit code:

K2 throws C++ std::string values for unsupported cases. Catching them all and returning UNKNOWN is how the repository keeps its rule that missing evidence never turns into PASS. As the next sections show, the rule holds whenever the model notices it is out of its depth.

The result contract

The repository spends more words on its contract than on any other topic, and for an automated gate the contract is the product. docs/backend-contract.md says backends "may be incomplete, but they must never turn missing evidence into PASS." The combiner is short:

std::string combine(const std::vector<StageResult> &stages) {
  bool saw_unknown = false;
  for (const auto &stage : stages) {
    if (stage.result == FAIL) {
      return FAIL;
    }
    if (stage.result == UNKNOWN) {
      saw_unknown = true;
    }
  }
  return saw_unknown ? UNKNOWN : PASS;
}
ResultMeaningTypical reasons
PASSEquivalent within the modelled semantics, and every rule command passedsmt_equivalence_pass, identity byte match
FAILMalformed input, incompatible metadata, or a semantic counterexamplesmt_equivalence_fail, program_type_mismatch, file_not_found, rule_fail
UNKNOWNOutside the model, timed out, or not enough metadata. Treat as "do not merge"unsupported helper id, unsupported map type, loops, non_identical_requires_equivalence_backend

The README states the intended policy directly: "UNKNOWN is a rejection for automated merge or deploy. It is still useful feedback for agents because it distinguishes unsupported modeling from a concrete counterexample." Note that the CLI process exits 1 for both FAIL and UNKNOWN. You have to read the result field in the JSON to tell them apart. The backend binary does use distinct codes 0/1/2.

Project-specific policy can be added after equivalence. A rule command might check the instruction count went down, that the new object still loads on a target kernel, or that a bpftool dump matches a pattern:

build/ebpf-tv check old.bpf.o new.bpf.o \
  --section xdp \
  --equiv-backend smt \
  --smt-equiv build/smt_ebpf_equiv \
  --rule-command 'my-rule --old {old} --new {new} --section {section}'

(That command is from the README. my-rule is a placeholder for your own script.) A rule's exit code 0, 1 or 2 maps to PASS, FAIL or UNKNOWN. Any other non-zero exit is UNKNOWN, because "the checker cannot distinguish an infrastructure error from an unsupported rule case."

The test suite

Five CTest tests run, from the cheapest to the most realistic:

  • ebpf_tv_cli_smoke: result aggregation, missing tools, identity-backend behaviour, rule commands, doctor and capabilities output. It also checks that the help text hides removed names (prevail, --k2, superopt, …).
  • ebpf_smt_inst_codegen_test: 190 checks that each instruction's compute_* (concrete interpreter) and predicate_* (SMT) agree, for example check predicate_add match compute_add SUCCESS. All 190 print SUCCESS. Note what this does and does not prove: it shows the SMT model agrees with K2's interpreter, not with the kernel. If both make the same mistake, the test still passes. One case below shows exactly that.
  • smt_equiv_smoke: --version fields, ret0 vs a copy (PASS, exit 0), ret0 vs ret1 (FAIL, exit 1).
  • ebpf_tv_smt_cli_integration: ELF section extraction, generated XDP descriptions, legacy map extraction, section-type prechecks, doctor.
  • ebpf_tv_real_app_corpus: 62 cases, each compiling an old and a new C file with clang -target bpf -O2 and asserting the result: 58 PASS, 1 FAIL and 3 UNKNOWN. This is the slowest test (about 50 s here).

The corpus cases are small, but they are real C compiled by a real clang. The packet-filter trio shows the style:

Unsound cases

Several rows say PASS for programs that behave differently. The cause is not Z3. It is the instruction model inherited from K2. The opcode table (opcode_2_idx in inst.cc) covers ALU64 ADD/OR/AND/LSH/RSH/XOR/MOV/ARSH (immediate and register), SUB register only, MUL and DIV immediate only, NEG, the 32-bit ADD/OR/AND/LSH/RSH/MOV/ARSH, byte swaps, loads and stores, atomic add, JA, JEQ/JGT/JGE/JNE/JSGT and the 32-bit JEQ/JNE. Everything else in RFC 9669 is missing, including MOD, SDIV/SMOD, MOVSX, sign-extending loads, JSET, JLT/JLE/JSGE/JSLT/JSLE, most JMP32 compares and BPF-to-BPF calls. A missing ALU opcode is not translated into any constraint, so the instruction is silently skipped: opcode_2_idx() maps any opcode it does not list to index 0 (IDX_NOP, type OP_NOP), and smt_prog::smt_block() only encodes instructions of the ALU, load, store and call types. A missing jump is not recognised as a branch. Neither raises an error, so neither becomes UNKNOWN. Since LLVM 20 the default BPF CPU is v3, which emits JMP32 compares freely, so this affects ordinary default builds. Until this is fixed, treat a PASS as trustworthy only if you have checked that both objects use only the opcodes listed above. One possible guard is to reject any instruction for which inst::is_valid_opcode is false in raw_program_loader.cc, turning it into UNKNOWN. That fix is a suggestion: it was not tested, and it does not address the signed-division issue.

The input range deserves context. The bound applies to the symbolic value of r1. For packet programs, r1 is a pointer, and the packet bytes are separate, unconstrained symbolic memory. So real programs that branch on packet or map contents are not affected. The bound bites only when a program computes with r1 itself, as in raw constant-mode inputs. The source marks it // TODO: set input limit, need to be generalized.

Other limits come straight from the design and the docs:

  • No safety. PASS says nothing about whether the new object loads. Pair it with the kernel verifier or PREVAIL (Chapter 03).
  • No loops, no subprograms. Back edges give UNKNOWN. So do programs that use unmodelled helpers such as bpf_loop, through the helper check. BPF-to-BPF calls fall into the unmodelled-opcode gap described above.
  • One program at a time. The CLI compares one section. Multi-program objects need one run per section (--old-section/--new-section help when names differ).
  • Small packets. The packet is 64 bytes by default (--smt-max-pkt-size changes it). Behaviour that depends on longer packets is outside the model.
  • Partial helpers and maps. About 60 helpers are modelled, mostly as fresh symbolic values with constant-argument preconditions. Hash-map capacity, LRU eviction, clocks that only move forward and ringbuf output are not modelled. The support matrix lists the details.
  • CO-RE. Objects whose behaviour depends on BTF relocations being applied at load time are outside the model (README: "not yet a complete CO-RE-aware object equivalence checker").
  • No counterexample in the output. FAIL carries a reason but not the input that triggered it, although K2's gen_counterex computes one internally.

Benefits

Even with those gaps, the repository gets several things right:

  • A precise interface. Two objects in, a JSON verdict out, with the command, exit code and stderr of every stage. The FAIL/UNKNOWN distinction is the right shape for a CI gate or an agent's feedback loop: "your rewrite is wrong" and "I cannot judge your rewrite" lead to different next actions.
  • Conservative defaults. The identity backend never claims more than byte equality. Missing tools, unsupported maps, helpers with dynamic sizes and loops all give UNKNOWN, and tests check that they do.
  • It reuses a published model. It does not invent a new eBPF semantics. It extracts K2's, which has been through peer review and artifact evaluation, and deletes the parts it does not need.
  • Bytecode level. Checking bytecode, not C, means the same checker works for clang flag changes, hand edits, superoptimizers and Rust-compiled programs. It also checks the thing that actually runs.
  • Cheap to run. The corpus programs take well under a second each. The whole corpus, including 124 clang compilations, finished in 50 s on a shared orb.

Related work

K2: where the model comes from (SIGCOMM 2021)

K2, by Xu, Wong, Wagle, Narayana and Sivaraman, is "a program-synthesis-based compiler that automatically optimizes BPF bytecode with formal correctness and safety guarantees." It runs a stochastic (MCMC) search over candidate programs. Each promising candidate is checked against the original with the SMT encoding described in this chapter, and also against K2's own safety model. A post-processing pass loads the best outputs into the kernel to weed out any the real verifier rejects. The paper reports 6–26% smaller programs than the best clang output. Its equivalence-checking optimizations (memory offsets, per-region tables, map modelling, caching) made the check about six orders of magnitude faster. ebpf-tv keeps the checker and throws away the search. In K2 the checker validates candidates the search produced. In ebpf-tv it validates whatever you give it. That shift matters for the gaps above. K2's search only proposes instructions from its own supported set, so an unmodelled opcode could reach the checker only from the original program. A general validator has to cope with any opcode clang emits.

Merlin (ASPLOS 2024)

Merlin, by Mao, Ding, Zhai and Ma, optimizes eBPF in two tiers: custom LLVM IR passes (alignment, macro-op fusion) and a bytecode rewriter that applies instruction merging and strength reduction before verification. It is rule-based and fast. The authors report 73% fewer instructions than the unoptimized programs, and an optimizer that runs about 106 times faster than K2. Its correctness rests on each rule being right, not on a per-program proof. Merlin's output is exactly the kind of old/new pair ebpf-tv is meant for.

EPSO (ASE 2025)

EPSO, by Zhu, Liu, Zhu, Liu and Bu, sits between K2 and Merlin. It runs an expensive superoptimizer offline to discover rewrite rules (795 in the arXiv version), caches them, and applies them cheaply to new programs. The paper reports it beats K2 on all benchmarks and Merlin on most. A cached rule is proven once and reused. Translation validation would still catch any context in which a rule's side conditions do not actually hold.

Jitterbug (OSDI 2020)

Jitterbug, by Nelson, Van Geffen, Torlak and Wang, is the compiler-verification side of the picture. It proves the kernel's BPF JITs correct for all inputs, one BPF instruction at a time, using Rosette and Serval. It found and fixed 16 bugs in deployed JITs and added a verified RV32 JIT. Jitterbug covers the step after loading (BPF → machine code). ebpf-tv covers rewrites before loading (BPF → BPF). The two designs also show the trade-off from the start of this chapter. Jitterbug proves the translator once, at great effort. ebpf-tv checks each output, cheaply, but only inside its model.

Heimdall (arXiv 2026)

The repository's docs/heimdall-notes.md discusses Heimdall (Dasu et al.), which uses LLMs to translate libbpf C programs to Aya Rust and proves each translation equivalent at the bytecode level, using angr-based symbolic execution of eBPF and Z3. It reports 109 of 115 programs proven equivalent. The notes say ebpf-tv borrows Heimdall's framing (compare compiled bytecode, use one shared environment for both programs, report unsupported cases), but not its pipeline (translation, repair, counterexample feedback).

Translation validation outside eBPF

The term and the method come from Pnueli, Siegel and Singerman (TACAS 1998). Necula's validator for gcc (PLDI 2000) showed it could keep up with a real optimizing compiler. Alive2 (PLDI 2021) does bounded translation validation for LLVM IR with an SMT solver and has found dozens of LLVM bugs. Alive2 also makes the same choice ebpf-tv makes about loops: unroll to a bound or give up, and say so.

Chapters 03, 17 and 19

Chapter 03 covers the safety half of the problem: the kernel verifier, tnums and range tracking, and PREVAIL's abstract interpretation. The verifier over-approximates one program to prove it never misbehaves. ebpf-tv encodes two programs exactly, within its model, to prove they behave alike. Chapter 17 (bpfix) helps humans and LLMs get rejected programs past the verifier. An LLM repair that gets a program accepted may still change what it does, and that is the question this chapter's tool answers. Chapter 19 (bpf-benchmark and bpfperf) is the natural consumer: an agent-driven loop that proposes eBPF optimizations and returns verifier, JIT and performance feedback, with a bpfopt component that rewrites bytecode. At the commits studied, bpf-benchmark does not call ebpf-tv: a search of that repository for ebpf-tv or correctness-verifier finds nothing. The connection is architectural. ebpf-tv supplies the "is it still the same program?" stage that a benchmark-driven loop otherwise lacks, and its UNKNOWN verdicts tell the agent to try a rewrite the checker can judge.

Check your understanding

Q1. The kernel verifier accepts both the old and the new object. What has that established about their equivalence?

The verifier checks memory safety, termination and helper usage for one program at a time. A safe program can still return the wrong verdict. Equivalence needs a separate check.

Q2. smt_ebpf_equiv adds ¬F to Z3, where F = pre ∧ PL_old ∧ PL_new ⇒ post. Z3 answers unsat. What does the tool report?

If ¬F has no satisfying assignment, F holds for every input, so the programs are equal within the model. sat would give a counterexample. Z3's separate unknown answer maps to UNKNOWN.

Q3. Why do both programs get the same value when each calls bpf_get_prandom_u32() once?

smt_var::get_next_random_u32() returns the next variable from a list built once for both programs. The value is unconstrained but shared, so x & 7 in both programs is provably equal.

Q4. Where does PREVAIL run in the current ebpf-tv check pipeline?

The early Python design had PREVAIL stages. Commit ec136b4 removed them, and the README now says the tool does not prove safety. The GitHub description is out of date.

Q5. An object compiled with -mcpu=v3 contains if w1 s> 4 goto …. Based on the measurements in this chapter, what can a PASS on that object be trusted for?

The measured v3 case returned PASS for programs that differ. Missing opcodes are not rejected, so you must check the opcodes yourself or add a guard that turns them into UNKNOWN.

Q6. What is the main difference between Jitterbug and ebpf-tv?

This is compiler verification versus translation validation. Jitterbug proves the BPF→machine-code JITs correct in general. ebpf-tv checks one BPF→BPF rewrite at a time and trusts nothing about the tool that made it.
