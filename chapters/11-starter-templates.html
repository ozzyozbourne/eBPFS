Chapter 11

Starter templates for libbpf and libbpf-rs

You have read how a libbpf program is compiled, embedded in a skeleton and loaded (06). Now you want your own repository: one tool, its own name, a build that works on a fresh laptop and in CI, and a release binary at the end. What is the shortest correct path from "nothing" to that, and what do eunomia-bpf's two starter templates actually give you?

Prerequisites: 06, 08Repos: eunomia-bpf/libbpf-starter-template @ 6e572b6, libbpf-rs-starter-template @ 8927eea~40 min

Why this matters: the first hour of an eBPF project

Writing the BPF program is rarely the hard part of starting an eBPF project. The hard part is everything around it. A libbpf application in C needs at least five things to line up before the first line of output appears:

  • a libbpf library of a known version, ideally linked statically so the binary does not depend on whatever libbpf.so the target distribution ships;
  • a bpftool new enough to generate skeletons for the BPF features you use;
  • a vmlinux.h for each CPU architecture you build for, so the BPF code can name kernel types (06 explains why this one header is enough when CO-RE is used);
  • a build that compiles the kernel half with clang -target bpf, turns the object into a skeleton header, and only then compiles the user half against it;
  • a toolchain on the build machine: clang, llvm, libelf, zlib, make. On the target, only libelf and zlib.

The libbpf authors solved this once in libbpf-bootstrap, which chapter 06 dissected. But libbpf-bootstrap is a collection of examples: one Makefile builds about fifteen demo apps (minimal, bootstrap, kprobe, fentry, uprobe, usdt, tc, lsm, profile and more) from inside examples/c/, with the submodules two directories up. It is not designed to be the root of somebody else's product. If you want a repository that contains only your tool, you have to cut it out: copy one example, copy the Makefile, fix the relative paths, delete the other apps, add the submodules to your own repo, and then write CI from scratch.

eunomia-bpf's starter templates are that cut-out, done in advance and published as GitHub template repositories. Each one contains exactly one example application, a build that works from the repository root, a Dockerfile, a development container, a Nix flake, and two GitHub Actions workflows that build the binary on every push, attach it to a GitHub release and push a container image. This chapter reads every file of the C and Rust templates, builds and runs the C one on this curriculum's orb, and shows exactly what you need to change to make the template yours.

Key idea

A starter template is not a framework and adds no runtime code. It is a pre-arranged repository layout: libbpf-bootstrap's build rules and one example app, moved to the root of a repository, with dependencies pinned (submodules in C, Cargo versions in Rust) and packaging and CI already wired. Everything you learned in chapter 06 applies unchanged; the template only decides where files live and what runs on git push.

What a GitHub template repository is

"Template" here is a GitHub feature, not an eBPF concept. Any repository whose admin ticks Template repository in its settings shows a Use this template button. Clicking it creates a new repository in your account with the same files and directory structure. According to GitHub's documentation, the differences from a fork are that the new repository starts with a single commit instead of the parent's full history, it is not linked to the parent, and by default only the default branch is copied (an Include all branches option copies the rest). The GitHub CLI does the same thing from a terminal:

# Illustrative: create your own repo from the C template and clone it (flags from `gh repo create --help`, gh 2.99)
$ gh repo create my-execsnoop --template eunomia-bpf/libbpf-starter-template --public --clone

All three eunomia-bpf starter repositories have the template flag set (GitHub API field is_template: true, checked 2026-11-06). Because the result is an unrelated repository, there is no "update from upstream" button later: if the template fixes a bug after you started, you copy the fix by hand. Keep that in mind when reading the maintenance section below.

Unverified: submodules

The C template depends on two git submodules. GitHub's template documentation does not say whether submodule links (the gitlink entries in the index) are carried into the generated repository. After you clone your new repository, run git submodule status. If it lists libbpf and bpftool with commit IDs, you are fine. If it prints nothing while .gitmodules exists, re-create them with git submodule add https://github.com/libbpf/libbpf.git libbpf (and the same for bpftool) and commit. The template's own README assumes they survive and tells you to clone with --recursive.

The template family

The README of each template lists four siblings, one per language/framework. Two of them are this chapter's subject; the other two are covered briefly here or elsewhere.

libbpf-starter-template (C)

libbpf + bpftool as submodules, a vendored per-architecture vmlinux.h directory, and libbpf-bootstrap's bootstrap example (process exec/exit tracer with a ring buffer). Built with make. Last commit 2026-09-16. 78 stars, 26 forks.

libbpf-rs-starter-template (Rust)

A Cargo crate using libbpf-rs and libbpf-cargo 0.20, with the runqslower example (run-queue latency via tp_btf) and a single vendored vmlinux.h. Built with cargo build through a build.rs. Last commit 2026-09-16. 30 stars, 1 fork.

cilium-ebpf-starter-template (Go)

cilium/ebpf v0.10.0 with bpf2go and a kprobe + ring buffer example. Less active: last commit 2023-03-25. Summarised later in this chapter.

eunomia-template (C, eunomia-bpf)

No hand-written loader at all: ecc compiles the BPF code to a package and ecli runs it. A different model, covered in 10 · eunomia-bpf, ecc and ecli.

Star and fork counts are from the GitHub API on 2026-11-06 and will drift. The C template is the most used and the most maintained of the group: it received a submodule refresh in July 2026 (13a3549, "updated submodules and its dependencies") and a compile fix in 2025. The Rust template's last functional change was in August 2024 (7553497 "fix compile and docker name"); later commits are a Dependabot bump and a CI action pin.

The application lives in src/ and follows libbpf-bootstrap's naming convention exactly: NAME.bpf.c is compiled for the BPF target, NAME.c for the host, and NAME.h holds the structures that cross the kernel/user boundary. Everything under src/.output/ is generated.

Two choices differ from libbpf-bootstrap. First, the vmlinux headers are copied into the repository instead of being a submodule pointing at libbpf/vmlinux.h. That makes the template self-contained but heavy (19 MB of headers in every repository generated from it), and it means the headers only change when someone commits new ones. Each architecture directory has a vmlinux.h symlink that selects one version; for x86 that is vmlinux_601.h, a header generated from a 6.1 kernel, even though 6.8 and 7.1 headers sit next to it. Second, there is no blazesym submodule, because the only example does not symbolize stack traces.

Which header should you use?

With CO-RE the header's kernel version matters less than you might think: field offsets are relocated at load time anyway. What the header decides is which types and fields exist at compile time. If your program uses a type or a field added after 6.1, switch the symlink (ln -sf vmlinux_71.h vmlinux/x86/vmlinux.h) or generate a header from your own kernel with bpftool btf dump file /sys/kernel/btf/vmlinux format c. Then guard newer fields with bpf_core_field_exists() so older kernels still load the program.

The build, end to end

The top-level Makefile only forwards to src/:

build:
	make -C src

clean:
	make -C src clean

install:
	sudo apt update
	sudo apt-get install -y --no-install-recommends \
        libelf1 libelf-dev zlib1g-dev libssl-dev \
        make clang llvm

make install is a convenience for Ubuntu/Debian; it installs the build toolchain, not your tool. The real work is in src/Makefile. Its first lines fix every path relative to src/ and pick the architecture:

OUTPUT := .output
CLANG ?= clang
LLVM_STRIP ?= llvm-strip
LIBBPF_SRC := $(abspath ../libbpf/src)
BPFTOOL_SRC := $(abspath ../bpftool/src)
LIBBPF_OBJ := $(abspath $(OUTPUT)/libbpf.a)
BPFTOOL_OUTPUT ?= $(abspath $(OUTPUT)/bpftool)
BPFTOOL ?= $(BPFTOOL_OUTPUT)/bootstrap/bpftool
ARCH ?= $(shell uname -m | sed 's/x86_64/x86/' \
			 | sed 's/aarch64/arm64/' \
			 | sed 's/ppc64le/powerpc/' \
			 | sed 's/mips.*/mips/' \
			 | sed 's/arm.*/arm/' \
			 | sed 's/riscv64/riscv/')
VMLINUX := ../vmlinux/$(ARCH)/vmlinux.h
# Use our own libbpf API headers and Linux UAPI headers distributed with
# libbpf to avoid dependency on system-wide headers, which could be missing or
# outdated
INCLUDES := -I$(OUTPUT) -I../libbpf/include/uapi -I$(dir $(VMLINUX))
CFLAGS := -g -Wall
ALL_LDFLAGS := $(LDFLAGS) $(EXTRA_LDFLAGS)

APPS = bootstrap
/* ... CLANG_BPF_SYS_INCLUDES, quiet-output helpers, allow-override for CC/LD ... */

Three things are worth noticing. APPS is the list of applications; adding a second tool is one word. ARCH maps uname -m to the kernel's architecture names, which is also the directory name under vmlinux/; the sed chain recognises powerpc and mips, but the template ships no headers for them, so on those machines you must supply your own vmlinux.h. And -I$(OUTPUT) comes first: libbpf's install step below copies the libbpf headers (bpf/libbpf.h, bpf/bpf_helpers.h, …) into .output/bpf/, so both halves of the app compile against the submodule's headers, never the system's.

The rules then build four things in order:

# Build libbpf
$(LIBBPF_OBJ): $(wildcard $(LIBBPF_SRC)/*.[ch] $(LIBBPF_SRC)/Makefile) | $(OUTPUT)/libbpf
	$(call msg,LIB,$@)
	$(Q)$(MAKE) -C $(LIBBPF_SRC) BUILD_STATIC_ONLY=1		      \
		    OBJDIR=$(dir $@)/libbpf DESTDIR=$(dir $@)		      \
		    INCLUDEDIR= LIBDIR= UAPIDIR=			      \
		    install

# Build bpftool
$(BPFTOOL): | $(BPFTOOL_OUTPUT)
	$(call msg,BPFTOOL,$@)
	$(Q)$(MAKE) ARCH= CROSS_COMPILE= OUTPUT=$(BPFTOOL_OUTPUT)/ -C $(BPFTOOL_SRC) bootstrap

# Build BPF code
$(OUTPUT)/%.bpf.o: %.bpf.c $(LIBBPF_OBJ) $(wildcard %.h) $(VMLINUX) | $(OUTPUT)
	$(call msg,BPF,$@)
	$(Q)$(CLANG) -g -O2 -fno-stack-protector -target bpf -D__TARGET_ARCH_$(ARCH) $(INCLUDES) $(CLANG_BPF_SYS_INCLUDES) -c $(filter %.c,$^) -o $@
	$(Q)$(LLVM_STRIP) -g $@ # strip useless DWARF info

# Generate BPF skeletons
$(OUTPUT)/%.skel.h: $(OUTPUT)/%.bpf.o | $(OUTPUT) $(BPFTOOL)
	$(call msg,GEN-SKEL,$@)
	$(Q)$(BPFTOOL) gen skeleton $< > $@

# Build user-space code
$(patsubst %,$(OUTPUT)/%.o,$(APPS)): %.o: %.skel.h

$(OUTPUT)/%.o: %.c $(wildcard %.h) | $(OUTPUT)
	$(call msg,CC,$@)
	$(Q)$(CC) $(CFLAGS) $(INCLUDES) -c $(filter %.c,$^) -o $@

# Build application binary
$(APPS): %: $(OUTPUT)/%.o $(LIBBPF_OBJ) | $(OUTPUT)
	$(call msg,BINARY,$@)
	$(Q)$(CC) $(CFLAGS) $^ $(ALL_LDFLAGS) -lelf -lz -o $@
  1. libbpf.a. The submodule's own Makefile builds only the static library (BUILD_STATIC_ONLY=1) and installs it with its headers into .output/.
  2. bpftool. The bootstrap target builds a minimal bpftool, enough for gen skeleton and btf dump, without optional libraries like libbfd or libcap. It is built for the host (ARCH= CROSS_COMPILE=) even when cross-compiling the app, because it runs during the build.
  3. The BPF object. clang -target bpf with -g (needed for BTF and CO-RE records), then llvm-strip -g to remove DWARF, which the kernel never reads. The -fno-stack-protector flag was added in 2025 (5ba4410, "fix: disable stack-protector for eBPF parts to fix compile error"): some distributions' clang enables stack protection by default, and the BPF target cannot use it.
  4. The skeleton and the binary. bpftool gen skeleton writes .output/bootstrap.skel.h; the static pattern rule makes bootstrap.o depend on it; the link step adds libbpf.a, -lelf and -lz.

Compared with libbpf-bootstrap at commit 820a1bd the rules are an older, simpler variant. libbpf-bootstrap now compiles to a temporary NAME.tmp.bpf.o and runs bpftool gen object (BPF static linking) to produce the final object, and both compilers write -MMD -MP dependency files. The template has neither. The first difference costs nothing for a one-file program. The second one is visible, as the next section shows.

The example program, kernel side

src/bootstrap.bpf.c is libbpf-bootstrap's bootstrap example with only whitespace changes (checked with diff against libbpf-bootstrap 820a1bd). It is a good choice for a template because it exercises the pieces most real tools need: a hash map for state, a ring buffer for events, a read-only global as a configuration knob, and CO-RE reads of kernel structures.

#include "vmlinux.h"
#include <bpf/bpf_helpers.h>
#include <bpf/bpf_tracing.h>
#include <bpf/bpf_core_read.h>
#include "bootstrap.h"

char LICENSE[] SEC("license") = "Dual BSD/GPL";

struct {
	__uint(type, BPF_MAP_TYPE_HASH);
	__uint(max_entries, 8192);
	__type(key, pid_t);
	__type(value, u64);
} exec_start SEC(".maps");

struct {
	__uint(type, BPF_MAP_TYPE_RINGBUF);
	__uint(max_entries, 256 * 1024);
} rb SEC(".maps");

const volatile unsigned long long min_duration_ns = 0;

SEC("tp/sched/sched_process_exec")
int handle_exec(struct trace_event_raw_sched_process_exec *ctx)
{
	struct task_struct *task;
	unsigned fname_off;
	struct event *e;
	pid_t pid;
	u64 ts;

	/* remember time exec() was executed for this PID */
	pid = bpf_get_current_pid_tgid() >> 32;
	ts = bpf_ktime_get_ns();
	bpf_map_update_elem(&exec_start, &pid, &ts, BPF_ANY);

	/* don't emit exec events when minimum duration is specified */
	if (min_duration_ns)
		return 0;

	/* reserve sample from BPF ringbuf */
	e = bpf_ringbuf_reserve(&rb, sizeof(*e), 0);
	if (!e)
		return 0;

	/* fill out the sample with data */
	task = (struct task_struct *)bpf_get_current_task();

	e->exit_event = false;
	e->pid = pid;
	e->ppid = BPF_CORE_READ(task, real_parent, tgid);
	bpf_get_current_comm(&e->comm, sizeof(e->comm));

	fname_off = ctx->__data_loc_filename & 0xFFFF;
	bpf_probe_read_str(&e->filename, sizeof(e->filename), (void *)ctx + fname_off);

	/* successfully submit it to user-space for post-processing */
	bpf_ringbuf_submit(e, 0);
	return 0;
}
/* ... handle_exit: SEC("tp/sched/sched_process_exit"), ignores thread exits,
       computes duration from exec_start, reads exit_code via BPF_CORE_READ ... */

For a template user, the interesting lines are the ones you will replace. SEC("tp/sched/...") chooses the hook (any section name libbpf understands works; see 05). The two .maps definitions become fields of the skeleton's maps struct by name. The const volatile global becomes skel->rodata->min_duration_ns. And struct event comes from bootstrap.h, which user space includes too, so both sides agree on the record layout. Chapter 04 covers maps and ring buffers in depth (04); chapter 06 covers BPF_CORE_READ and read-only globals.

#define TASK_COMM_LEN 16
#define MAX_FILENAME_LEN 127

struct event {
	int pid;
	int ppid;
	unsigned exit_code;
	unsigned long long duration_ns;
	char comm[TASK_COMM_LEN];
	char filename[MAX_FILENAME_LEN];
	bool exit_event;
};

The example program, user side

src/bootstrap.c is the loader. Apart from argument parsing with glibc's argp and a printing callback, it is the standard skeleton lifecycle: open, set read-only data, load, attach, poll, destroy.

#include <bpf/libbpf.h>
#include "bootstrap.h"
#include "bootstrap.skel.h"
/* ... argp options -v and -d, libbpf_print_fn, sig_handler, handle_event ... */

int main(int argc, char **argv)
{
	struct ring_buffer *rb = NULL;
	struct bootstrap_bpf *skel;
	int err;
	/* ... argp_parse, libbpf_set_print(libbpf_print_fn), SIGINT/SIGTERM handlers ... */

	/* Load and verify BPF application */
	skel = bootstrap_bpf__open();
	if (!skel) {
		fprintf(stderr, "Failed to open and load BPF skeleton\n");
		return 1;
	}

	/* Parameterize BPF code with minimum duration parameter */
	skel->rodata->min_duration_ns = env.min_duration_ms * 1000000ULL;

	/* Load & verify BPF programs */
	err = bootstrap_bpf__load(skel);
	if (err) {
		fprintf(stderr, "Failed to load and verify BPF skeleton\n");
		goto cleanup;
	}

	/* Attach tracepoints */
	err = bootstrap_bpf__attach(skel);
	if (err) {
		fprintf(stderr, "Failed to attach BPF skeleton\n");
		goto cleanup;
	}

	/* Set up ring buffer polling */
	rb = ring_buffer__new(bpf_map__fd(skel->maps.rb), handle_event, NULL, NULL);
	/* ... */
	while (!exiting) {
		err = ring_buffer__poll(rb, 100 /* timeout, ms */);
		/* ... -EINTR on Ctrl-C ends the loop ... */
	}

cleanup:
	/* Clean up */
	ring_buffer__free(rb);
	bootstrap_bpf__destroy(skel);

	return err < 0 ? -err : 0;
}

Every bootstrap_bpf name comes from the generated skeleton, and the skeleton's name comes from the object file name: bpftool takes bootstrap.bpf.o, drops .o, and turns the remaining dot into an underscore. This is the single most important fact when you rename the template. The skeleton generated in the orb begins like this (generated output, not a file in the repository):

A gap in the dependency rules

The prerequisite lists contain $(wildcard %.h). That looks like "depend on the matching header", but wildcard runs when make reads the Makefile, before any pattern is matched. It searches for a file literally named %.h, finds none, and expands to nothing. The effect, verified in the orb after a full build:

$ cd src
$ touch bootstrap.h && make -n          # prints nothing: no rebuild
$ touch bootstrap.bpf.c && make -n      # recompiles BPF object, skeleton, bootstrap.o, binary

If you change struct event in the header and run make, neither side is recompiled, and the old binary keeps using the old layout. Run make clean after editing shared headers, or port libbpf-bootstrap's -MMD -MP dependency generation (it adds -include $(wildcard $(OUTPUT)/*.d) at the end). This is a template you are meant to edit, so treat this as the first improvement to make.

Packaging and CI in the C template

Three ways to get a toolchain

The template offers three development environments so that "install clang and libelf-dev" is never the blocker:

The runtime Docker image

The file named dockerfile is the image users run, and it is tiny:

FROM ubuntu:22.04

WORKDIR /root/
COPY . /root/

RUN apt-get update \
    && apt-get install -y --no-install-recommends libelf1 \
    && rm -rf /var/lib/apt/lists/*

ENTRYPOINT ["/root/src/bootstrap"]

It does not compile anything. It copies the whole build context, including an already-built src/bootstrap, and installs only libelf1, because libbpf is linked in statically and zlib is already in the base image. So docker build only works after make build on the host, which is exactly the order CI uses. The image needs --privileged at run time to load BPF programs:

$ sudo docker run --rm -it --privileged ghcr.io/eunomia-bpf/libbpf-template:latest

Note the image name. The README still says libbpf-template, but since August 2024 (fd14bb1, "fix: docker name should be repo name") the workflow pushes to ghcr.io/${{ github.repository }}, i.e. ghcr.io/eunomia-bpf/libbpf-starter-template for the original and ghcr.io/<you>/<your-repo> for your copy. Whether the old name still resolves could not be checked from the orb (the package API requires a token scope it does not have).

The two workflows

Both workflows trigger on every push to master and skip themselves if the commit message contains [skip ci] or [ci skip]. publish.yml turns each push into a GitHub release:

name: Build and publish

on:
  push:
    branches: "master"

jobs:
  build:
    runs-on: ubuntu-latest
    if: "!contains(github.event.head_commit.message, '[skip ci]') && !contains(github.event.head_commit.message, '[ci skip]')"
    # ...
    steps:
    - uses: actions/checkout@v3
      with:
        submodules: 'recursive'

    - name: Set latest release version
      if:   github.event_name == 'push' && github.ref == 'refs/heads/master'
      id: set_version
      uses: actions/github-script@v6
      with:
        result-encoding: string
        script: |
          /* ... list releases and tags ... */
          if (releases.length === 0) { return "v0.0.1"; }
          /* ... increase_v() bumps the last number of the latest release tag ... */
          const tag = tags.find(tag => tag.commit.sha === context.sha);
          return tag ? tag.name : increase_v(latest_release_tag)

    - name: install deps
      run: |
        sudo apt-get install -y --no-install-recommends \
        libelf1 libelf-dev zlib1g-dev libclang-dev libssl-dev \
        make git clang llvm pkg-config build-essential

    - name: build package
      run:  make build

    - name: Publish
      if:   github.event_name == 'push' && github.ref == 'refs/heads/master'
      uses: softprops/action-gh-release@v3
      with:
          files: |
            src/bootstrap
          prerelease: false
          tag_name: ${{ steps.set_version.outputs.result }}
          generate_release_notes: true

The version logic is simple: the first release is v0.0.1; after that, if the pushed commit already has a tag, that tag is used, otherwise the patch number of the latest release is incremented. Every push to master therefore produces a release with src/bootstrap attached; the original repository is at v0.0.11 (July 2026). If you prefer releases only on tags, change the trigger. Two details to fix when you adopt it: the files: path must name your binary, and the job has a strategy.matrix.target of x86_64-unknown-linux-gnu that no step uses, so the template builds only for the runner's architecture.

docker.yml repeats checkout and make build, then uses docker/build-push-action to build dockerfile for linux/amd64 and push it to the GitHub Container Registry with the workflow's own GITHUB_TOKEN. Its last step echoes steps.docker_build.outputs.digest, but no step has the id docker_build, so it prints an empty line; it is cosmetic.

CI proves compilation, not loading

The verifier only runs when the program is loaded into a kernel. A green build in these workflows says nothing about whether the program passes the verifier on the runner's kernel or on yours. If you want that check, add a step that runs the binary with sudo for a few seconds (GitHub's hosted Ubuntu runners allow passwordless sudo), or use a VM-based kernel test harness. The template does neither.

libbpf-rs-starter-template (Rust)

The Rust template has the same packaging idea but a very different build: there are no submodules and no Makefile logic. Cargo and a build script do everything. The example is not bootstrap but runqslower, originally from the libbpf-rs repository (the crate's author field is still Daniel Xu, one of the libbpf-rs authors), which reports tasks that waited on a CPU run queue for longer than a threshold.

const SRC: &str = "src/bpf/runqslower.bpf.c";

fn main() {
    let mut out =
        PathBuf::from(env::var_os("OUT_DIR").expect("OUT_DIR must be set in build script"));
    out.push("runqslower.skel.rs");
    SkeletonBuilder::new()
        .source(SRC)
        .build_and_generate(&out)

    println!("cargo:rerun-if-changed={SRC}");

build.rs is the Rust counterpart of the whole BPF half of the C Makefile. When Cargo builds the crate it first compiles and runs this script. SkeletonBuilder (from libbpf-cargo) invokes clang on the BPF source, so clang must still be installed, and then generates a Rust skeleton module instead of a C header. The skeleton lands in Cargo's per-build OUT_DIR, and main.rs pulls it in with include!. The libbpf C library itself comes through the libbpf-sys crate (1.4.3, wrapping libbpf 1.4.5 according to its version string), so the libbpf you get is whatever Cargo.lock pins, not a submodule. The vmlinux.h in src/bpf/ is found because it is next to the source file.

There is the same kind of dependency gap as in C: rerun-if-changed lists only the .bpf.c file, so editing runqslower.h alone does not regenerate the skeleton. The upstream libbpf-rs example adds a second rerun-if-changed line for the header.

The BPF program: CO-RE with a type flavor

#include "vmlinux.h"
#include <bpf/bpf_core_read.h>
#include <bpf/bpf_helpers.h>
#include "runqslower.h"

#define TASK_RUNNING	0

const volatile __u64 min_us = 0;
const volatile pid_t targ_pid = 0;
const volatile pid_t targ_tgid = 0;

// Dummy instance to get skeleton to generate definition for `struct event`
struct event _event = {0};

// Kernel 5.14 changed the state field to __state
struct task_struct___pre_5_14 {
	long int state;
};
/* ... maps: start (HASH, pid -> u64 ts), events (PERF_EVENT_ARRAY) ... */
/* ... trace_enqueue(); tp_btf/sched_wakeup and tp_btf/sched_wakeup_new record a timestamp ... */

static inline long get_task_state(struct task_struct *t)
{
	if (bpf_core_field_exists(t->__state))
		return t->__state;

	return ((struct task_struct___pre_5_14*)t)->state;
}

SEC("tp_btf/sched_switch")
int handle__sched_switch(u64 *ctx)
{
	/* TP_PROTO(bool preempt, struct task_struct *prev,
	 *	    struct task_struct *next)
	 */
	struct task_struct *prev = (struct task_struct *)ctx[1];
	struct task_struct *next = (struct task_struct *)ctx[2];
	struct event event = {};
	u64 *tsp, delta_us;
	long state = get_task_state(prev);
	u32 pid;

	/* ivcsw: treat like an enqueue event and store timestamp */
	if (state == TASK_RUNNING)
		trace_enqueue(prev->tgid, prev->pid);

	pid = next->pid;

	/* fetch timestamp and calculate delta */
	tsp = bpf_map_lookup_elem(&start, &pid);
	if (!tsp)
		return 0;   /* missed enqueue */

	delta_us = (bpf_ktime_get_ns() - *tsp) / 1000;
	if (min_us && delta_us <= min_us)
		return 0;

	event.pid = pid;
	event.delta_us = delta_us;
	bpf_probe_read_kernel_str(&event.task, sizeof(event.task), next->comm);

	/* output */
	bpf_perf_event_output(ctx, &events, BPF_F_CURRENT_CPU,
			      &event, sizeof(event));

	bpf_map_delete_elem(&start, &pid);
	return 0;
}

This example teaches more CO-RE than the C template's. The programs are tp_btf ("BTF-enabled raw tracepoints"): their arguments are typed kernel pointers, so next->pid is a direct load the verifier checks with BTF, with no bpf_probe_read. get_task_state() handles a real kernel change: Linux 5.14 renamed task_struct::state to __state. The local type task_struct___pre_5_14 is a flavor; libbpf ignores the ___ suffix and matches it against the kernel's task_struct. On a kernel that has __state, bpf_core_field_exists() is patched to 1 and the other branch is removed as dead code (the mechanism is explained in 06). The dummy global _event exists only so the event type appears in the object's BTF, which makes libbpf-cargo generate a Rust struct for it.

One naming trap, inherited from upstream: trace_enqueue(tgid, pid) compares targ_tgid with the kernel's tgid (process ID) and targ_pid with the kernel's pid (thread ID), while main.rs fills targ_pid from the CLI argument pid and targ_tgid from the argument tid. So the argument called "pid" filters on a thread and the one called "tid" filters on a process. The upstream libbpf-rs example (9680ea7) still crosses the names the same way. Fix them when you adapt it.

The user side and its age

The template's main.rs targets the libbpf-rs 0.20 API. libbpf-rs has moved on: the repository's workspace version was 0.27.2 when this chapter was written, and the 0.24.0 changelog says "Adjusted SkelBuilder::open method to require mutable reference to storage space for BPF object". The upstream version of the very same example shows what changed:

Upstream also switched the BPF side from PERF_EVENT_ARRAY to a ring buffer, moved to clap 4, gets vmlinux.h from the vmlinux crate (a git dependency on libbpf/vmlinux.h at 991dd4b) passed with clang_args, and writes the skeleton into src/bpf/ instead of OUT_DIR. Maps are accessed as fields (skel.maps.events) instead of methods.

Because Cargo.toml says libbpf-rs = "0.20" and Cargo.lock pins 0.20.1, the template still builds exactly as written; Cargo will not jump to 0.24. The cost appears when you want a newer libbpf feature or follow today's libbpf-rs documentation: the moment you bump the version, the skeleton API calls above stop compiling and you rewrite main along the lines of the right-hand tab. The bump_memlock_rlimit call is a leftover from kernels before 5.11, which charged BPF memory to RLIMIT_MEMLOCK; it is harmless on newer kernels.

What was verified for the Rust template

The orb has no Rust toolchain (cargo and rustc are not installed), so the crate was not built for this chapter. To still check the kernel half on the orb's 6.1 kernel, runqslower.bpf.c and runqslower.h were compiled unchanged with the C template's Makefile and loaded by a 20-line throwaway C loader (open, set min_us = 1000, load, attach, poll the perf buffer for 3 s). All three tp_btf programs loaded and attached, and 46 events over 1 ms were reported in the 3 seconds. Whether the libbpf-rs 0.20 user side builds with a current stable Rust compiler was not tested.

A small README inconsistency: it tells Ubuntu users to run make install, but the Rust template's Makefile has only build and clean. Install the packages listed in dockerfile-dev instead (pkg-config build-essential zlib1g-dev clang llvm libelf1 libelf-dev) plus a Rust toolchain from rustup. Its Nix flake goes further than the C one: it uses fenix and naersk to build the crate, so nix run .# builds and runs runqslower.

Start your own project from the C template

The steps below turn the C template into a tool called execsnoop. Steps 3–5 were executed in a scratch copy in the orb: after them, make produced execsnoop and the skeleton defined struct execsnoop_bpf and execsnoop_bpf__open(). A second app was then added with APPS = execsnoop runqslower and also built. Steps 1, 2 and 6 involve GitHub and were not executed.

1. Create the repository

Click Use this template → Create a new repository on the template page, or run gh repo create my-execsnoop --template eunomia-bpf/libbpf-starter-template --public. Your repository starts with one commit. Keep the default branch name master, or edit the branches: trigger in both workflows if you rename it.

2. Clone with submodules and check them

git clone --recursive https://github.com/you/my-execsnoop.git
cd my-execsnoop
git submodule status          # expect lines for bpftool and libbpf
# already cloned without --recursive?
git submodule update --init --recursive

If git submodule status is empty, re-add the two submodules as described in the warning near the top of this chapter. Then install the toolchain (make install on Ubuntu, nix develop, or open the dev container) and confirm that make build && sudo src/bootstrap works before you change anything.

3. Rename the three source files

cd src
git mv bootstrap.bpf.c execsnoop.bpf.c
git mv bootstrap.c     execsnoop.c
git mv bootstrap.h     execsnoop.h
sed -i 's/^APPS = bootstrap/APPS = execsnoop/' Makefile

The base name must be the same for all three: the pattern rules derive execsnoop.bpf.o, execsnoop.skel.h and execsnoop.o from it, and APPS names the final binary.

4. Update the names the skeleton generates

sed -i 's/bootstrap\.h/execsnoop.h/; s/bootstrap\.skel\.h/execsnoop.skel.h/; s/bootstrap_bpf/execsnoop_bpf/g' \
    execsnoop.c execsnoop.bpf.c

bpftool names the skeleton after the object file, so bootstrap_bpf__open() becomes execsnoop_bpf__open(), struct bootstrap_bpf becomes struct execsnoop_bpf, and so on. Also update the argp_program_version and usage strings by hand.

5. Build from clean and run

make clean && make          # inside src/, or `make build` at the top
sudo ./execsnoop -v 2>&1 | head

Always build from clean after editing a shared header (the dependency gap described above). The -v log shows CO-RE relocations and any verifier error.

6. Update packaging and CI

  • src/.gitignore: replace /bootstrap with /execsnoop.
  • dockerfile: ENTRYPOINT ["/root/src/execsnoop"].
  • .github/workflows/publish.yml: files: src/execsnoop.
  • README.md: the image is now ghcr.io/you/my-execsnoop.
  • flake.nix: optionally rename the shell (name = "libbpf-template").

Push to master. The first run of publish.yml creates release v0.0.1 if your repository has no releases yet. If the release or image push fails with a permission error, check the repository's Actions setting for the GITHUB_TOKEN (it needs write access to contents and packages); that setting is outside the template.

7. Replace the program

Now change the logic: new SEC() hooks, new maps, a new struct event. Keep the pattern of one header shared by both sides. To add a second tool, drop in other.bpf.c, other.c and other.h and write APPS = execsnoop other. If you need kernel types newer than 6.1, point the vmlinux/x86/vmlinux.h symlink at vmlinux_71.h, or at a header you dumped from your own kernel.

For the Rust template the equivalent edits are: rename the package in Cargo.toml, rename src/bpf/runqslower.*, change SRC and the output file name in build.rs (the generated module is named after the file: RunqslowerSkelBuilder becomes YournameSkelBuilder), update mod runqslower and the runqslower_bss_types path in main.rs, then the binary path in dockerfile and publish.yml (target/release/<name>). Note that the Rust publish.yml only publishes when github.repository_owner == 'eunomia-bpf': in your copy the release step is skipped until you change that condition. These Rust steps were not executed in the orb.

Benefits and limitations

Benefits

Working build from minute one, with libbpf and bpftool pinned to known commits (C) or crate versions (Rust), so the build does not depend on the distribution's libbpf. A statically linked result that needs only libelf and zlib on the target. Delivery is already wired: a GitHub release and a container image on every push. Three ways to get a toolchain (apt, dev container, Nix). The example programs are well-known libbpf-bootstrap / libbpf-rs code, so tutorials (09) and chapter 06 apply directly.

Limitations

Once generated, your repository no longer receives template fixes. The C build lags libbpf-bootstrap (no bpftool gen object, no header dependency tracking) and vendors 19 MB of headers, defaulting to a 6.1 x86 header. The Rust template pins the 2023 libbpf-rs 0.20 API. CI builds only x86_64 and never loads the program, so verifier failures surface on your machine, not in CI. Small rough edges: the README image name, the empty digest step, the Rust README's missing make install, the owner check in the Rust release step. The Go sibling is unmaintained since 2023.

First improvements worth making

(1) Use $(MAKE) in the top Makefile so -j works. (2) Add -MMD -MP and -include $(wildcard $(OUTPUT)/*.d) so header edits rebuild. (3) Add a CI step that runs the binary under sudo timeout 5 to catch verifier rejections. (4) Add an arm64 runner or a cross-compile job if you ship to ARM servers; the arm64 headers are already in vmlinux/arm64/.

Related work and where to go next

  • libbpf-bootstrap is the upstream of the C template and of the build pattern itself: 06 · BTF, CO-RE and libbpf walks through its Makefile and the skeleton lifecycle in detail.
  • Loader libraries. libbpf-rs, cilium/ebpf and aya are compared in 08 · Ecosystem. aya, unlike libbpf-rs, lets you write the BPF half in Rust too; its project generator (cargo generate with aya-template) plays the same role as these templates for that ecosystem.
  • No loader at all. 10 · eunomia-bpf and its eunomia-template drop the user-space C file: ecc builds a package and ecli runs it. 12 · wasm-bpf moves the user-space half into WebAssembly.
  • Programs to put in your template. 09 · bpf-developer-tutorial has dozens of libbpf programs in the same NAME.bpf.c / NAME.c layout; most drop into src/ with an APPS entry.
  • Old kernels. If your users run kernels without BTF, 13 · bpf-compatible adds BTFHub-based BTF to a libbpf build like this one.
  • BCC's libbpf-tools (iovisor/bcc libbpf-tools) is a larger, production example of the same build style, with dozens of tools and multi-arch vmlinux headers; read its Makefile when your project outgrows one app.

Check your understanding

Q1. On an x86_64 machine, which vmlinux.h does the C template compile against by default?

ARCH maps x86_64 to x86 and VMLINUX := ../vmlinux/$(ARCH)/vmlinux.h. The headers are committed in the template; the symlink picks the 6.1 one, with 6.8 and 7.1 headers available next to it.

Q2. You add a field to struct event in src/bootstrap.h and run make. What happens?

Verified in the orb: touch bootstrap.h; make -n prints nothing. wildcard is evaluated when the Makefile is parsed and looks for a file literally named %.h. libbpf-bootstrap avoids this with -MMD -MP.

Q3. After renaming bootstrap.bpf.c to execsnoop.bpf.c, which function opens the skeleton?

bpftool gen skeleton strips .o and turns the remaining dot into an underscore: execsnoop.bpf → execsnoop_bpf. That is why step 4 of the stepper replaces bootstrap_bpf everywhere.

Q4. The template's Rust code calls skel_builder.open()?. You change Cargo.toml to libbpf-rs = "0.27". What must you expect?

The libbpf-rs 0.24.0 changelog changed SkelBuilder::open, and the upstream example uses open_skel.maps.rodata_data and skel.maps.events. libbpf-cargo still runs clang on the BPF source.

Q5. The template's x86 header and the orb's kernel are both "6.1", yet libbpf logged patched insn #30 ... imm 1416 -> 1400. Why?

Two kernels of the same version built with different Kconfig options have different task_struct layouts. Relocation happens at load time in libbpf, after the skeleton was generated.

Q6. What does the green check mark from the template's publish.yml prove?

The workflow runs make build and uploads src/bootstrap. Nothing executes the binary, so verifier and attach problems are not caught; add a run step if you need that.
